Overview

The palletizing algorithm computes optimal placement operations for sheet parts unloaded by TRUMPF automation units (SortMaster, SheetMaster, etc.). Given a set of palletizing tasks — each describing which parts must be placed, how they may be rotated, and where they may land — the algorithm produces a sequence of palletizing operations that minimises wasted space, avoids collisions, and respects machine constraints.

The algorithm runs up to eight strategies in parallel (varying start corner and positioning direction), evaluates their results with a multi-criteria score, and returns the best.

Source root: source/libraries/palletizing/algorithm/

Top-Level Entry Point

File: include/palletizing/algorithm/TcPalletizingGenerator.h / source/TcPalletizingGenerator.cpp

TcPalletizingGenerator is the single public class exposed by this library. Its constructor receives the full palletizing job; calling generate() returns a TsPalletizingResult.

Strategy Enumeration

TnCreatePalletizingGeneratorsWithFixedStartCornerAndPositioningDirection (in source/generator/) enumerates which (start corner, positioning direction) pairs to try:

Scenario Generators created
No constraints on either All 4 corners × 2 directions = 8 generators
Fixed corner, free direction 1 corner × 2 directions = 2 generators
Free corner, fixed direction 4 corners × 1 direction = 4 generators
Both fixed 1 generator

Each generator is launched via std::async so all strategies run concurrently. Results are collected and scored; the highest-scoring result wins.

Generator Hierarchy

TcPalletizingGenerator
 └─ (up to 8, parallel) TcPalletizingGeneratorWithFixedStartCornerAndPositioningDirection
       ├─ TcPalletizingGeneratorForSingleRun          (no repetitions)
       ├─ TcPalletizingGeneratorForMultipleRuns       (repetitions > 1)
       └─ TcPalletizingGeneratorWithPalletChange      (layout instance wrapping)

TcPalletizingGeneratorWithFixedStartCornerAndPositioningDirection

File: source/generator/TcPalletizingGeneratorWithFixedStartCornerAndPositioningDirection.*

Selects which concrete generator to use based on the job:

  • Repetition count = 1 → TcPalletizingGeneratorForSingleRun
  • Repetition count > 1 → TcPalletizingGeneratorForMultipleRuns
  • Pallet change required → wraps the above in TcPalletizingGeneratorWithPalletChange

TcPalletizingGeneratorForSingleRun

File: source/generator/TcPalletizingGeneratorForSingleRun.*

The core placement loop. Processes all palletizing tasks in stacking order.

Algorithm

for each palletizingTask (in stacking order):
    for each subTask in task:
        attempt = tryPalletizeOnExistingStack(subTask)
        if not attempt:
            attempt = tryPalletizeOnNewPosition(subTask)
        if not attempt:
            attempt = tryPalletizeWithAdjustedStackingMode(subTask)
        if not attempt:
            recordTaskNotPalletized(subTask)

Three placement strategies per sub-task:

  1. Existing stack addition — TcExistingStackFinder scans all stacks already on the layout and checks whether the sub-task's parts fit on top of one of them.

  2. New position on layout — TcNewPositionOnLayoutFinder searches for a free floor position using one of the three start-point-candidate strategies.

  3. Adjusted stacking mode — If the chosen stacking mode causes a collision, the algorithm tries alternative stacking modes (e.g. flipping from OptionalStackFirst to regular stacking) and retries steps 1–2.

Stack growth modes:

  • Stack Growth Sequentially — packs all parts of a sub-task onto the first compatible stack before moving on.
  • Stack Growth Evenly — distributes parts across multiple stacks to keep heights balanced. Uses cluster analysis (see Cluster-Based Stack Selection) to determine the minimum number of stacks required.

TcPalletizingGeneratorForMultipleRuns

File: source/generator/TcPalletizingGeneratorForMultipleRuns.*

Handles jobs where the same set of parts must be palletized multiple times (repetitions).

Algorithm

  1. First run — delegates to TcPalletizingGeneratorForSingleRun. Records the base stack height for every created stack.
  2. Subsequent runs — for each repetition r:
    • Target height = base_height + r × height_increment
    • For each operation from run 1:
      • Translate the part's position into stack coordinates using the stack-shift offset.
      • If the position has changed relative to run 1 (alternating layout), record the new position.
      • Check for collisions at the new height. If a collision occurs, try to switch the stacking mode (optional → required, or vice versa). If unavoidable, mark the operation with an issue flag.

Key methods:

Method Purpose
determinePalletizingOperationTargetHeightForCurrentRepetition height = base + (rep × increment)
hasPartPositionInStackCoordinatesChanged detects alternating-position layouts
tryAdjustStackingModeIfCollisionOccurs converts optional stacking modes to avoid collision

TcPalletizingGeneratorWithPalletChange

File: source/generator/TcPalletizingGeneratorWithPalletChange.*

Wraps the single-run (or multi-run) generator and handles jobs that span multiple layout instances (pallets).

Algorithm

currentLayoutInstance = 0
remaining = allTasks

loop:
    result = innerGenerator.run(remaining, currentLayoutInstance)
    notPlaced = result.tasksNotPalletized
    if notPlaced is empty: break
    currentLayoutInstance++
    if no more layout instances: break
    remaining = notPlaced
    innerGenerator.resetStateForNewPallet(currentLayoutInstance)

Each pallet change creates a fresh TcPalletizingGeneratorState for the new layout instance; stacks, operations, and issues are accumulated across all instances.

State Management

File: source/generator/TcPalletizingGeneratorState.*

TcPalletizingGeneratorState is the mutable heart of the algorithm. It is shared by all generator layers and updated as placements are made.

Tracked Data

Category Contents
Stacks Sections with their stacks, stack IDs, positioned-stack indices
Operations Palletizing operations with task index, stack-shift offsets, metadata
Issues — tasks Sub-tasks not palletized, with issue type (no position, collision, weight, etc.)
Issues — operations Operations where the unloading device collides with the stack
Weight Per-section loading weight accumulator
Sorting groups Task ordering / grouping state

Rollback

Before attempting a speculative placement, the algorithm saves a snapshot of the state. If placement fails, the state is fully restored. This enables backtracking within a sub-task's strategy loop without side effects.

Task Pre-Processing

Files: source/TnPalletizingTasksOrganization.*, source/TnPalletizingSubTask.*, source/TcPalletizingSubTask.*

Before the main loop runs, tasks are pre-processed:

  1. Stacking order split (TnPalletizingTasksOrganization) — tasks are partitioned into groups that must be stacked together vs. those that may be stacked successively.

  2. Sub-task creation (TcPalletizingSubTask) — each task is decomposed into sub-tasks, where each sub-task contains:

    • The parts to be placed on a pallet (the "to palletize" set).
    • The parts that remain gripped by the unloading device during placement (the "attached" set).

  3. Cluster formation — geometrically equivalent sub-tasks are grouped into clusters (see Cluster-Based Stack Selection).

  4. Rotation symmetry computation (TnAnglesOfRotationSymmetry) — determines which rotation angles produce geometrically equivalent placements, enabling the algorithm to accept rotated alternatives without introducing extra stack positions.

  5. Stack height limits (TnStackHeightComputation) — computes the maximum allowable stack height per section, respecting maxPartsPerStack, part outer curves, and available vertical clearance.

Position Finding

Layout Finder

File: source/newPositionFinder/TcNewPositionOnLayoutFinder.*

Top-level position-finding coordinator. Iterates over sections (in the order determined by TcSectionOrganizer) and delegates to the section finder or sub-unit finder.

for each section (filtered and sorted):
    pos = sectionFinder.find(section, subTask)
    if pos: return pos

    pos = subUnitFinder.find(section, subTask)  // cross-section
    if pos: return pos

return nullopt

After a successful placement, the finder updates all start-point-candidate finders so subsequent searches reflect the new stack.

Section Finder

File: source/newPositionFinder/TcNewPositionOnSectionFinder.*

Checks preconditions for a section (loading weight limit, container type compatibility, part type allowed) and then delegates to TcNewPositionInBoundingBoxFinder.

Bounding Box Finder

File: source/newPositionFinder/TcNewPositionInBoundingBoxFinder.*

Iterates the list of start-point candidates returned by the active TiStartPointCandidatesFinder and validates each via TcValidStartCornerPointFromStartPointCandidateComputer.

candidates = startPointFinder.getStartPointCandidates()
for each candidate in candidates:
    result = validStartCornerComputer.compute(candidate)
    if result.isValid:
        return result.position
return nullopt

Unloading Area Sub-Unit Finder

File: source/newPositionFinder/TcNewPositionOnUnloadingAreaSubUnitFinder.*

Handles the special case where a part is large enough to span multiple sections of the same unloading area sub-unit (e.g. a long sheet that bridges two cart zones). Checks that the part's centre of gravity does not tilt over section boundaries and computes per-section positions for each element of the parts layout.

Valid Start Corner Computer

File: source/newPositionFinder/TcValidStartCornerPointFromStartPointCandidateComputer.*

For a given start-point candidate, performs all final validation checks before accepting the position:

  1. Compute position offset (TcOffsetComputer).
  2. Validate placement is inside the bounding box.
  3. Compute movable-entity positions (cart, unloading device arm).
  4. Check reachability of the Y position given movable-entity constraints.
  5. Perform collision check with interference items and containers.
  6. Validate part centre of gravity is within safe bounds.

Returns nullopt if any check fails.

Start Point Candidates

The TiStartPointCandidatesFinder interface abstracts three independent strategies. The factory (TnStartPointCandidatesFinderFactoryCreation) selects the strategy at construction time based on job configuration.

Strategy When used Key characteristic
Bounding box-based Default Grid-aligned, staircase boundary
Contour-based (NFP) When container collision enabled Polygon-aware, TOPOS sorting
Pile-based When stack collision allowed Allows overlapping, resets when exhausted

Bounding Box-Based Strategy

Files: source/startPointCandidatesFinder/boundingBoxBased/

Places stacks in a rectangular grid. Maintains a staircase polygon — a monotone rectilinear boundary of already-placed stacks — and only offers candidates on or adjacent to that boundary.

Staircase Polygon

When a stack is placed at position P, new start-point candidates are generated at P + (stack_width, 0) and P + (0, stack_height) (adjusted for positioning direction). Candidates that fall inside the staircase (already blocked) are removed.

Offset Computation (TcBoundingBoxBasedOffsetComputer)

Computes the offset from the candidate point to the actual part reference corner:

  • Maintains minimum clearance between stacks (minDistanceBetweenStacks).
  • Maintains minimum clearance between stacks and the unloading device.
  • Handles the special case where the unloading device is positioned between stacks.

State Update

After each successful placement, updateState() is called. It adds the new bounding box to the internal set of occupied boxes and computes which candidate points to add or remove from the staircase.

Contour-Based Strategy (No-Fit Polygon)

Files: source/startPointCandidatesFinder/contourBased/

Based on the TOPOS algorithm (see doc/startPointCandidatesFinder/contourBased/topos_a_new_constructive_algorithm_for_nesting_problems.pdf). Uses no-fit polygons (NFPs) to compute the exact set of positions where a new part would not collide with any existing stack.

No-Fit Polygon

An NFP for part A relative to obstacle B is the Minkowski difference of A and B: the set of reference-point positions where A would touch B. Any position inside the NFP is a collision; valid positions lie outside all NFPs and inside the inner-fit polygon (IFP), which is the region where A fits inside the container.

Computation:

  • NFPs are computed via TcNoFitPolygonHolder (with caching and mutex-protected lazy initialisation).
  • The NFP for a stack is the union of the NFPs of all unique parts in that stack.
  • Container interference regions (fixed obstacles inside the pallet area) contribute additional forbidden zones (TnContainerInterferenceRegionsWithTranslation).

Valid region:

validRegion = IFP \ union(all NFPs)

Candidate points are extracted as the vertices of the boundary of validRegion.

Sorting (TcContourBasedStartPointCandidatesSorter)

Candidates are sorted using the TOPOS priority order:

  1. Minimise area of the bounding union of existing stacks ∪ new part.
  2. Minimise perimeter of the same union (tiebreaker for equal area).
  3. Maximise overlap area (pack tightly against existing stacks).
  4. Fallback to the start-corner / positioning-direction preference.

Caches

  • TcNoFitPolygonHolder — caches NFPs keyed by (part geometry, obstacle geometry, distances).
  • TcDiscretizedPolygonHolder — caches discretized polygon outlines for rotated parts and unloading device components (used for fast point-in-polygon tests).

Pile-Based Strategy

Files: source/startPointCandidatesFinder/pileBased/

Wraps TcBoundingBoxBasedStartPointCandidatesFinder but permits stack overlap (piling). When all candidates are exhausted, the finder resets to the base corner of the section, allowing new stacks to be placed on top of existing ones.

Used for jobs where the positioning type explicitly allows stacks to occupy the same floor footprint.

Existing Stack Finder

Files: source/existingStackFinder/

Before searching for a new floor position, the algorithm checks whether the sub-task's parts can be added on top of an already-placed stack. TcExistingStackFinder iterates all occupied sections and stacks and applies TcNewPartOnStackValidator.

Validation (TcNewPartOnStackValidator)

A candidate stack passes validation only if all of the following hold:

Check Description
Part geometry Last part on stack is geometrically equivalent to the new part (accounting for rotation symmetry)
Stack count Current stack count < configured maximum
Stack height New stack height ≤ configured maximum
Loading weight Section/layout weight after addition ≤ limit
Collision No collision of the unloading device with the stack at its new height
Mobility The unloading device can reach the stack position
Stacking order Stacking mode is compatible with the order requirement
Container type Section container type permits this part type
Interference No interference items block the position

Part geometry check (TnPartGeometryOnStackCheck):
Compares the outgoing part (last on stack) with the incoming part. Accepts equal geometries. If the part has rotation symmetry at a specific angle, an incoming part rotated by that angle is also accepted.

Cluster-Based Stack Selection

Files: source/cluster/

Used by the Stack Growth Evenly mode to avoid concentrating all parts on a single stack.

Cluster Formation (TcPalletizingSubTaskCluster)

Sub-tasks are grouped into a cluster when they share identical part geometry (so they can legally stack on each other). Each cluster tracks:

  • The set of member sub-tasks.
  • The minimum number of stacks required for even growth (= ceil(total_parts / maxPartsPerStack)).

Stack Selection (TcStackSelectorByCluster)

When selecting which existing stack to grow, TcStackSelectorByCluster:

  1. Determines the cluster for the current sub-task.
  2. Queries the cluster for the minimum required stacks.
  3. From the available stacks for this cluster, picks the one that keeps growth most even (lowest current height / fewest parts).

This prevents degenerate cases where all repetitions pile onto one stack.

Section Organizer

Files: source/sectionOrganizer/

Sections are not searched in arbitrary order. TcSectionOrganizer filters and sorts them before position finding.

Filtering (TcSectionValidator)

A section is excluded if:

  • Inside/outside machine constraint doesn't match (e.g. part must go outside, section is inside).
  • The section belongs to an exclusive sorting group that already contains parts of a different group.
  • The stacking mode requires a sorting group and the section has none.

Sorting (TcSectionComparator)

Sections are ordered by a lexicographic key:

  1. Sorting group membership — preferred group first, then group-compatible, then ungrouped.
  2. Inside/outside machine — respects job preference.
  3. Across-section optimisation — sections where cross-section palletizing is possible are preferred when that is beneficial.
  4. Layout order — fall back to the physical layout position of the section.

Sorting Group State (TcSortingGroupsWithState)

Tracks which parts (and which sorting groups) have been placed in each section. Updated after every successful palletizing operation so that subsequent section validation has accurate occupancy data.

Offset Computation

Files: source/offset/

The offset is the vector from a start-point candidate to the actual position where the part reference corner lands after applying all clearance constraints.

TcOffsetComputer

Computes the offset in two steps:

  1. Complement-corner direction — pushes the part toward the complement corner (opposite to the start corner) to maximise use of the section.
  2. Clearance enforcement — adjusts the offset so that:
    • Minimum distance between adjacent stacks is maintained.
    • Minimum distance between stack and unloading device is maintained.
    • Movable unloading-area unit limits (cart travel range) are not exceeded.

Partial Outside Palletizing (TnOffsetToPalletizePartiallyOutsideOfBoundingBox)

Some jobs allow parts to overhang the bounding box edge. This utility computes how much overhang is permissible and adjusts the offset accordingly so the part centre of gravity remains supported.

Start Point Candidate Boundary Validation (TnStartPointCandidate)

Checks whether a candidate point is on the valid boundary of the staircase polygon (bounding-box strategy) or the NFP complement (contour strategy), and discards points that have drifted off the boundary after an offset is applied.

Bounding Box Coordinate System

Files: source/bbToPalletizeIn/

All position computations work in a bounding-box-local coordinate system with origin at the start corner and axes aligned with the positioning direction. This decouples the algorithm from the physical machine coordinate system.

Components

File Responsibility
TnBoundingBoxToPalletizeInDetermination Computes the actual bounding box (the region within the section that may be used)
TnBoundingBoxToPalletizeInCoordinates Transforms points between machine coordinates and bounding-box-local coordinates
TnBoundingBoxToPalletizeInDataDetermination Aggregates bounding box, offsets, and reference data into TsBoundingBoxToPalletizeInData
TsBoundingBoxToPalletizeInData Data structure passed through position-finding pipeline

Rotation Symmetry

Files: source/rotationSymmetry/

Irregular parts may be rotationally symmetric (e.g. a square is symmetric at 90°). If a part is symmetric at angle θ, placing it at rotation φ is geometrically equivalent to placing it at φ + θ. The algorithm exploits this to accept more stack combinations.

Computation (TnAnglesOfRotationSymmetry)

Runs in parallel threads. For each part in the job:

  1. Collect all rotation angles already used for that part across all stacks and tasks.
  2. For each pair of angles, compute the difference.
  3. Check if the part geometry is invariant under that difference (i.e. the rotated outline matches the original).
  4. If yes, record the angle as a symmetry angle.
  5. Also considers unloading devices that can rotate by 90°: adds 90° steps if the device permits.

Results are stored in TcPartsToAnglesRelation (part → set of symmetry angles) and used by TnPartGeometryOnStackCheck during existing-stack validation.

Movable Entities

Files: source/movableEntities/

Some unloading devices and carts can move during a palletizing operation. The algorithm must verify that the device can reach the target position.

TcReachablePositionYWithMovableEntitiesComputer

Given the current cart / arm configuration and the target placement position, computes whether the Y coordinate is reachable. Considers:

  • Cart travel limits along the X axis.
  • Arm extension limits along the Y axis.
  • Interaction between cart position and arm extension (the reachable Y is a function of X).

TnBoundingBoxToPalletizeInPosition

Converts a position from bounding-box-local coordinates back to machine coordinates, then queries TcReachablePositionYWithMovableEntitiesComputer to verify reachability.

TsMovableEntitiesPositions / TsMovableEntitiesPositionsComputationData

Thin data holders representing the computed positions of all movable entities (cart, arm, vacuum gripper) for a given candidate placement.

Constraint Checkers

Collision Checker (TcCollisionWithInterferenceItemsChecker)

Implements TiCollisionWithInterferenceItemsChecker. Checks:

  • Whether the unloading device (in its computed position for a candidate placement) intersects any fixed interference items or existing stacks.
  • Whether the parts layout (in the candidate position) intersects container walls or other interference regions.

Accepts a map from stack ID → current height so collision checks use the actual stack heights, not the defaults.

Loading Weight Checker (TcUnloadingAreaLoadingWeightChecker)

Implements TiUnloadingAreaLoadingWeightChecker. Validates that adding the new part's weight to a section, layout, or unloading area unit does not exceed the configured limit.

Evaluation and Strategy Selection

File: source/TnPalletizingEvaluation.*

After all parallel strategies complete, results are ranked by a lexicographic score (lower = better):

Priority Criterion
1 (most important) Number of sub-tasks not palletized
2 Number of operations with issues (e.g. unavoidable unloading-device collision)
3 Number of pallet changes
4 Number of stacks on the last unloading area
5 (least important) Total area of sections containing stacks

The first strategy that achieves a strictly better score wins. In case of a tie across all criteria, the strategy with the lowest index (i.e. the first enumerated) is returned.
