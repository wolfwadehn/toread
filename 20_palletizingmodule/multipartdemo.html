LST Palletizing-Data Reader — Algorithm Documentation

LST Palletizing-Data Reader — Algorithm Documentation

Entry point: TnPalletizingData::readFromLst(path) → TcSheet
Core class: TcReadFromLst (source/libraries/lstdata/fromlst/algorithm/source/)

1 Functional view

What the algorithm does

readFromLst parses one TRUMPF LST file and returns a fully populated TcSheet — a description of every cut part on a metal sheet together with where, when, and how the robot arm must pick each part off the laser table and deposit it on the pallet.

The returned TcSheet contains a flat list of TcStackItem objects, one per cut part. Each item carries:

Property Meaning
getRemovalNumber() Which simultaneous lift this part belongs to (all parts with the same number are gripped at once)
getPalletizingSequenceNumber() Which pass of the sheet this part belongs to (multi-cycle sheets only)
getPartCenterOfGravityInSheetCoordinates() Where the part sits on the raw metal sheet
getPartRotationAngle() The part's rotation on the sheet (degrees → radians)
getPartType() finishedPart, wastePart, scrapSkeleton, etc.
getStackingOperation() Where the part must go (pallet target position, stack column, stacking mode)
getUnloadingDevicePositionAndRotationRelativeToPart() How the suction arm must be positioned relative to this part

LST file structure (relevant tables)

The LST is a structured text file. The algorithm reads seven named tables:

Table Contains TRUMPF concept
EINRICHTEPLAN_INFO Machine name, sheet name, layout ID, repetition count Setup plan header
SHEET_TECH Sheet thickness, material density Material properties
PROGRAMM Part geometry (geo blobs), one row per part type Cutting program
PARTS_IN_PROGRAM One row per distinct part type on this sheet; palletizing thickness Part catalogue
PARTS_PALLET_DATA PAPA records — one row per removal operation; stacking mode, stack ID, device type, destination coordinates Palletizing operations
PARTS_IN_PROGRAM_POS PAUD records — one row per individual part instance; sheet coordinates, removal number, PAPA/PAUD name links Part positions
PARTS_UNLOAD_DATA Suction-arm lift offsets and angles, one row per PAUD record Unloading mechanics

The PAPA / PAUD hierarchy

Every cut part is identified by a PAUD name (Part Unload Data). Each PAUD belongs to exactly one PAPA (Part Palletizing). A PAPA describes one removal operation — the arm lifts all PAUDs of the same PAPA simultaneously.

PAPA_0001  ←── removal group 1 (2-part lift)
  ├── PAUD_0001
  └── PAUD_0002

PAPA_0002  ←── removal group 2 (2-part lift)
  ├── PAUD_0003
  └── PAUD_0004

PAPA_0003  ←── removal group 3 (4-part lift)
  ├── PAUD_0005
  ├── PAUD_0006
  ├── PAUD_0007
  └── PAUD_0008

Coordinate derivation by device type

The LST does not store the part's target position on the pallet directly. Instead it stores the unloading device's target position (where the suction arm moves to) plus the arm's offset relative to the part's centre of gravity. The algorithm inverts this relationship per device type:

Device How partCOGInDestination is derived
SortMaster partCOG = deviceTarget − liftOffset; if device has a rotation angle, rotate the result around the device target point
SortMasterCompact Same subtraction, but the Y-axis of the lift offset is negated first (coordinate-system flip)
SortMasterSpeed partCOG is stored directly in fields 350/360 of PARTS_PALLET_DATA; no inversion needed

Build order (dependency graph)

SHEET_TECH            →  m_sheetThickness
PROGRAMM              →  m_mapPartTypeIndexToRegion   (geo blobs → region outlines)
PARTS_IN_PROGRAM      →  m_mapPartTypeIndexToPart     (part catalogue)
PARTS_UNLOAD_DATA     →  m_mapPaudNameToUnloadingDevicePositionAndRotationRelativeToPart
PARTS_IN_PROGRAM_POS  ─┐
PARTS_PALLET_DATA      ┘→  m_mapPapaPaudNameToStackingOperation
                             (destination COG derived here, PAPA↔PAUD map used)
PARTS_IN_PROGRAM_POS  →  m_stackItems   (assembles all maps into TcStackItem list)
EINRICHTEPLAN_INFO    →  m_machineSPtr, sheetName, layoutId, repetitionCount

2.1 Entry wrappers (TnPalletizingData.cpp)

TcSheet readFromLst( const std::filesystem::path& t_lstFile )
{
  TcReadFromLst lstReader;          // Create a fresh stateful reader
  return lstReader.read( t_lstFile ); // Parse and return the completed sheet
}

readRelevantDataAndFileFromLst is identical but also returns the raw parsed TiFile handle (needed by write-back operations in the conversion pipeline).

517: TcSheet TcReadFromLst::read( const std::filesystem::path& t_lstFile )

2.6 readUnloadingDevicePositionsAndRotationsRelativeToPart — step 4 (lines 769–802)

Populates m_mapPaudNameToUnloadingDevicePositionAndRotationRelativeToPart (paudName → list of TsUnloadingDeviceComponentPositionAndRotationRelativeToPart).

772:   const std::string tableName = "PARTS_UNLOAD_DATA";
773:   const long fieldIdName = 30;
774:   const long fieldIdUnloadingDeviceId = 70;

PARTS_UNLOAD_DATA has one row per PAUD record. Field 30 is the PAUD name. Field 70 identifies the device type as an integer (decoded by TnUnloadingDevice::getFromId).

783:     auto unloadingDevicePositionAndRotationRelativeToPart =
784:       getUnloadingDevicePositionAndRotationRelativeToPart( dataSet, unloadingDevice );

Dispatches to a device-specific function:

SortMaster (getSortMasterPositionAndRotationRelativeToPart, lines 370–385):

  • Field 40/50: lift offset X/Y relative to part COG (in mm)
  • Field 60: angle difference between device and part rotation (degrees → radians)
  • Returns a single TsUnloadingDeviceComponentPositionAndRotationRelativeToPart with m_unloadingDeviceComponent = nullopt (no named shuttle — it is a single-arm device)

SortMasterCompact (getSortMasterCompactPositionAndRotationRelativeToPart, lines 388–403):

  • Same field 40/50 for the offset, but negates Y before storing
  • Angle difference is always 0.0 (this device does not rotate)
  • Returns a single component, m_unloadingDeviceComponent = nullopt

SortMasterSpeed (getSortMasterSpeedSuctionShuttlePositionsRelativeToPart, lines 335–367):

  • Field 640: transport-and-palletizing-mode flag; if not 2 (= palletizing), returns empty vector (this console is not used for palletizing)
  • Field 480: console's X offset relative to part COG (shared by all three shuttles of this console)
  • Fields 500, 520, 540: Y offset for shuttle 1, 2, 3 respectively
  • Field 470: console number (1 or 2); combined with shuttle number → TeUnloadingDeviceComponent enum (identifies which of the 6 possible shuttles on the SMS this is)
  • Returns up to 3 TsUnloadingDeviceComponentPositionAndRotationRelativeToPart entries, one per shuttle
786:     if(
787:       TeUnloadingDevice::sortMasterSpeed == unloadingDevice
788:       && m_mapPaudNameToUnloadingDevicePositionAndRotationRelativeToPart.contains( paudName ) )
789:     {
790:       // Append — SortMasterSpeed has two consoles, each writing its own PARTS_UNLOAD_DATA row
791:       m_mapPaudNameToUnloadingDevicePositionAndRotationRelativeToPart[ paudName ].insert(
792:         ..., begin, end );

The SortMasterSpeed machine can write two PARTS_UNLOAD_DATA rows per PAUD (one per console). The second row's shuttles are appended to the first, giving the complete list of all active suction points for that part.

2.7 readStackingOperations — step 5 (lines 605–674)

Populates m_mapPapaPaudNameToStackingOperation ((papaName, paudName) → TcStackingOperation).

2.7.1 Build the PAPA → PAUD name map (readMapPapaNameToPaudNames, lines 434–463)

437:   const std::string tableName = "PARTS_IN_PROGRAM_POS";
439:   const long fieldIdPaudName = 210;
440:   const long fieldIdPapaName = 220;

Reads every PAUD row and groups them by their PAPA name. Result stored in m_mapPapaNameToPaudNames:

"PAPA_0001" → { "PAUD_0001", "PAUD_0002" }
"PAPA_0002" → { "PAUD_0003", "PAUD_0004" }

This is needed so that when processing a PAPA row in PARTS_PALLET_DATA, the code knows which PAUDs belong to it.

2.7.2 Process each PAPA record

609:   const std::string tableName = "PARTS_PALLET_DATA";
611:   const long fieldIdStackingMode = 60;
612:   const long fieldIdName = 120;         // PAPA name
613:   const long fieldIdUnloadingDeviceId = 130;
614:   const long fieldIdStackId = 140;
615:   const long fielIdStackShiftOffsetX = 210;
616:   const long fielIdStackShiftOffsetY = 220;

622:     if( isDataSetOfUnloadingOperation( dataSet ) )

isDataSetOfUnloadingOperation (lines 246–261): returns true if field 310 (SMS section ID) or field 80 (SortMaster unit ID) is > 0. Rows with ID 0 are non-palletizing entries (e.g., scrap-removal commands stored in the same table) — they are skipped.

624:     checkIfPalletizingThicknessIsEqualToSheetThicknessIfExists( dataSet );

Field 90 optionally holds the palletizing thickness for this PAPA. If present, it must match m_sheetThickness — mixed-thickness sheets are not yet supported; the algorithm throws rather than produce silently wrong results.

625:     auto papaName = dataSet.getStringById( fieldIdName );
626:     auto stackingMode = TnStackingMode::getFromInt( dataSet.getIntById( fieldIdStackingMode ) );
627:     auto unloadingDevice = TnUnloadingDevice::getFromId( dataSet.getIntById( fieldIdUnloadingDeviceId ) );
628:     auto destinationRegionId = getDestinationRegionId( dataSet, unloadingDevice );
629:     auto stackId = static_cast<TyStackId>( dataSet.getIntById( fieldIdStackId ) );
  • stackingMode: integer from field 60 decoded to TeStackingMode (deposit, drop, dropSoftly, etc.)
  • unloadingDevice: integer from field 130 decoded to TeUnloadingDevice (sortMaster, sortMasterCompact, sortMasterSpeed)
  • destinationRegionId: for SortMaster → field 80 (unloading area unit ID); for SMS/SMC → field 310 (section ID within the area). Different devices address the pallet location at different granularity.
  • stackId: the vertical stack column; parts stacked on top of each other across multiple removal operations share the same stackId
631:     auto structsPartCenterOfGravityAndRotationAngleRelativeToPaudName =
632:       getPartCenterOfGravityAndRotationAngleInDestinationRegion( dataSet, unloadingDevice );

Derives the part's target position on the pallet for each PAUD in this PAPA. Device-specific:

  • SortMaster (determinePartCenterOfGravityAndRotationAngleInDestinationRegionFromUnloadingDevicePositionAndRotation, lines 883–929):

    • Reads device target position from fields 30/40 and device rotation angle from field 50
    • For each PAUD under this PAPA, fetches the lift offset vector (from m_mapPaudNameToUnloadingDevicePositionAndRotationRelativeToPart)
    • Computes partCOG = deviceTarget − liftOffset
    • If deviceRotation ≠ 0: rotates partCOG around the device target point by the device rotation angle. This accounts for PAPA operations where the arm rotates while depositing — the part ends up at an angle on the pallet.
    • partRotationAngleInDestination = deviceRotation − angleDiffDevicePart

  • SortMasterCompact (determinePartCenterOfGravityInDestinationRegionFromSortMasterCompactPosition, lines 932–953):

    • Uses field 30 as negative X and field 200 (suctionFrameOffsetY) as Y for the device target, then subtracts the (Y-negated) lift offset
    • Rotation is always 0.0

  • SortMasterSpeed (determinePartCenterOfGravityInDestinationRegionForSortMasterSpeed, lines 956–982):

    • Part COG read directly from fields 350/360 — no inversion from device position
    • All PAUDs in the PAPA share the same destination COG and rotation 0.0
634:     for( const auto& structPartCenterOfGravity... : structsPartCOGAndRotation )
635:     {
636:       const auto& pairPapaPaudName = std::make_pair( papaName, paudName );
640:       const auto& existingStackingOperationSPtr =
641:         findStackingOperationInMapWithGivenPapaNamePartCenterOfGravityAndRotationAngle( ... );

findStackingOperationInMapWithGivenPapaNamePartCenterOfGravityAndRotationAngle (lines 482–514): checks if an identical TcStackingOperation (same PAPA, same destination COG within 0.01 mm, same angle) already exists in the map. This handles layered stacking: when removal group 4 lands parts on the same stack columns as removal group 2, the two groups produce identical TcStackingOperation objects — the algorithm shares the pointer rather than creating a duplicate, so getStackId() returns the same physical column ID for both.

648:       if( existingStackingOperationSPtr )
649:         m_mapPapaPaudNameToStackingOperation[ pairPapaPaudName ] = existingStackingOperationSPtr;
650:       else
651:       {
652:         // First time this (papaName, destination) combination is seen — create new operation
653:         auto stackingOperationSPtr = std::make_shared<TcStackingOperation>(
654:           stackingMode, destinationRegionId, stackId,
655:           partCOGInDestination, partRotationAngleInDestination,
656:           destinationRegionType,
657:           TnGeometry::TyPoint2D( stackShiftOffsetX, stackShiftOffsetY ) );
658:         m_mapPapaPaudNameToStackingOperation[ pairPapaPaudName ] = stackingOperationSPtr;
659:       }

stackShiftOffset (fields 210/220): a mechanical offset applied when stacking multiple layers in the same column — some machines shift each new layer slightly to improve stack stability. Stored as-is; not used in the COG calculation.

2.9 readMachine — step 7 (lines 751–766)

754:   const long fieldIdMaschineName = 10;
755:   const long fieldIdMaschineViewerName = 280;

Both names come from EINRICHTEPLAN_INFO. Field 10 is the machine code (e.g., "L76"); field 280 is the human-readable viewer name (e.g., "TruLaser 5030 (L76)"). If the table is missing or empty, m_machineSPtr remains nullptr — the caller must check getMachineSPtr() before dereferencing.

2.10 readSheet — step 8 (lines 547–554)

549:   auto density = getMaterialDensityInKgPerCubicMm( t_fileAccessor );

getMaterialDensityInKgPerCubicMm (lines 64–81): field 260 of SHEET_TECH, unit kg/m³ divided by 10⁹ to convert to kg/mm³.

550:   auto repetitionCount = getSheetRepetitionCount( t_fileAccessor );

Field 100 of EINRICHTEPLAN_INFO. If absent or ≤ 0, defaults to 1. Repetition count > 1 means the same sheet program is run multiple times — used by the downstream palletizing algorithm to compute total part counts.

551:   auto layoutId = getPalletizingSectionLayoutId( t_fileAccessor );

Field 340 of EINRICHTEPLAN_INFO. Identifies which unloading area layout this sheet is configured for. If absent (older machines), defaults to layout 1.

552:   auto sheetName = getSheetName( t_fileAccessor );

Field 110 of EINRICHTEPLAN_INFO — the original LST filename as stored in the setup plan header.

553:   return TcSheet( m_sheetThickness, density, repetitionCount, m_stackItems, m_machineSPtr, layoutId, sheetName );

All accumulated data bundled into a single immutable value object. TcSheet does not own the reader maps — it takes m_stackItems by copy and the TyMachineSPtr shared pointer.
