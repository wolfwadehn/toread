Project Overview

Palletizing is a C++20 library and application for computing optimal palletizing operations for TRUMPF automation units (SortMaster, SortMaster Speed, SortMaster Compact, SheetMaster). It handles sheet material unloading and placement algorithms.

Build Commands

Windows (Visual Studio 2026):

buildinfrastructure\localbuildscripts\build_vs.bat

Windows (Clang / GCC):

buildinfrastructure\localbuildscripts\build_clang.bat
buildinfrastructure\localbuildscripts\build_gcc.bat

Each script creates a build directory (e.g., build/vs), runs CMake, builds in Release, and installs artifacts to install/.

Run tests (must run INSTALL first — TnApplicationMain integration tests need data/ at build/vs/Release/data/):

cmake --build build\vs --config Release --target INSTALL
ctest.exe --test-dir build\vs -C Release --progress --parallel 10

Run a single test binary (after building, executables land in ${PROJECT_BINARY_DIR}):

.\build\vs\<LibraryName>Tests.exe --gtest_filter=<TestSuite>.<TestName>

In-source builds are forbidden — CMake will error if you try.

Architecture

The codebase follows a strict layered architecture. Dependencies only flow downward:

Layer Libraries
Application applicationcontrol, palletizing (app)
Domain / Algorithm palletizing (lib), unloadingarea, unloadingdevice, kernel, mathematics, validitycheck
Conversion / Persistence conversion, persistency, simulation, lstdata, reporting
Infrastructure config, jsonutility, infrastructure

Execution flow:

  1. Parse CLI options (cxxopts) → load data/config/default.json
  2. Read input: LST format or JSON palletize-job
  3. Convert to kernel model (conversion)
  4. Run palletizing algorithm (palletizing)
  5. Validate results (validitycheck: weight, procedure, completeness)
  6. Generate simulation model (simulation)
  7. Serialize output as JSON (persistency)

Key domain concepts:

  • kernel — core model types: parts, materials, layouts, palletizing tasks
  • palletizing — stacking-mode handling and the main placement algorithm
  • mathematics — geometry algorithms, coordinate transformations, intersection detection
  • unloadingdevice / unloadingarea — models for the physical unloading hardware and its sections
  • lstdata — TRUMPF-internal LST file format reading/writing

Prefix Meaning

Code Style

Formatting is enforced via .clang-format (LLVM-based, C++17 style). Static analysis rules are in .clang-tidy. Run clang-format before committing — the CI pipeline treats warnings as errors (/WX on MSVC, -Werror on GCC/Clang).

Compiler settings (in cmake/CompileOptions.cmake):

  • C++20 required
  • /permissive- (MSVC strict C++ conformance)
  • Hidden symbol visibility by default; explicit export headers generated per library

Adding a New Library

Use source/libraries/libtemplate/ as a reference — it contains a checklist and the standard directory layout (include/, source/, test/). CMake targets follow the Trumpf.Palletizing.<LibraryName> naming convention and export headers are generated automatically.

Testing

Each library has a test/ subdirectory using Google Test. Test data lives in test/testdata/. Tests have a 20-second timeout. The CI runs all three toolchains (MSVC, GCC 15, Clang 21) in parallel.

Runtime Data

The data/ directory must be co-located with the executable at runtime:

  • data/config/default.json — default application configuration
  • data/unloadingarea/ and data/unloadingdevice/ — example device configurations
  • data/swagger/ — Swagger API spec for the JSON models

CMake copies data/ to the build output directory automatically.
