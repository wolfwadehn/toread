TC 08 — Multi-Part Simultaneous Removal: Line-by-Line

TC 08 — Multi-Part Simultaneous Removal: Line-by-Line

Test: TnPalletizingData::readFromLst_L76_part_multipartremoval
Source: source/libraries/lstdata/fromlst/algorithm/test/TnPalletizingDataTest.cpp:426–602
Input: testdata/lstdatafromlstalgorithm/l76_multipartremoval.lst

Physical scenario

The LST file encodes a TruLaser 5030 (L76) sheet with 12 cut parts. The arm does not remove them one at a time — it grabs groups simultaneously. There are 5 removal operations, each lifting 2 or 4 parts at once:

Removal Parts lifted Stack they land on
1 items 1, 2 Stack 1 (layer 1)
2 items 3, 4 Stack 3 (layer 1)
3 items 5, 6, 7, 8 Stack 5 (layer 1)
4 items 9, 10 Stack 3 (layer 2, on top of removal 2)
5 items 11, 12 Stack 1 (layer 2, on top of removal 1)

Stacks 1 and 3 are filled in two passes — the machine interleaves removals to maintain physical access to the sheet. Stack 5 (the 4-part group in the hard-to-reach inner row) is completed in one pass.

Line-by-line

Arrange

426: TEST( TnPalletizingData, readFromLst_L76_part_multipartremoval )
427: {

Google Test macro registering the test in the TnPalletizingData suite. The name directly identifies the machine type and scenario.

429:   const std::string lstFilename = "testdata/lstdatafromlstalgorithm/l76_multipartremoval.lst";

Path to the input LST file, relative to the test's working directory (build/vs/Release/). LST is TRUMPF's binary-adjacent text format encoding the full laser cutting program — part geometry, machine data, and palletizing instructions (PAPA/PAUD records).

Act

432:   const auto sheet = TnLstData::TnFromLst::TnPalletizingData::readFromLst( lstFilename );

The single act: parses the entire LST and returns a TcSheet object. Internally this reads PAPA records (one per removal operation) and PAUD records (one per individual part within a removal), converts the raw LST coordinates into the model's coordinate system, and builds the TcStackItem list. The resulting sheet is the entire parsed state.

Assert — count

435:   const std::size_t expectedNumberOfStackItems = 12;
437:   const auto& stackItems = sheet.getStackItems();
438:   ASSERT_EQ( stackItems.size(), expectedNumberOfStackItems );

getStackItems() returns std::vector<TyStackItemSPtr> — one entry per cut part, not per removal. With 5 removal operations totalling 2+2+4+2+2 = 12 parts, the vector must have exactly 12 entries. ASSERT_EQ (not EXPECT_EQ) stops the test immediately on mismatch; the lines below would dereference vector entries by index and would segfault if the count were wrong.

Dereference all 12 items

440:   const auto& stackItem1  = *stackItems.at( 0 );
441:   const auto& stackItem2  = *stackItems.at( 1 );
       ...
451:   const auto& stackItem12 = *stackItems.at( 11 );

stackItems holds shared_ptr<TcStackItem>, so each *stackItems.at(n) dereferences to a TcStackItem const&. Using at() rather than operator[] adds a bounds check. All 12 references are bound upfront so the remaining assertions can read naturally as stackItem5.getRemovalNumber() rather than verbose repeated vector access.

Removal numbers

453:   ASSERT_EQ( 1, stackItem1.getRemovalNumber() );  // group 1: 2 parts
454:   ASSERT_EQ( 1, stackItem2.getRemovalNumber() );
455:   ASSERT_EQ( 2, stackItem3.getRemovalNumber() );  // group 2: 2 parts
456:   ASSERT_EQ( 2, stackItem4.getRemovalNumber() );
457:   ASSERT_EQ( 3, stackItem5.getRemovalNumber() );  // group 3: 4 parts
458:   ASSERT_EQ( 3, stackItem6.getRemovalNumber() );
459:   ASSERT_EQ( 3, stackItem7.getRemovalNumber() );
460:   ASSERT_EQ( 3, stackItem8.getRemovalNumber() );
461:   ASSERT_EQ( 4, stackItem9.getRemovalNumber() );  // group 4: 2 parts
462:   ASSERT_EQ( 4, stackItem10.getRemovalNumber() );
463:   ASSERT_EQ( 5, stackItem11.getRemovalNumber() ); // group 5: 2 parts
464:   ASSERT_EQ( 5, stackItem12.getRemovalNumber() );

getRemovalNumber() returns the PAPA record index from the LST — a 1-based integer that says "this part is lifted during removal operation N." Parts sharing the same number are gripped by the arm in a single physical movement. The assertions verify that the LST parser correctly grouped all 12 PAUD records back to their parent PAPA records in the right order. Group 3 is the only 4-part simultaneous lift; groups 1, 2, 4, 5 are 2-part lifts.

Palletizing sequence numbers

466:   ASSERT_EQ( 1, stackItem1.getPalletizingSequenceNumber() );
       ...
477:   ASSERT_EQ( 1, stackItem12.getPalletizingSequenceNumber() );

All 12 items have sequence number 1. This field distinguishes which pass of the sheet the part belongs to when a sheet is processed in multiple cycles. Because every part here belongs to the first (and only) processing pass, the value is 1 across the board. The assertion confirms the parser did not accidentally assign different cycle numbers to parts from different PAPA groups.

Tolerance

479:   const double tolerance = 0.001;

One micron — 0.001 mm. All subsequent coordinate comparisons use this as the allowed floating-point error. It is tighter than in some other L76 tests (TC 07 uses exact 0.0; TC 09 also uses 0.0) but realistic for coordinate arithmetic done in double precision on LST-derived values.

Center of gravity in sheet coordinates — items 1–8

These assertions verify where each part sits on the raw metal sheet, before the arm moves it anywhere.

481:   const TnGeometry::TyPoint2D expectedPartCOGInSheetCoordinatesStackItem1( 1154.15, 444.87 );
482:   ASSERT_TRUE( expectedPartCOGInSheetCoordinatesStackItem1.equals(
483:     stackItem1.getPartCenterOfGravityInSheetCoordinates(), tolerance ) );

TyPoint2D::equals() checks both x and y components against tolerance. getPartCenterOfGravityInSheetCoordinates() returns a TcVector2D in machine sheet coordinates (origin at sheet corner, in mm).

The 8 values show the parts arranged in three rows across the sheet:

Items y (mm) Description
1, 2 444.87 Bottom row — removal group 1
3, 4 858.77 Middle row — removal group 2
5, 6, 7, 8 1197.86 Top row — removal group 3 (4 parts) 
485:   const TnGeometry::TyPoint2D expectedPartCOGInSheetCoordinatesStackItem2( 1368.63, 444.87 );

Same y as item 1 (same row), x offset of ~214 mm — the part spacing within the row.

489:   const TnGeometry::TyPoint2D expectedPartCOGInSheetCoordinatesStackItem3( 999.53, 858.77 );
493:   const TnGeometry::TyPoint2D expectedPartCOGInSheetCoordinatesStackItem4( 1314.01, 858.77 );

Middle row. Items 3 and 4 are ~314 mm apart (the parts in this row are wider than in the bottom row).

Top row — 4 parts evenly spaced at ~155 mm intervals: 1227.87 → 1383.46 → 1539.04 → 1694.63.

Center of gravity in sheet coordinates — items 9–12

513:   const TnGeometry::TyPoint2D expectedPartCOGInSheetCoordinatesStackItem9(  1628.49, 858.77 );
517:   const TnGeometry::TyPoint2D expectedPartCOGInSheetCoordinatesStackItem10( 1942.97, 858.77 );

Items 9 and 10 are still in the middle row (y = 858.77) but further right on the sheet (x ~1628, ~1943) than items 3 and 4 (x ~999, ~1314). Items 11 and 12 are in the bottom row (y = 444.87), again further right than items 1 and 2. This confirms that the sheet has 12 distinct part positions — even though some will land on the same destination stack, they start at different locations on the raw sheet.

Stacking operations

530:   const auto& stackingOperationStackItem1  = *stackItem1.getStackingOperation();
       ...
541:   const auto& stackingOperationStackItem12 = *stackItem12.getStackingOperation();

getStackingOperation() returns a shared_ptr<TcStackingOperation>. Dereferencing gives the destination data for that part: which stack to land on, where within the stack, and the stacking mode. Binding all 12 upfront mirrors the stackItem binding above.

Center of gravity in destination — items 1–8

These coordinates are in the destination region's local coordinate frame (the pallet or container unit, not the machine sheet).

543:   const TnGeometry::TyPoint2D expectedPartCOGInDestinationSectionStackItem1( 130.0, 130.0 );
544:   ASSERT_TRUE( expectedPartCOGInDestinationSectionStackItem1.equals(
545:     stackingOperationStackItem1.getPartCenterOfGravityInDestinationRegion(), tolerance ) );

Item 1 lands at (130, 130) in its destination — 130 mm from each edge of the pallet section. This is the first-layer position for stack 1.

547:   const TnGeometry::TyPoint2D expectedPartCOGInDestinationSectionStackItem2( 344.48, 130.0 );

Same y as item 1 (same row on the pallet), x = 344.48. The two parts of removal group 1 are placed side by side on the pallet.

551:   const TnGeometry::TyPoint2D expectedPartCOGInDestinationSectionStackItem3( 180.0, 390.0 );
555:   const TnGeometry::TyPoint2D expectedPartCOGInDestinationSectionStackItem4( 494.48, 390.0 );

Items 3 and 4 land at y = 390 on the pallet (a different row from items 1 and 2), in stack 3. x values are 180 and 494.48.

559:   const TnGeometry::TyPoint2D expectedPartCOGInDestinationSectionStackItem5(   80.0, 600.0 );
563:   const TnGeometry::TyPoint2D expectedPartCOGInDestinationSectionStackItem6(  235.585, 600.0 );
567:   const TnGeometry::TyPoint2D expectedPartCOGInDestinationSectionStackItem7(  391.171, 600.0 );
571:   const TnGeometry::TyPoint2D expectedPartCOGInDestinationSectionStackItem8(  546.756, 600.0 );

The 4 parts of removal group 3 all land at y = 600, equally spaced at ~155.585 mm intervals (80 → 235.585 → 391.171 → 546.756). They go into stack 5, which is not reused by any later group.

Position reuse — items 9–12

575:   // the following stack items 9-12 are stacked on the same positions than stack items 1-4
576:   ASSERT_TRUE( expectedPartCOGInDestinationSectionStackItem3.equals(
577:     stackingOperationStackItem9.getPartCenterOfGravityInDestinationRegion(), tolerance ) );

Item 9 lands at the same destination position as item 3: (180.0, 390.0). This is the second layer placed on stack 3. The test reuses the expected...Item3 variable rather than declaring a new one — confirming via code that the positions are identical, not just numerically close.

579:   ASSERT_TRUE( expectedPartCOGInDestinationSectionStackItem4.equals(
580:     stackingOperationStackItem10.getPartCenterOfGravityInDestinationRegion(), tolerance ) );

Item 10 → same position as item 4: (494.48, 390.0). Together with item 9, this is the second layer of stack 3 from removal group 4.

582:   ASSERT_TRUE( expectedPartCOGInDestinationSectionStackItem1.equals(
583:     stackingOperationStackItem11.getPartCenterOfGravityInDestinationRegion(), tolerance ) );
585:   ASSERT_TRUE( expectedPartCOGInDestinationSectionStackItem2.equals(
586:     stackingOperationStackItem12.getPartCenterOfGravityInDestinationRegion(), tolerance ) );

Items 11 and 12 → same positions as items 1 and 2: (130.0, 130.0) and (344.48, 130.0). These are the second layer of stack 1, placed by removal group 5.

Note the non-obvious mapping: items 9–12 reuse positions 3, 4, 1, 2 — not 1, 2, 3, 4. Stacks are filled inward-first (stack 3 gets its second layer before stack 1), matching the removal order: group 4 targets stack 3, group 5 targets stack 1.

Stack IDs

590:   ASSERT_EQ( 1, stackingOperationStackItem1.getStackId() );
591:   ASSERT_EQ( 1, stackingOperationStackItem2.getStackId() );
592:   ASSERT_EQ( 3, stackingOperationStackItem3.getStackId() );
593:   ASSERT_EQ( 3, stackingOperationStackItem4.getStackId() );
594:   ASSERT_EQ( 5, stackingOperationStackItem5.getStackId() );
595:   ASSERT_EQ( 5, stackingOperationStackItem6.getStackId() );
596:   ASSERT_EQ( 5, stackingOperationStackItem7.getStackId() );
597:   ASSERT_EQ( 5, stackingOperationStackItem8.getStackId() );
598:   ASSERT_EQ( 3, stackingOperationStackItem9.getStackId() );
599:   ASSERT_EQ( 3, stackingOperationStackItem10.getStackId() );
600:   ASSERT_EQ( 1, stackingOperationStackItem11.getStackId() );
601:   ASSERT_EQ( 1, stackingOperationStackItem12.getStackId() );
602: }

getStackId() is the pallet stack column identifier from the LST's PAPA record. It ties a TcStackItem to a physical position on the unloading area unit — parts with the same stack ID are stacked vertically on top of each other across multiple removal operations.

The ID pattern is 1, 1, 3, 3, 5, 5, 5, 5, 3, 3, 1, 1:

  • Stack 1 (ID 1): holds items 1, 2 in layer 1 and items 11, 12 in layer 2
  • Stack 3 (ID 3): holds items 3, 4 in layer 1 and items 9, 10 in layer 2
  • Stack 5 (ID 5): holds items 5, 6, 7, 8 in a single 4-part layer

The IDs skip even numbers (1, 3, 5) because TRUMPF LST uses consecutive PAPA numbering and the three stacks are the 1st, 3rd, and 5th PAPA records in the file. These stack ID assertions are complementary to the destination COG assertions above: COG confirms where on the pallet a part goes; stack ID confirms which vertical column it belongs to.

What the test guarantees end-to-end

  1. The LST parser correctly reads all 5 PAPA records and 12 PAUD records without conflating groups.
  2. Removal grouping is preserved in the model — the removalNumber field faithfully reflects the PAPA sequence.
  3. Sheet coordinates are extracted per-part accurately (tolerance 0.001 mm), even when parts are geometrically close or symmetrically placed.
  4. Destination coordinates are computed correctly in the pallet's local frame for all three stack columns.
  5. Position reuse across removal passes is handled correctly — two separate removal operations targeting the same stack column produce identical getPartCenterOfGravityInDestinationRegion() values, which is what makes physical layering possible.
  6. Stack IDs are correctly propagated from LST PAPA records through the conversion pipeline.
