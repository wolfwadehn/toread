xlate.md

xlate.md

Agentic coding manual for Vulcan's localization system: how UI text is stored, looked up at runtime, and pushed through the XLate tool to produce translated builds. Read this before adding, renaming, or moving any user-facing string.

The big picture

No user-facing string is ever hard-coded as a naked literal in a widget. Instead:

  1. Every displayed phrase lives as a Key, English text line in a plain-text string table (*.txt under a Res\Lang folder).
  2. Code refers to the phrase only by its key — usually derived from an enum member (EMsg.Foo, ECmd.Foo, EMasterMode.Foo, ...) — and calls the .X() extension method to resolve it to display text in the current UI language.
  3. A separate offline tool, Tools\XLate, turns the English string tables into Excel workbooks for human translators, and turns the translators' completed workbooks back into per-language string tables (Res\Lang\<code>\*.txt).

This indirection is what lets LangUtils.Language be flipped at runtime (e.g. in Settings) without touching any code — every .X() call just re-resolves against a different dictionary.

There are two independent, parallel implementations of this mechanism, one per assembly, that don't share state:

Both are keyed the same way and follow the same text-file grammar, so from a "how do I add a string" standpoint you can treat them as one system — just be careful to add the key to the correct assembly's table list (see "Adding a new string" below).

Key format

  • Enum-derived keys: SomeEnum.Value.X() looks up the key "SomeEnum.Value" (built by Enum.ToS(): $"{e.GetType().Name}.{e}", e.g. CAMLib\Utils.cs:721, CUILib\Utils.cs:80). This is what almost all UI code uses — EMsg.* for messages/labels, ECmd.* for command/toolbar text, EMasterMode.* for the top-level mode tabs, etc. Example call sites: Src\RunPage.cs:192,353,364,475,564.
  • Numeric/string keys: "123".X() or id.X() looks up a bare string key. Used for legacy dotted numeric error codes, e.g. HMI_Error.txt / NC_Error.txt use codes like 1.0.1, 1.0.2 (Src\Res\Lang\HMI_Error.txt:2-8) rather than enum names.
  • Multi-segment keys (~N): if the English value contains a literal |, e.g. ECmd.DisplayDefaults, view defaults := User|Preset (Src\Res\Lang\LaserDB.txt:70), XLate treats each |-delimited segment as independently translatable and synthesizes sub-keys code~0, code~1, ... (Tools\XLate\XLate.cs:150-164, 296-298, 453-460). The runtime lookup (LangUtils/CAMLibLangUtils) does not need to know about ~N — it always looks up the whole value string for the base key; the splitting is purely an XLate authoring/translation-spreadsheet concern.

String-table file grammar (Res\Lang\*.txt)

Parsed at runtime by LangUtils.GetTranslationDict (CUILib\LangUtils.cs:26-47) and CAMLibLangUtils.GetTranslationDict (CAMLib\Utils.cs:789+); parsed for spreadsheet generation by XLate.MakeXlate/UseXlate (Tools\XLate\XLate.cs).

Vulcan, 88                                        // Home.txt only: first line is "ProductName, BuildNumber", used by XLate to stamp the spreadsheet title
                                                   // blank lines are ignored
// Home page ---------------------------------------------------------
EMasterMode.Setup, Setup
EMsg.Calibration, Calibration
EMsg.RegistrationInfo, Registration will require an internet connection,+
and will take less than a minute

(Src\Res\Lang\Home.txt:1-19, Src\Res\Lang\Home.txt:221-222)

Rules:

  • Key, value — first comma splits key from value (LANGDELIMITER = ','); the rest of the line (after trimming) is the value.
  • Blank lines are ignored.
  • // comment lines are ignored by the runtime loader, but are not just decoration to XLate: when generating a translator spreadsheet, a // line starts a new merged, greyed-out section-heading row (Tools\XLate\XLate.cs:242-284). If the comment ends with a [imagecode] (e.g. // Editing a Bend-Op [0045]), XLate embeds Tools\XLate\Data\0\<imagecode>.png into the sheet at that point, to show translators where the phrase appears in the UI.
  • Trailing + continues the value onto the next line, joined with \r\n (runtime: CUILib\LangUtils.cs:36-39; authoring: Tools\XLate\XLate.cs:288-291, 480-483). A doubled ++ inserts a blank line between the joined segments (CUILib\LangUtils.cs:37).
  • // STOP as the first line of a file tells XLate use/XLate make to stop processing that file entirely — everything after (or the whole file, if it's the first line) is left untouched/untranslated (Tools\XLate\XLate.cs:223, 240, 470). Not currently used by any table shipped in this repo, but respect it if you see it.
  • Quoted values with embedded punctuation: legacy numeric-keyed tables (HMI_Error.txt, NC_Error.txt) wrap the value in "..." and use := as an internal separator, e.g. 1.0.1,"IPCOM.DLL: not enough ipc memory := " (Src\Res\Lang\HMI_Error.txt:2). Treat these as opaque legacy content — don't reformat them to the plain Key, value style used elsewhere.

Conventions translators (and you) must preserve verbatim

These are enforced/described by the XLate instructions sheet (Tools\XLate\Data\Xlate.txt) and checked in part by XLate.TranslatePhrase (Tools\XLate\XLate.cs:383-420):

  • {0}, {1}, ... — string.Format placeholders. Enum.X(args) / string.Format(e.X(), args) (CAMLib\Utils.cs:730, CUILib\Utils.cs:95) fill these in at call time. XLate's CountFmtSpecs (Tools\XLate\XLate.cs:423-429) hard-fails (Environment.Exit(-1)) if the translated text doesn't have the same count as the English source — never add, remove, or reorder {n} placeholders when editing a value, only the surrounding words.
  • | pipe separators — as above, split into independently-translated segments; the number of |-separated pieces must match between English and any translation.
  • Leading _ on one letter of a word — marks a keyboard mnemonic/access-key (e.g. _Export...); the underlined/shortcut letter may move to a different letter in translation, but the underscore convention itself must be kept.
  • *word* — asterisks mark bold-rendered text in Flux's text renderer; preserve the asterisks around the (possibly re-ordered) translated word.
  • Line-count — multi-line (+-continued) values should keep roughly the same number of lines in translation for UI layout reasons (soft guideline, not enforced — the strict check for this in TranslatePhrase is present but disabled: Tools\XLate\XLate.cs:409 if (mismatch && false)).

Where the tables live, and the fallback chain

  • Base (English) table: Res\Lang\<Table>.txt (e.g. Src\Res\Lang\Error.txt).
  • Per-language override: Res\Lang\<LangCode>\<Table>.txt (e.g. Src\Res\Lang\DE\Error.txt), only containing keys that have a translation; anything missing falls through.
  • CAMLib and CUILib each ship their own Res\Lang tree for their own tables (CAMLib\Res\Lang\CAMLib.txt, CAMLib\Res\Lang\CN\CAMLib.txt, CUILib\Res\Lang\CUILib.txt) — these get merged into Src\Res\Lang\** at package time (see "Packing" below); don't assume Src\Res\Lang\CAMLib.txt is hand-maintained independently from CAMLib\Res\Lang\CAMLib.txt.
  • Runtime fallback order (LangUtils.XLate, CUILib\LangUtils.cs:53-61): look up the key in the current language's dict → if present, non-blank, and not "?", use it → otherwise fall back to the English dict (EnglishName) → otherwise return the raw key string itself (so an untranslated/missing key is visibly wrong in the running UI instead of silently blank — if you see a literal EMsg.Something string on screen, it means the key has no entry in any language table).
  • Currently only CN is actively round-tripped through the XLate pipeline (Tools\XLate\XLate.cs:334 sLangs = { "CN" }), even though Res\Lang has long-since-generated folders for BR, CN, CS, DE, ES, FR, JP, KO. Treat those other language folders as previously-shipped snapshots, not actively maintained by the current XLate make/use all workflow.

Adding a new user-facing string (agent checklist)

  1. Add an enum member for it (or reuse an existing EMsg/ECmd/etc. value) in the appropriate C# file.
  2. Add EYourEnum.NewValue, Your English text as a new line to the correct Res\Lang\<Table>.txt — pick the table (Create, Edit, Error, Home, LaserDB, Run, Settings, CAMLib, CUILib, ...) that matches where the string is used, not just its topic; the runtime only finds a key if the file containing it is in that assembly's active Tables list (see next step).
  3. Confirm that table name is present in whichever Tables array actually gets used by the code path resolving this key: CUILib.LangUtils.Tables (set in Src\HomePage.cs:926) for .X() calls from CUILib/Src/general UI code, or CAMLib.CAMLibLangUtils.Tables (set in Src\HomePage.cs:871) for .X() calls made from CAMLib code. If you add a brand-new table file, add its name to both this array and Tools\XLate\XLate.cs's mStringTables/mStringTables2 arrays (Tools\XLate\XLate.cs:504-505) so it participates in future XLate make/use runs.
  4. Call .X() on the enum value (or the string key) at the point you display it — don't concatenate translated fragments; keep format placeholders/pipes as a single .X(args) call so XLate's structure is preserved.
  5. Make sure the .txt file ships: it must be under a Res\Lang folder that ends up packed into Vulcan.wad (see "Packing" below) — a new table file added only on disk without updating the packing lists (makewad.bat, Tools\ShipVulcan\Program.cs BuildVulcanWad) will build locally but won't ship.
  6. Leave the actual translation blank — that's what the XLate workflow (next section) is for. Don't hand-invent translated text into the per-language .txt files; those are machine-generated from the Excel roundtrip.

Packing into the shipped app

  • CAMLibLangUtils reads its tables from inside Vulcan.wad (a zip archive), not loose files (ZipResource, CAMLib\Utils.cs:793-795) — so a change to a CAMLib-table .txt file has no runtime effect until Vulcan.wad is rebuilt.
  • Vulcan.wad is assembled by merging the Res\ folders of Src, CUILib, and CAMLib (later folders overwrite earlier ones on name clashes) — implemented twice, keep both in sync if you change the merge logic: makewad.bat (xcopy-based) and Tools\ShipVulcan\Program.cs's BuildVulcanWad (Tools\ShipVulcan\Program.cs:23-50).
  • CUILib.LangUtils, by contrast, reads loose files via ResUtils.OpenRead — no wad rebuild needed for those tables during local dev, only for release packaging.

The XLate tool itself

Tools\XLate is a separate legacy .NET Framework 4.5.2 WinExe (Tools\XLate\XLate.csproj, not part of Src\Vulcan.sln), driving Excel via COM interop (Microsoft.Office.Interop.Excel). It is a Windows+Excel-only developer tool, not something CI or a build agent without Excel installed can run. Entry point: Tools\XLate\Program.cs.

XLate make <language>      # build/update a translator-facing .xlsx from the current *.txt tables
XLate make all             # ...for every language in XLate.cs's sLangs
XLate use <language>       # apply a completed .xlsx back onto the per-language *.txt tables
XLate use all
XLate delpics <language>   # strip embedded help-images from a translated .xlsx before committing it

Full workflow (from the header comment in Tools\XLate\XLate.cs:1-28):

  1. During development, new strings are simply added to the English Res\Lang\*.txt files (as above) — no XLate step needed yet.
  2. Before shipping, XLate use all regenerates the foreign-language string tables from whatever translation spreadsheets currently exist. Newly-added English strings that have no translation yet just fall back to English in the shipped UI (per the runtime fallback chain above) — this is expected, not a bug.
  3. XLate make all regenerates the translator spreadsheets: for each table, it reuses any translation already present for existing keys and adds new rows (English filled in, translation cell left blank and colored yellow) for anything new. Help-context screenshots (// ... [code] comments) are re-embedded as images at this point.
  4. The refreshed spreadsheets go out to translation agencies; when they come back (days/weeks later) they're copied into Tools\XLate\Data\<lang>.xlsx, and XLate use all is run again to regenerate string tables with the new translations — this cycle repeats until coverage is complete.
  5. Before committing an updated spreadsheet, run XLate delpics <lang> to strip embedded images (keeps the repo/LFS blob small — images are re-derived from Tools\XLate\Data\0\*.png + the [code] comment markers, not stored redundantly per-language).

Spreadsheet layout produced by make (Tools\XLate\XLate.cs:220-331): one sheet per string table (name = table name uppercased), column B = key/code (never hand-edit), column D = English, column E = the target language, column A holds contextual screenshots. An Instructions sheet (from Tools\XLate\Data\Xlate.txt) and the conventions above (placeholders, pipes, mnemonics, bold-asterisks) are included for the translator's benefit.

Tools\XLate\Data\exclusions.txt lists literal English values that should never be translated (currently just axis names X, Y, Z — Tools\XLate\XLate.cs:370-379); both make and use skip these.

Gotchas for agents

  • Hard-coded dev paths: Tools\XLate\XLate.cs/Program.cs hard-code D:\Work\Vulcan\... throughout (not L:\..., unlike the rest of the build tooling — see the repo's CLAUDE.md for the L:/X: mapped-drive convention). This looks like a stale/inconsistent path baked in from a different dev machine; don't "fix" it without checking with a human, and don't assume XLate.exe will run correctly against this checkout without adjusting those paths first.
  • CAMLib\Text\EN\... is referenced by XLate.cs (mStringTables2 processing, comment at Tools\XLate\XLate.cs:5-6) but that directory does not exist anywhere in this repo — the real CAMLib tables live under CAMLib\Res\Lang\. That code path is effectively dead/no-op against the current layout; don't take the comment as an accurate map of where CAMLib strings live.
  • Two Regenerate concepts, don't confuse them: TestRunner.Regenerate (Tools\TestLib\Testing.cs, driven by CTester -regenerate) rebuilds golden test reference files and has nothing to do with translations. XLate make/use is the localization regeneration. Same word, unrelated systems.
  • Never hand-edit column B (the key) in a translator spreadsheet, and never rename/delete an existing enum-derived key casually — XLate use matches purely by that key string against the spreadsheet; a rename silently orphans the existing translation (it'll just fall back to English until someone re-sends the sheet).
  • Column E in a freshly-made, not-yet-translated spreadsheet is highlighted yellow (Tools\XLate\XLate.cs:311) — that's the "still needs a human translator" signal; don't fill it in with your own guess translation.
