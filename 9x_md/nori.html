C:\Work\Nori is a 2d/3d C# library

Architecture

Project layout / dependency graph

Core (Nori.Core)            platform-neutral core: geometry, drawing entities, mesh, model,
                             sim, IO, base utilities, and the test-runner types themselves
  ↑
Lux (Nori.Lux)               OpenGL scene-graph renderer, platform-neutral — depends only on
  ↑                          interfaces from Core, not on any concrete windowing/GL implementation
Host/GLFW, Host/WPF          platform-specific implementations of Core's Hub interfaces
  (Nori.Host.GLFW/WPF)       (IOpenGL, IDispatcher, IKeyboard, IMouse) — GLFW is cross-platform-
                             capable, WPF is Windows-only
GLU (Nori.GLU)                small OpenGL utility layer used above Host
Test (Nori.Test)             console app + custom reflection-based test runner (depends on Core,
                             Lux, Host/GLFW to get an offscreen GL context)
Tools/Generate (Nori.Gen)    Roslyn source generator, referenced as an Analyzer by Core and Lux
Tools/Console (Nori.Con)     dev CLI (coverage, line-count, id allocation, source cleanup, ...)
Tools/Doc (Nori.Doc)          generates HTML docs from XML doc comments
Tools/Cover (Nori.Cover)     WPF viewer for coverage.xml produced by `Nori.Con COVERAGE`
Demos/*                      GLShell, WPFDemo, ConShell, BenchShell — sample/scratch apps

Nori.slnx (the XML-based solution format, not a classic .sln) is the source of truth for which projects exist and how they're grouped.

Hub: dependency injection for platform services

Core/Base/Hub.cs is a static whiteboard exposing IDispatcher, IKeyboard, IMouse, IOpenGL (interfaces defined in Core/Base/Interface.cs). Core and Lux code depend only on these interfaces. A concrete host (GLFWHost.Init in Host/GLFW/Host.cs, or the WPF equivalent) fills in Hub.* at startup before any rendering happens. This is how Lux stays platform-neutral while still driving real windowing/OpenGL/input on Windows via WPF or cross-platform via GLFW.

Lux scene graph (Lux/Scene, Lux/Buffer, Lux/Shader, Lux/VNodes)

Rendering is organized as a VNode DAG (Lux/Scene/VNode.cs): each VNode can carry drawable geometry (via RBatch/RBuffer, built during Draw() using Lux.Draw calls), can have children (directly, or automated via a ChildSource implementing IAList/IObservable<ListChange>), and can bequeath attributes (color, transform, line type, ...) down its subtree. Scene (Lux/Scene/Scene.cs) owns the tree and drives per-frame rendering; Lux/VNodes/*VN.cs files are concrete VNode types that render specific domain entities (e.g. Dwg2VN renders a Dwg2 drawing, Ent2VN/Ent3VN render entities, MechanismVN renders Sim/Mechanism).

Source generators and code-gen attributes (Tools/Generate, Core/Base/Attributes.cs)

Two generator-driven patterns recur throughout Core/Lux — recognize them rather than hand-implementing the equivalent boilerplate:

  • [Singleton] on a class with a private parameterless constructor generates a thread-safe static It property (Tools/Generate/SingletonGen.cs).
  • [EPropClass] on a class + [EPropField(EProp.X)] TType mField on its backing fields (named with an m prefix) generates a public property (same name minus m) that raises change notifications tagged with the given EProp value when set — a lighter-weight alternative to INotifyPropertyChanged (Tools/Generate/EPropGen.cs).

Core subsystems

  • Core/Geom: 2D/3D geometry primitives (Point, Vector, Matrix, Bound, Poly, Seg, Nurbs, OBB, ConvexHull, FastTess2D tessellator, collision).
  • Core/Drawing: 2D drawing-entity layer (Dwg2, Ent2, dimensions in E2Dim*, snapping/stitching).
  • Core/Model: 3D model layer (Model3, Ent3, Curve3, surfaces, and Tenkai/ sheet-metal flat/flex/bend-pose support).
  • Core/Mesh: triangle mesh representation/build/slicing (Mesh, TopoMesh, CSMesher).
  • Core/Sim: kinematics/collision simulation (Mechanism, OBBTree, OBBCollider, RBRSolver).
  • Core/IO: file format readers/writers — DXF, STEP, STL, PNG, a custom binary/text serialization scheme (AuType/[AuPrimitive], Curl format) used for saving Nori's own object graphs, plus IStmLocator/Lib.OpenRead which resolves virtual paths like nori:GL/point.frag (backed by a zipped Nori.wad resource bundle or a loose folder).
  • Core/Base: cross-cutting utilities — Lib (module-level constants/helpers, Lib.Init() must be called before using the library), Hub, Undo (undo/redo), Ledger<T>, SymTable, collection helpers, and the [Fixture]/[Test]/TestRunner types used by Nori.Test.

Coding conventions worth preserving

  • Method call parens are preceded by a space (Foo (x), not Foo(x)); this is enforced by .editorconfig, not a matter of taste.
  • 3-space indentation, no forced braces on single-line if/for bodies.
  • Most .cs files start with a decorative banner comment naming the file and a one-line purpose (e.g. // ╔═╦╦═╦╦╬╣ Hub.cs); Nori.Con CLEAN can (re)generate/normalize these — don't remove them from existing files.
  • Prefer terse XML <summary> on a single line over multi-line <summary> blocks (the CLEAN command actively collapses 3-line summaries into one line).
  • IDE0130 (namespace-must-match-folder) is disabled: files are organized by subsystem folder, not by namespace — most public types live directly in namespace Nori; regardless of their folder.
