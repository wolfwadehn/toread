CLAUDE.md

C:\Work\Pix is a WPF 2D CAD/CAM application for sheet-metal drawings (DXF/GEO import-export, bend lines, edge notches, dimensioning, cleanup/QA tooling). It is built entirely on top of C:\Work\Nori (see C:\Work\Nori\CLAUDE.md) — Pix contributes no rendering, geometry, or file-format code of its own beyond what's listed below; it is a domain application layered on Nori's Core/Lux/Host. Pix is meant to become the base of a general 2D CAD tool, so this file also captures where today's implementation stops short of that goal (see "Implementation status" at the end).

Relationship to Nori

Pix.csproj references Nori.Core, Nori.Host.WPF, Nori.Lux (via the N: drive alias for C:\Work\Nori) and takes Nori.Gen as an analyzer, so Pix code can use [Singleton] and [EPropClass]/[EPropField] exactly like Nori itself. Pix depends only on Nori's public surface:

  • Dwg2/Ent2/Layer2/entity subtypes (E2Poly, E2Point, E2Text, E2Spline, E2Bendline, E2Dim, E2Leader, E2Insert, E2Solid) from Nori's Core/Drawing
  • Poly/Seg/PolyBuilder/Point2/Bound2 from Core/Geom
  • DXFReader/DXFWriter/CurlReader/CurlWriter from Core/IO
  • Model3/Tenkai (PaperFolder) from Core/Model — used for the 3D folded-part preview
  • UndoStack/UndoStep from Core/Base — all Pix edits are undoable steps
  • Scene2/Scene3/VNode/Lux drawing calls from Lux — Pix's DwgScene is a Scene2 subclass
  • Hub.Keyboard/Hub.Mouse (Rx observables) from Core/Base/Host.WPF — Pix's DwgHub subscribes to these directly rather than re-deriving input handling

Pix follows the same coding conventions as Nori (space before call parens, 3-space indent, banner comments on every file, terse one-line XML summaries, IDE0130 disabled) — see Nori's CLAUDE.md for the specifics; they are not repeated here.

Project layout

Pix.slnx groups the Nori projects under a /Nori/ solution folder and lists Pix, Pix.Test, Pix.Con alongside them.

Core subsystems

Command/Widget dispatch (DwgEdit/DwgHub.cs, Widgets/Widget.cs)

Every drawing command is an ECmd enum value (DwgEdit/DwgCmds.cs). Two dispatch tables are built once via reflection over the loaded assembly:

  • DwgHub.WidgetMap : Dictionary<ECmd, Type> — every concrete Widget subclass must carry a [DwgCmd(ECmd.X)] attribute; missing it is a hard startup exception.
  • DwgHub.MethodMap : Dictionary<ECmd, Action<Dwg2>> — static methods on DwgCmds tagged [DwgCmd(ECmd.X)], for commands needing no interactive input (Grid, LayerSetup, Cleanup).

Toolbar.cs reads Wad/Modes/manifest.txt (an ordered list of ECmd names, blank lines as separators, ;-prefixed lines commented out) to build the icon toolbar; each button looks itself up in WidgetMap/MethodMap and disables/greys out if neither has an entry for that ECmd.

DwgHub is a static whiteboard (mirrors Nori's own Hub pattern) holding the current Dwg2, the active Widget, the DwgSnap instance, and mouse/keyboard mode state. It subscribes directly to Hub.Keyboard.Keys/Hub.Mouse.Clicks/Hub.Mouse.Moves (Rx observables) and demuxes into either the active Widget or an in-progress DragOp (DwgEdit/DragOp.cs, used for things like rubber-band selection).

Widget (Widgets/Widget.cs) is Pix's own multi-phase-input abstraction — distinct from any WPF control. A widget declares its input fields via attributes:

  • [Click(n)] — field set by the n'th mouse click (snapped, unless [Unsnapped])
  • [Textbox(n)] — field editable in the input bar (keyboard-mode entry, @/< prefixes for relative/polar coordinates)
  • [Angle], [NoMouseMove], [Variant(obj)] — display/behavior modifiers
  • Class-level [CanRepeat], [NoKeyboardMode], [NoMouseInput], [AlwaysShowFeedback], [NoSimMouse]

CmdPrompt (DwgEdit/DwgCmds.cs) loads Wad/Modes/cmd-prompt.txt at first use and parses, per ECmd, a display name, input-box labels, and the step-by-step status-bar prompts shown while running the command.

Editing operation base classes (DwgEdit/*.cs)

  • PolyMaker (BaseWidget.cs) — base for single-Poly-producing commands (Line, Arc, Circle, Rect, polygon variants); builds incrementally per phase, draws live feedback, pushes one E2Poly on completion. Supports Ctrl+click "Repeat" of the last-drawn entity from a new anchor.
  • PolyEditor/PolyEditor2 — one-click corner/edge editors (Chamfer, Fillet, InFillet, CornerStep, EdgeRecess, EdgeU, EdgeV, KeySlot): pick a poly, compute a replacement Poly from typed-in parameters, Replace() the old entity. PolyMaker2-style variants (LineParallel, LinePerp) pick a segment then add new geometry alongside it.
  • DwgArranger/DwgLayouter (DwgOps.cs) — transform (Move, Rotate, Scale, Mirror) or copy-in-a-pattern (RectArray, PolarArray) the current selection; Ctrl toggles copy-vs-move.
  • DimMaker — dimension-specific widgets (linear, baseline, continue, angle, angle-3P, radius, diameter, callout, segment) that build E2Dim entities.
  • PolyDiff.cs / PolyOverlap.cs / DwgCleanup.cs — geometric analysis/cleanup: DwgCleaner stitches touching open polylines into closed ones (StitchReduced/StitchReducedSpl), and the Mark*/HighlightOverlaps/RemoveSmallSegs commands flag or fix small segments, overlaps, non-tangent corners, and large radii by writing marker geometry to a dedicated "CleanupMarker" layer.
  • PickMode.cs — PickWidget (selection), MeasureWidget (live distance/angle readout), BendWidget (click a line to add a bend, or an existing bend to edit it via EditBend.xaml).

All entity mutation goes through UndoStep subclasses (ModifyDwgEnts, ModifyEntLayer, ClubbedStep) pushed onto UndoStack.Current. BaseWidget.CreateStitchedAction is the common path for adding polys: when any added entity is an E2Poly, it re-stitches the full add/remove set against the drawing's existing polys per-layer before constructing the final ModifyDwgEnts, so newly drawn geometry automatically joins with abutting existing geometry.

UI layer (Widgets/, WPF/, VModel/, MainWindow.xaml*)

Pix's UI is ad-hoc/imperative, not classic MVVM/bindings. MainWindow hosts a DockPanel with a declarative Menu, a programmatically populated Toolbar, an InputBar for the active widget's fields/prompts, and a central Border whose Child is WPFHost.Init(this, OnLuxReady) — Nori's WPF OpenGL host. Once ready, Lux.UIScene = new DwgScene(dwg) puts the Lux scene graph in that panel.

  • CmdRouter.cs reflects over [CmdSink]-tagged MainWindow methods, wires MenuItem.Click handlers, and derives KeyGestures from the XAML — menu items with no matching sink are disabled.
  • InputBar.cs dynamically builds TextBox/CheckBox/ComboBox controls per active Widget field (via WField), routes typed text to DwgHub.OnTypeIn, and toggles keyboard-mode vs. mouse-mode.
  • UIBuilder.cs's TableEdit is a hand-built Grid-based table control (no DataGrid) driving the Layers dialog and bend-property table; VModel/TableVM.cs supplies rows/columns/cell get-set for it.
  • Dialog XAML files (LayersDlg.xaml, EditLayerDlg.xaml, EditBend.xaml) are near-empty skeletons; content is built in code-behind after Loaded.

Rendering (DwgScene.cs)

DwgScene : Scene2 composes Dwg2VN (the drawing itself) with several auxiliary [Singleton] VNodes: WidgetVN (current widget's feedback), ActiveDraggersVN (in-progress drag operations), DwgGridVN ×2 (major/minor graph-paper grid, fading out when zoomed out), DwgSnapVN/DwgConsLineVN (snap markers and alignment construction lines, driven by DwgHub.Snap/DwgSnap). EditBend also opens a 3D folded-part preview: FoldedPartScene : Scene3 runs Nori's Tenkai.PaperFolder over the current Dwg2 to build a folded Model3, rendered in a picture-in-picture sub-scene (Lux.AddSubScene) — this is Pix's bridge from flat-pattern 2D editing to 3D sheet-metal simulation.

File I/O (IO/GEOReader.cs, IO/GeoWriter.cs)

Pix relies on Nori's own DXFReader/DXFWriter/CurlReader/CurlWriter for .dxf/.curl — it implements no DXF parsing itself. .geo is Pix-specific: a text, section-tagged (#~1, #~31, #~33/#~331, #~37/#~371, ...) sheet-metal interchange format (see Spec/GEO.pdf, likely tied to TRUMPF/MetaCam-family CAM tooling — Spec/metacam.chm is bundled) carrying flat-pattern contours plus bend-line metadata (angle, radius, deduction). GEOReader.Load parses sections into indexed points → PolyBuilder-constructed polys → E2Poly/E2Text/E2Point/ E2Bendline entities in a Dwg2; GeoWriter does the inverse, and unconditionally explodes any E2Insert blocks before serializing (GEO has no block/insert concept).

MainWindow.LoadDwg sanitizes every loaded drawing regardless of source format: a lone top-level E2Insert (or a drawing that is otherwise "effectively" one non-empty top-level insert plus empty ones) is auto-exploded into its constituent entities, and E2Poly entities with non-finite bounds are dropped. This is currently the only place Insert/Block entities are manipulated in Pix — see gaps below.

Testing (Test/) and dev tooling (Tools/Console/)

Pix.Test reuses Nori's own [Fixture]/[Test]/TestRunner reflection-based framework rather than xUnit/NUnit — same attribute style, same runner, same Nori.Con COVERAGE-compatible instrumentation. Widget/WidgetTest.cs drives widgets through simulated clicks/typed input via DwgHub.OnClick/ OnTypeIn (the same entry points real mouse/keyboard events use), so widget tests exercise the full phase state machine, not just the geometry math. IO/GEOReaderTest.cs/GEOWriterTest.cs/ TPixDwg.cs round-trip DXF → Dwg2 → GEO/Curl and diff against TData/ fixtures. Tools/Console/Pix.Con mirrors Nori.Con: CLEAN (banner/summary normalization), COVERAGE, COUNT, NEXTID (test-ID allocation), OPTIMIZE/XMLDOC (csproj flag toggles), plus a Pix-only PNGCRUSH for the toolbar icon set.

Implementation status — commands with icons vs. commands with code

Wad/Modes/manifest.txt (toolbar layout) and the ECmd enum together list 90 commands. Cross-referencing against [DwgCmd(ECmd.X)] usage on Widget subclasses and DwgCmds methods shows roughly 55 have a real handler; the remainder have an icon, a name, and step-prompts in cmd-prompt.txt, but no Widget/DwgCmds entry — the toolbar button exists but is disabled at runtime. This gap is the clearest map of what "finishing the CAD tool" requires:

  • Boolean ops — Union, Intersect, Subtract, Divide: no polygon-boolean/clipping engine exists in Nori's Core/Geom (Poly/ConvexHull/FastTess2D today, but no general polygon clip). This is the single largest missing subsystem for a general-purpose 2D CAD tool.
  • Notch identity — CopyCornerNotch, CopyEdgeNotch, CopyToOtherEdge, CopyArcNotch, MirrorNotch, DeleteNotch: today's EdgeU/EdgeV/EdgeRecess/CornerStep/KeySlot commands bake a one-off geometric edit into the poly with no retained "this is a notch" identity, so there is nothing to copy, mirror, or delete afterwards. Needs a first-class notch/feature concept (or at least a marker/metadata layer) before these commands are implementable.
  • Spline/curve authoring — CreateSpline, PlineToSpline, EditSpline, FitArc, Decurve: E2Spline is already a renderable entity (see BaseWidget.DrawFeedback), but no widget creates or edits one interactively.
  • Dimension completeness — DimHorzOrdinate, DimVertOrdinate, AutoDim, DimSettings: ordinate dimensioning, an automatic dimension-placement command, and a dimension-style/defaults dialog are all absent even though the core DimMaker framework and most dimension types exist.
  • Block authoring — CreateBlock, InsertBlock, ExplodeBlock: E2Insert/block data model and round-trip support already exist (GeoWriter.ExplodeBlock, MainWindow.SanitizeDwg), but purely as automatic load/save behavior — there is no interactive command to define a block from a selection, insert an existing block, or explode one on demand.
  • Construction variants — LineFillet, LineTangent, CircleTTR, CircleTTT, Fillet3T, Offset, OffsetSeg, RoughTrim, Join: near-miss siblings of implemented commands (LineParallel/LinePerp exist, LineFillet/LineTangent don't; Trim/Extend exist, Join doesn't); relatively small, self-contained widgets to add given the existing PolyMaker/ PolyMaker2 base classes.
  • Text — TruetypeText, MarkText: E2Text is fully rendered (grid/dim labels, GEO import), but there's no interactive text-placement command.
  • Domain-specific — ParametricDucts, CommonShapes, IrregularArray, ShiftOrigin: each implies its own small subsystem (a duct-fitting parametric library, a shape-template picker, a non-uniform-pitch array, and a drawing-origin-shift utility) with no current infrastructure to build on beyond the generic PolyMaker/DwgLayouter bases.

Beyond command coverage, functional gaps to weigh against "base of a 2D CAD tool":

  • No multi-part layout/nesting concept — Pix edits one Dwg2 (one part) at a time; sheet nesting/material-utilization is out of scope today.
  • No dimension-style management (DimSettings absent) — dimension appearance is effectively hardcoded per dimension type.
  • No plugin/scripting/extensibility surface — every command is a compiled Widget/DwgCmds method discovered via reflection over the Pix assembly itself, not an open registration API.
  • Layer management (LayersDlg, EditLayerDlg) and undo/redo are solid and reusable as-is.
  • The 3D fold preview (FoldedPartScene/PaperFolder) is a notable head start toward flat-pattern ↔ folded-model round-tripping that a generic 2D-only CAD tool would otherwise lack.
