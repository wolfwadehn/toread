Import Workflow and Data Mapping

Steps

  1. Parse the LST per 01-lst-file-format-primer.md into an in-memory document that preserves every section (recognized and unrecognized) and their original order/formatting, so re-export is a round-trip rather than a regeneration.
  2. Extract sheet/job context from BEGIN_EINRICHTEPLAN_INFO (machine, controller, programmer, date, job name, material id, sheet weight, remark) and BEGIN_SHEET_TECH (sheet dimension X/Y/Z, material id/density) — used for job header display in the palletizing view and for Stacking Thickness defaults (sheet dimension Z, see 05-stack-and-pile-management/07-schedule-and-sheet-count.md).
  3. Extract machine-load context from BEGIN_MACHINE_LOAD_DATA (Pallet Changer Type, Sheet Stop, Calibration Active) — used to pre-select an automation profile, see 02-select-automation/02-selection-workflow.md.
  4. Extract the part catalog from BEGIN_PARTS_IN_PROGRAM — one row per distinct part (Part Identity Number = program name, Part File Name, Part Count, Dimension X/Y, Area, Cutting Length) — becomes each part's PartTypeRef master record for the Stack Data Model.
  5. Extract part instances from BEGIN_PARTS_IN_PROGRAM_POS — one row per physical instance on the sheet (Sequence, Position X/Y, Dimension X/Y, Angular Position, Centroid X/Y) — becomes the initial, unassigned pile membership pool the palletizing view starts from. Fields Unload Sequence, Reference Part, Unload Name, Pallet Name, Part Classification, Label Group Id are read if already populated (e.g. re-importing a previously palletized job) and otherwise start blank — these are exactly the fields Export LST writes back, see 08-export-lst/02-populated-fields-reference.md.
  6. Extract linking metadata from BEGIN_ANALYTICS_DATA (FluxCutLayoutGuid, FluxCutSessionGuid, NcProgramGuid) — retained for traceability back to the originating Flux Cut job, and echoed into any log/report the palletizing module produces.
  7. Leave untouched all cutting-technology sections not relevant to palletizing (BEGIN_PROGRAM_PROPERTIES, BEGIN_SHEET_PROCESS_INFORMATION, BEGIN_LTT_CALLS, BEGIN_LTT_STAMM, BEGIN_MICROJOINT, BEGIN_LEAD_IN) — parsed only far enough to preserve them verbatim on export.

Building the palletizing working set

After import, the module's internal state is:

  • One part-catalog entry per BEGIN_PARTS_IN_PROGRAM row (PartTypeRef).
  • One part-instance entry per BEGIN_PARTS_IN_PROGRAM_POS row, initially unassigned to any pile unless Unload Name/Pallet Name were already populated.
  • The stacking engine (chapter 05) then groups instances into piles, by default one pile per PartTypeRef (see Auto Arrange).

Example (from sample.LST)

BEGIN_PARTS_IN_PROGRAM lists 3 part types (hex, circ, rec, each Part Count = 3); BEGIN_PARTS_IN_PROGRAM_POS lists 9 instances (sequence 1–9) at their nested positions, all with empty Unload Sequence, Unload Name, and Pallet Name — i.e. this sample is a plain cutting job with no palletizing applied yet, the exact starting state Import LST must handle.
