LST File Format Primer

LST File Format Primer

What it is

The .LST file is a TRUMPF/MetaCAM Einrichteplan (setup plan) — a plain ASCII, line-oriented, table-based export produced by the nesting/cutting job application (in the sample, "Flux Cut") for one sheet program. It is both a machine setup document and the carrier of the NC subprograms.

Confirmed from sample.LST (a 945-line, single-sheet, 9-part job — 3× hex, 3× circ, 3× rec, matching hex.fx/circ.fx/rec.fx, produced from sample.fxjob):

BD
SET_METRIC
C
BEGIN_<SECTION_NAME>
C
ZA,MM,<n>                      <- n field definitions follow
MM,AT,1,<col>,1,1,,'<Field Name>',,'<unit>',<type>
...
C
ZA,DA,<n>                      <- n data rows follow
DA,<value1>,<value2>,...       <- one row; long rows continue with a
* <value...>                     leading "* " continuation line
C
ENDE_<SECTION_NAME>
C

then repeated BEGIN_.../ENDE_... blocks for every section, terminated by a final ED line.

Field-definition row (MM,AT,...)

MM,AT,1,<column>,1,1,,'<Field Name (padded)>',,'<unit>',<type> where <type> is T (text) or Z (numeric). Column numbers are stable identifiers (not necessarily contiguous — sections are extended over product versions by adding new column numbers, e.g. BEGIN_LTT_STAMM runs from column 10 to 4970), so a parser must match by field name, not by position in the row list, and must tolerate unknown/future columns being present or absent.

Data row (DA,...)

One DA, row per record, comma-separated, string values single-quoted. C lines are comment/separator markers and must be skipped. Long rows wrap onto continuation lines beginning with * (see e.g. the BEGIN_LTT_STAMM data row in sample.LST, which wraps across 39 continuation lines).

NC program bodies

Some sections (BEGIN_PROGRAMM) hold DA, header rows followed by an embedded NC subprogram between START_TEXT / STOP_TEXT markers — this is raw machine G-code/TC_-macro text, not table data, and must be preserved byte-for-byte on export (see 08-export-lst/03-nc-program-and-part-end-sequencing.md).

Practical parsing approach

  1. Split the file into BEGIN_X ... ENDE_X blocks.
  2. Within a block, parse the ZA,MM,n header to build a {column -> (name, unit, type)} map, then parse each ZA,DA,n group's DA, rows (reassembling *-continuations first) positionally against that map.
  3. Treat sections not recognized by the palletizing module as opaque (round-tripped unchanged) — see 07-import-lst/02-import-workflow-and-data-mapping.md and 08-export-lst/01-export-workflow-and-data-mapping.md.
