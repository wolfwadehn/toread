DataHub Arc42 — Validation against the code base

DataHub Arc42 — Validation against the code base

Validated: 2026-08-04 Document under review: CONNECTORS-DataHub Arc42-040826-082816.pdf (Confluence export, 67 pages, "DataHub Arc42 — CAMBridge") Validated against: DataHub repo @ aa942e6c (branch main)

Verdict

The Confluence arc42 is structurally sound but materially out of date. Its skeleton follows arc42 correctly and the configuration reference chapter is excellent — genuinely better than what most projects have. But the document was largely written around the MongoDB → PostgreSQL switch (Sep/Oct 2025) and has not tracked the code since.

Three classes of problem, in descending severity:

Class Count Impact
A — Stale/wrong: documents behaviour the code no longer has 7 A reader acts on false information
B — Missing: architecture in the code that is absent from the doc 8 The doc no longer explains the system
C — Placeholders/inconsistencies 9 Doc reads as unfinished
Bugs found while validating 7 Real defects, one causing silent data corruption

The single most consequential gap is B1 (TimescaleDB): the production storage engine is not the one the document describes.

A. Stale or factually wrong

A1. The "Local File System" secondary-storage concept no longer exists

Doc says (Crosscutting Concepts → Local File System): "The local file system is the secondary storage location where data is stored that is unfit for the database, for example, ZIP files." Data Management lists "5. Storing data on the local file system".

Code says: IIOManager exposes exactly one member — GetFreeDiskSpace(string path) (src/Core/IIOManager.cs:15). There is no file-writing path anywhere in src/Core or src/DataStorage. The DataHub writes only to PostgreSQL.

Fix: delete the concept, or restate it as "disk-space probing for the cleanup service".

A2. Cleanup does not delete files from disk

Doc says: "If some disk space limits are reached, old files are deleted on the disk as well (in addition to the database cleanup)."

Code says: CleanupManager issues only SQL — DELETE FROM, VACUUM, and TimescaleDB drop_chunks() (src/Cleanup/CleanupManager.cs:98,144,278,377). Free disk space is read (:229) purely as a trigger condition; nothing on disk is deleted.

A3. MetaDataExporter writes to the database, not the file system

Doc says (Runtime View, step 3): "It stores the returned database statistics (as condition log records) on the file system."

Code says: DatabaseStatisticsExporter calls context.PostgresStatisticsRecords.Add(...), context.PostgresTableStatisticsRecords.Add(...) and SaveChangesAsync() (src/MetaDataExporter/DatabaseStatisticsExporter.cs:139,173,257). Statistics land in database tables. Confirmed by the XML doc on MetaDataExporterWorker, which says records are written to condition logs "as well as inserted into the DataHub database itself" — and only the latter half is still true.

A4. The ConditionLogFileWriter configuration section is gone

Doc says: a full subsection "Settings for ConditionLogFileWriter" documenting LogDirectory (C:\ProgramData\TRUMPF\DataHub\CondLogs), LogFileSize, MaxNumberLogFiles.

Code says: zero occurrences of ConditionLogFileWriter, CondLogs, LogFileSize or MaxNumberLogFiles in any .cs, .json, .ps1 or .tcix outside the generated Documentation/ tree. Program.cs reads only these sections: PostgreSQL, ActServer, DataStorage, Cleanup, MetaDataExporter, RabbitMQ, Kestrel, Serilog (src/DataHubService/Program.cs:68-74).

Fix: delete the section. It is the clearest single indicator of doc drift.

A5. MaximumDatabaseSize is described in MongoDB terms

Doc says: "Corresponds to the total uncompressed BSON data in the database. This is because otherwise, reserved blocks containing only deleted data are counted towards the database size."

PostgreSQL has no BSON and no WiredTiger reserved blocks. This is verbatim MongoDB-era text left in place after ADR-9. The rationale needs rewriting against pg_database_size semantics + VACUUM.

A6. The package is a .tciz, not a .uif

Doc says (Deployment view): the artifact is DataHub.uif, "the UIF package".

Code says: createUif.ps1:78 produces DataHub_<SemVer>.tciz — a ZIP built with 7-Zip, whose root holds the component manifest component.tcix and a CycloneDX sbom.json, with payload under content/. UIF is the framework; .tciz is the artifact. The doc also omits the sidecar DataHub_<version>.build file carrying SCAPS component, source and build metadata, and the fact that nothing in the repo uploads to SCAPS — that is a downstream step.

A7. "Several dedicated RabbitMQ exchanges"

Doc says: "The DataHub manages several dedicated RabbitMQ exchanges, each of which defines the data that the DataHub expects…"

Code says: exactly one. RabbitMQExchangeConfiguration is (ConditionLogExchange, ConditionLogRoutingKey) — a two-field record with no trace or second exchange. The doc's own follow-up sentence ("Currently, the following main exchange exists") is the accurate one; the plural opener is aspirational and misleads.

Related code-side drift worth fixing in the same pass: the XML summary on RabbitMQCommunication still claims it communicates "with several channels for condition logs and traces". There is no trace channel.

B. Missing architecture

B1. TimescaleDB is the production storage engine — and is undocumented ⚠️

This is the big one. The document mentions TimescaleDB only in the Legacy Comparison benchmark section, where it appears as a rejected option ("MongoDB has been benchmarked against TimescaleDB… As a result of better performance, MongoDB has been selected").

In the shipping code TimescaleDB is load-bearing:

Evidence Location
.UseTimescaleDb() on the EF Core provider src/DataHubService/Program.cs:145
CmdScale.EntityFrameworkCore.TimescaleDB package src/Core/…/BendstepMeasurement.cs:1
[Hypertable(...)] attribute on the entity src/Core/…/BendstepMeasurement.cs:12
"TimescaleDB:IsHypertable" = true in the model snapshot src/Migrations/Versions/DataHubContextModelSnapshot.cs:558
Migration configures compression + chunk-skipping policies Migrations.Versions.BendstepMeasurementAndSensorTables
Cleanup detects hypertables and retains via drop_chunks() src/Cleanup/CleanupManager.cs:278,398
Cleanup hard-fails if timescaledb_information.hypertables is absent src/Cleanup/CleanupManager.cs:407-410

There is no ADR for adopting TimescaleDB, and the ER diagram/database-schema section does not distinguish hypertables from regular tables. A reader of the current doc would conclude plain PostgreSQL — and would be wrong about retention, compression and the cleanup service's failure modes.

B2. Time-series ingestion and storage

The most recent feature (61c0a93e "Implemented storage of time series data") introduced EquidistantTimeSeriesData, TimeSeriesPointEntity, BendstepMeasurement, Sensor, ITimeSeriesEntityBuilder / ITimeSeriesEntityFactory, BendstepMeasurementBuilder, SensorValues, and the Core.GraphQL.TimeSeries namespace. Registered in DI at Program.cs:89-90.

Notable architectural property the doc should capture: EquidistantTimeSeriesData "is never persisted as a whole but rather as an enumerable of concrete TimeSeriesPointEntity instances" — a record→many-rows fan-out that is unlike every other condition log record. BendstepMeasurement also gets a 7-day retention versus 30 days for everything else (appsettings.json:130).

None of this appears in the doc; the glossary entry for "Trace" is still TODO.

B3. GraphQL subscriptions

AddSubscriptionType<Subscription>() + AddInMemorySubscriptions() + app.UseWebSockets() (Program.cs:150-151,198). DataStore receives an ITopicEventSender and publishes on record receipt and insertion; topics are defined in SubscriptionTopicNames, with per-record-name specific topics (src/Core/GraphQL/Subscription.cs:76-116).

The doc describes the GraphQL API as query/filter/sort/aggregate only. Push-based consumers are an interface the doc does not admit exists.

B4. The Nitro licence workaround (a genuine ADR)

src/NitroAppStub is an entire project whose reason to exist is a licence constraint: ChilliCream.Nitro.App ships under ChilliCream License 1.0, "which is not allowed by default by TRUMPF, so the licensed assembly must not ship" — but HotChocolate.AspNetCore hard-requires it at runtime. The fix is to exclude all assets of the real package plus its transitive Yarp.ReverseProxy, and substitute an in-repo stub with the same assembly name and version (src/DataHubService/DataHubService.csproj:19-43).

This is exactly the kind of "expensive, risky, non-obvious" decision arc42 §9 exists for, and it carries a live maintenance obligation ("When updating HotChocolate.AspNetCore, we must re-check that the excluded versions and the stub still match"). Absent from the doc.

B5. Port-based endpoint isolation

The two Kestrel ports are documented, but not the mechanism that enforces separation: EndpointFilterAttribute on controllers/actions, EndpointSelectionMiddleware rejecting mismatches, and PortDocumentFilter making each port's Swagger page show only its own endpoints (Program.cs:172-175,200). This is a security-relevant concept (the Trumpf Analytics compatibility port must not expose DataHub endpoints), and it belongs in Crosscutting Concepts.

B6. There is no Security concept section at all

Nothing in the doc covers:

  • DataGovernanceType, mapped to a native PostgreSQL enum data_governance (Program.cs:139), and the JsonData vs SensitiveJsonData split in the GraphQL layer
  • credential encryption at rest via EncryptionHelper.Decrypt for RabbitMQ user/password (Program.cs:336,341) — the doc mentions Encrypt under RabbitMQ settings but never as a security concept, and never mentions the src/Encryptor tool or encryptAndWriteSecrets.ps1
  • GraphQL abuse protection: LimitMiddleware / UseLimitAttribute
  • that both HTTP endpoints are plain http://0.0.0.0 — no TLS, no authn/authz — with the firewall rule opened by the installer (component.template.tcix, <ConfigureFirewall>)
  • that error responses are deliberately generic to avoid leaking exceptions (Program.cs:243)

B7. Deployment view is missing the entire install mechanism

The doc's deployment view stops at "the UIF package is installed on the Main IPC". The .tcix component descriptor contains substantially more architecture:

  • Package dependencies: DataHubPostgreSQL (≥1.0.0 <2.0.0), SysParaUidRestInterface (≥1.0.0 <2.0.0), DotnetV10; and Replaces TrumpfAnalyticsMachine — i.e. the DataHub supersedes a previous product, which explains why port 12001 replicates the Trumpf Analytics endpoint
  • Install-time schema migration via efbundle.exe, each migration wrapped in a transaction so a power loss leaves the DB consistent and the installer merely needs re-running
  • Client-ID provisioning by generateTrumpfAnalyticsClientId.ps1 patching appsettings.json in place
  • Service rename handling: the old TAT.DataHubService is stopped and removed on upgrade
  • Ops integrations: MINEX backup/restore scripts, LogFileCollector log locations, MachineHealthMonitor service descriptor
  • Firewall configuration for the REST API

build/MachineHealthMonitorConfig/DataHub.json also contains the crispest one-line purpose statement anywhere in the repo — "Collects machine data for subsequent analysis, visualization and upload" — which would improve §1.

B8. GraphQLSourceGeneration and the generated GraphQL surface

An entire src/ project generating the *FilterInputType / *SortInputType / *AggregationResult types from [GenerateGraphQLQuery] / [SkipGraphQLQueryGeneration] attributes. This is why the API surface scales automatically with new record types — an important adaptability mechanism, and directly relevant to quality scenario SC6 (which currently claims a developer must hand-edit three things). Undocumented.

C. Placeholders and internal inconsistencies

  1. Requirements Overview is TODO — §1.1, arguably the most important subsection, has no content beyond a Jira link (BENDCAM-12431).
  2. Risks and Technical Debt is TODO, and its only entry ("Technical Debt: DataHub Code Base") is marked FIXED. So §11 is effectively empty for a system with real known risks (see below).
  3. Six ADRs have Consequences: TODO — ADR1, ADR2, ADR3, ADR4, ADR5, ADR6. arc42 §9 is explicit that consequences must be listed, "not just the positive ones".
  4. Stakeholder table is mostly empty — roles Mechanics / Electrics / Testing / Service / PM / TechDoku have no names and no expectations; the Software row has names but no expectations. No contact column.
  5. Quality-scenario numbering is broken. The Quality Tree references SC1, SC2, SC3, SC4, SC6, SC7 — but the scenario list defines SC1…SC6. SC7 is referenced and never defined; SC5 is defined and never referenced.
  6. SC1 contradicts the code. SC1 says "A RabbitMQ message must be acknowledged within 1 minute." The consumer uses autoAck: true (src/DataStorage/RabbitMQ/RabbitMQCommunication.cs:186) — messages are acknowledged on delivery, before processing. The scenario is unfalsifiable as written and hides a real property (see the risk note below). SC1's response measure is also TODO.
  7. "Business Context" and "Technical Context" are five WORK IN PROGRESS markers. Worse, two documented elements are not implemented: the Remote Storage Service ("retrieve the actual data … via a REST API") and Local Storage retrieval-by-reference. The only outbound HTTP call in the entire code base is MachineInfoManager → ACT server (src/Core/MachineInfoManager.cs:226); the sole IHttpClientFactory consumer. Nothing downloads referenced payloads.
  8. Hardware Assembly, Design Parameter, Important Documents and Numbers = "Not applicable"; glossary "Trace" = TODO; Meta Data Condition Log Records has two TODO: LINK TO CONDITION L….
  9. Runtime View has exactly one scenario ("DataHub Start-up"), and it names the three core services as DataStorage / Cleanup / MetaDataExporter whereas the actual hosted services are RabbitMQStorageWorker, CleanupWorker, MetaDataExporterWorker plus the Kestrel web host (Program.cs:92-93,120). Missing scenarios: record ingestion + cache flush, on-the-fly migration, cleanup execution, install-time migration, PostgreSQL-unavailable behaviour.

Bugs found while validating

Not documentation problems — real defects surfaced by reading the code against the doc. Listed here because they are the most actionable output of the exercise.

1. Multi-sensor time-series timestamps are wrong ⚠️ (highest priority)

BendstepMeasurementBuilder.BuildAsync initialises currentTimestamp outside the per-sensor loop and never resets it:

DateTime currentTimestamp = startTimestamp;      // outside the sensor loop
foreach (SensorValues sensorValues in sensorData)
{
    foreach (double? value in sensorValues.Values)
    {
        yield return new BendstepMeasurement { Timestamp = currentTimestamp, … };
        currentTimestamp = currentTimestamp.Add(samplingDelta);   // never reset per sensor
    }
}

Each SensorValues is one sensor's series over the same time base — the record has one StartTimestamp and one SamplingDelta, and the composite PK (Timestamp, BendstepStartId, SensorId) explicitly permits sensors to share a timestamp. Every sensor should start at StartTimestamp.

As written, sensor n is stamped starting where sensor n−1 ended. Two sensors × 1000 samples at 1 ms ⇒ the second sensor is shifted one full second into the future; more sensors compound it. Nothing fails, nothing is logged, the data looks plausible — and any cross-sensor correlation is silently wrong. Invisible with a single sensor, which is presumably why it survived.

Evidence: src/Core/TimeSeries/BendstepMeasurementBuilder.cs:46-62.

Fix: move the initialisation inside the sensor loop; add a two-sensor unit test. Retention for BendstepMeasurement is 7 days, so the exposure window is short — argues for fixing fast rather than writing a data migration.

2. Cached records are lost on every service stop

DataStore passes IHostApplicationLifetime.ApplicationStopping as the cancellation token to every SaveChangesAsync. The final cache flush happens during DI disposal — after that token is already signalled. So the shutdown flush runs cancelled, throws, and Cache<T> logs "Data is lost. {@LostElements}" with the queue already drained. Up to MaxCacheSize records per cache, on every restart — and restarts are routine (config changes, upgrades, MINEX backup).

Evidence: src/DataHubService/Program.cs:296,311; src/DataStorage/Caching/Cache.cs:315-316.

Fix: use ApplicationStopped, or a separate CTS with a bounded drain timeout, for the shutdown flush. Best value-per-effort item here.

3. The binary COPY path swallows every exception

CopyInsertAsync catches all exceptions, rolls back, and neither logs nor rethrows — so DataStore believes the insert succeeded. An entire time-series payload can vanish with no log line, no Error record, no notification. The only write path in the system with zero failure visibility.

Evidence: src/Core/EntityFrameworkCore/CopyInsertExtension.cs:63-66.

4. EndpointSelectionMiddleware fails open — and its own doc comment says otherwise

The 404 is returned only when the endpoint carries an EndpointFilterAttribute whose name mismatches. Endpoints without the attribute pass on every port. MapGraphQL() and MapSwagger() add no such metadata, so /graphql and /swagger are served on port 12001 as well as 31110 — a client restricted to the Trumpf Analytics port by network policy still has unrestricted GraphQL read access to the whole database.

The method's XML documentation explicitly states that an endpoint without the attribute receives a 404. The code does not do that.

Evidence: src/DataHubService/Middleware/EndpointSelectionMiddleware.cs:52-58 vs the doc comment at :35-38.

5. A hypertable with a Retain rule generates invalid SQL

For hypertables the statement is SELECT drop_chunks(...);; a Retain rule is then appended as AND NOT EXISTS (...). Latent only because BendstepMeasurement currently has no Retain. Adding one breaks that table's cleanup permanently — logged as a warning and skipped every cycle thereafter.

Evidence: src/Cleanup/CleanupManager.cs:275-319.

6. drop_chunks interval uses culture-sensitive formatting

DeleteOlderThanDays is a double interpolated as $"INTERVAL '{...} days'" with no InvariantCulture. On a German-locale machine a fractional value like 0.5 renders '0,5 days' and the statement fails. Non-hypertable tasks are safe (parameterised).

Evidence: src/Cleanup/CleanupManager.cs:277-282.

7. The AES "encryption" key is a hardcoded constant

EncryptionHelper uses one 16-byte AES key declared as a source literal — identical in every build, readable ASCII, shipped in Core.dll. The pipeline's "encrypt secrets" step is obfuscation only: anyone with the repo or the installed binaries can recover the RabbitMQ credentials. Cannot be rotated without a rebuild.

Evidence: src/Core/EncryptionHelper.cs:11.

Fix: at minimum stop calling it encryption. For real protection, Windows DPAPI (machine scope) needs no key distribution.

Risk the document should be recording but does not

Worth calling out separately, because it is a real property of the system rather than a documentation defect:

There is an at-most-once delivery window on the RabbitMQ path. Three facts compose:

  1. autoAck: true — the broker considers the message delivered and discards it immediately (RabbitMQCommunication.cs:186)
  2. The exchange and queue are non-durable — ExchangeDeclareAsync(exchange, type: Topic) and QueueDeclareAsync(exclusive: true, autoDelete: false) both default durable: false (:203,208)
  3. Records are then buffered in memory by Cache<T>, flushed only when MaxCacheSize (default 100) is exceeded or CacheFlushDelaySeconds (default 60) elapses (appsettings.json:55-56)

So a crash or forced shutdown can lose up to ~100 records or ~60 seconds of data per cache, with no broker-side redelivery. That may well be an accepted trade-off for machine telemetry — the doc's own ADR-11 reasoning ("all the existing data in the DataHub also exists in the cloud") suggests it is. But it is an undocumented accepted risk, and §11 is the place for it.

What the document gets right

Worth preserving as-is:

  • ADR-7 (migration-based tables) and ADR-9 (MongoDB → PostgreSQL) are exemplary — full context, honest negative consequences, explicit supersession chain (ADR3→ADR9, ADR8→ADR10). This is what the other six ADRs should look like.
  • ADR-11 (drop existing machine data) records the human/organisational reasoning, including who was consulted. Hard to reconstruct later; valuable that it was written down.
  • The configuration reference is accurate and complete for every section that still exists, including non-obvious semantics: MaxNumberConnectionRetries: -1 = infinite, HostEnvironmentVariableName presence-only check, jittered exponential backoff, the retention-condition DSL with its nested And/Or grammar. I verified this against Program.cs and appsettings.json — it matches.
  • RabbitMQ exchange/queue properties (Topic, non-durable, non-durable queue) — correct.
  • Error handling — errors logged and inserted as Error records is correct (src/DataStorage/DataStore.cs:436).
  • The .NET 10 dev-environment statement — correct (net10.0).
