DataHub — Defects found during architecture documentation review

DataHub — Defects found during architecture documentation review

Date: 2026-08-04 Reviewed: Connectors/DataHub @ aa942e6c (branch main) Context: These defects surfaced while writing an arc42 architecture documentation set from the code base (branch arc42, docs/) and validating it against the existing Confluence DataHub Arc42 page.

Method and caveat. Every item below was found by static reading of the source, and every claim cites the file and lines it rests on. Nothing here was reproduced against a running machine — no test was executed and no instance was instrumented. Severities are my assessment of blast radius, not a measured incident rate. Items marked latent are not reachable with today's configuration but become live under a plausible near-future change.

Summary

Ordered by severity. 29 defects, of which 5 cause data to be lost, corrupted or disclosed.

BUG-1 — Multi-sensor time-series timestamps are wrong

Severity: Critical — silent data corruption File: src/Core/TimeSeries/BendstepMeasurementBuilder.cs:46-62

Symptom

In a time-series measurement containing more than one sensor, every sensor after the first is stored with timestamps offset into the future by the cumulative sample count of all preceding sensors.

Root cause

currentTimestamp is initialised outside the per-sensor loop and advanced inside the per-value loop, but is never reset when moving to the next sensor:

DateTime currentTimestamp = startTimestamp;          // ← outside the sensor loop
foreach (SensorValues sensorValues in sensorData)
{
    foreach (double? value in sensorValues.Values)
    {
        yield return new BendstepMeasurement
        {
            Timestamp = currentTimestamp,
            BendstepStartId = bendstepStartDto.Id,
            SensorId = sensors[sensorValues.Name].Id,
            SensorValue = value
        };
        currentTimestamp = currentTimestamp.Add(samplingDelta);   // ← never reset per sensor
    }
}

Why this is a defect rather than intended behaviour

Each SensorValues element is one sensor's series over the same time base:

  • EquidistantTimeSeriesData carries a single StartTimestamp and a single SamplingDelta for the whole record.
  • The entity's composite primary key is (Timestamp, BendstepStartId, SensorId), which explicitly permits two sensors to share a timestamp — so there is no key-collision reason to stagger them.

Therefore every sensor's series should start at StartTimestamp.

Impact

With two sensors of 1000 samples each at a 1 ms sampling delta, the second sensor's data is shifted one full second into the future. With n sensors the error compounds linearly.

The failure is completely silent: the rows insert successfully, the values are correct, the timestamps are well-formed and monotonic, and nothing is logged. Only the alignment between sensors is wrong — which is precisely what multi-sensor capture exists to provide. Any downstream correlation, overlay or cross-sensor analysis produces wrong results while appearing healthy.

The defect is invisible when a record contains exactly one sensor, which is the likely reason it has not been noticed.

Fix

Move the initialisation inside the outer loop:

foreach (SensorValues sensorValues in sensorData)
{
    DateTime currentTimestamp = startTimestamp;       // ← reset per sensor
    foreach (double? value in sensorValues.Values)
    {
        ...
    }
}

Add a unit test with two or more sensors asserting that each sensor's first sample is stamped at StartTimestamp. Existing coverage evidently exercises the single-sensor case only.

Data already collected

BendstepMeasurement retention is 7 days (src/DataHubService/appsettings.json:128-131), so the exposure window on any machine is short. That argues for shipping the fix promptly rather than writing a correction migration. Worth confirming with whoever consumes this data whether any multi-sensor analysis has already been run on affected data.

BUG-2 — Cached records are discarded on every service stop

Severity: High — data loss on a routine operation Files: src/DataHubService/Program.cs:296,311; src/DataStorage/Caching/Cache.cs:301-317

Symptom

Records still sitting in the write-behind cache when the service stops are lost rather than flushed, and the loss is logged as an error on every stop.

Root cause

DataStore is constructed with IHostApplicationLifetime.ApplicationStopping as its global cancellation token:

var globalCancellationToken = hostApplicationLifetime.ApplicationStopping;   // Program.cs:296
return new DataStore(dataStoreConfiguration, dataStoreDependencies, globalCancellationToken);

That token is passed to every SaveChangesAsync and CopyInsertAsync. The final cache flush, however, happens in DataStore.DisposeAsync → Cache.DisposeAsync, which the DI container runs during host disposal — i.e. after ApplicationStopping has already been signalled.

The shutdown flush therefore executes with an already-cancelled token. SaveChangesAsync throws OperationCanceledException, which Cache catches:

catch (Exception ex)
{
    _logger.LogError(ex,
        "Exception occurred during the invocation of the cache flush receiver callback. Data is lost. {@LostElements}",
        new { LostElements = string.Join(", ", elementsToBeFlushed) });
}

By this point the elements have already been dequeued, so they are gone.

Impact

Up to MaxCacheSize records per cache (default 100, one cache for condition log records and one for Trumpf Analytics messages) are lost on every service stop or restart. Restarts are routine: configuration changes, package upgrades, and MINEX backup all stop the service.

There is a second-order consequence: build/MINEX/Invoke-MINEX.ps1 stops the DataHub specifically so that its caches are flushed and the database is consistent for the backup. If the flush is failing, that guarantee does not hold and backups may be missing the most recent records.

Fix

Do not use ApplicationStopping for the shutdown drain. Either use ApplicationStopped, or give DataStore a dedicated CancellationTokenSource that is cancelled only after a bounded drain timeout (e.g. 10 s), so the final batch gets a genuine chance to commit.

The existing log line makes this easy to confirm before and after: search machine logs for "Data is lost" — if BUG-2 is live, it should appear on essentially every service stop.

BUG-3 — The binary COPY path swallows every exception

Severity: High — silent data loss File: src/Core/EntityFrameworkCore/CopyInsertExtension.cs:63-66

Symptom

A failed bulk insert of time-series data is rolled back and then reported as success. The payload disappears with no trace anywhere.

Root cause

A bare catch with no logging and no rethrow:

try
{
    await using NpgsqlBinaryImporter writer = await conn.BeginBinaryImportAsync(copyCommand, cancellationToken);
    do { await WriteRowAsync(writer, enumerator.Current, propertyGetters, cancellationToken); }
    while (await enumerator.MoveNextAsync());
    await writer.CompleteAsync(cancellationToken);
    await tx.CommitAsync(cancellationToken);
}
catch                                   // ← no exception variable, no log, no rethrow
{
    await tx.RollbackAsync(cancellationToken);
}

DataStore.InsertTimeSeriesAsync has no way to distinguish this from success.

Impact

This is the only write path in the system with zero failure visibility. Every other path logs and writes an Error condition log record. Here an entire EquidistantTimeSeriesData payload — potentially thousands of rows — can vanish with no log line, no Error record and no subscription notification.

It also masks BUG-1's sibling failure modes and any schema mismatch on the COPY statement: the system would look perfectly healthy while storing nothing.

Fix

Capture, log and rethrow, and route the failure through the same Error-record path the batched insert path uses:

catch (Exception ex)
{
    await tx.RollbackAsync(cancellationToken);
    _logger.LogError(ex, "Binary COPY insert failed for {EntityType}. {RowCount} rows lost.", ...);
    throw;
}

CopyInsertExtension is currently a static extension with no logger; the simplest route is to let the exception propagate and let DataStore handle it, since DataStore already has both a logger and the Error-record machinery.

BUG-4 — The port filter fails open: GraphQL and Swagger are served on both ports

Severity: High — unintended exposure Files: src/DataHubService/Middleware/EndpointSelectionMiddleware.cs:42-63; src/DataHubService/Program.cs:204,208

Symptom

/graphql and /swagger are reachable on the Trumpf Analytics port (12001) as well as on the DataHub port (31110), despite the port-separation mechanism.

Root cause

The middleware returns 404 only when the endpoint carries an EndpointFilterAttribute whose name is not permitted for the request's local port:

if (_portToEndpointNamesMap.TryGetValue(port, out HashSet<string>? expectedEndpointNames))
{
    EndpointFilterAttribute? endpointFilter = endpoint.Metadata.GetMetadata<EndpointFilterAttribute>();

    if (endpointFilter is not null && !expectedEndpointNames.Contains(endpointFilter.EndpointName))
    {                                  // ← only rejects when the attribute EXISTS
        context.Response.StatusCode = StatusCodes.Status404NotFound;
        return Task.CompletedTask;
    }
}
return _next(context);                  // ← no attribute ⇒ allowed on every port

MapGraphQL() and MapSwagger() attach no such metadata, so both pass through unconditionally.

Resulting exposure

Endpoint Annotated On :12001 On :31110
/api/message, /api/operationalReadiness, /api/settings yes ✅ 404
/api/cond-log-records yes 404 ✅
/graphql (HTTP + WebSocket) no ✅ ✅
/swagger no ✅ ✅

Impact

Port 12001 exists for backwards compatibility with senders that previously targeted the TrumpfAnalyticsMachine component. Any network policy that permits a client to reach only 12001 — in the belief that this restricts it to the analytics contract — in fact grants unrestricted GraphQL read access to the entire DataHub database, plus the full API contract via Swagger.

Note this compounds with the absence of authentication (BUG-5's neighbour): there is no second line of defence behind the port filter.

Additional finding: the code contradicts its own documentation

The method's XML documentation states:

"If the port is contained in the port-endpoint mapping but the name does not match or if the endpoint does not have an EndpointFilterAttribute, a 404 response is returned."

The implementation does not do this. Because this XML comment is published into the generated component documentation, the wiki currently describes fail-closed behaviour that does not exist.

Fix

Fail closed — treat a missing EndpointFilterAttribute as "not permitted on any mapped port" — and annotate the GraphQL and Swagger endpoints explicitly with the port they belong to. Correct the XML comment either way. Separately, consider guarding Swagger UI behind an environment check rather than serving it unconditionally on production machines.

BUG-5 — The AES key is a compile-time constant

Severity: High — security File: src/Core/EncryptionHelper.cs:11

Symptom

RabbitMQ credentials stored in appsettings.json can be decrypted by anyone holding the shipped binaries or the repository.

Root cause

A single 16-byte AES key is declared as a source literal:

private static readonly byte[] _encryptionKey = [ /* 16 bytes, decoding to a readable ASCII phrase */ ];

It is identical in every build and every deployment, it is committed to the repository, and it ships inside Core.dll on every machine.

Impact

The release pipeline step named "encrypt secrets" provides obfuscation, not confidentiality. Anyone with read access to the repo — or to an installed DataHub — can recover the broker credentials from appsettings.json. The key cannot be rotated without rebuilding and redeploying the product to every machine.

The most immediate risk is not the cryptography but the false assurance: naming the mechanism "encryption" invites the reasonable but incorrect assumption that credentials in appsettings.json are protected.

Fix

Two options, in increasing order of cost:

  1. Cheapest, do this regardless: stop describing this as encryption in documentation and pipeline step names. Call it obfuscation, so nobody relies on it.
  2. Actual confidentiality: use the Windows DPAPI (ProtectedData with DataProtectionScope.LocalMachine). It requires no key distribution, is available on every target platform, and ties the ciphertext to the machine — which is exactly the trust boundary the DataHub already assumes.

BUG-6 — (latent) A hypertable with a Retain rule generates invalid SQL

Severity: Medium — latent File: src/Cleanup/CleanupManager.cs:275-319

Root cause

The deletion statement is built per table, branching on whether the table is a TimescaleDB hypertable:

if (hyptertableNames.Contains(deletionTask.TableName))
{
    deletionSql = $"""
    SELECT drop_chunks(
        older_than => INTERVAL '{deletionTask.DeleteOlderThanDays} days',
        relation => '"{deletionTask.TableName}"'
    );
    """;
}
else
{
    deletionSql = $"""
    DELETE FROM "{deletionTask.TableName}" t
    WHERE t."{deletionTask.TimestampField}" < @limit
    """;
}

A Retain rule is then appended unconditionally with +=:

deletionSql += $"""

    AND NOT EXISTS (
        SELECT 1 FROM "{deletionTask.TableName}" keep
        WHERE ({parameterizedSql.Sql})
        AND t."{deletionTask.TimestampField}" BETWEEN ...
    )
    """;

For a hypertable this yields SELECT drop_chunks(...); AND NOT EXISTS (...) — syntactically invalid, and additionally referencing a table alias t that the drop_chunks form never defines.

Impact

Currently unreachable: the only hypertable (BendstepMeasurement) has no Retain section. The moment someone adds one — an entirely reasonable request, e.g. "keep measurements around failed bends" — that table's cleanup breaks permanently and quietly. The failure path is NpgsqlException → LogWarning → skip the table, repeated every 10-minute cycle, with the table growing unbounded.

Fix

Reject the combination in the CleanupManager constructor with an explicit error (the constructor already validates configuration, so this fits the existing pattern), or implement retention windows for hypertables properly. A silent warning-and-skip is the worst available outcome.

BUG-7 — (latent) Culture-sensitive interval formatting in drop_chunks

Severity: Medium — latent, locale-dependent File: src/Cleanup/CleanupManager.cs:277-282

Root cause

DeleteOlderThanDays is a double interpolated directly into SQL with no invariant culture:

older_than => INTERVAL '{deletionTask.DeleteOlderThanDays} days',

On a machine whose current culture uses a comma decimal separator — German-locale TSI machines being the obvious case — a fractional value such as 0.5 renders as INTERVAL '0,5 days' and PostgreSQL rejects the statement.

Non-hypertable tasks are unaffected because they pass the limit as an NpgsqlParameter.

Impact

Latent because every configured DeleteOlderThanDays is currently a whole number, which formats identically in all cultures. The first fractional retention value on a hypertable — e.g. 0.5 for aggressive time-series retention — fails on German machines and works on English ones. That is an unpleasant class of bug to diagnose in the field.

Fix

Format with CultureInfo.InvariantCulture, or pass the interval as a parameter (make_interval(days => @days)) as the non-hypertable path already does.

BUG-8 — (latent) Retryable-exception matching ignores subclasses

Severity: Medium — latent File: src/Core/BaseConnector.cs:73

Root cause

The retry filter compares exception types by exact equality:

catch (Exception ex) when (_retryExceptions.Exists(retryExType => ex.GetType().Equals(retryExType)))

A subclass of a registered retryable exception does not match, so it is not retried.

Impact

RabbitMQConnector registers ConnectFailureException and BrokerUnreachableException. If the RabbitMQ client library throws a more specific derived type — now or after a package upgrade — connection retry silently stops working and the failure escalates to the worker, which (per DebugLoggingBackgroundService) logs Critical and brings the host down.

Fix

Use retryExType.IsInstanceOfType(ex) (or IsAssignableFrom) so derived exceptions are covered.

BUG-9 — Hypertable cleanup always reports "nothing deleted"

Severity: Medium — observability File: src/Cleanup/CleanupManager.cs:98-118

Root cause

The deleted-row count comes from ExecuteSqlRawAsync, whose return value is the affected row count of a non-query. The hypertable path executes SELECT drop_chunks(...), and a SELECT returns -1:

int deleted = await context.Database.ExecuteSqlRawAsync(info.SqlStatements.DeletionSql, info.Parameters, cancellationToken);
...
if (deleted > 0) { /* "Finished deleting data older than ..." */ }
else             { /* "No data older than {Limit} found to delete" */ }

Impact

BendstepMeasurement cleanup always takes the else branch and logs "No data older than … found to delete" — even when it has just dropped chunks containing millions of rows. The single largest table in the database is therefore the one whose retention cannot be verified from the logs, and a genuine "hypertable retention is not working" fault is indistinguishable from normal operation.

Fix

Handle the hypertable branch separately — drop_chunks returns the names of dropped chunks, so use SqlQuery<string> and log the chunk count, or at minimum change the log message so it does not assert that nothing was deleted.

BUG-10 — Stale MachineInfo is attached after an equipment-number change

Severity: Medium Files: src/DataStorage/DataStore.cs:50,464-468; src/Core/MachineInfoManager.cs:65-97; src/DataHubService/Workers/MetaDataExporterWorker.cs:43-53

Root cause

DataStore memoises the primary MachineInfo on first use and attaches that instance to every subsequently created DbContext. There is no invalidation. If MachineInfoManager.UpdatePrimaryMachineAsync later changes the equipment number or type, DataStore continues attaching the stale tracked entity.

Two related weaknesses in the same area:

  • Machine identity is refreshed only at MetaDataExporterWorker start and then once per cycle — every 10 hours by default. An equipment-number change is therefore misattributed for up to 10 hours.
  • If the very first ACT server call is cancelled, the worker returns and neither the statistics export nor any further identity refresh happens again until the host restarts.

Impact

Records can be attributed to a stale machine identity. More seriously, a MINEX restore that replaces the MachineInfo row underneath a running process leaves the cached entity pointing at a primary key that no longer exists, whose failure mode is a foreign-key violation on the next insert.

Fix

Invalidate the memoised instance when MachineInfo is updated (or re-resolve it per unit of work — it is a single-row lookup). Decouple identity refresh from the statistics-export interval. Make a failed first ACT call retry rather than terminate the worker loop.

BUG-11 — Published API documentation states behaviour that does not exist

Severity: Medium — documentation, but published to the wiki Files: src/DataHubService/Workers/MetaDataExporterWorker.cs:7-9; src/MetaDataExporter/DatabaseStatisticsExporter.cs:126-139,173,257

Root cause

The XML summary on MetaDataExporterWorker states that it

"exports DataHub meta data, such as database statistics, as condition log records and writes them to condition logs as well as inserts them into the DataHub database itself."

DatabaseStatisticsExporter only ever performs DbSet.Add followed by SaveChangesAsync. There is no file output anywhere; IIOManager exposes exactly one member, GetFreeDiskSpace.

Impact

Because this comment is published verbatim into Documentation/Component-Documentation/, the wiki tells readers that DataHub statistics appear in the condition-log stream. Anyone building on that expectation will find nothing. Either the comment is stale, or an intended publish path was dropped — worth confirming which, as it changes whether this is a doc fix or a missing feature.

This is the same drift class as the now-removed ConditionLogFileWriter configuration section, which the Confluence arc42 still documents in full but which no longer exists anywhere in code, config or pipelines.

Fix

Correct the XML comment to match the implementation, or reinstate the file export if it is still wanted.

BUG-12 — Cleanup table order is non-deterministic

Severity: Low–Medium File: src/Cleanup/CleanupManager.cs:78-84,270,323-330

Root cause

ProcessTimestampDeletionTasksAsync iterates a Dictionary<string, TimestampDeletionTaskSqlInfo>, whose enumeration order is not contractually guaranteed, and re-evaluates the size/disk gate before every table — returning as soon as the gate no longer holds.

Impact

Under resource pressure, an arbitrary subset of the ~43 configured tables is trimmed and the rest waits for the next 10-minute cycle. There is no notion of priority or of least-valuable data. The configuration format strongly implies that task order expresses deletion priority — and the Confluence documentation states it explicitly ("it executes the first deletion task. After this task is finished, it checks … and if so, executes the second task") — but the implementation does not honour it.

Fix

Preserve configuration order explicitly by using an ordered collection (List<KeyValuePair<…>> or similar) instead of a dictionary, so the documented priority is real.

BUG-13 — encryptAndWriteSecrets.ps1 fragilities

Severity: Low–Medium — build/release robustness File: encryptAndWriteSecrets.ps1:14-15,25-32

Three separate issues in one 32-line script:

a) Hardcoded Debug build path.

$encryptorExePath = [IO.Path]::Combine($pwd, "src", "Encryptor", "bin", "Debug", "net10.0", "Encryptor.exe");

The release pipeline must build Encryptor in Debug purely to satisfy this path. It breaks on a Release-only build, a target-framework bump, or an RID-specific output layout.

b) It rewrites a version-controlled file in place. The target is src/DataHubService/appsettings.json — a tracked file. Running the script on a developer machine leaves encrypted credentials in the working tree, where they can be committed by accident. The ConvertTo-Json round-trip also reformats the entire file (and Out-File may alter the existing UTF-8 BOM), producing a large spurious diff.

c) -Depth 10 has only two levels of headroom. I measured the current maximum nesting depth of appsettings.json at 8, so -Depth 10 is sufficient today — this is not currently a live truncation bug. But the retention condition DSL explicitly supports arbitrarily nested And/Or groups, and two further levels of nesting in a Retain.Condition would exceed the limit. PowerShell truncates silently at that point, which would corrupt the shipped configuration without any error.

Fix

Write secrets to a separate, git-ignored overlay file (appsettings.Production.json or an environment-variable injection) rather than mutating the tracked file; resolve the Encryptor path from the actual build output; raise -Depth well above any plausible nesting.

BUG-14 — Encryptor.exe exits 0 when given the wrong argument count

Severity: Low — robustness File: src/Encryptor/Program.cs:4-15

Root cause

if (args.Length != 2)
{
    Console.WriteLine("Usage:");
    ...
    return;                     // ← exit code remains 0
}

Every other error path sets Environment.ExitCode (EnvironmentVariableNotFound, InvalidArguments), so the contract is internally inconsistent.

encryptAndWriteSecrets.ps1 checks $LASTEXITCODE -ne 0 and otherwise takes stdout as the result. BUG-15 — Debug.Assert guard is compiled out in Release

Severity: Low File: src/ConditionLogRecordDocumentation/Program.cs:105-114

Root cause

The invariant that renamed and alternative record names are disjoint is enforced only by Debug.Assert, and the TryAdd return value is otherwise ignored:

bool successfullyAdded = allNames.TryAdd(alternativeName, actualName);

Throw (or Trace.Assert) instead, so the invariant holds in the build that actually ships.

BUG-17 — MetaDataExporter writes to the database without the global semaphore

Severity: High — the persistence concurrency invariant is broken File: src/MetaDataExporter/DatabaseStatisticsExporter.cs:126-139,173,257

Symptom

One of the three background workers writes to the database without taking the mutex that every other writer takes.

Root cause

All database access in the DataHub is supposed to be serialised through a single process-wide SemaphoreSlim(1,1) exposed as IDatabaseService.DatabaseSemaphore. Grepping for every acquisition of it:

Component Acquires the semaphore?
DataStore (SynchronizedDataHubContext) ✅ DataStore.cs:488
CleanupManager ✅ CleanupManager.cs:93,139
MachineInfoManager ✅ MachineInfoManager.cs:128
DatabaseStatisticsExporter ❌ never

DatabaseStatisticsExporter creates its own context, runs its catalog queries and COUNT(*)s, adds rows and calls SaveChangesAsync — all outside the lock.

Impact

The semaphore exists to guarantee that exactly one database operation is in flight at a time. That is the stated foundation of the persistence design: it is what prevents duplicate referenced entities, EF Core thread-affinity problems and cleanup/insert interference. One writer ignoring it means the invariant does not actually hold.

Concretely, a statistics export can run concurrently with a DataStore batch insert or with a cleanup DELETE + VACUUM (FULL). The most likely observable consequences are lock contention and VACUUM FULL blocking the export's own COUNT(*)s — but "we serialise everything" is now an assumption a future contributor will rely on and be wrong about.

Note this also runs a full-table COUNT(*) over every table (see the design-level notes), so it is not a short operation.

Fix

Wrap the export in IDatabaseService.DatabaseSemaphore like the other three writers. Better still, move the acquisition into DatabaseService itself (e.g. a CreateSynchronizedContextAsync() factory method) so that obtaining a context and holding the lock cannot be separated — the current design makes it easy to forget, and it was forgotten.

BUG-18 — Full record payloads, including Customer-classified data, are written to the plaintext log

Severity: High — data governance Files: src/DataStorage/Caching/Cache.cs:313-316; src/Core/EntityFrameworkCore/Entities/ConditionLogRecordEntity.cs:123-138

Symptom

When a cache flush fails, the complete contents of every affected record are written verbatim into the plaintext log file — regardless of the record's data governance classification.

Root cause

The flush-failure handler logs the elements themselves:

_logger.LogError(ex,
    "Exception occurred during the invocation of the cache flush receiver callback. Data is lost. {@LostElements}",
    new { LostElements = string.Join(", ", elementsToBeFlushed) });

string.Join calls ToString() on each entity, and ConditionLogRecordEntity.ToString() reflects over every property and emits its value:

public override string ToString()
{
    Type type = GetType();
    return $"Entity: {type.Name}, " + string.Join(", ", type.GetProperties().Select(p =>
    {
        ...
        return $"{p.Name}: {p.GetValue(this)}";
    }));
}

There is no filtering on DataGovernanceType. The enum includes Operational, Technology, Environmental and Customer (src/Core/DataGovernanceType.cs).

Impact

The DataHub carries a data governance classification on every record precisely so that handling rules can be applied. This log path ignores it and writes the payload in clear text to C:\ProgramData\TRUMPF\DataHubFramework\DataHub\Logs\Log.txt — which LogFileCollector is configured to harvest off the machine (build/LogFileCollectorConfig/DataHub.xml), and which the integration pipeline publishes as a build artifact.

This compounds badly with BUG-2: because the shutdown flush uses an already-cancelled token, this error path is expected to fire on every service stop, meaning up to 100 records per cache are dumped into the log each time. Fixing BUG-2 largely closes this in practice, but the code path remains a governance hole for any genuine flush failure.

Fix

Log identifiers, counts and record names — not payloads. Something like "Data is lost: 100 records ()" preserves the diagnostic value without the disclosure. If payload logging is genuinely wanted for diagnosis, gate it on governance type and on an explicitly opt-in verbose setting.

BUG-19 — The host fails to start if PostgreSQL is unreachable

Severity: Medium–High — availability File: src/Cleanup/CleanupManager.cs:49,269,390-413

Root cause

CleanupManager's constructor queries the database to discover which tables are TimescaleDB hypertables:

.SqlQuery<string>($"SELECT hypertable_name AS \"Value\" FROM timescaledb_information.hypertables")

An NpgsqlException here is rethrown as InvalidOperationException. Because ICleanupManager is a DI singleton resolved during host start-up, a database that is unreachable at that moment prevents the entire host from starting — including the REST and GraphQL surfaces that have nothing to do with cleanup.

Impact

The DataHub is otherwise carefully defensive about its dependencies: RabbitMQ absence is tolerated, ACT server failure degrades to a fallback equipment number, and transient database failures are retried. This one path is different — it is a hard start-up dependency on PostgreSQL being up at that instant.

On a machine, service start order is not fully under the DataHub's control. The installer explicitly starts the PostgreSQL service before running efbundle.exe, which suggests the ordering concern is already known. If PostgreSQL is slow to become ready after a machine boot, the DataHub may fail to start and rely on the service control manager to retry.

Fix

Move hypertable discovery out of the constructor and into the first cleanup cycle, where a failure can be logged and retried on the next 10-minute tick. The DataHub would then start and serve queries even if cleanup is temporarily unable to initialise — which is the correct trade-off given the other two dependencies are already handled that way.

BUG-20 — Worker loops can spin without delay

Severity: Medium — CPU / resource Files: src/DataHubService/Workers/CleanupWorker.cs:34-48; src/DataHubService/Workers/MetaDataExporterWorker.cs:55-68

Root cause

The try/catch (OperationCanceledException) sits inside the while body, and the catch swallows the exception without breaking out:

while (!stoppingToken.IsCancellationRequested)
{
    try
    {
        await _cleanupManager.PerformCleanupAsync(stoppingToken);
        _logger.LogInformation("Cleanup done. Sleeping {TotalMinutes} minutes.", _interval.TotalMinutes);
        await Task.Delay(_interval, stoppingToken);
    }
    catch (OperationCanceledException)
    {
        _logger.LogDebug("Task was canceled.");      // ← no break, no delay
    }
}

If an OperationCanceledException originates from anything other than stoppingToken — a linked token, or an EF Core / Npgsql command timeout surfacing as cancellation — then stoppingToken.IsCancellationRequested is still false, the loop condition holds, and the next iteration starts immediately. Because the exception can be thrown before Task.Delay is reached, there is no delay at all.

Impact

A tight, delay-free loop that repeatedly attempts cleanup (or statistics export) and repeatedly fails, burning CPU on a machine whose whole point is not to have its CPU burned by the DataHub (quality goal: co-existence). Each iteration logs only at Debug, so with the production Information minimum level the spin is invisible in the logs.

Fix

Distinguish the two cases:

catch (OperationCanceledException) when (stoppingToken.IsCancellationRequested)
{
    break;      // genuine shutdown
}
catch (OperationCanceledException ex)
{
    _logger.LogWarning(ex, "Cleanup cancelled unexpectedly.");
    await Task.Delay(_interval, stoppingToken);      // still back off
}

BUG-21 — GroupByDynamic reflects over unvalidated client input

Severity: Medium — security / robustness Files: src/Core/GraphQL/QueryableExtensions.cs:24-47; src/GraphQLSourceGeneration/GraphQLSourceGenerator.cs:176-181

Root cause

Every generated Aggregate{X}(groupBy: String) resolver passes the client-supplied string straight into reflection with no validation:

MemberExpression property = Expression.Property(parameter, propertyName);   // propertyName is client input

Impact

Two distinct problems:

  1. It bypasses the GraphQL schema as an allow-list. Expression.Property resolves any public property of the entity type, including properties that the GraphQL schema does not expose. The resolved value is then returned to the caller as AggregationResult.GroupingValue, so a client can read the distinct values of a property that was deliberately not part of the API surface. This is an information-disclosure path around the schema.

  2. Unknown property names throw. Expression.Property raises ArgumentException for a name that does not exist, which surfaces as a server error rather than a GraphQL validation error — so a typo produces a 500-class failure instead of a useful message.

This is not SQL injection: the expression tree is translated by EF Core, so no SQL text is concatenated. The risk is schema-surface bypass and error handling, not query injection.

Fix

Validate propertyName against the set of properties the GraphQL schema actually exposes for that type before building the expression, and return a GraphQL validation error for anything else. A generated enum of permitted grouping keys per type would be strictly better than a String argument — the source generator already knows the property set, so it can emit it.

BUG-22 — GraphQL has no depth, complexity or timeout limits

Severity: Medium — availability / DoS File: src/DataHubService/Program.cs:146-154

Root cause

The GraphQL server is configured with projections, filtering and sorting, but none of HotChocolate's protective options:

services
    .AddGraphQLServer()
    .RegisterDbContextFactory<DataHubContext>()
    .AddQueryType<Query>()
    .AddSubscriptionType<Subscription>()
    .AddInMemorySubscriptions()
    .AddProjections()
    .AddFiltering()
    .AddSorting();

There is no MaxExecutionDepth, no cost/complexity analysis (ModifyCostOptions), no execution timeout, no mandatory paging and no persisted-query allow-list. The limit argument supplied by [UseLimit] is optional, so omitting it returns the entire table.

Impact

An unauthenticated caller — and per BUG-4 that includes anyone who can reach either port — can issue a deeply nested or unbounded query against a multi-gigabyte database on a machine control PC. Because there are also no non-primary-key indexes, such a query is a sequential scan. This is a straightforward way to degrade a production machine's IPC, and it requires no credentials.

Fix

Set MaxExecutionDepth, enable cost analysis with a budget, add an execution timeout, and make paging mandatory (or give limit a default rather than leaving it optional).

BUG-23 — Async CleanUp() is invoked without awaiting, including from Dispose()

Severity: Low–Medium — resource cleanup File: src/DataStorage/RabbitMQ/RabbitMQCommunication.cs:56,73,92 vs the declaration at :222

Root cause

Communication.CleanUp() is declared internal async Task CleanUp() but is invoked in three places without await — one of which is the synchronous Dispose(). The returned Task is discarded, so cleanup proceeds concurrently with (or after) disposal, and any exception inside it is unobserved.

Impact

Channel cancellation and closure may not have completed when Dispose() returns. Unobserved exceptions land in TaskScheduler.UnobservedTaskException — which the host does log as Critical, so this would appear as an alarming but non-actionable log entry. During shutdown or broker reconnection, channel state may be left inconsistent.

Fix

Make the disposal path IAsyncDisposable and await the cleanup, or block deliberately and document why.

BUG-24 — The cache flush blocks the calling ingest thread

Severity: Low–Medium — performance File: src/DataStorage/Caching/Cache.cs:216,239-260

Root cause

AttemptFlushCache performs a blocking SemaphoreSlim.Wait() on the caller's thread, then starts the flush with Task.Run + ContinueWith that nobody awaits during normal operation. The caller is the ingest path — a REST request thread or the RabbitMQ consumer callback.

Impact

This partially undermines the purpose of write-behind caching. An ingest call that happens to trigger a flush blocks synchronously until it can acquire the flush semaphore, so a REST POST can be delayed by an in-progress flush — the precise coupling the cache exists to remove. On a thread-pool thread this also risks pool starvation under burst load.

Fix

Use await WaitAsync(...) on the flush semaphore and make the trigger path fully asynchronous.

BUG-25 — Licence document and SBOM generation depends on an LLM API key

Severity: Low–Medium — supply chain / legal reproducibility File: azure-pipelines-integrationTest-template.yml (variable group Tat.LicenseGenerator_ApiTokens; GitHubApiKey, GeminiApiKey)

Observation

The Tat.LicenseGenerator tool that produces the shipped licence document and the CycloneDX sbom.json requires a GitHub API key and a Gemini (LLM) API key at build time.

Why this is worth a decision rather than a fix

Two consequences:

  1. The build is not reproducible or hermetic. Producing a shippable package requires two external services to be reachable and two credentials to be valid. An expired key or an API outage blocks a release.
  2. A legal artifact is generated with LLM assistance. The licence disclosure installed onto customer machines is, in part, LLM-derived. Whether that is acceptable is a question for legal/compliance, not for engineering — but it should be a conscious decision, and I could not find it recorded anywhere.

Flagging rather than prescribing: someone with the compliance context should confirm this is intended and signed off.

BUG-27 — .editorconfig rules have no severities, so nothing is enforced

The .editorconfig codifies conventions the code base does not follow, and because no style rule carries a :warning or :error severity, none of them are enforced by the build — despite TreatWarningsAsErrors being set.

Reconcile the two — update the rules to match what the code base actually does, then attach severities so the build enforces them from that point on. Doing it in that order avoids a large mechanical diff.

BUG-29 — operationalReadiness is async with no await

Severity: Low — hygiene File: src/DataHubService/Controllers/TrumpfAnalyticsController.cs:76-84

CheckOperationalReadiness is declared async but contains no await, which produces a compiler warning (CS1998) — notable given TreatWarningsAsErrors is enabled, so it is presumably suppressed somewhere. More importantly, the method is hardcoded to report ready: it does not check the database, the AMQP consumer, or whether machine identity was resolved.

See also the design-level note on the absence of health checks — this endpoint is the closest thing the DataHub has to one, and it always says yes.

Design-level concerns (not defects — decisions worth revisiting)

Recorded here for completeness because they surfaced in the same review, but each is a legitimate design choice rather than a bug. They are documented with full rationale in docs/11_technical_risks.md on branch arc42.

Topic Concern
No authentication or TLS Both listeners bind 0.0.0.0 over plain HTTP with no authn/authz, and the installer opens a firewall rule. Presumably an accepted reliance on machine-network isolation — but it is not written down anywhere, and it is the reason BUG-4 has no second line of defence. Worth an explicit ADR.
At-most-once AMQP delivery autoAck: true, non-durable exchange and queue, no prefetch limit, no dead-letter exchange, then an in-memory cache. Any crash drops in-flight records with no redelivery. Plausibly the right trade-off for telemetry (ADR-11 notes the data also exists in the cloud) — but currently an implicit assumption rather than a recorded decision.
Cleanup gate is conjunctive Retention engages only when the database exceeds its cap and free disk is below the floor. This is deliberate and commented (otherwise another process filling the disk would make the DataHub delete its own data). The consequence: with the shipped defaults of 2 GB and 100 GB, a machine with a roomy disk never triggers cleanup and the database grows past its stated cap indefinitely. The integration test has to set the free-disk threshold to 999 TB to make cleanup fire at all.
Global database semaphore All database access is serialised through one SemaphoreSlim(1,1). This eliminates a whole class of concurrency bug, but it is a hard throughput ceiling — and cleanup's VACUUM (FULL, ANALYZE) holds it while rewriting a table under an ACCESS EXCLUSIVE lock, blocking all ingestion for the duration. Combined with the unbounded cache queue, a slow vacuum grows the heap with no back-pressure.
No non-primary-key indexes ForeignKeyIndexConvention is removed and the model declares no HasIndex. A defensible write-throughput trade-off, but it means cleanup's correlated NOT EXISTS subqueries are sequential scans executed while holding the global semaphore.
No schema verification at runtime The service never checks GetPendingMigrations(). A deployment where efbundle.exe was skipped or failed starts normally and manifests only as per-query errors and dropped batches.
No health check There is no health endpoint, and GET /api/operationalReadiness reports ready unconditionally — including when PostgreSQL is unreachable or the AMQP consumer never attached.
