FP182NewLantekLicensing

product: psb org: metamation tags: [code-review, PSB, licensing] project: PlatformServiceBend branch: feature/FP-182-new-lantek-licensing ticket: FP-182 date: 2026-07-09 reviewer: Claude status: open

Code Review — FP-182 New Lantek Licensing

Scope

Migrates the Lantek license provider from the Protection.Key.Standard package to Lantek.Licensing.Key.Client, switches the NuGet feed to the Azure DevOps Artifactory feed, and bumps some Microsoft.Extensions.* packages.

Files changed

  • NuGet.Config
  • src/PlatformServiceBend.Core/PlatformServiceBend.Core.csproj
  • src/PlatformServiceBend.Licensing/LicenseProvider/Lantek.cs
  • src/PlatformServiceBend.Licensing/PlatformServiceBend.Licensing.csproj

Overall: migration reads cleanly (the System.Linq removal is correct, and AreProtectionsAvailable([code])[0] → IsProtectionAvailable(code) is a good simplification). A few items below are worth attention before merge.

[!warning] Verification limitation The new Lantek.Licensing.Key.Client package could not be restored or inspected locally (feed 403 + not in NuGet cache), and run5199280.json in the working tree is a CI result for a different branch (release/26.7.0), so it does not prove this branch compiles. The API-shape findings are reasoned from the call sites, not verified against the assembly.

Findings

🔴 1. Factory call in the field initializer defeats the graceful-degradation try/catch

File: Lantek.cs:65

readonly LKeyClient.IClient _lantekKey = LKeyClientFactory.Create();

The constructor wraps OpenKey in a try/catch so that a licensing failure logs a warning and leaves "all features unavailable" rather than crashing (Lantek.cs:14-19). But C# runs instance field initializers before the constructor body — so LKeyClientFactory.Create() executes outside that try block.

The old code was new Key() (a plain, cheap ctor). A factory Create() is far more likely to do real work (load native DLLs, probe a dongle/driver) and throw. If it does, the exception propagates out of the Lantek ctor → out of the switch at AppLicensing.cs:40 → out of the AppLicensing ctor. Since AppLicensing is registered as a singleton (Program.cs:52), DI construction fails and the app fails to start — exactly the outcome the try/catch was meant to prevent.

Suggested fix: create the client inside the try block (assign in the ctor) so a Create() failure is caught like an OpenKey failure.

🟠 2. Inconsistent / partial version bump in PlatformServiceBend.Core.csproj

File: PlatformServiceBend.Core.csproj:27-30

Only two of the four Microsoft.Extensions.* packages were bumped to 10.0.9:

Package Version
Configuration.Abstractions 9.0.5 → 10.0.9
Configuration.Binder 9.0.5 (unchanged)
Hosting.Abstractions 9.0.5 (unchanged)
Logging.Abstractions 9.0.5 → 10.0.9

This leaves version skew within the same package family (NuGet unifies upward, likely emitting NU1608-style warnings, and mixes v9/v10 assemblies). By contrast Licensing.csproj bumped all three of its packages consistently to 10.0.9, which makes the Core split look like an accidental/incomplete edit.

Suggested fix: bump the whole family to 10.0.9 or none of it.

🟠 3. Production dependency on a 0.x pre-release

File: PlatformServiceBend.Licensing.csproj:29

<PackageReference Include="Lantek.Licensing.Key.Client" Version="0.4.5-beta" />

A 0.4.5-beta package gating licensing is a stability/supply-chain risk: pre-release APIs (OpenKey, IsProtectionAvailable, CloseKey, ClientFactory.Create) can change between betas, and 0.x implies no API-stability guarantee. The version is pinned exactly (good). Confirm this is intentional for the target release.

🟡 4. Licensing is effectively inert — all FeatureCodes are 0 (pre-existing)

File: Lantek.cs:58-62

All three features map to protection code 0, so CheckFeatures() calls Take(0) for everything. Since Service is required at AppLicensing.cs:49 to keep the Lantek provider, the provider will almost certainly fall back to the grace period unless code 0 happens to be "available" — and IsProtectionAvailable(0)'s behavior against a real key is unknown (could throw).

Not introduced by this PR (there is a // TODO and a prior "restore feature codes to 0" commit), but since this PR is the licensing migration, confirm real codes / the new LantekBendLicenseGroup = 55 opening group aren't blocked on this before shipping.

Minor / non-blocking

  • run5199280.json is an untracked stray Azure DevOps run dump in the repo root — don't accidentally commit it (add to .gitignore or delete).
  • The NuGet.Config change is fine; encoding %40 for @Local in the Azure feed URL is expected.

Bottom line

  • #1 is the one to fix before merge — it can turn a recoverable licensing failure into a startup crash.
  • #2 looks like an oversight worth a one-line fix.
  • #3 / #4 are judgment calls to confirm with the team.
