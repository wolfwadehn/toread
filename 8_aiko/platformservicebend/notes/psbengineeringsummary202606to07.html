PlatformServiceBend — Engineering Summary (Jun–Jul 2026)

Technical reference for all PSB work carried out across Claude Code sessions between 2026-06-16 and 2026-07-09 (21 sessions analysed). Organised by topic/ticket rather than chronologically. For the FP-182 review specifics see [[FP-182 New Lantek Licensing]].

[!info] What "PSB" is PlatformServiceBend is a .NET service that wraps the Flux bending engine (Flux.Core / Flux.API, referenced from the mapped drive X:\Src\bin\*.dll) behind a versioned HTTP API (/api/v1…). Work is tracked under FP-xxx Jira tickets; PRs live in Azure DevOps.

Recurring environment & constraints

These apply across almost every session — capture them once:

  • Local integration tests return 403. Tests in the [Collection("FluxApi")] group boot a real Flux WPF app + API over localhost:8099; the corporate proxy (srv01prox2v) returns a bare-HTML 403 Forbidden. Workaround: NO_PROXY=localhost,127.0.0.1,::1, otherwise inspect built artifacts instead of running end-to-end. See memory local-integration-tests-403.
  • Flux source/binaries live on X:\ (X:\Src, X:\Src\bin, test data under X:\Data\Machine). Flux internals behind the //FLUX.CORE boundary are not in this repo — inspect DLL string tables / MetadataLoadContext reflection when signatures are needed.
  • Snapshot tests self-heal only when missing. Assert.EqualWithJsonFile / EqualWithFile write a baseline only if the file is absent; updating C# without deleting the stale .json/.txt/OpenAPI snapshot silently leaves them out of date. Several sessions had to delete-and-regenerate. Beware locally regenerated Pickup snapshots — they can contain degenerate IK poses (see FP / 26.7 below) and should not be committed.
  • Azure DevOps MCP exposes build/pipeline tools only (no PR/git-content). PR comments, diffs, and iterations were driven via the REST API with AZURE_DEVOPS_EXT_PAT (az CLI). ⚠️ The PAT was echoed to a terminal in one session — rotate if not already done.
  • Git Bash vs PowerShell heredocs. PowerShell @'…'@ heredocs leak literal @ into commit messages / mangle /p: MSBuild switches under Git Bash. Use bash <<'EOF' heredocs and the -p: switch form.

1. Licensing — FP-182 New Lantek Licensing (current branch)

Branch: feature/FP-182-new-lantek-licensing · PR #232685 · headline in-flight work.

What/why. Migrate the Lantek license provider off Protection.Key.Standard onto the new Lantek.Licensing.Key.Client package that supports the new licensing system, and point NuGet at the Azure DevOps Artifactory feed.

Key changes

  • LicenseProvider/Lantek.cs: new Key() → LKeyClientFactory.Create() + OpenKey/CloseKey; AreProtectionsAvailable([code])[0] → IsProtectionAvailable(code); dropped the now-unused System.Linq.
  • NuGet.Config: Lantek feed switched to the real Azure DevOps feed (%40Local = @Local, expected).
  • PlatformServiceBend.Licensing.csproj: <PackageReference Include="Lantek.Licensing.Key.Client" Version="0.4.5-beta" />; all three Microsoft.Extensions.* bumped to 10.0.9.
  • Config constants: LantekProgramName = "PlatformServiceBend", LantekYear = 2026, LantekVersion = "V46", LantekBendLicenseGroup = 55.

Code review (session 826e323d, high effort, report-only) — 4 findings:

# Sev Finding Status
1 🔴 LKeyClientFactory.Create() in the field initializer runs outside the ctor try/catch → a throwing factory crashes DI/startup, defeating graceful degradation. Fixed (commit 6127b250: Create() moved into the try; field now = null!).
2 🟠 Only 2 of 4 Microsoft.Extensions.* bumped → version skew. Fixed (commit 0970d946: all at 10.0.9).
3 🟠 Production dependency on 0.4.5-beta pre-release (pinned, but 0.x = no API-stability guarantee). Judgment call — confirm with team.
4 🟡 All FeatureCodes map to protection code 0 → licensing effectively inert; IsProtectionAvailable(0) behaviour vs a real key unknown. Pre-existing (// TODO). Open — confirm real codes before shipping.

[!warning] Verification limitation The new package could not be restored/inspected locally (feed 403 + not cached), and run5199280.json in the working tree is a CI result for a different branch (release/26.7.0) — it does not prove this branch compiles. API-shape findings were reasoned from call sites. Also: run5199280.json is an untracked stray dump — gitignore or delete.

Follow-up recommendation: prefer IClient? _lantekKey (nullability as the "is-open" signal, drop the _lantekKeyOpen bool) over = null!, which suppresses the exact nullable analysis that guards the failure path.

2. Bend-cell robot endpoints

FP-185 — Pickup/deposit "parts per stack" (session 60525be9, feature/FP-185-expand-stack, 9ac21fa7)

What/why. Resolve a TODO in BendTechPickupSequenceEndpoints asking for the number and positions of parts per source stack (e.g. topmost part per stack). The flat pickup sequence returned one step per part but wasn't partitioned into physical stacks.

  • There is no explicit Stack entity; parts map to BendCellComponent (shelf/pallet/furniture). "Topmost" = highest PartIndexInStage on deposit / next-to-pick on pickup.
  • The adapter collapsed the single Pickup/Shelf so per-part→stack mapping was lost (PartIndexInStage = NOverall). Reconstructed grouping from the Flux PPlan model (Qty, per-item Matrix.X/Y/Z, Shift, Corner, LastInLayer) → column/row/layer.
  • Scope reduced late: the flat PickupAction/DepositAction already carry identical stack info, so the grouped deposit /stacks endpoint + DTOs were removed and a redundant IsFirstToPick flag dropped. Shipped = grouped pickup /stacks endpoint + flat StackColumn/StackRow/Layer/Position fields on both sequences.
  • Files: BendTechPickup/DepositSequenceEndpoints.cs, ApiServer.cs, BendTechAdapter.cs, BendTechService.cs, DTO PickupStacks.cs (kept) / DepositStacks.cs (added then removed); background snapshot tests + regenerated OpenAPI/GetPickupStacks.json.
  • Status: committed & pushed; build clean; tests green against a reprogrammed Multi-Pickup-657.1.fx baseline. An intermittent NullReferenceException at partRef.Instance.BendTech.CellTech.Q was confirmed pre-existing (session loaded without bend tech), resolved after the session was reprogrammed.
  • Security-reviewed (sessions a51b40fa add / 885c8f22 + c0d90a51 removal): no findings — reuses GetPartSessionInfo() auth, only bool includeNulls is client-controllable.
  • Merged into refactor/Test-fixes-for-26.7 in session 3c7c2bc4 (clean, no conflicts).

FP-189 — Backgauge signal lost under "No Extraction" (session 16d5c185, feature/FP-189-backgauge-signal-no-extraction)

What/why. With the "No Extraction" robot strategy, BackgaugeMoveToNextPosition (and F_PRESS_CMD(5)/F_PRESS_CHECK(5)) was no longer emitted.

  • Root cause: StepSignalAdapter.cs:24 attached the signal only on the PostBendSafe phase; the No-Extraction .ls program omits PostBendSafe/PostBendSafe2, so the signal vanished.
  • Fix (+4/−1): keep PostBendSafe emission; add a fallback emitting the signal on the always-present UpOpen phase, guarded by a new StageHasPostBendSafe(stage) helper so it only fires when the stage lacks PostBendSafe → double-emission impossible. Mirrors pre-migration logic hinted in a commented TODO.
  • Branched from freshly-fetched origin/main (local main was 3 commits stale).
  • Status: committed; Adapter project builds clean (0 warnings). Runtime/e2e not verified (403). Baselines: GetBendTech_BM60Large = canonical correct case; GetBendTech_AB15_Winkel and GetBendTechWithNulls flagged for confirmation (possible double-emit with PartRotate).

3. DTO/adapter refactors migrated from FanucTest → main

Session 81830b49 replayed two already-merged FanucTest PRs onto the restructured main (FluxService.* → src/PlatformServiceBend.*). Diffs were hand-applied to strip the stray UTF-8 BOM the source commits injected.

FP-179 — PartRef Name → FileName/CodeFileName (feature/FP-179-Extend-regripstage, 80abbf0b)

  • PartRef.Name (backed by Info.PartID) split into FileName = Info.FileNameBase and CodeFileName = Info.CodeFileName. Files: PartRef.cs, PartAdapter.cs, PartService.cs, SessionService.cs.
  • NOT an API-breaking change: verified against FanucTest source that test assertions on generated download filenames (Content-Disposition, e.g. single-bend_machine-13.dxf, -27.jupidu) were unchanged — FileNameBase/CodeFileName yield the same strings as old PartID for these fixtures. Security review (f507a389): no findings; reduces attack surface vs the old user-settable PartID (on-disk names sanitised via Path.GetFileName).
  • ⚠️ Branch is named "Extend-regripstage" but the RegripStage change was added and reverted within the source PR → no RegripStage change actually merged.

FP-180 — Move AngleCorrection to PressBeamSettings (feature/FP-180-move-anglecorrection-to-pressbeamsettings, bcf9c77c)

  • Property renames (ClosingSpeed→RapidDownwardSpeed, PinchPoint*→Clamping*, DecompressionPosition→DecompressionDistance, OpeningSpeed→RapidUpwardSpeed), AngleCorrection moved onto PressBeamSettings, BendStage.PressBeam split into read-only params + configurable settings, BendingForce added, DecompressionMode enum replaced by a DecompressionAutomatic bool; PressBeamSettingsAdapter.From(BendOpSettings) widened internal → public. 4 DTO + 4 adapter files.
  • ⚠️ Breaking API change. DTO/JSON schema changes on GET/PUT for …/bend/tech/settings/press-beam, …/stages/{i}/settings/press-beam, …/stages, …/stages/{i}, …/basic and machine-settings routes. Highest risk: on PUT press-beam, old field names silently fail to bind — values dropped, no error. A full release-notes breaking-change description was produced. Security review (e63bbada): no findings.
  • Status (both): committed to feature branches, not pushed (awaiting go-ahead); solution + tests build clean. OpenAPI snapshot regen blocked locally (403).

4. Tool Setup Optimizer (TSO) — Jupidu NC corrections

Backend ingestion (session cc2c441d, no ticket, not committed by request)

What/why. Determine whether TSO auto-consumes operator corrections from uploaded NC/Jupidu code, then implement server-side ingestion.

  • Finding: PSB's pipeline is strictly FX-in → FX/NC/PDF-out; NC is only ever generated (Flux.ProgOutput.GenBendCode), never consumed. Flux's own Flux.JupiduReader (X:\Src\Core\Bend\Ops\JupiduReader.cs) does read corrections (angle → op.Settings.AngleCorrection, plus backgauge/ACB/pass-through in MiscData), but auto-load lives in TSOBatch.PartData (.jupidu sibling via Path.ChangeExtension(OriginalFile, ".jupidu")), not in the BOptimizer.Optimize path PSB calls — so it never triggers in PSB today.
  • Design "Option B": call Flux's JupiduReader.Update() directly (same entry point TSOBatch uses) rather than adopting the opinionated TSOBatch/BendBoost.BatchTSO pipeline (different output layout, report templates, Permit.BendTSO gate, bool/Error() error model).
  • Pairing by filename convention (part.jupidu beside part.fx, both via the existing files field). Mismatch = warn, not fail (SeqChanged/PartChanged/OldJupidu/corrupt-zip → optimises without corrections). New nullable DTO fields Corrected / CorrectionMessage (null omitted so existing snapshot stays green).
  • Files: ToolSetupOptimizerAdapter.cs (ApplyJupiduCorrections), ToolSetupOptimizerService.cs, ToolSetupOptimizerPartResult.cs, ToolSetupOptimizerEndpoints.cs, tests + fixtures. Final run 11 passed / 1 skipped (positive-path test skipped: depends on machine 120097 not in the default test DB). Left uncommitted for user review.

Demo app (session d33749e1, demos/PlatformServiceBend.Demo)

  • Let the WPF demo upload .jupidu alongside .fx in the same multipart request. No backend change — pairing already exists server-side.
  • File dialog + drag/drop accept both extensions; ordered/deduped List<string> mPaths as source of truth; ListBox bound to ObservableCollection<FileRow> rebuilt via RebuildFileRows() pairing FX with case-insensitive base-name jupidu (orphan jupidu → warning). Spec committed; build clean.

5. Test infrastructure — FP-177 Flux phase catalog regression

Branch: feature/FP-177-Phases-test. Guards against Flux bending phases changing between versions.

  • Create (session ecd93a78, ceab9d01): enum-catalog snapshot via reflection. Step.Phase comes from bendStep.Q.Phase.ToString() = Flux.EBPhase (166 members); Flux.API.EBPhase = 161 (differs by 5 internal members). Two committed .txt baselines (FluxPhases.txt 166, FluxApiPhases.txt 161), format {value} = {name} sorted by value so a rename is a one-line diff. TDD: 11 classifier unit tests + 2 enum snapshot tests; tamper-tested end-to-end. Added a Flux.Core project reference.
  • Simplify after PR feedback (session be8aec95, cb37531d, −296 lines): reviewer questioned the custom EqualWithFile + PhaseCatalog class. Confirmed the only genuinely-needed behaviour was line-ending tolerance (.txt baselines check out CRLF via * text=auto; renderer emits LF). Deleted PhaseCatalog.cs (~90 lines) + PhaseCatalogTests.cs (13 tests), inlined into a RenderPhases helper, switched to the existing EqualWithFile(ignoreLineEndingDifferences: true). The diff/classify machinery only relabelled renames in the failure message (cosmetic; xUnit's string diff already pinpoints the line).
  • Security-reviewed twice (229dd1d5 add / 53e2c063 simplify): test-only, no source→sink path, no findings.

6. Release & build engineering

Version stamping / PSB 1.0.0 release (sessions 34b01365 + 98c9279f)

  • Release model: tag-driven. azure-pipelines-release.yml's ResolveReleaseContext parses psbVersion from refs/tags/release/<x.y.z> and fluxVersion from a pipeline parameter. Created release/26.6.0 (from main @ cb49da70) + tag release/1.0.0; bumped release-pipeline FluxVersion default 26.2.0 → 26.6.0. Produced PRs #226947 (main) / #226948 (release, merged).
  • Root cause of wrong reported version: /api/v1/basic/info reads AssemblyInformationalVersion from the Http assembly, whose csproj hardcoded 0.0.1-beta.209, overriding the pipeline $(Version). The +<sha> suffix is SDK SourceLink. Real bug = property-name mismatch: /p:AssemblyInformationalVersion is a no-op; the SDK reads InformationalVersion. Fix renamed the pipeline arg in both YAMLs.
  • Follow-up (98c9279f) answering Florian's PR comment: empirically confirmed command-line /p: global properties override <PropertyGroup> and propagate down <ProjectReference> — proven by building App with -p:Version=99.9.9 and inspecting the baked-in Http.dll (99.9.9-beta.777). So the hardcoded 0.0.1-beta.209 is safe to pin for CI yet still overridden by the pipeline, and was restored (commit 98bb0ed5) because local tests depend on it in the user's unblocked env. Restored the shared X:\Src\bin\Http.dll afterward.

26.7 prep + CVE (session 3f685eff, refactor/Test-fixes-for-26.7)

  • Merged origin/main cleanly (f16726ff); bumped FluxVersion default → 26.7.0 across 5 pipeline YAMLs.
  • NU1903 (GHSA-v5pm-xwqc-g5wc): vulnerable transitive Microsoft.OpenApi 2.3.0 (via Microsoft.AspNetCore.OpenApi 10.0.2 / Swashbuckle.AspNetCore 10.1.0) — fixed by a direct PackageReference pin to 2.7.5; warning cleared on restore.
  • Snapshot analysis: new OverBending/Decompress bend steps + richer acbLaser values are legitimate 26.7 engine changes; but many Pickup robot joint angles (J1–J6) collapsing to degenerate home poses (J2=90, J3=−90) are a local-regeneration artifact (pickup data is normally produced via the proxy-blocked HTTP path) → must not be committed.

CI triage — SonarCloud (session db50c148, advisory only)

  • FileNotFoundException: Plugin resource not found: securitycsharpfrontend 11.35.0.47322 in the "Prepare SonarCloud" step = the scanner failing to download a Roslyn analyzer plugin from the SonarCloud server (exit 0xE0434352 = generic .NET unhandled exception; the downstream SonarQubeAnalysisConfig.xml not found is a cascade). Diagnosed as server-side/transient, unrelated to the branch — recommended re-running.

Cross-cutting observations

  • Snapshot / OpenAPI regeneration is the most common footgun — several sessions spent effort distinguishing legitimate engine changes from local 403/regeneration artifacts. Treat any locally regenerated Pickup/robot-pose baseline with suspicion.
