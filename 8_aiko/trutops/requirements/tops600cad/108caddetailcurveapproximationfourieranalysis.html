CAD Detail — Curve Approximation & Fourier Analysis

Detailed reverse-engineered requirements (Tier: command/algorithm level). Child of [[10 - FR - CAD Geometry & Drawing Editing]]. Reconstructed intent from static source analysis, not an authoritative spec.

1. Purpose & Scope

This document is the algorithm-level refinement of two numerical geometry libraries that sit beneath the interactive CAD editor and the drawing-comparison subsystem:

  • tc_aprox — curve approximation. A strategy-driven engine (Tc_Approximator) that converts a parametrised 2D curve (rational/integral B-spline, polynomial, parametric arc) into a chain of straight-line and circular-arc segments that stay within a caller-defined deviation tolerance. It is the machine that lets a NURBS/spline be exported or manufactured as lines+arcs. It is consumed by IGES export (tc_iges/ig_ausg.cpp), the drawing "thin/linearise" command (tc_dbase/dbase_command/TcDbaseThinCommand.cpp), micro-joint/nest utilities and contour tooling (tc_cad/cad_ttf/TcContour.cpp, tc_nest/taf_util, tc_mi/mi_write.cpp).
  • tc_fou — Fourier contour analysis. Computes a Fourier coefficient set (FKS) and a rotation/scale/translation-invariant Fourier descriptor set (FDS) of a closed contour (TcFourierBeschr), tests whether two contours are geometrically related ("verwandt"), and — when related — recovers the relationship parameters (Drehwinkel = rotation angle, Streckungsfaktor = scale factor, Translationsvektor = translation, plus a combined transformation matrix). It is consumed by the contour/feature finders (tc_dbase/dbase_util/TcDbaseContourFinder, tc_dbase/dbase_pattern/TcPatFeatList, tc_las/las_tech/db/TcKonturenSucher).

It refines the parent system-level requirements: FR-CAD-018 (smooth/thin/linearise), FR-CAD-025 (curve approximation used by smooth/melt/equidistant, IGES/DXF export) and the drawing-comparison capability that consumes Fourier matching. Boolean contour arithmetic is in [[10.7 - CAD Detail - Contour Arithmetic Algorithms]]; the geometry kernel primitives are in [[10.6 - CAD Detail - Geometry Kernel Algorithms]]. German domain terms link to [[04 - Domain Model & Glossary]].

Architecture note (applies throughout Part A). Tc_Approximator is a factory + orchestrator over four pluggable strategy roles (comments at tc_aprox/tc_aprox.cpp:29-39): Parameterstrategie (WHICH parameter interval to approximate next), Segmentstrategie (HOW to approximate that interval — line/arc variants), Verbindungsstrategie (how a new segment connects to the previous one — point/tangent continuity) and Bewertungsstrategie (evaluate/accept a candidate segment and score it). The curve itself is any subclass of the abstract Tc_ParametricCurve (tc_interface/tc_aprox/paracurv.h). Error codes are integers; 0 = success; 10600-10644 = domain errors; 10613/10614 are non-fatal warnings; 10630 = approximation finished (no more segments); 10631 = no acceptable segment found.

Architecture note (applies throughout Part B). A TcFourierBeschr is built from a dbase contour S_kontur*. The contour is (a) forced to a defined orientation (Umlaufsinn), (b) rounded to nk_stellen decimals, (c) polygonised (arcs sampled at F_W_INKR = 10°), (d) reduced to a complex polygon list S_K_KONTUR, then (e) transformed into a Fourier coefficient list S_FOU (struct Fou = {int index; S_KOMPLEX coeff; double winkel; next}) and a normalised descriptor list. Tolerances come from TcToleranzContainer (e_fouEpsilonWert base ≈ 1e-4, e_t3_eilo_FourAnzNKS decimals, e_wert general). All angles internally in radians (converted to degrees at the public boundary).

3. Detailed Requirements

Part A — Curve approximation (tc_aprox)

FR-CAD-APX-001 — Abstract parametric-curve model

  • Requirement: The approximation engine SHALL operate on any curve exposing the Tc_ParametricCurve interface, which SHALL provide: getParamInterval(tmin,tmax), getPoint(t,x,y), getFirstDerivative(t,x,y), getSecondDerivative(t,x,y) and getLength(tStart,tEnd,length). The engine SHALL NOT depend on the concrete curve subtype.
  • Inputs/Outputs & tolerances: Parameter t is a scalar in [tmin,tmax]; points and derivatives are 2D (x,y). Out-of-domain t SHALL yield 10603; incompletely defined curve SHALL yield 10604; undefined derivative SHALL yield 10608.
  • Priority: Essential
  • Rationale: Decoupling the approximator from spline/polynomial/arc specifics is the core design contract; every strategy is written against this interface only.
  • Source: tc_interface/tc_aprox/paracurv.h:12-32; tc_aprox/tc_aprox.cpp:45-73.
  • Verification: Inspection (interface) + Test (drive engine with each concrete curve subclass).

FR-CAD-APX-002 — Integral B-spline point evaluation (de Boor)

  • Requirement: For an integral B-spline of order k with n+1 control points and knot vector of length n+k+1, Tc_BSpline::getPoint(t) SHALL evaluate the curve point using the de Boor recurrence over the support interval containing t, after locating that interval via getInterval.
  • Inputs/Outputs & tolerances: Zero-division in the recurrence weight SHALL be guarded (fakt2 == 0 ⇒ fakt = 0, bspline.cpp:617-624). t outside [param[iStart],param[iEnd]] ⇒ 10603; not fully defined ⇒ 10604; interval not found ⇒ 10605; illegal order ⇒ 10606.
  • Priority: Essential
  • Rationale: Point sampling is the primitive on which every deviation measurement and segment fit ultimately depends.
  • Source: tc_aprox/bspline.cpp:320-343 (getPoint), :555-574 (getInterval), :599-631 (calcBSplineValue).
  • Verification: Test (compare against reference NURBS evaluation at sampled parameters).

FR-CAD-APX-003 — Rational B-spline (NURBS) evaluation with weights

  • Requirement: Tc_BSplineRational SHALL extend the integral B-spline with a per-control-point weight array and SHALL evaluate points in homogeneous coordinates, dividing the weighted x/y sums by the weighted weight sum to obtain non-homogeneous (x,y).
  • Inputs/Outputs & tolerances: Division by the homogeneous weight SHALL be performed only when |w| > 1e-5; otherwise the homogeneous values SHALL be retained unscaled. Weight index outside 0..n ⇒ 10600; undefined weight read ⇒ 10607. isDefined() SHALL require all knots, all knot-vector params and all weights set.
  • Priority: Essential
  • Rationale: Real CAD splines are rational; weights change both point positions and derivatives.
  • Source: tc_aprox/bspliner.cpp:116-162 (getPoint), :407-414 (isDefined), :55-66 (setWeight).
  • Verification: Test (rational vs. integral evaluation of a circle-arc NURBS).

FR-CAD-APX-004 — Open/closed B-splines, knot wrap, uniform knot vector, parameter restriction

  • Requirement: A B-spline SHALL support an open flag selecting support bounds (open: iStart=k-1, iEnd=n+1; else iStart=0, iEnd=n+1). For closed splines, control-point and parameter indices SHALL wrap via calcKnotIndex/calcParamDiff. setUniformParam() SHALL fill a clamped uniform knot vector for open splines and a plain integer sequence otherwise. setParamInterval(tmin,tmax) SHALL further restrict the reported parameter domain to a sub-interval without altering control data.
  • Inputs/Outputs & tolerances: getParamInterval SHALL clamp the restricted [tMin,tMax] into the knot-defined domain when att_restricted is set.
  • Priority: Essential
  • Rationale: Closed contours and clamped-endpoint behaviour are both required by CAD geometry; restriction lets a caller approximate only part of a spline.
  • Source: tc_aprox/bspline.cpp:14-51, :144-175 (setUniformParam), :252-298 (getParamInterval/setParamInterval), :802-882 (wrap helpers).
  • Verification: Test (closed spline continuity across wrap; restricted-domain sampling).

FR-CAD-APX-005 — B-spline first and second derivatives

  • Requirement: getFirstDerivative SHALL evaluate as an order-(k-1) B-spline over the divided differences of the control polygon (scaled by k-1); getSecondDerivative SHALL evaluate as an order-(k-2) B-spline over second divided differences (scaled by (k-1)(k-2)). For rational splines the homogeneous weight derivative SHALL be applied identically.
  • Inputs/Outputs & tolerances: First derivative requires k ≥ 2, second requires k ≥ 3, else 10608.
  • Priority: Conditional (needed only by tangent-continuity and one-sided strategies)
  • Rationale: Tangent continuity (FR-CAD-APX-027) and orientation checks need curve tangents.
  • Source: tc_aprox/bspline.cpp:368-465; tc_aprox/bspliner.cpp:187-352.
  • Verification: Analysis + Test (finite-difference cross-check of derivatives).

FR-CAD-APX-006 — Curve arc-length by adaptive linear interpolation

  • Requirement: getLength(tStart,tEnd,length) SHALL approximate arc length by summing chord lengths of points sampled at a parameter step derived from the straight-line endpoint distance. The B-spline implementation SHALL use at least 5 subdivision steps (so closed curves whose endpoints coincide do not report length 0) and SHALL cap the chord-distance estimate at 10000 to guard against astronomically large splines.
  • Inputs/Outputs & tolerances: tStart<tmin/tEnd>tmax ⇒ 10603; tStart>tEnd ⇒ 10609. Result is an approximation, not exact arc length.
  • Priority: Essential
  • Rationale: Length underlies the curveLength/curveCount parameter strategies and residual checks; the "≥5 steps / cap 10000" guards were added for degenerate closed and huge curves.
  • Source: tc_aprox/bspline.cpp:488-533; tc_aprox/polynom.cpp:287-325.
  • Verification: Test (length of known circle/segment within a few percent).

FR-CAD-APX-007 — Polynomial curve of arbitrary degree (Horner)

  • Requirement: Tc_Polynom(order n) SHALL represent a 2D polynomial with n+1 (cx,cy) coefficients and SHALL evaluate points and derivatives via Horner's scheme. getPoint SHALL require all coefficients defined (10604) and t ∈ [tmin,tmax] (10603).
  • Inputs/Outputs & tolerances: First derivative requires n ≥ 1, second requires n ≥ 2, else 10608. Coefficient index outside 0..n ⇒ 10610; undefined coefficient read ⇒ 10611.
  • Priority: Optional (supported curve family, less used than splines)
  • Rationale: Provides a lightweight parametric curve family reusing the same approximation engine.
  • Source: tc_aprox/polynom.cpp:169-265; tc_aprox/polynom.h.
  • Verification: Test (polynomial point/derivative vs. closed-form).

FR-CAD-APX-008 — Parametric circular-arc curve

  • Requirement: TcParametricArc SHALL represent an arc parametrised by angle, defined by start point, centre point, end point and a direction (CLW/CCLW). getParamInterval SHALL return start and end angles via atan2 (normalised to [0,2π), end raised by 2π when start > end); for a clockwise arc the start/end angles SHALL be swapped, and getPoint SHALL invert the parameter (t = minAngle + maxAngle − t) so the reported parameter always increases. getLength SHALL return angle × radius.
  • Inputs/Outputs & tolerances: Incomplete definition (start, centre, end and direction not all set) ⇒ 10604. Derivatives are intentionally not implemented (return 1).
  • Priority: Conditional
  • Rationale: Lets arcs be handled through the same Tc_ParametricCurve contract as splines.
  • Source: tc_aprox/parametricarc.cpp:84-260; tc_interface/tc_aprox/parametricarc.h.
  • Verification: Test (arc point/length vs. analytic).

FR-CAD-APX-009 — Parametric-arc definition and radius-consistency validation

  • Requirement: When start/centre/end are set incrementally, TcParametricArc SHALL verify that the start-to-centre and end-to-centre radii agree within S_Tolerance = 0.0001; a mismatch SHALL return 10644 and reject the offending point. When all four defining items are set, the internal min/max angles SHALL be (re)computed.

  • Verification: Test (square ⇒ symmetry 4, rectangle ⇒ 2, circle ⇒ special).

FR-CAD-APX-044 — Orientation detection from spectrum

  • Requirement: The engine SHALL infer the contour orientation from the coefficient spectrum: when the first significant coefficient does not have index 1, it SHALL compute the index-(−1) coefficient; if that is non-zero the orientation SHALL be F_LINKS_SYS (CLW) and the (−1) coefficient re-anchored to the list head, otherwise error 213. When the first significant index is 1 and symmetry > 2, orientation SHALL be F_RECHTS_SYS (CCLW). Otherwise it SHALL remain F_UNBEKANNT.
  • Priority: Conditional
  • Rationale: Confirms/derives winding needed for consistent comparison and for the descriptor normalisation reference.
  • Source: tc_fou/f_math.cpp:1119-1152; enums tc_fou/f_glob.h:87-89.
  • Verification: Test (orientation reported per known contours).

FR-CAD-APX-045 — Circle special-case description

  • Requirement: When the contour's single element is a circle, the engine SHALL bypass the polygon integrals: c0 SHALL be the (rounded, optionally transformed) circle centre, c1 SHALL be the circle radius, the symmetry degree SHALL be infinity (F_UNENDL), orientation F_RECHTS_SYS and type = 1 (circle). The descriptor d1 SHALL be 1.
  • Inputs/Outputs & tolerances: Radius rounded to nk_stellen; F_UNENDL = 1e308.
  • Priority: Essential
  • Rationale: A circle has no finite symmetry degree; the analytic path avoids polygonisation error and yields exact scale via the radius ratio.
  • Source: tc_fou/f_math.cpp:789-867 (f_rech_kreis_fks_u_fds), :1532-1540.
  • Verification: Test (two circles ⇒ scale = radius ratio, angle 0).

FR-CAD-APX-046 — Standard tool-type recognition

  • Requirement: During coefficient computation the engine SHALL, where possible, classify the contour as a standard tool type per the CAPT tool table: 1 = circle, 2 = rounded rectangle, 3 = square, 4 = rectangle, 7 = rounded square, 8 = slot (Langloch), 16 = radius; otherwise 0. The recognised type SHALL set the coefficient index stride (FR-CAD-APX-043).
  • Priority: Conditional
  • Rationale: Enables standard-punch matching and faster/cleaner spectra for regular shapes.
  • Source: tc_fou/f_math.cpp:1071-1082, 1310-1315; TcFourierBeschr.cpp:389.
  • Verification: Test (standard shapes classified correctly).

FR-CAD-APX-047 — Fourier descriptor computation (invariant fingerprint)

  • Requirement: The engine SHALL compute a descriptor set (FDS) by normalising each non-zero coefficient (index ≠ 0) against a normalisation coefficient (the index-1 or index-(−1) coefficient with magnitude > e_fouEpsilonWert), dividing by it and multiplying by a phase term e^{ i·((idx_norm − idx)/symmetryDegree)·Δφ }, where Δφ is the phase difference of the two normalisation coefficients. The resulting descriptors SHALL be invariant to start-point shift, rotation, size and translation.
  • Inputs/Outputs & tolerances: If too few coefficients exist to normalise, no descriptors are produced (diagnostic printed).
  • Priority: Essential
  • Rationale: Descriptors are the comparison key; invariance is what lets "same shape, any pose/size" be detected.
  • Source: tc_fou/f_math.cpp:1184-1286 (f_rech_poly_dk, f_rech_poly_fds).
  • Verification: Analysis + Test (descriptors unchanged under rotation/scale/translation of one contour).

FR-CAD-APX-048 — Relationship (verwandtschaft) test via descriptor comparison

  • Requirement: doCompare(other, tol) SHALL report two contours as related iff their descriptor sets are identical in both index sequence and coefficient values within tol (compareFourierDeskriptorenSaetze): descriptors SHALL be compared pairwise (index equality AND |Δreal| < tol AND |Δimag| < tol), and the sets SHALL have equal length.
  • Inputs/Outputs & tolerances: tol is caller-supplied (drawing-comparison tolerance); a NULL set fails the comparison.
  • Priority: Essential
  • Rationale: This boolean is the gate before any relationship parameters are computed; it is the core of geometric duplicate/feature detection.
  • Source: tc_fou/TcFourierBeschr.cpp:546-555; tc_fou/f_kont.cpp:1007-1044, :943-992 (f_pruefe_2_fou_list_auf_ident).
  • Verification: Test (congruent/similar shapes match; different shapes do not).

FR-CAD-APX-049 — Relationship parameter: rotation angle (Drehwinkel)

  • Requirement: f_rech_poly_dphi SHALL compute the rotation angle carrying the reference contour onto the comparison contour from the phase angles of two matched coefficients (indices q and r): φ = (r·(φ_q^ek − φ_q^rk) − q·(φ_r^ek − φ_r^rk))/(r − q), rounded to the tolerance grid. When symmetry is to be honoured (genau = 1), the angle SHALL be reduced modulo 360°/(r−q) (equivalently 360°/symmetryDegree) so that, e.g., a square's 90/180/270° relate to 0°; otherwise it SHALL be reduced modulo 360°. The result SHALL be returned in radians internally.
  • Inputs/Outputs & tolerances: Tolerance grid = e_fouEpsilonWert; requires matching coefficient indices, else error 224.
  • Priority: Essential
  • Rationale: Rotation recovery is one of the three relationship outputs the CAD/comparison layer needs to place one contour onto another.
  • Source: tc_fou/f_math.cpp:1581-1660.
  • Verification: Test (rotate a contour by known angle ⇒ recovered angle within tolerance; square symmetry folding).

FR-CAD-APX-050 — Relationship parameter: scale factor (Streckungsfaktor)

  • Requirement: f_rech_poly_my SHALL compute the scale factor μ as the magnitude ratio of the first significant coefficient of the comparison contour to that of the reference contour (|c1^ek| / |c1^rk|), provided their indices match; it SHALL also report the absolute magnitude difference. Missing coefficients ⇒ error 224. For a circle, μ SHALL instead be the real-part ratio of the radius coefficients (FR-CAD-APX-045).
  • Priority: Essential
  • Rationale: Scale recovery is required to decide size identity and to build the transformation matrix.
  • Source: tc_fou/f_math.cpp:1403-1428; circle path :1886-1895.
  • Verification: Test (scaled contour ⇒ recovered μ equals scale factor).

FR-CAD-APX-051 — Relationship parameter: translation vector (Translationsvektor)

  • Requirement: The engine SHALL compute two translation-related vectors: (a) f_rech_poly_delta(μ, φ, rk, ek) = c0^ek − e^{iφ}·μ·c0^rk, the vector accounting for a tool reference point differing from the centroid (rotation and scale included); and (b) f_rech_poly_translation(rk, ek) = c0^ek − c0^rk, the pure centroid-to-centroid shift used when assembling the transformation matrix. Vectors SHALL be returned in the xy plane.
  • Priority: Essential
  • Rationale: Translation completes the pose; the code history (comments) shows the centroid-shift form is the one used in the matrix, while delta covers non-centroid reference points.
  • Source: tc_fou/f_math.cpp:1694-1777.
  • Verification: Test (translated contour ⇒ recovered translation equals shift).

FR-CAD-APX-052 — Relationship transformation matrix assembly

  • Requirement: f_rech_verwandt_parameter SHALL assemble the relationship (Verwandtschafts-) matrix as the product rotation × scale × translation, where rotation is about the z-axis through the reference contour's centroid (drehe_um_gerade about c0, not the origin), scale is skalierungs_matrix(μ,μ,1) and translation uses the centroid-to-centroid vector. For a circle it SHALL set angle 0 and derive μ and translation analytically. Absence of a c0 coefficient ⇒ error 250.
  • Priority: Essential
  • Rationale: The single matrix applied to the reference contour reproduces the comparison contour — the deliverable of the whole relationship computation.
  • Source: tc_fou/f_math.cpp:1872-1960; matrix helper f_rechne_fourier_matrix :1810-1825.
  • Verification: Test (applying matrix to reference points reproduces comparison points within tolerance).

FR-CAD-APX-053 — Relationship API (calcRelationship)

  • Requirement: calcRelationship(other, optWinkel, μ, angle, translation, matrix) SHALL return the scale factor, rotation angle (converted to degrees at the boundary), translation vector and transformation matrix for two related descriptions; optWinkel = true SHALL request the symmetry-folded minimal angle. It SHALL succeed only when both descriptions are status-OK and the underlying computation returns 0. It SHALL NOT re-test relatedness (the caller must have called doCompare first).
  • Inputs/Outputs & tolerances: Angle output in degrees; internal radians converted via RAD_TO_DEG.
  • Priority: Essential
  • Rationale: The public façade over FR-CAD-APX-049..052 used by consumers.
  • Source: tc_fou/TcFourierBeschr.cpp:686-733.
  • Verification: Test (end-to-end recovery of angle/scale/translation for a posed contour).

FR-CAD-APX-054 — Size-identity comparison (doCompareSizeIdentity)

  • Requirement: doCompareSizeIdentity(other, tol, matrix) SHALL report the contours as identical in size iff their descriptors match within tol AND the recovered scale factor satisfies |μ − 1| < tol; on success it SHALL output the relationship matrix.
  • Priority: Essential
  • Rationale: Distinguishes congruent (same-size) shapes from merely similar ones — needed for true duplicate detection.
  • Source: tc_fou/TcFourierBeschr.cpp:572-601.
  • Verification: Test (same-size relatives pass; scaled relatives fail).

FR-CAD-APX-055 — Pose-identity comparison (doCompareLookIdentity)

  • Requirement: doCompareLookIdentity(other, tol, matrix) SHALL report identity iff size identity holds (FR-CAD-APX-054) AND the recovered 2D rotation angle of the relationship matrix is ≈ 0 within the general tolerance e_wert. It SHALL assert/fail when either description is not status-OK (e.g. an open contour).
  • Priority: Conditional
  • Rationale: Detects contours that are identical and already in the same orientation (no rotation needed) — e.g. to avoid re-placing an already-aligned feature.
  • Source: tc_fou/TcFourierBeschr.cpp:617-655.
  • Verification: Test (same size + same angle passes; rotated copy fails).

FR-CAD-APX-056 — Contour centroid retrieval (getSchwerpunkt)

  • Requirement: getSchwerpunkt(vector) SHALL return the contour centroid as the real/imag parts of the index-0 Fourier coefficient (z = 0), returning false when no c0 coefficient exists.
  • Priority: Conditional
  • Rationale: The centroid is a useful placement/anchor point and the rotation pivot.
  • Source: tc_fou/TcFourierBeschr.cpp:746-771.
  • Verification: Test (centroid equals geometric centroid of known contour).

FR-CAD-APX-057 — Symmetry and orientation accessors

  • Requirement: The description SHALL expose getSymmetrie() (rotational symmetry degree), getSymmetrieAngle() (360°/degree) and getUmlaufsinn() (−1 = CLW, 0 = undetermined, 1 = CCLW).
  • Priority: Optional
  • Rationale: Consumers use symmetry degree/angle for angle folding and orientation for comparability checks.
  • Source: tc_fou/TcFourierBeschr.cpp:486-533.
  • Verification: Inspection + Test (accessor values for known shapes).

FR-CAD-APX-058 — Complex-number tolerance stages

  • Requirement: Equality of two complex coefficients SHALL be tested component-wise (|Δreal| < ε AND |Δimag| < ε), where ε is the base Fourier tolerance e_fouEpsilonWert multiplied by 10^(stage−1) for stage ∈ {1,2,3,4} (stage 1 ≈ 1e-4, stage 2 ≈ 1e-3, stage 3 ≈ 1e-2, stage 4 ≈ 1e-1).
  • Priority: Essential
  • Rationale: A single, documented tolerance ladder underlies coefficient significance, symmetry detection and descriptor comparison; the stage lets callers relax matching.
  • Source: tc_fou/f_math.cpp:408-454 (f_ident_k_zahlen, compareKoeffizienten).
  • Verification: Test (stage widens the acceptance band by decades).

FR-CAD-APX-059 — Consumer integration contract

  • Requirement: The two libraries SHALL be usable by higher-level features without modification: the approximator by IGES export, the drawing thin/linearise command, nest/micro-joint utilities and contour tooling; the Fourier description by the contour finder, pattern/feature list and laser contour searcher. Each consumer SHALL configure the approximator strategies it needs and SHALL gate Fourier relationship recovery on a prior doCompare/isStatusOK.
  • Inputs/Outputs & tolerances: IGES export uses te_adaptiv + te_maxDistance + te_minLength; the thin command adds te_maxRadius.
  • Priority: Conditional
  • Rationale: Documents the intended integration surface and typical strategy recipes, grounding the parent FR-CAD-018/025 refinements.
  • Source: tc_iges/ig_ausg.cpp:1199-1308; tc_dbase/dbase_command/TcDbaseThinCommand.cpp:1000-1150; tc_dbase/dbase_util/TcDbaseContourFinder.cpp; tc_dbase/dbase_pattern/TcPatFeatList.cpp; tc_las/las_tech/db/TcKonturenSucher.cpp.
  • Verification: Demonstration (drive one consumer end-to-end for each library).

4. Open Questions & Ambiguities

  1. Least-squares direction fit details. The header documents Tc_ApproxSegmentLeastSquareLine as "point + slope via Gauss least squares" but the exact normal-equation formulation and the sampling count feeding it are inside segmstg.cpp (calcLinePoint/calcDirection) and were not fully traced. The att_precision = 20 figure is captured; the residual weighting is not. (inferred that it is unweighted uniform sampling.)
  2. te_maxLength two-parameter overload bug. In addEvaluationStrategy(strategy, param1) the te_minLength case constructs a Tc_ApproxEvalMinLength, but in the two-parameter overload te_minLength constructs a Tc_ApproxEvalMaxLength (tc_aprox.cpp:524). This looks like a copy-paste defect; unclear whether any caller exercises the two-parameter min-length path.
  3. Exact symmetry-folding branch for negative angles. The f_rech_poly_dphi genau=1 branch (f_math.cpp:1628-1644) has non-obvious sign handling around delta/*dphi; the precise intended behaviour for angles near the half-symmetry boundary should be confirmed against test vectors.
  4. FGlob_AnzahlKoeffizienten runtime value. F_ANZ_PRUEF_KOEFF = 4 is the compile-time constant, but the actual count used is the global FGlob_AnzahlKoeffizienten; where/when it is set (and whether it can differ from 4 at runtime) was not located in the read slice.
  5. delta vs translation selection. f_rech_verwandt_parameter computes both f_rech_poly_delta (returned as *delta) and f_rech_poly_translation (used to build the matrix). The extensive comment history shows repeated reversals; which vector a given consumer should trust as "the translation" is context-dependent and should be documented per consumer.
  6. Circle vs polygon symmetry infinity handling in comparison. doCompare on a circle relies on descriptor d1 = 1; how two circles of different radius (same descriptors, different c1) interact with doCompareSizeIdentity when symmetry is F_UNENDL should be verified.
  7. Units of the approximation tolerance. Assumed to be drawing units (mm or inch per GRITUNIT), inherited from the curve's coordinate space; not asserted in tc_aprox itself. (inferred.)
  8. Derivative-free parametric arc + tangent connection. TcParametricArc does not implement derivatives (returns 1), so using te_tangent connection with an arc curve would fail; whether any path combines them is unconfirmed.
