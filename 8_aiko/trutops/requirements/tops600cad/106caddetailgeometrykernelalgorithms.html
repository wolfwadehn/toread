CAD Detail — Geometry Kernel Algorithms

Detailed reverse-engineered requirements (Tier: command/algorithm level). Child of [[10 - FR - CAD Geometry & Drawing Editing]]. Reconstructed intent from static source analysis, not an authoritative spec.

1. Purpose & Scope

This document specifies, at the algorithm/implementation level, the 2-D geometry kernel that underpins the TruTops CAD editor. It refines the system-level requirements of the parent [[10 - FR - CAD Geometry & Drawing Editing]] (in particular FR-CAD-001..035 concerning geometry creation, editing, contour arithmetic, snapping and dimensioning) by documenting the primitives, numeric tolerances, and algorithms on which those interactive commands depend.

The primary implementation surveyed is the managed GeoAlgorithmsKernel / GeoKernel assembly (Trumpf.TruTops.GeoKernel.*, C#), which supersedes the older native tc_math primitives. Where CAD's native C/C++ layer (cad_asm, tc_dbase, tc_geoPlan, tc_math, tc_geoUtils) still hosts geometry, this is noted, together with the C++/CLI GAKUnmanagedAdapter bridge that marshals native Element/Kontur/Teil structures into the managed kernel.

Scope covered here:

  • Geometric primitives and their operations: point/vector, line segment, arc segment, curve, single-area, area, bounding box.
  • Element–element intersection (line-line, line-arc, arc-arc) and tolerance handling.
  • Point-in-contour / containment (curve-point, curve-segment, curve-curve, area).
  • Transformation matrices and composition (2-D homogeneous 3×3; native 4×4).
  • Distance / nearest-point / orthogonal projection / tangent computations.
  • Contour orientation, oriented area size, and centroid.
  • Higher-level shape recognition and convex-hull generation.
  • The topological plan/graph model (tc_geoPlan corner/element iterators; GeoKernel DCEL half-edge structure) and the quad-tree spatial index.
  • Metric/inch consistency, and the managed/unmanaged bridge.

Out of scope (covered elsewhere): boolean contour arithmetic (offset/union/difference) — see [[10.7 - CAD Detail - Contour Arithmetic Algorithms]]; curve approximation and Fourier analysis — see [[10.8 - CAD Detail - Curve Approximation & Fourier Analysis]]; punching/laser technology decomposition (GeoAlgorithmsKernel/PunchUp, Technologie).

German domain terms used: Kontur=contour, Ecke=corner, Element=element (line/arc/circle), Äquidistante=equidistant/offset, Rundung=fillet, Fase=chamfer, Langloch=slot/oblong, Fläche=area, Fangen=snapping, Winkelhalbierende=angle bisector, Umschreibendes Rechteck=bounding rectangle. Link terms to [[04 - Domain Model & Glossary]].

3. Detailed Requirements

FR-CAD-KRN-001 — Immutable 2-D vector / point primitive

  • Requirement: The kernel SHALL provide an immutable 2-D vector type (TcGeoVector) storing double-precision X, Y, exposing a cached Length = sqrt(X²+Y²) and GetSquareLength(), providing the singletons NULL_VECTOR (0,0), UNIT_VECTOR_X (1,0), UNIT_VECTOR_Y (0,1), and a factory CreateRotatedVector(angle, length) / CreateRotatedUnitVector(angle). The same type SHALL represent both free vectors and positional points in the plane.
  • Inputs/Outputs & tolerances: Inputs are two doubles (or a copy source). Length is computed once at construction. CreateRotatedVector asserts length > 0. No unit is intrinsic to the vector; values are interpreted in the active drawing unit (mm or inch, see FR-CAD-KRN-009).
  • Priority: Essential
  • Rationale: Immutability lets vectors be shared by reference across segments/curves without defensive copies (exploited by the copy-ctors of TcGeoLineSegment/TcGeoArcSegment), simplifying the whole kernel.
  • Source: GeoAlgorithmsKernel/GeoKernel/GeoElements/TcGeoVector.cs (fields mX/mY/mLength, readonly; NULL_VECTOR, ctor).
  • Verification: Inspection (immutability), Test (length/factory values).

FR-CAD-KRN-002 — Vector arithmetic operators

  • Requirement: TcGeoVector SHALL support operator +, binary and unary -, scalar * (both operand orders), and scalar /, each returning a new immutable vector computed component-wise.
  • Inputs/Outputs & tolerances: Exact IEEE-754 double arithmetic; no tolerance applied. Division by zero yields ±∞/NaN per IEEE-754 (not guarded).
  • Priority: Essential
  • Rationale: Vector algebra is the substrate for every downstream geometric computation.
  • Source: TcGeoVector.cs (#region Operators).
  • Verification: Test.

FR-CAD-KRN-003 — Absolute angle of a vector

  • Requirement: The kernel SHALL compute the vector's absolute angle via AbsoluteAngle_Atan2() returning atan2(Y,X) in (−π, π], and AbsoluteAngle() returning the angle normalized to [0, 2π), with an explicit guard that prevents the result reaching 2π through floating-point overshoot (resetting to 0.0).
  • Inputs/Outputs & tolerances: Undefined for the zero vector — asserted (Debug.Assert(X!=0 || Y!=0)); in release builds a zero vector yields atan2(0,0)=0. Output range invariant asserted 0 ≤ angle < 2π.
  • Priority: Essential
  • Rationale: Consistent [0,2π) normalization is required by arc parameterization and corner-angle computations.
  • Source: TcGeoVector.cs AbsoluteAngle()/AbsoluteAngle_Atan2().
  • Verification: Test (boundary near 2π), Analysis (zero-vector edge case).

FR-CAD-KRN-004 — Vector equality within tolerance

  • Requirement: TcGeoVector.Matches(other[, tolerance]) SHALL return true iff the squared Euclidean distance between the two points is ≤ tolerance², using TcDefinitions.TOL as the default tolerance. The tolerance SHALL be asserted non-negative.
  • Inputs/Outputs & tolerances: Comparison uses squared distance (no square root) against squared tolerance. Default tolerance TOL = 1e-4 mm (FR-CAD-KRN-008).
  • Priority: Essential
  • Rationale: Point coincidence is the atomic tolerance decision reused by segment-matching, curve closedness, circle detection, and intersection snapping.
  • Source: TcGeoVector.cs Matches(...).
  • Verification: Test.

FR-CAD-KRN-005 — Dot product and 2-D cross product

  • Requirement: The kernel SHALL provide ScalarProduct (dot product x1·x2 + y1·y2) and VectorProductZ/CrossProductZ (the z-component of the 3-D cross product, x1·y2 − y1·x2) as TcGeoVector extension methods.
  • Inputs/Outputs & tolerances: Exact double arithmetic, no tolerance. The sign of VectorProductZ encodes left/right orientation used by corner convexity tests.
  • Priority: Essential
  • Rationale: Dot/cross products drive angle, projection, orientation, area, and left/right decisions throughout the kernel.
  • Source: TcGeoVectorExtensions.cs ScalarProduct, VectorProductZ, CrossProductZ.
  • Verification: Test.

FR-CAD-KRN-006 — Orthogonal, rotation and normalization operations

  • Requirement: The kernel SHALL provide GetOrthogonalClw() = (Y, −X), GetOrthogonalCclw() = (−Y, X), GetRotated(angle) (2-D rotation by angle rad), and GetNormalized() (divide by cached length).
  • Inputs/Outputs & tolerances: GetNormalized() divides by Length; on a zero vector this yields NaN (not guarded). Rotation uses Math.Cos/Sin.
  • Priority: Essential
  • Rationale: Offset/equidistant construction (normal direction) and arc point evaluation depend on these.
  • Source: TcGeoVectorExtensions.cs (GetOrthogonalClw/Cclw, GetRotated); TcGeoVector.cs GetNormalized.
  • Verification: Test.

FR-CAD-KRN-007 — Direction relation tests (parallel / antiparallel / orthogonal / angle)

  • Requirement: The kernel SHALL provide IsParallelTo, IsAntiparallelTo, IsParallelOrAntiparallelTo, IsOrthogonalTo, AngleTo, and GetDirectionRelation (LEFT/RIGHT/EQUAL/INVERTED) for direction vectors. Parallelism SHALL be decided by comparing the distance between the normalized vectors against TcDefinitions.TOL_ANGLE_RAD (exploiting the small-angle approximation d = 2·sin(α/2) ≈ α); orthogonality by |cos α| < TOL_ANGLE_RAD; AngleTo SHALL return a value in [0,π] clamping cos α to [−1,1] to avoid acos domain errors.
  • Inputs/Outputs & tolerances: Default angular tolerance TOL_ANGLE_RAD = TOL_ANGLE_DEG·π/180 = 0.01°·π/180 ≈ 1.745e-4 rad. Zero-length inputs asserted invalid.
  • Priority: Essential
  • Rationale: These decide colinearity, right-angle detection, and the parallel/overlapping branch of line-line intersection.
  • Source: TcGeoVectorExtensions.cs (IsParallelTo, IsAntiparallelTo, IsOrthogonalTo, AngleTo, GetDirectionRelation); TcDefinitions.cs.
  • Verification: Test, Analysis (small-angle approximation validity).

FR-CAD-KRN-008 — System-wide tolerance constants

  • Requirement: The kernel SHALL centralize numeric tolerances in TcDefinitions with defaults: TOL = 1e-4, TOL_AREA = 1e-4, TOL_PERCENT = 0.001, TOL_ANGLE_DEG = 0.01 (deriving TOL_ANGLE_RAD), TOL_TWINLINE_DISTANCE = 0.001, SCALLOP_HEIGHT = 0.15, OVERLAPPING = 2.0, TOL_MIN_SCRAP_AREA_REMOVAL_PARTS = 1e-8, plus flags INCH_MODE, MULTITHREADING_ENABLED, BOOLEAN_LIBRARY_LOGGING (all default false). SetDefinition(key, value) SHALL validate ranges (e.g. TOL ∈ [0, MaxValue), TOL_PERCENT ∈ [0,100), TOL_ANGLE_DEG ∈ [0,360)) and throw ArgumentException for unknown keys or out-of-range values. The helper TOL_PARAM_FOR_LENGTH(length) = TOL / max(TOL, length) SHALL convert a length tolerance into a segment-parameter tolerance.
  • Inputs/Outputs & tolerances: Values are set at startup and may be overridden per TruTops version (metric/inch). Units are millimeters unless INCH_MODE transforms them.
  • Priority: Essential
  • Rationale: A single, validated tolerance source guarantees consistent tolerance behavior across every algorithm and both unit systems.
  • Source: GeoElements/TcDefinitions.cs.
  • Verification: Test (range validation), Inspection (default values).

FR-CAD-KRN-009 — Metric / inch unit consistency

  • Requirement: Where a fixed length threshold is used, the kernel SHALL scale it to the active unit via TcDefinitions.ConvertMmToInchIfNecessary(valueInMm), which divides by 25.4 when INCH_MODE is set. On the native side, the tolerance singleton TcToleranzContainer SHALL supply per-purpose tolerances (enumerated TeToleranz: length, value, area, degree, radian, coarse length, fine value, …) selected by the gritunit metric/inch flag, with values loaded from the database (toleranz.asc, e.g. length metric 1e-4 vs inch 1e-5).
  • Inputs/Outputs & tolerances: Conversion factor exactly 25.4. toleranz.asc records carry the unit column (0=metric, 1=inch, 99=unit-independent).
  • Priority: Essential
  • Rationale: CAD ships in metric and inch builds; hard-coded thresholds (e.g. the 0.05 mm relevance threshold in convex-hull bridging) must track the active unit to keep behavior geometrically equivalent.
  • Source: TcDefinitions.cs ConvertMmToInchIfNecessary; used in TcGeoConvexHullGeneration.cs; tc_math/TcToleranzContainer.h, tc_math/toleranz.asc.
  • Verification: Test (both modes), Inspection.

FR-CAD-KRN-010 — Abstract segment parameterization contract

  • Requirement: The kernel SHALL define an abstract TcGeoSegment (implementing TiGeoElement, TiBoundingBox, TiTransformable, ICloneable) exposing Start, End, Length, BoundingBox, a Parent curve reference, and the parameterization contract ParameterToPoint(t), PointToParameter(point), DirectionInPoint, DirectionAtParameter, CreateParallelSegment, SnapParameterToEnds, GetInvertedSegment, GetTransformed, Clone. Segment parameter t=0 SHALL map to Start and t=1 to End.
  • Inputs/Outputs & tolerances: Concrete subtypes are TcGeoLineSegment and TcGeoArcSegment; dispatch elsewhere is by runtime type test (is).
  • Priority: Essential
  • Rationale: A uniform parametric contract lets curves, intersection, projection and containment treat lines and arcs polymorphically.
  • Source: GeoElements/TcGeoSegment.cs.
  • Verification: Inspection.

FR-CAD-KRN-011 — Finite line segment

  • Requirement: TcGeoLineSegment SHALL represent a finite line from Start to End, exposing Direction = End − Start, lazily-cached normalized NormDirection, Length = |Direction|, ParameterToPoint(t) = (1−t)·Start + t·End, and PointToParameter(p) = ((p−Start)·Direction)/|Direction|² (i.e. orthogonal-projection parameter). DirectionInPoint/DirectionAtParameter SHALL return NormDirection regardless of the argument.
  • Inputs/Outputs & tolerances: PointToParameter yields values outside [0,1] for points beyond the segment ends. Zero-length segments produce division by zero (callers must ensure Length > TOL; asserted in DebugAssertConsistency).
  • Priority: Essential
  • Rationale: Lines are the most common contour element; the projection-based parameter is reused by intersection and distance.
  • Source: GeoElements/TcGeoLineSegment.cs.
  • Verification: Test.

FR-CAD-KRN-012 — Arc segment representation and span angle

  • Requirement: TcGeoArcSegment SHALL represent an arc by Center, Radius, Start, End, StartAngle, EndAngle, and Orientation (CLW/CCLW), providing constructors from (center, start, enclosed angle), (start, end, center[, radius], orientation, isCircle-flag), and (center, startAngle, endAngle, radius, orientation, isCircle). It SHALL compute the oriented SpanAngle (negative for CLW, positive for CCLW; ±2π for a full circle) and Length = |SpanAngle · Radius|. ParameterToPoint(t) SHALL rotate (Start − Center) by t·SpanAngle; t=0→Start and t=1→End are returned exactly.

FR-CAD-KRN-013 — Arc full-circle detection and handling

FR-CAD-KRN-022 — Centroid / center of gravity

FR-CAD-KRN-027 — Line–line intersection

  • Requirement: Line-line intersection SHALL classify the base-geometry relation as Identic / Parallel / Intersecting / NotIntersecting and the segment relation as NoCommonPoints / Intersecting / Overlapping. FR-CAD-KRN-028 — Line–arc intersection

  • Requirement: Line-arc intersection SHALL compute the distance d from the arc center to the infinite line; classify Touching when |Radius − d| ≤ min(tolerance, 0.5·Radius) (touch point = orthogonal projection of center onto the line), Intersecting when d < Radius (two points at parameterMiddle ± sqrt(R²−d²)/lineLength about the center's projection), else NotIntersecting. Each candidate point SHALL be reclassified to a segment common point only if it lies on both finite segments. The arc-line overload SHALL delegate to line-arc and swap the result.

  • Rationale: Line-arc is needed for trimming lines against fillets/holes and for tangency detection.

FR-CAD-KRN-029 — Arc–arc intersection

FR-CAD-KRN-032 — Point-in-curve (ray-casting) test

  • Requirement: TcGeoCurve.Intersect(point, tolerance[, bboxesHolder]) SHALL classify a point as OUTSIDE, OVERLAPPING (on the boundary), or INSIDE. It SHALL (1) reject points outside the tolerance-expanded curve bounding box as OUTSIDE; (2) report OVERLAPPING when the minimum distance to any bounding-box-candidate segment is < tolerance; (3) otherwise perform a parity (even-odd) ray-cast, counting crossings of a probe segment from the point to just outside the bounding box, with zero intersection tolerance. Probe directions SHALL be chosen cyclically across the four bounding-box sides at a fixed pseudo-random sequence of side parameters; when a probe hits a vertex (parameter within 1e-6 of a segment end) or touches/overlaps a segment, the result SHALL be deemed ambiguous and the test retried with a different probe, up to 99 attempts.
  • Inputs/Outputs & tolerances: Boundary band = tolerance (default TOL). Ray-cast crossing uses tolerance 0. Fixed RNG seed (new Random(1)) makes the probe sequence deterministic. After 99 ambiguous tries, the last parity result is returned and a diagnostic logged.
  • Priority: Essential
  • Rationale: Point-in-contour is fundamental to selection, hole classification, containment and technology assignment; the retry-on-ambiguity scheme robustly handles the degenerate cases (vertex/tangent hits) that break naive ray casting.
  • Source: GeoMath/TcGeoIntersectionCurvePoint.cs; relation enum TcGeoIntersectionDataCurvePoint.TeRelationCurvePoint {OUTSIDE, OVERLAPPING, INSIDE}.
  • Verification: Analysis (parity method & ambiguity handling), Test (point near vertex, on edge, inside, outside).

  • Source: tc_math/TcTransformationMatrix.h; used by tc_geoPlan/TcGeoPlan.h ctors and GAK bridge (ConvertToAdapterVektor(..., transformation)).
  • Verification: Inspection.

FR-CAD-KRN-041 — Line-point distance and orthogonal projection

  • Requirement: The kernel SHALL provide CalcLinePointDistance(line, point) (= |NormDirection × (point−Start)|, absolute perpendicular distance to the infinite line), CalcLinePointOrientedDistance (signed variant giving left/right side), CalcOrthogonalProjectionParameter, and CalcOrthogonalProjectionPoint(line, point[, out parameter]) (foot of perpendicular on the infinite line).
  • Inputs/Outputs & tolerances: No tolerance; exact. The oriented distance sign encodes half-plane membership.
  • Priority: Essential
  • Rationale: Perpendicular distance and projection are needed for snapping, dimension witness lines, line-arc touch detection and overlap tests.
  • Source: GeoMath/TcGeoMath.cs (CalcLinePointDistance, CalcLinePointOrientedDistance, CalcOrthogonalProjection*).
  • Verification: Test.

FR-CAD-KRN-042 — Segment-point nearest distance

  • Requirement: TcGeoSegment.DistanceTo(point) SHALL return the true nearest distance from a point to the finite segment: for a parameter within [0,1] the perpendicular distance, otherwise the distance to the nearer endpoint. For an arc whose center equals the point, it SHALL return the radius. DistanceFromPointToStraightLine SHALL give the perpendicular distance to the infinite line of a line segment.
  • Inputs/Outputs & tolerances: Endpoint clamping avoids reporting perpendicular distance to a projection lying beyond the segment. Center-coincidence special case avoids an undefined arc parameter.
  • Priority: Essential
  • Rationale: Correct point-to-segment distance underlies the boundary band of point-in-curve, snapping to nearest element, and proximity queries.
  • Source: GeoElements/TcGeoSegmentExtensions.cs DistanceTo, DistanceFromPointToStraightLine.
  • Verification: Test (foot inside, beyond ends, arc center case).

FR-CAD-KRN-043 — Nearest vertex / edge lookup

  • Requirement: The kernel SHALL provide TcGeoArea.NearestVertex(point) (the segment start point at minimum Euclidean distance; throws on an empty area), FindVertex(vertex, out edge1, out edge2) (the two edges meeting at a matching vertex) and FindEdge(point, out edge) (an edge on which the point lies). GetLongestSegment/GetShortestSegment and their index variants SHALL select extremal segments from a collection.
  • Inputs/Outputs & tolerances: Vertex matching uses TcGeoVector.Matches. Edge membership uses the point-in-curve/segment overlap tolerance.
  • Priority: Conditional
  • Rationale: Snapping to vertices/edges and identifying corner geometry (for fillet/chamfer) require nearest-feature lookups.
  • Source: GeoElements/TcGeoAreaExtensions.cs (NearestVertex, FindVertex, FindEdge); TcGeoSegmentExtensions.cs (GetLongestSegment, etc.).
  • Verification: Test.

FR-CAD-KRN-044 — Circle / arc tangent construction

  • Requirement: The kernel SHALL compute tangents: CalcTouchingPointsOfTangentThroughExteriorPoint(center, radius, exteriorPoint) (two touch points via the Thales circle / two-circle radical construction, with reprojection onto the circle for numerical robustness), CalcTouchingPointsOfOuterTangentsOfTwoCircles (outer common tangents via the intercept theorem for unequal radii or the center-normal for equal radii), and the arc-clamped variants TcGeoArcSegment.GetTangentPointsThroughExteriorPoint, GetTouchingPointsOfTangentThroughExteriorPoint, GetTouchingPointsOfOuterTangentsToArcSegment, GetTouchingPointOfTangentForTangentDirection that filter/clamp touch points to the arc's parameter range.
  • Inputs/Outputs & tolerances: Exterior-point precondition asserted (|p−center| > radius + TOL). Computed points reprojected if they exceed radius + TOL. Arc variants keep only touch points with parameter in [0,1].
  • Priority: Conditional
  • Rationale: Tangent construction is required by the arc-aware convex hull and by tangent-line/round-off editing operations.
  • Source: GeoMath/TcGeoMath.cs (CalcTouchingPointsOf…); TcGeoArcSegment.cs GetTangentPointsThroughExteriorPoint; TcGeoSegmentExtensions.cs (GetTouchingPointsOf…).
  • Verification: Analysis (construction correctness), Test.

FR-CAD-KRN-045 — Shape recognition (square / rectangle / round)

  • Requirement: TcGeoShapeRecognizer SHALL identify canonical tool/part shapes centered at the origin: IdentifyRectangularShaped(area, out width, out height) (area is a rectangle, axis-parallel, symmetric about the origin within TOL), IdentifySquareShape(area, out sideLength) (rectangle with |width−height| < TOL), and IdentifyRound(area, out radius) (single circle centered at the origin with radius > TOL; excentric rounds — e.g. push-out tools — return false). IsOblongTool is declared but not implemented (asserts false).
  • Inputs/Outputs & tolerances: All comparisons use TcDefinitions.TOL. Excentric/off-origin shapes are rejected as not-recognized (by design, for tool typing).
  • Priority: Conditional
  • Rationale: Recognizing standard tool footprints (round, square, rectangular, oblong) drives punch-tool selection and technology mapping.
  • Source: GeoElements/TcGeoShapeRecognizer.cs.
  • Verification: Test (positive & excentric cases), Inspection (IsOblongTool not implemented).

FR-CAD-KRN-046 — Curve / area shape predicates

  • Requirement: The kernel SHALL provide shape predicates on curves and areas: IsCircle, IsPolygon, IsConvexPolygon, IsTriangle, IsQuadrangle, IsConvexQuadrangle, IsRectangle([tolerance]), IsParallelogram, IsTrapezoid, HasAnyLineSegment/HasOnlyLineSegments, HasAnyArcSegment/HasOnlyArcSegments, HasAnyRightAngle/HasOnlyRightAngles, and segment/corner convexity tests (IsConvex/IsConcave for arcs; IsConvexCorner/IsConcaveCorner using the sign of the corner cross product against orientation, threshold TOL). Rectangle recognition SHALL require four line segments each orthogonal to its successor (checked via orthogonal-direction match within lengthTolerance).
  • Inputs/Outputs & tolerances: IsRectangle default tolerance TOL; convex/concave corner threshold TOL on the (signed) cross product. IsCircle = one segment and closed.
  • Priority: Essential
  • Rationale: These predicates classify user-drawn geometry for dimensioning, variant recognition, and technology decisions.
  • Source: GeoElements/TcGeoCurveExtensions.cs; TcGeoSingleAreaExtensions.cs; TcGeoAreaExtensions.cs; TcGeoSegmentExtensions.cs (IsConvexCorner/IsConcaveCorner, IsConvex/IsConcave).
  • Verification: Test (each predicate, boundary tolerance).

FR-CAD-KRN-047 — Convex hull including arcs (managed)

  • Requirement: TcGeoConvexHullGeneration.CalculateConvexHull(curve) SHALL compute the convex hull of a closed, oriented curve respecting arc segments (not just vertices). It SHALL require the curve closed and oriented (throwing ArgumentException otherwise), work on a CLW clone (inverting a CCLW/inner curve and re-inverting the result), replace concave arcs with their chord line, then iteratively bridge concave corners with tangent line segments — using outer-tangent touch points for arc-arc, arc-line and line-arc constellations (clamping arcs to their touch points) — while resolving self-intersections introduced by bridging (inner/outer loop with a relevance tolerance of 0.05 mm, unit-scaled) and rejecting bridges lying inside the current hull.
  • Inputs/Outputs & tolerances: Relevance tolerance TcDefinitions.ConvertMmToInchIfNecessary(0.05); antiparallel-tangent match tolerance 0.005. Two full cycles over the ring (the top-left corner is not otherwise re-evaluated). Output hull preserves arc segments where they lie on the hull boundary.
  • Priority: Conditional
  • Rationale: An arc-aware hull is needed for tight bounding, collision and nesting envelopes of contours containing fillets/holes, where a vertex-only hull would be wrong.
  • Source: GeoMath/TcGeoConvexHullGeneration.cs; exposed via TcGeoCurveExtensions.CalculateConvexHull.
  • Verification: Analysis (bridging & self-intersection resolution), Test (contours with convex/concave arcs).

FR-CAD-KRN-048 — Graham-scan convex hull (native)

  • Requirement: The native TcConvexHullGraham(pointList) SHALL compute the convex polygon of an unsorted 2-D point cloud by Graham's algorithm: pick the lowest-leftmost point, fan-sort the remaining points counter-clockwise by angle (without evaluating the exact angle), then scan, keeping convex turns (cross product > 0) and discarding concave ones (cross product < 0). computeHull() SHALL reorder the input list so that indices 0..return hold the hull vertices and return that count.
  • Inputs/Outputs & tolerances: In-place reordering of the caller's TyPoint2DList. Convexity by cross-product sign. (Point-cloud hull only; does not model arcs — cf. FR-CAD-KRN-047.)
  • Priority: Conditional
  • Rationale: The legacy native hull is retained for point-based hull needs; it is superseded for contour hulls by the managed arc-aware routine.
  • Source: tc_math/TcConvexHullGraham.h/.cpp; base tc_math/TcConvexHull.h (merged into Graham).
  • Verification: Test, Inspection.

FR-CAD-KRN-049 — Geometry equality comparison

  • Requirement: TcGeoElementChecker SHALL provide tolerance-based equality comparisons: CompareVectors (X,Y within TOL), CompareLineSegment/CompareArcSegment/CompareSegments (bounding box, endpoints, length within TOL, plus center/radius/circle-flag/end-angle within TOL/TOL_ANGLE_DEG for arcs), CompareCurves (bounding box, orientation, segment count), CompareSingleAreas (area size within TOL_AREA, bounding box, outer curve, order-independent segment and inner-curve matching), and CompareAreas (area size, bounding box, order-independent single-area matching). Set-style comparisons SHALL match each element of one collection to an unused element of the other. Additionally, TcGeoCurve.Matches/TcGeoSegment.Matches SHALL provide orientation-aware (optionally inverse) structural equality within a given tolerance.
  • Inputs/Outputs & tolerances: Value tolerance TOL, area tolerance TOL_AREA, angle tolerance TOL_ANGLE_DEG. CompareDoubleValues is an inclusive band test.
  • Priority: Conditional
  • Rationale: Duplicate detection, undo/redo verification, nesting identity and regression testing all need robust geometry equality.
  • Source: GeoElements/TcGeoElementChecker.cs; TcGeoCurveExtensions.Matches; TcGeoSegmentExtensions.Matches.
  • Verification: Test.

FR-CAD-KRN-050 — Bounding rectangle, rotated bounding box and main direction

  • Requirement: The kernel SHALL compute: the axis-aligned bounding box of any curve/area (union of segment boxes); the area's main-direction angle CalcMainDirectionAngle (in [0, π/2)) as the direction (mod π/2, within TOL_ANGLE_RAD) carrying the greatest total edge length, optionally ignoring arcs; the rotation CalcTrafoToMainDirection (−mainDirectionAngle) that aligns the area to its principal axes; a rotated/oriented bounding box (TcRotatedBoundingBox); and GetMaximalEmptyRectangle(obstacles) (largest axis-aligned obstacle-free rectangle, per Breuel's recursive pivot approach).
  • Inputs/Outputs & tolerances: Main-direction binning tolerance TOL_ANGLE_RAD; full circles and (optionally) arcs are excluded from the direction histogram. Empty-rectangle recursion asserts obstacles lie within the box.
  • Priority: Conditional
  • Rationale: Oriented bounding boxes and main-direction alignment support minimal-envelope nesting, labeling orientation and free-space placement.
  • Source: GeoElements/TcGeoAreaExtensions.cs (CalcMainDirectionAngle, CalcTrafoToMainDirection, MapSegmentsAnglesToLengthSums); TcBoundingBox.cs GetMaximalEmptyRectangle; TcRotatedBoundingBox.cs.
  • Verification: Analysis, Test (rotated rectangle, obstacle field).

FR-CAD-KRN-051 — Topological plan / graph model with iterators

  • Requirement: The native TcGeoPlan SHALL build and manage a list of geometry descriptors (TcGeoPlanObjekt) from a list of contour elements (TiElementAdapter) and a contour adapter (TiKonturAdapter), optionally positioned by a TcTransformationMatrix. It SHALL create typed iterators via erzeugeGeoIterator(TeIteratorTyp) — e_AllGeoPlanObjekteIterator, e_EckenIterator (corners), e_ElementeIterator (elements) — and SHALL support corner iterators filtered by corner type (erzeugeEckenIterator) and element iterators filtered by element type (erzeugeElementeIterator), each optionally constrained to a rectangular search window (t_suchFensterMin/Max).
  • Inputs/Outputs & tolerances: Element types (TcElement::TeElementTyp): e_Linie=1, e_Bogen=2, e_Kreis=4, e_UnbestimmterTyp=7 (all). Iteration order follows contour traversal. Search windows are axis-aligned bounding filters.
  • Priority: Conditional
  • Rationale: The plan/graph model gives CAD commands (snapping, corner operations, geometric queries) a navigable topological view over a contour independent of the raw dbase storage.
  • Source: tc_geoPlan/TcGeoPlan.h; TiGeoPlanIterator.h (TeIteratorTyp); TcEckenIterator.*, TcElementeIterator.*, TcAllGeoPlanObjekteIterator.*; TcElement.h (TeElementTyp).
  • Verification: Inspection, Demonstration (iterate corners/elements within a window).

FR-CAD-KRN-052 — Corner classification (Ecke)

  • Requirement: TcEcke SHALL represent a contour corner with an enclosed angle getWinkel() (angle in the good part), a position getPunkt(), a bisector query (Winkelhalbierende), an associated element pointer, and a corner-type TeEckenArt: e_KeineEcke=0 (no corner), e_InnenEcke=1 (inner/concave corner), e_AussenEcke=2 (outer/convex corner), e_UnbestimmteEcke=3 (both/indeterminate). The classification SHALL be derivable from the corner angle relative to the traversal orientation.
  • Inputs/Outputs & tolerances: Angle stored in radians (m_winkel); classification by the corner's turn direction. The managed equivalent is TcGeoSegmentExtensions.IsConvexCorner/IsConcaveCorner with threshold TOL (cf. FR-CAD-KRN-046).
  • Priority: Conditional
  • Rationale: Distinguishing inner vs. outer corners is required for fillet/chamfer placement, kerf offset direction, and corner-based snapping.
  • Source: tc_geoPlan/TcEcke.h (TeEckenArt, getWinkel, getPunkt, bisector); managed counterpart TcGeoSegmentExtensions.cs.
  • Verification: Test (inner vs outer corner), Inspection.

FR-CAD-KRN-053 — DCEL half-edge topology

  • Requirement: The kernel SHALL provide a doubly-connected edge list TcDcel<TV,TE,TF> (half-edge data structure) whose TcHalfEdge carries Data (edge), Origin (start vertex), Face, Twin (opposite-direction half-edge sharing the two endpoints), Next and Prev (successor/predecessor around the same face), plus container linkage (NextInContainer/PrevInContainer) and RemoveFromContainer() in O(1). Navigation and modification helpers SHALL be provided (NavigationHelper, ModificationHelper, ValidationHelper) together with adapters (IVertexAdapter, IFaceBoundaryAdapter, AreaToHalfEdge) to build a DCEL from a TcGeoArea.
  • Inputs/Outputs & tolerances: Generic over vertex/edge/face payloads; twin/next/prev invariants define face boundaries. Topological, not tolerance-driven.
  • Priority: Conditional
  • Rationale: A DCEL supports planar-subdivision queries (face adjacency, boundary walking) used by advanced decomposition/boolean and area-to-topology conversions.
  • Source: GeoAlgorithmsKernel/GeoKernel/HalfedgeTopology/TcDcel.cs, AreaToHalfEdge.cs, IVertexAdapter.cs, IFaceBoundaryAdapter.cs, NavigationHelper/, ModificationHelper/, ValidationHelper/.
  • Verification: Inspection, Test (twin/next/prev consistency via ValidationHelper).

FR-CAD-KRN-054 — Spatial index for segments (quad-tree)

  • Requirement: The kernel SHALL provide a bounding-box spatial index TcBoundingBoxesHolder<T> selectable as SimpleList, QuadTree (default), or SimpleListAndQuadTree, wrapping TcQuadTree<T> — a self-balancing region quad-tree that splits a node when it holds more than SPLIT_THRESHOLD (6) objects and merges when a subtree drops below MERGE_THRESHOLD (3). It SHALL support Add/AddRange and Intersect(box|segment, tolerance) returning candidate objects whose bounding boxes intersect the query. Point-in-curve, curve-segment and curve-curve routines SHALL use this index to restrict intersection tests to spatially relevant segments.
  • Inputs/Outputs & tolerances: Objects must expose a valid (non-NaN) bounding box (asserted). Default index-area hint [-0.5,0.5]². Thresholds constrain MERGE_THRESHOLD ≥ 2, SPLIT_THRESHOLD > MERGE_THRESHOLD.
  • Priority: Essential
  • Rationale: Without spatial indexing, intersection/containment over large contours would be O(n²); the quad-tree makes CAD-scale geometry interactive.
  • Source: GeoAlgorithmsKernel/GeoKernel/GeoIndex/TcQuadTree.cs, TcBoundingBoxesHolder.cs, TiBoundingBoxesHolder.cs.
  • Verification: Test (split/merge behavior, query completeness).

FR-CAD-KRN-055 — Managed / unmanaged (GAK) bridge

  • Requirement: The C++/CLI GeoAlgorithmsKernelAdapter together with TcGAKUnmanagedAdapter SHALL bridge native CAD geometry into the managed GeoKernel. TnGAKUnmanagedAdapterConversion SHALL define POD adapter structs (TsAdapterGeoVector, TsAdapterGeoSegment, TsAdapterGeoCurve, TsAdapterGeoSingleArea, TsAdapterGeoArea, TsAdapterBoundingBox, TsAdapterInterval) and conversion functions mapping between native types (TcVector, Element, Kontur, TCOKontur, Teil, dbase S_teil, TcTempTeil) and those adapter structs, including a variant that applies a TcTransformationMatrix during vector conversion for absolute positioning. Native call sites SHALL invoke geometry algorithms through TcGAKUnmanagedAdapter (which forwards to the managed layer) rather than reimplementing them natively.
  • Inputs/Outputs & tolerances: Round-trip conversion (native→adapter→managed and back to TCOKontur/TcTempTeil) must preserve geometry within kernel tolerance; open contours are ignored when converting TcTempTeil→TsAdapterGeoArea (documented). Unit consistency governed by FR-CAD-KRN-009.
  • Priority: Essential
  • Rationale: The bridge lets the legacy native CAD core reuse the modern managed kernel, avoiding duplicate (and divergent) geometry code.
  • Source: GeoAlgorithmsKernel/GAKUnmanagedAdapter/TcGAKUnmanagedAdapter.h/.cpp, TnGAKUnmanagedAdapterConversion.h/.cpp; GeoAlgorithmsKernel/GeoAlgorithmsKernelAdapter/ (TcGeoAlgorithmsKernelAdapter, TcCallbacksAdapter, TcManagedUnmanagedObjectMap.h).
  • Verification: Inspection (struct/function mapping), Test (native↔managed round-trip fidelity).

4. Open Questions & Ambiguities

  1. Area orientation tolerance FIXME. TcGeoCurve.Orientation compares oriented area against TOL·TOL with an in-code note that this should be TOL_AREA. Degenerate/near-zero-area curves yield UNDEFINED and trigger a "please report" assertion — the intended production behavior for such contours is unspecified.
  2. Full-circle-from-short-arc risk. The legacy tolerance-based DoesLookLikeCircle can misclassify a sufficiently short arc as a full circle (acknowledged in comments). The magnitude of arc that triggers this, and whether all call paths now use the explicit isCircle flag, is not established.
  3. Mirror transforms on arcs. TcGeoArcSegment.GetTransformedArcSegment carries a TODO: a mirror (negative-determinant) matrix is applied without flipping arc orientation, which would invert the swept region. Whether callers ever pass mirror matrices to arcs is unverified.
  4. Point-in-curve determinism vs. concurrency. TcGeoIntersectionCurvePoint seeds Random(1) for reproducible probe directions, but TcMath.Rand seeds from DateTime.Now. The interaction with MULTITHREADING_ENABLED (default false) and thread-safety of the point-in-curve static state is not documented.
  5. IsOblongTool unimplemented. TcGeoShapeRecognizer.IsOblongTool asserts false and returns false; the intended slot/oblong (Langloch) recognition algorithm and its tolerances are undefined here — possibly handled elsewhere (variant scripting, see [[10.5 - CAD Detail - Parametric Variants & Scripting]]).
  6. Tolerance source duality. Managed TcDefinitions holds a small fixed tolerance set, while native TcToleranzContainer enumerates 80+ purpose-specific tolerances from the database (toleranz.asc). How (and whether) the managed defaults are re-synchronized from the database per install/unit is not evidenced in the surveyed files.
  7. Curve-segment overlap on open vs. closed segments. The "interesting point" sampling in TcGeoIntersectionCurveSegment uses a hard-coded arbitrary parameter (0.123456789) for a circle with no common points; the robustness of this choice against pathological curves is unverified.
  8. geoPlan corner angle convention. TcEcke.getWinkel is described as "angle in the good part" (Gutteil); the exact reference (interior angle vs. turn angle) and its unit at the boundary between inner/outer classification were not confirmed from the header alone.
  9. Native vs. managed authority. Some geometry (e.g. tc_math matrices, tc_geoPlan) still lives natively while equivalents exist in the managed kernel. Which layer is authoritative for a given CAD command (and where the bridge is invoked) requires call-graph analysis beyond the surveyed headers.
  10. Degenerate/zero-length inputs. Several operations (GetNormalized, PointToParameter, CreateParallelLineSegment) divide by length with only debug-time assertions; release-mode behavior for zero-length segments (NaN propagation) and whether upstream commands always prevent them is not established.
