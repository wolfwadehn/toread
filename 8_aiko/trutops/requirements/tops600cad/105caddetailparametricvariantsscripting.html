CAD Detail — Parametric Variants & Scripting

Detailed reverse-engineered requirements (Tier: command/algorithm level). Child of [[10 - FR - CAD Geometry & Drawing Editing]]. Reconstructed intent from static source analysis, not an authoritative spec.

1. Purpose & Scope

This document specifies, at the command and algorithm level, the parametric-variant (Varianten) subsystem of the TruTops CAD editor. A variant geometry is an ordinary CAD drawing augmented with (a) a list of named expression variables and references to geometry, (b) an ordered list of parametric changes (transformations, deletions, property/dimension changes, template insertions, loops and conditions), and (c) machinery to execute / undo those changes and to persist them. Expressions are evaluated through an embedded Python interpreter.

It refines the system-level parent [[10 - FR - CAD Geometry & Drawing Editing]] — specifically the parent requirements covering parametric/variant behaviour (FR-CAD-030..035 in the parent overview) — and complements the sibling detail documents:

  • [[10.1 - CAD Detail - Geometry Creation Commands]]
  • [[10.2 - CAD Detail - Editing & Transformation Commands]] (the non-parametric equivalents of Move/Rotate/Mirror/Stretch/Delete)
  • [[10.3 - CAD Detail - Dimensioning Commands]]
  • [[10.4 - CAD Detail - Attributes, Snapping, Selection & Lifecycle]]
  • [[10.6 - CAD Detail - Geometry Kernel Algorithms]] (the kernel transforms invoked by variant changes)
  • [[10.7 - CAD Detail - Contour Arithmetic Algorithms]] (close-contour, offset)
  • [[10.8 - CAD Detail - Curve Approximation & Fourier Analysis]]

Primary evidence. UI/command masks: tc_bof/cad_var.gritx (31 masks) and the variant action functions in tc_bof/aCadFunc.gritx (16 masks). The changes are created/persisted/executed by the singleton engine tc_dbase/dbase_cad/TcDbaseVarManager.{h,cpp} (interface TiDbaseVarManager). Expressions run on tc_python/TcPythonInterpreter.{h,cpp}. The MMK masks talk to the engine through the ASM bridge command asm_call( variant … ); the ASM verbs seen are on/off/close/read/working/refresh/field/check/last/next/back/fetch/count/create/multi create/multi remove/copy/remove/move next|back/set …/reference …/name …/liste … plus positional forms variant <id> current|copy|remove|fetch|set ….

Domain terms (German → English, original kept): Variante=variant, Änderung=change, Bewegen=move, Rotieren=rotate, Spiegeln=mirror, Dehnen=stretch, Löschen=delete, Kopie=copy, Schleife=loop, Bedingung=condition, Ausdruck=expression, Referenz=reference, Kontur schließen=close contour, Rundung=fillet/rounding, Biegewinkel=bend angle, Durchmesser=diameter, Vorlage (Vlg)=template, Eigenschaft=(file) property, Bezeichnung=label/description. See [[04 - Domain Model & Glossary]].

3. Detailed Requirements

FR-CAD-VAR-001 — Enter variant mode

  • Requirement: When the user activates Variants, the system SHALL enter variant mode by (a) swapping the control field to F_SteuerVarianten, the menu field to #ST_MenueVarianten, and the toolbar row to F_VarMenueZeichnungZeileRest; (b) setting ST_ZeichnungVariantenModus = 1; (c) issuing asm_call( variant on ), binding the file-name field via variant field 'O_MenueZeichnungDateiname', and variant read; and (d) disabling the ordinary Undo/Redo and line-colour scroll controls and clearing the undo stack (undo clear).
  • Parameters & options: none (toggle). Side effect: TcDbaseVarManager::activate() marks the manager active (isActive()==true).
  • Priority: Essential
  • Rationale: Variant editing needs a dedicated modal context because ordinary undo/redo is replaced by variant execute/undo.
  • Source: aCadFunc.gritx mask aCadVariantEnter (L36865–36887); TcDbaseVarManager::activate (header L69–89).
  • Verification: Demonstration — enter mode; confirm control/menu swap, disabled Undo/Redo, active manager.

FR-CAD-VAR-002 — Leave variant mode

  • Requirement: When the user exits Variants, the system SHALL restore the standard control/menu/toolbar fields, issue variant off, then variant close, clear the undo stack, re-enable the standard scroll/attribute/Undo/Redo controls, and set ST_ZeichnungVariantenModus = 0.
  • Parameters & options: none. See FR-CAD-VAR-003 for the file-name reset it performs.
  • Priority: Essential
  • Rationale: Clean teardown of the modal context; variants remain defined on the geometry (prepareVariantClose).
  • Source: aCadVariantExit (L37122–37160); TcDbaseVarManager::deactivate, prepareVariantClose (header L76–81, 149–158).
  • Verification: Demonstration — exit mode; confirm standard UI restored and variants preserved.

FR-CAD-VAR-003 — GMV-only persistence when changes are defined

  • Requirement: While any change is defined, the geometry SHALL be persistable only in the GMV format; on exit, if the current file name is not of type GMV (tmp_FUNC_FileType != c_gmv) and variant working reports defined changes (ST_ERROR == 1), the system SHALL clear the proposed file name so the user must choose a GMV name.
  • Parameters & options: isInUse() returns true whenever changes are defined or the manager is active.
  • Priority: Essential
  • Rationale: Only GMV round-trips variable definitions, references and the change list; other formats would silently drop them.
  • Source: aCadVariantExit (L37124–37150, variant working); TcDbaseVarManager::isInUse doc (header L91–102).
  • Verification: Test — define a change, try to save as DXF; expect the name to be blanked/GMV enforced.

FR-CAD-VAR-004 — Export geometry without variant data

  • Requirement: When the user chooses Export variant, the system SHALL invoke Save-As on the drawing with the c_NoVariants flag so the exported file contains only the current geometry state, without variable definitions, references or the change list.
  • Parameters & options: flag c_NoVariants.
  • Priority: Conditional
  • Rationale: Downstream consumers (nesting, NC) need a plain part, not the variant program.
  • Source: aCadVariantExport (L37398–37400 → aCadSaveAsDrawing, c_NoVariants).
  • Verification: Test — export; reload exported file; expect no variants present.

FR-CAD-VAR-005 — Load / select a variant value set

  • Requirement: When the user loads a variant, the system SHALL present the variant list M_CadVarVariantenListe (populated via variant liste @file default) and, on selection, set the chosen change as current via variant #tmp_varVariantenId current followed by variant refresh.
  • Parameters & options: picks a variant id from a finder scroll (format %5.5s%1.1s %-100.100s).
  • Priority: Conditional
  • Rationale: Lets the user jump directly to a named end-state.
  • Source: aCadLoadVariant (L16226–16240); M_CadVarVariantenListe (L60342–60420).
  • Verification: Demonstration — load a variant and confirm the geometry reflects that state.

FR-CAD-VAR-006 — Define / name an expression variable

  • Requirement: The system SHALL allow the user to create a named expression variable via M_CadVarVariablen by entering a name (O_Name) and an expression (O_Ausdruck) and issuing asm_call( variant name @O_Name @O_Ausdruck ), which calls TcDbaseVarManager::defineExpression(name, expression, reevaluate=true). If the name equals a reserved keyword the system SHALL show message 10895; if the variable cannot otherwise be created it SHALL show 10894; an empty expression SHALL show 10868 and an empty name SHALL show 10867.
  • Parameters & options: name (string), expression (string, may reference other variables/references and use math functions). New expressions are appended at the list end (finder set to position 999). An expression may be typed directly, built with the calculator (aTcoOpenCalculator), or appended from a reference value (see FR-CAD-VAR-019).
  • Priority: Essential
  • Rationale: Named variables/expressions are the core of parametric drive.
  • Source: M_CadVarVariablen OK handler (L55794–55840); defineExpression (header L240–251); ASM verb variant name @name @expr.
  • Verification: Test — define w=10, l=2*w; confirm l evaluates to 20.

FR-CAD-VAR-007 — Variable-name validity

  • Requirement: The system SHALL reject a variable name that is a reserved keyword (per FR-CAD-VAR-008) or that begins with a digit; isValidName returns false for such names, and defineExpression SHALL fail (ST_ERROR set) accordingly.
  • Parameters & options: name string; validity = not isKeyName AND not starting 0–9.
  • Priority: Essential
  • Rationale: Names must be safe Python identifiers and must not shadow built-in functions/constants.
  • Source: isValidName (cpp L1557 uses isKeyName; header L229–238).
  • Verification: Test — attempt sin=3 and 2x=1; expect rejection.

FR-CAD-VAR-008 — Reserved keyword / function set

  • Requirement: The system SHALL treat the following identifiers as reserved (usable in expressions but not as variable names): abs, acos, acosh, and, asin, asinh, atan, atan2, cos, cosh, degrees, e, exp, fabs, false, float, floor, fmod, hypot, int, log, log10, max, min, not, or, pow, radians, round, sin, sinh, pi, sqrt, tan, tanh, find, rfind, true. The identifiers e, pi, true, false SHALL be flagged as value keywords (t_isValue). Matching SHALL be case-insensitive (uppercase accepted although Python is lower-case).
  • Parameters & options: find/rfind are string methods; and/or/not are boolean operators; the rest are math/builtin functions.
  • Priority: Essential
  • Rationale: Defines the exact expression vocabulary and prevents collisions.
  • Source: isKeyName (cpp L1339–1532).
  • Verification: Inspection — cross-check the list against isKeyName; Test that pi*r*r evaluates.

FR-CAD-VAR-009 — Expression evaluation pipeline

  • Requirement: The system SHALL evaluate an expression by: (1) scanning it left-to-right, extracting identifier tokens and substituting each via resolveName — a named value/reference becomes float(<%12.6f value>), a named string becomes a double-quoted literal (with a trailing accessor suffix if any), and reserved value keywords true/false become 1/0; (2) requiring at least one numeric literal or defined expression (else "undefined"); (3) prepending a_value = and running the result through the embedded Python interpreter (executeString); (4) reading a_value back as double/long/string. Unresolved identifiers SHALL be recorded in a "missing" list and auto-created as undefined value expressions.
  • Parameters & options: three typed variants — evaluateDouble, evaluateBool (nonzero long → true), evaluateString; each accepts an optional missing-names accumulator.
  • Priority: Essential
  • Rationale: This is the evaluation core that turns text expressions into driving values.
  • Source: evaluateExpression (cpp L8019–8184), resolveName (L7868–7990), evaluateDouble/Bool/String (L8199–8356).
  • Verification: Test — evaluate sqrt(w*w+h*h) with w=3,h=4 → 5.0; w>0 and h>0 → true.

  • Priority: Essential
  • Rationale: Single reusable editor for creating and editing every change type.
  • Source: M_CadVarVariante (L57488–60210, type dispatch L57500–57628, popup L59316–59520).
  • Verification: Demonstration — open editor, pick each type, confirm correct parameter sub-mask loads.

FR-CAD-VAR-048 — Create a variant/change

  • Requirement: On creating a change, the system SHALL run M_CadVarVariante, then asm_call( variant create #tmp_varArt @tmp_varBedingung ) (defineChange+setChangeType+setCondition), push each parameter tmp_varParam1..N (N=tmp_varParamCount) via asm_call(@tmp_varParamK) (addChangeParameter), issue asm_call( confirm ), and, if a label was given, asm_call( variant 0 @tmp_varBezeichnung ) (setDescription). The variant list SHALL then be refreshed and the new change fetched as current.
  • Parameters & options: type, condition, up to 7 parameters, optional label.
  • Priority: Essential
  • Rationale: The canonical create sequence used by both aCadCreateVariant and the management dialog.
  • Source: M_CadVarVariantenVerwaltung create button (L62472–62540); manager defineChange/setChangeType/setCondition/addChangeParameter/setDescription (header L474–594).
  • Verification: Test — create a Move change with a label; confirm it appears in the list with the label.

FR-CAD-VAR-049 — Edit an existing variant/change

  • Requirement: On editing a selected change, the system SHALL variant #id fetch (loading its type/condition/parameters into tmp_var*), reopen M_CadVarVariante, and on OK apply variant #id @label, variant #id set #type, variant #id set @condition, variant #id set control, re-push parameters, and (for type 9) confirm. If no change is selected it SHALL show message 10892.
  • Parameters & options: same parameter set as create.
  • Priority: Essential
  • Rationale: In-place modification of a defined change.
  • Source: M_CadVarVariantenVerwaltung edit button (L62671–62748).
  • Verification: Test — edit a change's parameter and condition; confirm persisted.

FR-CAD-VAR-050 — Copy a variant/change

  • Requirement: When a change is selected, the system SHALL duplicate it via variant #O_Id copy (copyChange), refresh the list, and fetch the copy as current; if none selected, show 10892.
  • Parameters & options: id (0 = current).
  • Priority: Conditional
  • Rationale: Fast reuse of a configured change.
  • Source: M_CadVarVariantenVerwaltung copy button (L62175–62200); copyChange (header L490–498).
  • Verification: Test — copy a change; confirm a duplicate is inserted.

FR-CAD-VAR-051 — Delete a variant/change

  • Requirement: When a change is selected, the system SHALL delete it via variant #O_Id remove (deleteChange), clearing the selection and refreshing the list; deleting a loop SHALL also delete its children; if none selected, show 10892.
  • Parameters & options: id; children cascade for loops.
  • Priority: Essential
  • Rationale: Remove an unwanted change.
  • Source: M_CadVarVariantenVerwaltung delete button (L62325–62347); deleteChange (header L681–690).
  • Verification: Test — delete a loop; confirm children removed too.

FR-CAD-VAR-052 — Reorder a variant/change

  • Requirement: When a change is selected, the system SHALL move it earlier/later via variant #O_Id move back / move next (moveChange(id, up)), refresh the list and keep the finder cursor on it; if none selected, show 10892.
  • Parameters & options: direction up/down.
  • Priority: Conditional
  • Rationale: Change execution order (order is semantically significant).
  • Source: M_CadVarVariantenVerwaltung move handlers (L63033–63200); moveChange (header L703–711).
  • Verification: Test — reorder two changes; confirm new execution order.

FR-CAD-VAR-053 — Create and dissolve a loop

  • Requirement: The system SHALL create a loop by selecting an anchor change and issuing variant multi create #O_Id @condition (or variant multi create 0 @condition when none selected) with type=18 (defineLoop), then pushing parameters and confirm. The system SHALL dissolve a loop by variant multi remove #O_Id (dissolveLoop), re-integrating its children; if the selected item is not a loop it SHALL show message 11094 ("choose loop first").
  • Parameters & options: anchor id, condition; loop parameters count+counter-name.
  • Priority: Essential
  • Rationale: Grouping consecutive changes into a repeated block.
  • Source: M_CadVarVariantenVerwaltung loop-create (L63524–63560) and dissolve (L63368–63400); defineLoop/dissolveLoop (header L481–701).
  • Verification: Test — wrap two changes in a loop, then dissolve; confirm children restored in order.

FR-CAD-VAR-054 — Execute the next change

  • Requirement: When the user chooses execute variant, the system SHALL verify the end-state is not already reached (variant check; if reached, message 10893), then execute the next change via variant next followed by variant refresh.
  • Parameters & options: none; advances one step (steps into loop iterations).
  • Priority: Essential
  • Rationale: Step-wise forward execution for authoring/debugging.
  • Source: aCadExecuteVariant (L12275–12295); engine executeChange, getNextChange (header L713–721, 1835–1844).
  • Verification: Test — step through several changes; confirm one applied per click.

FR-CAD-VAR-055 — Undo the last change

  • Requirement: When the user chooses undo variant, the system SHALL verify a predecessor exists (variant last; if not, message 10890), then undo the last change via variant back + variant refresh (unexecuteChange).
  • Parameters & options: none; reverses one step.
  • Priority: Essential
  • Rationale: Step-wise backward execution.
  • Source: aCadUndoVariant (L36366–36390); unexecuteChange (header L723–729).
  • Verification: Test — undo a step; confirm geometry reverts exactly.

FR-CAD-VAR-056 — Execute all changes

  • Requirement: When the user chooses execute all, the system SHALL verify not already at end-state (variant check; else 10893) and execute forward to the last change via variant 999 current (setCurrentChange(S_lastId=999)) + variant refresh.
  • Parameters & options: special id 999 = execute to end.
  • Priority: Essential
  • Rationale: Materialise the final variant state in one action.
  • Source: aCadExecuteAllVariants (L12021–12040); setCurrentChange doc (header L731–744).
  • Verification: Test — from initial state, execute-all; confirm final geometry.

FR-CAD-VAR-057 — Undo all changes

  • Requirement: When the user chooses undo all, the system SHALL verify a predecessor exists (variant last; else 10890) and revert to the initial state via variant 0 current (setCurrentChange(0)) + variant refresh.
  • Parameters & options: special id 0 = revert to initial.
  • Priority: Essential
  • Rationale: Return to the un-transformed base geometry.
  • Source: aCadUndoAllVariants (L36112–36135).
  • Verification: Test — after execute-all, undo-all; confirm base geometry restored.

FR-CAD-VAR-058 — Set current change / renumber

  • Requirement: setCurrentChange(id) SHALL bring the geometry to the state after change id by executing or un-executing all intervening changes as needed (id 0 = all undone, id 999 = all executed). After structural edits the system SHALL renumber changes (renumberChanges) reporting whether ids actually changed.
  • Parameters & options: target id; missing-parameter/break outputs propagate (FR-CAD-VAR-061).
  • Priority: Essential
  • Rationale: Random-access navigation of the change list and stable numbering.
  • Source: setCurrentChange/renumberChanges (header L731–753); used by aCadLoadVariant, aCadManageVariants.
  • Verification: Test — jump from state 5 to state 2; confirm three undos executed.

FR-CAD-VAR-059 — Open the variant management dialog

  • Requirement: When the user chooses manage variants, the system SHALL save the current change id, reset to initial (variant 0 current), open M_CadVarVariantenVerwaltung, and on close restore either the user-selected change (variant #tmp_varId current) or the previously active one (variant #tmp_varIdSave current), then variant refresh.
  • Parameters & options: none.
  • Priority: Essential
  • Rationale: Central hub for create/edit/copy/delete/move/loop and browsing changes.
  • Source: aCadManageVariants (L17037–17060); M_CadVarVariantenVerwaltung (L60961+).
  • Verification: Demonstration — open management, make edits, confirm restore of active state.

FR-CAD-VAR-060 — Default change description

  • Requirement: When a change has no explicit label, the system SHALL generate a default description from the change type and its leading parameters (getCurrentDescription/getChangeDescription); an explicit label (getDefinedChangeDescription) SHALL be used verbatim when present.
  • Parameters & options: description string shown in the variant list.
  • Priority: Conditional
  • Rationale: Human-readable list entries even without manual labels.
  • Source: getCurrentDescription/getDefinedChangeDescription/getChangeDescription (header L656–679, 1909–1930).
  • Verification: Demonstration — create an unlabeled Move; confirm a sensible default label in the list.

FR-CAD-VAR-061 — Missing-parameter and break reporting on execute

  • Requirement: When executing a change, the system SHALL collect the names of any expressions/references that could not be resolved into a "missing" list and return it (t_missingPtr); and, for a Break change with a true condition, SHALL return the break reason (t_breakPtr). Execution SHALL be treated as failed/blocked in these cases so the UI can inform the user.
  • Parameters & options: outputs: missing-parameter list, break message.
  • Priority: Essential
  • Rationale: Deterministic, explainable failure when a variant is under-specified or guarded.
  • Source: executeChange (cpp L4231–4350, a_missing, t_breakPtr); doc (header L713–721).
  • Verification: Test — execute a change referencing an undefined variable; confirm the missing name is reported and geometry unchanged.

FR-CAD-VAR-062 — Persist the change list (versioned, loop-aware)

  • Requirement: The system SHALL serialize expressions and the change list (writeExpressions/writeChanges) and read them back (readExpressions/readChanges), including a version number and terminated by #~END. On read, loops written in linear form (with a child-count parameter) SHALL be reconstructed (adjustLoops), and copy ids from before version 1.2 SHALL be upgraded to include a pass counter (adjustAllIds/adjustId). Element and bending references SHALL be re-bound to their original ids on load.
  • Parameters & options: version field (e.g. >1.0 adds per-change description; ≥1.2 adds copy pass counter).
  • Priority: Essential
  • Rationale: Round-trips the entire variant program within the GMV file.
  • Source: readChanges (cpp L936–1012), writeChanges/readExpressions/writeExpressions (header L160–205); adjustLoops/adjustAllIds/adjustId (header L1875–1907).
  • Verification: Test — save then reload a variant with loops and copies; confirm identical structure and ids.

FR-CAD-VAR-063 — Variants menu and measuring helpers

  • Requirement: The variants menu F_MenueZeichnungVarianten SHALL provide entry points to: create a change (aCadCreateVariant), manage variants (aCadManageVariants), select/copy change elements (aCadSelectVariantElem/aCadCopyVariantElem), manage variables (aCadManageVariantVariables), start the profile builder, and set/delete/show references. It SHALL also offer measuring helpers that feed values into expressions: two-points, point, vertical, horizontal, angle, circle, and length (asm_call( measure … ), each wrapped in getsomethingchanged/somethingchanged).
  • Parameters & options: measure verbs: two_pts, point, vertical, horizontal, angle, me_circle, length.
  • Priority: Conditional
  • Rationale: Discoverable grouping of variant authoring tools with on-canvas measuring.
  • Source: F_MenueZeichnungVarianten (L39320–42700).
  • Verification: Demonstration — invoke each menu item; confirm the corresponding function launches.

FR-CAD-VAR-064 — Variants control (mode) panel

  • Requirement: The control field F_SteuerVarianten SHALL present the mode-selector buttons (draw / modify / macros / create / bend, etc.) with highlight of the active mode (ST_SteuerVarianten, default 11), and on selection swap the associated menu field (feld_umschalten(MenueFeld, …)) while keeping the variants context.
  • Parameters & options: button matrix O_SteuerButtonRC; active button highlighted with select colours.
  • Priority: Optional
  • Rationale: Navigation shell for the variant editing session.
  • Source: F_SteuerVarianten (L42797–45080).
  • Verification: Demonstration — switch modes; confirm menu field swaps and highlight tracks selection.

FR-CAD-VAR-065 — Relationship to Python script buttons

  • Requirement: The system SHALL distinguish two Python usages: (a) variant expression evaluation, where the CAD MMK masks call the C++ engine which internally uses TcPythonInterpreter::executeString to evaluate short expressions on a persistent stack (FR-CAD-VAR-009/010); and (b) standalone Python scripting, where TcPythonInterpreter executes whole .py files (executeFile) — including a start-up runCustomizationScript("TruTops_customize.py") from the app-utils Python sub-directory — exposing the ToPs and ToPsGraphics modules and ASM/MMK callbacks (mmkDebugHook, asmWheel/Int/Float/PointCallback). Script buttons therefore invoke the same interpreter class but via file/script execution rather than the variant change list.
  • Parameters & options: modules import math/from math import */import ToPs/from ToPs import *; env TOPS_PYTHON_PATH, TOPS_APP_UTILS_PATH; error text via getErrorState and optional TruTops_exceptionHook.
  • Priority: Conditional
  • Rationale: Clarifies that parametric variants and Python "script buttons" share the interpreter but are separate mechanisms.
  • Source: TcPythonInterpreter executeFile/executeString/runCustomizationScript (cpp L244–427), module init (L122–187), callbacks (L864–1117); ToPs module includes (L46–47).
  • Verification: Inspection — confirm both paths use TcPythonInterpreter; Test — run a customization script and a variant expression in one session.

FR-CAD-VAR-066 — Persistent element/bending identity

  • Requirement: To keep references and change-target sets valid across save/load, the system SHALL, on storage preparation (prepareElementStorage/prepareVariantClose), revert to the initial state and tag every original element/bending that is transformed or used as a reference with an attribute carrying its current id, and SHALL restore those original ids on reload; the preparation SHALL be reversible (unprepareElementStorage).
  • Parameters & options: temporary attribute/link lists; ids mapped via m_elementMap/m_bendingMap.
  • Priority: Essential
  • Rationale: Change parameters and references address elements by id; ids must survive a GMV round-trip.
  • Source: prepareElementStorage/unprepareElementStorage/prepareVariantClose (header L128–158); setElementId/getElementId (header L1291–1347).
  • Verification: Test — save/reload a variant; confirm references and change targets still resolve to the same elements.

4. Open Questions & Ambiguities

  1. Radius vs. diameter type mapping. The enum comments mark e_varChangeCircle=10 as obsolete ("replaced by ChangeDiameter on load"), yet F_CadVarKreisRadiusAendern actively writes type 10 (radius) while F_CadVarKreisAendern writes type 14 (diameter). It is unclear whether a freshly authored radius change is silently migrated to a diameter change on save/load, or whether type 10 remains a live "radius" change distinct from 14. Needs runtime confirmation. (FR-CAD-VAR-035/036)
  2. Mirror axis semantics. Mirror mode 0 is labelled "horizontal" but stores an x-coordinate (x1), and mode 1 "vertikal" stores y1. Whether "horizontal" means "mirror across a vertical axis at x=x1" (left-right flip) or the literal axis orientation is inferred, not proven, from the coordinate used. (FR-CAD-VAR-028/031)
  3. Loop parameter count discrepancy. F_CadVarSchleife sets tmp_varParamCount=2 (count, counter-name) but the management loop-create path sets count 0 and executeLoop reads two parameters; the exact serialized parameter arrangement for loops (and the child-count parameter added at write time) should be confirmed against a saved GMV. (FR-CAD-VAR-045/062)
  4. variant count / execute-all messaging. One management button issues variant count and shows messages 11151/11152 (NO_CHANGE). Its precise role (recount/re-evaluate vs. execute) versus the toolbar aCadExecuteAllVariants was not fully disambiguated. (FR-CAD-VAR-056/059)
  5. Property key set completeness. The eight :key: property tokens (:id: :note: :programmer: :machine: :material: :thickness: :min: :max:) come from the UI mask; whether the engine (setProperty) accepts additional keys is unverified. (FR-CAD-VAR-042)
  6. Units and angle sign conventions for rotate/mirror/bend-angle are assumed to follow the general CAD drawing convention (mm, degrees, CCW-positive) but are not asserted in the variant code inspected; confirm against [[10.6 - CAD Detail - Geometry Kernel Algorithms]].
  7. aCadCreateVariant lives in aCadCreateFunc.gritx (outside this slice). It mirrors the management create sequence (FR-CAD-VAR-048); its full behaviour (e.g. initial element selection) was only partially inspected.
  8. ToPs Python module surface. import ToPs exposes an API to scripts (FR-CAD-VAR-065) whose functions are defined in pythonModules/moduleToPs* — not analysed here; the scripting capability beyond the variant expression subset is out of scope for this document.
  9. Concurrency / singleton. TcDbaseVarManager and the Python environment are process singletons; behaviour with multiple open drawings/variants simultaneously was not examined.
