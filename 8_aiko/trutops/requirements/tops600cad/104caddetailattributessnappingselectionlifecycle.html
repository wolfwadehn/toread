CAD Detail — Attributes, Snapping, Selection & Drawing Lifecycle

Detailed reverse-engineered requirements (Tier: command/algorithm level). Child of [[10 - FR - CAD Geometry & Drawing Editing]]. Derived from static source analysis — reconstructed intent, not an authoritative spec.

1. Purpose & Scope

This document is the fine-grained, command- and algorithm-level companion to the system-level summary in [[10 - FR - CAD Geometry & Drawing Editing]]. Where the parent states that the editor supports colour/style attributes, snapping, selection, undo/redo and a drawing lifecycle, this document specifies how each individual mask (interactive command) and each kernel capability behaves — parameters, options, modes, defaults, units, tolerances and degenerate cases.

It refines the following parent requirements:

In scope: the 16-entry GRIT line-colour palette (index 0–15) and the 9 line styles; the colour-as-layer-surrogate model and DXF layer↔colour/style mapping; the snapping subsystem (fangen) — mode/what, kind/how, scope/where, region/area, radius, catch conditions, disable, tracers, per-element catch algorithms; interactive selection (pick/box/confirm/all) with mode/method/focus/scope filters; marking; the contour assistant; the undo/redo transaction model; the native drawing lifecycle (new/open/save/save-as/save-selection/workfile/close/scale) including the Geo read/write facades and cad_load/cad_store; and the metric/inch (gritunit) unit duality with the tolerance container.

Domain terms link to [[04 - Domain Model & Glossary]].

Interpreter model. Commands live as masks in tc_bof/aCadFunc.gritx (176 masks total). Each mask's EnterFunction runs an MMK-interpreter script that opens dialogs (dialog_box) and drives the C++ finite-state automata via asm_call( … ). The automata (e.g. color, line_type, undo, load, store) are defined in tc_cad/**, and mutate the dbase model (S_draw/S_teil/S_kontur/S_element) in tc_dbase/**. aCad* masks are the full interactive commands; tCad* masks are thin, parameterised entry points (typically called from ribbon/tool buttons) that pass a _Par0/_Par1 argument straight to an asm_call.

3. Detailed Requirements

3.1 Line colour & line-style attributes

FR-CAD-ATT-001 — Set active line colour

  • Requirement: The system shall provide a command to set the active line colour used for all subsequently created contour, text and marker elements; on selection of a colour it SHALL call set_color_index(farbe) which sets the contour, text and marker default colour on the element initializer and updates the drawing background/feedback pen accordingly.
  • Parameters & options: Named colours accepted by the color automaton and mapped by befehl_to_farbe: white(1), black(0), red(2), green(4), blue(6), cyan(5), magenta(7), yellow(3) → TnColor::TeColor. tCadSetColor_Par0 ∈ {c_white,c_red,c_yellow,c_green,c_cyan,c_blue,c_magenta,c_black}; unknown → white (default). Initial active colour = TnColor::e_white. A non-positive index is rejected with message 206.
  • Priority: Essential
  • Rationale: The active colour is the primary element-classification default; colour is used in place of named layers (see FR-CAD-ATT-012).
  • Source: tc_bof/aCadFunc.gritx tCadSetColor (L44613); tc_cad/cad_asm/color.cpp set_color_index, farb_fkt, init_color_befehl; tc_cad/allg_asm/cline.cpp befehl_to_farbe; tc_visualize/visDefines.h TnColor::TeColor.
  • Verification: Test — set each colour, create an element, inspect stored S_element.farbe.

FR-CAD-ATT-002 — Set active line style

  • Requirement: The system shall provide a command to set the active line style for subsequently created elements; on selection it SHALL call set_linetype_index(linetype) which sets the contour style on the element initializer, updates the GUI style-preview text and emits confirmation message 208 (or 209 for a negative index).
  • Parameters & options: 9 styles (TC_MAX_ANZ_LINETYPES = 9): TC_SOLID(0), TC_DASH(1), TC_DOT(2), TC_DASH_DOT(3), TC_DASH_DOT_DOT(4), TC_LONG_DASH(5), TC_CENTER_DASH(6), TC_CENTER_DASH_DASH(7), TC_SOLID_THICK(8). Automaton tokens: solid,dash,dot,dash_dot,dash_dot_dot,long_dash, plus a raw ASM_INTEGER index. tCadSetType_Par0 ∈ {c_solid,c_dash,c_dot,c_dash_dot}; unknown → solid. Default active style = TC_SOLID. Note: the interactive preview text only distinguishes solid/dash/dash_dot/dot; styles 4–8 fall back to the solid preview text.
  • Priority: Essential
  • Rationale: Line style classifies elements (e.g. construction vs. cut) and is preserved in native Geo and mapped to DXF linetypes.
  • Source: tCadSetType (L45137); tc_cad/cad_asm/linetype.cpp set_linetype_index, linetype_fkt, linetype_zahl_fkt; cline.cpp befehl_to_linetype; visDefines.h line-art constants.
  • Verification: Test — set each style, create an element, inspect stored S_element.art.

FR-CAD-ATT-003 — Change colour of picked / confirmed elements

  • Requirement: When the "change colour" option is active, the system shall let the user select a target colour and then recolour interactively picked, box-selected or confirmed elements via a TcDbaseChangeColorCommand, executing the change only when the confirmed-selection count is greater than zero and then clearing the selection.
  • Parameters & options: Enter via color … change <colour>; per-pick handler change_col(x,y) picks then executes; change_col_confirm executes on the confirmed set; the feedback selector is createSelector(e_allParts, e_elements); info level e_selectInfoCount. tCadChangeElemColorSelection_Par0 selects the target colour token; aCadChangeElemColorSelection first resolves the GRIT palette index to a colour name then issues asm_call( end color change <name> ).
  • Priority: Essential
  • Rationale: Editing element classification after creation is a core CAD task.
  • Source: aCadChangeElemColorSelection (L3195), tCadChangeElemColorSelection (L38156); color.cpp set_change_col,change_col,change_col_confirm,change_col_execute; tc_cad/cad_asm/color.cpp uses TcDbaseChangeColorCommand.
  • Verification: Test — pick two elements, apply red, confirm both become e_red; verify empty selection cannot execute.

FR-CAD-ATT-004 — Change colour of all elements

  • Requirement: When the user chooses "all" during colour change, the system shall recolour every element in the active scope to the selected colour in a single command (change_col_all → controller->all() → TcDbaseChangeColorCommand::execute).
  • Parameters & options: Automaton token YACC_ALL; aCadChangeElemColorAll opens M_ZeichnungKopiereFarbe then issues the returned asm_call.
  • Priority: Conditional
  • Rationale: Bulk reclassification (e.g. make everything a cut colour).
  • Source: aCadChangeElemColorAll (L2953); color.cpp change_col_all.
  • Verification: Test — apply "all → white"; verify every element becomes e_white.

FR-CAD-ATT-005 — Replace one colour by another (recolour by attribute)

  • Requirement: When the user selects the "replace" colour option, the system shall gather all elements currently carrying a specified old colour (via db_fange_sel_attribut_rekursiv(..., farbe=oldColor, art=-1)), fix any pending change first, and recolour that set to the new active colour.
  • Parameters & options: Two-colour interaction: old colour picked in state z6, new colour previously set; catch list keyed on fang_kenn = e_catchElements, aend_kenn = AENDERE_ELEM. -1 means "ignore this attribute".
  • Priority: Conditional
  • Rationale: Global remap of a classification colour without manual picking.
  • Source: color.cpp f_replace_farbe; tc_dbase/fang_sel.h db_fange_sel_attribut_rekursiv.
  • Verification: Test — with mixed colours, replace red→blue; verify only red elements changed.

FR-CAD-ATT-006 — Change line style of picked / confirmed elements

  • Requirement: When the "change style" option is active, the system shall let the user select a target style and restyle interactively picked, box-selected or confirmed elements via a TcDbaseChangeStyleCommand, executing only when the confirmed-selection count is greater than zero.
  • Parameters & options: line_type … change <style>; handlers change_lt, change_lt_confirm, change_lt_execute; selector createSelector(e_allParts, e_elements). tCadChangeElemStyleSelection_Par0 ∈ {c_solid,c_dash,c_dot,c_dash_dot} → asm_call( end line_type change <style> ); unknown → solid.
  • Priority: Essential
  • Rationale: Post-creation restyling mirrors recolouring.
  • Source: aCadChangeElemStyleSelection (L3750), tCadChangeElemStyleSelection (L38428); linetype.cpp set_change_lt,change_lt*.
  • Verification: Test — pick element, apply dash, verify art == TC_DASH.

FR-CAD-ATT-007 — Change line style of all elements

  • Requirement: When the user chooses "all" during style change, the system shall restyle every element in the active scope to the selected style (change_lt_all → controller->all()).
  • Parameters & options: YACC_ALL; aCadChangeElemStyleAll opens M_ZeichnungKopiereArt.
  • Priority: Conditional
  • Rationale: Bulk restyling.
  • Source: aCadChangeElemStyleAll (L3508); linetype.cpp change_lt_all.
  • Verification: Test — apply "all → solid"; verify uniform style.

FR-CAD-ATT-008 — Replace one line style by another (restyle by attribute)

  • Requirement: When the user selects the "replace" style option, the system shall gather all elements carrying a specified old style (via db_fange_sel_attribut_rekursiv(..., farbe=-1, art=oldType)), fix any pending change first, and restyle that set to the new active style.
  • Parameters & options: As FR-CAD-ATT-005 but keyed on art (line style) rather than colour.
  • Priority: Conditional
  • Rationale: Global style remap (e.g. dot→dash).
  • Source: linetype.cpp f_replace_linetype; fang_sel.h.
  • Verification: Test — restyle all dotted → dashed; verify only dotted changed.

FR-CAD-ATT-009 — 16-entry GRIT line-colour palette (index 0–15)

  • Requirement: The system shall present a line-colour chooser dialog offering a 16-entry palette indexed 0–15 (GRIT display palette), and shall translate the chosen GRIT index into the corresponding ToPs colour name before activating it.
  • Parameters & options: Dialog M_MenueZeichnungAuswahlLinCol; result on O_AktLineColor. 3.4 Undo / redo transaction model

FR-CAD-ATT-039 — Undo

  • Requirement: After an editing operation, the system shall undo the most recent operation on request, restoring the exact prior geometry state, via asm_call( undo 1 ) which drives TcASMUndo::turnBack(1) against the TcUndoManager undo stack.
  • Parameters & options: aCadUndo → undo 1; the automaton command id is YACC_T2_UNDO(7101); step count is the numeric argument (1 by default).
  • Priority: Essential
  • Rationale: Reversibility of edits is a core editor guarantee (parent FR-CAD-034).
  • Source: aCadUndo (L35875); tc_undo/undo_asm/TcASMUndo.h turnBack; tc_undo/undo_asm/undo_lex.hpp YACC_T2_UNDO.
  • Verification: Test — edit, undo, verify geometry restored.

FR-CAD-ATT-040 — Redo

  • Requirement: After an undo, the system shall redo the last-undone operation on request via asm_call( redo 1 ), provided the undone transaction consisted only of redoable actions.
  • Parameters & options: aCadRedo → redo 1; command id YACC_T2_REDO(7102). The redo stack is filled automatically during undo when the transaction is fully redoable.
  • Priority: Essential
  • Rationale: Redo complements undo.
  • Source: aCadRedo (L28529); undo_lex.hpp YACC_T2_REDO; TcUndoManager.h (redo-stack semantics, L57–67).
  • Verification: Test — edit, undo, redo, verify edit re-applied.

FR-CAD-ATT-041 — Transaction grouping (atomic / non-atomic)

  • Requirement: The system shall group a sequence of dbase actions into a single undoable transaction so that one undo reverses the whole group; explicit sequence bracketing SHALL be available (undo sequenz start / undo sequenz stop), and transactions SHALL be either atomic (auto-collecting the atomic create/delete/modify actions of undoable objects) or non-atomic (rejecting those atomic actions).
  • Parameters & options: aCadSaveWorkfile brackets its store with undo sequenz start/stop. TcUndoManager distinguishes atomic vs. non-atomic transactions; undo/redo operate per whole transaction.
  • Priority: Essential
  • Rationale: Multi-step commands must undo as a unit, not step-by-step.
  • Source: tc_undo/undo_allg/TcUndoManager.h (transaction model, L46–130); aCadSaveWorkfile (undo sequenz start/stop).
  • Verification: Test — run a composite command, undo once, verify all sub-steps reverse together.

FR-CAD-ATT-042 — Clear undo history

  • Requirement: When starting a new drawing or loading a file, the system shall clear the undo/redo history (asm_call( undo clear )), and the undo manager SHALL provide reset(), resetUndoActions() and resetRedoActions() which destroy the stored actions (permanently deleting objects held for deletion-undo) and notify listeners of the new undo/redo availability.
  • Parameters & options: undo clear invoked from aCadNewDrawing, tCadLoadDrawing, aCadLoadWorkfile after a load.
  • Priority: Essential
  • Rationale: History from a previous drawing must not leak into a new one.
  • Source: aCadNewDrawing (L20471), tCadLoadDrawing (L39750); TcUndoManager.h reset/resetUndoActions/resetRedoActions (L100–117).
  • Verification: Test — after new/load, verify undo is unavailable.

FR-CAD-ATT-043 — Dbase action / memento model

  • Requirement: The system shall implement undo via a dbase action manager that records typed actions and object mementos for created/deleted/changed model objects, enabling exact state capture and restoration; the manager SHALL be globally enable/disable-able and drive undo/redo GUI availability.
  • Parameters & options: TcDbaseActionManager (singleton, M_isEnabled); action types include TcDbaseChangeColorAction, TcDbaseChangeStyleAction, TcDbaseCreatedElementAction, TcDbaseDeleteElementAction, TcDbaseChangeElementAction, TcDbaseCompositeAction, plus mementos (TcDbaseLineMemento, TcDbaseArcMemento, TcDbaseCircleMemento, TcDbasePointMemento, TcDbaseTextMemento, TcDbasePartMemento, …) built by TcDbaseMementoFactory; TcAppStateCurrentState::SetStateUndo/Redo reflect availability.

  • Source: tc_dbase/dbase_undo/TcDbaseActionManager.cpp (Enable/Disable); tc_dbase/dbase_undo/TcDbase*Action.*, TcDbase*Memento.*, TcDbaseMementoFactory.*.
  • Verification: Analysis/Test — recolour then undo; verify colour action reverses via memento.

FR-CAD-ATT-044 — Undo/redo button enablement

4. Open Questions & Ambiguities

  1. GRIT palette index → colour name inconsistency. Index 2 maps to limegreen in aCadChangeActSettings/aCadChangeElemColorSelection but to the default white in the aCadAssiContourColor recolour map (which omits indices 2, 8, 13, 14). Is this deliberate (assistant only offers the ToPs-machining subset) or a latent bug? The exact 16-entry RGB palette lives in the external binary GRITCOL.24, which was not inspected.
  2. Palette breadth vs. model breadth. The chooser exposes 16 GRIT indices but the element model (TnColor::TeColor) has only 11 semantic colours (0–10, incl. e_highlight1/2 and e_lightGrey). Which GRIT indices are ever actually storable on an element, and how are the collapsed duplicates (e.g. two "red", two "blue") resolved on store? befehl_to_farbe only ever yields the 8 primary ToPs colours.
  3. Line-style breadth vs. UI. TC_MAX_ANZ_LINETYPES = 9 (incl. TC_CENTER_DASH, TC_CENTER_DASH_DASH, TC_SOLID_THICK) but the interactive automata and preview text only expose 6 (solid/dash/dot/dash_dot/dash_dot_dot/long_dash). Are the center/thick styles creatable only via import (DXF CENTER/BORDER) and macros, never interactively?
  4. attribute keep/no_keep scope. The precise set of edit operations affected by the keep-attributes toggle (transform, copy, colour change, split/merge?) is not evident from the mask scripts alone; the consuming automaton logic was not traced.
  5. Snap radius units. db_set_fanggroesse takes a double "size" converted to pixels; whether the caller passes world units (mm/inch via gritunit) or a raw pixel value is not fully determined from the header.
  6. Undo granularity of attribute changes. TcDbaseChangeColorAction/TcDbaseChangeStyleAction exist, but whether a multi-element "change all/replace" is recorded as one composite transaction (single undo) or per-element actions was not confirmed from the manager code read.
  7. Workfile concurrency. The workfile name embeds the session user (_<user>) to avoid collisions, but no locking is evident; behaviour with two concurrent sessions of the same user is unspecified.
  8. DXF import colour-code → TruTops colour. getLayerColor returns the raw DXF layer colour code; the mapping from AutoCAD colour indices (1–255) to TnColor on import was not located in the files read (export mapping is explicit in dxfutil.cpp; the import side needs confirmation).
  9. e_UnitUndefined handling. How geometry values are treated when the active unit is undefined (getActUnit()==e_UnitUndefined) — reject, default to metric, or defer — is not specified in units.h.
