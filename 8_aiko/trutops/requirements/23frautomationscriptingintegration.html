23FRAutomationScriptingIntegration

product: trutopscad org: trumpf title: "FR — Automation, Scripting & Integration" doc: "23 - FR - Automation, Scripting & Integration" id-prefix: "FR-AUTO" srs-standard: "ISO/IEC/IEEE 29148:2018" status: reverse-engineered-draft source: "TruTopsCAD legacy source snapshot (files dated May 2024)" related: ["[[00 - Index & Reading Guide]]", "[[30 - External Interface Requirements]]", "[[17 - FR - Nesting & Palletizing]]", "[[22 - FR - UI Framework, Dialogs & Interaction (GRIT)]]", "[[12 - FR - Part & Data Management]]", "[[04 - Domain Model & Glossary]]"] tags: [requirements, trutops, functional-requirements]

FR — Automation, Scripting & Integration

Reverse-engineered requirement draft — derived from static analysis of legacy source, NOT an authoritative specification. Treat SHALL statements as reconstructed intent.

1. Purpose & Scope — what this area does and which editions it serves.

This document specifies the programmatic automation, scripting and integration capabilities of the TruTops CAD/CAM suite: the surfaces through which the application can be extended, driven, or coupled to external systems without direct interactive use of the drawing editor.

The area covers five distinct integration technologies found in the source snapshot:

  1. Embedded Python scripting (tc_python) — a Python 2.5 interpreter embedded in every TruTops executable, exposing a ToPs and ToPsGraphics module that lets scripts read the application environment/database, drive the internal command interpreters, register callbacks and embed graphics.
  2. The application command interpreters — the ASM application state machine (tc_asm) and the MMK mask/dialog interpreter, which Python (and the UI) drive with command strings. These are the substrate for scripted command sequences.
  3. The external component API (API/…, Xidl-based) — per-edition CAD/Laser/Nest/Tube/Combi APIs exposed to out-of-process (.NET) clients through an Xidl "remote factory" and a GRIT message-queue trigger.
  4. The fabrication / MES adapter (tc_fabAdapter) — a PPS/MES coupling that imports production orders and reports job/file state back to TruTops Fab, via a registry-discovered, licence-checked .NET plugin.
  5. Headless / batch DLL interop (tc_reproduction, TruTopsDllNET, tc_las/LaserDlls) — pure-C DLLs with .NET P/Invoke wrappers for server-side geometry nesting reproduction and laser shop-floor programming, plus trace-file (.taf) recording for reproduction/regression.

Editions served: all. The Python interpreter and command interpreters are linked into every product executable (tcad, t100, t400, t300, tnest, tstub — evidenced in topsmain/bin/**/*.map). The external API, Fab adapter and headless DLLs are edition/licence dependent (TruTops CAD, Punch/ToPs 300, Laser/ToPs 100, Bending/ToPs 600, Nest, Tube). Where a feature is edition- or licence-gated it is marked Conditional.

2. Capability Overview — bulleted summary of the main capabilities.

  • Embedded Python 2.5 interpreter executing script files or in-memory strings, with a persistent per-instance interpreter stack.
  • Startup customization hook (TruTops_customize.py) auto-run from the Python sub-directory of the application-utils folder.
  • ToPs Python module exposing application services: environment variables, database texts, active language, stack variables, console output, file/directory existence checks, password checks, window title.
  • Command driving from script: asmCall() drives the ASM state machine; processMmkString() drives the MMK interpreter; stack-variable get/set exchange data with masks.
  • Callback / hook registration: Python exception hook, MMK step-debug hook, and ASM input callbacks (wheel, integer, float, point).
  • ToPsGraphics module binding a Tk window handle (HWND) as an output device, world/device coordinate transforms, mouse events, and pan/update.
  • External component API per edition (Cad, Laser, Nest, Tube, TubeCad, Combi, CommonLaserCombi) connecting to an Xidl remote factory by URI + plugin name, processed on the GUI thread via a message-queue trigger.
  • Fabrication/MES adapter: import production orders from a PPS system, discover the PPS plugin from the Windows registry, verify its licence, validate nesting jobs, and feed job/file state back to Fab.
  • Reference CSV order source plugin reading *.csv from an exchange directory.
  • Headless reproduction nesting DLL (P/Invoke) for server-side geometry nesting with error/result iteration.
  • Laser shop-floor-programming DLL (C API) for headless convert / nest / GMT / NC-list creation.
  • Trace recording (TraceMode) for reproduction and regression.

4. Functional Requirements

FR-AUTO-001 — Embedded Python interpreter execution

  • Requirement: The system shall provide an embedded Python interpreter that can execute a Python script supplied either as a file path or as an in-memory script string.
  • Priority: Essential
  • Rationale: Scripting is the primary user-facing automation/extension mechanism; both file and string execution are required for customization and interactive command entry.
  • Source: tc_python/TcPythonInterpreter.h (executeFile(), executeString()); tc_python/pythonEmpty/TcPythonInterpreter.cpp; python25.dll imports in topsmain/bin/Release/tcad.map.
  • Verification: Test

FR-AUTO-002 — Startup customization script

  • Requirement: Where a customization script exists in the Python sub-directory of the application-utils directory, the system shall execute it during application start-up.
  • Priority: Optional
  • Rationale: Lets sites inject initialization (variables, hooks, UI tweaks) without a rebuild; absence of the file must not block start-up.
  • Source: tc_python/TcPythonInterpreter.h (runCustomizationScript() docstring naming TruTops_customize.py); tc_python/mmkDebugger/TruTops_customize.py.
  • Verification: Demonstration

FR-AUTO-003 — ToPs Python module application services

  • Requirement: The system shall expose to Python a ToPs module providing read access to the application environment (getEnvVar), database texts (getDbText), active language (getLanguage), file/directory existence checks (fileExists, directoryExists), console output (nprint) and window title control (setWindowTitle).
  • Priority: Essential
  • Rationale: These primitives are what scripts use to inspect state and report progress; without them scripting cannot interact with the running application.
  • Source: tc_python/pythonModules/moduleToPs.cpp (PyMethodDef ToPsModuleMethods); moduleToPsImpl.h/.cpp (getEnvVar, getDbText, getLanguage, print).
  • Verification: Test

FR-AUTO-004 — Drive the ASM command interpreter from script

  • Requirement: When a script calls ToPs.asmCall() with a command string, the system shall process that string through the application state machine (ASM) and execute the resulting state function.
  • Priority: Essential
  • Rationale: asmCall is the mechanism by which scripts replay interactive command sequences; it is the core of scripted automation of the editor.
  • Source: tc_python/pythonModules/moduleToPsImpl.cpp (asmCall() → cad_asm_bearbeite_text() + ASM_do_zustand_fkt()); tc_asm/automat.hpp, tc_asm/tc_asm.hpp.
  • Verification: Test

FR-AUTO-005 — Execute MMK interpreter command strings from script

  • Requirement: When a script calls ToPs.processMmkString() with a command string, the system shall execute that string with the MMK (mask/dialog) interpreter.
  • Priority: Essential
  • Rationale: Allows scripts to trigger dialog/mask logic and data operations that are otherwise reached only through the GUI.
  • Source: tc_python/pythonModules/moduleToPs.cpp (processMmkString); moduleToPsImpl.h.
  • Verification: Test

FR-AUTO-006 — Interpreter stack variable exchange

  • Requirement: The system shall allow a script to read (getStackVar) and write (setStackVar) named variables on the MMK interpreter variable stack.
  • Priority: Essential
  • Rationale: Stack variables are the data channel between scripts, masks and the ASM; the MMK debugger and customization hook both rely on them.
  • Source: tc_python/pythonModules/moduleToPs.cpp (getStackVar, setStackVar); tc_python/mmkDebugger/TruTops_customize.py (resolveVar/setVar, mmkDebuggerCommand).
  • Verification: Test

FR-AUTO-007 — Python callback / hook registration

  • Requirement: The system shall allow a script to register callback functions for: Python exceptions (setExceptionHook), the MMK debug hook (setMmkDebugHook), and ASM user input events — mouse wheel, integer, float and point (setAsmWheelCallback, setAsmIntCallback, setAsmFloatCallback, setAsmPointCallback).
  • Priority: Conditional
  • Rationale: Callbacks let scripts intercept errors and interactive input, enabling debuggers and interactive scripted tools; required only where scripting is used.
  • Source: tc_python/TcPythonInterpreter.h (setExceptionHook, setMmkDebugHook, setAsm*Callback); tc_python/pythonModules/moduleToPsImpl.h.
  • Verification: Test

FR-AUTO-008 — MMK interactive step debugger

  • Requirement: Where the MMK debug hook is registered, the system shall drive an interactive step debugger (step into / step over / step out / continue) over MMK interpreter text and return the chosen command via the mmkDebuggerCommand stack variable.
  • Priority: Optional
  • Rationale: A developer/support aid for diagnosing mask logic; not needed in normal production use.
  • Source: tc_python/mmkDebugger/TcMmkDebugger.py, TruTops_customize.py, mmkDebugger.readme, MMK-Debugger-Kurzanleitung.ppt; TcPythonInterpreter.h (mmkDebugHook()).
  • Verification: Demonstration

FR-AUTO-009 — Graphics window embedding & interaction bridge

  • Requirement: The system shall expose a ToPsGraphics Python module that binds a Tk window handle (HWND) as the ToPs output device, transforms points between device and world coordinates, reports the ToPs window rectangle, and forwards mouse move/click/enter/exit and pan/update events.
  • Priority: Optional
  • Rationale: Enables Python-hosted (Tk) UIs to display and interact with the ToPs drawing canvas; a convenience for scripted tooling.
  • Source: tc_python/pythonModules/moduleToPsGraphics.cpp (setHWND, dc2Wc, wc2Dc, mouseMove, windowPan, getToPsWindowRect, …).
  • Verification: Demonstration

FR-AUTO-010 — Persistent interpreter stack across executions

  • Requirement: The system shall preserve variables and objects placed on an interpreter instance's stack between successive script executions on that instance, and provide typed read-back of variable values as string, long and double.
  • Priority: Conditional
  • Rationale: Interactive/stepwise scripting relies on state persisting between calls (e.g. variables set in one command used by the next).
  • Source: tc_python/TcPythonInterpreter.h (class description; getValueAsString/Long/Double; m_interpreterStack).
  • Verification: Test

FR-AUTO-011 — Python error capture and reporting

  • Requirement: If a script raises an error during execution, then the system shall capture the Python error text, make it retrievable (getErrorState) and report it to the ToPs console, without terminating the host application.
  • Priority: Essential
  • Rationale: Robustness — a faulty script must be diagnosable and must not crash the CAD/CAM session.
  • Source: tc_python/TcPythonInterpreter.h (getErrorState(), errorHandling(), m_errorText); moduleToPsImpl.h (print).
  • Verification: Test

FR-AUTO-012 — Scriptless-edition stub module

  • Requirement: Where an executable is built without the scripting feature, the system shall link an empty (stub) implementation of the ToPs module and interpreter so that scripting symbols resolve without pulling in the full runtime.
  • Priority: Conditional
  • Rationale: Keeps link dependencies and footprint minimal for editions that do not ship scripting; documented "empty vs normal" implementation split.
  • Source: tc_python/pythonEmpty/; tc_stub/tc_python/pythonModules/moduleToPsStub.cpp; moduleToPsImpl.h header comment (empty vs normal implementation).
  • Verification: Inspection

FR-AUTO-013 — Password-gated scripting feature checks

  • Requirement: The system shall let a script query whether a ToPs application password (checkToPsPwd) or a post-processor password (checkPpPwd) is available, and expose the trace-mode state (getTraceModeActive/setTraceModeActive).
  • Priority: Conditional
  • Rationale: Scripts must be able to gate licence-dependent behaviour and control diagnostic tracing; see [[19 - FR - Tools, Machines, Materials & Technology]] for licensing.
  • Source: tc_python/pythonModules/moduleToPs.cpp (checkToPsPwd, checkPpPwd, getTraceModeActive, setTraceModeActive); moduleToPsImpl.cpp (TcUmgeb->isTraceModeActive()).
  • Verification: Test

FR-AUTO-014 — ASM command / state-machine interpreter

  • Requirement: The system shall provide an application state machine (ASM) that parses a command string (yacc/lex grammar) and executes the corresponding state transition and state function, accepting point, real, integer and text inputs.
  • Priority: Essential
  • Rationale: The ASM is the command substrate that both the interactive UI and scripted asmCall() drive; it defines the automatable command vocabulary.
  • Source: tc_asm/tc_asm.hpp (ASM_POINT/REAL/INTEGER/TEXT tokens, error codes), tc_asm/automat.hpp, tc_asm/tc_asm_yacc.y, tc_asm_lex.l, asm_cmnd.cpp.
  • Verification: Test

FR-AUTO-015 — Edition-specific external component API

  • Requirement: Where the corresponding edition/licence is present, the system shall expose a component API (CAD, Laser, Nest, Tube, TubeCad, Combi or CommonLaserCombi) that connects to and disconnects from an Xidl remote factory addressed by a registration URI and a plugin name.
  • Priority: Conditional
  • Rationale: The external API is how companion applications and .NET clients invoke TruTops functionality out-of-process; each edition provides its own API surface.
  • Source: API/CadAPINImpl/TcCadAPIProvider.{h,cpp} (init/deInit, connect/disconnect); API/{Nest,Laser,Tube,TubeCad,Combi,CommonLaserCombi}APINImpl/; Common/TRUMPF/dist/win/Msvc100/API/Tn*API.hh.
  • Verification: Test

FR-AUTO-016 — API request processing on the GUI thread

  • Requirement: When an external API request arrives, the system shall trigger processing of the API message queue by posting a GRIT message so the request executes on the application's GUI thread.
  • Priority: Conditional
  • Rationale: The single-threaded legacy core requires marshalling external calls onto the GUI thread; the message-queue trigger provides that hand-off.
  • Source: API/CadAPINImpl/MessageQueueTrigger.cpp (triggerAPIMessageQueue() → send_message()); identical trigger in Nest/Laser/Tube/TubeCad/Combi MessageQueueTrigger.cpp.
  • Verification: Analysis

FR-AUTO-017 — Managed/native (.NET) API wrapper

  • Requirement: The system shall provide, for each component API, a managed .NET wrapper generated by the Xidl toolkit and bound to the native provider by dependency injection of the managed-DLL factory.
  • Priority: Conditional
  • Rationale: Allows .NET clients to consume the API as managed objects rather than raw native calls; the provider injects the managed factory at construction.
  • Source: API/CadAPINImpl/TcCadAPIProvider.cpp (m_cadAPIDllInitializer( 0, "CadAPIMImpl", "TnCadAPI.TcMImplFactory" )); Common/TRUMPF/dist/win/Msvc100/API/CadAPI/TnCadAPIMImpl.hh.
  • Verification: Inspection

FR-AUTO-018 — Import production orders from a PPS/MES system

  • Requirement: Where a PPS plugin is available, the system shall retrieve the list of production orders from the PPS/MES system, each carrying at least order number, operation number, part number, material, desired quantity, due date, machine/workplace, priority and rotatability.
  • Priority: Conditional
  • Rationale: Feeding real production orders into nesting is the core purpose of the Fab/MES adapter.
  • Source: tc_fabAdapter/XidlInterface/FabAdapterApi.xidl (ProdOrder, getProdOrderList, RotatabilityEnum); tc_fabAdapter/FabAdapter/FabConnectorInterface/Interfaces.cs (TiProductionOrder, GetProductionOrdersForNesting).
  • Verification: Test

FR-AUTO-019 — PPS plugin discovery via Windows registry

  • Requirement: The system shall discover the PPS/MES plugin assembly by reading HKLM\SOFTWARE\TRUMPF\TruTops Fab\PPS-Plugin\<version>\PluginPath from the Windows registry and loading the assembly identified there.
  • Priority: Conditional
  • Rationale: Registry-based discovery decouples the shipped adapter from customer-specific PPS connectors.
  • Source: tc_fabAdapter/FabAdapter/FabPluginLocator.cs (FindPlugin(), LoadPlugin(), TcPluginTypeAttribute).
  • Verification: Test

FR-AUTO-020 — PPS plugin licence verification

  • Requirement: If a discovered PPS plugin fails its licence check, then the system shall reject the plugin and behave as if no plugin were available.
  • Priority: Conditional
  • Rationale: Prevents use of unlicensed MES connectors while degrading gracefully to no-adapter operation.
  • Source: tc_fabAdapter/FabAdapter/FabPluginLocator.cs (CheckLicense() gate); FabConnectorInterface/Interfaces.cs (TiPlugin.CheckLicense).
  • Verification: Test

FR-AUTO-021 — Nesting-job validation before hand-off

  • Requirement: When a nesting job is about to be saved or handed to Fab, the system shall let Fab validate it and return a list of validation errors (empty on success).
  • Priority: Conditional
  • Rationale: Nest must not persist jobs that Fab cannot accept; validation errors are surfaced to the user.
  • Source: tc_fabAdapter/XidlInterface/FabAdapterApi.xidl (ValidateNestingJob, ValidationError); FabConnectorInterface/Interfaces.cs (TiJobStateTracker.ValidateNestingJob, TcValidationError).
  • Verification: Test

FR-AUTO-022 — Job and file state feedback to Fab

  • Requirement: The system shall notify Fab of job/file lifecycle events — a nesting job saved from Nest (NotifyNestingJobFromNest), a file loaded or saved (NotifyFile), and a job declared done by the user (DeclareJobAsDone) — tagged with the originating plugin type (Punch, Laser, Nest, CAD, Tube).
  • Priority: Conditional
  • Rationale: Closed-loop status reporting keeps the MES view of production consistent with what operators do in TruTops.
  • Source: tc_fabAdapter/XidlInterface/FabAdapterApi.xidl (NotifyNestingJobFromNest, NotifyFile, DeclareJobAsDone, PluginEnum); FabConnectorInterface/Interfaces.cs (TiJobStateTracker, TeProgrammingSuitePlugin).
  • Verification: Test

FR-AUTO-023 — Notify Fab about CAD file changes

  • Requirement: When a CAD file (e.g. GEO, DXF) is changed in the CAD plugin, the system shall notify Fab of that change after the change has been persisted, logging any failure without aborting the CAD operation.
  • Priority: Conditional
  • Rationale: Keeps the MES aware of part-geometry edits; must be fail-safe so a Fab outage never blocks CAD work.
  • Source: tc_interface/tc_fabAdapter/jobStateTracker.h (notifyFabAboutCadFileChange(), isJobStateTrackerAvailable(), stub-vs-real note).
  • Verification: Test

FR-AUTO-024 — Reference CSV order source plugin

  • Requirement: The system shall provide a reference PPS plugin that reads all *.csv files in a configured exchange base directory and returns their rows as production orders.
  • Priority: Optional
  • Rationale: Gives sites without a full MES a working, file-based order source and a template for custom connectors.
  • Source: tc_fabAdapter/FabAdapter/BasicPpsPlugin/{Plugin.cs,OrderSource.cs,CsvReader.cs} (ReadCsvFilesInBaseDir, StrExchangeBaseDir, CheckLicense always true).
  • Verification: Test

FR-AUTO-025 — Show production order manager from the adapter

  • Requirement: The system shall allow the adapter to open the production-order manager, optionally focusing a given order.
  • Priority: Optional
  • Rationale: Convenience integration so operators can jump from a nest into order management.
  • Source: tc_fabAdapter/XidlInterface/FabAdapterApi.xidl (showProductionOrderManager); FabConnectorInterface/Interfaces.cs (ShowProductionOrderManager).
  • Verification: Demonstration

FR-AUTO-026 — Headless reproduction nesting DLL

  • Requirement: The system shall provide a native reproduction DLL, callable via a pure-C interface from .NET P/Invoke, that accepts a list of parts (id, quantity, angle increment, zero-position angle, GEO buffer), runs a geometry nest on a specified sheet with margins and minimum part distance, and returns per-part placement results (id, angle, X/Y) and an error list.
  • Priority: Conditional
  • Rationale: Enables server-side / batch nesting without the interactive application (e.g. for TruTops Fab or regression), reusing the core nesting engine. See [[17 - FR - Nesting & Palletizing]].
  • Source: tc_reproduction/TopsReproduction/ReproductionPublicInterface.h (addPart, startNest, getNextResultItem, getErrorList, getNestStatus); tc_reproduction/TopsReproductionNET/TcTopsReproduction.cs, TcTopsReproductionUnmanaged.cs.
  • Verification: Test

FR-AUTO-027 — Reproduction module lifecycle and unit selection

  • Requirement: The system shall require the reproduction module to be initialized with a unit system (metric or US customary) before any other call, and shall support reset and unloading of the nest core to release resources and permit re-initialization.
  • Priority: Conditional
  • Rationale: The shared nesting core is a global resource; correct init/reset/unload sequencing prevents cross-talk and leaks between batch runs.
  • Source: ReproductionPublicInterface.h (initialize(long unit), reset(), unloadNestCore()); TcTopsReproduction.cs (Initialize, Reset, Dispose, sReinitialize, UnloadNestCore).
  • Verification: Test

FR-AUTO-028 — Batch reproduction driven from a configuration file

  • Requirement: The system shall support driving reproduction runs from a configuration file that defines, per job, the unit system, sheet dimensions, sheet margins, minimum part distance, and a list of parts with quantity, angle and angle increment.
  • Priority: Conditional
  • Rationale: Provides repeatable, scriptable regression/batch execution of the nesting engine.
  • Source: tc_reproduction/TestTopsReproductionNET/testconfig.ini (JOB, UNIT, SHEET_X/Y, MARGIN_*, DISTANCE, PART=); TcTestTopsReproduction.cs; TruTopsDllNET/test/TestReproduction.ini.
  • Verification: Test

FR-AUTO-029 — Interactive command trace recording (TraceMode)

  • Requirement: Where trace mode is enabled, the system shall record the interactive command trace so a session can be reproduced from a trace file.
  • Priority: Optional
  • Rationale: Trace files underpin reproduction/regression and support diagnostics; the reproduction config references a "TruTops CAD trace file name".
  • Source: tc_python/pythonModules/moduleToPsImpl.cpp (TcUmgeb->isTraceModeActive(), setTraceModeActive); tc_reproduction/TestTopsReproductionNET/testconfig.ini (JOB = trace file name).
  • Verification: Demonstration

FR-AUTO-030 — Laser shop-floor-programming headless DLL

  • Requirement: Where the Laser edition is licensed, the system shall provide a native DLL, callable via a pure-C P/Invoke interface, that initializes for a machine/control/unit/language, converts a DXF drawing to a part, creates a sheet, nests parts onto the sheet, creates a GMT with microjoint/lead-in options, and generates an NC list.
  • Priority: Conditional
  • Rationale: Supports headless / server-side laser shop-floor programming from .NET clients (e.g. TruTops Fab); NC/technology semantics themselves are specified in [[14 - FR - Laser Cutting (ToPs 100)]] and [[18 - FR - NC Generation & Motion Optimization]].
  • Source: tc_las/LaserDlls/LaserCInterface/LaserPublicInterface.h (initialize, convertDrawing, createSheet, nestPartsOnSheet, createGmt, createLst, getLTTList); tc_las/LaserDlls/LaserDotNetInterface/TcLaserDotNetInterface.cs; test TruTopsDllNET/test/TcTestSFP.cs.
  • Verification: Test

FR-AUTO-031 — Managed wrapper resource lifecycle and strong-naming

  • Requirement: The system shall provide managed .NET wrapper assemblies for the interop DLLs that implement deterministic disposal (IDisposable), reference-count the shared nest core so it is unloaded only when the last wrapper is released, and are signed with a strong name.
  • Priority: Conditional
  • Rationale: Prevents resource leaks and cross-talk when multiple wrapper objects share one native core, and satisfies .NET strong-name/GAC requirements.
  • Source: tc_reproduction/TopsReproductionNET/TcTopsReproduction.cs (sObjectCount, DoDispose, UnloadNestCore, ~TcTopsReproduction); Trumpf.Sys.snk, Trumpf.Sys.PublicKey.snk.
  • Verification: Test

FR-AUTO-032 — Native/managed interface signature synchronization

  • Requirement: The system shall keep each native C interface and its corresponding C# P/Invoke declaration in sync so that marshalling of parameters and return types is consistent across the managed/unmanaged boundary.
  • Priority: Essential
  • Rationale: A mismatch between the C export and the P/Invoke signature causes silent memory corruption or crashes; the headers explicitly mandate synchronization.
  • Source: tc_reproduction/TopsReproduction/ReproductionPublicInterface.h ("ATTENTION … synchronized with TopsReproductionNET/TcTopsReproductionUnmanaged.cs"); tc_las/LaserDlls/LaserCInterface/LaserPublicInterface.h (same "ATTENTION" note re TcLaserDotNetUnmanaged.cs).
  • Verification: Inspection

FR-AUTO-033 — Database schema source-control command hooks (inferred)

  • Requirement: The system's build/database tooling shall drive versioning of the SQL schema through configurable command-line hooks (get-latest, add, edit, delete, commit, revert) executed against the Perforce source-control system. (inferred — developer/DB tooling, not end-user runtime)
  • Priority: Optional
  • Rationale: Captures the only command-line/hook driving artifact in scope; it configures Red Gate SQL Source Control against Perforce, not application automation. Retained for traceability; ownership likely belongs to build/DB tooling rather than this functional area.
  • Source: CommandLineHooks.xml (Red Gate HooksConfig, Perforce P4 -s sync/add/edit/delete/submit/revert).
  • Verification: Inspection

5. External Interfaces (area-specific)

Formats, systems and machines this area touches (full detail in [[30 - External Interface Requirements]]):

  • Embedded language runtime: Python 2.5 (python25.dll), Tk/Tkinter for the ToPsGraphics/MMK-debugger UI.
  • External API transport: Xidl toolkit "remote factory" addressed by URI + plugin name; managed/native marshalling; GUI-thread message-queue trigger (GRIT send_message).
  • MES/PPS coupling: TruTops Fab PPS plugin, discovered via Windows registry (HKLM\SOFTWARE\TRUMPF\TruTops Fab\PPS-Plugin); reference CSV exchange directory; production-order and nesting-job data objects (Xidl-generated).
  • .NET interop: P/Invoke DLLs — TopsReproduction.dll / Trumpf.Tops.ReproductionNET.dll, TruTopsLaser C DLL / TnLaserNET managed wrapper; strong-named assemblies.
  • File formats consumed/produced by these surfaces: GEO / DXF / GMT part files, LST (NC list), TAF trace files, CSV order files. See [[11 - FR - Import, Export & File Formats]].
  • Machine/control identity: machine name + type, control name + version (e.g. "L22" / "BR ARNC0") passed into the laser SFP DLL and carried in MachineKey. See [[19 - FR - Tools, Machines, Materials & Technology]].
  • Source-control system: Perforce (via CommandLineHooks.xml) — build/DB tooling only.

6. Assumptions & Constraints

Cross-cutting items link to [[50 - Constraints & Assumptions]]:

  • Legacy runtime versions. Scripting is pinned to Python 2.5 (2014-era); scripts and the Tkinter debugger patch are 2.x-only. This is a fixed technology constraint.
  • Single-threaded core. The interactive core is not thread-safe; external API calls are marshalled onto the GUI thread, and the shared nest core must be reference-counted and unloaded carefully (FR-AUTO-016, -027, -031). Interop tests deliberately exercise cross-talk between reproduction and laser DLLs.
  • Text encoding. Legacy sources use ISO-8859-1 (Latin-1); Python module strings and docstrings are Latin-1. Interop strings crossing the .NET boundary are UTF-16 (wchar_t* / PtrToStringUni).
  • Optional linkage. Automation features exist in "real" and "empty/stub" implementations so editions can omit them (FR-AUTO-012, FR-AUTO-023 stub); presence is edition/licence dependent.
  • Windows-only integration. Registry-based plugin discovery, HWND graphics binding and __declspec(dllexport) interop assume Windows.
  • Signature-sync discipline. The C/C# boundary correctness relies on manual synchronization (FR-AUTO-032); there is no automatic generator for these particular P/Invoke DLLs (unlike the Xidl API).
  • Timestamps. All source carries $Change: 272422 $ / 2014/05/22; the snapshot files are dated May 2024. Treat behaviour as circa this baseline.

7. Open Questions & Ambiguities

  • CommandLineHooks.xml scope mismatch. The file is a Red Gate SQL Source Control / Perforce hook config (DB schema versioning), not application command-line/hook driving. FR-AUTO-033 records it but its true owner is build/DB tooling. Is there a separate, genuine application command-line driver (e.g. -auto/batch switches on the exes) not present in this snapshot?
  • gritx aTucadFunc / aTulasFunc. The brief cites these as evidence of headless flows, but no matching symbols were found under grit/ in this snapshot. Their location/definition could not be confirmed — possibly generated, renamed, or in a module not shipped here.
  • API operation surface. The dist headers (TnCadAPINImpl.hh, etc.) expose only connect/disconnect and Xidl plumbing; the actual callable API operations (open part, run nest, export…) live in the managed *MImpl layer / .xidl definitions not fully present here. The concrete external-API command vocabulary per edition is therefore only partially evidenced.
  • Customization-script caller. runCustomizationScript() is linked into all executables (per .map files) but the exact call site (and whether it runs unconditionally at start-up) was not located in the available .cpp sources.
  • tc_catch classification. Listed in scope, but its content (catchdef.h, pickmodi, dc_catch) is geometry pick / hit-testing for interactive selection — it appears to belong to [[22 - FR - UI Framework, Dialogs & Interaction (GRIT)]] or [[10 - FR - CAD Geometry & Drawing Editing]] rather than automation. Flagged for the owning analyst.
  • tc_interface role. This directory is a public-header aggregation hub (per-module published interfaces), i.e. the internal cross-module API layer, rather than an external automation surface. Only tc_interface/tc_fabAdapter is clearly in this area; the rest cross-cuts other functional areas.
  • Trace-file (.taf) format & replay path. TraceMode recording is evidenced, but the exact trace-file schema and the code path that replays a trace for reproduction were not fully traced.
  • NestCore vs reproduction vs SFP boundaries. Reproduction and the laser SFP DLL both wrap a shared NestCore (tc_nest/NestCore); the precise division of responsibility and whether they can run concurrently in one process (beyond the cross-talk test) is unclear.
