Bending Detail — NC Code Generation

Reverse-engineered requirement draft — derived from static analysis of legacy source, NOT an authoritative specification. Treat SHALL statements as reconstructed intent. This is a Tier-2 detail document that refines [[16 - FR - Bending (ToPs 600)]]; its requirements are tracked here and are not added to the 603-item system register (same convention as the CAD Tier-2 sub-suite 10.1–10.8).

1. Purpose & Scope

This document specifies the functional requirements for bending NC code generation — turning a technologically finished bend program (a part with classified bends, assigned tools, computed factors and, for an automated cell, a handling plan) into the controller-specific text that drives the press brake and, where present, the automation/handling controller of a bending cell such as the [[16.2 - Cell7000 — Overview|TruBend Cell 7000]].

In the existing suite, bending NC output was explicitly declared out of scope for [[18 - FR - NC Generation & Motion Optimization]] ("Bending NC output (ToPs 600, Bend.NC_FORMATE) is out of scope and owned by [[16 - FR - Bending (ToPs 600)]]"). [[16 - FR - Bending (ToPs 600)]] in turn recorded it as delegated (FR-BEND-030, inferred). This document fills that gap by specifying what the ToPs 600 bend database and the BendAPI automation surface reveal about the bending post-processor.

Provenance boundary — read first. There is no readable C++ in this snapshot that generates bending press/automation NC, computes bend sequence, drives robot motion, or performs press-brake collision checking. Every NC_AUSGABE*/ROBOTERPROZESS/KemroK2 token occurs only in SQL; the C++ that mentions "bending" is exclusively CAD flat-pattern unfolding (Abkantfaktor) math (tc_profil/TcProfilAbwickler.cpp, tc_interface/tc_profil/TiProfilFaktorBerechner.h). The generation engine is compiled application code (ToPs 600 / TruTops bend runtime, "BendMaster"), driven headlessly through the BendAPI AutomationCommand over .NET Remoting (see FR-BEND-NC-017 and [[30 - External Interface Requirements]]). What is reverse-engineerable — and what this document specifies — is the data contract: the Bend schema tables that define the NC template model, its formatting, limits, presets and transfer routing. Statements about the algorithm are therefore marked (inferred); statements about the data contract are grounded in the schema.

Editions/scope. ToPs 600 bending. The Bend schema was migrated from the ToPs 600 database (MS_SSMA_SOURCE = T600_V100.*); the two schema snapshots (Databases/SQLServerDatabase/Tables/ and Databases_SQL_2019/DatabaseStructure/TruTopsMaster/Tables/) are structurally identical (differing only in collation and GRANTs). Source citations below use the Databases/SQLServerDatabase/Tables/ path for consistency with [[16 - FR - Bending (ToPs 600)]].

2. Capability Overview

  • Template-driven NC emission — a generated NC block is produced by expanding a stored NC record template (NC_SATZ) that contains $ placeholders, one template set for the press control and one for the automation control.
  • Placeholder value formatting — each $ placeholder is rendered by a printf-style format selected by control + placeholder number, with separate metric and inch formats.
  • Unit-aware output — the emitted unit text and decimal precision come from the active units table; metric/inch mode is a system setting.
  • Output validation — the assembled NC is checked against field/record limits (maximum records, pattern-record occurrence caps).
  • Per-machine/per-user output presets — program numbering, file names, paths, which artefacts to produce, transfer targets and bend-time surcharges are stored as presets.
  • Multi-artefact output — NC program, setup plan (Einrichteplan), simulation/setup graphics, barcode, bend-time file and robot-interface file are individually selectable.
  • Robot/automation output — the automation controller (KemroK2) has its own NC template stream, robot speed-profile reference numbers, and a robot-interface file transfer path.
  • Crowning compensation — ram/table deflection (Bombieren) correction data is held per machine for the post-processor.
  • Delegated generation — the actual substitution / assembly / limit-check / file-write engine is compiled ToPs 600 code, invoked via BendAPI.

4. Functional Requirements

FR-BEND-NC-001 — Template-driven NC record model

  • Requirement: The system SHALL generate bending NC by expanding stored NC record templates (NC_SATZ), each of which is an "NC-Ausgabe-Beschreibung mit Platzhalter (\()" — an NC block text carrying `\)` placeholders that are resolved to formatted values at generation time.
  • Priority: Essential
  • Rationale: A data-driven template model lets new controllers/dialects be supported by editing table data rather than changing code.
  • Source: Databases/SQLServerDatabase/Tables/Bend.NC_AUSGABE_PRESSE.sql, Bend.NC_AUSGABE_AUTOMAT.sql (NC_SATZ nvarchar(max), MS_Description "NC-Ausgabe-Beschreibung mit Platzhalter ($)").
  • Verification: Inspection / Test.

FR-BEND-NC-002 — Separate press and automation NC output streams

  • Requirement: The system SHALL maintain two independent NC output template streams: one for the press brake (NC_AUSGABE_PRESSE) and one for the automation/handling controller (NC_AUSGABE_AUTOMAT).
  • Priority: Essential
  • Rationale: The press control and the cell/robot controller are different devices with different code; an automated cell requires both a press program and a coordinated automation program.
  • Source: Bend.NC_AUSGABE_PRESSE.sql (default NC_STEUERUNG = 'DA24+58'), Bend.NC_AUSGABE_AUTOMAT.sql (default NC_STEUERUNG = 'KemroK2'; wider NC_ZYKLUS nvarchar(40) vs press nvarchar(15)).
  • Verification: Inspection.

FR-BEND-NC-003 — Controller-keyed template selection

  • Requirement: The system SHALL select NC templates by controller designation (NC_STEUERUNG) and cycle/output description (NC_ZYKLUS), and SHALL reserve a controller-version window (NC_ST_VERSION_MIN/NC_ST_VERSION_MAX) for version-scoped selection.
  • Priority: Essential
  • Rationale: Each control (e.g. Delem/TRUMPF DA24+58 presses, Keba KemroK2 automation) emits a different dialect; the template set is chosen per control.
  • Source: Bend.NC_AUSGABE_PRESSE.sql/Bend.NC_AUSGABE_AUTOMAT.sql (NC_STEUERUNG, NC_ZYKLUS, NC_ST_VERSION_MIN/MAX, non-clustered indexes on NC_STEUERUNG/NC_ZYKLUS).
  • Verification: Inspection.

FR-BEND-NC-004 — Placeholder value formatting (metric and inch)

  • Requirement: When expanding an NC template, the system SHALL render each $ placeholder using an output format selected by controller (AUS1_STEUERUNG) and placeholder number (AUS1_NUMMER), applying the metric format (AUS1_FORMAT_METRISCH) or the inch format (AUS1_FORMAT_INCH) according to the active unit mode.
  • Priority: Essential
  • Rationale: The same placeholder must render differently for metric and inch output; formatting is data-driven and control-specific.
  • Source: Bend.NC_FORMATE.sql (AUS1_NUMMER "Nummer des Platzhalters (siehe NC_AUSGABE_PRESSE bzw NC_AUSGABE_AUTOMAT)", AUS1_STEUERUNG, AUS1_FORMAT_METRISCH, AUS1_FORMAT_INCH, AUS1_FAKTOR; UNIQUE index on AUS1_NUMMER).
  • Verification: Test (compare emitted value formatting metric vs. inch on a reference part).

FR-BEND-NC-005 — Unit text and decimal precision from the units tables

  • Requirement: The system SHALL take the NC unit text and decimal-shift for generated NC from the active units table, and SHALL select metric or inch operation from system settings.
  • Priority: Conditional
  • Rationale: The literal unit string and number of decimals emitted into NC are configurable per unit definition; metric/inch is a global mode.
  • Source: Bend.EINHEITEN_METRISCH.sql/Bend.EINHEITEN_INCH.sql (EINHEIT_NC_TEXT "Ausgabetext der Einheit im NC", NACHKOMMASTELLEN_SHIFT); Bend.EINHEITEN_VERZEICHNIS.sql (active units table selection); Bend.SETTINGS.sql (ST_AUTO_INCH).
  • Verification: Test.

FR-BEND-NC-006 — Field/record-limit validation of generated NC

  • Requirement: The system SHALL validate the generated NC against configured field limits, enforcing a maximum number of records per group (NC_GRP_MAX_SATZ) and, where enabled, a pattern-record ("Mustersatz") check that counts occurrences of a value at a given position and enforces a maximum.
  • Priority: Conditional
  • Rationale: Controllers have finite program/field/record capacity; exceeding it produces an unloadable program.
  • Source: Bend.NC_FELDGRENZEN.sql (NC_GRP_NAME, NC_GRP_MAX_SATZ, NC_MM_PRUEFEN, NC_MM_MUSTERSATZ, NC_MM_POSITION_SATZ, NC_MM_POSITION_WERT, NC_MM_POSITION_MAX, NC_CONTROL).
  • Verification: Test.

FR-BEND-NC-007 — Per-machine / per-user NC output presets

  • Requirement: The system SHALL store NC output presets keyed by machine name and user, including last program number, NC program name and storage path.
  • Priority: Essential
  • Rationale: Output naming/paths and the running program number are per-operator/per-machine settings that must persist.
  • Source: Bend.NC_VOREINSTELLUNG.sql (Maschinenname, Userkennung, Programmnummer, NCName, NCPfadname; PK (Maschinenname, Userkennung)).
  • Verification: Demonstration.

FR-BEND-NC-008 — Selectable output artefacts

  • Requirement: When generating output, the system SHALL let the user select which artefacts are produced, including at minimum the NC program, a graphic, and a robot program, encoded as a bit flag.
  • Priority: Essential
  • Rationale: Different runs need different deliverables (program only, program + graphics, or a robot program for an automated cell).
  • Source: Bend.NC_VOREINSTELLUNG.sql (FlagBendprogramNew "Kennflag was ausgegeben wird ( 1 = Progamm, 2 = Grafik, 4 = Roboterprogramm etc. )"; legacy FlagBendprogramOld).
  • Verification: Demonstration.

FR-BEND-NC-009 — Robot/automation interface file output

  • Requirement: Where automation output is enabled, the system SHALL produce a robot-interface file with a configured name and path, and SHALL provide a transfer target path for that file.
  • Priority: Conditional
  • Rationale: An automated bending cell is fed by a robot-interface file distinct from the press NC program.
  • Source: Bend.NC_VOREINSTELLUNG.sql (FlagRobotInterface, RobotIFName, RobotIFPfadname, TransferIFPfadname "Wohin soll die Interfacedatei für den Roboter transferiert werden"; FlagBendprogramNew bit 4 = Roboterprogramm).
  • Verification: Demonstration.

FR-BEND-NC-010 — NC program naming scheme

  • Requirement: The system SHALL derive the NC program name from a configurable scheme in which the low byte selects the program-name basis and the high byte selects a setup-number suffix.
  • Priority: Conditional
  • Rationale: Shops standardise NC file naming; the scheme must be configurable and encode a setup (Rüst) number.
  • Source: Bend.PROZESSDATEN.sql (NCPROGNAME "Default für NC-Programmname (Bit 0-7) und Anhängsel Rüstnummer (Bit 8-15)"); Bend.NC_VOREINSTELLUNG.sql (Programmnummer, NCName).
  • Verification: Inspection.

FR-BEND-NC-011 — Setup plan (Einrichteplan) output

  • Requirement: Where a setup plan is requested, the system SHALL generate an Einrichteplan with configurable content and output mode, and MAY allow editing it before printing.
  • Priority: Conditional
  • Rationale: The operator needs a printable setup document to rig tools and run the program.
  • Source: Bend.NC_VOREINSTELLUNG.sql (EPPfadname, EPName, FlagInhaltEinrichteplan, FlagAusgabe, FlagEditor "Einrichteplan bearbeiten vor dem Drucken", FlagDruckerwahl). See [[18 - FR - NC Generation & Motion Optimization]] (FR-NC-025) for the punch/laser analogue.
  • Verification: Demonstration.

FR-BEND-NC-012 — Bend-time calculation and surcharges

  • Requirement: Where bend-time output is enabled, the system SHALL compute a bend-time figure using configurable time surcharges (Zeitzugaben) for checking, tool set-up/tear-down, bending, feed-in and rest allowances, and SHALL write it to a configured interface file.
  • Priority: Conditional
  • Rationale: Bend-time is needed for costing/scheduling and is fed to downstream systems.
  • Source: Bend.NC_VOREINSTELLUNG.sql (FlagBendtime, BendtimeName, BendtimePfadname, BendtimeBerechnung, ZugabeFuerPruefen, ZugabeRuestenMatrize, ZugabeRuestenStempel, ZugabeAbruestenStempel, ZugabeAbruestenMatrize, ZugabeFuerBiegen, ZugabeFuerEinfahren, ZugabeErholung).
  • Verification: Test.

FR-BEND-NC-013 — Automatic transfer of generated output

  • Requirement: Where transfer is enabled, the system SHALL transfer the NC program, the bend-time file and the robot-interface file to their configured destinations according to a transfer selection flag.
  • Priority: Conditional
  • Rationale: Integrates output with machine loading/DNC without manual file handling.
  • Source: Bend.NC_VOREINSTELLUNG.sql (FlagTransfer, TransferPfadname, TransferTimePfadname, TransferIFPfadname).
  • Verification: Demonstration.

FR-BEND-NC-014 — Robot speed-profile selection by reference number in NC

  • Requirement: The system SHALL select a robot motion dynamics profile in the generated automation NC by emitting its reference number.
  • Priority: Conditional
  • Rationale: The robot's accel/velocity/decel/jerk profile is chosen per motion by a small numeric handle emitted into the program rather than by inlining the full dynamics.
  • Source: Bend.ROBOTGESCHWINDIGKEIT.sql (Referenznummer "Referenznummer zur Ausgabe im NC"; acceleration/velocity/deceleration/jerk values for each of Drehen/Fahren/Orient). See [[16.4 - Cell7000 — Robot, Process & Motion Data]].
  • Verification: Inspection.

FR-BEND-NC-015 — Crowning (Bombieren) compensation data for the post-processor

  • Requirement: The system SHALL hold per-machine crowning compensation data — beam/table deflection at the load point/load case and a crowning-setting-to-DELTA_Y correction curve per Z position — for use in generating the press program's crowning command.
  • Priority: Conditional
  • Rationale: Ram/table deflection under load must be compensated for a straight bend; the values are machine-specific and post-processor input.
  • Source: Bend.BOMBWERTE.sql, Bend.BOMB_EINSTELLWERTE.sql (crowning setting → DELTA_Y at each POS_Z). See [[16.3 - Cell7000 — Machine & Cell Configuration]].
  • Verification: Analysis.

FR-BEND-NC-016 — Table-to-struct export mechanism for the runtime

  • Requirement: The system SHALL provide a data-driven mapping from runtime technology-class names to their backing database tables and the key fields identifying a row, so bend technology/NC data can be serialised into the compiled runtime's structures.
  • Priority: Conditional
  • Rationale: The compiled bend runtime consumes DB rows as C/C++ structures; the mapping is itself data-driven and can exclude tables from export.
  • Source: Bend.EXPORT_CLASSNAME_TABLE_MAP.sql (EXPORT_CLASSNAME "Klassenname (Technoklassen)" → EXPORT_TABLENAME), Bend.EXPORT_TABLE_DEF.sql (EXPORT_KEY1..3); Databases/SQLServerDatabase/Views/Bend.DATADICT.sql (DD_createSdbTopsInterface "Tabelle wird nicht in die c/cpp-Strukturen exportiert").
  • Verification: Inspection.

FR-BEND-NC-017 — NC generation delegated to the compiled ToPs 600 / BendAPI runtime (inferred)

  • Requirement: The placeholder-substitution, block-assembly, limit-checking and file-writing engine for bending NC SHALL be provided by the compiled ToPs 600 / TruTops bend runtime, invoked headlessly through the BendAPI AutomationCommand, rather than being implemented in the readable ToPs 600 CAD source. (inferred)
  • Priority: Conditional
  • Rationale: No readable C++ NC/robot generation exists in this snapshot; the BendAPI exposes only a generic AutomationCommand(AutomationData: string) over .NET Remoting whose payload semantics live in the compiled DLL.
  • Source: Common/TRUMPF/dist/win/Msvc100/API/BaseAPI/TiNAutomationCommand.cpp (AutomationData, doc "No compiled in documentation available."), TiNImplAutomationCommand.hh (virtual void execute() = 0); Common/TRUMPF/dist/win/Msvc100/API/BendAPI*; absence of NC_AUSGABE_AUTOMAT/ROBOTERPROZESS/KemroK2 in any .cpp/.h/.gritx. See [[30 - External Interface Requirements]] and FR-BEND-030.
  • Verification: Analysis.

FR-BEND-NC-018 — Reserved version and cycle-time hooks (inferred)

  • Requirement: The system MAY use the reserved controller-version window and per-block cycle-time fields for version-scoped template selection and block-level cycle-time contribution; in this snapshot these fields are documented "für die Zukunft" (reserved) and effectively inert. (inferred)
  • Priority: Optional
  • Rationale: The schema documents these hooks as reserved; effective keying today is by control + cycle/placeholder, and bend-time comes from NC_VOREINSTELLUNG surcharges, not per-block NC_ZEIT.
  • Source: Bend.NC_AUSGABE_PRESSE.sql/Bend.NC_AUSGABE_AUTOMAT.sql (NC_ST_VERSION_MIN/MAX, NC_NUMMER "immer 1 (für die Zukunft)", NC_ZEIT "Relevanz für Zykluszeitberechnung (für die Zukunft)"); Bend.NC_FORMATE.sql (AUS1_FAKTOR, AUS1_ST_VERSION_MIN/MAX "für die Zukunft").
  • Verification: Inspection.

FR-BEND-NC-019 — Barcode output for shop-floor identification

  • Requirement: Where enabled, the system SHALL emit a barcode for the generated program using a configurable font, size and storage path.
  • Priority: Optional
  • Rationale: Shop-floor scanning of programs requires a barcode artefact.
  • Source: Bend.NC_VOREINSTELLUNG.sql (FlagBarcodeNetwork, BarcodePfadname, BarcodeFont, BarcodeFontsize).
  • Verification: Demonstration.

FR-BEND-NC-020 — Simulation and setup graphics output

  • Requirement: Where enabled, the system SHALL output simulation/setup graphics with configurable layout (graphics per page, additional views, single-graphic mode) alongside the NC program.
  • Priority: Optional
  • Rationale: Operators use setup/simulation graphics to verify the program before running.
  • Source: Bend.NC_VOREINSTELLUNG.sql (FlagGrafikSimulation, FlagGrafikRuestplan, AnzahlGrafikVertikal, AnzahlGrafikHorizontal, FlagZusatzgrafik, FlagEinfachgrafik, FlagSofortAnzeigen, GrafikWinkelinkrement).
  • Verification: Demonstration.

5. External Interfaces (area-specific)

  • ToPs 600 bend database — Bend schema NC tables: NC_AUSGABE_PRESSE, NC_AUSGABE_AUTOMAT, NC_FORMATE, NC_FELDGRENZEN, NC_VOREINSTELLUNG, plus the units tables (EINHEITEN_*), crowning (BOMBWERTE, BOMB_EINSTELLWERTE) and the export map (EXPORT_CLASSNAME_TABLE_MAP, EXPORT_TABLE_DEF). Migrated from T600_V100. See [[19 - FR - Tools, Machines, Materials & Technology]] and [[30 - External Interface Requirements]].
  • BendAPI (native + .NET) — the headless drive surface (AutomationCommand, lifecycle commands) over a .NET Remoting TCP channel; the compiled implementation performs the actual NC generation. See [[23 - FR - Automation, Scripting & Integration]] and [[30 - External Interface Requirements]].
  • Press-brake controller — target of the press NC (DA24+58 and family).
  • Automation/handling controller — target of the automation NC (KemroK2 / Keba KeMotion family); consumes the robot-interface file. See [[16.2 - Cell7000 — Overview]].
  • Output files & transfer — NC program, setup plan (HTML/print), graphics, barcode, bend-time file and robot-interface file, transferred to configured destinations.

6. Assumptions & Constraints

  • A1. The bend program (bends, tools, factors, and for a cell the handling plan) is complete and technologically valid before NC generation runs; this area emits, it does not create technology. (inferred)
  • A2. The actual generation algorithm is compiled ToPs 600 code (FR-BEND-NC-017); the schema evidences the inputs and contracts of generation, not the algorithm. Every requirement traced only to Bend.NC_* tables inherits this assumption.
  • C1. Effective template keying is by control + cycle/placeholder; the version-window and per-block cycle-time fields are reserved (FR-BEND-NC-018).
  • C2. Metric and inch behaviour is data-driven (NC_FORMATE dual formats, EINHEITEN_* NC text/decimals); correct output depends on the active unit mode and units table.
  • C3. Controllers observed as defaults are DA24+58 (press) and KemroK2 (automation); the full set of NC_STEUERUNG values is data, not schema, and was not enumerated.
  • Cross-cutting constraints/assumptions are consolidated in [[50 - Constraints & Assumptions]]; quality targets in [[40 - Non-Functional Requirements]].

7. Open Questions & Ambiguities

  1. $-placeholder grammar. The exact placeholder numbering/escaping syntax inside NC_SATZ is not in the schema — only "Platzhalter ($)" and the join to NC_FORMATE.AUS1_NUMMER. Needs sample data or the compiled engine.
  2. NC_STEUERUNG domain. Whether KemroK2 is the only automation control (and whether a TruBend Cell 7000 uses a distinct NC_STEUERUNG string) is data-dependent and unresolved.
  3. NC_CONTROL in NC_FELDGRENZEN has no description; its role as a per-control scope is inferred from its PK membership.
  4. FlagBendprogramNew bit set — documented "1=Programm, 2=Grafik, 4=Roboterprogramm etc."; the "etc." bits and FlagInhaltEinrichteplan/FlagAusgabe/FlagZusatzgrafik bit meanings are undocumented.
  5. AusgabeBMT ("BMT" file) format and its relation to the automation transfer path is undocumented.
  6. Cycle-time source. With NC_ZEIT reserved, bend-time comes from NC_VOREINSTELLUNG.Zugabe* surcharges; the calculation model behind them was not located in readable source.
  7. Which compiled module reads these tables and performs generation (ToPs 600 exe vs. BendAPI DLL) is outside this snapshot.
