Bending — Module Overview

Reverse-engineered orientation page — derived from static analysis of legacy source, NOT an authoritative specification. This is the map of the bending area and the entry point to the Tier-2 bending detail sub-suite that refines [[16 - FR - Bending (ToPs 600)]].

1. What "bending" covers in TruTops

TRUMPF's bending world spans CAD bend definition (ToPs 600), the ToPs 600 bend-technology database, and the automated bending cell (e.g. the TruBend Cell 7000). Turning a part into a runnable press-brake program involves four layers:

  1. CAD bend definition & unfolding — mark bend lines; classify each bend by kind/method/technique; capture angle, radii; compute the bend-deduction factor (Abkantfaktor) and the flat pattern (Abwicklung); assign punch/die tools; author profiles, bumping bends, corner reliefs and custom tools. This is the readable ToPs 600 CAD source and is specified by [[16 - FR - Bending (ToPs 600)]] (FR-BEND-001..030).
  2. Bend technology (ToPs 600 database) — the shared bend-factor table, the punch/die/hem/Z/swivel/wave/flat/hinge tool catalogue, tool groups, adapters/holders/receivers, machine configuration, crowning, and units. It is the data backbone behind layers 1, 3 and 4.
  3. Automation & handling (bending cell) — the robot (BendMaster), grippers, regripping, turning/unload stations, pallets and conveyors that let the cell run unattended. Specified by the [[16.2 - Cell7000 — Overview|Cell7000 sub-suite]].
  4. NC code generation — turning the finished, technologically valid program into controller-specific press NC and the coordinated automation/robot program. Specified by [[16.1 - Bending — NC Code Generation]].

Provenance boundary. In this snapshot, layer 1 is readable C++/GRIT; layers 2–4 are almost entirely SQL data plus a thin compiled automation API. Automatic bend-sequence determination, press-brake collision checking, robot motion and NC emission are delegated to the separate compiled ToPs 600 / BendAPI ("BendMaster") application and are not reverse-engineerable from C++ here. This overview and the detail docs specify the data contract and the automation surface, not the compiled algorithms. This is consistent with [[16 - FR - Bending (ToPs 600)]] FR-BEND-030 (delegated, inferred).

3. Where bending sits relative to the rest of the suite

  • Tools/machines/materials — the bend tool catalogue and factors are part of the master-data foundation shared with [[19 - FR - Tools, Machines, Materials & Technology]]; the bend database is the ToPs 600 Bend schema.
  • NC generation — [[18 - FR - NC Generation & Motion Optimization]] covers punch/laser/tube NC and explicitly excludes bending; bending NC is specified here in [[16.1 - Bending — NC Code Generation]]. The two are architecturally different: punch/laser NC is data-driven and has readable C++ post-processor/optimizer code (tc_nc, tc_constrainedTspSolver, tc_wopt), whereas bending NC is data-driven with a compiled, non-readable engine.
  • Palletising/part flow — the cell's stacking/handling parallels punch/laser palletising in [[17 - FR - Nesting & Palletizing]] but is bend-specific (Bend schema).
  • Automation/integration — the cell is driven headlessly via the BendAPI (see [[23 - FR - Automation, Scripting & Integration]] and [[30 - External Interface Requirements]]).
  • Glossary — bend and cell terms are collected in [[04 - Domain Model & Glossary]] and in [[16.2 - Cell7000 — Overview]] §5.

4. Editions & controllers

  • Editions: ToPs 600 (bending CAD/CAM; Full/Lite/Basic), with the ToPs 600 bend database as the technology + automation backbone.
  • Controllers observed: DA24+58 (press-brake control, default for NC_AUSGABE_PRESSE) and KemroK2 (automation/handling control, default for NC_AUSGABE_AUTOMAT). The full NC_STEUERUNG domain is data, not schema.
  • Units: metric and inch database variants; NC unit text and precision are data-driven (EINHEITEN_*).
