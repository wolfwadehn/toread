Cell7000 Detail — Machine & Cell Configuration

Reverse-engineered requirement draft — derived from static analysis of legacy source, NOT an authoritative specification. Treat SHALL statements as reconstructed intent. Tier-2 detail refining [[16 - FR - Bending (ToPs 600)]]; not added to the 603-item register.

1. Purpose & Scope

This document specifies how the bending database models the machine and cell configuration that a robotic bending cell such as the TruBend Cell 7000 instantiates: the machine-configuration identity, the generic cell component/parameter model (MASCH_CELL*), the shared typed parameter store (PARAMETER*), the crowning (Bombieren) compensation tables, the transillumination/backlight table (Durchleuchttisch), and the unit definitions that steer numeric output.

Provenance & evidence note. None of the tables in this cluster contains a literal "Cell7000"/"BendMaster" string; the Cell 7000 relationship is structural — a Cell 7000 machine is one MASCHINE_KONF whose MASCH_CELL_CONFIG selects a cell configuration whose components/parameters are the ones described here, and whose BendMaster defaults live in [[16.4 - Cell7000 — Robot, Process & Motion Data]]. All tables carry MS_SSMA_SOURCE = T600_V100.* (migrated from the ToPs 600 bend DB). Referential integrity is almost entirely application-enforced — apart from the PARAMETER_TEXT/PARAMETER_ZAHL foreign keys, the tables here declare no FK constraints and link by name strings. Requirements below describe the data contract; the consuming logic is compiled ToPs 600 code (see [[16.1 - Bending — NC Code Generation]] FR-BEND-NC-017).

2. Capability Overview

  • Identify a bend machine configuration (MASCHINE_KONF) and map it to a numeric cell configuration (MASCH_CELL_CONFIG).
  • Describe a cell as a set of components (MASCH_CELL — press, robot, stations…), each with an active flag.
  • Attach typed parameters (real / long / string) to each cell component (MASCH_CELL_PARAM), and map generic cell parameters onto legacy machine parameters (MASCH_CELL_PARAM_MAPPING).
  • Maintain a shared, self-referential parameter store (PARAMETER + PARAMETER_TEXT/PARAMETER_ZAHL/PARAMETER_UNIT) and assign parameters to machines (PARAMETER_TO_MASCHINE_KONF).
  • Hold crowning (Bombieren) compensation: deflection at the load point (BOMBWERTE) and a crowning-setting→DELTA_Y correction curve (BOMB_EINSTELLWERTE).
  • Hold transillumination table geometry (DURCHLEUCHTTISCH) for the measuring/backlight step.
  • Define units (EINHEITEN_METRISCH/EINHEITEN_INCH/EINHEITEN_VERZEICHNIS) that drive NC unit text and precision; global settings (SETTINGS) and enum values (ENUMWERTE); schema version (DB_VERSION).

3. Domain Entities

4. Functional Requirements

FR-CELL-CFG-001 — Identify a bend machine configuration

  • Requirement: The system SHALL identify each configured bend machine by a unique machine-configuration name that keys its process, robot, NC-output and tooling data across the Bend schema.
  • Priority: Essential
  • Rationale: The machine-configuration name is the join key tying together process defaults, robot defaults, NC presets and cell layout for one physical machine/cell.
  • Source: Databases/SQLServerDatabase/Tables/Bend.MASCHINE_KONF.sql; the MASCHINE_KONF_NAME key recurs in Bend.ROBOTERPROZESSDATEN, Bend.PROZESSDATEN, and (as Maschinenname) Bend.NC_VOREINSTELLUNG.
  • Verification: Analysis.

FR-CELL-CFG-002 — Map a machine to a cell configuration

  • Requirement: The system SHALL map each machine name to exactly one numeric cell configuration id.
  • Priority: Essential
  • Rationale: A cell's component set is selected by resolving the machine to its configuration id (one configuration per machine).
  • Source: Bend.MASCH_CELL_CONFIG.sql (CELL_MAP_MASCHINE → CELL_MAP_CONFIG; PK on CELL_MAP_MASCHINE).
  • Verification: Inspection.

FR-CELL-CFG-003 — Describe a cell as configured components

  • Requirement: The system SHALL describe a cell configuration as a set of components, each with a component id, a machine-component key, a designation and an active flag.
  • Priority: Essential
  • Rationale: A robotic cell is an assembly of components (press, robot, stations); the configuration records which are present and active.
  • Source: Bend.MASCH_CELL.sql (CELL_CONFIG_ID, CELL_KOMP_ID, CELL_MASCH_KOMP, CELL_KOMP_BEZ, CELL_KOMP_AKTIV; PK (CELL_CONFIG_ID, CELL_KOMP_ID)).
  • Verification: Inspection.

FR-CELL-CFG-004 — Attach typed parameters to cell components

  • Requirement: The system SHALL attach named parameters to each cell component, storing each parameter's value in parallel real, long and string slots.
  • Priority: Essential
  • Rationale: Cell components carry heterogeneous configuration values; a typed key/value model stores them generically.
  • Source: Bend.MASCH_CELL_PARAM.sql (CELL_KOMP_CONFIG_ID, CELL_KOMP_ID, CELL_KOMP_PARAM_ID, CELL_KOMP_PARAM_NAME, CELL_KOMP_PARAM_REAL, CELL_KOMP_PARAM_LONG, CELL_KOMP_PARAM_STRING).
  • Verification: Inspection.

FR-CELL-CFG-005 — Map generic cell parameters onto legacy machine parameters

  • Requirement: The system SHALL translate a generic cell parameter name to a corresponding legacy machine parameter (name, type and owning table/component) so cell configuration can be reconciled with the legacy machine-parameter model.
  • Priority: Conditional
  • Rationale: The cell model and the legacy machine-parameter model coexist; a bridge maps between them.
  • Source: Bend.MASCH_CELL_PARAM_MAPPING.sql (generic CELL_PARAM_NAME → MASCH_PARAM_NAME/MASCH_PARAM_TYPE, with TABELLE/KOMPONENTE string references). The mapping is resolvable only in application code (no FK).
  • Verification: Analysis.

FR-CELL-CFG-006 — Maintain a typed parameter store

  • Requirement: The system SHALL maintain a shared parameter store in which parameters form a tree (each parameter may reference a parent) and are typed, with 1:1 text and numeric extension records and an associated unit.
  • Priority: Conditional
  • Rationale: Bending technology/configuration is parameterised through a general typed parameter model reused across features.
  • Source: Bend.PARAMETER.sql (self-reference via PARAMETER_VATER, PARAMETER_TYP), Bend.PARAMETER_TEXT.sql and Bend.PARAMETER_ZAHL.sql (1:1 extensions, FK to PARAMETER ON DELETE CASCADE — the only real FKs in the cluster), Bend.PARAMETER_UNIT.sql, Bend.PARAMETER_TO_MASCHINE_KONF.sql (machine assignment with AKTIV flag).
  • Verification: Inspection.

FR-CELL-CFG-007 — Assign parameters to machines with an active flag

  • Requirement: The system SHALL associate parameters with machine configurations through a many-to-many assignment carrying an active flag.
  • Priority: Conditional
  • Rationale: The same parameter definitions apply to multiple machines; the assignment records applicability and activation.
  • Source: Bend.PARAMETER_TO_MASCHINE_KONF.sql (machine ↔ parameter with AKTIV).
  • Verification: Inspection.

FR-CELL-CFG-008 — Hold ram/table crowning (Bombieren) compensation

  • Requirement: The system SHALL hold, per machine, crowning compensation data consisting of beam/table deflection at the load point per load case (BOMBWERTE) and a crowning-setting-value-to-DELTA_Y correction at each Z position (BOMB_EINSTELLWERTE).
  • Priority: Conditional
  • Rationale: Deflection under bending load must be compensated for a straight bend; the values are machine-specific and feed the press post-processor (see [[16.1 - Bending — NC Code Generation]] FR-BEND-NC-015).
  • Source: Bend.BOMBWERTE.sql, Bend.BOMB_EINSTELLWERTE.sql (keyed by machine/crowning id; BOMBWERTE.MASCH_ID nvarchar(20), no FK to MASCHINE_KONF).
  • Verification: Analysis.

FR-CELL-CFG-009 — Hold transillumination-table geometry

  • Requirement: Where a cell uses a transillumination/backlight table for part recognition or measurement, the system SHALL hold that table's geometry — table length/width/height plus the light-band position and size — and a drawing reference.
  • Priority: Conditional
  • Rationale: The backlight (Durchleucht) station geometry is needed to plan/measure the transillumination step; its presence per program is flagged in the robot process data.
  • Source: Bend.DURCHLEUCHTTISCH.sql (table L/W/H, Lichtband position/size, drawing name). Consumed with Bend.ROBOTERPROZESSDATEN.DURCHLEUCHTEN_FLAG "Kennung ob BendMasterprogramm mit/ohne Durchleuchtstation" (see [[16.4 - Cell7000 — Robot, Process & Motion Data]]).
  • Verification: Inspection.

FR-CELL-CFG-010 — Define units and drive NC unit text/precision

  • Requirement: The system SHALL define metric and inch unit tables carrying, per unit, the NC output text and a decimal-shift, select the active units table by name, and expose a global metric/inch conversion setting.
  • Priority: Essential
  • Rationale: Numeric output (including NC) depends on the active units definition for unit text and precision; metric/inch is a global mode.
  • Source: Bend.EINHEITEN_METRISCH.sql/Bend.EINHEITEN_INCH.sql (EINHEIT_NC_TEXT "Ausgabetext der Einheit im NC", NACHKOMMASTELLEN_SHIFT), Bend.EINHEITEN_VERZEICHNIS.sql, Bend.SETTINGS.sql (ST_AUTO_INCH). See [[16.1 - Bending — NC Code Generation]] FR-BEND-NC-005.
  • Verification: Test.

FR-CELL-CFG-011 — Maintain enumeration values and schema version

  • Requirement: The system SHALL maintain a table of enumeration values used to validate coded columns, and SHALL record the bend database schema version.
  • Priority: Conditional
  • Rationale: Many bend columns are coded integers validated against enum sets; the schema version gates migration/compatibility.
  • Source: Bend.ENUMWERTE.sql (enum values; referenced by checks.tsf_CheckBendEnums(...) constraints elsewhere), Bend.DB_VERSION.sql.
  • Verification: Inspection.

5. External Interfaces (area-specific)

  • ToPs 600 bend database — Bend schema configuration tables (MASCHINE_KONF, MASCH_CELL*, PARAMETER*, BOMB*, DURCHLEUCHTTISCH, EINHEITEN_*, SETTINGS, ENUMWERTE, DB_VERSION). See [[19 - FR - Tools, Machines, Materials & Technology]] and [[16.7 - Cell7000 — Bend Automation Data Model (Reference)]].
  • Robot/process defaults — the machine-configuration name keys ROBOTERPROZESSDATEN/PROZESSDATEN (see [[16.4 - Cell7000 — Robot, Process & Motion Data]]).
  • NC post-processor — units, crowning and the export map feed NC generation (see [[16.1 - Bending — NC Code Generation]]).

6. Assumptions & Constraints

  • A1. The cell configuration chain (MASCHINE_KONF → MASCH_CELL_CONFIG → MASCH_CELL → MASCH_CELL_PARAM) uses one logical configuration id across tables despite inconsistent column names (CELL_CONFIG_ID / CELL_KOMP_CONFIG_ID / CELL_MAP_CONFIG); no FK enforces the join. (inferred)
  • A2. Cross-table links are name/number strings resolved in application code (e.g. MASCH_CELL_PARAM_MAPPING.TABELLE/KOMPONENTE, EINHEITEN_VERZEICHNIS.EINHEITEN_TABELLE).
  • C1. The Cell 7000 is a specific instantiation of this generic model; the schema does not name it. (inferred — see [[16.2 - Cell7000 — Overview]])
  • C2. Both schema snapshots are structurally identical (collation/GRANT differences only); all tables originate from T600_V100.

7. Open Questions & Ambiguities

  1. Config-id identity. Confirm that CELL_CONFIG_ID, CELL_KOMP_CONFIG_ID and CELL_MAP_CONFIG denote the same id domain (no FK enforces it).
  2. BOMBWERTE.MASCH_ID (nvarchar(20)) vs MASCHINE_KONF_NAME (nvarchar(50)) — is MASCH_ID a truncated/coded machine key, and how does it join?
  3. PARAMETER_ZAHL USE_MIN/USE_MAX MS_Descriptions appear swapped in the source metadata; PARAMETER_UNIT_NUMMER description is a copy-paste referencing PARAMETER.PARAMETER_NUMMER though it is a unit id. Verify semantics before writing validation rules.
  4. Which MASCH_CELL component rows / CELL_MASCH_KOMP values correspond to a TruBend Cell 7000 (press, BendMaster, stations) — runtime data, not in the DDL.
  5. How the cell components link to the process defaults in ROBOTERPROZESSDATEN/PROZESSDATEN beyond the shared machine name.
