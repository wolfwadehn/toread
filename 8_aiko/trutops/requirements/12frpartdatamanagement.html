FR — Part & Data Management

Reverse-engineered requirement draft — derived from static analysis of legacy source, NOT an authoritative specification. Treat SHALL statements as reconstructed intent.

1. Purpose & Scope

This document specifies the functional requirements for the persistence and management layer of the TruTops CAD/CAM suite: how parts, drawings, sheets and order data are stored and retrieved, and the relational database infrastructure that underpins the whole product family.

The area spans two complementary storage worlds that the code deliberately keeps separate:

  1. Geometry/document files — the actual parts and drawings are stored as TRUMPF-native geometry files (the MI text format and its .geo/.taf relatives) on the file system or in a PDM (TRUMPF PDM / TRUMPF.NET) vault, abstracted behind an OmAdapter facade. The in-memory model, the file readers/writers and the binary/.NET geometry interface live in tc_dbase, tc_mi and tc_verw.
  2. The relational database — a set of SQL Server databases (deployable as locally attached MDF/"MDB" files) reached through ODBC, holding the technology/configuration data, the system rule-set (Regelwerk), order/part lists, stock/sheet inventory, multilingual text and — via the DATADICT data dictionary — the definition of the schema itself. The DB access layer is tc_dbif; the schema, versioning and migration machinery is in Databases/ and tc_tab.

Scope covered here: geometry file I/O and versioning, the part/drawing/sheet catalog and attribute query, PDM integration, the ODBC/SQL-Server/local-MDB layer, the data dictionary and auto-provisioning of tables, DB versioning & migration, metric/inch database duality, rule-set configuration caching and validation, order/part-list and stock persistence, record locking, referential integrity, DB access roles, XML I/O, and table/list infrastructure.

Editions served: all. The database is partitioned per technology/edition (schemas CAD, Laser≈T100, Punch≈T300, Tube≈T400, Bend≈T600, Nest, Common, Text, DATADICT), and each edition ships metric and inch (*_inch) database variants. Parts and drawings are common across all CAD-capable editions.

The technology content of those tables (tool/machine/material/laser/punch/bend parameters) is owned by [[19 - FR - Tools, Machines, Materials & Technology]] and the per-technology FR documents; this document owns the persistence, schema and access mechanics. File-format import/export to foreign formats (DXF, IGES, STEP, …) is owned by [[11 - FR - Import, Export & File Formats]].

2. Capability Overview

  • Save and load parts, drawings and nested sheets to/from TRUMPF-native geometry files, with a versioned file format.
  • Store an individual part (Einzelteil) extracted from a drawing as its own file.
  • Provide a C/.NET-callable geometry interface DLL (TruTopsGeoInterface) with binary object serialization for external components.
  • Access files transparently from the local file system or from a PDM/TRUMPF.NET vault through a single abstraction, plus a PDM browser.
  • Query file attributes (material, thickness, …) as a lightweight catalog lookup without fully loading the file — directly from the PDM server when in PDM mode.
  • Check whether a part matches the active material and machine before loading.
  • Reach the relational databases through ODBC against SQL Server / locally attached MDF files.
  • Maintain parallel metric and inch databases and provide unit-aware configuration access with automatic metric↔inch conversion.
  • Cache and validate the system rule-set (Regelwerk) configuration key/value store.
  • Describe the entire schema (tables, columns, data types, units, constraints, relations, indexes) in the DATADICT data dictionary and auto-provision physical tables from it.
  • Track schema version per schema/product, and migrate/upgrade older databases with defined update scripts.
  • Port data between metric and inch representations.
  • Audit-log structural, data-transfer, porting and check operations.
  • Persist order part-lists, stock/sheet inventory (with geometry-file references) and lock in-use entries.
  • Enforce foreign-key referential integrity and role-based access rights.
  • Read/write XML documents; generate tabular reports of technology tables.
  • Store multilingual UI/domain text keyed by language.

3. Domain Entities

Full definitions and cross-references live in [[04 - Domain Model & Glossary]].

Entity German Description

Drawing Zeichnung (Draw) The CAD document containing geometry elements, contours, parts and bends; the top-level saved unit.
Geometry element Element Line, arc, circle, spline, point, construction line, chamfer (Fase), fillet (Rundung), rectangle, arrow, text — the primitives serialized in a geometry file.
Contour Kontur An ordered chain of elements forming a closed/open boundary within a part.
Sheet / stock Tafel / Blech A raw or remnant sheet onto which parts are nested; persisted with dimensions, material and geometry reference.

Data dictionary Datenverzeichnis (DATADICT) Metadata describing tables, columns, relations and indexes that drive schema creation and migration.

MI file MI-Datei TRUMPF-native text geometry file format interpreted by the MI-Interpreter, carrying a format version.
Material / sheet material Werkstoff / Material Material master and sheet-stock records; the sheet record links to a geometry file directory/name.
Language text Sprache / Text Translatable UI and domain texts stored per language/culture.

4. Functional Requirements

FR-DATA-001 — Persist drawing to native geometry file

  • Requirement: When a user saves a drawing, the system shall write all geometry elements of the active drawing (lines, arcs, circles, splines, text, contours and bending information) to a TRUMPF-native geometry file.
  • Priority: Essential
  • Rationale: Storing the part/drawing is the fundamental persistence act of a CAD/CAM system.
  • Source: tc_dbase/store.h (db_schreibe_file); tc_dbase/db_def.h element type codes (LINIE, BOGEN, KREIS, SPLINE, DB_TEXT, FASE, RUNDUNG, VIERECK, …); tc_mi/mi_write.cpp (MI-Interpreter writer).
  • Verification: Test

FR-DATA-002 — Load drawing/part from native geometry file

  • Requirement: When a user opens a geometry file, the system shall reconstruct the in-memory drawing/part model from the file contents.
  • Priority: Essential
  • Rationale: A stored part is useless unless it can be reloaded and edited/processed.
  • Source: tc_dbase/lese_teil.h (lese_teil); tc_dbase/lesen.h; tc_mi/mi_lese.cpp ("CONTENTS: MI-Interpreter").
  • Verification: Test

FR-DATA-003 — Store an individual part (Einzelteil)

  • Requirement: The system shall be able to store an individual part extracted from a drawing to its own geometry file, optionally translating the part geometry to the coordinate origin.
  • Priority: Essential
  • Rationale: Nesting and re-use require single parts to be saved independently of the drawing they were authored in.
  • Source: tc_dbase/store.h (db_schreibe_einzelteil, parameter t_verschieben = translate-to-origin flag).
  • Verification: Test

FR-DATA-004 — Persist and load nesting sheets (Tafel)

  • Requirement: Where nesting is available, the system shall store and load nesting-sheet layouts (Tafel), including nested part instances and their placement/transformation matrices.
  • Priority: Conditional
  • Rationale: Nesting layouts must round-trip so that a job can be re-opened, edited and re-posted. Feature depends on the nesting edition (see [[17 - FR - Nesting & Palletizing]]).
  • Source: tc_dbase/lese_taf.h (db_lese_tafel, includes TcTransformationMatrix.h, TcDBNestTyp.h); tc_dbase/store_taf.h.
  • Verification: Test

FR-DATA-005 — Versioned geometry file format

  • Requirement: The system shall stamp each saved geometry file with a format-version identifier and shall correctly interpret files written under earlier format versions on read.
  • Priority: Essential
  • Rationale: A decades-old format must stay backward-compatible so legacy parts remain openable.
  • Source: tc_mi/tc_mi.h (MI_Version_Nr, MI_RELEASE_1 2.21, MI_RELEASE_2 2.4); tc_dbase/db_def.h (DB_FILE_VERSION "1.03"); tc_dbase/store.h (version parameter).
  • Verification: Inspection

FR-DATA-006 — Binary geometry interface (TruTopsGeoInterface DLL)

  • Requirement: Where an external or .NET component requires geometry exchange, the system shall expose a C-callable import/export interface (TruTopsGeoInterface.dll) to transfer geometry, strokes, marks and bend meta-information via a binary object representation.
  • Priority: Conditional
  • Rationale: Downstream .NET applications and services consume geometry through this stable DLL boundary rather than the internal C++ model.
  • Source: tc_dbase/GeoInterface/GeoInterfaceFunctions.h (extern "C" import/export functions, GEO_DLL_DECLSPEC); TcObjectBin.h/.cpp; GeoInterfaceDotNet/.
  • Verification: Test

FR-DATA-007 — Transparent PDM / file-system access

  • Requirement: The system shall access part, drawing and technology files either from the local file system or from a PDM (TRUMPF PDM / TRUMPF.NET) vault through a single abstraction, transparently to calling code.
  • Priority: Conditional
  • Rationale: The same product runs standalone (file system) or integrated into PDM; callers must not branch on the storage backend.
  • Source: tc_util/pdmUtilities/ (TcInputFileStream, TcOutputFileStream wrapping TyOmAdapterFileStreamSmp; pdmFunctions.h pdmLocator, normalizePathname, getFileType); includes TiPdmFacet.h, OmAdapterIncludes.h; tc_viewer/viewerdll/{filesystemImplementation,pdmImplementation}/TcPdmBootStrap.
  • Verification: Demonstration

FR-DATA-008 — PDM browser

  • Requirement: Where PDM is active, the system shall provide a browser to navigate and select parts/drawings held in the PDM vault.
  • Priority: Conditional
  • Rationale: Users need to locate and open PDM-managed documents from within the application.
  • Source: tc_cad/allg_asm/pdmBrowser.cpp ("Automat zum Einstellen und Anzeigen des PDM Browsers").
  • Verification: Demonstration

FR-DATA-009 — Lightweight file-attribute (catalog) query

  • Requirement: The system shall read attribute/value pairs (e.g. material, raw material, sheet thickness) from any supported file type without fully loading the file, querying the PDM server directly when in PDM mode.
  • Priority: Essential
  • Rationale: Catalog listing, filtering and compatibility checks must be fast and must not require a full geometry load.
  • Source: tc_verw/geoinfo.h (TcGeoInfos, TeGeoInfoType covering Geo, Gmt100/300, Tmt100/300, Taf, Mtl, Vlg, Wzg, Rot/Rmt/Rpf, Dat, Lst, Ein, Dxf, Xml, Trg; "Im PDM-Betrieb werden die Informationen direkt beim PDM-Server abgefragt").
  • Verification: Test

FR-DATA-010 — Check part compatibility with active material and machine

  • Requirement: When a part file is opened, the system shall determine whether the part's material and machine match the active configuration and shall report whether a change is not needed, possible, or impossible because the material/machine is absent from the database.
  • Priority: Essential
  • Rationale: Prevents processing a part against an incompatible or unknown material/machine.
  • Source: tc_verw/TcCheckPartProperties.h ("Klasse zum Pruefen, ob Datei zu aktivem Material und Maschine passt"; TeChangeModus = e_change_no/e_change_yes/e_change_cancel).
  • Verification: Test

FR-DATA-011 — Relational database access via ODBC

  • Requirement: The system shall access its relational databases (SQL Server, or locally attached MDF/"MDB" files) through an ODBC data source.
  • Priority: Essential
  • Rationale: All technology, configuration and production tables are reached over ODBC; the DSN is provisioned at install/deploy time.
  • Source: Databases/createSqlServerOdbcEntry.bat (imports an ODBC registry template per database); Databases/AttachSqlServerLocalMdb.bat, createSqlServerLocalMdb.bat.
  • Verification: Inspection

FR-DATA-012 — Parallel metric and inch databases

  • Requirement: The system shall maintain parallel metric and inch (imperial) database variants and shall select the applicable unit system per application/edition.
  • Priority: Essential
  • Rationale: North-American and metric markets run the same product against unit-appropriate data.
  • Source: *_inch table schemas (CAD_inch, Common_inch, Laser_inch, Punch_inch, Tube_inch, Nest_inch, Text_inch); DATADICT.DATADICT_DATABASES.DDDB_UNITSYSTEM; InchPort.* schema; ini_files/*Inch.*.
  • Verification: Inspection

FR-DATA-013 — Unit-aware configuration value access

  • Requirement: The system shall provide typed (long, double, string) and unit-aware read/write access to system rule-set configuration values, converting between metric and inch target units according to the active unit system.
  • Priority: Essential
  • Rationale: Configuration must be consumed with correct units regardless of the machine's unit system, using metric-defined defaults with an inch fallback.
  • Source: tc_dbif/dbif.hpp (DBInterface::GetValue long/double/char overloads with t_DefMetricValue/t_InchTargetUnit; DBInterface::SetValue).
  • Verification: Test

FR-DATA-014 — Cache the system rule set (Regelwerk)

  • Requirement: The system shall cache the system rule-set variables read from the REGEL_ALLG table so that repeated configuration lookups are served from memory.
  • Priority: Essential
  • Rationale: Rule-set values are read pervasively; per-lookup DB round-trips would be prohibitive.
  • Source: tc_dbif/dbif.hpp ("Klasse cacht die Systemregelwerksvariablen aus Tabelle regel_allg"); CAD.REGEL_ALLG (REGEL_NAME, REGEL_WERT, REGEL_WERT_MIN/MAX, REGEL_EINHEIT, …); tc_dbif/srobj.hpp (SRObj).
  • Verification: Test

FR-DATA-015 — Validate configuration values against constraints

  • Requirement: When a configuration value is set, the system shall validate it against the value's defined minimum, maximum, regular expression and unit, and shall reject values that violate these constraints.
  • Priority: Essential
  • Rationale: Guards the rule set against out-of-range or malformed entries that would corrupt downstream processing.
  • Source: tc_dbif/srobj.hpp (SRObj::TeValueError = too-small/too-large/illegal-chars/illegal-unit/illegal-RE/invalid-chars; tCheckLimits); REGEL_ALLG columns REGEL_WERT_MIN/MAX, REGEL_PRUEF_INFO, REGEL_FORMAT, REGEL_EINHEIT.
  • Verification: Test

FR-DATA-016 — Data dictionary defines the schema

  • Requirement: The system shall define its database tables, columns, data types, units, value constraints, relationships and indexes in a central data dictionary.
  • Priority: Essential
  • Rationale: A single metadata source drives schema creation, unit handling, validation and migration consistently across all schemas.
  • Source: Databases/SQLServerDatabase/Tables/DATADICT.DATADICT.sql; DATADICT.DATADICT_SPALTEN (per-column DD_SPALTEN_METRIC_UNIT/_INCH_UNIT, _MIN_VALUE/_MAX_VALUE, _REG_EXPR, _IS_UNIQUE, _CHECK); DATADICT.DATADICT_RELATIONS; DATADICT.DATADICT_INDEX, DATADICT.DATADICT_INDEX_COLUMNS.
  • Verification: Inspection

FR-DATA-017 — Auto-provision tables from the data dictionary

  • Requirement: When a table definition is inserted into the data dictionary, the system shall automatically create the corresponding physical table in each technology schema flagged for that table.
  • Priority: Essential
  • Rationale: Keeps the physical schema in lock-step with the dictionary and its per-technology partitioning without hand-written DDL.
  • Source: DATADICT.DATADICT trigger ttr_createTableFromDATADICT (AFTER INSERT; branches on MASTERTABT100→Laser, MASTERTABT300→Punch, MASTERTABT400→Tube, MASTERTABT600→Bend, MASTERTABTCAD, MASTERTABTNEST, MASTERTABTCOMMON, …).
  • Verification: Test

FR-DATA-018 — Track database schema version

  • Requirement: The system shall record the schema version for each database schema and product edition, and shall expose the minimum table version and maximum compatible product version.
  • Priority: Essential
  • Rationale: The application must detect version mismatch between its binaries and the attached database.
  • Source: Per-schema DB_VERSION tables (CAD.DB_VERSION, Common.DB_VERSION, Punch.DB_VERSION, …, PK VERSION_BEMERKUNG); DATADICT.DATADICT_DATABASES.DDDB_DBVERSION; DATADICT.DATADICT_ProductVersion (DDPV_MinTableVersion, DDPV_MaxProductVersion).
  • Verification: Inspection

FR-DATA-019 — Migrate/upgrade an outdated database

  • Requirement: If the application detects a database older than the version it requires, then the system shall apply the defined schema-update and data-migration steps to bring the database up to the required version.
  • Priority: Essential
  • Rationale: Installing a new product build over an existing database must upgrade the data in place without loss.
  • Source: Common._DB_MODIFY (DBM_VERSION, DBM_TABELLE, DBM_SPALTEN, DBM_UPDATE); Common.DB_UPDATE_SPECIAL (DB_SQL); tc_tab/tab_dbup (tabellen_db_update); DATADICT.DATADICT_SPALTEN.DD_SPALTEN_PATCH_UPGRADEVALUEEXPR.
  • Verification: Test

FR-DATA-020 — Port data between metric and inch

  • Requirement: Where the inch product variant is built, the system shall port/convert database content between metric and inch representations using the per-column conversion metadata (unit, factor, direction).
  • Priority: Conditional
  • Rationale: The inch databases are generated from the metric masters; conversion must be metadata-driven and repeatable.
  • Source: Databases/DB_Port_SqlSrv.ps1, DB_Port_SqlSrv_InchRefresh_ExecuteOnlyAtNight_legacy.ps1; InchPort.* (KONFIG, NiceMetricValues, RoundIs3); DATADICT.DATADICT_SPALTEN.DD_SPALTEN_FAKTOR/_INCH_ADDITIV_DIRECTION.
  • Verification: Test

FR-DATA-021 — Audit-log structural and data operations

  • Requirement: The system shall log database structural changes, data-transfer, porting and integrity-check operations with a timestamp, criticality, schema name and message.
  • Priority: Essential
  • Rationale: Schema/data changes made by triggers and migration scripts must be traceable for support and diagnosis.
  • Source: Logging.StructureLog, Logging.PortierungLog, Logging.DataTransferLog, Logging.DatabaseCheckLog, Logging.InchDataUpdateLog, Logging.LdmImportLog (columns DateAndTime, Criticality, SchemaName, Message, TaskName); stored procedure tsp_logging.
  • Verification: Inspection

FR-DATA-022 — Persist an order's part list

  • Requirement: The system shall persist the parts belonging to an order, including each part's file path and name, target/minimum/maximum quantities, priority, material and processing status.
  • Priority: Conditional
  • Rationale: Production planning and nesting operate on stored order/part lists rather than loose files. Present in nesting/order-capable editions (see [[20 - FR - Production Planning & Projects]], [[17 - FR - Nesting & Palletizing]]).
  • Source: Nest.TEILE_ERFASSEN (TEIL_AUFTRAG = order, TEIL_PFAD_NAME, TEIL_NAME, TEIL_IST/_MIN/_MAX, TEIL_PRIORITAET, TEIL_MTL, TEIL_STATUS, TEIL_DATUM).
  • Verification: Test

FR-DATA-023 — Persist sheet/stock inventory with geometry reference

  • Requirement: The system shall persist sheet and remnant-stock entries, each carrying its dimensions and material and referencing the associated geometry file by directory and name.
  • Priority: Essential
  • Rationale: Stock records must link inventory to the geometry that represents the physical sheet/remnant.
  • Source: Common.MAT_SHEET (MAT_LAGERGUTID, MAT_ABMESS_X/Y, MAT_GEO_DIRECTORY, MAT_GEO_NAME, MAT_IS_REMAINDER_SHEET); Nest.TAFEL_VARIANT (VAR_ABMESS_X/Y/Z, VAR_LAGERGUTID, VAR_WS_INDEX).
  • Verification: Test

FR-DATA-024 — Lock in-use stock/nesting records

  • Requirement: While a stock or nesting-sheet entry is in use by an order, the system shall mark the entry locked to prevent conflicting modification or reuse.
  • Priority: Essential
  • Rationale: Prevents two jobs from consuming or editing the same physical sheet/remnant concurrently.
  • Source: Nest.TAFEL_VARIANT.VAR_EINTRAG_GESPERRT, VAR_BENUTZT_VON_AUFTRAG; Common.MAT_SHEET.MAT_LOCKSTATE.
  • Verification: Test

FR-DATA-025 — Enforce referential integrity

  • Requirement: The system shall enforce the foreign-key relationships defined in the data dictionary, applying the specified update and delete referential actions.
  • Priority: Essential
  • Rationale: Cross-table consistency (e.g. between machine, tool and parameter tables) must be guaranteed by the database.
  • Source: DATADICT.DATADICT_RELATIONS (DD_REL_FK_*/DD_REL_REF_*, DD_REL_FK_DELETE_REFERENTIAL_ACTION, DD_REL_FK_UPDATE_REFERENTIAL_ACTION).
  • Verification: Inspection

FR-DATA-026 — Role-based database access rights

  • Requirement: The system shall restrict access to database objects according to defined roles and rights groups.
  • Priority: Conditional
  • Rationale: Multi-user installations restrict who may read/modify technology and configuration data.
  • Source: DATADICT.DATADICT_ROLES, DATADICT.DATADICT_ROLE_MEMBERS, DATADICT.DATADICT_SECURABLES; Databases/SQLServerDatabase/Security/{Roles,Users,Schemas}; DATADICT.DATADICT.RECHTEGRUPPE.
  • Verification: Inspection

FR-DATA-027 — XML document persistence

  • Requirement: The system shall read and write structured data as XML documents through a common persistence interface.
  • Priority: Conditional
  • Rationale: Certain settings, exchange payloads and document data are stored as XML rather than in the native geometry format or the RDBMS.
  • Source: tc_xml/xml_io/ (TcXmlGenerator, TcXmlParser, TiDateiPersistenz strategy interface, TcDateiPersistenzStream; Xerces DOM).
  • Verification: Test

FR-DATA-028 — Store multilingual text keyed by language

  • Requirement: The system shall store UI and domain texts together with their translations in the database, keyed by language/culture.
  • Priority: Conditional
  • Rationale: The suite is localized; text is data-driven per installed language. (Rendering/selection of language is owned by [[22 - FR - UI Framework, Dialogs & Interaction (GRIT)]].)
  • Source: Text.COMMON_TEXT, Text.SPRACHEN (SP_SPRACHNR, SP_DBSPRACHE, SP_DOTNET_CULTURE, SP_CODEPAGE), Text.CONST_TRANSLAT, Text.COL_TRANSLAT.
  • Verification: Inspection

FR-DATA-029 — Generate tabular listings of technology tables

  • Requirement: The system shall generate printable tabular listings of stored technology tables and rule sets.
  • Priority: Optional
  • Rationale: Operators and service staff need human-readable dumps of parameter and rule tables.
  • Source: tc_tab/tab_prnt/ (db_tabel.cpp verarbeite_db_las_tabelle, verarbeite_db_wasser_tabelle; tabellen.cpp); tc_tab/tab_rewe/ (tabellen_druck_regel).
  • Verification: Demonstration

5. External Interfaces (area-specific)

Consolidated interface requirements are in [[30 - External Interface Requirements]].

  • Native geometry files — MI text format (.geo and relatives) with a format version; sheet (.taf) files. Producer/consumer: tc_mi, tc_dbase. See [[11 - FR - Import, Export & File Formats]].
  • TruTopsGeoInterface.dll — extern "C" / .NET import-export API and binary object bin for external geometry exchange (tc_dbase/GeoInterface).
  • ODBC → SQL Server — DSN-based access; databases deployable as locally attached MDF files (Databases/*.bat).
  • PDM / TRUMPF.NET vault — file access via the OmAdapter/TiPdmFacet facade; PDM browser (tc_util/pdmUtilities, tc_cad/allg_asm/pdmBrowser.cpp).
  • XML — Xerces DOM read/write (tc_xml).
  • Foreign file types read for attributes — Dxf, Igs, Pdf, Html, plus TRUMPF Gmt/Tmt/Rot/Rmt/Rpf/Wzg/Mtl (tc_verw/geoinfo.h).

6. Assumptions & Constraints

Cross-cutting items are tracked in [[50 - Constraints & Assumptions]].

  • Split persistence model. Parts/drawings live in geometry files (file system or PDM); the RDBMS holds technology/configuration, rule-set, order/stock and text data, and only references geometry files (e.g. MAT_SHEET.MAT_GEO_DIRECTORY). There is no single "parts" table — the part catalog is the file store plus lightweight TcGeoInfos attribute reads.
  • SQL Server is the current RDBMS. The "local Access MDB" heritage now manifests as locally attached SQL Server MDF files reached over ODBC; DDL and triggers are T-SQL specific.
  • Metadata-driven schema. Physical tables, columns, constraints and even table creation derive from the DATADICT dictionary; hand-editing physical tables outside the dictionary is out of contract.
  • Metric/inch duality is pervasive. Almost every requirement has a unit dimension; inch databases are generated from metric masters (see FR-DATA-012, FR-DATA-020).
  • Legacy code constraints. German-language identifiers/comments; C-style and Tw*/Om* framework types; the MI format must remain backward-compatible indefinitely.
  • Editions. Per-technology schemas mean many tables are only populated for the relevant edition; the DATADICT MASTERTAB* flags encode which schemas a table belongs to.

7. Open Questions & Ambiguities

  • Ownership of technology-table content. The vast majority of SQL tables (Bend.*, Laser.*, Punch.*, Tube.*, WZG_*, MAS_*, REGEL*, MAT_*) hold tool/machine/material/technology data whose semantics belong to [[19 - FR - Tools, Machines, Materials & Technology]] and the per-technology FR docs. This document only claims their persistence/schema aspects.
  • Exact MI/GEO file grammar. The full record grammar of the MI format was not reverse-engineered line by line (mi_lese.cpp/mi_write.cpp are ~60k/112k lines of interpreter); the format-version boundaries (2.21, 2.4) and what each release changed are only partially evidenced.
  • PDM server contract. The OmAdapter/TiPdmFacet API surface (check-in/check-out, versioning, locking semantics against the PDM vault) is referenced but its detailed operations live in framework code (OmAdapter.dll) not present in this snapshot; PDM record-locking vs. DB LOCKSTATE may be distinct mechanisms.
  • Concurrency model. Whether multi-user conflict handling relies solely on the SQL Server engine, on the *_GESPERRT/LOCKSTATE flags, or on PDM check-out could not be fully determined.
  • CAD.TEMP_RECORD / *.TEMP_RECORD. Generic scratch tables (5×long/float/char columns) appear per schema; their exact role as an app↔DB exchange buffer is inferred, not confirmed. (inferred)
  • Calc.LttOrgValuesOfEncrypted / Updates.LASERTECHNO_Blacklist. Encryption/blacklisting of certain technology values is hinted at but the mechanism and scope are unclear.
  • Bend gripper configuration store (BendGripperConf.*). A separate object store with LOCK/OWNER/CHANGES tables suggesting its own versioning/locking — likely owned by [[16 - FR - Bending (ToPs 600)]] but its persistence pattern overlaps this area.
