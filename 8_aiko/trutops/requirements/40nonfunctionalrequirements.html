40NonFunctionalRequirements

product: trutopscad org: trumpf title: "Non-Functional Requirements" doc: "40 - Non-Functional Requirements" id-prefix: "NFR" srs-standard: "ISO/IEC/IEEE 29148:2018" status: reverse-engineered-draft source: "TruTopsCAD legacy source snapshot (files dated May 2024)" related: ["[[00 - Index & Reading Guide]]", "[[30 - External Interface Requirements]]", "[[50 - Constraints & Assumptions]]", "[[22 - FR - UI Framework, Dialogs & Interaction (GRIT)]]", "[[12 - FR - Part & Data Management]]", "[[19 - FR - Tools, Machines, Materials & Technology]]"] tags: [requirements, trutops, nfr]

Non-Functional Requirements

This document specifies the quality attributes and constraints of the TruTops CAD/CAM suite (ToPsCad, ToPs 100, ToPs 300, ToPs 400, ToPsNest, ToPs Tube and their Lite/2000 variants). It is reverse-engineered from static analysis of the legacy source snapshot and is complementary to the functional requirements in documents [[10 - FR - CAD Geometry & Drawing Editing]] through [[23 - FR - Automation, Scripting & Integration]], the interface requirements in [[30 - External Interface Requirements]] and the environmental limits recorded in [[50 - Constraints & Assumptions]].

Because the system is a mature product reverse-engineered from code, most quality targets are implicit — the code embodies a mechanism (a bounded optimizer, a crash-reporting hook, a metric/inch database pair) without stating a numeric acceptance threshold. Where a metric is evidenced in source it is quoted; otherwise the attribute is stated and its target marked (to be quantified) so a maintainer can set a measurable bound against the current release. Domain terms are defined in [[04 - Domain Model & Glossary]].

Priority levels follow ISO/IEC/IEEE 29148: Essential (the product is not acceptable without it), Conditional (adds value; degradation is tolerable), Optional (desirable).

Performance & Capacity

NFR-001 — Interactive editing and view responsiveness

Requirement. Interactive CAD/CAM operations (pick, drag, zoom/pan, redraw of the drawing or nested sheet) shall present visible feedback without perceptible lag under normal working part sizes. The rendering stack shall use off-screen bitmap double-buffering and a redraw cache to avoid flicker and full recomputation on each repaint, and shall bracket every repaint by an explicit start/end redraw guarded by a redraw-in-progress flag so overlapping redraws cannot corrupt the display. Category. Performance & Capacity Priority. Essential Rationale. The suite is an interactive editor; sluggish or flickering redraw directly degrades operator productivity on the shop floor and touch panels. Source. tc_visualize off-screen DC / redraw-cache design and TC_Viewport redraw lifecycle (digest [[21 - FR - Visualization, Viewing & Plotting]], FR-VIS-004); interactive echo/XOR rubber-band mode; GRIT Grafb graphics canvas. Verification. Timed interaction test on a reference large part and a full nested sheet, measuring frame/redraw latency; visual inspection for flicker with double-buffering enabled vs disabled. Target frame latency (to be quantified).

NFR-002 — Large-part, large-nest and large-program capacity

Requirement. The system shall load, edit, nest and generate NC for production-scale data: sheet drawings containing many parts, contours and geometry elements; nested sheets with many placed parts; and punch/laser programs with large operation counts. No fixed compile-time array shall silently truncate a valid production data set; capacity limits that do exist (e.g. path/filename buffers) shall be documented. Category. Performance & Capacity Priority. Essential Rationale. Real jobs routinely nest hundreds of parts per sheet and generate thousands of hits/cuts; the punch technology module alone is ~840k LOC and the laser module ~590k LOC, reflecting the scale of programs handled. Source. tc_stz (~840k LOC) and tc_las (~590k LOC) scale (digest [[13 - FR - Punching (ToPs 300)]], [[14 - FR - Laser Cutting (ToPs 100)]]); nesting to order quantities across multi-sheet/multi-format nests ([[17 - FR - Nesting & Palletizing]]); fixed buffer constants observed in tc_dbase (MAX_DIR_SIZE 500, MAX_FNAME_SIZE 100, MAX_EXT_SIZE 10). Verification. Load/nest/NC-generate stress test with a large representative order; confirm element/part/hit counts survive a save-load-round-trip; audit fixed-size buffers against documented limits. Concrete capacity numbers (to be quantified).

NFR-003 — Bounded, configurable nesting and optimization compute time

Requirement. Long-running automatic operations — true-shape nesting and processing-order optimization — shall run within an operator-configurable time budget and shall return the best result found so far when the budget is reached. The nesting engine shall accept an explicit maximum run time in seconds, and the utilization optimizer shall run a bounded set of trials. Category. Performance & Capacity Priority. Essential Rationale. Nesting and TSP-style sequencing are NP-hard; without a time bound the operator cannot predict programming turnaround. A configurable ceiling trades solution quality for throughput. Source. GSSL NestLib NSetMaxTimeLimit(maxTimeInSecs) / NInqMaxTimeLimit wrapped in tc_nest/nestlib_interface (verified in source); multi-trial utilization optimizer with trial sets and time limit (digest [[17 - FR - Nesting & Palletizing]]); configurable optimization quality/level FR-NC-010 ([[18 - FR - NC Generation & Motion Optimization]]). Verification. Run nesting/optimization with several time limits and confirm the run terminates within the limit and yields a valid (if suboptimal) layout.

NFR-004 — Geometry- and motion-compute correctness and efficiency

Requirement. Compute-intensive kernels — boolean contour arithmetic and offset generation, curve approximation/Fourier similarity, constrained-TSP sequencing, per-tool travel-time optimization, jerk-limited cycle-time estimation and collision-free path finding — shall produce numerically stable results within tolerances and complete in a time proportional to problem size acceptable for interactive/batch programming. Category. Performance & Capacity Priority. Essential Rationale. These algorithms drive both correctness (valid cut paths) and estimated machine time; instability or poor scaling makes generated programs unusable. Source. GeoAlgorithmsKernel / BooleanLibraryAdapter, tc_aprox, tc_fou, tc_contourArithmeticTool ([[10 - FR - CAD Geometry & Drawing Editing]]); tc_constrainedTspSolver (nearest-neighbour + Ant-Colony + post-optimization), tc_wegzeit (jerk-limited ramps), tc_wopt, tc_pathf ([[18 - FR - NC Generation & Motion Optimization]]). Verification. Unit/regression tests (see tc_contourArithmeticToolTest, unitTests) comparing algorithm output against reference geometries and timing curves over increasing element counts.

NFR-005 — Batch and headless throughput

Requirement. Batch and server-side surfaces — the standalone converter, headless reproduction nesting and headless laser shop-floor programming — shall process jobs without an interactive session and shall support unattended, schedulable execution (including overnight bulk operations). Category. Performance & Capacity Priority. Conditional Rationale. Integration with PDM/MES and regression pipelines depends on non-interactive throughput; database porting is explicitly scheduled for off-hours to avoid contention. Source. tc_conv.exe / pdmConvert.exe with @response files ([[11 - FR - Import, Export & File Formats]]); tc_reproduction (NestCore re-nesting) and TruTopsLaser SFP DLL ([[23 - FR - Automation, Scripting & Integration]]); DB_Port_SqlSrv_InchRefresh_ExecuteOnlyAtNight_legacy.ps1. Verification. Run each headless entry point on a batch of representative inputs and confirm completion, output validity and absence of GUI dependency.

Reliability & Data Integrity

NFR-006 — Transaction-based undo/redo

Requirement. User-initiated editing and technology operations shall be reversible. Groups of related actions shall be committed or rolled back atomically as a single transaction, so undo/redo never leaves the model in a partially-modified state; the framework shall notify the UI when undo/redo is (un)available. Category. Reliability & Data Integrity Priority. Essential Rationale. Atomic undo is the primary safety net against operator error and is a baseline expectation of a CAD editor. Source. tc_undo (TcUndoManager, TcUndoCaretaker, TcTransactionStart, TiUndoPossibleNotify, atomic/non-atomic transactions); tc_undo/undo_asm command-ID coupling to tc_stz/tc_las ASM (verified in source); FR-UI transaction-based undo/redo ([[22 - FR - UI Framework, Dialogs & Interaction (GRIT)]]). Verification. Perform composite operations (e.g. a multi-element transform) and confirm a single undo restores the pre-operation state exactly; confirm redo availability signalling.

NFR-007 — Crash reporting and diagnostic capture

Requirement. On an unhandled fault the application shall produce a diagnostic report via Windows Error Reporting (WER) containing at minimum a minidump of the crash call stack, and shall associate the currently open document file(s) with the report so TRUMPF can reproduce the fault from concrete data rather than a stack alone. Progress logging shall be captured such that it is available in the crash report. Category. Reliability & Data Integrity Priority. Essential Rationale. A large legacy C++ codebase deployed at many customer sites needs field-fault telemetry; WER + registered document files materially shortens defect diagnosis. Source. tc_log/TnWindowsErrorReporting (TcActiveDocumentFileRegistry, minidump + winqual portal description, verified in source); tc_log logging facility (LOG_MELDEBOX/LOG_DATEI). Verification. Trigger a controlled fault in a test build and confirm a WER report with minidump and the registered active document is generated.

NFR-008 — Database transactional integrity and record locking

Requirement. Concurrent access to shared master data, orders and stock inventory shall preserve integrity. Records that must not be edited while in use (stock/nesting/gripper-config records) shall be lockable, and lock/governance state shall be honoured across sessions. Relational writes shall use the SQL Server / ODBC engine's transactional guarantees. Category. Reliability & Data Integrity Priority. Essential Rationale. Multiple programmers and machines share one technology database; unmanaged concurrent edits would corrupt orders, stock counts and rule sets. Source. *_GESPERRT / MAT_LOCKSTATE / VAR_EINTRAG_GESPERRT locking flags and ODBC/SQL Server access ([[12 - FR - Part & Data Management]]); BendGripperConf LOCK/OWNER/CHANGES store; per-record *_LOCKSTATE/*_VISIBLE governance flags ([[19 - FR - Tools, Machines, Materials & Technology]]). Verification. Concurrency test: two clients attempt to edit a locked stock/rule record; confirm the second is refused or serialized without data loss. Exact concurrency model (engine vs flags vs PDM check-out) (to be quantified).

NFR-009 — Schema-enforced referential and value integrity

Requirement. The relational schema shall enforce referential integrity between related tables and value integrity (type, unit, min/max, regex, uniqueness) on individual columns, driven by the data dictionary rather than ad-hoc application checks, so invalid technology/master data cannot be persisted. Category. Reliability & Data Integrity Priority. Essential Rationale. Technology data feeds NC generation directly; out-of-range or dangling values would produce unsafe machine programs. Source. DATADICT / DATADICT_SPALTEN (type, units, min/max, regex, uniqueness) and relation definitions ([[12 - FR - Part & Data Management]]); TiConsistencyChecker and MAS_REGEL rule bounds ([[19 - FR - Tools, Machines, Materials & Technology]]). Verification. Attempt inserts violating type/range/uniqueness/foreign-key rules and confirm rejection; audit that schema creation derives from DATADICT.

NFR-010 — Robust import with error reporting and graceful degradation

Requirement. Foreign-format import shall not abort silently on malformed or partially-unsupported input. Import errors shall be collected by scope/line and offered as an optional load report (LOG/HTML), and the importer shall recover as much valid geometry as possible while flagging what was dropped. Category. Reliability & Data Integrity Priority. Essential Rationale. Customer CAD files are frequently non-conforming; a hard failure with no diagnostics blocks the whole job. Source. TcDxfLoadReport (errors by scope/line, optional .LOG/HTML) and per-format import controls ([[11 - FR - Import, Export & File Formats]], FR-IMPEX-007); TnIssueManager severity-typed issue tracking ([[13 - FR - Punching (ToPs 300)]] task/issue manager, verified in tc_issue). Verification. Import a corpus of malformed DXF/IGES/MI files; confirm a report is produced and valid geometry is retained.

NFR-011 — File- and document-format version tolerance

Requirement. Readers shall accept documented prior versions of TRUMPF-native and project formats and shall reject or migrate incompatible versions with a clear diagnostic rather than misinterpreting data. Geometry files carry an MI/GEO format version; programming projects carry a PPJ document version. Category. Reliability & Data Integrity Priority. Essential Rationale. Long product lifetime means old files must remain readable; misreading a version would corrupt geometry or machining. Source. MI versions 2.21/2.4 with MI_Version_Nr ([[12 - FR - Part & Data Management]]); PPJ XML versions 1.0–5.0 with explicit incompatible-version rejection FR-PLAN-005 ([[20 - FR - Production Planning & Projects]]); GEO/GEO_102 ([[11 - FR - Import, Export & File Formats]]). Verification. Round-trip and open files of each supported version; confirm an out-of-range version is rejected with a message, not silently loaded.

NFR-012 — Consistency and issue surfacing

Requirement. The system shall detect and surface program/data consistency problems (technology inconsistencies, validation failures) as classified issues with severity (low/medium/high/critical) and lifecycle state (valid/outdated/resolved), so the operator can act before NC generation. Category. Reliability & Data Integrity Priority. Conditional Rationale. Surfacing issues before hand-off to the machine prevents scrapped sheets and machine faults. Source. tc_issue (TcIssueManager, TcIssue TeSeverity/TeState, verified in source); program consistency checking ([[13 - FR - Punching (ToPs 300)]]); collision detection/reporting ([[14 - FR - Laser Cutting (ToPs 100)]]). Verification. Introduce a known inconsistency and confirm it is raised with correct severity/state and clears when resolved.

Usability & Interaction

NFR-013 — Consistent interaction model across all editions

Requirement. All editions shall present one coherent interaction model — masks/dialogs, finder lists, popup menus, buttons, keyboard/mouse handling, and interactive graphical selection (pick/box/all, single/add/invert, type-filtered) — through the shared GRIT framework, so an operator moving between punch, laser, bend, tube, nest and CAD editions encounters uniform behaviour. Category. Usability & Interaction Priority. Essential Rationale. A single UI framework across editions reduces training cost and operator error. Source. GRIT framework shared by all editions; mask object model, six button types, selection modes ([[22 - FR - UI Framework, Dialogs & Interaction (GRIT)]]); tc_selection, tc_catch picking. Verification. Cross-edition UI review confirming identical selection/menu/dialog conventions.

NFR-014 — Input plausibility validation at point of entry

Requirement. Data-entry fields shall validate input against declared plausibility rules (interval, set, alphanumeric, constant, free-form) and against unit/format/decimal constraints before the value is accepted, giving immediate feedback on invalid entry. Category. Usability & Interaction Priority. Essential Rationale. Catching bad technology/geometry values at entry prevents downstream failures and is safer than post-hoc checks. Source. GRIT Plausi validation (interval/set/alphanum/constant/freeform) and input-field format/decimal control ([[22 - FR - UI Framework, Dialogs & Interaction (GRIT)]]). Verification. Enter out-of-interval and wrong-type values into representative fields; confirm rejection with feedback.

NFR-015 — Interactive graphical feedback and on-screen help

Requirement. Interactive geometry operations shall provide live visual feedback (reversible XOR/echo rubber-band drawing), and the UI shall offer per-language tooltips and prompt/help text for controls, plus toggleable display classes so the operator can focus the view (geometry, machining, tool paths, micro-joints, cycles, collisions, scrap, etc.). Category. Usability & Interaction Priority. Conditional Rationale. Rubber-band feedback and selective display are essential for accurate manual editing and for reviewing dense nests. Source. Echo/XOR interactive drawing mode, tooltips, per-language help/prompt text ([[22 - FR - UI Framework, Dialogs & Interaction (GRIT)]]); toggleable display classes ([[21 - FR - Visualization, Viewing & Plotting]], FR-VIS). Verification. Exercise rubber-band operations and display-class toggles; confirm feedback and per-language tooltip text.

NFR-016 — Guided programming for non-expert operators

Requirement. Where automatic technology assignment is available, the system shall offer guided/assistant workflows (technology assistant, bend tool assistant) and rule-based automation so a less-experienced operator can produce a valid program with minimal manual technology decisions. Category. Usability & Interaction Priority. Conditional Rationale. Shop-floor programming (including Lite editions) targets operators, not CAM specialists; guidance widens the usable operator base. Source. Guided automatic programming (technology assistant) FR-PUNCH-002 ([[13 - FR - Punching (ToPs 300)]]); AutoCut/Regelwerk automatic assignment ([[14 - FR - Laser Cutting (ToPs 100)]]); Biegewerkzeugassistent ([[16 - FR - Bending (ToPs 600)]]). Verification. Task-based usability walkthrough producing a program via the assistant path.

Localization & Units

NFR-017 — Multi-language user interface

Requirement. All operator-facing text shall be presented in a user-selected language, selectable at startup and switchable, with support for a large language set (framework capacity of 30 language slots, including CJK) and per-language, per-resolution fonts. No functional behaviour shall depend on the active language. Category. Localization & Units Priority. Essential Rationale. TruTops ships worldwide; language coverage (incl. CJK glyph rendering) is a market requirement. Source. GRIT language array of 30 slots (ANZ_SPRACHEN, verified grit/src/graf.cpp); GRITLANG startup key and LANGUAGE=-C de-DE launch parameter (GritCad.org, StartTruTops.bat); up to 30 languages incl. CJK, per-language+resolution fonts ([[22 - FR - UI Framework, Dialogs & Interaction (GRIT)]]). Verification. Switch language across the supported set (incl. a CJK language) and confirm correct text/glyph rendering and unchanged behaviour.

NFR-018 — Metric / imperial (mm / inch) duality

Requirement. The system shall operate in either a metric or an imperial measurement system, selected per installation/session, with unit-aware configuration and a parallel inch technology database so that dimensions, tolerances, technology parameters and displayed unit suffixes are consistent throughout. Switching measurement systems shall not require recompilation. Category. Localization & Units Priority. Essential Rationale. North-American and other imperial markets require inch working; mixing units would produce wrong-scale parts. Source. Parallel *_inch schemas (e.g. Punch/Punch_inch, Laser/Laser_inch, Nest/Nest_inch) in Databases/SQLServerDatabase/Tables; per-edition Inch.Org config files (topsCadInch.org, ToPs100Inch.ORG, …); GRITUNIT key and StartTruTops.bat m/i selection; Common.UNITS/Common.SI_UNITS; metric/inch DB duality ([[12 - FR - Part & Data Management]]). Verification. Run an edition in metric and inch; confirm dimensions, DB values and unit suffixes are consistent and no metric/inch cross-contamination occurs.

NFR-019 — Externalized, localizable text and resources

Requirement. Domain and UI text shall be stored externally (translation tables / config), keyed by text number and language, rather than hard-coded, so translation and re-branding require no source change. Colour, font and icon tables shall likewise be externally configurable. Category. Localization & Units Priority. Essential Rationale. Externalized strings/resources are prerequisite to the 30-language capability and to customer-specific configuration. Source. Text.COMMON_TEXT / SPRACHEN and *_TEXTNR columns ([[19 - FR - Tools, Machines, Materials & Technology]], [[12 - FR - Part & Data Management]]); GRIT GRITCOLOR/GRIT_RGB/GRITCONF/GRITFONT/GRITICON config files (GritCad.org). Verification. Change a text-number entry and a colour/font table and confirm the running UI reflects it without recompilation.

Portability & Platform

NFR-020 — Windows platform and toolchain baseline

Requirement. The product shall build and run on supported Microsoft Windows releases using the established toolchain, rendering via the Windows GDI graphics and print stack. The primary shipped configuration is a 32-bit build produced with Visual Studio 2010 (compiler Msvc100, MultiByte character set). Category. Portability & Platform Priority. Essential Rationale. The deployed platform is Windows; the toolchain baseline constrains dependencies and third-party libraries and must be recorded for maintenance. Source. tcolib_win_VS2010.sln/.vcxproj (PlatformToolset v100, <Platform>Win32</Platform>, CharacterSet MultiByte); CompilerName.txt = Msvc100; GDI rendering (vis_gdi, grit/drive/elem_win.cpp) ([[21 - FR - Visualization, Viewing & Plotting]]). Verification. Clean build with the pinned toolchain and smoke test on a supported Windows version. Exact supported Windows versions (to be quantified) — see [[50 - Constraints & Assumptions]].

NFR-021 — 64-bit build capability

Requirement. The codebase shall additionally support a 64-bit (x64) build to remove 32-bit address-space limits for very large jobs, using the newer compiler toolchain provided for that target. Category. Portability & Platform Priority. Conditional Rationale. Large nests/programs can exhaust the 32-bit address space; an x64 path future-proofs capacity. Source. _shell_x64/environment.bat (VS2012/VS2015 amd64 vcvars64.bat) alongside the 32-bit _shell (VS2010); Databases_SQL_2019 newer-server support. Verification. Build and smoke-test the x64 configuration; confirm large-job handling beyond the 32-bit ceiling.

NFR-022 — Backend-abstracted rendering and platform-neutral core

Requirement. Rendering shall be isolated behind a backend-independent visualizer abstraction (GDI / GRIT / headless), and interactive/UI drawing shall not assume a specific windowing system, preserving the historical portability boundary (a Unix/X11 rendering path exists) and enabling headless operation. Category. Portability & Platform Priority. Conditional Rationale. The abstraction supports headless batch rendering today and reflects the product's cross-platform (HP-UX/X11) heritage; keeping it clean protects future portability. Source. Backend-independent visualizer vis_gdi/vis_grit/vis_none FR-VIS-002 ([[21 - FR - Visualization, Viewing & Plotting]]); legacy X11/Motif rendering path (grit/drive/elem_ux.cpp, grit/src/graf_x11.cpp, grit/drive/x11_def.h, grit/hpux). Verification. Render the same drawing via GDI and headless backends and compare output; confirm no direct Win32 calls leak into core geometry code.

Interoperability

NFR-023 — Broad CAD and exchange-format interoperability

Requirement. The system shall import and export the industry CAD/exchange and TRUMPF-native formats required for customer data hand-off, through a shared converter framework, with per-format import controls and post-processing. See [[30 - External Interface Requirements]] for the authoritative format list. Category. Interoperability Priority. Essential Rationale. Fabricators receive geometry in many formats; broad, controllable interchange is a core value proposition. Source. DXF/DWG/IGES/ME10-MI/DSTV import and DXF/ME10/IGES/SVG/HPGL/GEO/XML/XCAD export via convmain ([[11 - FR - Import, Export & File Formats]]); GeoViewer multi-format load ([[21 - FR - Visualization, Viewing & Plotting]]). Verification. Round-trip representative files per format and confirm geometric fidelity within tolerance.

NFR-024 — Data-management, database and PDM interoperability

Requirement. The system shall interoperate with SQL Server (and locally-attached MDB) technology databases over ODBC, and with the TRUMPF.NET PDM vault (via a file-access facade / CORBA naming service) transparently, so file access and catalog queries work identically over the local file system or the vault. Category. Interoperability Priority. Essential Rationale. Enterprise deployments store parts in PDM and technology in a shared database; transparent access is required for those workflows. Source. ODBC/SQL Server and locally-attached MDF; OmAdapter/TiPdmFacet PDM facade ([[12 - FR - Part & Data Management]]); pdmConvert.exe CORBA naming-service connection ([[11 - FR - Import, Export & File Formats]]); GRITPATH= X:\TRUMPF.NET\Data\... (GritCad.org). Verification. Exercise open/save/catalog over both local FS and a PDM vault and confirm equivalent behaviour.

NFR-025 — Programmatic and integration interoperability

Requirement. The system shall expose programmatic surfaces for automation and MES integration: an embedded Python interpreter, command interpreters (ASM/MMK), per-edition external component APIs, headless P/Invoke interop DLLs with managed .NET wrappers, and a PPS/MES (TruTops Fab) adapter, so third-party and in-house software can drive nesting, conversion and laser programming. Category. Interoperability Priority. Conditional Rationale. Integration into factory MES/PPS and regression pipelines depends on stable programmatic entry points. Source. tc_python (Python 2.5), tc_asm, Xidl component APIs, tc_reproduction/TruTopsDllNET P/Invoke, tc_fabAdapter ([[23 - FR - Automation, Scripting & Integration]]); TruTopsGeoInterface.dll C-API ([[12 - FR - Part & Data Management]]). Verification. Drive a nesting/conversion job through each programmatic surface and confirm expected results.

Security & Licensing

NFR-026 — Dongle / Wibu licensing enforcement

Requirement. Product and feature availability shall be gated by hardware/software licensing (dongle and/or Wibu software licence) validated at the relevant entry points; when a required licence is absent the corresponding functionality shall be denied. A dongle-less emulation/check-file mode shall be supported for machine-side operation as designed. Category. Security & Licensing Priority. Essential Rationale. Licensing protects TRUMPF's commercial model and gates per-edition/per-format capabilities. Source. tc_pwd (TcDongle, TcLicenseCheck, check_dll, dongle-less check-file emulation described in tops_pwd); per-format passwords DXF_PASSWORD/IGES_PASSWORD/… ([[11 - FR - Import, Export & File Formats]]). Verification. Run with/without dongle and with/without a format password; confirm gated features are enabled/denied accordingly.

NFR-027 — Per-format and per-machine feature gating

Requirement. Individual import/export formats and machine-specific post-processor licences shall be independently licensable, including per-machine (Wibu) licences for modular ("Baukasten"/Hawc-OPP) machine families, so a customer receives exactly the capabilities purchased. Category. Security & Licensing Priority. Essential Rationale. Fine-grained gating matches TRUMPF's à-la-carte licensing and machine-specific post-processors. Source. Per-format Wibu/password keys ([[11 - FR - Import, Export & File Formats]]); tc_pwd machine-password check (checkMachinePassword) with the S_WIBU_Map_HawcOPP_Machines modular-machine map and per-machine postprocessor licence check (verified in tc_pwd/tops_pwd.cpp). Verification. Toggle format and machine-postprocessor licences and confirm independent enable/deny.

NFR-028 — Controlled superuser / service bypass

Requirement. A superuser/service mode may bypass certain licence checks (e.g. Lite edition restrictions) for support and factory scenarios; when active it shall be applied consistently and shall not silently relax checks in normal operation. Category. Security & Licensing Priority. Conditional Rationale. Support and manufacturing need a controlled override; it must be explicit to avoid becoming a security hole. Source. Superuser-mode handling in tc_pwd/tops_pwd.cpp (Lite password check skipped only in superuser mode, verified in source); superuser bypass noted in [[11 - FR - Import, Export & File Formats]]. Verification. Confirm superuser mode is required to bypass and that normal mode enforces the checks.

NFR-029 — Database access-role authorization

Requirement. Access to the relational technology/master databases shall be governed by defined database roles with least-privilege grants, distinguishing at least read-only viewing, administration, import and porting/migration duties. Category. Security & Licensing Priority. Conditional Rationale. Separating admin/import/port roles from ordinary viewing limits accidental or unauthorized modification of technology data that drives machine programs. Source. GRANT role model in Databases/SQLServerDatabase/Tables/*.sql: VIEWER, MDB_ADMIN, MDB_IMPORTER, MDB_PORTER (verified — thousands of per-object grants). Verification. Connect under each role and confirm the permitted DML/DDL matches the intended privilege set.

Maintainability & Configurability

NFR-030 — Data-driven technology and NC output

Requirement. Adding or changing a machine, controller, material, tool, technology table or NC cycle/format shall be possible by editing database master data (not source code). NC generation shall render controller-specific output from data-driven cycle/format/head tables keyed by machine + controller + version. Category. Maintainability & Configurability Priority. Essential Rationale. The product supports a wide, evolving machine/controller/material matrix; a data-driven model is essential to maintain it without a release for every new machine. Source. Data-driven NCZYKLEN/AUS_FORMAT/NC_KOPF_TABELLEN/NC_KOPFTAB_MASCHINE keyed by machine+controller+version ([[18 - FR - NC Generation & Motion Optimization]]); machine/tool/material/LTT master tables and AUTOCUT_KONFIG ([[19 - FR - Tools, Machines, Materials & Technology]]). Verification. Add a machine/controller-version row and confirm NC output adapts without a code change.

NFR-031 — Externalized runtime configuration and per-edition feature flags

Requirement. Runtime behaviour — active edition, feature/menu exposure, mask set, language, unit, colour/font/icon tables, paths and resolution — shall be controlled by external .org/.ini/.ORG configuration files, so editions and site variants are configured without rebuilding. Category. Maintainability & Configurability Priority. Essential Rationale. One codebase produces many editions/site configurations; externalized configuration is how that is achieved. Source. Per-edition ini_files/<Edition>/*.Org/Grit*.ORG and *.ORG/*Inch.ORG pairs; StartTruTops.bat edition/unit selection; edition .ORG feature/menu control ([[13 - FR - Punching (ToPs 300)]], [[22 - FR - UI Framework, Dialogs & Interaction (GRIT)]]). Verification. Change a feature flag / mask set in the .org/.ini and confirm the running edition reflects it.

NFR-032 — Schema-driven, source-controlled database maintenance

Requirement. The database schema shall be defined and maintained through the data dictionary and kept under source control with automated compare/sync tooling, so schema evolution is auditable and reproducible across metric and imperial variants. Category. Maintainability & Configurability Priority. Conditional Rationale. A ~1,700-table schema with metric/inch variants is unmanageable without dictionary-driven generation and versioned compare/sync. Source. DATADICT schema-driving triggers ([[12 - FR - Part & Data Management]]); Red Gate SQL Source Control + Perforce hooks (RedGate.ssc, CommandLineHooks.xml, Databases/RedGateFilter/RedGateStructure{Metric,Imperial}.scpf); ~1,773 .sql table files under Databases/SQLServerDatabase. Verification. Regenerate the schema from the dictionary and diff against the source-controlled baseline; confirm metric/imperial structures stay in sync.

Installability & Operability

NFR-033 — Scripted, repeatable deployment

Requirement. Installation and provisioning of databases and connectivity shall be automated and repeatable: create/attach the SQL Server databases (or local MDB), create ODBC DSN entries, generate the runtime ini files, and launch a chosen edition — without manual per-step database administration. Category. Installability & Operability Priority. Essential Rationale. Field installs and developer/test setups must be reproducible; manual DB setup is error-prone at customer sites. Source. Databases/createSqlServerLocalMdb.bat, AttachSqlServerLocalMdb.bat, createSqlServerOdbcEntry.bat, createTcolibIniFiles.bat, createAll.bat, StartTruTops.bat (verified). Verification. Run the provisioning scripts on a clean machine and confirm a working, launchable installation.

NFR-034 — Database/application version compatibility and migration

Requirement. The application shall verify that the connected database schema version is compatible with the running executable version and refuse or guide the user on mismatch; supported schema upgrades and metric↔inch porting shall be provided as migration procedures, including the recorded provenance of the Access-to-SQL-Server migration. Category. Installability & Operability Priority. Essential Rationale. Running a new executable against an old schema (or vice versa) can silently corrupt or misread technology data; explicit compatibility gating and migrations prevent this. Source. Per-schema DB_VERSION tables and DbRequiredApplicExeVersion system rule set to the current exe version (Databases/UpdateDbRequiredApplicExeVersion_ps_legacy.bat, VERSION=140, verified); DB_Port_SqlSrv*.ps1 porting incl. overnight inch refresh; MS_SSMA_SOURCE extended properties recording the SQL Server Migration Assistant source (e.g. TCommon_V100); DB versioning & migration ([[12 - FR - Part & Data Management]]). Verification. Point a new executable at an out-of-date schema and confirm the mismatch is detected; run a metric→inch port and a schema upgrade and confirm success.

Notes and open points

  • tc_catch is snapping/picking, not exception handling. The crash-handling capability cited in the brief for "tc_catch/tc_issue" is actually implemented in tc_log/TnWindowsErrorReporting (WER minidumps, NFR-007); tc_issue is a consistency/validation issue manager (NFR-012); tc_catch is geometry hit-testing/snapping (see [[10 - FR - CAD Geometry & Drawing Editing]] / [[22 - FR - UI Framework, Dialogs & Interaction (GRIT)]]).
  • Numeric targets are largely unstated in source. Many performance/capacity thresholds (frame latency, element/part ceilings, supported Windows versions, concurrency model) are marked (to be quantified); they should be pinned against the current release and recorded in [[50 - Constraints & Assumptions]].
  • Mixed toolchain. The 32-bit product uses VS2010/Msvc100 while the x64 shell targets VS2012/VS2015; the authoritative shipping configuration should be confirmed with the build owner (NFR-020/NFR-021).
  • Cross-references: interfaces referenced here are specified in [[30 - External Interface Requirements]]; domain terms in [[04 - Domain Model & Glossary]]; full traceability in [[60 - Requirements Traceability Index]].
