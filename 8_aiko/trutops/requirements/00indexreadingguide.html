product: trutopscad org: trumpf title: "Index & Reading Guide" doc: "00 - Index & Reading Guide" id-prefix: "-" srs-standard: "ISO/IEC/IEEE 29148:2018" status: reverse-engineered-draft source: "TruTopsCAD legacy source snapshot (files dated May 2024)" related: ["[[01 - Vision & Scope]]", "[[03 - System Context & Architecture Overview]]", "[[04 - Domain Model & Glossary]]", "[[30 - External Interface Requirements]]", "[[40 - Non-Functional Requirements]]", "[[60 - Requirements Traceability Index]]"] tags: [requirements, trutops, index, moc]

TruTops CAD/CAM — Reverse-Engineered Requirements

This vault holds a reverse-engineered Software Requirements Specification (SRS) for TruTops, TRUMPF's legacy 2D offline CAD/CAM suite for sheet-metal fabrication. TruTops turns part drawings into optimised, machine-ready NC programs across punching, laser, tube and bending machines, delivered as a family of editions (ToPs 100 / 300 / 400 / 400 Cad / ToPsCad / ToPsNest) built from one shared C++ code base and master-data model.

Every document in this set was reconstructed by static analysis of the source snapshot (files dated May 2024) — the C++ tcolib modules, the GRIT UI masks, the SQL Server schema, and the ini/config files. The requirements are written to the structure and vocabulary of ISO/IEC/IEEE 29148:2018.

[!warning] Read this first — provenance caveat These are reconstructed requirements for understanding and migration, not the original authoritative specification. They describe what the code appears to do, inferred without access to the product's own requirements, test suites, or engineers. Treat every statement as a well-evidenced hypothesis: individual documents carry Open Questions listing exactly where evidence was thin or where module ownership is contested. Verify against the shipping product before relying on any single requirement.

How to Read This Suite

Documents are numbered so the number encodes the document's role. The band tells you what kind of content to expect:

Band Role Documents
00 Orientation This index / map of content
01–04 Context Vision, stakeholders, architecture, domain model & glossary
10–23 Functional Requirements (FR) The fourteen capability areas
30 / 40 / 50 Cross-cutting External interfaces, non-functional requirements, constraints & assumptions
60 Traceability Requirement → source-module / requirement → requirement index

Documents numbered NN.x (e.g. [[10.2 - CAD Detail - Editing & Transformation Commands]]) are Tier-2 detailed specifications that refine their parent NN document at command/algorithm granularity. They carry their own extended ID prefixes and requirement counts and are tracked separately from the system-level register — see the CAD sub-suite listed under the Document Map below.

ID scheme

Every requirement carries a stable ID so it can be cited and traced (see [[60 - Requirements Traceability Index]]):

  • FR-<AREA>-NNN — a functional requirement, where <AREA> names the capability group (e.g. FR-CAD-012, FR-LASER-024, FR-NEST-001). The per-area prefixes are listed in the Document Map below.
  • IF-NNN — an external interface requirement ([[30 - External Interface Requirements]]).
  • NFR-NNN — a non-functional / quality requirement ([[40 - Non-Functional Requirements]]).
  • CON-NNN — a constraint or assumption ([[50 - Constraints & Assumptions]]).

Each requirement is also tagged with an ISO 29148 priority: Essential (the product is not the product without it), Conditional (present, but gated by edition, licence, machine or configuration), or Optional (nice-to-have / peripheral).

Domain terms in German appear throughout because the source is German-origin; every term is defined once in [[04 - Domain Model & Glossary]] and referenced from there.

Document Map

Each row links to the document (Obsidian wikilink) and summarises its purpose. Functional-area docs also show their requirement ID prefix and count.

Functional Requirements (10–23)

Doc Purpose Prefix #
[[10 - FR - CAD Geometry & Drawing Editing]] The interactive 2D CAD editor and geometry kernel: primitives, parametric hole macros, transformations, trim/split/merge, fillet/chamfer/notch, offset, boolean contour arithmetic, dimensioning, attributes/snapping, curve approximation, geometry comparison and parametric variants. Core of the ToPsCad edition and drawing front end of ToPs 100/400/300. FR-CAD 35
[[11 - FR - Import, Export & File Formats]] Reading/writing external CAD & exchange formats (DXF, DWG, IGES, ME10/MI, DSTV), native TRUMPF formats (GEO/GMT/TAF) and raster images, plus export to DXF/ME10/IGES/SVG/HPGL/XML/XCAD. Centres on the shared converter framework (convmain), the batch executables, per-format import controls, a post-processing pipeline and per-format licensing. FR-IMPEX 33
[[12 - FR - Part & Data Management]] Persistence across two storage worlds: TRUMPF-native geometry files (MI on disk or in a PDM vault via an OmAdapter facade) and the relational database (SQL Server/MDF over ODBC), with the schema defined by the DATADICT data dictionary. Covers file I/O & versioning, catalog query, PDM integration, metric/inch duality, rule-set caching, migration, integrity, roles and XML I/O. FR-DATA 29
[[13 - FR - Punching (ToPs 300)]] The Punching/Nibbling technology area: automatic and manual tool assignment, punch/nibble along contours, common cutting, micro-joints, forming, marking, sheet clamping and repositioning, tool-hit optimization/simulation, scrap/skeleton handling, switching cycles and processing patterns. Editions: ToPs 100 / 100 Lite / 2000. FR-PUNCH 38
[[14 - FR - Laser Cutting (ToPs 100)]] Laser-cutting technology programming: technology/ruleset assignment, lead-in/lead-out and piercing, part-retention features, marking/engraving, kerf/corner correction, sheet dividing and remainder handling, gas/cooling parameters, cutting-sequence and path optimization, collision detection, cut simulation, and automated part removal. FR-LASER 33
[[15 - FR - Tube & Profile Machining (ToPs 400)]] Laser cutting of tubes, pipes and open profiles (ToPs Tube on the ToPs 400 platform): 3D modelling and unrolling, the profile library and cross-section families, machining-case assignment, corner treatment and weld-seam positioning, technology/rule/NC-cycle lookup, machine guiding elements, collision checking, sequence optimization, measuring cycles, NC/APD output and SolidWorks/PDM/TEO integration. FR-TUBE 32
[[16 - FR - Bending (ToPs 600)]] Press-brake programming: defining bends (kind/method/technique/angle/radius), computing bend-deduction factors and flat patterns from the ToPs 600 bend database, assigning punch/die tools, the interactive profile editor, bumping bends and corner reliefs, and the bend tool assistant. Automatic bend-sequence and collision checking appear delegated to the separate ToPs 600 application. FR-BEND 30
[[17 - FR - Nesting & Palletizing]] Automatic and interactive nesting of order parts onto raw sheets (true-shape, rectangular, tile), sheet-utilization optimization, multi-sheet/multi-format nests, remnant/offcut management with stock deduction, results and reports, and automatic/interactive palletizing for LiftMaster/SortMaster automation. Served by the stand-alone ToPsNest and embedded in ToPs 100/400. FR-NEST 35
[[18 - FR - NC Generation & Motion Optimization]] Turning a finished layout into an executable, controller-specific NC program and optimizing machine motion: constrained-TSP processing-order sequencing, per-tool travel-time optimization, collision-avoiding rapid-traverse path finding, jerk-limited cycle-time estimation, data-driven NC post-processing, setup-plan and multiple-up generation, NC transfer and simulation-data export. FR-NC 32
[[19 - FR - Tools, Machines, Materials & Technology]] The master-data & technology foundation: machine definitions, tool catalogs (punch tools, dies, multi-tools, thread formers, per-tool technology, XML import/export, central ITM/SW06 connection), material/thickness definitions, and technology tables (laser technology tables, AutoCut, micro-joints, tube technology). Shared master data driving all processors and editions. FR-TECH 31
[[20 - FR - Production Planning & Projects]] The organisational layer between nesting/NC and the shop floor: programming projects (PPJ workbooks) binding an order to machine/material/sheets/parts; production plans (NcListe) via the external NcLink tool; grouping captured parts into nesting orders with quantities/priorities/due dates; and job hand-off to production. Real scheduling is external (TruTops Fab). FR-PLAN 32
[[21 - FR - Visualization, Viewing & Plotting]] The graphics stack: on-screen 2D rendering of drawings/parts/nests, view navigation, display of tool paths and technology via toggleable content classes, the display-attribute model, and the three output paths — raster screenshots, GDI printing, and HPGL pen plotting. Rendering is backend-abstracted, plus an embeddable/standalone GeoViewer OCX. FR-VIS 33
[[22 - FR - UI Framework, Dialogs & Interaction (GRIT)]] The GRIT UI framework shared by all editions: masks/dialogs, the embedded MMK interpreter with mini_sql data binding, typed variables and control flow, input validation, finder lists, popup menus, interactive graphical selection, transaction-based undo/redo, unit and multi-language rendering, config files, and the Qt action bridge. FR-UI 31
[[23 - FR - Automation, Scripting & Integration]] The programmatic surfaces: an embedded Python 2.5 interpreter with a ToPs module, the ASM/MMK command interpreters, the per-edition Xidl external component API, the TruTops Fab (PPS/MES) adapter, and headless P/Invoke DLLs for batch nesting reproduction and laser shop-floor programming. FR-AUTO 33

Detailed CAD sub-suite (Tier 2 — refines [[10 - FR - CAD Geometry & Drawing Editing]])

The CAD row above (doc 10, FR-CAD, 35 system-level requirements) is expanded by a set of eight Tier-2 detailed documents (10.1–10.8) that specify each interactive command and geometry-kernel algorithm at its own verifiable granularity. Chapter 10 — doc 10 together with 10.1–10.8 — is grouped in the folder Requirements/ToPs 600 CAD/ — CAD historically shipped bundled with the ToPs 600 product (tops/tops_cad/tops_app.cpp still carries a commented-out TOPS600 password); its stand-alone name is ToPsCad (applic number CAD, product key TOPSCAD). Their requirements use extended prefixes and are tracked in their own documents — they refine, and are not added to, the 603-item system register (see the Coverage Summary note). All eight are written (457 requirements in total).

Detailed Bending sub-suite (Tier 2 — refines [[16 - FR - Bending (ToPs 600)]])

The Bending row above (doc 16, FR-BEND, 30 system-level requirements) is expanded by a Tier-2 sub-suite under Requirements/ToPs 600 Bending/ that details the bending NC code generation and the TruBend Cell 7000 automated bending cell — areas that doc 16 recorded as delegated to the separate ToPs 600 / BendAPI ("BendMaster") application. The sub-suite reverse-engineers the ToPs 600 Bend SQL data contract and the BendAPI automation surface (there is no readable C++ NC/robot generation in this snapshot). Like the CAD Tier-2 docs, these requirements are tracked in their own documents and are not added to the 603-item system register. Start at [[16.0 - Bending — Module Overview]].

Coverage Summary

The suite captures 603 numbered requirements across the functional, interface, non-functional and constraint documents (excluding the context docs 01–04 and the traceability index 60).

By priority

  • Essential — 264 (46%): the irreducible product. Note how heavily this concentrates in the platform/foundation areas — Constraints (34), Non-Functional (24), Production Planning (21), Tube (20), CAD and Data Management (19 each).
  • Conditional — 249 (44%): features gated by edition, licence, machine capability or configuration. This is the largest band overall and dominates the technology processors (Punch 20, Laser 20, Tech 22) and the interface catalog (39) — reflecting a single code base fanned out into many licensed editions.
  • Optional — 59 (10%): peripheral or convenience capabilities.

Largest and thinnest areas

  • Largest single document: [[30 - External Interface Requirements]] at 69 — unsurprising for a 30-year-old CAD/CAM hub that must speak to every CAD format, database, machine controller, PDM vault and automation surface in a shop.
  • Largest functional area: [[13 - FR - Punching (ToPs 300)]] at 38, closely followed by [[10 - FR - CAD Geometry & Drawing Editing]] and [[17 - FR - Nesting & Palletizing]] (35 each). Punching's tc_stz module alone is ~840k LOC.
  • Thinnest: [[22 - FR - UI Framework, Dialogs & Interaction (GRIT)]] carries 0 numbered requirements — it is a cross-cutting framework described narratively rather than enumerated. Among enumerated areas, [[12 - FR - Part & Data Management]] (29) and [[16 - FR - Bending (ToPs 600)]] (30) are the leanest, the latter because much bending logic lives in the separate ToPs 600 product outside this snapshot.

Caveats & Provenance

  • Reverse-engineered, not authoritative. Everything here was inferred from source; there was no access to original requirements, design docs, test cases or product engineers. Statements describe observed/inferred behaviour, not committed contract.
  • Static analysis only. No code was executed, no machine was driven, and no NC output was validated against a real controller. Runtime-only behaviour (backend selection, actual concurrency model, numeric performance) is inferred and frequently marked "(to be quantified)" in [[40 - Non-Functional Requirements]].
  • Single snapshot. Evidence is a May 2024 file snapshot. Per-release format changes (e.g. MI/GEO 2.21 vs 2.4) and the exact shipping build configuration (32-bit VS2010 primary vs the x64 VS2012/2015 path) were not resolved — see [[50 - Constraints & Assumptions]].
  • German-origin domain language. Terms such as Abwicklung, Nachsetzen, Regelwerk, Zerstanzen, Anfahren are used deliberately and defined once in [[04 - Domain Model & Glossary]].
  • Areas where evidence was thin (drawn from the per-document Open Questions — consult each doc's own list before relying on it):
    • Contested module ownership. Several modules are attributed differently by different analysts: tc_forml (formula collection → Bending/Technology, not CAD variants); tc_stl (Stanz-Laser punch-laser combi, not stereolithography STL); tc_scan/tc_gts/tc_bitm/tc_mtl (→ Nesting collision/parting, not raster/material); tc_aps (lead-in variants → NC/Laser, not Production Planning); tc_optimizer/tc_bsort/tc_fsel (→ NC Generation). The module map in [[03 - System Context & Architecture Overview]] records these but does not finally resolve them.
    • Shared-concept boundaries. AutoCut (punch ↔ laser), MFN/multiple-up (nesting ↔ NC), tc_profil (CAD ↔ bending ↔ tube), micro-joint/common-cut logic, and GTS all straddle document boundaries and may be double-counted.
    • Delegated-to-external behaviour. Automatic bend-sequence determination and press-brake collision checking, and true cross-machine scheduling, appear to live in the separate ToPs 600 / TruTops Fab products and are outside this snapshot.
    • Governance flags & concurrency. The semantics of the pervasive *_VISIBLE, *_LOCKSTATE/*_GESPERRT and *_TRUMPF_FLAG columns, and whether multi-user integrity relies on the SQL Server engine, the lock flags, or PDM check-out, were not fully determined ([[12 - FR - Part & Data Management]]).
    • Format completeness. MI export and the interactive Save-As-IGES path may be stubs; whether all GeoViewer SVG/BMP export paths are implemented is unconfirmed ("currently only GEO format realised").
    • Controller coverage. Only SIN840D (Siemens), KemroK2 and DA24+58 were directly observed; the full set of NC controller families driven by the data-driven cycle/format tables is not enumerated.

Suggested Reading Paths

New to the product / onboarding. Start with the story, then the shape: [[01 - Vision & Scope]] → [[04 - Domain Model & Glossary]] (keep this open as a companion) → [[03 - System Context & Architecture Overview]] → [[02 - Stakeholders & Actors]]. Then dip into one functional area that interests you, e.g. [[10 - FR - CAD Geometry & Drawing Editing]].

Planning a migration / rewrite. Bound the problem before the features: [[01 - Vision & Scope]] → [[50 - Constraints & Assumptions]] (the frozen toolchain, dongle licensing, dual metric/inch schema, mandated directory layout) → [[30 - External Interface Requirements]] (every integration you must preserve) → [[40 - Non-Functional Requirements]] (the quality bar) → [[12 - FR - Part & Data Management]] and [[19 - FR - Tools, Machines, Materials & Technology]] (the shared data model everything depends on). Use [[60 - Requirements Traceability Index]] for impact analysis when scoping a module.

Working on a specific machine domain. Read the domain FR doc alongside its shared foundations. In every case: pair the technology doc with [[19 - FR - Tools, Machines, Materials & Technology]] (master data), [[18 - FR - NC Generation & Motion Optimization]] (output) and [[04 - Domain Model & Glossary]].
