product: trutopscad org: trumpf title: "External Interface Requirements" doc: "30 - External Interface Requirements" id-prefix: "IF" srs-standard: "ISO/IEC/IEEE 29148:2018" status: reverse-engineered-draft source: "TruTopsCAD legacy source snapshot (files dated May 2024)" related: ["[[00 - Index & Reading Guide]]", "[[11 - FR - Import, Export & File Formats]]", "[[12 - FR - Part & Data Management]]", "[[18 - FR - NC Generation & Motion Optimization]]", "[[23 - FR - Automation, Scripting & Integration]]", "[[04 - Domain Model & Glossary]]"] tags: [requirements, trutops, interfaces]

External Interface Requirements

This document consolidates every external interface surfaced by the functional-area analyses ([[11 - FR - Import, Export & File Formats]], [[12 - FR - Part & Data Management]], [[14 - FR - Laser Cutting (ToPs 100)]], [[15 - FR - Tube & Profile Machining (ToPs 400)]], [[16 - FR - Bending (ToPs 600)]], [[17 - FR - Nesting & Palletizing]], [[18 - FR - NC Generation & Motion Optimization]], [[19 - FR - Tools, Machines, Materials & Technology]], [[20 - FR - Production Planning & Projects]], [[21 - FR - Visualization, Viewing & Plotting]], [[22 - FR - UI Framework, Dialogs & Interaction (GRIT)]], [[23 - FR - Automation, Scripting & Integration]]) and specifies them as IF-NNN requirements per ISO/IEC/IEEE 29148:2018 §9.5. Interfaces are grouped into data/file formats, database/PDM, machine/controller/NC, programmatic, and user/hardware. Domain terms are defined in [[04 - Domain Model & Glossary]]; non-functional envelopes (throughput, compatibility, reliability) are in [[40 - Non-Functional Requirements]] and platform constraints in [[50 - Constraints & Assumptions]].

Notation: Direction is In (system reads/consumes), Out (system writes/produces), or In/Out (bidirectional). Priority follows the SRS convention — Essential (present in every shipped edition), Conditional (present only for a specific edition, licensed feature, or deployed peripheral), Optional (auxiliary/convenience or not fully realized in the snapshot).

2. Data & File-Format Interfaces

Import/export of vector CAD exchange formats, TRUMPF-native geometry, raster images and the planning/machining artefact files. The shared converter framework (convmain: readDrawingFromFile → doDrawingConversion → writeDrawingToFile) underlies most of these; per-format handling lives in tc_dxf, tc_iges, tc_mi, tc_me10, tc_dstv, tc_dbase. See [[11 - FR - Import, Export & File Formats]] for the functional behaviour and [[19 - FR - Tools, Machines, Materials & Technology]] for tool-data files.

IF-001 — DXF (AutoCAD exchange) import

Requirement: The system shall import AutoCAD DXF files into the Dbase drawing model, reading the full supported entity set (LINE, POLYLINE, LWPOLYLINE, CIRCLE, ARC, ELLIPSE, SPLINE, POINT, TEXT, MTEXT, INSERT, SOLID, HATCH, DIMENSION). Import shall be controllable per the DXF options in [[11 - FR - Import, Export & File Formats]]: layer selection (with frozen/off layers ignored by default), single-block / single-layout selection, spline-conversion mode, text/font handling, Z-coordinate suppression (2D projection), and generation of an optional load-error report (TcDxfLoadReport, .LOG/HTML). DXF layers, having no native equivalent, shall be mapped onto element colour/line-style. Priority: Conditional (per-format Wibu/dongle + DXF_PASSWORD). Rationale: DXF is the dominant customer-geometry exchange format for sheet-metal CAD hand-off. Source: tc_dxf; convmain (readDrawingFromFile); tec_cad.gritx (F_DxfLayerFinder); FR-IMPEX-001..007. Verification: Test — import reference DXF files covering each entity type and each option combination; compare resulting Dbase geometry against expected drawings and inspect the generated load-error report.

IF-002 — DXF export

Requirement: The system shall export the current drawing (or an individual nested sheet) to AutoCAD DXF via tc_dxf, preserving geometry, element colour/line-style mapping and text. Priority: Conditional (DXF licence). Rationale: Round-trip hand-off of geometry and nested layouts to external CAD. Source: tc_dxf; nesting DXF sheet export ([[17 - FR - Nesting & Palletizing]]); FR-IMPEX. Verification: Test — export a known drawing to DXF, re-import into TruTops and a third-party CAD tool, and confirm geometric equivalence within tolerance.

IF-003 — DWG import via external DwgConverter.exe

Requirement: The system shall import AutoCAD DWG files by invoking the external DwgConverter.exe (TRUMPF Utils) to produce a temporary DXF, which is then imported through the DXF path (IF-001). The converter shall be locatable either by a database-configured path (DwgConverterDBCall) or a fixed static path (DwgConverterStaticCall). Priority: Conditional (DWG_PASSWORD / Wibu licence; external tool present). Rationale: DWG is binary and cannot be parsed natively; conversion is delegated to a licensed external tool. Source: tc_dwg/TcDwgConverter.h; FR-IMPEX-008. Verification: Test — with the external converter installed, import a DWG file and confirm the temporary DXF is produced and consumed; verify a clear error when the converter is absent or unlicensed.

IF-004 — IGES import

Requirement: The system shall import IGES neutral CAD files (entity types 100/106/110/116/124/126/212/308/408) into the Dbase model via ig_lese. Priority: Conditional (IGES_PASSWORD / Wibu licence). Rationale: IGES is a common neutral CAD interchange format. Source: tc_iges (ig_lese); FR-IMPEX-009. Verification: Test — import IGES files exercising each supported entity type and confirm correct geometry.

IF-005 — IGES export

Requirement: The system shall provide IGES export via ig_ausgabe. Priority: Optional. Rationale: Bidirectional IGES exchange for downstream CAD. Source: tc_iges (ig_ausgabe); FR-IMPEX. Note: the convmain converter's schreibe_iges_format() is a stub (returns 0); the interactive Save-As-IGES path was not fully traced, so batch IGES export may be unavailable (open question, [[11 - FR - Import, Export & File Formats]]). Verification: Test — export a drawing to IGES via the interactive path and re-import; confirm whether batch (converter) IGES output is functional or stubbed.

IF-006 — ME10 / MI (Macro Interchange) import incl. CAPT

Requirement: The system shall import HP ME10 MI files (versions 2.21 and 2.4) via tc_mi, including the CAPT mode that additionally converts punch single-stroke (Einzelhub) technology into Dbase attributes according to file-driven stroke-conversion rules (TcMiStrokeConversionRule). Priority: Conditional (MI_PASSWORD / Wibu licence). Rationale: ME10/MI is a legacy TRUMPF/HP CAD exchange format still received from customers and carrying punch technology. Source: tc_mi; FR-IMPEX-010; single-stroke rules ([[13 - FR - Punching (ToPs 300)]]). Verification: Test — import MI 2.21 and 2.4 files, and a CAPT file, verifying geometry and single-stroke attribute mapping.

IF-007 — ME10 export

Requirement: The system shall export drawings to HP ME10 format via tc_me10. Priority: Optional. Rationale: Interchange with ME10-based CAD systems. Source: tc_me10; FR-IMPEX. Note: the convmain converter's schreibe_mi_format() is a stub; MI/ME10 batch export may be limited (open question). Verification: Test — export to ME10 and re-import; confirm geometric equivalence.

IF-008 — DSTV steel-construction NC import

Requirement: The system shall import the 2D geometry of DSTV (Deutscher Stahlbau-Verband) NC files via tc_dstv/db_dstv, ignoring bending/powder information not relevant to sheet geometry. Priority: Conditional (DSTV_PASSWORD / Wibu licence). Rationale: DSTV files carry sheet-metal part geometry from steel-construction workflows. Source: tc_dstv; FR-IMPEX. Verification: Test — import DSTV files and confirm 2D contours are produced while non-geometry data is safely ignored.

IF-009 — Native GEO / GEO_102 geometry file

Requirement: The system shall read and write TRUMPF-native GEO and GEO_102 geometry files as the internal storage/exchange format, through the on-disk parser in tc_dbase and the converter framework. Priority: Essential. Rationale: GEO is the primary internal geometry persistence format across all editions. Source: tc_dbase; convmain; FR-IMPEX; FR-DATA-001/002/005. Verification: Test — save a drawing to GEO/GEO_102, reload it and confirm loss-free round-trip.

IF-010 — Native MI part/drawing/sheet files (versioned)

Requirement: The system shall persist and load parts, drawings and nesting sheets as versioned TRUMPF-native MI-format text geometry files through tc_mi/tc_dbase, carrying a format version (MI_Version_Nr, e.g. 2.21/2.4) and, for sheets (Tafel), placement matrices. File access shall be transparent over the local file system or a PDM vault (IF-031). Priority: Essential. Rationale: The versioned native geometry file is the canonical persisted unit for parts, drawings and sheets ([[12 - FR - Part & Data Management]]). Source: tc_mi, tc_dbase; FR-DATA-001..005. Verification: Test — save/load parts, drawings and sheets; verify version markers and backward-compatible reading of older versions.

IF-011 — GMT geometry format and drawing-number stamping

Requirement: The system shall read and write the GMT (ToPs 1000) geometry format and shall be able to stamp its drawing/part number, so the GMT drawing number can serve as the through-going part identifier in the Blechfabrik workflow. Priority: Conditional (GMT-based workflows / ToPs 1000 interchange). Rationale: GMT links geometry to the part identity used across the sheet-metal factory. Source: tc_dbase; converter (getNextGrafikFormatId); FR-IMPEX; FR-PLAN. Verification: Test — import a GMT, stamp a drawing number, re-export and confirm the number is persisted and retrievable.

IF-012 — TAF archive/table input

Requirement: The system shall accept the TAF (TRUMPF archive/table) format as a converter input, applying the required TAF→DXF special-export path where needed. Priority: Conditional. Rationale: TAF is an accepted converter input in batch conversion. Source: convmain (TeGrafikFormat); FR-IMPEX. Note: TAF record structure was only observed at dispatch level. Verification: Test — convert a TAF input to a supported output and confirm geometry.

IF-013 — Raster image import via ToPsVectorize

Requirement: The system shall import raster images (BMP, JPG, PNG, TIF, GIF) by invoking the external ToPsVectorize.exe (path from TOPS_VECTORIZE_PATH), which vectorizes the pixel image and returns GEO geometry for loading into the drawing model. Priority: Conditional (external tool present + licence). Rationale: Enables reconstruction of vector geometry from scanned/photographed parts. Source: tc_cad/cad_vectorize; TOPS_VECTORIZE_PATH; FR-IMPEX. Note: tc_scan/tc_bitm are unrelated (parting-cut skeleton / nesting collision bitmaps). Verification: Test — with ToPsVectorize installed, import each raster type and confirm vector geometry is produced; verify a clear error when the tool is missing.

IF-014 — SVG export

Requirement: The system shall export drawings to SVG (Scalable Vector Graphics) with configurable stroke width, via db_svg, and the embeddable viewer shall support SVG export. Priority: Optional. Rationale: Web/document-friendly vector output. Source: db_svg; tc_viewer; FR-IMPEX; FR-VIS. Verification: Test — export SVG and render it in a standard browser; confirm geometry and stroke width.

IF-015 — XML calculation-info export

Requirement: The system shall export contour calculation information as XML for the ToPs 1000 calculation/costing tool. Priority: Optional. Rationale: Feeds downstream costing. Source: convmain; FR-IMPEX. Verification: Test — export XML calculation info for a known part and validate structure/content against the consuming tool.

IF-016 — XCAD internal-exchange export

Requirement: The system shall export the Dbase model to the internal TRUMPF XCAD exchange format via db2XCad/exportDbaseToXCad. Priority: Optional. Rationale: Internal TRUMPF component interchange. Source: db2XCad; FR-IMPEX. Note: XCAD record structure observed only at dispatch level. Verification: Test — export XCAD and confirm the consuming component accepts it.

IF-017 — STL 3D exchange (not supported — documented gap)

Requirement: The system does not provide stereolithography STL 3D mesh import or export. The module named tc_stl is Stanz-Laser (punch-laser combi) technology, not STL geometry; no true 3D STL file interface exists in the snapshot. Any future STL requirement shall be treated as a new interface. Priority: Optional (documented absence). Rationale: Recorded to prevent misattribution of tc_stl and to flag the coverage gap for the interface owner. Source: tc_stl/stl_tech (punch-laser technology); FR-IMPEX open question. Verification: Inspection — confirm no STL reader/writer symbols exist and tc_stl contents are punch-laser technology.

IF-018 — Tube 3D geometry (ROT / RMT) import

Requirement: The system shall import tube 3D surface files (.rot) and raw-material tube files (.rmt) and triangulate them for display (roh_to3d); RMT files shall carry material, wall thickness and section dimensions used to match or create a tube technology record. Priority: Conditional (ToPs Tube edition). Rationale: Tube programming starts from imported 3D tube/stock geometry ([[15 - FR - Tube & Profile Machining (ToPs 400)]]). Source: tc_rohr/roh_to3d; FR-TUBE-001/006. Verification: Test — import ROT and RMT files and confirm the 3D model and derived stock data.

IF-019 — RPF profile cross-section file

Requirement: The system shall read and write RPF profile files describing open or closed cross-section geometry, with open/closed validation, via roh_rpf. Priority: Conditional (ToPs Tube edition). Rationale: RPF backs the profile library for tube/profile machining. Source: tc_rohr/roh_rpf (TeTubeRpfError); FR-TUBE-009/010. Verification: Test — create, save, reload and modify an RPF profile; confirm open/closed validation rejects invalid geometry.

IF-020 — TEO tube-exchange file (via PDM)

Requirement: The system shall exchange grouped tube contours with partner tube-CAD systems through TEO files, opened/saved via the PDM browser (roh_teo, openSaveTeoBrowser). Priority: Conditional (ToPs Tube + PDM). Rationale: TEO is the tube-contour interchange with partner CAD. Source: tc_rohr/roh_teo; FR-TUBE. Verification: Test — export and re-import a TEO file through the PDM browser and confirm contour groups.

IF-021 — Tool definition XML import/export (WZG)

IF-064 — On-screen display backend (Windows GDI / X11)

Requirement: The system shall render 2D geometry to screen through a backend-independent visualizer with Windows GDI (vis_gdi), legacy X11 (elem_ux.cpp) and headless (vis_none) backends, providing world↔device transformation, redraw lifecycle management, off-screen double-buffering and an interactive XOR/echo mode. Priority: Essential. Rationale: On-screen rendering is required for all interactive editions; the headless backend supports server/batch use. Source: tc_visualize, grit/drive; FR-VIS-001..004. Note: how the runtime selects between backends (build-time vs runtime/per-edition) was not fully determined (open question). Verification: Test — render on GDI and (where available) headless; confirm redraw and coordinate transforms.

IF-065 — Windows GDI printing

Requirement: The system shall print drawings via the Windows GDI printer interface (setPrinterDC, GetDeviceCaps, Escape(SET_BOUNDS)), supporting margins, aspect correction, scaling, orientation, black/white swap and an optional header. Priority: Conditional (printer available). Rationale: Operators print parts/nests for shop-floor paperwork. Source: tc_visualize/grit/drive; FR-VIS. Verification: Test — print a drawing at defined scale/orientation with header and confirm the output.

IF-066 — HPGL / HPGL2 pen-plotter output

Requirement: The system shall output drawings to HPGL/HPGL2 pen plotters over the host/PC interface defined by a plotter profile (DB_Plotter: HPGL2 flag, rotation, pen colours, line types, symbols, DIN paper list), via tc_plot, optionally applying a projection matrix (e.g. isometric) and a scale factor. Priority: Conditional (plotter present). Rationale: Legacy plotting output for large-format drawings. Source: tc_plot; FR-VIS. Note: the on-disk location/format of the plotter-config file read by db_lese_plotter_konfig was not located (open question). Verification: Test — plot a drawing with a configured plotter profile and confirm pen/paper/scale handling.

IF-067 — Raster hardcopy (BMP / TIFF)

Requirement: The system shall capture a screen region/viewport as a raster hardcopy written to a BMP or TIFF file or stream, in colour or monochrome. Priority: Optional. Rationale: Screenshots for documentation and reports. Source: tc_bitm (write_tiff), tc_visualize; FR-VIS. Verification: Test — capture a viewport to BMP and TIFF (colour and monochrome) and confirm the images.

IF-068 — Dongle / Wibu licensing & password protection

Requirement: The system shall protect editions and per-format import/export features with hardware/software dongle (Wibu) licensing plus a per-format password list (DXF_PASSWORD, DWG_PASSWORD, IGES_PASSWORD, MI_PASSWORD, DSTV_PASSWORD, tube password), checked via TcLicenseCheck, with a superuser mode that bypasses the password check and configurable dongle access (local vs network) and module id. Absent or invalid licences shall block the protected feature with a clear message. Priority: Essential. Rationale: Licensing governs which editions and formats a site may use. Source: convmain/tc_conv.h (m_passwordCheck, m_dongleAccess, m_dongleId); TcLicenseCheck; TiTubeConnection.isLicenseValid/isPasswordValid; FR-IMPEX, FR-TUBE. Verification: Test — run with and without valid dongle/password for a protected format; confirm blocking and superuser bypass.

IF-069 — GRIT configuration files (.org/.ini, colour/font/icon)

Requirement: The system shall be configured at startup from per-edition .org/.ini files (keys GRITLANG, GRITUNIT, GRITCOLOR, GRITFONT, GRITICON, GRITSIZE, GRITTITLE, MASK_OLB, plus edition feature/menu exposure) and referenced colour (GRITCOL.24, RGB.TXT), font (GRIT_ALL.DEF) and icon tables. Each edition (ToPsCad, ToPs 100/100 Lite/2000, ToPs 300, ToPs 400/400 Cad, ToPsNest) ships its own .ORG/Grit*.ORG set. Priority: Essential. Rationale: All per-edition UI language, units, fonts, colours and feature exposure are externalized to configuration. Source: ini_files/*/*.ORG, ini_files/*/Grit*.ORG; FR-UI. Verification: Test — start each edition with its .org/.ini set and confirm language/unit/colour/font/menu configuration is applied.

Open Questions & Boundary Notes

  • IGES/ME10 batch export (IF-005/IF-007): the convmain converter's schreibe_iges_format()/schreibe_mi_format() are stubs; only interactive export paths may be functional.
  • STL (IF-017): no true STL interface exists; tc_stl is punch-laser technology.
  • PDM contract (IF-031/IF-032): check-in/out, versioning and locking live in OmAdapter.dll outside the snapshot; the relationship between PDM locking and DB LOCKSTATE is unresolved.
  • Controllers (IF-037/IF-038): only Siemens SIN840D was directly observed; the full NC_STEUERUNG set driven by the data-driven tables was not enumerated.
  • MFN / tc_lift ownership: multiple-up generation (tc_mfn) and holding-device modelling (tc_lift) straddle Nesting, NC and Laser; only their interface facets are captured here.
  • Converter CLI (IF-056): the exact multi-output syntax and the summed error-code return value were inferred, not confirmed end-to-end.
  • GeoViewer export (IF-057): SVG/BMP export completeness across all formats is uncertain (source comment implies only GEO is realized).
  • Access MDB (IF-028): referenced historically; the shipped stand-alone path is SQL Server local MDF.

See the per-area documents for the functional detail behind each interface, and [[60 - Requirements Traceability Index]] for cross-references.
