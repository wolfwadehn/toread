FR — UI Framework, Dialogs & Interaction (GRIT)

Reverse-engineered requirement draft — derived from static analysis of legacy source, NOT an authoritative specification. Treat SHALL statements as reconstructed intent.

1. Purpose & Scope

This document specifies the functional requirements of the GRIT UI framework — the presentation and interaction layer shared by every TruTops CAD/CAM product edition. GRIT ("Graphics Interactive Tool", GfT / Graphics mbH, in use since ~1989) provides: screen forms ("masks"/dialogs), buttons and menus, an embedded interpreter language (MMK) that scripts dialog behaviour and binds dialogs to the database via mini_sql, interactive graphical selection, undo/redo, keyboard/mouse handling, and unit- and language-dependent rendering of the UI.

The scope covers how the user interacts and how dialogs/commands are defined and driven, not the CAD/CAM domain logic that those dialogs invoke (that logic is owned by [[10 - FR - CAD Geometry & Drawing Editing]], [[13 - FR - Punching (ToPs 300)]], [[14 - FR - Laser Cutting (ToPs 100)]], [[17 - FR - Nesting & Palletizing]] etc.). Requirements here derive from grit/ (src, tco_api, drive, win), tco_grit_tools/ (GritFile / GritDialog converters, mask tool), tc_bof/*.gritx + *.olb masks and their MMK/mini_sql scripts, tops/topsgrit, tc_selection, tc_undo, tc_text, tc_guiAdapter, GUI/Controller, and the runtime configuration in ini_files/*/*.org and tco_grit_tools/mask/gritw/GRIT_ALL.DEF.

Editions served: all (ToPs 100/300/400, ToPs Cad, ToPs Nest, ToPs Tube, and the "Lite"/2000 variants). GRIT is a cross-cutting foundation; edition-specific behaviour comes from which mask files (.olb) and .org configuration are loaded.

2. Capability Overview

  • Mask/dialog definition & storage. Dialogs are authored as .gritx XML (GRIT v2.63, UTF-8), stored/deployed as binary .olb and legacy ASCII .a26, and converted between all three formats.
  • Mask object model. Each file holds up to 10 fonts and N masks; each mask has Enter/Exit/Key lifecycle callbacks and buttons of type normal / text / bitmap / input (Eingabe) / graphic (Grafik) / scroll.
  • Per-button interaction bindings. Up to five mouse-key functions plus mouse-enter/exit/move handlers, each optionally running a named C function or an MMK script.
  • MMK interpreter. A lex/yacc scripting language embedded in mask CDATA, with typed variable substitution (@ text, # number, : field, $ field-change), IF/ELSE-IF/ELSE control flow, built-in dialog and utility commands, and date/time formatting.
  • mini_sql data binding. SELECT … INTO (FINDER lists / named fields), plus INSERT/UPDATE/DELETE/RECORD, with JOIN/UNION/ORDER BY and variable substitution — the mechanism that turns database rows into on-screen list content and writes edits back.
  • Input widgets & validation. Input fields with prompt, suffix, format, decimal-place control; plausibility checking against interval / set / alphanumeric / constant / free-form rules.
  • Lists, menus, tooltips, help. Scrollable FINDER lists, popup menus/toolbars, per-mask tooltips, and per-button help text held per language.
  • Interactive selection. Pick, box, select-all, invert, confirm and deselect over CAD/technology/tube objects, with single / multiple-add / multiple-invert modes and preview highlighting.
  • Undo/redo. Transaction-based undo/redo (atomic and non-atomic transactions) with stack size limits and UI availability notification.
  • Units & language. Metric/imperial unit rendering with configurable decimal shift; up to 30 UI languages including CJK (Kanji/Korean/Chinese), with resolution- and language-specific font tables.
  • Keyboard/mouse. Function keys, arrow keys, Ctrl/Shift/Alt combinations, Home/End/PgUp/PgDn, Escape.
  • Runtime configuration. .org/.ini keys select language, unit, colours, fonts, icons, window size, title and mask set.
  • Modern GUI bridge. tc_guiAdapter AppStates and the Qt GUI/Controller action framework connect the legacy GRIT layer to the current front-end.

4. Functional Requirements

FR-UI-001 — Mask definition format and multi-format storage

  • Requirement: The system shall represent every dialog ("mask") as a structured definition that can be read from and written to GRIT ASCII (.a26), GRIT binary (.olb) and GRIT XML (.gritx, version 2.63, UTF-8) forms.
  • Priority: Essential
  • Rationale: Masks are authored/inspected as XML and deployed as binary .olb; a common object model must round-trip all three so dialogs survive editing, build and runtime.
  • Source: tco_grit_tools/convUtils/GritFile.h (leseAusA26/leseAusOlb/schreibeInA26/schreibeInOlb, TeGritFileVersion enum 2.6–2.63); tc_bof/*.gritx headers <GritFile version="GRIT Version 2.63" ascii="UTF-8">; .olb files beside each .gritx.
  • Verification: Test (convert a .gritx to .olb and back, compare object models).

FR-UI-002 — Mask object model (fonts, masks, lifecycle functions)

  • Requirement: The system shall load, per mask file, up to 10 fonts (AllFonts) and a declared number of masks (AllMasks mask_count), and for each mask shall hold its name, type, save flag and an Enter, Exit and Key lifecycle function.
  • Priority: Essential
  • Rationale: The mask is the fundamental UI unit; its lifecycle callbacks drive initialization, teardown and key handling.
  • Source: tc_bof/muster.gritx (<AllFonts>, <AllMasks mask_count="25">, <Mask save_flag mask_type mask_name>, <EnterFunction>/<ExitFunction>/<KeyFunction>); tco_grit_tools/convUtils/GritDefines.h (GRIT_ANZAHL_FONTS 10).
  • Verification: Inspection (mask XML schema) + Test (open a mask, confirm Enter function fires).

FR-UI-003 — Button widget types

  • Requirement: The system shall support buttons of type normal, text, bitmap, input (Eingabe), graphic (Grafik) and scroll, and shall render each according to its type.
  • Priority: Essential
  • Rationale: These six widget kinds cover all interactive elements in the framework.
  • Source: tco_grit_tools/convUtils/GritFile.h (TeGritButtonTyp: Normal 0, Text 1, Bitmap 2, Eingabe 3, Grafik 4, Scroll 5); grit/src/c_button.hpp (#define TEXTW 1, SCROLLW 5); dedicated classes GritTextButton/GritBitmapButton/GritEingabeButton/GritGrafikButton/GritScrollButton.
  • Verification: Demonstration (a mask containing all six types renders correctly).

FR-UI-004 — Per-button mouse interaction bindings

  • Requirement: For each button the system shall allow up to five mouse-key functions (MouseFunction1..MouseFunction5) plus mouse-enter, mouse-exit and mouse-move handlers, each optionally invoking a named function or an MMK script.
  • Priority: Essential
  • Rationale: Multi-button and hover interaction (e.g. context actions, live preview) is defined declaratively per button.
  • Source: tc_bof/muster.gritx (<MouseFunctions key_1..key_5>, <MouseEnterFunction>/<MouseExitFunction>/<MouseMoveFunction>); grit/src/c_button.hpp (gib_func1..gib_func5, gib_menter/gib_mexit/gib_mfunc).
  • Verification: Test (bind and trigger each mouse function).

FR-UI-005 — Mask lifecycle callbacks execution

  • Requirement: When a mask is opened, the system shall execute its Enter function; when the mask is closed it shall execute its Exit function; and when a key event occurs while the mask is active it shall execute its Key function.
  • Priority: Essential
  • Rationale: Data loading (typically a mini_sql SELECT) is bound to mask entry; cleanup and key handling to exit/key callbacks.
  • Source: grit/src/c_oberfl.hpp (pushMmkEnterFunction, getActiveEnterfunctionDialogPtr); grit/src/c_oberfl.cpp (MMK_callEnterFunction); tc_bof/muster.gritx Enter function running dialog_neu(FINDER_2); mini_sql(SELECT …).
  • Verification: Test (open a finder mask, confirm the Enter script populates the list).

FR-UI-006 — MMK interpreter execution

  • Requirement: The system shall provide an embedded MMK interpreter that executes the script contained in a mask's or button's <function_content> CDATA block against the active surface and button context.
  • Priority: Essential
  • Rationale: MMK is the scripting mechanism that drives virtually all dialog behaviour and data binding across the product.
  • Source: grit/tco_api/tc_api/t_pars.hpp (MMK_interpreter(Oberfl*, Button*, int, int, int), parse_stmt, GritFunc); grit/tco_api/tc_api/tc_api_lex.l + tc_api_yacc.y (lex/yacc grammar); registered as function "MMK_interpreter" in grit/tco_api/tc_api/tc_mmk.fun and tops/topsgrit/topsgrit.fun.
  • Verification: Test (run an MMK EnterFunction and observe its effect).

FR-UI-007 — MMK typed variable substitution

  • Requirement: The MMK interpreter shall resolve variable references by type prefix, substituting @name as a text value, #name as a numeric value, :name as a bound dialog field, and $name as a field-change target.
  • Priority: Essential
  • Rationale: Typed substitution is how scripts read/write dialog fields and inject values into SQL and commands.
  • Source: grit/tco_api/tc_api/tc_api_lex.l (\@→YACC_CHANGE_TEXT, \#→YACC_CHANGE_NUMBER, \:→YACC_FELD_KENNUNG, "$"→YACC_CHANGE_FELD); grit/tco_api/tc_api/s_var.hpp (S_var type/name/value); usage e.g. @ST_BMInfoMusterGruppe, :BM_NAME, #tmp_Buttons in tc_bof/muster.gritx and tc_bof/roh_func.gritx.
  • Verification: Test (set a variable, reference it with each prefix, verify substitution).

FR-UI-008 — mini_sql read binding into finder lists and fields

  • Requirement: The MMK interpreter shall execute mini_sql SELECT statements — including JOIN, UNION, WHERE (with variable substitution) and ORDER BY — and shall write the result set INTO a finder list (FINDER_1..FINDER_6) or into named dialog fields (RECORD).
  • Priority: Essential
  • Rationale: This is the primary mechanism that fills list dialogs from the technology/production database.
  • Source: grit/tco_api/tc_api/tc_api_yacc.y (do_sql_into, Yacc_dest = FINDER_1..6 / RECORD, YACC_SELECT/FROM/UNION); tc_bof/muster.gritx (mini_sql(SELECT :BM_NAME … INTO (FINDER_2) FROM BEARBMUSTER INNER JOIN … WHERE MGM_MG_NAME LIKE @… ORDER BY …)).
  • Verification: Test (execute a SELECT, verify finder rows and field values).

FR-UI-009 — mini_sql write-back (INSERT/UPDATE/DELETE)

  • Requirement: The MMK interpreter shall execute mini_sql INSERT, UPDATE and DELETE statements so that dialog edits can be persisted to the database.
  • Priority: Essential
  • Rationale: Editable catalog/management dialogs must write user changes back to the database.
  • Source: grit/tco_api/tc_api/tc_api_yacc.y tokens YACC_INSERT, YACC_UPDATE, YACC_DELETE, YACC_L_DELETE, YACC_RECORD.
  • Verification: Test (edit a record via a mask, confirm the row changes in the database). See [[12 - FR - Part & Data Management]] for the underlying stores.

FR-UI-010 — MMK conditional control flow

  • Requirement: The MMK interpreter shall support IF, ELSE IF and ELSE conditional blocks with comparison operators (==, !=, >, <), and shall correctly evaluate nested conditionals to at least 40 levels of depth.
  • Priority: Essential
  • Rationale: Branching on field values and question-dialog answers is pervasive in mask scripts.
  • Source: grit/tco_api/tc_api/tc_api_yacc.y (YACC_IF/YACC_ELSE_IF/YACC_ELSE, state machine zustand[][], state[] sized 41 — "damit funktioniert Schachteltiefe 40"); tc_api_lex.l ("IF", "ELSE IF", "ELSE", ==,!=,>,<); usage IF( '' == @tmp_frage_varname ) { … } in tc_bof/roh_func.gritx.
  • Verification: Test (nested IF/ELSE evaluation) + Analysis (nesting-depth bound).

FR-UI-011 — MMK built-in dialog control commands

  • Requirement: The MMK interpreter shall provide built-in dialog commands to rebuild/clear a dialog (dialog_neu), open a dialog/message box (dialog_box), pop a dialog (pop_dialog), switch the active field (feld_umschalten), toggle popup menus (pop_umschalten, pop_einschalten) and insert a surface (oberfl_einsetzen).
  • Priority: Essential
  • Rationale: These commands are how scripts programmatically open, refresh and navigate the dialog surface.
  • Source: grit/tco_api/tc_api/tc_api_lex.l ("dialog_neu", "feld_umschalten", "pop_dialog", "pop_umschalten"); tc_api_yacc.y tokens YACC_DIALOG_NEU/YACC_DIALOG_BOX/YACC_POP_DIALOG/YACC_FELD_UMSCHALTEN/YACC_POP_UMSCHALTEN/YACC_POP_EINSCHALTEN/YACC_OBERFL_EINSETZEN; tops/topsgrit/topsgrit.gritx (dialog_box(M_MASCHINE_KONF), dialog_box(DB_MELDUNG_LISTE)).
  • Verification: Test (script opens/refreshes a dialog).

FR-UI-012 — MMK built-in variable and utility commands

  • Requirement: The MMK interpreter shall provide built-in commands to assign/expand variables (copy, ecopy), call another mask's enter function (callEnterFunction) and split a file path into directory/file/extension (split_path).
  • Priority: Essential
  • Rationale: Scripts compose behaviour by chaining enter functions and manipulating string/path variables.
  • Source: tc_bof/roh_func.gritx (ecopy(tmp_Buttons, c_yesNoCancel), copy(#tmp_frage_varname = c_no), callEnterFunction(FUNC_FrageSpeichernDialog, …), split_path(tmp_Dir, tmp_File, tmp_Ext, @ST_RohrZeichnungDateiname)); C entry MMK_callEnterFunction in grit/src/c_oberfl.cpp.
  • Verification: Test (invoke each command and verify variable/dialog effect).

FR-UI-013 — MMK date/time formatting

  • Requirement: The MMK interpreter shall format date and time values into configurable representations, including TO_CHAR/TO_DATE, HHMM, HHMMSS, and year/day orderings (YYYYMMDD, DDMMYYYY, with optional time and . or / separators) and calendar-week (KW) output.
  • Priority: Optional
  • Rationale: Order/schedule dialogs must present dates and times in locale-appropriate formats.
  • Source: grit/tco_api/tc_api/tc_api_yacc.y (YACC_TO_CHAR/YACC_TO_DATE/YACC_HHMM/YACC_HHMMSS/YACC_POINT_DDMMYYYYHHMMSS/YACC_SLASH_YYYYMMDD/YACC_STRICH_KW_KJ and YACC_feld_to_time).
  • Verification: Test (format a known timestamp in several patterns).

FR-UI-014 — Alternative Python scripting and MMK debugger

  • Requirement: Where the customization Python interpreter is present, the system shall allow dialog logic to be driven by Python instead of MMK, and shall provide an MMK debug hook supporting step-into, step-over, step-out and continue.
  • Priority: Conditional
  • Rationale: Customization/automation and script debugging are optional developer/integrator capabilities layered on the interpreter. See [[23 - FR - Automation, Scripting & Integration]].
  • Source: grit/tco_api/tc_api/t_pars.hpp (pythonInterpreter(...)); tc_api_yacc.y (debugFunction, TcPythonInterpreter::GetCustomizationScriptInterpreter, mmkDebugHook, commands step_over/step_out/continue/step_into); function "python" in tc_mmk.fun.
  • Verification: Demonstration (single-step an MMK script via the debugger).

FR-UI-015 — Input field definition

  • Requirement: The system shall support input fields that carry a prompt text, an optional suffix, a display format, an input type and a configurable number of digits before and after the decimal separator.
  • Priority: Essential
  • Rationale: Numeric/technology parameter entry requires typed, formatted input fields.
  • Source: tco_grit_tools/convUtils/GritEingabeButton.h (m_promptPtr[GRIT_ANZAHL_SPRACHEN], m_anhangPtr[] suffix, m_form, m_eTyp, m_anzStellenVorKomma, m_anzStellenNachKomma, m_cursorEnterFunktionPtr/m_cursorExitFunktionPtr).
  • Verification: Inspection (field attributes) + Test (enter a value with a defined format).

FR-UI-016 — Input plausibility validation

  • Requirement: When a value is entered into an input field with a plausibility specification, the system shall validate the value against the specified rule — interval/range, enumerated set, alphanumeric, constant, or free-form — and shall reject values that do not conform.
  • Priority: Essential
  • Rationale: Preventing invalid parameter entry protects downstream CAD/CAM and NC generation.
  • Source: grit/src/c_plausi.cpp (#define INTERVALL 1, MENGE 2, ALPHANUM 3, KONSTANTE 4, FREIFORM 5; plausib(Oberfl*, Button*, …), switch(knoten[i].typ)).
  • Verification: Test (enter out-of-range and in-range values, confirm accept/reject).

FR-UI-017 — Scrollable finder list widget

  • Requirement: The system shall present scroll (FINDER) list widgets that display the rows produced by a mini_sql query and allow the user to scroll and select a row, which the associated script can then read.
  • Priority: Essential
  • Rationale: Catalog/selection dialogs (materials, patterns, tools, orders) rely on scrollable data lists.
  • Source: tco_grit_tools/convUtils/GritScrollButton.h; grit/tco_api/tc_api/t_finder.cpp/t_scroll.cpp/customScroll.cpp; finder targets FINDER_1..6 in tc_api_yacc.y; tc_bof/muster.gritx finder population.
  • Verification: Demonstration (populate and scroll a finder list, select a row).

FR-UI-018 — Popup menus and toolbars

  • Requirement: The system shall support popup menus/toolbars composed of text lines, bitmap lines and header lines, and shall allow scripts to switch them on/off.
  • Priority: Essential
  • Rationale: Command menus and icon toolbars are a primary navigation surface.
  • Source: grit/src/c_popup.hpp (class Popup : public Oberfl); tco_grit_tools/convUtils/GritFile.h (TeGritPopupZeileTyp: Text 1, Bitmap 2, Header 4); MMK pop_umschalten/pop_einschalten; grit/src/c_popein.cpp.
  • Verification: Demonstration (open a popup menu, toggle it via script).

FR-UI-019 — Per-mask tooltips

  • Requirement: Where tooltip masks are defined, the system shall display a tooltip for a UI element when the pointer hovers over it.
  • Priority: Optional
  • Rationale: Tooltips aid discoverability of toolbar/icon actions.
  • Source: tc_bof/tco_ttip.gritx (masks F_ToolTip_Flaeche, F_ToolTip_Info, F_ToolTip_Redraw, F_ToolTip_Show*, F_ToolTip_Profile*Degree, …); mouse-enter/exit handlers per button (FR-UI-004).
  • Verification: Demonstration (hover a toolbar icon, tooltip appears).

FR-UI-020 — Per-language button and prompt text

  • Requirement: The system shall store button help text and input-field prompt/suffix text as a set of per-language strings and shall display the string for the active UI language.
  • Priority: Essential
  • Rationale: All UI captions and help must be localizable without changing dialog structure.
  • Source: tc_bof/muster.gritx (<HelpTexts text_id> with repeated <HelpText text=""> slots); tco_grit_tools/convUtils/GritEingabeButton.h (m_promptPtr[GRIT_ANZAHL_SPRACHEN], m_anhangPtr[GRIT_ANZAHL_SPRACHEN]); GritDefines.h (GRIT_ANZAHL_SPRACHEN 30).
  • Verification: Test (switch language, confirm captions change).

FR-UI-021 — Interactive graphical object selection

  • Requirement: The system shall let the user select graphical objects interactively by point pick, by drag box, by select-all and by confirm, and shall support deselecting all.
  • Priority: Essential
  • Rationale: Every CAD/CAM editing command operates on a user-chosen set of objects.
  • Source: tc_selection/TcSelectionController.h (pick(x,y), isBoxActive, all(), confirm(), deselectAll(), getCaughtPosition); tc_selection/TcSelection.h (unique-id selection set).
  • Verification: Demonstration (pick, box-select and select-all objects in a drawing).

FR-UI-022 — Selection modes

  • Requirement: The system shall support selection modes of single (act after each pick), multiple-add (accumulate across picks) and multiple-invert (re-picking an already selected object removes it), and shall allow the active mode and box-change behaviour to be set.
  • Priority: Essential
  • Rationale: Different editing operations need different accumulation semantics.
  • Source: tc_selection/TcSelectionController.h (TeSelectionMode = e_selectSingle/e_selectMultipleAdd/e_selectMultipleInvert, setMode, setBoxChangeMode, setPreview).
  • Verification: Test (verify each mode's accumulation behaviour).

FR-UI-023 — Type-filtered selectors

  • Requirement: The system shall route selection through pluggable selectors so that only objects of the currently relevant type (e.g. CAD geometry, database/technology objects, tube-CAD objects) become selectable.
  • Priority: Essential
  • Rationale: A command that edits contours must not let the user pick technology markers, and vice versa.
  • Source: tc_selection/TcSelectionController.h (getSelector/removeSelector); sub-libraries tc_selection/sel_cad (TcCadContourSelector), sel_dbase, sel_tec, sel_tubeCad; tc_selection/TcSelector.cpp, TcDualSelector.
  • Verification: Test (attempt to pick a filtered-out object, confirm it is not selectable).

FR-UI-024 — Transaction-based undo/redo

  • Requirement: The system shall record editing actions within undo transactions (atomic or non-atomic) up to a configured maximum number of transactions, and shall reverse the most recent transaction on undo and re-apply it on redo.
  • Priority: Essential
  • Rationale: Reliable, grouped undo/redo is a baseline expectation of an interactive editor.
  • Source: tc_undo/undo_allg/TcUndoManager.h (TeType e_undo/e_redo, TcUndoManager(unsigned long t_maxSize), atomic vs non-atomic transactions, isAtomicTransactionInProgress, reset/resetUndoActions/resetRedoActions); TcUndoTransaction, TcObjCreatedAction/TcObjDeletedAction/TtObjModifiedAction.
  • Verification: Test (perform, undo and redo a multi-step edit).

FR-UI-025 — Undo/redo availability notification

  • Requirement: The system shall report whether undo and redo are currently possible and shall notify registered UI listeners when that availability changes.
  • Priority: Essential
  • Rationale: Undo/redo toolbar and menu items must enable/disable to match the stack state.
  • Source: tc_undo/undo_allg/TcUndoManager.h (isUndoPossible, isRedoPossible, isPossible(TeType[, anzahl]), isUndoRedoInProgress); TiUndoPossibleNotify.h.
  • Verification: Test (confirm undo/redo controls enable/disable as the stack changes).

FR-UI-026 — Unit-dependent value rendering

  • Requirement: The system shall render dimensional values in the configured measurement unit, applying the unit's name and decimal shift, and shall support switching the active unit (e.g. metric vs imperial).
  • Priority: Essential
  • Rationale: The suite ships metric and inch editions and must present values consistently.
  • Source: grit/src/c_unit.hpp (class GrUnit, uname, ushift "Anzahl, um die das Komma verschoben werden soll", setze_unit_index, finde_default_unit); config key GRITUNIT in tco_grit_tools/mask/grit_mask.ini and ini_files/*/*.org; separate *Inch.Org configs.
  • Verification: Test (switch unit, confirm displayed values convert).

FR-UI-027 — Multi-language UI with per-language fonts

  • Requirement: The system shall support up to 30 UI languages, including CJK scripts (Japanese/Kanji, Korean, Chinese), and shall select fonts from a table keyed by both language and screen resolution.
  • Priority: Essential
  • Rationale: A globally deployed product must render every supported language with correct glyphs at each resolution.
  • Source: tco_grit_tools/convUtils/GritDefines.h (GRIT_ANZAHL_SPRACHEN 30, KANJI 6, KOREAN 9, CHINESE_1 12, CHINESE_2 13); tco_grit_tools/mask/gritw/GRIT_ALL.DEF (sections [*_640], [6_640] Kanji, [9_640] Korean, [10_640] Polish, font[1..10]); config key GRITLANG.
  • Verification: Inspection (font tables) + Demonstration (render a CJK language).

FR-UI-028 — Keyboard interaction

  • Requirement: The system shall handle keyboard input including function keys, arrow keys, Home/End/PgUp/PgDn, Escape and Ctrl/Shift/Alt modifier combinations, and shall route them to the active mask's key handler.
  • Priority: Essential
  • Rationale: Keyboard navigation and shortcuts are required for efficient operation and accessibility.
  • Source: grit/tco_api/tc_api/keydef.h (K_PGUP/K_PGDN/K_HOME/K_END/K_UP..K_RIGHT, K_CTRL_*, K_ALT_S, K_SHIFT_*, K_F9..K_F12); grit/src/c_tasten.hpp (T_LEFT/T_RIGHT/T_UP/T_DOWN/T_HOME/T_END/T_PGUP/T_PGDWN/T_DEL/T_ESCAPE); mask KeyFunction.
  • Verification: Test (exercise key events, confirm handler invocation).

FR-UI-029 — GRIT runtime configuration

  • Requirement: The system shall read startup configuration selecting UI language, unit, colour table, font set, icon set, window size, window title, fixed-window and splash behaviour, and the mask (.olb) set to load.
  • Priority: Essential
  • Rationale: Each product edition and installation is parameterized entirely through these keys.
  • Source: tco_grit_tools/mask/grit_mask.ini and ini_files/*/Grit*.ORG/*.org (GRITLANG, GRITUNIT, GRITCOLOR, GRITFONT, GRITICON, GRITSIZE, GRITTITLE, FIXEDWINDOW, SPLASHWINDOW, MASK_OLB, GRITLANG_BASIC); grit/src/c_umgeb.hpp, readenv.h.
  • Verification: Inspection (config keys) + Test (change GRITLANG/GRITUNIT, confirm UI reflects it). See [[30 - External Interface Requirements]].

FR-UI-030 — Application-state UI toggles (GUI adapter)

  • Requirement: Where the modern GUI adapter is present, the system shall expose named application states that can be queried and set (checkable toggles such as show/hide overlays) and shall manage combo-box and named-action content bridged to the legacy GRIT layer.
  • Priority: Conditional
  • Rationale: The current Qt front-end reflects and controls legacy dialog state through the adapter; not every legacy/embedded configuration uses it.
  • Source: tc_guiAdapter/appState_util.h (setActiveAppState/getActiveAppState, setNameGuiAction, setComboBoxContent, setComboBoxDefaultLength/Angle/DoubleContent, state keys e.g. SHOW_PARTNUMBER); tc_guiAdapter/TcAppState*.h.
  • Verification: Test (toggle an AppState, confirm both GUI and legacy dialog update).

FR-UI-031 — Model-based action trigger bridge

  • Requirement: Where the Qt GUI is present, the system shall process user actions through action controllers that translate an application-model action trigger into the corresponding legacy ToPs/GRIT function and signal completion.
  • Priority: Conditional
  • Rationale: Menu/toolbar commands in the modern shell must invoke the legacy command implementations.
  • Source: GUI/Controller/TcActionController.h (triggerAction(TcActionTrigger&), "Anbindung an den (alten) ToPs", "signal Executed des action triggers"); GUI/Controller/TcActionGroupController.*, TcDialogActionController.*, TcControllerFactory.*.
  • Verification: Test (trigger a Qt action, confirm legacy function executes and completion is signalled).

5. External Interfaces (area-specific)

  • GRIT mask files — .gritx (XML, v2.63 UTF-8, authoring/inspection), .olb (binary, runtime), .a26 (legacy ASCII). Encoding handled per platform (WinNt/HpUx/Linux/Ansi) by GritAscii. See [[30 - External Interface Requirements]].
  • GRIT configuration files — .org/.ini startup keys (GRIT*), plus resource files GRIT_ALL.DEF (fonts), GRITCOL.*/rgb.txt (colours), icon and font directories.
  • Relational database (ODBC/SQL) — read/write via mini_sql through grit/tco_api/tc_odbc; tables surfaced include BEARBMUSTER, MUSTERGRUPPE_MITGLIED, WERKSTOFF, MATERIAL. Domain ownership of these tables lies with [[19 - FR - Tools, Machines, Materials & Technology]] / [[12 - FR - Part & Data Management]].
  • Python customization interpreter — optional scripting/debug back-end (TcPythonInterpreter). See [[23 - FR - Automation, Scripting & Integration]].
  • Qt GUI (ApplicationModel) — action/trigger and AppState bridge via GUI/Controller and tc_guiAdapter.

6. Assumptions & Constraints

  • GRIT is a long-lived legacy C++ framework (origins ~1989, GfT/Graphics mbH) retained across all editions; the modern Qt shell wraps rather than replaces it. Cross-cutting constraints belong in [[50 - Constraints & Assumptions]].
  • The MMK interpreter is a bespoke lex/yacc language with fixed limits (e.g. IF nesting depth 40, GRIT_MAX_LINELEN 131072, up to 10 fonts, up to 30 languages, six finder lists). These are hard constraints, not tunables.
  • Identifiers, comments and configuration are predominantly German; entity names in this document keep the original term.
  • On Windows GritInt is 16-bit (short), affecting numeric ranges of mask coordinates/indices — a platform constraint.
  • Performance, responsiveness and localization-completeness expectations are captured in [[40 - Non-Functional Requirements]].

7. Open Questions & Ambiguities

  • MMK built-in command dispatch. copy, ecopy, callEnterFunction and split_path appear only inside mask CDATA, not as C++ string literals in the searched sources; their dispatch table (as opposed to the yacc-handled keywords) could not be located and may live in generated code or a header not fully read. The exact parameter semantics of ecopy vs copy are inferred (ecopy = assign/expand a default; copy = numeric/field assignment) (inferred).
  • Language count discrepancy. GRIT_ANZAHL_SPRACHEN = 30 but GRIT_ANZAHL_SPRACHEN_261 = 10; the relationship between the legacy 10-language limit and the current 30 (and how existing 10-language .olb files are migrated) is unclear.
  • Runtime authority. Whether the legacy GRIT masks (.olb) or the Qt ApplicationModel is authoritative for a given dialog at runtime — and how the two are kept in sync beyond AppStates/actions — was not fully determined.
  • tc_tab module. tc_tab (tab_allg/tab_dbup/tab_prnt/tab_rewe) appears to concern database tables/table upgrades and printing rather than GRIT interaction; it likely belongs to [[12 - FR - Part & Data Management]] or [[21 - FR - Visualization, Viewing & Plotting]]. Flagged for the owning analyst.
  • tc_text scope overlap. tc_text provides vector stroke fonts (kaFont) used for drawing/annotation text; that overlaps with CAD text rendering ([[10 - FR - CAD Geometry & Drawing Editing]] / [[21 - FR - Visualization, Viewing & Plotting]]) — only its role as the UI font/glyph source is claimed here.
  • muster.gritx domain content. The BEARBMUSTER/MUSTERGRUPPE (processing-pattern) data driven by that mask is technology-domain content owned by [[19 - FR - Tools, Machines, Materials & Technology]]; only the dialog/finder mechanics are in scope here.
  • Selection–undo coupling. Whether interactive selection state participates in undo transactions (e.g. selection restored on undo) was not confirmed from the headers read.
