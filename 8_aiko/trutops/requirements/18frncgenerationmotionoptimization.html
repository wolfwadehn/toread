FR — NC Generation & Motion Optimization

Reverse-engineered requirement draft — derived from static analysis of legacy source, NOT an authoritative specification. Treat SHALL statements as reconstructed intent.

1. Purpose & Scope

This document specifies the functional requirements for the NC Generation & Motion Optimization area of the TruTops CAD/CAM suite. This area turns a technologically finished CAD/CAM layout (a sheet or tube populated with parts, tools, lead-ins, micro-joints and machining operations) into an executable, controller-specific NC program, and it optimizes the order and geometry of the machine motions so the program runs in the shortest realistic time without collisions or re-cutting.

The area covers five tightly-coupled capability clusters:

  1. Processing-order optimization — sequencing of cuts/hits/punches as a constrained Travelling-Salesman-style (TSP) problem, honouring machining dependencies (tc_constrainedTspSolver).
  2. Way / travel optimization — ordering the individual objects of one tool/operation for minimum traverse time given machine dynamics (tc_wopt, ant-colony algorithm).
  3. Rapid-traverse path finding — collision-free and already-cut-avoiding traverse geometry between operations (tc_pathf).
  4. Cycle / processing-time estimation — physically-based movement-time calculation from acceleration/velocity/jerk ramps (tc_wegzeit).
  5. NC post-processing & auxiliary output — emission of controller-specific NC code from cycle/format definitions, plus setup plans (Einrichteplan), multiple-up (Mehrfachnutzen) generation, and machine-simulation data (tc_nc, tc_mfn, tc_liftMachineSimulationData).

Editions served: ToPs 300 (punching/nibbling), ToPs 100 (laser cutting), and ToPs Tube (tube/profile cutting). Each edition has its own optimizer configuration and NC cycle/format tables keyed by machine type and controller. Bending NC output (ToPs 600, Bend.NC_FORMATE) is out of scope and owned by [[16 - FR - Bending (ToPs 600)]].

Domain terms are defined in [[04 - Domain Model & Glossary]]; interface/format details are consolidated in [[30 - External Interface Requirements]]; performance/quality targets in [[40 - Non-Functional Requirements]].

2. Capability Overview

  • Constrained processing-order optimization — rearranges all machining operations of an optimization area into a short total-processing-time sequence using a dependency graph plus an external constrained-TSP solver (nearest-neighbour + Ant-Colony + post-optimizer).
  • Selectable optimization strategies — tool-change-optimal, part-complete, or row-wise processing; part-wise vs. row-wise cut-out (Austrennen); configurable start corner and meander direction.
  • Dependency & constraint handling — inner-before-outer contour, removal/cut-out operations last, micro-joint-as-removal, deburring (Entgraten) dependencies, trim-edges-first (Besäumen), clamping-area (Aufspannbereich) grouping; automatic check-and-repair of violated sequences.
  • Way/time optimization per tool — orders the hits/cuts of one tool for minimum traverse time using a machine-dynamics model (per-axis acceleration/velocity, C-axis polynomial).
  • Rapid-traverse path finding — shortest collision-free traverse between two points that respects minimum distance to contours and treats already-processed contours as obstacles.
  • Physically-based cycle-time estimation — jerk-limited acceleration ramps for linear and circular segments, exact-stop and no-stop variants, with optional logging.
  • Controller-specific NC generation — assembles NC code from machine/controller-keyed cycle (Zyklus), instruction and output-format definitions, including customer cycles and a fallback read strategy.
  • Setup & auxiliary documentation — Einrichteplan (setup plan) with sheet/part graphics, tool and technology-table lists, exported as HTML/PDF.
  • Automatic multiple-up (Mehrfachnutzen/MFN) generation — derives MFN blocks from arbitrary sheet layouts for punch transfer/unload strategies.
  • NC transfer & post-processing — automatic transfer to the machine (NcLink), post-processing programs, and RMT storage.
  • Interactive optimization & motion simulation — manual re-ordering, micro-joint/bridge assignment, dynamics editing, and forward/backward processing-simulation playback.
  • Machine-simulation data export — generation of a machine-simulation data file (zip) from unloading/lift data.

4. Functional Requirements

FR-NC-001 — Optimize processing order for minimum total processing time

  • Requirement: The system shall rearrange the machining operations (Bearbeitungen) of an optimization area into a sequence that yields a preferably short total processing time.
  • Priority: Essential
  • Rationale: Cutting/punching sequence dominates machine cycle time; minimizing traverse and tool-change effort is the core value of the CAM optimizer.
  • Source: tc_constrainedTspSolver/TcSortProcessings.h (sortProcessings(TcOptimierungsbereich*), class comment); tc_wopt/do_opti.cpp; gritx tec_opti.gritx (FUNC_STZ_StartOptimierung, FUNC_STZ_OkOptimierung), tel_opt.gritx (F_MenueOptimierungBerechnen).
  • Verification: Analysis / Test (compare traverse-time metric before/after on a reference layout).

FR-NC-002 — Selectable processing-order strategy

  • Requirement: The system shall allow the user to select the processing-order strategy from at least: tool-change optimal (WERKZEUGWECHSELOPTIMAL), part-complete (TEILEKOMPLETT), and row-wise processing (REIHENWEISEABARBEITEN).
  • Priority: Essential
  • Rationale: Different production goals (minimize tool changes vs. finish parts early vs. row throughput) require different sequencing objectives.
  • Source: tc_constrainedTspSolver/TcSortProcessings.h (enum TeSortOptimierStrategie, setKindOfSort); SQL Laser.OPTIMIERER / Punch/Tube optimizer tables (OPT_STR_*); gritx tec_opti.gritx (FUNC_OptiSetStrategie, O_BearbeitungStrategieSel).
  • Verification: Demonstration (each strategy produces the expected sequencing pattern).

FR-NC-003 — Selectable cut-out (separation) mode

  • Requirement: Where a part must be separated from the sheet, the system shall support selecting part-wise (TEILEWEISE) or row-wise (REIHENWEISE) cut-out of the outer contour.
  • Priority: Conditional
  • Rationale: Separation strategy affects sheet stability and unloading; it is edition/machine dependent.
  • Source: tc_constrainedTspSolver/TcSortProcessings.h (enum TeSortTrennweise, setKindOfRemoving).
  • Verification: Demonstration.

FR-NC-004 — Honour machining dependencies during sequencing

  • Requirement: While optimizing the processing order, the system shall enforce machining dependencies including inner-contour-before-outer-contour, removal/cut-out operations after their part's contours, and deburring (Entgraten) predecessor relations.
  • Priority: Essential
  • Rationale: Violating these dependencies produces unmachinable or scrapped parts (e.g. cutting a part free before its inner features are done).
  • Source: tc_constrainedTspSolver/TcDependencyGraph.{h,cpp}, TcSortProcessings.h (setTopsDependencies, setWeakDependencies, enum TeToolUsage = INNER_BEFORE_OUTER_CONTOUR/PARTWISE); TcProcessingInformationProvider.h (getProcessingsWith/WithoutEntgratenDependency, getOuterContourProcessings*).
  • Verification: Test (assert ordering constraints hold in solver output).

FR-NC-005 — Check and repair constraint-violating sequences

  • Requirement: If a processing sequence violates its dependency constraints, then the system shall detect and repair the sequence to a valid processing order.
  • Priority: Essential
  • Rationale: Manual reordering, imported plans, or post-optimization can produce invalid orders that must be corrected before NC output.
  • Source: tc_constrainedTspSolver/TcCheckAndRepairProcessingSequence.{h,cpp} (uses TsGeoAlgorithmsKernelProcessingOrder).
  • Verification: Test (feed an invalid order, verify repaired order satisfies dependencies).

FR-NC-006 — Respect configured part order

  • Requirement: Where a part order (Teilereihenfolge) is configured, the system shall sequence the operations of each part according to that order.
  • Priority: Conditional
  • Rationale: Users control the production order of parts for downstream sorting/handling; the optimizer must not override it.
  • Source: tc_constrainedTspSolver/TcProcessingInformationProvider.h (getProcessingsConsideringPartOrder, m_partOrder); TcSortProcessings constructor takes std::list<TcTeileReihenfolgeObject*>; gritx tec_opti.gritx (M_TeileRFolgeAendern, M_SRT_TEILE_FOLGE_RICHTUNG_V*).
  • Verification: Demonstration.

FR-NC-007 — Micro-joint treated as removal operation

  • Requirement: Where micro-joints (Mikrostege) are used, the system shall optionally treat the micro-joint operation as the part's removal operation, separately configurable for punching and laser.
  • Priority: Conditional
  • Rationale: Micro-joints keep parts in the skeleton; whether the joint break counts as the removal step changes the last-operation sequencing.
  • Source: tc_constrainedTspSolver/TcSortProcessings.h (setPunchMicrojointIsRemovalProcessing, setLaserMicrojointIsRemovalProcessing); TcProcessingInformationProvider.h (same setters); gritx tec_opti.gritx (O_LaserMJIsRemoval); tel_opt.gritx (M_MicrojointParameter, F_MicroKonturPara, F_MicroTeilPara).
  • Verification: Demonstration.

FR-NC-008 — Trim-edges-first option

  • Requirement: Where edge trimming (Besäumen) is present, the system shall support processing the trim operations before all other operations.
  • Priority: Optional
  • Rationale: Trimming the sheet edge first can improve sheet handling and remnant management.
  • Source: tc_constrainedTspSolver/TcSortProcessings.h (setdoBesaeumenFirst); gritx tec_opti.gritx (O_DoBesaeumenFirst, O_DoBesaeumenFirstText).
  • Verification: Demonstration.

FR-NC-009 — Constrained-TSP solving with metaheuristics

  • Requirement: The system shall solve the processing-order sequencing as a Hamiltonian-path problem over the dependency graph using a nearest-neighbour construction and an Ant-Colony metaheuristic, followed by a post-optimization pass.
  • Priority: Essential
  • Rationale: The problem is combinatorial (TSP-class); heuristic solving is required to obtain good sequences in acceptable time.
  • Source: tc_constrainedTspSolver/TcNextNeighbourSolverQuadTree.{h,cpp}, TcPostOptimizer.{h,cpp}; tc_wopt/AntAlgorithm/ (TcACOStrategie.h "TSP mit Hilfe eines Ameisenalgorithmus", TcSolver.h, TcMMASPheromonUpdateStrategie.h).
  • Verification: Analysis (inspect solver pipeline and result quality on benchmark).

FR-NC-010 — Configurable optimization quality/level

  • Requirement: The system shall provide a configurable optimization level that tunes the metaheuristic parameters (number of ants, next-neighbour count, runs per ant, pheromone factors) to trade solution quality against runtime.
  • Priority: Optional
  • Rationale: Users need to balance optimization time against sequence quality for large layouts.
  • Source: tc_wopt/AntAlgorithm/TcAntSettings.h (M_ant_number_of_ants, M_ant_alpha/beta/rho, initialize(int t_optimizationLevel)).
  • Verification: Test (verify parameter sets change with level).

FR-NC-011 — "Small NC program" optimization mode

  • Requirement: Where the small-NC-program option is enabled, the system shall bias the sequencing to reduce the size/number of NC blocks emitted.
  • Priority: Optional
  • Rationale: Older/limited controllers benefit from compact NC programs (fewer subroutine calls / repetitions).
  • Source: tc_constrainedTspSolver/TcSortProcessings.h (setOptimizeForKleinesNCProgramm); gritx tec_opti.gritx (O_Kleines_NC_Programm).
  • Verification: Demonstration.

FR-NC-012 — User-cancellable optimization

  • Requirement: While optimization is running, the system shall allow the user to cancel it and shall report a cancelled result without corrupting the existing plan.
  • Priority: Essential
  • Rationale: Optimization can be long-running; the operator must retain control.
  • Source: tc_constrainedTspSolver/TcSortProcessings.h (enum TeOptimizationResult::e_canceledByUser); gritx progress/cancel dialogs.
  • Verification: Test.

FR-NC-013 — Way/travel-time optimization of one tool's objects

  • Requirement: The system shall order the objects (hits/cuts) of a single tool/operation so as to minimize the total traverse time from a given entry point, searching in forward, backward and ant-based variants and keeping the fastest result.
  • Priority: Essential
  • Rationale: Within one tool, the traverse order between positions is itself a short-path problem that materially affects cycle time.
  • Source: tc_wopt/tc_wopt.h/do_opti.cpp (Weg_Zeit_Optimierer::time_optimize_forw/backw/ant, get_fastest_start_point); gritx aLasOptimize.gritx (aLasSetPosiwayAuto, aLasSetPosiwayManu, aLasEndPosifolgeManuell).
  • Verification: Analysis / Test.

FR-NC-014 — Machine-dynamics-aware traverse-time model

  • Requirement: The system shall compute traverse time using a machine-dynamics model comprising per-axis acceleration and velocity limits and a polynomial model for the C-axis.
  • Priority: Essential
  • Rationale: Traverse ordering must reflect real machine kinematics, not just Euclidean distance, to be time-accurate.
  • Source: tc_wopt/wopt_dat.h (class Wopt_Dynamik: acceleration, velocity, t_grenz, s_grenz, formel_grad_C, koeff_C[10], calculate_time); gritx aLasOptimize.gritx (aLasSetDynamik, aLasSetBeschleunigung).
  • Verification: Analysis.

FR-NC-015 — Collision-free rapid-traverse path finding

  • Requirement: The system shall compute the shortest rapid-traverse path between two points that avoids all registered contours while maintaining a configurable minimum distance from them.
  • Priority: Essential
  • Rationale: Rapid moves must not collide with parts, clamps or already-cut geometry.
  • Source: tc_pathf/TcPathfinder.h (calculatePath, connectTwoPoints, findCollisions, getMinDistanceFromHoles, isTooClose, setClampsContourList, setBorderContour).
  • Verification: Test (verify path clears obstacles by ≥ tolerance).

FR-NC-016 — Treat already-processed contours as obstacles

  • Requirement: When a contour has been processed and marked as creating a hole, the system shall treat that contour as an obstacle for subsequent rapid-traverse path finding to avoid crossing already-cut areas.
  • Priority: Essential
  • Rationale: Traversing over an already-cut opening risks head/part collision and tipping.
  • Source: tc_pathf/TcPathfinder.h (addContour(..., bool t_holeWhenDone), calculatePath(bool t_ignoreHoleForSelf), isInsideContour(..., t_onlyWithHole)).
  • Verification: Test.

FR-NC-017 — Configurable path-finding parameters

  • Requirement: The system shall allow configuration of path-finding behaviour including calculation timeout, per-turn cost, quality (1..100), contour-follow level (0..100), whether border crossing is allowed, and maximum path length between points.
  • Priority: Conditional
  • Rationale: Trade-offs between path quality and computation time, and machine-specific rules (border crossing), must be tunable.
  • Source: tc_pathf/TcPathfinder.h (setTimeout, setTurnCost, setQuality, setContourFollowLevel, setBorderCrossAllowed, setMaxPathLength, setUseAlternativedistance).
  • Verification: Inspection / Test.

FR-NC-018 — Physically-based cycle-time estimation

  • Requirement: The system shall estimate the movement time of linear and circular path segments from jerk-limited acceleration ramps, supporting both exact-stop (Genauhalt) and continuous (no-stop) segment transitions.
  • Priority: Essential
  • Rationale: Reliable cycle-time estimates are needed for scheduling, costing and comparison of optimization results.
  • Source: tc_wegzeit/ (TcWegZeitAbstract.h bridge design; TcWegZeitLinear, TcWegZeitCircular; TcRampeGenauhalt "Geschwindigkeit am Anfang und Ende null", TcRampeKeinHalt "gegebener Endgeschwindigkeit"; getBahnGeschwindigkeit/-Beschleunigung/-Ruck).
  • Verification: Analysis / Test (compare estimated vs. measured times).

FR-NC-019 — Time-calculation logging

  • Requirement: Where time-calculation logging is enabled, the system shall record the details of movement-time calculations to a log stream.
  • Priority: Optional
  • Rationale: Diagnostics for validating and tuning the time model.
  • Source: tc_wegzeit/TcTimeCalculationLogger.{h,cpp} ("globaler Datei-Stream zur Protokollierung von Zeitberechnungsbelangen").
  • Verification: Inspection.

FR-NC-020 — Generate controller-specific NC program

  • Requirement: When NC generation is triggered for a finished layout, the system shall produce an executable NC program targeting the assigned machine's controller and store it as an NC file in the object management.
  • Priority: Essential
  • Rationale: Emitting runnable NC code is the terminal deliverable of the CAM chain.
  • Source: tc_nc/nc_cont/nc25.hpp/nc25.cpp (class NCContainer: nccNewOpenOutStream, nccWriteBlockStart/Satz/Ende, nccCloseDelOutStream_write2File; controller SIN840D references); gritx tec_nc.gritx (M_NcErzeugen, FUNC_STZ_StartNcErzeugen), tel_nc.gritx, roh_nc.gritx.
  • Verification: Test (generate NC for a reference part; verify against controller syntax).

FR-NC-021 — Cycle/format-driven NC emission keyed by machine and controller

  • Requirement: The system shall render NC blocks using cycle (Zyklus), NC-instruction and output-format definitions selected by machine type, controller and controller version.
  • Priority: Essential
  • Rationale: Each controller/machine emits different code; definitions are data-driven so new machines can be supported without code changes.
  • Source: SQL Punch/Laser/Tube.NCZYKLEN (NC_STEUERUNG, NC_MATYP, NC_MANAME, NC_ST_VERSION, NC_ZYKLUS, NC_SATZ, NC_AUSGABE_TYP), *.AUS_FORMAT (AUS1_FORMAT, AUS1_FAKTOR, AUS1_MASSSYSTEM), *.NC_MASCHINE, *.NC_KOPFTAB_MASCHINE; tc_nc/zyklen/ (TcZyklus, TcFormat, TtNCInstructionManager, TtZyklusFilter) keyed by TcMaschinenSchluessel (tc_maschine/TcMaschinenSchluessel).
  • Verification: Inspection / Test.

FR-NC-022 — Fallback read strategy for cycle/instruction data

  • Requirement: If no cycle/instruction records are found for the given machine access key, then the system shall perform a second read using fallback parameters before failing.
  • Priority: Conditional
  • Rationale: Robustness against incomplete machine configuration; ensures a usable default set of cycles.
  • Source: tc_nc/zyklen/TtNCInstructionManager.h, TtZyklusFilter.h ("Schlägt das Lesen ... fehl ... erfolgt ein zweiter Lesevorgang mit Fallback-Parametern"; deselectable).
  • Verification: Test (query with a key having no records; verify fallback used).

FR-NC-023 — Support customer cycles alongside NC cycles

  • Requirement: The system shall support customer-defined cycles (Kundenzyklen) in addition to standard NC cycles when generating NC code.
  • Priority: Conditional
  • Rationale: Sites extend controllers with their own subroutines/macros that must be emittable.
  • Source: SQL *.NC_KUNDE, *.ZYKLUS_NAME; tc_nc/zyklen/TtZyklusContainer (TtZyklusContainer<TwCString> for customer cycles vs. <long> for NC cycles).
  • Verification: Demonstration.

FR-NC-024 — NC generation dialog metadata

  • Requirement: When generating an NC program, the system shall let the user specify program identification and documentation metadata including program number, operator (Bearbeiter), company (Firma), and free-text remarks.
  • Priority: Essential
  • Rationale: NC programs must carry traceable identification and shop-floor notes.
  • Source: gritx tec_nc.gritx/tel_nc.gritx/roh_nc.gritx (O_Nc_ProgNr/O_NcProgNr, O_Nc_Bearbeiter/O_NcBearbeiter, O_Nc_Firma/O_NcFirma, O_Nc_Bemerkung_1/2, M_NC_RemarksExtended).
  • Verification: Demonstration.

FR-NC-025 — Generate setup plan (Einrichteplan) documentation

  • Requirement: Where setup-plan output is requested, the system shall generate an Einrichteplan containing sheet/part graphics, tool and technology-table (LTT) lists and general/production data, and shall export it as HTML and/or PDF.
  • Priority: Conditional
  • Rationale: The operator needs a printable setup document to load tools/sheet and run the program.
  • Source: gritx tec_nc.gritx/tel_nc.gritx/roh_nc.gritx (O_Nc_CreateEin, O_Nc_CreateHtml, O_Nc_CreatePdf, O_Nc_EpTafelGrafik, O_Nc_EpEtGrafik, O_Nc_EpLttListe, O_Nc_EpAllgDaten); tc_nc/nc_cont EPI (EinrichtePlanInformationen), F_NcErzeugenEinrichteplan.
  • Verification: Demonstration.

FR-NC-026 — Sheet/skeleton removal and unloading in NC

  • Requirement: The system shall emit the auxiliary machine operations for scrap/skeleton stripping (Abstreifen), part push-out/unloading (Ausschieben/Entladen), and sheet repositioning (Nachsetzen) as configured for the machine.
  • Priority: Conditional
  • Rationale: A complete NC program must include material-handling motions, not only cutting.
  • Source: gritx tec_nc.gritx (M_BlechAbstreifen, M_ManualScrapSkeletonRemoval, O_AbstreifStrategie*, O_Nc_AusschiebeUpTransfer, O_Nc_BeladenVorbereiten), tel_nc.gritx (O_Entladen); tc_nc/nc_cont UNL (PrepareSheet/Part-UNLoad), RPO (RePositionInfo/Nachsetzen); gritx aPnLasOptimize.gritx (aPnLasChangeNsetPos, aPnLasChangeNsetWeg).
  • Verification: Demonstration.

FR-NC-027 — Automatic transfer and post-processing of NC output

  • Requirement: Where automatic transfer is enabled, the system shall transfer the generated NC program to the machine/DNC and optionally run a configured post-processing (Nachbearbeitung) program, including storing the program in RMT form.
  • Priority: Conditional
  • Rationale: Integrates CAM output with machine loading and downstream tooling without manual file handling.
  • Source: gritx aTcoNc.gritx (FUNC_NcNachbereitungAuftrag: winexec ... ST_LAS_NcNachbearbeitungPrg, FUNC_NcProduktionePlanAuftrag); tec_nc.gritx (O_Nc_AutoTransfer); roh_nc.gritx (O_Nc_NachbearbeitungPrg, O_NcAlsRmtSpeichern); ini ToPs400.Org (TC_NCLINK_LANGUAGE_INI → NcLink). See [[30 - External Interface Requirements]].
  • Verification: Demonstration.

FR-NC-028 — Automatic multiple-up (Mehrfachnutzen) generation

  • Requirement: The system shall automatically generate multiple-up (MFN) blocks from an arbitrary sheet layout, offering strategies that trade minimum block count against non-interleaved blocks suitable for GTS/flap unloading.
  • Priority: Conditional
  • Rationale: Grouping identical parts into MFN blocks shortens NC programs and enables block-wise unloading on punch machines.
  • Source: tc_mfn/TcMFNGenerator.h ("Automatischer Mehrfachnutzengenerator", enum TeMFNGeneratorStrategy = e_GeneratorStrategy_MinimumNumberOfBlocks, non-interleaved variant), TcMFNBlockBuilder, mk_mfn.{h,cpp}; gritx tec_opti.gritx (F_SRT_MFN_REIHEN_KOMPLETT).
  • Verification: Analysis / Test.

FR-NC-029 — Interactive re-ordering and motion simulation

  • Requirement: The system shall provide interactive optimization tools to manually reorder processings/parts, assign micro-joint/bridge patterns (Stegbelegung), edit dynamics, and play the processing sequence forward and backward in a motion simulation.
  • Priority: Conditional
  • Rationale: Operators must be able to review and correct the automatic result and visually verify the motion before running the machine.
  • Source: gritx tel_opt.gritx (F_MenueOptimierungUmordnen, F_SteuerOptimierungManu, O_bearStegeSetzen/Auswahl/Sichern); aLasOptimize.gritx (aLasChooseStegbelegung, aLasSaveStegbelegung, aLasOptidataManuell); aPnLasOptimize.gritx (aPnLasBackSimulation, aPnLasContinueHoldSimulation, aPnLasCancelSimulation).
  • Verification: Demonstration.

FR-NC-030 — Tube-specific processing optimization

  • Requirement: Where the tube edition is active, the system shall optimize the processing order using tube-specific field/grid parameters distinguishing arced and flat regions of the tube.
  • Priority: Conditional
  • Rationale: Tube cutting has a different working geometry (rotational C-axis, arc vs. flat faces) than flat-sheet, requiring its own optimizer configuration.
  • Source: SQL Tube.ROHROPTIMIERER (ROPT_FIELDSMIN/MAX_ARC, ROPT_FIELDSMIN/MAX_FLAT, ROPT_GRIDMODE_ARC/FLAT, ROPT_DIRECTION_ARC, ROPT_STEUERUNG); gritx roh_nc.gritx (M_NcSptTube, O_NcOffsetA). See [[15 - FR - Tube & Profile Machining (ToPs 400)]].
  • Verification: Inspection / Test.

FR-NC-031 — Machine-simulation data export

  • Requirement: The system shall be able to export a machine-simulation data file (compressed archive) derived from the layout's unloading/lift data for use by external machine-simulation.
  • Priority: Optional
  • Rationale: Off-line machine simulation validates handling/motion before production.
  • Source: tc_liftMachineSimulationData/createLiftSimulationDataZip.{h,cpp} ("aus TruTops-Liftdaten eine Maschinensimulationsdatei zu erstellen"), createSuccerSimulationGraphic.cpp.
  • Verification: Demonstration.

FR-NC-032 — Configurable start corner and processing direction

  • Requirement: The system shall allow configuring the start corner (Startecke) and processing direction (standard/meander) from which sequencing begins.
  • Priority: Conditional
  • Rationale: Start corner and traversal direction influence unloading side, thermal distribution and traverse effort.
  • Source: SQL *.OPTIMIERER (OPT_STR_STAND_T_STARTECKE, OPT_STR_STAND_T_RICHT, OPT_STR_MEAND_T_RICHT); gritx tec_opti.gritx (FUNC_OptiSetRichtung, FUNC_OptiSetTextStartecke, M_OPTI_MN_RICHT_1..6).
  • Verification: Demonstration.

5. External Interfaces (area-specific)

  • NC program files — controller-specific NC text output (e.g. Siemens SIN840D dialect), written to the object management/file system. See [[30 - External Interface Requirements]].
  • NcLink / DNC transfer — NC transfer service configured via TC_NCLINK_LANGUAGE_INI (registry-referenced); target of automatic transfer (FR-NC-027).
  • Database (SQL Server / MDB, per edition) — cycle, instruction and format tables: Punch/Laser/Tube.NCZYKLEN, .NCZYKLUS_STV, .AUS_FORMAT, .NC_KUNDE, .ZYKLUS_NAME, Punch.NC_MASCHINE, .NC_KOPFTAB_MASCHINE, Common.NC_KOPF_TABELLEN[_600], Common.NC_TAB_GRUPPEN; optimizer configuration Laser/Punch.OPTIMIERER, Tube.ROHROPTIMIERER.
  • Setup-plan documents — HTML and PDF Einrichteplan output (FR-NC-025).
  • Machine-simulation data — compressed simulation-data archive for external machine simulation (FR-NC-031).
  • CAD/CAM layout model — consumes the technology model (Bearbeitung, Kontur, Werkzeug, Tafel, Aufspannbereich) produced by [[13 - FR - Punching (ToPs 300)]], [[14 - FR - Laser Cutting (ToPs 100)]], [[15 - FR - Tube & Profile Machining (ToPs 400)]] and [[17 - FR - Nesting & Palletizing]].
  • Machine/tool/technology definitions — via tc_maschine (shared with [[19 - FR - Tools, Machines, Materials & Technology]]).

6. Assumptions & Constraints

  • A1. The processing model (Bearbeitung/Kontur/Werkzeug graph, lead-ins, micro-joints, clamping areas) is assumed complete and technologically valid before optimization and NC generation run; this area sequences and emits, it does not create technology. (inferred)
  • A2. Every target machine has a consistent set of cycle/instruction/format records keyed by machine type + controller + version; otherwise the fallback read strategy (FR-NC-022) applies. See [[19 - FR - Tools, Machines, Materials & Technology]].
  • C1. The traverse-time and cycle-time models are approximations of real machine kinematics (per-axis accel/velocity, jerk ramps, C-axis polynomial); absolute accuracy depends on correct machine-dynamics parameters. (inferred)
  • C2. Processing-order optimization is a heuristic (constrained TSP via nearest-neighbour + Ant-Colony); results are near-optimal, not provably optimal, and depend on the optimization level (FR-NC-010).
  • C3. Optimizer/NC behaviour is edition- and controller-dependent (ToPs 300 / 100 / Tube), reflected in per-edition SQL tables and gritx masks.
  • C4. Legacy code (nc25*) uses German identifiers and RogueWave/Tw* collection types; German domain terms are retained per [[04 - Domain Model & Glossary]].
  • Cross-cutting constraints and assumptions are consolidated in [[50 - Constraints & Assumptions]]; non-functional targets (optimization time, NC correctness) in [[40 - Non-Functional Requirements]].

7. Open Questions & Ambiguities

  1. MFN ownership boundary. tc_mfn (Mehrfachnutzengenerator) sits between nesting and NC; it derives multiple-up blocks from a layout. Whether MFN generation is triggered as part of nesting ([[17 - FR - Nesting & Palletizing]]) or as an NC-preparation step could not be conclusively determined and may be double-counted with that area.
  2. tc_lift scope. tc_lift (Sauger/suction-cup and holding-device modelling) appears to belong to Palletizing/Unloading rather than NC; only tc_liftMachineSimulationData (simulation-file export) was documented here (FR-NC-031). The exact owner of tc_lift should be confirmed with [[17 - FR - Nesting & Palletizing]].
  3. Optimizer version 2. gritx tec_opti.gritx references M_OPTIMIZER_VERSION_2 / FUNC_STZ_OkOptimierung_V2 and OPT_ST_VERSION; the functional differences between optimizer v1 and v2 (and which editions default to which) were not determined from source.
  4. Common-cut / shared-cut sequencing. No explicit common-cut (gemeinsames Schneiden) handling was found in the TSP solver headers surveyed; whether it is modelled as a dependency, elsewhere, or not at all is unresolved.
  5. Exact NC dialects supported. Only SIN840D (Siemens) was directly observed in nc25.hpp; the full set of controllers driven by the data-driven cycle/format tables (NC_STEUERUNG values) was not enumerated.
  6. Post-optimization use policy. setUsePostOptimization and the TcPostOptimizer exist, but the default/automatic conditions under which post-optimization runs (vs. is skipped for performance) were not established.
  7. Time-model calibration source. Whether the tc_wegzeit ramp parameters (Bahngeschwindigkeit/-beschleunigung/-ruck) are read from machine DB records or hard-coded per machine class was not confirmed.
  8. tc_wegzeit vs. tc_wopt dynamics duplication. Both modules model machine dynamics/time; the division of responsibility (segment-level physical time vs. sequencing cost) is inferred and should be verified.
