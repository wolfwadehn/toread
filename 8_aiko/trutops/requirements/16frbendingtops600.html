FR — Bending (ToPs 600)

Reverse-engineered requirement draft — derived from static analysis of legacy source, NOT an authoritative specification. Treat SHALL statements as reconstructed intent.

[!info] Detailed Bending sub-suite (Tier 2) The bending NC code generation and the TruBend Cell 7000 automated cell — the areas this document records as delegated to ToPs 600 (see FR-BEND-030 and Open Questions) — are now detailed in a Tier-2 sub-suite under Requirements/ToPs 600 Bending/, reverse-engineered from the ToPs 600 Bend SQL data contract and the BendAPI surface. Start at [[16.0 - Bending — Module Overview]]; the automated cell is covered by the [[16.2 - Cell7000 — Overview|Cell7000 sub-suite]] and NC output by [[16.1 - Bending — NC Code Generation]].

1. Purpose & Scope

This document specifies the functional requirements for the bending / press-brake programming area of the TruTops CAD/CAM suite, marketed as ToPs 600. The area lets a programmer describe the bends of a sheet-metal part, obtain the correct flat pattern (Abwicklung) by applying bend-deduction factors (Abkantfaktoren), assign bend tools (Biegewerkzeuge) — punch (Oberwerkzeug/Stempel) and die (Unterwerkzeug/Gesenk) — and create custom bend-tool geometry with the bend tool assistant (Biegewerkzeugassistent).

The bend technology draws its factors, tool catalogue and machine configuration from the ToPs 600 bend database (SQL Server Bend schema plus Common.AKF_BENDFACTORS). Material names known to ToPs 100/300 are mapped onto their ToPs 600 equivalents before database look-up.

Editions served: ToPs 600 (bending CAD/CAM; Full, Lite and Basic password variants), with the ToPs 600 bend database as the technology backbone.

Scope boundary / evidence note. In this snapshot the bending area is comparatively lightly represented in readable source. Well-evidenced capabilities are CAD bend definition, unfolding, the bend-factor look-up, the profile editor, bumping/notch geometry, and the bend-tool assistant (tc_cad/cad_asm/{cad_bieg,bendtool,bumping,profile}.cpp, tc_dbase/dbase_cad/bendDbFunc.cpp, tc_bof/bendassi.gritx). Automatic bend-sequence determination and press-brake collision checking are not present as readable C++ here and appear to be delegated to the separate ToPs 600 / TruTops Bend application (see Open Questions). Requirements that could not be directly evidenced are marked (inferred).

2. Capability Overview

  • Mark part edges as bend lines and create bends on a flat or 3D part.
  • Classify each bend by kind (Biegeart), method (Biegemethode) and technique (Biegetechnik), and capture angle, pre-angle, inner/end radius and the bend-deduction factor.
  • Determine the bend-deduction factor (Abkantfaktor) automatically from the ToPs 600 bend-factor table, keyed by material, thickness, tool group, angle and radius, with inner/outer/radius/tangent dimensioning.
  • Unfold a bent part into its flat pattern and re-unfold when factors change.
  • Assign upper and lower bend tools and derive their tool groups; look up punch/die geometry and load limits from the ToPs 600 tool catalogue.
  • Profile editor: interactively build a bent cross-section from straight and hemmed segments with per-segment angle and radius.
  • Create bumping bends (large radius from several small parallel bends) and corner reliefs / notches (Klinkungen) at bend intersections.
  • Bend tool assistant: create and edit standard punch, die, Z-tool and adapter geometry as polygon profiles, stored in the shared BendTools file store.
  • Attach descriptive tag labels (Schildchen) to bend lines; copy, count, mark, and validate bends; full undo/redo of bend operations.
  • Map ToPs 100/300 material names onto ToPs 600 material names for correct technology look-up.

4. Functional Requirements

FR-BEND-001 — ToPs 600 edition activation and licensing

  • Requirement: Where the ToPs 600 bending application is started, the system SHALL verify the applicable dongle/password (TOPS300, or the _LITE/_BASIC variant according to the active mode) before enabling bending functionality.
  • Priority: Conditional
  • Rationale: Bending is a licensed edition; Full, Lite and Basic variants gate the available feature set.
  • Source: tops/tops_300/tops_app.cpp (TC_CHECK_APPLIC_PASSWORD "TOPS300", ..._LITE_PASSWORD, ..._BASIC_PASSWORD, tops_einzel_applic_password_check, get_check_lite_pwd).
  • Verification: Test.

FR-BEND-002 — Create and mark bend lines on a part

  • Requirement: When the operator selects a line on a part and confirms it as a bend, the system SHALL create a bend line and register the associated bend in the part's bend list.
  • Priority: Essential
  • Rationale: The bend line is the fundamental object every downstream bend calculation and NC step depends on.
  • Source: tc_cad/cad_asm/cad_bieg.cpp (start_bend, set_bend, identify_bend_line, create_bend_line, create_bend_line_confirm, create_bend_line_all); tc_dbase/dbase_command/TcDbaseCreateBendingCommand.h ("Kommando um Biegungen zu erzeugen"); TcDbaseMarkBendlineCommand.h.
  • Verification: Demonstration.

FR-BEND-003 — Classify bend kind (Biegeart)

  • Requirement: The system SHALL allow each bend to be classified as one of the defined bend kinds: normal bend, hemming, wave bend, conical bend, flat processing, Z-bend, die-bend, double bend, swivel bend or auxiliary bend.
  • Priority: Essential
  • Rationale: The bend kind drives allowance, tooling and NC treatment.
  • Source: tc_dbase/benddef.h (NORMKANTUNG, FALZUNG, WELLENBIEGUNG, KONISCHBIEGUNG, FLACHBEARBEITUNG, Z_BIEGUNG, GESENKBIEGUNG, DOPPELBIEGUNG, SCHWENKBIEGUNG, HILFSBIEGUNG); cad_bieg.cpp (set_bend_type).
  • Verification: Inspection.

FR-BEND-004 — Select bend method (Biegemethode)

  • Requirement: The system SHALL allow each bend to be assigned a forming method: air bending (Freibiegen), coining (Prägen), seam-with-gap (Falz mit Spalt), closing (Zudrücken) or swivel bending (Schwenkbiegen).
  • Priority: Essential
  • Rationale: The forming method affects springback, factor and force calculation.
  • Source: tc_dbase/benddef.h (FREIBIEGEN, PRAEGEN, FALZ_MIT_SPALT, ZUDRUECKEN, SCHWENKBIEGEN); cad_bieg.cpp (set_bend_method).
  • Verification: Inspection.

FR-BEND-005 — Select bend technique (Biegetechnik)

  • Requirement: The system SHALL allow each bend to be assigned a technique such as normal, pre/post-bending, bumping, U-die, V-die, round die, coining, joining or forming.
  • Priority: Conditional
  • Rationale: The technique selects the die style and step strategy used to realise the bend.
  • Source: tc_dbase/benddef.h (NORMALKANTEN, VOR_NACHKANTEN, BUMPING, U_GESENK, V_GESENK, RUNDGESENK, PRAEGUNG, FUEGUNG, UMFORMEN, STANZUNG); cad_bieg.cpp (set_bend_tech).
  • Verification: Inspection.

FR-BEND-006 — Capture bend angle and pre-angle

  • Requirement: The system SHALL capture and store the bend angle (Winkel) and pre-angle (Vorwinkel) for each bend.
  • Priority: Essential
  • Rationale: The angle is the primary geometric parameter of a bend and a key into the bend-factor table.
  • Source: tc_dbase/benddef.h (winkel, vorWinkel); cad_bieg.cpp (set_bend_win, set_bend_vwin).
  • Verification: Test.

FR-BEND-007 — Capture inner and end bend radius

  • Requirement: The system SHALL capture and store the inner/start radius (Schenkelradius) and end radius for each bend.
  • Priority: Essential
  • Rationale: Radius, together with material and angle, determines the flat allowance.
  • Source: tc_dbase/benddef.h (stRad, endRad); cad_bieg.cpp (set_bend_srad, set_bend_erad).
  • Verification: Test.

FR-BEND-008 — Determine bend-deduction factor from the ToPs 600 bend-factor table

  • Requirement: When the parameters of a bend are known, the system SHALL determine its bend-deduction factor (Abkantfaktor) from the bend-factor table using material, material thickness, upper/lower tool group, bend angle and radius.
  • Priority: Essential
  • Rationale: Correct flat-length calculation is the core value of press-brake CAM; wrong factors scrap parts.
  • Source: tc_dbase/dbase_cad/bendDbFunc.{h,cpp} (bestimmeAbkantFaktor); Databases/SQLServerDatabase/Tables/Common.AKF_BENDFACTORS.sql (AKF_MATERIAL_DICKE, AKF_OW_GRUPPE, AKF_MA_GRUPPE, AKF_WINKEL, AKF_RADIUS, AKF_FAKTOR, AKF_MIN_DICKE, AKF_MAX_DICKE).
  • Verification: Test.

FR-BEND-009 — Support inner/outer/radius/tangent dimensioning basis

  • Requirement: The system SHALL determine the bend-deduction factor consistently with the selected dimensioning basis — inside, outside, radius or tangent — including the special case of a hemming bend.
  • Priority: Essential
  • Rationale: The same physical bend yields different flat lengths depending on the dimensioning reference; this must be explicit and correct.
  • Source: bendDbFunc.h (bestimmeAbkantFaktor params t_innen, t_falzen, t_dimRad); tc_cad/cad_asm/profile.cpp (e_profilBemassungAussen, e_profilBemassungInnen, e_profilBemassungRadius, e_profilBemassungTangente).
  • Verification: Test.

FR-BEND-010 — Unfold a bent part / profile to its flat pattern

  • Requirement: The system SHALL compute the flat pattern (Abwicklung) of a bent part or profile by applying the per-bend deduction factors to the developed length.
  • Priority: Essential
  • Rationale: The flat pattern is the geometry sent to the cutting/punching machine; it is the primary deliverable of bend programming.
  • Source: bendDbFunc.h (db_wickle_biege_profil_ab); tc_cad/cad_asm/profile.cpp (TiProfilAbwickler); tc_cad/cad_asm/cad_bieg.hpp (m_unfoldPtr / TcDbaseChangeUnfoldCommand).
  • Verification: Test.

FR-BEND-011 — Adjust an existing unfolding when bend factors change

  • Requirement: When the bend-deduction factors of a part change, the system SHALL recalculate and update the existing flat pattern accordingly.
  • Priority: Essential
  • Rationale: Factor edits (e.g. after tool or material change) must propagate to the flat geometry without redrawing the part.
  • Source: tc_dbase/dbase_command/TcDbaseChangeUnfoldCommand.h ("Kommando zum Aendern einer Abwicklung. Anhand neuer Abkantfaktoren wird eine Abwicklung angepasst"); cad_bieg.cpp (m_unfoldPtr).
  • Verification: Test.

FR-BEND-012 — Assign upper and lower bend tools to a bend

  • Requirement: The system SHALL allow an upper tool (Oberwerkzeug/Stempel) and a lower tool (Unterwerkzeug/Gesenk) to be assigned to each bend.
  • Priority: Essential
  • Rationale: Tool assignment is required for factor look-up, force calculation and NC output.
  • Source: tc_dbase/benddef.h (wzgOben, wzgUnten); cad_bieg.cpp (set_bend_wzgO, set_bend_wzgU, set_bend_wzgU_profile); cad_bieg.hpp (m_topTool, wzgO, wzgU).
  • Verification: Demonstration.

FR-BEND-013 — Derive tool groups from assigned tools

  • Requirement: When upper and lower tools are assigned, the system SHALL derive their tool groups (Werkzeuggruppen) for use in bend-factor and technology look-up.
  • Priority: Conditional
  • Rationale: The bend-factor table is keyed by tool group, not individual tool; the mapping must be resolved.
  • Source: bendDbFunc.h (bestimmeWerkzeugGruppen); Bend.WZG_OW.sql/Bend.WZG_GESENK.sql (GruppeID); Bend.WZG_OW_GRUPPE.sql, Bend.WZG_MA_GRUPPE.sql.
  • Verification: Analysis.

FR-BEND-014 — Look up punch and die from the ToPs 600 tool catalogue

  • Requirement: Where the ToPs 600 bend database is available, the system SHALL retrieve punch and die definitions — including geometry, angle, radius, die width, working height, permitted sheet-thickness range and maximum load — from the bend tool tables.
  • Priority: Conditional
  • Rationale: Realistic tooling data underpins collision-free, force-valid bend programs; it is edition/database dependent.
  • Source: Databases/SQLServerDatabase/Tables/Bend.WZG_OW.sql (Winkel, Radius, Arbeitshoehe, BelastungMax, Stempelform, Haltertyp), Bend.WZG_GESENK.sql (Gesenkweite, Gesenktiefe, Winkel, Radius, BlechdickeMin/Max, BelastungMax); Bend.WZG_TABELLEN.sql.
  • Verification: Inspection.

FR-BEND-015 — Map ToPs 100/300 material names to ToPs 600

  • Requirement: When looking up bend technology, the system SHALL translate a ToPs 100/300 material name into the corresponding ToPs 600 material name before querying the bend database.
  • Priority: Essential
  • Rationale: The bend database uses ToPs 600 material naming; without mapping, factor look-up fails silently or returns defaults.
  • Source: bendDbFunc.h (changeMaterialNameTo600 — "Aendert einen ToPs 100/300 Materialnamen in einen ToPs 600 Materialnamen").
  • Verification: Test.

FR-BEND-016 — Profile editor: construct a bent cross-section

  • Requirement: The system SHALL provide a profile editor in which the operator builds a bent cross-section from consecutive segments, specifying per-segment bend angle and radius, and from which the flat development and factors are computed.
  • Priority: Essential
  • Rationale: The profile editor is the primary interactive means of authoring a bent part and its unfolding.
  • Source: tc_cad/cad_asm/profile.{h,cpp} (S_ProfileData_Geo{m_angle,m_radius,...}, TcProfilFaktorBerechner::holeFaktor, TiProfilModell, TiProfilAbwickler, init_profileAngle_befehl); enums e_profilNormalBiegung, e_profilElementWinkelDx/Dy.
  • Verification: Demonstration.

FR-BEND-017 — Profile editor: hemming (Falzung) segments

  • Requirement: Where a segment is a hemming bend, the system SHALL support upward and downward hems and apply the hemming-specific deduction factor.
  • Priority: Conditional
  • Rationale: Hems (closed/almost-closed folds) need distinct geometry and factor handling.
  • Source: tc_cad/cad_asm/profile.cpp (e_profilFalzung, e_profilFalzungHoch, e_profilFalzungRunter); bendDbFunc.h (t_falzen flag "aus Profileditor").
  • Verification: Test.

FR-BEND-018 — Bumping bends (multi-edge rounded bend)

  • Requirement: The system SHALL create a bumping bend that realises a large radius as several parallel small bend edges formed together, and represent it as a single bumping attribute on the part.
  • Priority: Conditional
  • Rationale: Bumping produces rounded/large-radius bends on a standard V-die; it is a distinct programming operation.
  • Source: tc_cad/cad_asm/bumping.{h,cpp} (S_Bumping_Geo, TcDbaseBumpingCommand, TcDbaseCornerSelector); tc_dbase/bend_attribute/TcBendBumpingAttribute.h ("Eine Bumping-Biegung besteht aus mehreren parallelen Biegekanten"); profile.cpp (e_profilBumpingBiegung).
  • Verification: Demonstration.

FR-BEND-019 — Create corner reliefs / notches at bend intersections

  • Requirement: The system SHALL create corner reliefs (Klinkungen) at bend-line intersections/corners to avoid material collision during folding.
  • Priority: Conditional
  • Rationale: Relief notches prevent tearing and interference where adjacent bends meet.
  • Source: tc_dbase/dbase_command/TcDbaseNotchCommand.h ("Kommando um Klinkungen zu Erzeugen"); tc_dbase/dbase_command/TiDbaseBendLineAutoNotch.h; tc_dbase/dbase_util/TcDbaseKlinkung.cpp.
  • Verification: Demonstration.

FR-BEND-020 — Bend tool assistant: create standard bend-tool geometry

  • Requirement: The system SHALL provide a bend tool assistant (Biegewerkzeugassistent) that guides the operator through creating standard bend-tool geometry — punch, die, Z-tool and adapter — from parametric polygon profiles.
  • Priority: Essential
  • Rationale: Users must be able to define tools not present in the catalogue for correct simulation and factors.
  • Source: tc_bof/bendassi.gritx (masks M_CadBendToolCreateAssistant, F_CadBendToolDataHead/Tip/Gesenk/Corner/Front/ZTool/Polygon, command aCadCreateBendtool, bendtool create); tc_cad/cad_asm/bendtool.cpp (bendToolCreate, startBendTool, init_bendtool_befehl).
  • Verification: Demonstration.

FR-BEND-021 — Restrict modification to assistant-created standard tools

  • Requirement: If the operator attempts to modify a bend tool that is not a standard tool created by the assistant (or that consists only of auto-generated elements), then the system SHALL reject the modification and inform the operator.
  • Priority: Essential
  • Rationale: Editing non-standard/auto-generated geometry would corrupt the parametric tool model.
  • Source: tc_bof/bendassi.gritx (mask M_CadBendToolChangeAssistant, command aCadChangeBendtool; messages "Werkzeug kann nicht geändert werden … muss ein Standardwerkzeug sein, welches mit dem Assistenten erstellt wurde" / "besteht nur aus automatisch erzeugten Elementen"); bendtool.cpp (bendToolNewCheck, bendToolCurrentCheck).
  • Verification: Test.

FR-BEND-022 — Capture bend-tool geometry parameters

  • Requirement: The system SHALL capture the geometric parameters of an assistant-created bend tool, including tool type, tool height, tool width, opening angle, tip radius, groove-ground radius, die width (with/without feed radius), feed/insertion radius and adapter/holder type.
  • Priority: Essential
  • Rationale: These parameters define the tool profile used for collision, load and factor evaluation.
  • Source: tc_bof/bendassi.gritx (labels "Öffnungswinkel", "Nutgrundradius", "Gesenkweite", "Gesenkweite ohne Einzugsradius", "Einzugsradius", "Höhe des Werkzeugs", "Werkzeugbreite", "Art des Werkzeugs", "Typ der Werkzeugaufnahme", "Z-Werkzeug"); bendtool.cpp (bendToolAngle, bendToolGrooveRadius, bendToolTipRadius, bendToolTotalWidth, bendToolHeight, bendToolWidth, bendToolAdapter, bendToolType, bendToolZLength).
  • Verification: Inspection.

FR-BEND-023 — Store and load bend-tool geometry files

  • Requirement: The system SHALL store created/edited bend tools as geometry files in the shared bend-tool directory and load them for reuse.
  • Priority: Essential
  • Rationale: Bend tools must persist across sessions and be shared among programmers.
  • Source: ini_files/Tops300/ToPs300.ORG (TOPS_BENDTOOL_PATH = $(TOPS_DATA_PATH_SHARED)/BendTools); tc_bof/bendappl.gritx (store tool #FS_LOAD_OPTION ... confirm, load del_draw ... window fit); bendtool.cpp (bendToolRead).
  • Verification: Test.

FR-BEND-024 — Preview and stepped display of tool/bend construction

  • Requirement: When constructing a bend tool or bend, the system SHALL provide a preview and stepwise display of the resulting geometry before it is committed.
  • Priority: Optional
  • Rationale: Visual feedback reduces errors when authoring parametric geometry.
  • Source: tc_bof/bendassi.gritx (FUNC_CadBendToolSample, FUNC_CadBendToolShowStep, FUNC_CadBendToolAngle, FUNC_CadBendToolExecute); bendtool.cpp (bendToolPreview, bendToolSample, bendToolShowElement, bendToolShowCorner).
  • Verification: Demonstration.

FR-BEND-025 — Attach descriptive tag labels to bend lines

  • Requirement: The system SHALL allow a free-text label (Schildchen) to be attached to a bend line as an annotation.
  • Priority: Optional
  • Rationale: Operators annotate bends with notes/identifiers for shop-floor communication.
  • Source: tc_dbase/bend_attribute/TcBendTagAttribute.h ("‘Schildchen’-Attribut fuer Biegelinien … beliebiger bezeichnender Text"); TeBendAttributeType.h (e_bendTagAttribute).
  • Verification: Demonstration.

FR-BEND-026 — Copy bends and bend lines

  • Requirement: The system SHALL copy a bend (and its bend line and data) to new positions, optionally applying a transformation, preserving the bend parameters.
  • Priority: Optional
  • Rationale: Repeated identical bends on a part are common; copying avoids re-entry.
  • Source: tc_cad/cad_asm/cad_bieg.cpp (copy_bend, copy_bend_execute, copy_bend_all, create_bend_line_all); tc_dbase/biegung.h (db_kopiere_biegung, db_kopiere_alle_biegungen, db_kopiere_biegelinien).
  • Verification: Demonstration.

FR-BEND-027 — Count, mark and validate bends

  • Requirement: The system SHALL count and mark the bends of a part and check the bend set for consistency, including detection of duplicate/coincident bends.
  • Priority: Conditional
  • Rationale: Validation catches modelling errors (e.g. overlapping bend lines) before NC output.
  • Source: tc_cad/cad_asm/cad_bieg.cpp (countBendings, markBendingExecute, markBendingAll, checkBendline); tc_dbase/biegung.{h,cpp} (db_zaehle_biegungen, db_pruefe_biegungen, db_sucheGemeinsameBiegungen, areBendingsDouble, db_compare_biegedaten).
  • Verification: Test.

FR-BEND-028 — Undo and redo of bend operations

  • Requirement: The system SHALL support undo and redo of bend creation, bend-data change, unfolding change and bend-attribute changes.
  • Priority: Essential
  • Rationale: Interactive bend authoring requires reversible operations to be usable and safe.
  • Source: tc_dbase/bend_undo/ (TcBendAttributeAction, TcBendChangeAttributeAction, TcBendChangeAttachmentAction, TcBendCreatedAttributeAction, TcBendDeleteAttributeAction, TcBendAttributeActionFactory); tc_dbase/dbase_undo/TcDbaseBendingMemento.*, TcDbaseChangeBendingDataAction.*; cad_bieg.cpp (undo sequenz start/stop).
  • Verification: Test.

FR-BEND-029 — Visualize bend lines distinctly

  • Requirement: The system SHALL draw bend lines with a distinct colour and line type so they are visually distinguishable from cut contours.
  • Priority: Essential
  • Rationale: Operators must instantly recognise bend geometry on screen.
  • Source: tc_cad/cad_asm/cad_bieg.hpp (S_Bend{farbe, line_type}); tc_dbase/biegung.h (db_zeichne_biegungen_all, db_zeichne_biegung, zeichne_biegung_einzeln). See [[21 - FR - Visualization, Viewing & Plotting]].
  • Verification: Demonstration.

FR-BEND-030 — Bend sequence and press-brake collision (delegated) (inferred)

  • Requirement: Where automatic bend-sequence determination and press-brake collision checking are required, the system SHALL delegate them to the ToPs 600 / TruTops Bend application via its automation interface rather than computing them within the ToPs 600 CAD snapshot. (inferred)
  • Priority: Conditional
  • Rationale: No readable bend-sequence or collision-check C++ exists in this snapshot; the ToPs 600 bend database (machine configuration, NC output, robot/gripper, crowning) and the BendAPI automation wrapper indicate this logic lives in the separate bend application.
  • Source: Common/TRUMPF/dist/win/Msvc100/API/BendAPI/ (TcNBendAPI, TiNVisitor_BendAPI_BendAPI.hh, TiNVisitor_BaseAPI_*Command); ToPs 600 DB tables Bend.MASCHINE_KONF, Bend.NC_AUSGABE_PRESSE, Bend.NC_AUSGABE_AUTOMAT, Bend.BOMBWERTE; absence of sequence/collision source in tc_cad/tc_dbase.
  • Verification: Analysis.

5. External Interfaces (area-specific)

  • ToPs 600 bend database — SQL Server Bend schema and Common.AKF_BENDFACTORS: bend-deduction factors, punch/die/hemming/Z/swivel tool tables (WZG_OW, WZG_GESENK, WZG_FALZ, WZG_ZBIEG, WZG_SCHWENKBIEGER), tool groups, adapters/holders, machine configuration (MASCHINE_KONF), NC output formats (NC_AUSGABE_PRESSE, NC_FORMATE), crowning (BOMBWERTE), automation/gripper tooling. See [[19 - FR - Tools, Machines, Materials & Technology]] and [[30 - External Interface Requirements]].
  • BendTools file store — shared directory TOPS_BENDTOOL_PATH holding assistant-created bend-tool geometry files.
  • BendAPI (.NET/native automation wrapper) — managed/native API exposing activation, initialize, save, quit, set-language and MRU commands to drive the bend application headlessly. See [[23 - FR - Automation, Scripting & Integration]].
  • Part / geometry files — part geometry with bend data persisted via the CAD geometry store (GeoSaveExt); part registration into part management (teileverwaltung insert). See [[11 - FR - Import, Export & File Formats]] and [[12 - FR - Part & Data Management]].
  • GRIT UI / MMK interpreter — the interactive bend dialogs and assistant are GRIT masks driven by the MMK interpreter. See [[22 - FR - UI Framework, Dialogs & Interaction (GRIT)]].

6. Assumptions & Constraints

  • The bending technology is only fully functional with the ToPs 600 bend database attached; without it, factor and tool look-ups fall back to defaults. (Conditional dependency — see [[50 - Constraints & Assumptions]].)
  • Metric and Inch database variants exist (createSqlServerLocalMdb_Bend.bat, Bend.EINHEITEN_INCH/EINHEITEN_METRISCH); unit handling must match the active edition.
  • The bend CAD area is a legacy C++/ASM state-machine + GRIT application; numeric behaviour (factor tables, tolerances) is data-driven and not fully derivable from source.
  • Material and tool naming conventions differ between ToPs 100/300 and ToPs 600 and require explicit mapping (FR-BEND-015).
  • Cross-cutting non-functional constraints (performance, DB availability, localization) are captured in [[40 - Non-Functional Requirements]] and [[50 - Constraints & Assumptions]].

7. Open Questions & Ambiguities

  • Automatic bend-sequence determination — not found as readable source in this snapshot. Is it implemented in the compiled t300.olb/bend libraries, or entirely in the separate ToPs 600 / TruTops Bend product? (FR-BEND-030 is inferred.)
  • Press-brake collision checking — likewise absent from readable source; the tc_cad/cad_allg TcCheckFeedbackPosition/fullfeed machinery appears to relate to punching feed-position checks, not press-brake tool/part collision. Ownership unclear.
  • tc_bof/ToPs300_autom_Durchlauf.gritx speaks of "Schachtelauftrag" (nesting order) and "NC-Programm und Einrichteplan für jede Tafel" (NC program + setup plan per sheet) — this looks like a shared nesting/NC automatic-run dialog reused under a ToPs 300 name rather than press-brake bending; likely belongs to [[17 - FR - Nesting & Palletizing]] / [[18 - FR - NC Generation & Motion Optimization]]. Needs confirmation.
  • tc_bof/t300appl.gritx exposes a generic "tool parameters" technology dialog (mask F_ToPsTechnologieStzStl, FUNC_ValidateDatabase) whose naming ("StzStl") suggests punch/laser technology; its exact role in bending is unclear.
  • Force/tonnage calculation — tool tables carry BelastungMax/FestigkeitVon/Bis, but the calculation that validates a bend against machine tonnage was not located in readable source.
  • Crowning (Bombieren) and gripper/robot automation tables exist in the ToPs 600 DB but have no ToPs 600 CAD consumer here; they are assumed to belong to the bend NC/automation application.
  • The exact file format/extension of stored bend-tool geometry (BendTools) and whether it is the generic .geo CAD format was not confirmed.
