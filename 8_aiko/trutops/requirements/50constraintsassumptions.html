product: trutopscad org: trumpf title: "Constraints & Assumptions" doc: "50 - Constraints & Assumptions" id-prefix: "CON" srs-standard: "ISO/IEC/IEEE 29148:2018" status: reverse-engineered-draft source: "TruTopsCAD legacy source snapshot (files dated May 2024)" related: ["[[00 - Index & Reading Guide]]", "[[03 - System Context & Architecture Overview]]", "[[30 - External Interface Requirements]]", "[[40 - Non-Functional Requirements]]", "[[12 - FR - Part & Data Management]]", "[[22 - FR - UI Framework, Dialogs & Interaction (GRIT)]]"] tags: [requirements, trutops, constraints]

Constraints & Assumptions

This document records the constraints — conditions that limit the design space and are not open to negotiation by the requirements engineering team — and the assumptions — conditions taken to be true for the requirements to hold — governing the reverse-engineered TruTops CAD/CAM suite. Constraints and assumptions are recorded per ISO/IEC/IEEE 29148:2018 §9.5 (constraints on the system) and §5.2.8 (assumptions and dependencies).

Because these requirements are reverse-engineered from a legacy source snapshot rather than authored greenfield, most constraints are as-built (the system does depend on X) rather than imposed (the system shall use X). Each item states the constraint, its type, the rationale, and the concrete source evidence in the code base under /Users/Aiko.Radlingmayr/dev/trumpf/TruTopsCAD.

Constraint types used below:

  • Build/Toolchain — how the software is compiled and assembled.
  • Platform/Runtime — the operating environment the binaries need.
  • Interface/Dependency — a mandated external component or protocol (see [[30 - External Interface Requirements]]).
  • Data/Persistence — storage engine, schema and file-format constraints (see [[12 - FR - Part & Data Management]]).
  • Domain/Business — sheet-metal-fabrication and product-line constraints (see [[01 - Vision & Scope]], [[04 - Domain Model & Glossary]]).
  • Regulatory/Safety — machine-safety and liability considerations.

Related non-functional targets (performance, portability, maintainability, security) are specified separately in [[40 - Non-Functional Requirements]]; the interfaces referenced here are detailed in [[30 - External Interface Requirements]].

1. Technical / Implementation Constraints (CON requirements)

CON-001 — Build toolchain fixed to Visual Studio 2010 / MSVC 10.0

Constraint: The native code base is built exclusively with the Microsoft Visual C++ 10.0 compiler (Visual Studio 2010). The master solution tcolib_win_VS2010.sln declares Solution File Format 11.00 / # Visual Studio 2010, the project uses MSBuild ToolsVersion="4.0", CompilerName.txt contains Msvc100, the global build props set <MsvcVersion>Msvc100</MsvcVersion>, and the developer shell _shell/environment.bat calls "%VS100COMNTOOLS%\vsvars32.bat". Upgrading the compiler is not supported without broad rework. Type: Build/Toolchain. Rationale: All third-party binary distributions under Common/.../dist/win/Msvc100 are ABI-matched to this compiler; mixing toolsets would break linkage. Source: tcolib_win_VS2010.sln, tcolib_win_VS2010.vcxproj, CompilerName.txt, makeutil/msbuild/tcolib_global_sys_defines.props, _shell/environment.bat.

CON-002 — 32-bit (Win32) target for the legacy core

Constraint: The legacy tcolib_win core and its edition executables target the Win32 (x86, 32-bit) platform only; the project defines <Platform>Win32</Platform> and no x64 configuration for the core. An _shell_x64 exists but references newer tooling (VS2012/VS2014 vcvars64.bat) for auxiliary components, not the legacy core. Type: Build/Toolchain, Platform/Runtime. Rationale: 32-bit pointer/address-space assumptions pervade the C/C++ code and the pinned 3rd-party libraries; the product ships as 32-bit binaries. Source: tcolib_win_VS2010.vcxproj (<Platform>Win32</Platform>), _shell_x64/environment.bat.

CON-003 — Polyglot implementation: C++ + C#/.NET + Python + generated parsers

Constraint: The system is a mix of native C++ (the bulk of tc_*/grit), managed C#/.NET assemblies (e.g. GeoAlgorithmsKernel, tc_nest/NestCore, tc_fabAdapter, XIDL interop, TruTopsDllNET), embedded Python, and lex/yacc-generated command interpreters. Any change touching a cross-language boundary must satisfy all four toolchains simultaneously (MSBuild orchestrates C++, C# and code generators in one run). Type: Build/Toolchain. Rationale: Managed geometry/nesting engines and the automation surfaces (see [[23 - FR - Automation, Scripting & Integration]]) are interop-bound to the native core via P/Invoke and the XIDL remote factory. Source: Build_tcolib_win_05XX.msbuild (OLB/Gdl/XIDL/GeneratedXIDLProjects targets), *.csproj inventory, tcolib_win_VS2010.sln.

CON-004 — Managed assemblies pinned to .NET Framework 2.0/3.5/4.0

Constraint: The C# assemblies target legacy .NET Framework versions — a survey of *.csproj shows v2.0 (×1), v3.5 (×4) and v4.0 (×49). No .NET Core / .NET 5+ target exists for these components. A separate licensing wrapper distribution targets .NET4.6.1. Type: Build/Toolchain, Platform/Runtime. Rationale: Interop with the 32-bit native core and the frozen TRUMPF dist libraries fixes the CLR era. Source: TargetFrameworkVersion across *.csproj; Common/TRUMPF/dist/win/.NET4.0, .../.NET4.6.1.

CON-005 — Embedded Python 2.5 scripting runtime (end-of-life)

Constraint: Automation and parametric-variant scripting are bound to Python 2.5 (python_2_5_0 in the build props; Python25/python25 paths in the ini files). Python 2.5 is long past end-of-life; scripts and the embedded interpreter (tc_python) cannot be run on a modern Python without porting. Type: Build/Toolchain, Interface/Dependency. Rationale: The TcPythonInterpreter links python25.dll; the ToPs/ToPsGraphics modules and TruTops_customize.py assume the 2.5 C-API and standard library (see [[23 - FR - Automation, Scripting & Integration]]). Source: tcolib_global_sys_defines.props (PythonPath=...python_2_5_0), ini_files/ToPs100/ToPs100.ORG (TOPS_PYTHON_PATH=...\Python25).

CON-006 — Frozen third-party library versions

Constraint: The build depends on a set of specific, old third-party library versions that are checked into Common/3rdParty and Common/TRUMPF: Qt 4.3.5, ACE 5.5.1 + TAO 1.5.1 (CORBA), Xerces-C 2.7.0 (XML), FreeType 2.3.1 (fonts), Boost 1.50.0, ICU 49, crypto++ 5.5.0, lp_solve 5.5 (LP optimizer), libodbc++ 0.2.4pre1 (ODBC C++ wrapper), and the GSSL NestLib nesting engine. These versions are effectively immutable for this branch. Type: Build/Toolchain, Interface/Dependency. Rationale: Each is ABI-compiled for MSVC 10.0 / Win32 and integrated at source level; version bumps would ripple through many modules. Source: makeutil/msbuild/tcolib_global_sys_defines.props (QtPath, AceTaoPath, XercesPath, FreeTypePath, BoostPath, IcuPath, CryptoPath, LpSolvePath, LibOdbcPath, NestlibPath).

CON-007 — GRIT UI framework and MMK interpreter are the mandatory interaction layer

Constraint: All interactive behaviour is expressed through the proprietary GRIT UI framework and its embedded MMK interpreter (with mini_sql data binding). Dialogs are GRIT masks; command logic lives in MMK/ASM scripts. There is no alternative UI path for the legacy screens; the modern Qt front-end is bridged through tc_guiAdapter AppStates rather than replacing GRIT. Type: Platform/Runtime, Interface/Dependency. Rationale: The entire interactive command surface, validation, finder lists and undo are implemented against GRIT/MMK (see [[22 - FR - UI Framework, Dialogs & Interaction (GRIT)]]). Source: grit/, tc_bof/*.gritx, tc_guiAdapter/, build target OLB in Build_tcolib_win_05XX.msbuild.

CON-008 — GRIT mask storage formats and build-time GDL/OLB/XIDL code generation

Constraint: UI masks are stored in three interconvertible formats — .gritx (XML authoring form, v2.63/UTF-8), .olb (binary runtime form) and .a26 (legacy ASCII) — and the runtime loads a compiled .OLB (e.g. TOPS_OLB=...\bin\T100.OLB). The build must run dedicated code-generation steps (GDL translation, OLB compilation, XIDL interface generation) before compiling C++/C#; these are ordered dependencies (DependsOnTargets="Gdl;XIDL;OLB;GeneratedXIDLProjects;..."). Type: Build/Toolchain. Rationale: Masks and cross-process interfaces are generated artefacts, not hand-written source; the build order is not free. Source: Build_tcolib_win_05XX.msbuild (targets OLB/Gdl/XIDL/T100), ini_files/ToPs100/ToPs100.ORG (TOPS_OLB).

CON-009 — Parser generators (flex/bison) required to build the interpreters

Constraint: The MMK and ASM command interpreters are generated from lex/yacc grammars, so the build depends on flex 2.5.4 and bison 1.35 distributed under Common/3rdParty/dist/win/gcc32. These GNU tools must be present in the toolchain even though the product is otherwise MSVC-based. Type: Build/Toolchain. Rationale: The tc_asm state machine and the MMK interpreter behind GRIT are yacc/lex-based (see [[23 - FR - Automation, Scripting & Integration]]). Source: tcolib_global_sys_defines.props (FlexPath=...flex_2_5_4, BisonPath=...bison_1_35).

CON-010 — Relational persistence on Microsoft SQL Server via ODBC

Constraint: All master/technology/order data is held in Microsoft SQL Server databases accessed over ODBC (via the libodbc++ wrapper and grit/tco_api/tc_odbc). A SQL Server instance (default TRUMPFSQL1) and per-database ODBC DSN entries are provisioned by admin scripts. Provisioning references SQL Server client tooling versions 100/110 (SQL Server 2008 / 2008 R2 era), with a separate 2019 structure snapshot present. Type: Data/Persistence, Interface/Dependency. Rationale: The whole technology/config layer, rule set (REGEL_ALLG) and inventory are relational tables; there is no non-SQL persistence path for them. Source: Databases/createSqlServerLocalMdb.bat, Databases/createSqlServerOdbcEntry.bat, Databases_SQL_2019/, ini_files/*/*.ORG (SERVER=, DBVLOG=).

CON-011 — Locally-attached MDF single-workstation database variant

Constraint: In addition to a networked SQL Server instance, the product supports locally-attached MDF database files (attached/detached by AttachSqlServerLocalMdb.bat / DetachSqlServerLocalMdb.bat), giving a single-workstation deployment. (Analysts elsewhere describe this as an "Access MDB" mode; no Jet/ACE Access-driver dependency was found — the local store is a SQL Server .mdf attached to a local instance.) Attaching/detaching requires local administrator rights. Type: Data/Persistence, Platform/Runtime. Rationale: Standalone editions (e.g. ToPsCad, Lite) run without a shared server; the same schema is served from a local MDF. Source: Databases/AttachSqlServerLocalMdb.bat, Databases/createSqlServerLocalMdb.bat (admin-rights check S-1-5-32-544), Databases/DetachSqlServerLocalMdb.bat.

CON-012 — DATADICT-driven schema and per-schema DB versioning/migration

Constraint: The physical schema is defined and provisioned from the DATADICT data dictionary (tables/columns/relations/indexes), and each technology schema carries a DB_VERSION marker. The installed database version must be compatible with the application; migration/porting is applied in place at install/upgrade. Type: Data/Persistence. Rationale: Tables are auto-created from dictionary rows and the app validates schema version on connect (see [[12 - FR - Part & Data Management]]). Source: Databases/SQLServerDatabase/Tables/DATADICT.*.sql, .../Common.DB_VERSION.sql, .../Laser.DB_VERSION.sql, .../CAD.DB_VERSION.sql.

CON-013 — Technology-partitioned, dual metric/inch databases

Constraint: Data is partitioned into technology schemas (Punch, Laser, Bend, Tube, Nest, Common, CAD, Text, DATADICT, Logging, …) and every measurement-bearing schema is duplicated in an _inch variant (Punch_inch, Laser_inch, Tube_inch, Common_inch, Nest_inch, CAD_inch, Text_inch). The application must select the unit-correct database and keep the two representations in sync via a porting step. Type: Data/Persistence, Domain/Business. Rationale: Metric and imperial are maintained as parallel physical databases rather than by runtime conversion. Source: Databases/SQLServerDatabase/Tables/ schema-prefix inventory; Databases/RedGateFilter/RedGateStructureImperial.scpf / ...Metric.scpf; Databases/DB_Port_SqlSrv*_InchRefresh*.ps1.

CON-014 — CORBA (ACE/TAO) as the PDM integration transport

Constraint: Integration with TRUMPF PDM uses CORBA over ACE 5.5.1 + TAO 1.5.1, addressed through a naming service (servername:port). The PDM connection is therefore bound to this CORBA stack and its addressing model. Type: Interface/Dependency. Rationale: pdmConvert, the OmAdapter/TiPdmFacet file abstraction and the per-edition XIDL component APIs connect via the CORBA naming service. Source: tcolib_global_sys_defines.props (AceTaoPath=...ACE_5_5_1+TAO_1_5_1), ini_files/ToPs100/ToPs100.ORG (PdmServiceName, PdmNameServiceSpec=XXXX:9999).

CON-015 — Java (Saxon) required for build-time / report XSLT

Constraint: A Java runtime and Saxon 9 are required to translate report/plan stylesheets (XSLT) during build and reporting; the build props set a Saxon classpath (saxon9.jar, saxon9-jdom.jar, saxon9-sql.jar). Type: Build/Toolchain, Interface/Dependency. Rationale: Nesting/production-plan reports are rendered through XSL transforms driven by Saxon. Source: tcolib_global_sys_defines.props (SaxonClassPath, ThirdPartyJavaDir).

CON-016 — Single monolithic project producing per-edition executables

Constraint: The editions (ToPs 100/300/400, ToPs 400 Cad, ToPsCad, ToPsNest, plus Lite/2000 and a TStub) are not separate code bases: they build from the one shared tcolib_win core, differentiated by thin executable projects (topsmain/T100, T300, T400, T400Cad, TCad, TNest, TStub) and by runtime .ORG/.OLB configuration and licensing. A change to the shared core affects all editions at once. Type: Build/Toolchain, Domain/Business. Rationale: Edition behaviour is selected by config and license, not by code fork; there is one deliverable core library. Source: topsmain/*.vcxproj, Build_tcolib_win_05XX.msbuild (T100/T300/T400 targets), ini_files/ per-edition folders.

CON-017 — Source retains obsolete HP-UX / X11 rendering paths

Constraint: The graphics and system-adapter layers still contain HP-UX / X11 code paths (grit/drive/elem_ux.cpp, grit/src/graf_x11.cpp/.h, grit/drive/x11_def.h, grit/hpux/, grit/tco_api/tc_api/t_sysux.cpp). These are legacy remnants; the live rendering path is Windows GDI (vis_gdi, elem_win.cpp). Maintainers must not assume the Unix paths are current or tested. Type: Platform/Runtime, Build/Toolchain. Rationale: The product historically ran on HP-UX; the ported-out code was never fully removed (see [[21 - FR - Visualization, Viewing & Plotting]]). Source: grit/drive/elem_ux.cpp, grit/src/graf_x11.cpp, grit/hpux/, tc_visualize/visFunc.cpp.

CON-018 — Development configuration management on Perforce + Red Gate SQL Source Control

Constraint: The source and database schema are versioned in Perforce (files carry $Id: //cadCam/TruTops/...#N $ keywords; CommandLineHooks.xml drives P4 sync/add/edit/delete/submit/revert) with Red Gate SQL Source Control managing the DB schema (RedGate.ssc, RedGateDatabaseInfo.xml). Build/branch metadata is Perforce-specific. Type: Build/Toolchain. Rationale: DB objects are scripted per-object and reconciled through Red Gate; the P4 depot layout is baked into hooks and build server info. Source: CommandLineHooks.xml, Databases/RedGate.ssc, buildServerInfo, Perforce $Id$/$Change$ keywords in headers.

2. Environmental & Deployment Constraints

CON-019 — Windows-only runtime environment

Constraint: The delivered product runs only on Microsoft Windows: it uses Win32 GDI for display and printing, the Windows registry for configuration discovery, drive-letter/UNC filesystem paths, and Windows-hosted SQL Server/ODBC. There is no supported non-Windows runtime. Type: Platform/Runtime. Rationale: GDI rendering, registry reads and drive-letter path templates are hard dependencies of the runtime. Source: grit/drive/elem_win.cpp, registry reads in ini_files/*/*.ORG ($(REGISTRY_VAR,HKEY_LOCAL_MACHINE\...)), ini_files/ToPs100/Grit100.ORG drive-letter paths.

CON-020 — Mandated TRUMPF.NET / PDM directory layout

Constraint: The runtime expects a fixed TRUMPF.NET directory tree rooted at a configured drive: TOPS_DRIVE → TOPS_PATH=<drive>\TRUMPF.NET with the sub-tree Applications\TOPS<edition>, Utils (MACROS, APT, Python25, Iris, ImageMagick, Reports, …), Data (local and shared, e.g. ToPsDrawings, PunchTools, BendTools, TubeProfiles, NestingProfiles, ProcessingSamples), Templates, Licences, and TEMP. Deployment must reproduce this layout; the paths are consumed throughout the code via named environment variables. Type: Platform/Runtime, Interface/Dependency. Rationale: Hundreds of environment-variable path references (and legacy TC_*_PFAD aliases) resolve against this exact structure. Source: ini_files/ToPs100/ToPs100.ORG ([ENVIRONMENT] block: TOPS_* and TC_*_PFAD mappings).

CON-021 — Dongle-based licensing (Hardlock / HASP / Wibu)

Constraint: The software is protected by hardware dongle licensing plus a software time-limit fallback. Implementations exist for Hardlock and its successor HASP (both Aladdin/SafeNet) and a Wibu/CodeMeter machine-license provider. Access mode is configurable (TC_DONGLE_ACCESS: 1 = local, 2 = network); per-format import/export licences use named passwords (e.g. DXF_PASSWORD, DWG_PASSWORD, IGES_PASSWORD) with a superuser bypass. A valid, readable license is a precondition for feature availability. Type: Platform/Runtime, Domain/Business. Rationale: Edition and per-format capabilities are gated by the license check at startup and on demand (see [[30 - External Interface Requirements]]). Source: Common/TRUMPF/dist/win/Msvc100/licenseCheck/ (TcLicenseCheckHardlockImpl.h, TcLicenseCheckHaspImpl.h, TcLicenseCheckWibu.h, TcMachineLicenseIdProviderWibu.h), tc_pwd/ (check_dll.cpp, pp_pwd.cpp), ini_files/ToPs100/ToPs100.ORG (TC_DONGLE_ACCESS, TOPS_PWD_PATH).

CON-022 — Two PDM deployment modes: shared vault vs. local file system

Constraint: File access runs either through a TRUMPF PDM vault (CORBA naming service PdmServiceName=TruTopsPDM2, PdmNameServiceSpec=<server>:<port>, local attribute cache, client logging) or directly on the local/shared file system. Switching to PDM requires removing the $(TOPS_DRIVE) element from TOPS_SHARED per the ini comment. The OmAdapter/TiPdmFacet facade abstracts both. Type: Platform/Runtime, Interface/Dependency. Rationale: Persistence and browsing are routed through one facade whose backend is a deployment choice, not a code choice (see [[12 - FR - Part & Data Management]]). Source: ini_files/ToPs100/ToPs100.ORG (PDM settings block, TOPS_SHARED/TOPS_PATH comment), tc_util/pdmUtilities.

CON-023 — Required external helper executables at runtime

Constraint: Several capabilities are delegated to external executables that must be installed and path-configured: NcLink/NCLINK_GUI (production-plan/DNC transfer), ToPsVectorize.exe (raster→vector), DWGConverter.exe (DWG→DXF), ToPs400Export.exe (tube NC/APD), ImageMagick Convert.exe (bitmap conversion), Ghostscript/NikNak topdf.exe (PS→PDF), HtmlEditor.exe (HTML→PDF setup plans), and Iris.exe (LST analysis). Missing helpers disable the corresponding features. Type: Interface/Dependency, Platform/Runtime. Rationale: These functions are shelled out rather than implemented in-process (see [[11 - FR - Import, Export & File Formats]], [[18 - FR - NC Generation & Motion Optimization]]). Source: ini_files/ToPs100/ToPs100.ORG (PathBmpConvert, CmdLineEplanBmpConvert, CmdLineEplanHtmlConvert, CmdLinePsConvert, TOPS_IRIS_PATH, TC_NCLINK_LANGUAGE_INI), digest interfaces for TOPS_VECTORIZE_PATH/DWGConverter.

CON-024 — Windows registry as a configuration/discovery source

Constraint: The runtime reads configuration from the Windows registry under HKEY_LOCAL_MACHINE\Software\Trumpf\... (e.g. NcLink ini path, PS→PDF tool path, PPS-plugin path HKLM\SOFTWARE\TRUMPF\TruTops Fab\PPS-Plugin) and ODBC DSNs are installed as registry entries. The .ORG files support a $(REGISTRY_VAR,...) substitution to pull values at load time. Type: Platform/Runtime, Interface/Dependency. Rationale: Machine-local settings and third-party tool locations live in the registry, not only in the ini files. Source: ini_files/ToPs100/ToPs100.ORG ($(REGISTRY_VAR,HKEY_LOCAL_MACHINE\\Software\\Trumpf\\NcLink\\Ini,...), CmdLinePsConvert=HKEY_LOCAL_MACHINE\...), Databases/createSqlServerOdbcEntry.bat (reg.exe import).

CON-025 — Administrator privileges required for database/ODBC provisioning

Constraint: Installing/attaching databases and creating ODBC entries requires local administrator rights — the provisioning scripts explicitly check group SID S-1-5-32-544 and UAC elevation and abort otherwise. Ordinary end-user operation does not require admin, but initial deployment/upgrade does. Type: Platform/Runtime. Rationale: Attaching SQL Server MDFs and importing registry ODBC DSNs are privileged operations. Source: Databases/createSqlServerLocalMdb.bat, Databases/createSqlServerOdbcEntry.bat (whoami /groups | find "S-1-5-32-544", net.exe session).

CON-026 — Machine/NC transfer over a filesystem directory

Constraint: Generated NC programs and production plans are handed to machine controls through a configurable filesystem transfer directory (per machine, default TOPS_MACHINE_PATH=<drive>\Trumpf.NET\DATA_PDM2\Transfer\MASCH01, overridable by the machine rule PRP_PfadModal), and/or via the external NcLink/DNC service. There is no direct online machine protocol in this snapshot. Type: Interface/Dependency, Platform/Runtime. Rationale: Output routing is file-drop plus NcLink, keyed by machine transfer path (see [[18 - FR - NC Generation & Motion Optimization]], [[20 - FR - Production Planning & Projects]]). Source: ini_files/ToPs100/ToPs100.ORG (TOPS_MACHINE_PATH), digest (PRP_PfadModal, NcLink CLI).

3. Domain & Business Constraints

CON-027 — Scope limited to 2D sheet-metal fabrication

Constraint: The suite is a 2D CAD/CAM system for sheet-metal fabrication. The geometry model is 2D contours/elements; there is no general 3D solid modeller. Tube machining is handled as a 3D surface that is unrolled (Abwicklung) to a 2D development for programming, and bending works on a flat pattern — not as free-form 3D CAD. Requirements must not assume general 3D solid capabilities. Type: Domain/Business. Rationale: The kernel, editors and NC paths operate on 2D drawings/contours; 3D appears only as tube unrolling and bend flat-patterns (see [[04 - Domain Model & Glossary]], [[15 - FR - Tube & Profile Machining (ToPs 400)]]). Source: digest (FR-CAD, FR-TUBE overviews), tc_dbase 2D geometry model, tc_rohr Abwicklung.

CON-028 — Edition-gated product line and shared master data

Constraint: Functionality is partitioned into editions — ToPs 300 (punch/nibble), ToPs 600 (bending), ToPs 100 (laser), ToPs 400 Cad, ToPsCad (CAD), ToPsNest (nesting), ToPs Tube, plus ToPs 100 Lite / ToPs 2000 — each exposing a licensed subset over the same shared master data and core. Bend factor/tool data is owned by the external ToPs 600 product. Feature visibility is controlled by license + per-edition config, so a requirement's applicability is always edition-scoped. Type: Domain/Business. Rationale: One code base, many licensed products; the edition matrix and ToPs 600 dependency shape every functional area. Source: ini_files/ per-edition .ORG sets, digest edition lists across FR docs, Databases/.../Bend.* (ToPs 600 schema references).

CON-029 — Machine- and controller-specific, data-driven NC output

Constraint: NC generation is controller-specific and data-driven from cycle/format tables (NCZYKLEN, NCZYKLUS_STV, AUS_FORMAT, NC_KOPF_TABELLEN, …) keyed by machine + control + control-version, with control-version compatibility gating (STEUERUNGSVERSIONEN). Output correctness depends on correctly maintained control tables; the only controller directly observed in source is Siemens SIN840D, though the mechanism is generic. Type: Domain/Business, Interface/Dependency. Rationale: The post-processor renders NC purely from database tables per control version (see [[18 - FR - NC Generation & Motion Optimization]], [[19 - FR - Tools, Machines, Materials & Technology]]). Source: digest (FR-NC, FR-TECH), Databases/SQLServerDatabase/Tables/*.NCZYKLEN.*, control-version tables.

CON-030 — Master data is authoritative and prerequisite to programming

Constraint: Machines, tools, materials, sheets and technology tables constitute authoritative master data that must exist and be mutually compatible before a part can be programmed; the system validates part compatibility with the active material and machine and delegates technological correctness to these tables (e.g. laser LTT, punch rules STANZ_REGELN, bend factors AKF_BENDFACTORS). The application does not invent technology values absent from the database. Type: Domain/Business, Data/Persistence. Rationale: Rule-based automatic tool/technology assignment reads directly from master tables (see [[19 - FR - Tools, Machines, Materials & Technology]]). Source: digest (FR-TECH, FR-PUNCH, FR-LASER, FR-BEND), tc_verw compatibility check, Databases/.../STANZ_REGELN, LASERTECHNO, Common.AKF_BENDFACTORS.

CON-031 — Metric/imperial duality as a first-class domain constraint

Constraint: The product must operate in metric or imperial units end-to-end: dual databases (CON-013), a GRITUNIT (0 = metric, 1 = inch) runtime switch, dedicated inch .ORG/Grit*.ORG configurations and inch build configurations. Unit is a deployment/session-level constraint that pervades data access, UI rendering and NC output. Type: Domain/Business, Platform/Runtime. Rationale: Sheet-metal customers work in both systems; the code and data are structured around the split rather than converting on the fly. Source: ini_files/*/…Inch.ORG, ini_files/ToPs100/Grit100.ORG (GRITUNIT), tcolib_win_VS2010.vcxproj (Inch configuration).

CON-032 — Internationalized UI with German as source/base language

Constraint: The UI supports up to 30 languages (raised from a legacy limit of 10), including CJK, with translatable texts stored in the database (COMMON_TEXT, SPRACHEN) and per-language + per-resolution fonts. The source/base domain language is German (identifiers, comments and domain terms are German), and the default startup language is deu with English as basic fallback. Reverse-engineering and any glossary work must treat German as the canonical term source (see [[04 - Domain Model & Glossary]]). Type: Domain/Business. Rationale: TRUMPF is a German manufacturer; the code base and default configuration are German-first. Source: grit #define GRIT_ANZAHL_SPRACHEN 30 / GRIT_ANZAHL_SPRACHEN_261 10, ini_files/ToPs100/ToPs100.ORG (TC_LANGUAGE=deu, TC_LANGUAGE_BASIC=eng), ini_files/ToPs100/Grit100.ORG (GRITLANG, GRITFONT).

CON-033 — Safety-critical output driving physical machines

Constraint: The generated NC controls physical machine tools (multi-kilowatt lasers, punch presses, press brakes, tube lasers). Consequently collision detection, machine work-area/axis-dynamics limits, clamp/dead-zone avoidance, and control-version compatibility are business-critical correctness constraints, and the dongle/control-version gating restricts which programs may be transferred to which control. No explicit external safety/regulatory standard (e.g. a cited CE/ISO machine-safety norm) is referenced in the source snapshot; machine safety is enforced by the physical controls and by these in-software checks. Type: Regulatory/Safety, Domain/Business. Rationale: Incorrect NC or an out-of-limits path can damage the machine or produce scrap; the software embeds the guards but is not the final safety authority. Source: digest (collision detection in FR-PUNCH/FR-LASER/FR-TUBE, machine limits in FR-TECH, control-version gating in FR-NC).

CON-034 — Bend-sequence, press-brake collision and true scheduling are external

Constraint: Certain domain functions are out of scope of this code base and delegated to separate TRUMPF products: automatic bend-sequence determination and press-brake tool/part collision checking reside in ToPs 600 / TruTops Bend, and cross-machine, due-date-driven scheduling resides in TruTops Fab (MES). This code captures due dates, priorities and quantities but does not schedule. Type: Domain/Business. Rationale: Analysts found no readable bend-sequencing or scheduling engine in the snapshot; both are handed off (see [[16 - FR - Bending (ToPs 600)]], [[20 - FR - Production Planning & Projects]]). Source: digest open questions (FR-BEND, FR-PLAN), tc_fabAdapter hand-off (declareJobAsDone).

4. Assumptions

CON-035 — Assumption: DB schema version matches the application version

Assumption: At runtime the connected databases are assumed to be at a schema version compatible with the installed application, with any migration already applied at install/upgrade time; the app validates and rejects incompatible versions rather than adapting to arbitrary schemas. Type: Data/Persistence (dependency). Rationale: DB_VERSION markers and DATADICT-driven provisioning imply a lock-step version relationship. Source: CON-012 evidence; Databases/UpdateDbRequiredApplicExeVersion_ps_legacy.bat, DATADICT.DATADICT_ProductVersion.

CON-036 — Assumption: a valid, readable license/dongle is present

Assumption: The system assumes that at startup a valid license is accessible — a local or network dongle (Hardlock/HASP/Wibu) or a time-limited software license — matching the requested edition and per-format options; absent a license, the corresponding features are unavailable rather than degraded. Type: Platform/Runtime (dependency). Rationale: The license check is a hard gate for edition and format capabilities (CON-021). Source: Common/.../licenseCheck/, tc_pwd/, ini_files/ToPs100/ToPs100.ORG (TC_DONGLE_ACCESS).

CON-037 — Assumption: the mandated directory tree and paths are provisioned

Assumption: The TRUMPF.NET directory layout, drive letters and transfer paths (CON-020, CON-026) are assumed present and writable as configured; the installer/administrator provisions them, and the software resolves environment variables against them without runtime discovery of an alternative layout. Type: Platform/Runtime (dependency). Rationale: Path variables are consumed literally; a missing directory yields failures, not fallbacks. Source: ini_files/*/*.ORG [ENVIRONMENT] blocks.

CON-038 — Assumption: PDM vault or shared network storage is reachable (else local fallback)

Assumption: When configured for PDM, the CORBA naming service and PDM server are assumed reachable; otherwise the deployment is assumed to use the local/shared file system. The OmAdapter facade is assumed to hide which backend is active, and shared-drive availability is assumed for multi-user data. Type: Interface/Dependency. Rationale: The two backends are a deployment switch (CON-022); code assumes one is available. Source: ini_files/ToPs100/ToPs100.ORG PDM block, digest (OmAdapter/TiPdmFacet).

CON-039 — Assumption: concurrency is managed by SQL Server plus record locks / PDM check-out

Assumption: Multi-user safety is assumed to be provided by the SQL Server engine together with record lock flags (*_GESPERRT, MAT_LOCKSTATE) and PDM check-out; there is no single unified concurrency layer, and the exact interplay is not fully determined. Deployments are assumed to accept this composite model. Type: Data/Persistence (dependency). Rationale: Analysts could not confirm a single concurrency mechanism; lock flags and engine locking coexist (see [[12 - FR - Part & Data Management]] open questions). Source: digest (FR-DATA open questions), Databases/.../*LOCKSTATE*, *_GESPERRT columns.

CON-040 — Assumption: imported geometry is 2D or projectable and cleanable

Assumption: Externally imported CAD (DXF/DWG/IGES/MI/DSTV, raster) is assumed to be 2D or safely projectable to 2D (Z-suppression), and assumed to be repairable by the conversion post-processing (point-merge, contour-close, thinning) into valid contours suitable for machining. 3D solids beyond tube surfaces are not assumed importable as machinable geometry. Type: Domain/Business (dependency). Rationale: The importer + post-processing pipeline targets a 2D contour model (see [[11 - FR - Import, Export & File Formats]]). Source: digest (FR-IMPEX capabilities: Z-suppression, contour-close, thinning).

CON-041 — Assumption: target machine, control, material and tools exist and are compatible

Assumption: Programming and NC generation assume that the selected machine + control-version + material + tools all exist in master data and are mutually compatible; the technology processors rely on this and validate compatibility, but assume the master data is correctly maintained by the technology administrator. Type: Domain/Business (dependency). Rationale: Automatic technology assignment and NC output read master data as ground truth (CON-029, CON-030). Source: digest (FR-TECH, FR-PUNCH, FR-LASER, FR-NC), tc_verw compatibility check.

CON-042 — Assumption: scripts, macros and MMK/ASM variables are trusted (not sandboxed)

Assumption: Embedded Python customization (TruTops_customize.py), MMK/ASM command strings and interpreter stack variables are assumed to originate from trusted authors (administrators/integrators) and are executed without a security sandbox; no untrusted-script threat model is present in the snapshot. Type: Platform/Runtime (dependency), Regulatory/Safety. Rationale: The automation surfaces execute scripts and drive the ASM directly with full application privileges (see [[23 - FR - Automation, Scripting & Integration]]). Source: tc_python/, tc_asm/, ini_files/ToPs100/ToPs100.ORG (TOPS_KONFIG_VARS_*, TOPS_MACROS_PATH).

CON-043 — Assumption: the legacy toolchain is preserved for maintenance

Assumption: Maintenance is assumed to occur on the pinned toolchain (VS2010/MSVC100, Win32, .NET ≤4.x, Python 2.5, Qt 4.3.5, the frozen 3rd-party set); upgrading any of these is treated as a project in its own right and is outside the assumptions under which the current requirements hold. Type: Build/Toolchain (dependency). Rationale: Cross-cutting ABI and API coupling across CON-001–CON-006 makes toolchain modernization non-incremental. Source: CON-001–CON-006 evidence.

Traceability note

These constraints and assumptions apply cross-cutting to all functional areas. They are aggregated in [[60 - Requirements Traceability Index]] and complement the interface obligations in [[30 - External Interface Requirements]] and the quality targets in [[40 - Non-Functional Requirements]]. Open scoping questions raised by the functional analysts (e.g. PDM-vs-DB locking, unconfirmed controller set, Access-vs-MDF wording) are reflected as bounded assumptions above rather than firm constraints.
