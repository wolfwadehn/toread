FR — Visualization, Viewing & Plotting

Reverse-engineered requirement draft — derived from static analysis of legacy source, NOT an authoritative specification. Treat SHALL statements as reconstructed intent.

1. Purpose & Scope — what this area does and which editions it serves.

This area covers everything TruTops draws on screen and everything it sends to a hardcopy device. It defines the graphics engine that turns geometry, tool paths and technology into pixels, the interactive viewing controls (fit/zoom/pan, view-content toggles, split viewports, touch vs. desktop schemes), the display-attribute model (colours, line styles, markers, fill patterns, fonts) and the three output paths: raster screenshots (BMP/TIFF), Windows GDI printing, and HPGL/HPGL2 pen plotting.

The rendering layer is deliberately backend-abstracted: a single TiVisualizer / TiVisualSettings interface (tc_visualize) is realised over Windows GDI (vis_gdi), the GRIT UI framework (vis_grit) and a headless "none" backend (vis_none) for batch/server operation. The low-level device driver (grit/drive: tc_darst.cpp = Darstellung/display, tc_devic, tc_koord, elem_win.cpp) maps these primitives onto Windows GDI display contexts, off-screen bitmaps and printer DCs. tc_viewer provides an embeddable/standalone part viewer (GeoViewer executable + ActiveX/OCX plugin) and the interactive TcViewport; tc_bitm rasterises drawings to bitmaps; tc_plot implements pen plotting.

This area serves all editions — ToPs 300 (Punch), ToPs 600 (Bending), ToPs 100 (Laser), Tube, Nest and the CAD editions all share this graphics stack. Some content toggles and output paths are edition-specific (e.g. the View-Options dialog exposes Punch/Laser/Tube variants; a hardcopy view context is enabled for the bending application). The area does not own the geometry model itself (see [[10 - FR - CAD Geometry & Drawing Editing]]) nor the surrounding dialog framework (see [[22 - FR - UI Framework, Dialogs & Interaction (GRIT)]]); it consumes both.

2. Capability Overview — bulleted summary of the main capabilities.

  • 2D rendering primitives: move/draw vectors, lines, arcs (by centre + start/end), circles, points/markers, text, polygons and filled contours into a viewport, through a backend-independent visualizer interface (GDI / GRIT / headless).
  • Coordinate model: world↔device conversion, pixel-size query, per-viewport window (min/max) with configurable border margin.
  • View navigation: fit-to-extents (zoom-all), zoom-to-rectangle, incremental zoom in/out by percent and absolute zoom, pan, zoom-to-selected-parts, current zoom-factor query.
  • Display attributes: element colour (palette + extended constant colours), 9 line styles, 14 marker types + marker colour, text font/size/slant/spacing/alignment, 4 fill patterns and 27 fill colours (incl. 10 user-defined), thick-pen mode.
  • Canvas control: black or white background with automatic contrast adjustment and automatic black/white swap for printing.
  • View-content toggles: show/hide geometry, machining, points, positioning (rapid) paths, tools, micro-joints, NC cycles, collisions, bend lines, scrap areas, sheet info, part numbering, attributes and symbols — per application mode, persisted per context.
  • Interactive echo: XOR/echo drawing mode for rubber-band and cursor feedback.
  • Redraw management & acceleration: redraw lifecycle (start/end/flag), off-screen back-buffer bitmap (double buffering) and a redraw cache.
  • Raster output: capture a screen region / viewport / drawing button to a BMP (colour or monochrome) or TIFF file or stream; rasterise drawings/parts/contours to a bitmap.
  • Printing: print the current drawing to a Windows GDI printer with margins, aspect-ratio correction, scaling, orientation and an optional text header.
  • Plotting: HPGL/HPGL2 pen plotting driven by a configurable plotter profile (paper/DIN sizes, pen colours, line types, symbols, interfaces), scale-to-paper or fixed scale, frame/title/filename/part-number annotations, clipping, and projected (2D/3D via transformation matrix) element output.
  • Embeddable viewer: standalone GeoViewer + ActiveX/OCX plugin loading GEO/MI/IGES/DXF/DSTV/DWG and exporting SVG/BMP; Part-in-Part (PiP) family visualization with per-part/family colours and show/hide; touch-screen vs. desktop schemes and single vs. split (double) viewports.

4. Functional Requirements

FR-VIS-001 — Viewport 2D primitive rendering

  • Requirement: The system shall render, into a viewport, the geometric primitives line (two points), poly-line/polygon, arc (defined by centre plus start and end points), circle, point/marker and text.
  • Priority: Essential
  • Rationale: These primitives are the atomic drawing operations on which all drawing, part, sheet and tool-path display is built.
  • Source: tc_visualize/TiVisualizer.h (line, polygon, arcStartEnd, circle, point, text, move, draw); tc_visualize/visFunc.h; grit/drive/tc_drive.h (tc_line_two_pntsGrit, tc_arc_start_endeGrit, tc_circleGrit, tc_pointGrit, tc_textGrit).
  • Verification: Test

FR-VIS-002 — Backend-independent rendering abstraction

  • Requirement: The system shall expose a single rendering interface (TiVisualizer/TiVisualSettings) implemented over interchangeable output backends, providing at minimum a Windows-GDI backend, a GRIT-framework backend and a headless (no-output) backend.
  • Priority: Essential
  • Rationale: Allows the same drawing code to target interactive display, the GRIT UI and batch/server runs without an attached display.
  • Source: tc_visualize/vis_gdi/ (TcVisualizerGdi), tc_visualize/vis_grit/ (TcVisualizerGrit), tc_visualize/vis_none/ (TcVisualizerNone); factory createVisualizer() in TiVisualizer.h.
  • Verification: Inspection

FR-VIS-003 — World/device coordinate transformation

  • Requirement: The system shall convert coordinates between world coordinates and device (pixel) coordinates in both directions for a given viewport, and shall report the size of one pixel in world coordinates.
  • Priority: Essential
  • Rationale: Required to map mouse input to geometry and to lay out elements at correct scale on any device.
  • Source: tc_visualize/visFunc.h (tc_dc_to_wc, tc_wc_to_dc, getWcPixelSize); TiVisualizer.h (getWorldCoordinates, getDeviceCoordinates); grit/drive/tc_koord.cpp, tc_drive.h.
  • Verification: Test

FR-VIS-004 — Redraw lifecycle management

  • Requirement: The system shall bracket every repaint with an explicit start-redraw and end-redraw, expose a redraw-in-progress flag, and provide clear-viewport and commit-picture operations.
  • Priority: Essential
  • Rationale: Prevents partial/torn frames and lets callers detect and serialise redraws.
  • Source: tc_visualize/visFunc.h (tc_start_redraw, tc_end_redraw, tc_gib_redraw_flag, tc_clear_viewport, tc_make_picture_current); TiVisualizer.h (startRedraw, endRedraw, isRedrawStarted, clear).
  • Verification: Test

FR-VIS-005 — Fit-to-extents (zoom all) with border margin

  • Requirement: When the user requests fit-to-view, the system shall set the viewport window to the bounding box of the displayed geometry plus a configurable percentage border margin.
  • Priority: Essential
  • Rationale: The primary "show everything" navigation action; the margin keeps geometry off the window edge.
  • Source: tc_visualize/visFunc.h (tc_set_window with t_border); grit/drive/tc_drive.h (tc_set_windowGrit, rand_in_proz); tc_viewer/XCadViewer/TcViewport.h (ZoomAll); tc_viewer/TcViewerInterface.h (fitWindowSize).
  • Verification: Test

FR-VIS-006 — Zoom to a user-defined rectangle

  • Requirement: When the user drags a zoom rectangle in device coordinates, the system shall set the viewport window to the corresponding world rectangle.
  • Priority: Essential
  • Rationale: Standard box-zoom navigation.
  • Source: tc_viewer/XCadViewer/TcViewport.h (ZoomRect); tc_viewer/TiGeoViewer.h (zoom); tc_viewer/TcViewerInterface.h (zoom).
  • Verification: Test

FR-VIS-007 — Incremental and absolute zoom

  • Requirement: The system shall zoom in or out by a specified percentage step, shall support setting an absolute zoom, and shall report the current zoom factor.
  • Priority: Essential
  • Rationale: Keyboard/wheel/button zooming and zoom-level readback.
  • Source: tc_viewer/XCadViewer/TcViewport.h (ZoomIncrement, zoomRelative, get_ZoomFactor); tc_viewer/XCadViewer/XCadViewerControl.h (TeZoomDirection: e_ZoomIn, e_ZoomOut, e_ZoomAbsolute).
  • Verification: Test

FR-VIS-008 — Pan

  • Requirement: When the user drags in pan mode, the system shall translate the viewport window by the corresponding world displacement without changing the zoom factor.
  • Priority: Essential
  • Rationale: Core navigation for repositioning the view.
  • Source: tc_viewer/TiGeoViewer.h (pan); tc_viewer/TcViewerInterface.h (pan); tc_viewer/XCadViewer/XCadViewerControl.h (TeMoveDirection).
  • Verification: Test

FR-VIS-009 — Zoom to selected parts / labels

  • Requirement: Where a part/label model is loaded, the system shall zoom the view to the extents of a specified set of parts or label parts.
  • Priority: Conditional
  • Rationale: Lets the user focus the view on chosen nested parts or their labels.
  • Source: tc_viewer/XCadViewer/TcViewport.h (ZoomToParts, ZoomToLabelParts, LabelScaleFactor).
  • Verification: Test

FR-VIS-010 — Element colour selection from a defined palette

  • Requirement: The system shall set and query the drawing colour for elements from a defined colour palette (indices black, white, red, yellow, green, cyan, blue, magenta, two highlight colours and light-grey), plus an extended set of constant display colours.
  • Priority: Essential
  • Rationale: Colour distinguishes element roles (geometry, tool path, technology, highlight) on screen and in output.
  • Source: tc_visualize/visDefines.h (TnColor::TeColor, TC_COL_* constants); tc_visualize/TiVisualSettings.h (setElementColor/getElementColor); grit/drive/tc_darst.cpp (TC_Farben[]).
  • Verification: Test

FR-VIS-011 — Line-style selection

  • Requirement: The system shall set and query the element line style from the nine defined line types (solid, dash, dot, dash-dot, dash-dot-dot, long-dash, centre-dash, centre-dash-dash, solid-thick).
  • Priority: Essential
  • Rationale: Line style conveys element semantics (e.g. construction vs. contour vs. bend line).
  • Source: tc_visualize/visDefines.h (TC_SOLID…TC_SOLID_THICK, TC_MAX_ANZ_LINETYPES); TiVisualSettings.h (setElementStyle); grit/drive/tc_darst.cpp (TC_Line_Types[]).
  • Verification: Test

FR-VIS-012 — Marker (point-symbol) appearance

  • Requirement: The system shall render point elements using one of the fourteen defined marker symbols and shall set and query the marker type and marker colour.
  • Priority: Essential
  • Rationale: Markers denote piercing points, reference points, snap points and similar features.
  • Source: tc_visualize/visDefines.h (TC_DOT_MARKER…TC_MEDIUMDOT_MARKER, TC_MAX_ANZ_MARKER); TiVisualSettings.h (setMarkerType, setMarkerColor); grit/drive/tc_darst.cpp (TC_Marker[]).
  • Verification: Test

FR-VIS-013 — Text rendering attributes

  • Requirement: The system shall render text with configurable font, height, width ratio, character (slant) angle, line spacing, colour, reference point/alignment (nine anchor combinations) and writing orientation (right/left/up/down).
  • Priority: Essential
  • Rationale: Annotations, dimensions, part numbers and system messages must be legible and correctly placed.
  • Source: tc_visualize/TiVisualizer.h (text, text4System); TiVisualSettings.h (setTextFont, setTextSize, setTextColor); visDefines.h (TC_VERTICAL_*, TC_HORIZONTAL_*, TC_PATH_*, TC_DEFAULT_FONT); grit/drive/tc_darst.cpp (tc_berechne_text_size).
  • Verification: Test

FR-VIS-014 — Contour fill (pattern and colour)

  • Requirement: The system shall fill a closed contour, bracketed by start-contour-fill and end-contour-fill, using one of the defined fill patterns (hollow, solid, hatch, cross-hatch) and one of the defined fill colours including ten user-defined fill colours.
  • Priority: Essential
  • Rationale: Filled areas visualise parts, scrap, material and highlighted regions.
  • Source: tc_visualize/TiVisualizer.h (startContourFill, endContourFill); visDefines.h (TC_INT_HOLLOW…TC_INT_HATCH2, TC_FILL_*, TC_FILL_USER1…TC_FILL_USER10); grit/drive/tc_drive.h (tc_start_contour_fillGrit, tc_end_contour_fillGrit, tc_get_interior_style).
  • Verification: Test

FR-VIS-015 — Thick-pen display mode

  • Requirement: Where emphasised rendering is requested, the system shall draw lines at a caller-specified world-coordinate width and allow the mode to be queried and disabled.
  • Priority: Optional
  • Rationale: Used to emphasise selected/technology lines and to approximate kerf/beam width.
  • Source: tc_visualize/visFunc.h (activateThickPenMode, deactivateThickPenMode, isThickPenModeActive); TiVisualSettings.h (setThickPenMode, getThickPenMode).
  • Verification: Test

FR-VIS-016 — Configurable colour table and fonts

  • Requirement: The system shall obtain its display RGB colour table, font set and icon set from external GRIT configuration files rather than hard-coding them.
  • Priority: Conditional
  • Rationale: Lets installations retune colours, fonts and screen resolution without code changes.
  • Source: ini_files/ToPsCad/GritCad.org (GRITCOLOR=…GRITCOL.24, GRIT_RGB=…RGB.TXT, GRITFONT, GRITICON, GRITSIZE, GRITUNIT); tco_grit_tools/mask/gritw/GRITCOL.24.
  • Verification: Inspection

FR-VIS-017 — Canvas background and print colour handling

  • Requirement: The system shall support a black or a white canvas background, shall adjust element colours for visibility against the chosen background, and shall swap black and white when producing hardcopy/print output.
  • Priority: Essential
  • Rationale: On-screen work typically uses a dark canvas, while print/plot output must be legible on white paper.
  • Source: grit/drive/tc_drive.h (useWhiteCanvas, useBlackCanvas); grit/drive/elem_win.cpp (tc_tausche_schwarz_weiss in setPrinterDC/unsetPrinterDC); tc_viewer/TcViewerInterface.h (t_useBlackCanvas, setBackgroundColor).
  • Verification: Test

FR-VIS-018 — Selectable display of geometry, technology and tool-path classes

  • Requirement: The system shall let the user show or hide, independently, each display class — geometry, machining, points, positioning (rapid) paths, tools, micro-joints, NC cycles, collisions, bend lines, scrap areas, sheet info, part numbering, attributes and symbols — with the applicable class set depending on the active application (Punch, Laser, Tube, Bending).
  • Priority: Essential
  • Rationale: Users must be able to declutter the view and inspect specific aspects of a part or nest.
  • Source: tc_bof/tco_view.gritx masks F_ToPsViewEinstellungen/…Laser/…Tube, buttons O_Geometrie, O_Bearbeitung, O_Punkte, O_Positionierwege, O_Werkzeug, O_Stege, O_NcZyklen, O_Kollision, O_Bend, O_ScrapArea, O_Tafelinfo, O_Teilenummerierung, O_Attribute, O_Symbol.
  • Verification: Demonstration

FR-VIS-019 — Persist and copy view settings per context

  • Requirement: The system shall persist the view-content settings per context (sheet layout, technology, optimisation, NC and — for bending — hardcopy) and shall copy a settings group between configurations.
  • Priority: Conditional
  • Rationale: Different work phases need different default visibility, which must survive across sessions.
  • Source: tc_bof/tco_view.gritx FUNC_ReadViewOptions/FUNC_SaveViewOptions/FUNC_CopyViewOptions (contexts c_beleg, c_techno, c_opti, c_nc, c_hcpy; KFG_ config-prefix variables; IF( 300 == #APPLIC_NUMMER )).
  • Verification: Test

FR-VIS-020 — Interactive echo (rubber-band) drawing mode

  • Requirement: While the user performs an interactive construction, the system shall draw dynamic feedback in a reversible echo (XOR) drawing mode so the feedback can be erased without repainting the scene.
  • Priority: Essential
  • Rationale: Rubber-band lines, drag previews and cursor markers require fast reversible drawing.
  • Source: grit/drive/tc_darst.cpp (tc_drawing_mode, tc_echo_type, G_xorDrawMode); grit/drive/tc_drive.h (tc_get_drawing_mode, tc_get_echo_type).
  • Verification: Test

FR-VIS-021 — Icon drawing and hit-testing in the viewport

  • Requirement: Where icon overlays are used, the system shall draw a named GUI icon at a world position with a device-coordinate offset and shall test whether a given point lies on a previously drawn icon.
  • Priority: Optional
  • Rationale: In-canvas interactive icons (e.g. handles, badges) need to be drawn and clicked.
  • Source: tc_visualize/TiVisualizer.h (drawIcon, testPointOnIcon); tc_visualize/visFunc.h (tc_draw_icon, tc_test_point_on_icon).
  • Verification: Test

FR-VIS-022 — Off-screen redraw acceleration and caching

  • Requirement: Where acceleration is enabled, the system shall render into an off-screen bitmap (back buffer) and blit it to the screen, and shall cache redrawn regions, to avoid flicker and redundant repaints.
  • Priority: Conditional
  • Rationale: Large nests and drawings must repaint smoothly during pan/zoom. Related non-functional targets: see [[40 - Non-Functional Requirements]].
  • Source: tc_visualize/TiRedrawAccelerator.h (isAccelerationEnabled, createBitmap, activateBitmap, deactivateBitmap, drawBitmap, deleteBitmap); tc_visualize/TiRedrawCache.h (TsRedrawCacheBox); tc_viewer/XCadViewer/TcViewport.h (createBackBufferDC, isBackBufferCreated).
  • Verification: Test

FR-VIS-023 — Raster hardcopy to image file/stream

  • Requirement: When the user requests a hardcopy, the system shall write a raster image of a specified screen region, viewport or the whole drawing area to a bitmap file (BMP) or output stream, at a specified pixel size and in either colour or monochrome, and shall also support TIFF raster output.
  • Priority: Essential
  • Rationale: Screenshots are needed for reports, documentation and archiving.
  • Source: grit/drive/hardcopy.cpp (tc_hardcopy, tc_hardcopy_viewport, tc_hardcopy_all); grit/drive/tc_drive.h (hardcopy_to_bmp, setBitmapDcGrit); tc_visualize/visFunc.h (useBitmapDc, writeAndCloseBitmapDc, t_useMonochromeBitmap); tc_viewer/viewer_drive/hardcopy.cpp; tc_bitm/tc_bitm.h (BitMap::write_tiff, writeBitmapBinary).
  • Verification: Test

FR-VIS-024 — Raster/vector image export from the viewer

  • Requirement: Where the embeddable viewer is used, the system shall export the currently loaded view as an SVG or BMP image.
  • Priority: Conditional
  • Rationale: Vector (SVG) and raster (BMP) export feed web previews, documentation and part catalogues.
  • Source: tc_viewer/TcViewerInterface.h (save, TeFileFormat::e_svg write-only, e_bmp write-only, t_bitmapIsMonochrome); see [[30 - External Interface Requirements]].
  • Verification: Test

FR-VIS-025 — Print current drawing to a Windows printer

  • Requirement: When the user prints, the system shall render the current drawing to a Windows GDI printer device context, applying page margins, aspect-ratio (non-square-pixel) correction, a fit/scale factor and page orientation, and shall optionally print a configured text header.
  • Priority: Essential
  • Rationale: Direct printing to office printers is the everyday hardcopy path; aspect correction ensures circles are not distorted.
  • Source: grit/drive/elem_win.cpp (setPrinterDC, unsetPrinterDC, device-caps margins, verhaeltnis, plotScale, orientation); grit/drive/tc_drive.h (tc_getPrinterScale, printTextHeader); tc_visualize/visFunc.h (getPrinterScaleFactor).
  • Verification: Test

FR-VIS-026 — HPGL/HPGL2 pen plotting via configurable profile

  • Requirement: Where a plotter is configured, the system shall generate HPGL or HPGL2 plot output driven by a plotter profile that defines the HPGL2 flag, rotation, available pen colours, line types, symbols, paper (DIN) sizes and the host/PC interface, loaded from the plotter configuration file.
  • Priority: Conditional
  • Rationale: Large-format pen/inkjet plotters are a distinct legacy output path with device-specific capabilities.
  • Source: tc_plot/plotdate.h (DB_Plotter, DB_Papier); tc_plot/plotlese.cpp (db_lese_plotter_konfig, db_lese_papier_daten, db_gib_interface); tc_plot/plotutil.h (tc_plott_start, tc_plott_ausgabe, tc_plott_ende).
  • Verification: Test

FR-VIS-027 — Plot scaling to paper or fixed factor

  • Requirement: When plotting, the system shall either scale the drawing to fit the selected paper size or apply a caller-specified fixed scale factor, shall support plotting the whole drawing or only a section, and shall reject a scale factor that would exceed the paper or an invalid paper/drawing area.
  • Priority: Conditional
  • Rationale: True-to-scale plots and section plots are required for shop-floor use; oversize requests must fail cleanly.
  • Source: tc_plot/plotber.cpp (tc_pruefe_und_setze_skalierung: was full/section, skfakt, errors 6100 "Skalierungsfaktor zu gross" / 6102 "Papier und/oder Zeichenbereich falsch"); tc_plot/plotber.h (tc_get_plott_scale).
  • Verification: Test

FR-VIS-028 — Plot annotations (frame, title, filename, part numbers, scale)

  • Requirement: When plotting, the system shall optionally add a border frame, a title, the source filename, part numbering and a scale-factor note to the plot.
  • Priority: Conditional
  • Rationale: Plots used as production paperwork must be self-identifying.
  • Source: tc_plot/plotutil.h (tc_plott_frame, tc_plott_titel, tc_plott_datei, tc_plott_teil_nummer, tc_plott_skal_faktor); tc_plot/tc_plot.h (db_plotte_zeichnung params frame, titel, datei).
  • Verification: Demonstration

FR-VIS-029 — Plot clipping to the plot area

  • Requirement: The system shall clip plotted lines and points to the defined plot area so that nothing is emitted outside the paper bounds.
  • Priority: Conditional
  • Rationale: Prevents out-of-bounds pen moves and stray marks when a section or oversized drawing is plotted.
  • Source: tc_plot/plotclip.h (tc_clip_plott_line, tc_clip_plott_punkt, tc_set_plott_clip_bereich, tc_get_plott_clip_bereich).
  • Verification: Test

FR-VIS-030 — Projected (2D/3D) element output

  • Requirement: Where a projection is active, the system shall apply a transformation (projection) matrix to each element before plotting, including arcs, so that projected views (e.g. isometric) are produced.
  • Priority: Conditional
  • Rationale: Tube and folded parts are plotted through a projection rather than as raw model coordinates.
  • Source: tc_plot/plotelem.h (plotte_* with TcTransformationMatrix* abbild, abart); tc_plot/plotten.h (tc_plott_2D_bogen, tc_plott_3D_bogen).
  • Verification: Analysis

FR-VIS-031 — Standalone and embeddable part viewer

  • Requirement: The system shall provide a standalone GeoViewer application and an ActiveX/OCX viewer control that load and render part files in GEO, MI (ME10), IGES, DXF, DSTV and DWG formats.
  • Priority: Conditional
  • Rationale: Lightweight viewing of parts (including embedded in web pages / host applications) without the full CAD/CAM suite.
  • Source: tc_viewer/geoviewerMain/ (geoviewer.exe, TcGeoViewerMain.cpp); tc_viewer/geoViewerPlugin/ (geoViewerPlugin.ocx, TcHTTPFile); tc_viewer/TcViewerInterface.h / TiGeoViewer.h (loadFile, TeFileFormat); see [[11 - FR - Import, Export & File Formats]].
  • Verification: Demonstration

FR-VIS-032 — Part-in-Part (PiP) family visualization

  • Requirement: Where a PiP model is loaded, the system shall visualise part families and their placed instances, set/query per-part and per-family contour and fill colours, show or hide individual parts and families, and pick a part by device position.
  • Priority: Conditional
  • Rationale: Interactive multi-part previews (e.g. nested or family drawings) need per-part styling and selection.
  • Source: tc_viewer/TiGeoViewer.h (addPipPart, positionPipPart, setFillColorPart, setContourColorPartFamily, showPart, showPartFamily, pickPipPart); tc_viewer/XCadViewer/TcPartFamily.*, TcPart.*.
  • Verification: Test

FR-VIS-033 — Interaction schemes and split viewports

  • Requirement: The system shall support selectable interaction schemes — desktop single-view, passive single-view and touch-screen double-view — and shall support splitting the drawing area into an upper and a lower viewport, where in touch double-view the upper viewport is fully zoomed and defines the zoom window of the lower viewport.
  • Priority: Conditional
  • Rationale: The same viewer serves office desktops and shop-floor touch panels with different navigation ergonomics.
  • Source: tc_viewer/XCadViewer/XCadViewerControl.h (TeInteractionScheme: e_DoubleViewportTouch, e_SingleViewportPassive, e_SingleViewportDesktop; TeViewport upper/lower); TcTouchScreenDoubleViewInteractionMediator.h, TcDesktopSingleViewInteractionMediator.h, TcTouchScreenSingleViewInteractionMediator.h.
  • Verification: Demonstration

5. External Interfaces (area-specific)

  • Display / GDI: Windows GDI device contexts for on-screen rendering, off-screen bitmap DCs and printer DCs (grit/drive/elem_win.cpp, vis_gdi). Non-Windows path uses X11 (grit/drive/x11_def.h, elem_ux.cpp).
  • Printing: Windows GDI printer via setPrinterDC, GetDeviceCaps, Escape(SET_BOUNDS) (grit/drive/elem_win.cpp).
  • Plotting: HPGL / HPGL2 pen plotters over a host or PC interface defined in the plotter configuration file (tc_plot, DB_Plotter).
  • Image files: BMP (write), TIFF (write), SVG (write, viewer). Read/render formats via the viewer: GEO, MI (ME10), IGES, DXF, DSTV, DWG.
  • Configuration files: GRIT colour table (GRITCOL.24), RGB table (RGB.TXT), fonts (GRITFONT), icons (GRITICON), units (GRITUNIT) referenced from *.ORG/*.org ini files.
  • Embedding: ActiveX/OCX control and standalone executable; part streaming over HTTP (TcHTTPFile).

Full specifications and format details: see [[30 - External Interface Requirements]] and [[11 - FR - Import, Export & File Formats]].

6. Assumptions & Constraints

  • The graphics stack is Windows-centric (Win32 GDI, ActiveX/OCX, HDC/RECT/BITMAPINFO); an X11/HP-UX path exists in grit/drive but appears legacy. Cross-cutting platform constraints: see [[50 - Constraints & Assumptions]].
  • Colour, line-type and marker sets are fixed-size enumerations (11 element colours, 9 line types, 14 markers, 27 fill colours); some plotter/GRIT colour indices are hard-coded to match external tables (gritcol.xxx), so the external tables must stay in sync with the code (tc_darst.cpp comments).
  • The rendering model is fundamentally 2D with world/device mapping; "3D" output is achieved by projecting geometry through a transformation matrix (Abbildungsmatrix) prior to drawing/plotting rather than by a real-time 3D shaded engine in these modules.
  • TC_Viewport/TC_Driver are opaque void* handles; callers must treat them as tokens.
  • The visualizer offers a headless backend (vis_none), implying batch/server rendering must be possible without a display.
  • View-content visibility is configuration-driven and application-mode dependent (APPLIC_NUMMER).

7. Open Questions & Ambiguities

  • True 3D / hidden-line / shaded views: no evidence of a real-time shaded or hidden-line 3D renderer was found in tc_viewer/tc_visualize/tc_plot/grit/drive; 3D display for bending (tc_lift) and tube (tc_rohr) likely lives in those modules and is owned by other analysts. The scope item "hidden-line/shaded views" could not be confirmed here — confirm where (if anywhere) shaded 3D is implemented.
  • Free rotation: only a 180° viewport orientation flip (TeViewportOrientation::e_Rotate180) and rapid-move direction enums were found; interactive free rotate of the view was not evidenced in these modules.
  • tc_bitm ownership: the bitmap module serves both image export (visualization) and collision detection (kollision_element, bitmkoll.cpp); the collision use belongs to [[17 - FR - Nesting & Palletizing]]. Confirm the split.
  • Plotter configuration file: the exact on-disk location/name and format of the plotter-config file read by db_lese_plotter_konfig (via tc_fopen) were not located in the snapshot; the paper/pen tables are defined but the shipped profile file needs confirmation.
  • db_plotte_zeichnung parameters: the precise meaning of some flags (was, fakt) versus the scale factor skfakt is inferred from plotber.cpp comments and not from an authoritative spec.
  • GDI vs. GRIT backend selection: how the runtime chooses between vis_gdi, vis_grit and vis_none (build-time vs. runtime, per edition) was not fully determined.
  • Extended constant colours (128–154): mapping of TC_COL_* display constants to the external RGB table and their relationship to the 11-entry element palette is only partially evidenced.
