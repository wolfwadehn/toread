Requirements Traceability Index

This index maps every one of the 603 reverse-engineered requirements in the TruTops CAD/CAM SRS suite back to the source modules, directories and database objects they were derived from. It is intended for coverage analysis (which requirements exercise a given module) and migration planning (which requirements are at risk when a module is retired, ported or rewritten). Because the requirements were recovered by static analysis of the legacy source, every trace here is a derivation link — the requirement was inferred from the named code/config/schema evidence — rather than a forward design allocation.

The register spans the thirteen functional-requirement documents ([[10 - FR - CAD Geometry & Drawing Editing|10]]–[[23 - FR - Automation, Scripting & Integration|23]]), the [[30 - External Interface Requirements|external interface requirements]] (IF-*), the [[40 - Non-Functional Requirements|non-functional requirements]] (NFR-*) and the [[50 - Constraints & Assumptions|constraints and assumptions]] (CON-*). The non-normative scoping documents ([[01 - Vision & Scope|01]], [[02 - Stakeholders & Actors|02]], [[03 - System Context & Architecture Overview|03]], [[04 - Domain Model & Glossary|04]]) carry no numbered requirements and are not listed in the register. Domain terms referenced below are defined in [[04 - Domain Model & Glossary]].

[!note] How to read a trace A requirement may derive from several modules; it therefore appears under each of its source modules in Section 1 (reverse lookup) and lists its full set of source paths in Section 2 (register). Source modules are shown at their top-level directory / module granularity in Section 1; the register preserves the exact sub-paths, headers and database tables. SQL Server schema tables (e.g. Punch.MASCHINE, Common.MAT_SHEET, DATADICT.*) and the Databases/... provisioning scripts are collapsed into a single Databases bucket in Section 1 — the per-table detail lives in the register and in each owning FR document.

[!note] Tier-2 detail sub-suites are traced in their own documents The Tier-2 detail sub-suites — the CAD sub-suite (FR-CAD-CRE/EDT/DIM/ATT/VAR/KRN/CAT/APX, docs 10.1–10.8) and the Bending sub-suite (FR-BEND-NC and FR-CELL-CFG/ROB/GRP/HDL, docs under Requirements/ToPs 600 Bending/) — are not included in this 603-item register. Each Tier-2 requirement cites its source (for the bending sub-suite, chiefly the ToPs 600 Bend/BendGripperConf SQL schema and the Common/TRUMPF/.../API/BendAPI surface) inline in its own document. See [[16.7 - Cell7000 — Bend Automation Data Model (Reference)]] for the bending table→document map.

3.4 Coverage gaps and caveats

  • [[22 - FR - UI Framework, Dialogs & Interaction (GRIT)]] carries 31 numbered requirements (FR-UI-001–FR-UI-031). The GRIT UI framework is now specified as discrete functional requirements covering mask definition/storage, the MMK interpreter and mini_sql data binding, input widgets and validation, finder lists and popups, interactive selection, transaction-based undo/redo, unit and multi-language rendering, keyboard/mouse handling, runtime configuration and the Qt GUI bridge. In addition to these FR-UI-* requirements the framework is also traced through interface requirements ([[30 - External Interface Requirements|IF-049]], [[30 - External Interface Requirements|IF-060]], [[30 - External Interface Requirements|IF-062]], [[30 - External Interface Requirements|IF-063]], [[30 - External Interface Requirements|IF-069]]), several NFR-* (NFR-013–015, NFR-017) and constraints CON-007–009.
  • Non-normative documents by design. [[01 - Vision & Scope]], [[02 - Stakeholders & Actors]], [[03 - System Context & Architecture Overview]] and [[04 - Domain Model & Glossary]] contain no requirements; this is expected for scoping/context documents and is not a gap.
  • The Databases bucket is the single largest trace target. SQL Server schema tables and provisioning scripts are cited across punch, laser, tube, bending, nesting, material/technology, data-management, NC and NFR/constraint requirements. Migrating or re-versioning the DATADICT-driven schema therefore affects the widest set of requirements; per-table impact must be read from the register and the individual FR documents, not from this collapsed bucket.
  • Contested / unowned modules. Several modules are flagged in the source documents' open questions as mis-attributed or not yet owned, so their requirement coverage may shift: tc_forml (machine-technology formula collection, likely Bending/Technology, currently untraced); tc_geoPlan (topological plan/graph model, role vs tc_dbase unresolved); tc_stl/stl_tech (Stanz-Laser combi technology, not stereolithography — the only STL trace, [[30 - External Interface Requirements|IF-017]], documents an absent 3D-STL capability); tc_scan, tc_gts, tc_bitm, tc_mtl (parting-cut / nesting bitmap / collision, likely Nesting rather than their current homes); tc_aps (lead-in variant generation, NC/Laser rather than Production Planning); tc_optimizer, tc_bsort, tc_fsel (cutting-sequence/thermal/batch-sort, likely NC Generation). tc_optimizer currently appears only via [[40 - Non-Functional Requirements|NFR-003]].
  • Shared modules span areas. tc_bof (GRIT masks), tc_dbase, tc_cad/cad_asm, convmain, grit, ini_files, Databases and tc_las/tc_stz each trace to requirements owned by multiple documents; ownership boundaries for AutoCut (punch vs laser), MFN (nesting vs NC), and tc_profil (CAD vs bending vs tube) remain open per the respective FR documents. See [[04 - Domain Model & Glossary]] for the shared vocabulary and [[03 - System Context & Architecture Overview]] for the authoritative module-to-area map.
  • Priority mix. With Essential requirements the largest single class, the reverse-engineered baseline is weighted toward must-have capability; Conditional requirements are predominantly edition-, machine- or licence-gated features (see [[40 - Non-Functional Requirements|NFR-027]] and [[50 - Constraints & Assumptions|CON-028]]).
