FR — Production Planning & Projects

Reverse-engineered requirement draft — derived from static analysis of legacy source, NOT an authoritative specification. Treat SHALL statements as reconstructed intent.

1. Purpose & Scope

This area covers the organisational layer that sits between nesting/NC programming and the shop floor: how parts are grouped into orders/jobs (Auftrag / Schachtelauftrag), how a programming project (Programmierprojekt, "PPJ") holds the sheets, parts, tools, machine and material for one order, and how the finished NC programs for many sheets are collected into a production plan (Produktionsplan) that is exported to the machine control via the external NcLink tool.

Concretely the area provides:

  • Programming-project / workbook management — creating a project from a nesting order, opening/saving it as a versioned XML .ppj file, tracking its lifecycle state, copying it to another machine, and resetting it (tc_programmierProjekt, gritx tec_ppj, aPnLasPpj).
  • Sheet (Rohling/Tafel) and part-overview (Mustertafel) management inside an order, including repeat counts, per-sheet processing state, automatic TMT creation and transfer of machining from representative parts to all identical parts.
  • Production-plan assembly — bracketing several NC programs (Fertigungsauftrag entries) into an NcListe with target counts, and driving NcLink to produce the machine production plan (tc_prodplan, gritx aTcoProdplan, tco_prodplan).
  • Nesting-order / job grouping of captured parts with quantities, priorities and due dates, plus job export/import and the job-order interface (Nest.TEILE_ERFASSEN, Nest.TAFEL_VARIANT, gritx aNestAllg, aNestAuftrag).
  • Job execution feed to production — automatic run through all sheets and a "declare job done" hand-off to TruTops Fab.

Editions served: ToPs 300 (punch), ToPs 100 (laser) and ToPsNest are the in-scope editions. The programming-project framework is shared through tc_stz (its concrete product handler is the legacy-named TcPpjToPs300), so the same PPJ machinery is used by punch and laser; the production plan is offered for ToPs 300 / ToPs 100. Real scheduling (assigning jobs to machine time slots against due dates) is performed by the external TruTops Fab MES and is not implemented here — see Open Questions.

Cross-cutting: domain terms → [[04 - Domain Model & Glossary]]; file/DB/tool interfaces → [[30 - External Interface Requirements]]; nesting itself → [[17 - FR - Nesting & Palletizing]]; NC/lead-in → [[18 - FR - NC Generation & Motion Optimization]]; part/material handling → [[12 - FR - Part & Data Management]] and [[19 - FR - Tools, Machines, Materials & Technology]].

2. Capability Overview

  • Create a programming project from a nesting order (job file), or open an existing one, falling back to creation if none exists.
  • Persist the project as a versioned XML .ppj (PPJ_FOLDER) document carrying header metadata, machine key, material, sheets, parts and dynamic tools.
  • Enforce machine, material and document-version consistency when a project is opened.
  • Track the lifecycle state of an order (nested → in-progress → completed) and the per-sheet processing state (unprocessed → processed → NC-generated → auto-TMT).
  • Manage the sheets (Rohlinge) of an order — repeat counts, navigation (first/last/next/previous/specific), activation, TAF/TMT/NC/setup-plan IDs, and validity/consistency of those references.
  • Build a master sheet / part overview (Mustertafel/Teileuebersicht) of representative parts, apply machining once, and transfer it to all identical parts; optionally auto-generate TMTs.
  • Assemble a production plan (NcListe) of production jobs (Fertigungsauftrag) and generate it through NcLink, emitting a machine plan file (.LST/.TPP) plus a human-readable overview (HTML/TXT/XML).
  • Group captured parts into a nesting order with quantities (actual/min/max), priority, due date and rotation/mirror options; export/import and join orders; expose a job-order interface.
  • Copy a project to a different machine, reset/delete it, run all sheets automatically, and declare a job done to TruTops Fab.

4. Functional Requirements

FR-PLAN-001 — Create programming project from a nesting order

  • Requirement: When the user opens an order that has no existing programming project, the system shall create a new programming project from the nesting order by reading the job (Schachtelauftrag) data, creating one blank (Rohling) per determined sheet, and preparing the used parts for entry.
  • Priority: Essential
  • Rationale: The programming project is the working container for all downstream planning; it must be derivable automatically from a nesting order.
  • Source: tc_programmierProjekt/ppj_manager/TcPpjAuftragManager.h (erzeugeProgrammierProjekt, oeffneProgrammierProjekt, 3-step doc comment); gritx tec_ppj.gritx (FUNC_AuftragLadenAll*).
  • Verification: Test

FR-PLAN-002 — Open existing project, create if absent

  • Requirement: When the user requests to open a programming project for an order, the system shall search for an existing project and load it, and if none can be loaded it shall create a new one.
  • Priority: Essential
  • Rationale: Users resume prior work seamlessly; a missing project must not block the workflow.
  • Source: TcPpjAuftragManager.h (oeffneProgrammierProjekt, oeffnePPJ, ladeProgrammierProjektDatei); gritx tec_ppj.gritx (FUNC_AuftragLadenAllJobSelect, FUNC_AuftragLadenAllPpjSelect, FUNC_AuftragLadenAllLoad); aPnLasPpj.gritx (aPnLasLoadJob, aPnLasShowJobManagement).
  • Verification: Test

FR-PLAN-003 — Persist project as versioned PPJ XML document

  • Requirement: The system shall persist a programming project as an XML document of type PPJ_FOLDER containing a header (PPJ version, application, generator, database DSN, creation and modification timestamps), the order/workfile block, material, machine, dynamic tools, sheet entries and parts.
  • Priority: Essential
  • Rationale: The .ppj file is the durable representation shared between sessions and applications.
  • Source: tc_programmierProjekt/programmier_projekt/TcArbeitsMappe.h (speichern, TcKopf); ppj_persistenz/TcPpjXmlKeys.h (element keys header, workfile, material, machine, entry, part; S_PPJ_DocumentVersion 1.0–5.0).
  • Verification: Inspection

FR-PLAN-004 — Bind order to machine, material and job file

  • Requirement: The system shall store, for each programming project, the order-ID, the machine key (identifier, type, control identifier and version), the material ID and thickness, and the associated job filename.
  • Priority: Essential
  • Rationale: These identify what is produced, on which machine, and from which material — the minimum needed to program and produce the order.
  • Source: TcArbeitsMappe.h (m_auftragsID, m_maschinenSchluessel, m_materialID, m_materialDicke, m_jobFileName); TcPpjXmlKeys.h (job-ID, job-filename, material-ID, material-thickness, machine-identifier, control-identifier).
  • Verification: Inspection

FR-PLAN-005 — Reject incompatible PPJ document version

  • Requirement: If a programming-project file has a document version incompatible with the running software, then the system shall refuse to load it and report an invalid-version error.
  • Priority: Essential
  • Rationale: Silently reading an incompatible schema would corrupt planning data.
  • Source: TcArbeitsMappe.h (TeOpenError::e_openInvalidVersion, istVersionOk, ermittleElementVonVersion); TePpjErrors.h (e_openInvalidVersion).
  • Verification: Test

FR-PLAN-006 — Verify machine matches the order on load

  • Requirement: If the machine currently selected differs from the machine stored in the order, then the system shall detect the mismatch and report an invalid-machine condition before loading.
  • Priority: Essential
  • Rationale: NC programs and setups are machine-specific; loading an order onto the wrong machine produces unusable output.
  • Source: TcPpjAuftragManager.h (pruefeMaschine returns 1 on mismatch); TePpjErrors.h (e_invalidMachine).
  • Verification: Test

FR-PLAN-007 — Verify order material exists on load

  • Requirement: If the material recorded in an order does not exist in the database, then the system shall report an unknown-material condition.
  • Priority: Essential
  • Rationale: Nesting, technology and production depend on a valid material record.
  • Source: TcPpjAuftragManager.h (pruefeMaterial returns 1 if absent); TePpjErrors.h (e_unknownMaterial).
  • Verification: Test

FR-PLAN-008 — Track order lifecycle state

  • Requirement: The system shall maintain, for each order/workbook, a lifecycle state of nested, in-progress or completed, and shall make it queryable.
  • Priority: Essential
  • Rationale: Users and downstream automation need to know how far an order has progressed.
  • Source: TcArbeitsMappe.h (TeAuftragsZustand: e_geschachtelt, e_inArbeit, e_abgeschlossen; getBearbStatus).
  • Verification: Test

FR-PLAN-009 — Copy a project to another machine

  • Requirement: Where the copy-order feature is available, the system shall copy a programming project so it can be produced on a different machine, and if a project for that machine already exists it shall not overwrite it but report that it already exists.
  • Priority: Conditional
  • Rationale: The same parts are often produced on alternative machines; duplicate creation must be prevented.
  • Source: TcPpjAuftragManager.h (kopierePpjAuftrag); TePpjErrors.h (TePpjCopyError::e_copyAlreadyExists); gritx tec_ppj.gritx (FUNC_PPJ_AuftragKopieren, FUNC_PPJ_Dlg_BAufAuswCpyBtnChk).
  • Verification: Test

FR-PLAN-010 — Reset / delete an order and its generated files

  • Requirement: When the user resets or deletes an order, the system shall remove the order's TMT and NC-program references and physically delete those files, optionally also removing the .ppj file and working GMTs.
  • Priority: Essential
  • Rationale: Re-programming an order requires a clean slate; stale TMT/NC files must not be produced.
  • Source: TcPpjAuftragManager.h (zuruecksetzenAuftrag, loeschenAuftrag, loeschePpjDatei); gritx tec_ppj.gritx (FUNC_PPJ_AuftragReset, FUNC_PPJ_AuftragLoeschen).
  • Verification: Test

FR-PLAN-011 — Manage sheets of an order with repeat counts

  • Requirement: The system shall represent each sheet of an order as an entry (Rohling) carrying a sheet number, a repeat count (Wiederholzahl) stating how often the sheet is produced, and references to its TAF, TMT, NC-program and setup-plan.
  • Priority: Essential
  • Rationale: Production quantity per sheet and the links to its geometry/NC artefacts are core planning data.
  • Source: ppj_adapter/TcPpjRohling.h (getWiederholzahl, getTAFID, getTMTID, getNcCodeID, getEinEPlanID, getTafelnummer); programmier_projekt/TcEintrag.h (m_wiederholzahl, m_lfnTafelNummer); TcPpjXmlKeys.h (repeat-count, no-of-entry).
  • Verification: Inspection

FR-PLAN-012 — Navigate and activate sheets within an order

  • Requirement: The system shall let the user move to the first, last, next, previous or a specific sheet of an order and activate it as the current sheet.
  • Priority: Essential
  • Rationale: Sheet-by-sheet programming and review is the central interaction in an order.
  • Source: ppj_manager/TcPpjTafelManager.h (liefereNameErster/Letzter/Naechster/Vorheriger/GesuchterTafel..., aktiviereTafel); gritx aNestAuftrag.gritx (aNestAuftragErsteTafel, ...LetzteTafel, ...NaechsteTafel, ...VorherigeTafel, ...EinzelTafel, ...AlleTafeln); aPnLasPpj.gritx (aPnLasLoad{First,Last,Next,Prev}Sheet).
  • Verification: Test

FR-PLAN-013 — Track per-sheet processing state

  • Requirement: The system shall maintain for each sheet a processing state of unprocessed, processed, NC-generated or auto-TMT, and shall report the current sheet's state.
  • Priority: Essential
  • Rationale: The operator must see which sheets still need machining or NC generation.
  • Source: TcEintrag.h (TeTafelZustand: e_unbearbeitet, e_bearbeitet, e_NCerzeugt, e_autoTMT); TcPpjTafelManager.h (liefereZustandAktTafel, bewerteTafelBearbeitungsZustand).
  • Verification: Test

FR-PLAN-014 — Report aggregate NC-generation state across sheets

  • Requirement: The system shall compute and report the order-wide NC state as: no NC generated for any sheet, NC generated for at least one sheet, or NC generated for all sheets.
  • Priority: Essential
  • Rationale: Determines whether the order is ready to be assembled into a production plan.
  • Source: TcPpjTafelManager.h (liefereZustandTafeln returns 10 / 30 / 40).
  • Verification: Test

FR-PLAN-015 — Auto-generate TMT for sheets lacking one

  • Requirement: Where automatic TMT creation is enabled, the system shall, for each sheet (TAF) that has no TMT yet, adopt the machining from the part-overview parts and save a TMT for that sheet.
  • Priority: Conditional
  • Rationale: Removes repetitive manual machining of identical sheets; feature is controlled by a flag.
  • Source: TcPpjTafelManager.h (erzeugeAlleAutoTmts, erzeugeEinzelnesAutoTmt, erzeugeTmt); gritx tec_ppj.gritx (FUNC_AuftragCheckMusterTafel).
  • Verification: Test

FR-PLAN-016 — Invalidate dependent TMT/NC when a sheet changes

  • Requirement: If a sheet's geometry or machining changes such that its TMT or NC program is no longer current, then the system shall mark the affected TMT and NC-program references invalid and evaluate TAF/TMT compatibility and NC currency.
  • Priority: Essential
  • Rationale: Prevents producing from stale NC programs that no longer match the sheet.
  • Source: TcPpjTafelManager.h (ungueltigsetzenTmtIDs, zuruecksetzenTmtIDs, zuruecksetzenAutoTmtIDs); TcPpjRohling.h (bewerteTafelNCAktualitaet, isTAFTMTKompatibel, istGueltigTmtID, istGueltigNcCodeID); TePpjErrors.h (e_TAFsAreNewerThanTMTs).
  • Verification: Test

FR-PLAN-017 — Assign NC program and setup-plan IDs to a sheet

  • Requirement: When an NC program or setup plan (Einrichteplan) is produced for the current sheet, the system shall associate its ID with that sheet.
  • Priority: Essential
  • Rationale: The link from sheet to its NC/setup artefacts is required for production and the production plan.
  • Source: TcPpjTafelManager.h (einfuegenNcProgrammId, einfuegenEplanId, einfuegenTmtId, liefereNcNameAktuellerTafelImAuftrag).
  • Verification: Test

FR-PLAN-018 — Build a master sheet (part overview) of representative parts

  • Requirement: When the user opens the part overview, the system shall create a master sheet holding one representative per distinct part and rotation, laid out on a grid whose orientation (horizontal or vertical) is configurable.
  • Priority: Essential
  • Rationale: Machining parts once on a representative and propagating is the defining efficiency of the programming project.
  • Source: ppj_manager/TcPpjTeileUebersManager.h (erzeugeTeileUebers, TeTeileUebersAusrichtung horizontal/vertical, umschaltenTeileUebersichtAusrichtung, zeichneRasterLinienUmTeil); gritx tec_ppj.gritx (FUNC_MusterTafelAnzeigen, FUNC_AuftragTafUebersicht).
  • Verification: Test

FR-PLAN-019 — Transfer machining from representatives to all identical parts

  • Requirement: When the user leaves the part overview, the system shall transfer the machining defined on each representative part to every identical part on the production sheets.
  • Priority: Essential
  • Rationale: Ensures all instances of a part are machined consistently from a single definition.
  • Source: TcPpjTeileUebersManager.h (uebertrageBearbeitungen, speichereRepraesentantenTeile); TiPpjToPs.h (uebertrageBearbeitungen strategy method); TcPpjAuftragManager.h (verlasseTeileUebersicht).
  • Verification: Test

FR-PLAN-020 — Verify part overview before it is left

  • Requirement: When the user attempts to leave the part overview, the system shall verify that the number of used tools does not exceed the machine's available tools and that no required disposals are missing at inner or outer contours, and shall report any violation.
  • Priority: Conditional
  • Rationale: Catches un-producible programs (tool overflow, missing part removal) before NC generation; depends on machine/technology data.
  • Source: TcPpjTeileUebersManager.h (verlasseTeileUebersichtPruefung, pruefeAnzahlBearbAufTeileUebersicht); TiPpjToPs.h (ermittleMaxAnzWzg, ermittleAnzFehlendeEntsorgungen).
  • Verification: Test

FR-PLAN-021 — Manage dynamic multitools within a project

  • Requirement: Where the machine supports dynamic multitools, the system shall read the current tool box's dynamic-multitool composition, store it in the project, and restore it into the tool box when the project is reloaded.
  • Priority: Conditional
  • Rationale: Punch dynamic-multitool assignments are part of the reproducible program and must survive save/load; feature is punch-specific (ToPs 300).
  • Source: TcPpjTeileUebersManager.h (exportWerkzeuge, importWerkzeuge, getWerkzeuge); TcArbeitsMappe.h (TyDynamicMultiToolPunchesByDynamicMultiToolId); TcPpjXmlKeys.h (dynMultitool, dynIdentNr, dynStempel).
  • Verification: Test

FR-PLAN-022 — Assemble a production plan of production jobs

  • Requirement: The system shall collect NC programs into a production-plan list (NcListe), where each production job (Fertigungsauftrag) carries the NC file, the NC program name, a target count (Sollzahl) and technology data (sheet material, setup-plan path, NC duration, sheet X/Y dimensions and palletizing mode).
  • Priority: Essential
  • Rationale: Grouping finished NC programs with quantities is the deliverable that drives a machine's production run.
  • Source: tc_prodplan/prodplan_tech/TcNcListe.h (TcFertigungsAuftrag, TsTecParameter, addNeueZeile); tc_prodplan/prodplan_asm/prodplan_produktionsplan.hpp (TcASMProduktionsplan, pushFAT).
  • Verification: Test

FR-PLAN-023 — Reject invalid entries in the production plan

  • Requirement: If an NC program with the same program name is already in the production plan, or a target count is less than 1, then the system shall reject the entry and raise an insertion error.
  • Priority: Essential
  • Rationale: Duplicate programs and zero quantities would corrupt the plan sent to the machine.
  • Source: TcNcListe.h (addNeueZeile ... throw( TxEinfuegeFehler ), istVorhandenNCP, M_TEXT_NCPVORHANDEN, M_TEXT_ANZAHLISTNULL).
  • Verification: Test

FR-PLAN-024 — Generate the production plan via NcLink

  • Requirement: When the user creates a production plan, the system shall invoke the external NcLink tool either over an explicit list of NC files or over the pending nesting order (passing the order name and job file), and shall pass the resulting plan back for display.
  • Priority: Essential
  • Rationale: NcLink is the engine that sequences the programs and formats the plan for the control.
  • Source: gritx aTcoProdplan.gritx (aTcoCreateProdplanInterakt — asm_call( prp_produktionsplan ... ), NcLink params -s, -vj, -p, -u -y); tco_prodplan.gritx (FUNC_ErstelleProdPlan, FUNC_StarteNcLink, M_ProduktionsplanErstellen); prodplan_produktionsplan.hpp (getNcLinkOptionen, setNcLinkParameterFilename).
  • Verification: Demonstration

FR-PLAN-025 — Emit machine-specific plan file and human-readable overview

  • Requirement: The system shall produce the production plan in the format required by the machine control — a .LST file for production-plan types below 30 and a .TPP file for types 30 and above — and shall additionally produce a viewable overview/log in HTML, text or XML; for machines without table output it shall render a paper production plan via a configurable XSL stylesheet.
  • Priority: Conditional
  • Rationale: Different controls consume different plan formats; the operator also needs a readable summary. The exact format is machine-rule dependent.
  • Source: gritx aTcoProdplan.gritx (aTcoShowProdplan .LST/.TPP by NcLinkProduktionsPlanTyp; aTcoShowProdplanOverview HTML/TXT/XML by NcLinkLogType); prodplan_produktionsplan.hpp (writeProduktionsplanLog, setStylesheet, M_PRP_ERSETZUNGSMODUS).
  • Verification: Demonstration

FR-PLAN-026 — View an existing production plan and its overview

  • Requirement: The system shall let the user select and open a previously created production-plan file and its overview/log in the appropriate viewer.
  • Priority: Optional
  • Rationale: Operators revisit previously generated plans without re-running NcLink.
  • Source: gritx aTcoProdplan.gritx (aTcoShowProdplan, aTcoShowProdplanOverview; ST_Prp_LetzterPfad, ST_Prp_LetztesLog, FUNC_GetInfoForFileType, FUNC_SystemCall).
  • Verification: Demonstration

FR-PLAN-027 — Group captured parts into a nesting order with quantities, priority and due date

  • Requirement: The system shall let parts be captured into a nesting order, recording per part the order name and customer-order name, actual/minimum/maximum quantities, the already-nested quantity, a priority, a due date (Termin) and rotation/mirror options.
  • Priority: Essential
  • Rationale: This is how orders are populated with what to produce, how many, and by when — the entry point of production planning.
  • Source: SQL Databases/SQLServerDatabase/Tables/Nest.TEILE_ERFASSEN.sql (TEIL_AUFTRAG, TEIL_KUNDE_AUFTRAG, TEIL_IST, TEIL_MIN, TEIL_MAX, TEIL_ANZ_GESCHACHELT, TEIL_PRIORITAET, TEIL_TERMIN, TEIL_DREHEN, TEIL_SPIEGELN); gritx aNestAuftrag.gritx (aNestAuftragTeileVerwalten, ...TeileAendern, ...TeileUebernehmen).
  • Verification: Test

FR-PLAN-028 — Manage sheet variants used by an order

  • Requirement: The system shall record alternative sheet variants that an order may use, each with sheet dimensions (X/Y/Z), material/workpiece index, storage-good ID and the nesting method used, and shall associate a variant with the order that uses it.
  • Priority: Conditional
  • Rationale: Orders can be produced on different stock sheet sizes/materials; the chosen nesting method is recorded per variant.
  • Source: SQL Nest.TAFEL_VARIANT.sql (VAR_ABMESS_X/Y/Z, VAR_WS_INDEX, VAR_LAGERGUTID, VAR_BENUTZT_VON_AUFTRAG, VAR_GENUTZTE_SCHACHTELART); gritx aNestAllg.gritx (aNestAuswahlTafeln, aNestNeuTafel).
  • Verification: Inspection

FR-PLAN-029 — Export, import and join nesting orders / jobs

  • Requirement: The system shall let the user export (back up) a nesting order or sheet to a file, import a previously backed-up order, and append/join another job file into the current order.
  • Priority: Optional
  • Rationale: Orders are exchanged between installations and combined; a backup/restore path is needed.
  • Source: gritx aNestAllg.gritx (aNestExportAuftrag → M_SchachtelAuftragBackup; aNestImportAuftrag → M_SchachtelAuftragBackupImport; aNestAnfuegenAuftrag → asm_call( nest_job join )).
  • Verification: Test

FR-PLAN-030 — Provide a job-order interface

  • Requirement: Where the job-order interface feature is present, the system shall launch a job-order interface through which orders can be exchanged with an external order source.
  • Priority: Conditional
  • Rationale: Integrates ToPs with upstream order management; availability depends on configuration/edition.
  • Source: gritx aNestAllg.gritx (aNestAuftragsschnittstelle → asm_call( invoke_with call 'asmNestingJob:launchJobOrderInterfaceGUI' )).
  • Verification: Demonstration

FR-PLAN-031 — Run all sheets of a job automatically

  • Requirement: Where automatic run is enabled, the system shall process the sheets of a job in sequence automatically, supporting start, continue-with-next and stop, and shall report progress to the user.
  • Priority: Conditional
  • Rationale: Unattended batch programming/production of a job's sheets; feature is edition/configuration dependent.
  • Source: gritx aPnLasPpj.gritx (aPnLasStartAutoRunKonfig, aPnLasStartAutoRunAuto, aPnLasContinueAutoRun, aPnLasStopAutoRun); tec_ppj.gritx (FUNC_AutoDurchlauf, FUNC_PPJ_AutoDurchlaufKommando); TiPpjToPs.h (logKundeFortschrittszeile).
  • Verification: Demonstration

FR-PLAN-032 — Declare a job as done to TruTops Fab

  • Requirement: Where TruTops Fab integration is present, the system shall report a job's completion to Fab by name so that the production-management system can update its status.
  • Priority: Conditional
  • Rationale: Closes the loop with the external MES; present only when Fab integration is configured.
  • Source: gritx aPnLasPpj.gritx (aPnLasDeclareJobAsDone → asm_call( invoke_with @ST_PPJ_JobFileName call 'stz_load:fab:declareJobAsDone' ), aPnLasLoadFabJob).
  • Verification: Demonstration

5. External Interfaces (area-specific)

Full definitions in [[30 - External Interface Requirements]].

  • .ppj programming-project file — XML PPJ_FOLDER document, versions 1.0–5.0; read/written by TcArbeitsMappe via keys in TcPpjXmlKeys.h.
  • Job file (.job / Schachtelauftrag) — container for orders and sheets; created/joined via nest_job, taf_nest:openNewEmptyJob, asmNestingJob.
  • Production-plan files — .LST and .TPP machine plan files; overview/log as HTML/TXT/XML; paper plan via XSL stylesheet.
  • NcLink — external executable invoked with CLI options (-s, -vj, -p, -t, -u -y, -x, -4 -n for Tube) and a NCLINK_GUI front-end; sequences programs and formats the production plan.
  • TruTops Fab (MES) — integration via stz_load:fab:* (declareJobAsDone, fab job loading) and the Python FabAutomationScript.py.
  • Nesting database (Nest schema) — Nest.TEILE_ERFASSEN (part capture with quantities/priority/due date), Nest.TAFEL_VARIANT (sheet variants); material joins to Common.MAT_MATERIAL.
  • TAF / TMT / GMT, NC programs and setup plans (Einrichteplan) — file artefacts referenced from sheets (TcPpjRohling).
  • PDM / part-data browser — used to resolve GMTs and file paths (pdm_browser, pdm_util).
  • Machine control transfer path — production-plan output directory from machine rule PRP_PfadModal or transfer path (TOPS_MACHINE_PATH).

Configuration keys observed (machine/system rule set): NcLinkProduktionsPlanTyp, NcLinkLiteModus, NcLinkLogType, PRP_PfadModal, PRODUKTIONSPLAN_PFAD, PRODLW (see [[30 - External Interface Requirements]] and [[19 - FR - Tools, Machines, Materials & Technology]]).

6. Assumptions & Constraints

Cross-cutting items → [[50 - Constraints & Assumptions]].

  • The production plan is not computed inside this codebase; the area delegates sequencing/formatting to the external NcLink tool and only assembles inputs and consumes outputs.
  • The NcListe holding the current production plan is a process-wide singleton (TcNcListe::GetInstance), so only one production plan is assembled at a time.
  • The programming-project product behaviour is provided through a strategy interface TiPpjToPs, concretely implemented in tc_stz as TcPpjToPs300; the framework itself is product-agnostic but assumes exactly one active project.
  • Order/PPJ persistence is file-based (.ppj, job files); the relational database primarily holds the nesting-order part list (Nest.TEILE_ERFASSEN) and sheet variants (Nest.TAFEL_VARIANT).
  • Quantities are tracked as actual/min/max plus already-nested count; the system assumes counts ≥ 1 for production-plan entries (FR-PLAN-023).
  • Time/date fields are stored as strings (TEIL_TERMIN nvarchar(16), TEIL_DATUM nvarchar(14)) rather than typed dates — a legacy constraint.

7. Open Questions & Ambiguities

  • tc_aps is misattributed to this area. Its content (TcAnfahrfahnenBuilder, TcAnfahrVariantenManager, TcKollisionsErmittler, TcToPs100GewichtungsStrategie, aps_util.h) is about lead-in/approach-flag (Anfahrfahne) variant generation and collision avoidance, i.e. NC/lead-in technology, not advanced planning/scheduling. It belongs to [[18 - FR - NC Generation & Motion Optimization]] / [[14 - FR - Laser Cutting (ToPs 100)]]. Recommend re-assigning; not documented here.
  • No true scheduling engine (mapping due dates to machine time slots / sequencing across machines) was found in this codebase. Due dates and priorities are captured (TEIL_TERMIN, TEIL_PRIORITAET) but the scheduling decision appears to live in external TruTops Fab. Confirm ownership.
  • The Nest.TEILE_ERFASSEN column TEIL_AUFTRAGS_ID is documented as "Ref. Tafel_erfassen", but no TAFEL_ERFASSEN table exists in this snapshot. The order/sheet header persistence location (legacy dbase job file vs. missing table) is unclear.
  • The semantics of the production-plan type numbering (< 30 → .LST, >= 30 → .TPP) beyond file extension selection are not evident from the masks.
  • The programming-project handler is named TcPpjToPs300 (ToPs 300 = bending) yet the in-scope editions are 100/400/Nest; whether bending (ToPs 300) genuinely shares this PPJ framework should be confirmed with the owner of [[16 - FR - Bending (ToPs 600)]].
  • Remnant-sheet (Resttafel) deduction (aNestAbbuchenResttafel → nest_rawmaterial deduct, aNestResttafelVerwaltung) straddles planning and material/inventory management; documented here only as a link, with the material-inventory detail owned by [[19 - FR - Tools, Machines, Materials & Technology]].
  • Whether the "min/max/actual" quantity fields drive automatic re-nesting (produce until min met) or are purely informational could not be determined from headers/SQL alone.
