TruJira Jira↔FogBugz Sync — Diagnosis & Fix Plan

Date: 2026-07-13 · Author: Aiko (with Claude Code) · Repo: TruKitV5

Four reported failures in the Jira↔FogBugz sync (versions, people, and two status cases). All four root causes were traced in code, independently verified by adversarial review, and then validated against the live Jira (trumpf.atlassian.net) and FogBugz (metamation.fogbugz.com) systems using the tool's own stored credentials in a read-only probe.

1. Reported cases + live ground truth

Issue Jira status Jira fixVersion Jira assignee FB # FB status FB milestone FB assignee Broken field
BENDCAM-2286 Code Review 26.8.0 (Wangshu) Hussain Musaddeque 25757 For Review 26.07.Veles Hussain Musaddeque Version
BENDCAM-9902 Code Review 26.8.0 (Wangshu) Florian Engertsberger 40527 For Review 26.08.Wangshu Dinesh Assignee
BENDCAM-10854 Ready 26.8.0 (Wangshu) Metamation (Do not delete) 43002 For Review 26.08.Wangshu Dinesh Status
BENDCAM-11717 Code Review¹ 26.8.0 (Wangshu) Metamation (Do not delete) 46179 For Merge 26.08.Wangshu Priya Status

¹ Was "In Progress" in the Jul-8 screenshot; advanced to "Code Review" since.

Real workflow values (validated)

  • Jira statuses (BENDCAM workflow): Preparation, Ready, In Progress, Done, Ready for Estimation, Open, Testing, Waiting, Parked, Scheduled, Code Review.
  • FogBugz statuses in use: Active, Code Complete, For Review, For Merge, Internal Test, Machine Test, Ready to Ship, plus Resolved (…) / Closed (…) incl. Closed (Won't Fix), Resolved (Not Reproducible), Closed (Responded).
  • Version naming differs by system, joined only by the codename:
    • Jira 26.8.0 (Wangshu) ⇄ FogBugz 26.08.Wangshu
    • Jira 26.7.0 (Veles) ⇄ FogBugz 26.07.Veles
  • Metamation engineers (Dinesh, Priya, …) have no individual Jira account; their Jira work sits under the shared Metamation (Do not delete) account (noreply@trumpf.com, but its email is hidden — must be resolved by display name).

Validation finding: the mapping table references statuses that don't exist

mappings/default.toml was a verbatim port of the legacy TruKitV3 tables and was never validated against the live workflow. Confirmed mismatches:

  • ❌ Pull Requested (the Jira target for For Merge/For Review/Ready to Ship) does not exist in the BENDCAM workflow → any apply toward it fails with TransitionNotFound.
  • ❌ Machine Test as a Jira status does not exist (FogBugz-only).
  • ❌ FogBugz Closed (Won't Fix), Resolved (Not Reproducible), Closed (Responded) are absent from the "Done" group (it lists Won't Do, not Won't Fix) → false conflicts + apply no-ops.
  • ❌ Real Jira status Parked isn't in any group.

2. Root causes (code + data)

RC-1 · Version apply writes the raw name (the two systems name releases differently)

  • Detection does fire for 2286 (codenames Wangshu ≠ Veles), but apply_version sends the raw Jira string as the FogBugz milestone: fb.edit_case(sFixFor: "26.8.0 (Wangshu)") — FogBugz has no such milestone (it's 26.08.Wangshu) → write fails. Reverse direction is symmetric.
    • crates/trujira/src/commands.rs:3506 (Jira→FB), :3530-3531 (FB→Jira) — never calls the version mapping.
  • Detection is also fragile: version_conflict calls jira_version_to_fogbugz(jv, &[]) with an empty milestone list (commands.rs:2674), so codename resolution against real milestones can't happen, and the fallback is a case-sensitive substring test (commands.rs:2679) that returns "no conflict" (unwrap_or(false), :2680) for any version without a (Codename) or static-map entry.

RC-2 · Assignee apply can't handle team-only (Metamation) people

  • Dinesh exists only in tmm_team_fogbugz (default.toml:221), not in [assignee.fogbugz_to_jira_email]. Both apply directions use only that email map:
    • FB→Jira: fogbugz_assignee_to_jira_email (commands.rs:3685) → None → "no email mapped for FogBugz assignee Dinesh".
    • Jira→FB: fogbugz_assignee_for_jira_email (commands.rs:3648) can only ever return names present in the map.
  • The team logic (assignee_in_agreement, mapping.rs:345) is used for detection only, never for apply.
  • Data bugs (found in audit): "Gugler Gerhard" (team) ≠ "Gerhard Gugler" (email map) → never matches; "lukas.holzleithner" missing @trumpf.com (default.toml:190).

RC-3 · "For Review" ≈ "Ready" (coarse Open bucket) → 10854 never flagged

  • FB For Review sits in the same "Open" group as Jira Ready/Code Review/… (default.toml:141-160), so status_in_same_group("Ready","For Review") is true → no conflict (commands.rs:2693). And the canonical target for any Open-group FB status is jira[0] = "In Progress" (mapping.rs:314), never Code Review.

RC-4 · Status apply targets a wrong/nonexistent value

  • apply_status Jira→FB always resolves group member [0] (Active) and writes it via edit_case(sStatus:"Active") (commands.rs:3767) — but FogBugz status is command-driven (resolve/close/reactivate, client.rs:164-180), so a plain sStatus edit to a custom sub-status is a silent no-op / false success. resolve_case/reactivate_case are dead code (never called), so a closed case can never be reopened. FB→Jira toward the nonexistent Pull Requested fails with TransitionNotFound (transition_by_name, client.rs:316).

3. Confirmed decisions

  • Status table (FogBugz → Jira), using only statuses that exist:

    FogBugz Jira
    Active In Progress
    Code Complete In Progress
    For Review Code Review
    For Merge Code Review
    Internal Test Testing
    Machine Test Testing
    Ready to Ship Testing
    Resolved (*) / Closed (*) Done

  • Assignee: Metamation people (all tmm_team_fogbugz) → the shared Metamation (Do not delete) Jira account, resolved by display name (its email is hidden). Fix TRU-side name/domain gaps too.

  • Version: match/apply by codename against the real version + milestone lists (already cached by the app).

4. Fix plan

Phase 0 — Immediate mitigation via user-overrides.toml (no rebuild)

The app merges ~/Library/Application Support/TruJira/mappings/*.toml over the bundled defaults (load_with_overrides), and a non-empty status.groups replaces the whole list (mapping.rs:167). So a corrected mapping file fixes detection and the FB→Jira status apply (which uses reachable transitions) today:

# ── Status groups (validated against live BENDCAM workflow) ──
# jira[0] / fogbugz[0] are the canonical apply targets.

[[status.groups]]
name    = "In Progress"
jira    = ["In Progress", "Open", "Preparation", "Ready", "Scheduled", "Waiting", "Parked", "Ready for Estimation"]
fogbugz = ["Active", "Code Complete"]

[[status.groups]]
name    = "Code Review"
jira    = ["Code Review"]
fogbugz = ["For Review", "For Merge"]

[[status.groups]]
name    = "Testing"
jira    = ["Testing"]
fogbugz = ["Internal Test", "Machine Test", "Ready to Ship"]

[[status.groups]]
name    = "Done"
jira    = ["Done"]
fogbugz = [
  "Resolved (Completed)","Resolved (Fixed)","Resolved (Implemented)","Resolved (By Design)",
  "Resolved (Not Reproducible)","Resolved (Won't Fix)","Resolved (Duplicate)","Resolved (Responded)",
  "Closed (Completed)","Closed (Fixed)","Closed (Implemented)","Closed (By Design)",
  "Closed (Not Reproducible)","Closed (Won't Fix)","Closed (Duplicate)","Closed (Responded)","Closed",
]

# ── Version static map for the current releases (stopgap until RC-1 code fix) ──
[version.jira_to_fogbugz]
"Backlog"           = "Undecided"
"26.8.0 (Wangshu)"  = "26.08.Wangshu"
"26.7.0 (Veles)"    = "26.07.Veles"
"26.6.0 (Ugarit)"   = "26.06.Ugarit"

[version.fogbugz_to_jira]
"Undecided"      = "Backlog"
"26.08.Wangshu"  = "26.8.0 (Wangshu)"
"26.07.Veles"    = "26.7.0 (Veles)"
"26.06.Ugarit"   = "26.6.0 (Ugarit)"

# ── Assignee data fixes ──
[assignee.fogbugz_to_jira_email]
"Gugler Gerhard"     = "gerhard.gugler@trumpf.com"   # team list uses reversed order
"Lukas Holzleithner" = "lukas.holzleithner@trumpf.com"  # add missing domain

⚠️ Phase 0 does not fix: version apply (still writes raw name), assignee apply for Metamation people, or the Jira→FB status write model. Those need code.

Phase 1 — Version (RC-1) · crates/

  1. version_conflict (commands.rs:2664): pass the real milestone list instead of &[]; make codename matching case-insensitive; add a normalized-name fallback (strip non-alphanumerics, lowercase) so non-codename versions compare directly instead of unwrap_or(false).
  2. apply_version (commands.rs:3488): resolve through the mapping before writing —
    • Jira→FB: jira_version_to_fogbugz(jv, &fb_milestones) → write the resolved FogBugz milestone name.
    • FB→Jira: fogbugz_milestone_to_jira(ms, &jira_versions) → write the resolved Jira version name.
    • Fetch the lists (or read the existing fogbugz_milestones / jira_versions:* caches).

Phase 2 — Assignee (RC-2) · crates/

  1. Make apply_assignee team-aware, mirroring assignee_in_agreement:
    • FB→Jira: if the FB assignee ∈ tmm_team_fogbugz and there's no email row, resolve to the Metamation Jira account by display name (reuse the post_migration.metamation_email = "metamation (do not delete)" resolution path already used by FB→Jira migration).
    • Jira→FB: the shared account maps to many FB people — skip with a clear message (ambiguous) rather than guessing.
  2. Ship the default.toml data fixes from Phase 0 in the bundled file.
  3. Verify JiraClient can resolve an account by display name (the email of the Metamation account is hidden); add a helper if only find_user_account_id(email) exists.

Phase 3 — Status model (RC-3, RC-4) · crates/ + mappings/default.toml

  1. Replace the bundled status.groups with the validated table (Phase 0 block).
  2. FB→Jira status apply already works via transition_by_name to reachable statuses — keep, but guard TransitionNotFound with a friendly message ("no direct transition to X from current status").
  3. Jira→FB status apply: replace the sStatus-via-edit model with the command-driven one —
    • target ∈ Resolved/Closed → resolve_case then/or close_case;
    • target is an active sub-status → set via ixStatus (needs a per-category status-id lookup) or reactivate_case when coming from a closed state.
    • This is the hardest piece; needs a FogBugz listStatuses call (see Phase 4).

Phase 4 — Close the validation gap (prevents recurrence)

  • Add FogbugzClient::list_statuses() (cmd=listStatuses) and a JiraClient project-status lister, then a "Validate mapping" action in the Mappings UI that flags any group entry not present in the live systems. The tool currently lists categories/priorities/milestones/areas but never statuses, which is why this drift went unnoticed.

5. Verification

  • Re-run the read-only probe (scratchpad sync_probe) after each phase to confirm applies land.
  • Concrete acceptance:
    • 2286: version conflict shows; Jira-master apply sets FB milestone to 26.08.Wangshu (not the raw Jira string).
    • 9902: assignee conflict shows; FB-master apply sets Jira assignee to Metamation (Do not delete).
    • 10854: status conflict now shows (Ready ≠ For Review); FB-master apply transitions Jira to Code Review.
    • 11717: with For Merge→Code Review, Jira Code Review + FB For Merge now agree (no false conflict); when Jira is behind (e.g. In Progress), FB-master apply → Code Review.

6. Key source references

  • Version: commands.rs:2664 (version_conflict), :3488 (apply_version); mapping.rs:254 / :272 (resolvers).
  • Status: default.toml:82-173 (groups), mapping.rs:299/309/317 (group logic), commands.rs:2685 (status_conflict), :3733 (apply_status); jkit-jira/src/client.rs:316 (transition_by_name); jkit-fogbugz/src/client.rs:154-180 (edit/close/resolve/reactivate).
  • Assignee: default.toml:183-257, mapping.rs:326/345/382, commands.rs:2718 (assignee_conflict), :3629 (apply_assignee).
