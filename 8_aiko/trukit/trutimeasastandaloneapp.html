TruTime as a standalone app (and still a TruKit tool)

Date: 2026-07-16 · Status: IN PROGRESS — P0–P3 done, P4–P5 remaining

Implementation status

  • P0 ✅ (shipped 5.0.66) — SAP extracted to the sap-tauri crate; TruTime pulls SAP via plugin:trutime|sap_import. App-level sap_time_import (TruWork/TruHomo) delegates to the same code.
  • P1 ✅ — shared time libs → trukit-ui-kit subpath exports (9f10f36); TruTime tool → its own packages/trutime package with own svelte-check + vitest, loaded via import('trutime') (11a8cdb).
  • P2 ✅ — trutime::init_with(JiraCredSource); standalone owns its jira.enc with TruJira fallback; TruKit unchanged (741b07e).
  • P3 ✅ (shipped TruKit 5.0.67; first standalone build produced) — new apps/trutime host + packages/trutime-app frontend; plugin:trutime|open_external decouples from TruJira; build-alpha.sh --trutime; capability audit covers both apps. TruTime-5.0.67-x64-setup.exe builds (2.5 MB). (4ed795c, 5e76769)
  • P4 ⏳ — extract update.rs → shared trukit-update crate; TruTime's own gist manifest + OneDrive folder + self-update; wire build-alpha --trutime publish; independent TruTime version line.
  • P5 ⏳ — standalone "Connect Jira" settings (write own creds) + reuse-if-present detection; icon/title/About polish.

Goal

Ship TruTime as its own installable app that can be distributed on its own, and keep the same TruTime as a tool inside TruKit for users who have TruKit. One source of truth, two hosts — no fork, no copy-paste.

The lever: "tool = library, host = thin shell"

TruKit is already built this way. Each tool is a Tauri plugin crate plus a frontend component, wired together by a thin host (apps/desktop) with a tool registry. TruARV already lives as its own frontend package (packages/truarv). So the move is: add a second, thin host apps/trutime that reuses the exact same crates and the same frontend tool package.

The backend is already in good shape: crates/trutime is a self-contained plugin — trutime::init() registers plugin:trutime|* commands and manages its own state from the OS data dir. A standalone app just calls trutime::init().

Current couplings to the TruKit host (the only things to break)

  1. SAP import → the app-level sap_time_import command (shared with TruWork/TruHomo). The TruTime plugin has no SAP code; the frontend calls the global command via rawInvoke('sap_time_import', …).
  2. Jira credentials → TruTimeState::new_in opens <data>/TruJira/credentials/jira.enc read-only (hardcoded path). TruTime never writes creds; TruJira owns them.
    • ⭐ The encryption key is derived from machine UUID + OS username, not the app identity. So any app run by the same user on the same machine can decrypt that file — a standalone TruTime can transparently reuse TruJira's login when TruKit is installed.
  3. Frontend tool lives inside the monolithic packages/ui (src/tools/trutime), and depends on shared libs (lib/worktime, lib/austrianHolidays, lib/sapImport) that other tools also use, plus trukit-ui-kit (platform abstraction) and the shell registry.

Plus cross-cutting: one unified workspace version, and self-update (apps/desktop/src/update.rs, SharePoint webview + sha256-verified installer) lives in the TruKit app with a single gist manifest.

Target architecture

        shared crates                         shared frontend
  ┌───────────────────────────┐   ┌────────────────────────────────────┐
  │ jkit-core (http/cipher/    │   │ packages/trutime  (<TruTimeTool/>) │
  │           credentials)     │   │ packages/time-lib (worktime,       │
  │ jkit-jira                  │   │   austrianHolidays, sapImport)     │
  │ sap-time                   │   │ trukit-ui-kit (platform, theme)    │
  │ trutime  (Tauri plugin)    │   └────────────────────────────────────┘
  └───────────────────────────┘                     │
              │                                      │
     ┌────────┴─────────┐                   ┌────────┴─────────┐
     │ apps/desktop     │                   │ apps/trutime     │  ← NEW
     │ (TruKit)         │                   │ (standalone)     │
     │ registers trutime│                   │ registers trutime│
     │ + all other tools│                   │ + SAP + update   │
     │ mounts via rail  │                   │ mounts full-win  │
     └──────────────────┘                   └──────────────────┘

Both hosts consume identical crates + the identical <TruTimeTool> package. TruKit is unchanged in behaviour; the standalone host is a tiny new shell.

The four decouplings (the actual work)

1. SAP → a plugin command

Add plugin:trutime|sap_import to the trutime plugin, wrapping the sap-time crate directly (it already provides the WinHTTP/SSO transport). The TruTime frontend calls the plugin command instead of the global sap_time_import.

  • TruKit keeps its app-level sap_time_import for TruWork/TruHomo.
  • Result: TruTime's SAP import works in any host. sap-time becomes a direct dependency of the trutime plugin.

2. Credentials: own store + reuse-if-present

Turn the hardcoded jira.enc path into a credential-source strategy the host picks at init:

  • In TruKit (init_with(CredSource::TruJiraReadOnly)): unchanged — read TruJira's jira.enc, no write. Creds stay managed by TruJira.
  • Standalone (init_with(CredSource::OwnWithFallback)):
    • Primary: TruTime owns <data>/TruTime/credentials/jira.enc (gains write) with a minimal "Connect Jira" settings screen (site / email / token).
    • Fallback: if TruTime has no own creds but <data>/TruJira/credentials/jira.enc exists, read it (same machine key decrypts it) → zero re-login when TruKit is also installed.

3. Frontend extraction

  • Move packages/ui/src/tools/trutime → packages/trutime exporting <TruTimeTool> + its api/store (mirrors packages/truarv).
  • Move the genuinely shared libs (worktime, austrianHolidays, sapImport) into a shared package (packages/time-lib, or fold into trukit-ui-kit) since TruWork/TruHomo use them too.
  • Both hosts import the package (pnpm workspace already supports this).
  • Standalone frontend = a tiny main.ts mounting <TruTimeTool> full-window with minimal chrome (title, settings, update-check, theme) via trukit-ui-kit.

4. Self-update extraction

Move update.rs (SharePoint sign-in webview + sha256-verified silent installer + host allowlist) into a shared crate trukit-update, parameterized by (manifest_url, installer_name, identifier). Both apps reuse it, each with its own gist manifest + OneDrive folder + installer name. Integrity model unchanged.

(cross-cutting) Version split

Give TruTime its own semver, decoupled from the unified workspace version. Standalone TruTime revs on its own cadence; TruKit bundles whatever trutime version is in-tree. The in-app Changelog already keys entries per tool, so the standalone app shows only TruTime's line.

Build & distribution

  • New apps/trutime/tauri.conf.json: identifier com.trumpf.trutime, own window, installer TruTime-<v>-x64-setup.exe, its own capability set (trutime + sap + update only; reuse the positive-deny for the update webview).
  • build-alpha.sh gains --app trukit|trutime (default trukit): cross-builds the NSIS installer per app, publishes to that app's OneDrive folder, updates that app's gist manifest (own id).
  • Coexistence: distinct identifiers/install dirs → both installable on one machine; shared machine-keyed jira.enc → no double login.
  • CI (azure-pipelines.yml) builds both apps; capability audit covers the new app's windows.

Migration roadmap (each step independently shippable)

  • P0 — SAP → plugin:trutime|sap_import (decouple from the app-level command). Ship in TruKit; no visible change.
  • P1 — Extract packages/trutime + packages/time-lib; TruKit consumes them. No visible change.
  • P2 — Credential-source strategy (init_with); TruKit unchanged, plugin now standalone-ready.
  • P3 — New apps/trutime host: tauri.conf + capabilities + minimal shell + trutime::init(). First standalone build.
  • P4 — Extract update.rs → trukit-update; wire TruTime's manifest/gist + build-alpha --app.
  • P5 — Standalone "Connect Jira" settings + reuse-if-present detection; polish (icon, title, About).

P0–P2 are small and low-risk (decouple + extract, no behaviour change). P3–P4 are the bulk (new host + update/build plumbing). P5 is small.

Risks & notes

  • A Tauri plugin registered by two apps is fine (per-app instances).
  • WinHTTP SSO for SAP is OS-level (not app-specific), so it works unchanged in the standalone host via the shared sap-time transport — worth a real-Windows check.
  • The machine-keyed jira.enc crossing app boundaries is intentional (same user, same machine) — document it as a deliberate trust decision.
  • Keep TruTime read-only on TruJira's file in TruKit; only the standalone owns a writable store, so the two can't fight over one file.

Status — SHIPPED (2026-07-16, v5.0.68 → 5.0.69)

All phases P0–P5 done. TruTime is a fully standalone, self-updating, self-configuring app and still bundled in TruKit (unified 5.0.x versioning).

What shipped

  • P0 sap-tauri crate → plugin:trutime|sap_import (TruTime pulls SAP itself).
  • P1 packages/trutime (tool) + packages/trukit-ui-kit (shared worktime / austrianHolidays / sapImport libs); TruKit consumes them.
  • P2 trutime::init_with(JiraCredSource) — TruJiraReadOnly (in TruKit) vs OwnWithTruJiraFallback (standalone).
  • P3 apps/trutime host (com.trumpf.trutime) + packages/trutime-app frontend (Vite :5174). First standalone build.
  • P4 Self-update extracted to shared trukit-update crate (run() installer flow + check(manifest_url, current)); TruJira delegates to it. TruTime has app-level check_for_update / start_self_update + a Settings update banner. build-alpha.sh --trutime publishes to a sibling OneDrive folder and TruTime has its own gist manifest.
  • P5 Standalone Connect Jira UX: save_jira_credentials (validates via GET /myself before persisting) + clear_jira_credentials; read path resolved per-call (own → TruJira fallback → own) so a fresh Connect needs no restart; the write path never touches TruJira's shared file. UI is a connect form + Settings connection card; inert inside TruKit.

Distribution facts (for future releases)

  • TruTime gist id: 4fa6e5c3c6ea513a39e62ba1f11bdb22 (raw: https://gist.githubusercontent.com/aikoradlingmayr/4fa6e5c3c6ea513a39e62ba1f11bdb22/raw).
  • TruTime OneDrive/SharePoint folder: …/02_TecZone Bend/Tools/TruTime (SharePoint sites/TecZoneBendDEV/Freigegebene Dokumente/Tools/TruTime); local publish path in gitignored scripts/publish-dir-trutime.local.
  • Release both in lockstep: bump workspace Cargo.toml, then build-alpha.sh <v> --release --windows (TruKit) and … --trutime (TruTime); update both gists' version + sha256.
  • assert-capabilities.mjs now requires the update positive-deny on both apps.

Security invariants held

  • The update webview (remote SharePoint origin) has zero IPC — apps/trutime/capabilities/update-remote.json positive-deny + no remote.urls.
  • Installer runs only after SHA-256 matches the manifest (fails closed).
  • Machine-keyed jira.enc reuse across apps is intentional (same user + machine).

P6 — two separate git repos: DONE (2026-07-16)

Driver: TruTime must be reviewable by a third party, so the code has to physically live in its own repo — not behind a submodule into TruKit. That ruled out the submodule idea (which would put the shared "brains" in the wrong repo, or create a TruKit↔TruTime cycle since TruKit's desktop app depends on the trutime plugin+tool) and chose the fully self-contained / vendored-copy model.

  • New repo: https://trumpf.ghe.com/TRUMPF/TAT500_CAMBridge_TruTime.git (GHE — GitHub Actions works there, unlike TruKit's Azure DevOps origin). Local clone: ~/dev/trumpf/TAT500_CAMBridge_TruTime (sibling of …/TruKitV5). Initial commit 109479e, branch main, at v5.0.69.
  • Layout mirrored from the monorepo, so every Cargo path dep (../jkit-core, ../../crates/trutime), workspace:*, and name-based import works UNCHANGED — the copy was near-mechanical, only the root manifests were rewritten for the subset.
  • Contents: crates {jkit-core, jkit-jira, sap-time, sap-tauri, trukit-update, trutime}, apps/trutime, packages {trukit-ui-kit, trutime, trutime-app}, plus mappings/default.toml (jkit-core include_str!s it at compile time — needed even though TruTime never uses the mapping at runtime). Excluded: trujira, jkit-fogbugz, apps/desktop, packages/ui, truarv.
  • Own scripts/build-trutime.sh (trutime-only build), trimmed assert-capabilities.mjs, and a reviewer-facing README.md (module map, build steps, security surfaces). Verified self-contained: pnpm install/check/test + cargo build/clippy -D warnings/test + capability audit all green in the new repo alone.
  • TruKit repo left UNCHANGED — still builds the desktop app (bundling its own copy of the trutime tool). The split is additive.
  • Drift caveat: the shared libs + trutime plugin/tool now exist as independent copies in BOTH repos → fixes must be ported by hand. No sync automation yet. Both repos' build scripts point at the SAME TruTime gist (4fa6e5c3c6ea513a39e62ba1f11bdb22) + OneDrive folder, so releases can come from either — prefer the standalone repo going forward.
