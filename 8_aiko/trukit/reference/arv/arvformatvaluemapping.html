product: trukit org: trumpf title: "ARV Format & Value Mapping" tags: [trukit, truarv, arv, bend, reference, moc] source: "TruTopsCAD legacy source — Bend DB schema (ToPs 600), files dated May 2024" status: reverse-engineered-draft related: ["[[TruARV]]", "[[ARV Tables - Suction & Grippers]]", "[[ARV Tables - Magnets & Removal Stations]]", "[[ARV Tables - Upper Tools (Punches)]]", "[[ARV Tables - Dies & Special Bend Tools]]", "[[ARV Tables - Holders, Adapters, Seats & Lists]]", "[[ARV Tables - Bend Factors & Materials]]", "[[ARV Value Legends (consolidated)]]"]

ARV Format & Value Mapping

Hub / map-of-content for the ARV documentation set. This note explains what a .arv file is, how it is structured, and how a coded attribute value is decoded into a human-readable meaning. The per-table detail — every column of every table, with its meaning, type, unit and value legend — lives in the six cluster notes indexed below. Read this note first, then jump to the cluster that owns the table you are looking at.

What an .arv file is

A .arv archive is an export from the ToPs 600 (Bend) database — TRUMPF's tool/fixture/material master data for press-brake bending. A single archive bundles a set of database rows (one per exported record) together with any attached geometry (3D solids, 2D contours, drawings). It is the interchange format for shipping bending tools, automation grippers, dies, holders, seats, bend-deduction factors and material data between systems.

.arv files are opened and decoded by [[TruARV]] (which replaced the legacy standalone TruNinja tool). TruARV lists the archive's entries, renders each coded value inline together with its legend (e.g. 2 · Air Bending), and previews / exports the attached geometry.

The data falls into a few broad families, each documented in its own cluster: automation grippers (suction, magnet, tong, multi-arm), bending tools (punches, dies, and special forming tools), holders / adapters / seats that mount those tools, station/pallet fixtures, and bend factors + material master data.

File structure

Plain text, CRLF line endings, Windows-1252 encoding. The file is a flat list of bracketed sections; every data line is key:<tab(s)>value. String values are single-quoted; booleans are the literals yes / no.

Section Repeats Holds
[HEADER] once Archive metadata: typ, tops600_version, entries (count), attachements (count).
[ENTRY_i] per record One exported database row. table: names the source Bend DB table; then attribnameN / attribvalueN pairs give each exported column name and its value; plus meta keys keyname, keys, fkeysets (primary/foreign key info).
[ATTACHEMENT_i] per attachment A geometry blob: name, typ, data (hex — usually ACIS SAT 3D geometry, or GEO / DXF 2D), and entry1 = the index of the [ENTRY_i] that owns it.

Note the section keyword is spelled [ATTACHEMENT_i] in the format (a fixed misspelling — match it literally when parsing).

So an [ENTRY_i] is, in effect, one row of one Bend DB table, flattened into attribname/attribvalue pairs. The attribute name is (almost always) the literal DB column name, and its value is that column's value — frequently a coded integer whose meaning is an enum legend. Decoding that integer is the whole point of the cluster notes.

A worked decode

An entry that begins table: 'WZG_OW' (an upper tool / punch) carrying the pair attribname7: 'Biegeart' / attribvalue7: 2 decodes as:

  • table: → look up WZG_OW → the [[ARV Tables - Upper Tools (Punches)]] cluster.
  • Biegeart → that cluster's legend: 1 = Folding; 2 = Air Bending (Freibiegen); 3 = Bottom Bending (Prägen).
  • value 2 → Air Bending.

TruARV renders this as 2 · Air Bending. Uncoded columns (dimensions, weights, free-text names) are shown as-is with a unit where known.

How decoding works

  1. Attribute name = Bend DB column. Find the table: of the entry, open the cluster note that owns it, find the column row in that table's spec.

  2. Coded value → legend. If the column is a coded integer (an enum, a flag, a catalog id), the cluster note gives the legend mapping code → meaning. If it is an uncoded scalar or string, no legend applies.

  3. Where legends come from. TruARV ships a built-in legend set in its INFO_TEXTS (migrated from the legacy TruNinja Resources.resx). This is what the viewer uses to render values. It is convenient and, for the classic tool enums (BeschreibungID, Biegeart, LageID, Verwendung, surface treatment, …), it agrees with the schema.

  4. Authoritative meaning = Bend schema MS_Description. Each DB column carries a German MS_Description extended-property comment; this is the source of truth for what the column means. Where INFO_TEXTS and MS_Description disagree (most notably TypGreifnut: INFO_TEXTS 0 None / 1 A0 / 2 A1 … vs. schema 0 B06 / 1 B23), the cluster notes record both and flag the conflict rather than silently trusting the viewer.

  5. The ENUMWERTE / SPRACHEN mechanism. In the live Bend DB the numeric code→label mapping for many columns is not hard-coded — it lives in the ENUMWERTE table (code + enum-group), joined to language text in the SPRACHEN_* tables (e.g. SPRACHEN_ENG). Seat catalogs, material numbers, finishing types, die/shape ids and several flags resolve this way.

    Why those legends are missing here: the reverse-engineering source is a schema-only DDL snapshot — it contains table/column definitions, MS_Description comments and CHECK constraints, but no ENUMWERTE / SPRACHEN seed rows and no catalog data. So any column whose labels live only in ENUMWERTE (WerkstoffID, EndbearbeitungID, AufnahmeID catalog, Separierungstyp, Eignung, the die/shape *formID enums, task/Aufgaben codes, …) has a known meaning but an undetermined numeric legend, and is flagged as such. Resolving them needs a real data dump or a live DB.

Source & confidence model

Every value legend in the cluster notes carries a Source and a confidence (high / medium / low). The source tags mean:

Source tag What it means Typical confidence
INFO_TEXTS Legend shipped in TruARV's built-in legend set (ex-TruNinja Resources.resx). Matches the viewer's own rendering. high (medium where the catalog is truncated/installation-dependent)
MS_Description Read directly from the column's German schema comment (meaning, and sometimes an inline value list). Source of truth for meaning. high
CHECK Value domain bounded by a CHECK constraint (e.g. {0,1}, 0..3). Confirms the range even when labels are unknown. high for the range; low for per-value labels if undocumented
code-crossref Cross-referenced against another documented column/enum group (e.g. shared ENUMWERTE group 481 seat catalog, or a sibling table's legend). medium
inferred Deduced from a documented convention (chiefly the ToPs600 4 = yes / 5 = no flag idiom, or 0/1 boolean wording) plus the column default — not stated numerically for that column. medium / low
undetermined Column is coded but its legend is not derivable from a schema-only snapshot (labels live in ENUMWERTE). Flagged, never guessed. low

ToPs600-vs-tc_dbase enum caveat (important). The ARV/ToPs600 enums are a different numbering from the C++ tc_dbase code enums, even when the concepts match. For example the ARV Biegeart (1 Folding / 2 Air Bending / 3 Bottom Bending) and AKF_VERFAHREN (0 folding-with-gap / 1 folding-without-gap / 2 air bending / 3 coining) are not interchangeable with benddef.h Biegeart (0 Normkantung … 9 Hilfsbiegung) or Biegemethode. Likewise the tc_lift / tc_stz sucker enums do not match WZG_SAUGER_TYP.Saugertyp. The ARV column numbering is authoritative for .arv files; the code enums are cross-reference only and must never be substituted.

Table index

Six clusters, ~67 tables in total. Each links to its full column-level spec.

Cluster note Tables Scope
[[ARV Tables - Suction & Grippers]] 10 Automation gripping tools: suction-plate family (WZG_SAUGERPLATTE/SAUGER/SAUGER_TYP), multi-arm gripper (WZG_MULTIGREIFER*), tong gripper (WZG_GREIFZANGE/GREIFPRATZE/PRATZENPOSITION), cantilever (WZG_AUSLEGER*).
[[ARV Tables - Magnets & Removal Stations]] 18 Magnet grippers (WZG_MAGNET*), the bending-die tool family grouped here (WZG_MA*, WZG_MA_SCHWENK*), removal/unloading stations (WZG_ENTNAHMESTATION*), turn stations (WZG_WENDESTATION), re-gripping consoles (WZG_UMGREIF*), conveyor (FOERDERER), backlight table (DURCHLEUCHTTISCH), pallets (PALETTEN).
[[ARV Tables - Upper Tools (Punches)]] 3 Upper bending tools / punches (Oberwerkzeug): WZG_OW (tool-type master), WZG_OW_ATTRIBUTE (per-length instances), WZG_OW_GRUPPE (bend-deduction group).
[[ARV Tables - Dies & Special Bend Tools]] 17 Lower tools & special forming tools: dies (WZG_GESENK), folding/hemming (WZG_FALZ), flat (WZG_FLACH), Z-bend (WZG_ZBIEG), hinge (WZG_SCHARNIER), swivel bender (WZG_SCHWENKBIEGER), shaft (WZG_WELLE), measuring ranges/legs (WZG_MESS_*), sensor disks (WZG_TASTSCHEIBEN) + their _ATTRIBUTE companions.
[[ARV Tables - Holders, Adapters, Seats & Lists]] 9 Tool holders (WZG_HALTER), adapters (WZG_ADAPTER), seats/mounts (WZG_AUFNAHME), catalog registry (WZG_TABELLEN), tool-assembly lists with sectioning (WZG_LISTE, WZG_LISTE_STUECKELUNG), the two _ATTRIBUTE companions, and WZG_TYP (no DDL in snapshot).
[[ARV Tables - Bend Factors & Materials]] 10 Bend-deduction factors / Abkantfaktor (AKF_BENDFACTORS, AKF_ABKANTFAKTOR*) and material master data (MAT_MATERIAL, MAT_RAWMATERIAL, MAT_GRP, MAT_SHEET, MATERIAL*) — mostly views over the Common schema.

For a single flat lookup of every coded attribute across all clusters, see [[ARV Value Legends (consolidated)]].

Caveats

  • Schema-only snapshot. The whole documentation set is reverse-engineered from a Bend DB DDL snapshot (definitions + MS_Description + CHECK), files dated May 2024. There are no ENUMWERTE / SPRACHEN seed rows and no catalog data, so ENUMWERTE-backed legends (materials, finishings, seat catalog, shape ids, task codes, several enums/flags) are partial or undetermined and flagged, not guessed.
  • Value legends are partial. Coverage is strong for the classic INFO_TEXTS tool enums and for anything with an inline MS_Description list or a CHECK range; it is weak for FK-catalog columns and for a handful of flags whose 4/5 or 0/1 legend is only inferred from a convention plus the default.
  • Known conflicts / schema bugs are recorded in-place. e.g. the TypGreifnut INFO_TEXTS-vs-schema divergence; the BeschreibungID 38–51 punch/die legend that must not be applied to WZG_GREIFZANGE tongs; several copy-paste MS_Description errors (transposed axis descriptions, wrong "Sauger"/"Ausleger" wording, NULL comments). See each cluster's Open questions.
  • Draft. Status reverse-engineered-draft. Not verified against a live ToPs 600 database or a real .arv sample export; confirm before relying on any low/medium-confidence legend or any inferred flag.
