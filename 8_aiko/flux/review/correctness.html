🐛 Flux Review — Correctness

[!abstract] Scope · priority: firm Numeric, null, empty-result, precision, loop-bound, resource and concurrency correctness.

This page has two parts: the official repo rules for this theme (G014, D015, D024) and Arvind's mined additions (24 rules, 24 novel).

📘 Official repo rules (source of truth)

G014: #nullable enable in Every New File (21 occurrences)

Severity: Medium

Every new .cs file must include #nullable enable at the top (after the copyright header):

// Flux ~ Sheet metal CAD/CAM system, Copyright (c) Trumpf Metamation India.
// MyClass.cs ~ Handles ...
#nullable enable

namespace Flux;

D015: Validate Bounds After Any Geometric Transform

After applying a transform to a part or mesh, always check that it does not collide with surrounding components. Do not assume the transform is safe.

"When we compute the transform, I would like to avoid part double sheet collision. Change the part rotation angle to 40 degrees — part collides with the double sheet detector. We should take the bound and avoid such collision."

Pattern: After transform, call GetBound () and check against known obstacles before accepting the result.

D024: Validate Assumptions When Extending Existing Patterns

Before using an API in a new scenario (e.g., a flag designed for one use case applied in another), verify that the assumptions still hold.

"As flags are designed to represent bitmasks, I think the cast automatically includes all set bits at once. Please check."
"No need to check if a PlineCut is a TraceCut as every PlineCut should be a TraceCut as it is derived from the latter."

🎓 Arvind's additions (mined from PR reviews)

Ordered by importance (severity, then how often he repeated it). Quotes verbatim; links to the source PR.

Represent nullability truthfully; never suppress nullable warnings with sentinels

🔴 firm · 🆕 novel

Only annotate a member/element as nullable if it can genuinely be null; do not add ? just to quiet the compiler. When you relax a value to nullable upstream, fix every dereference site — masking with ?. only hides an unhandled null. To clear a warning, keep the true default (usually null) and prove non-nullness to the compiler at the point it is guaranteed, rather than assigning string.Empty. Remember null and empty-string are not interchangeable (a null WPF tooltip is suppressed; "" shows an empty yellow box).

“This is a dangerous change. You have suppressed the errors by setting mIDSel as "", rather than null... figure out how to tell the compiler that after ConfirmOperation returns true, mIDSel is guaranteed not to be null.”

// Don't — sentinel/annotation masks the real contract
string mIDSel = "";                // "" != null
List<TreeViewItem?> items = ...;   // list never holds nulls
// Do
string? mIDSel = null;             // keep true default; prove non-null after the guard
List<TreeViewItem> items = ...;

— Arvind, PR#2540

Don't crash on First()/FirstOrDefault(); handle empty and default results

🔴 firm · 🆕 novel

Use FirstOrDefault(predicate) (collapse Where(cond).FirstOrDefault() into FirstOrDefault(cond)), then explicitly handle the no-match case: null-check before dereferencing, and treat a default/zero result as "not found" and substitute a sensible fallback rather than letting 0 propagate. When matching IDs or machine codes, compare case-insensitively.

“What if there is no downstream mount that is a punch or a die? This code will crash. Use FirstOrDefault.”

// Don't — throws if empty; 0 flows downstream
var m = mounts.First (x => x.IsPunchOrDie);
var wzg = list.Where (c).FirstOrDefault ().WzgArt;
// Do
var m = mounts.FirstOrDefault (x => x.IsPunchOrDie);
if (m == null) return;
var wzg = list.FirstOrDefault (c)?.WzgArt ?? 0;
if (wzg == 0) wzg = 19;

— Arvind, PR#244, PR#225, PR#810, PR#2204

Compare floats with tolerance helpers, never == or against 0

🔴 firm · 🆕 novel

Never write x == y, x != y, or x == 0 for floats/doubles. Use the project tolerance helpers: .IsZero(), .Between(min,max), or .EQ(other). Apply the tolerant comparison consistently to every field in a comparator — do not mix exact != on some coordinates with EQ on others.

“Don't compare a float with 0. Perhaps use !a.FlangeHeights[1].IsZero () or use something like a.FlangeHeights[1].Between (0.001, 2.3)”

// Don't
if (a.FlangeHeights[1] == 0f) ...
if (pose.Axes[4] == 180) ...
// Do
if (!a.FlangeHeights[1].IsZero ()) ...        // or .Between (0.001, 2.3)
if (pose.Axes[4].EQ (180)) ...                // tolerant, on ALL fields

— Arvind, PR#787, PR#877, PR#2496

Fix the root cause; keep parsing symmetric and free of hardcoded structural assumptions

🔴 firm · 🆕 novel

When List- and Dict-style handling should be logically symmetric, make them symmetric and fix the offending offset at its source rather than adding a defensive guard. Don't assume what follows a token: after ] there may be ., another [, or nothing; don't assume indices stay single-digit (no more than 9). Back suspect parsing logic with a stress test that exercises every case.

“That code seems correct, so is the fix as simple as changing the n2+2 to n2+1? ... using n2+2 seems incorrect to me.”

// n2 is the index of ']', which may be followed by '.', '[', or nothing
// Don't — assumes ']' is always followed by '.', and hides the bug behind a length guard
field = key.Substring (n2 + 2);
// Do — mirror the correct IDictionary code
field = key.Substring (n2 + 1);

— Arvind, PR#2475, PR#2306

Guard optional sub-objects before dereferencing; don't assume API objects are populated

🔴 firm · 🆕 novel

Use a null-conditional guard before touching optional sub-objects (if (part.BendTech?.Cell != null) ...). For API objects that are populated lazily, callers must explicitly trigger creation (e.g. call UnfoldTo2D when Part.Dwg is null) and still null-check afterward, because the build step can fail. Never rely on a value being silently populated as a side effect deep in the pipeline.

“Crashes when we save an FXDiag for a manual bend machine. Why not merge this block ... into a condition like this: if (part.BendTech?.Cell != null) ...”

// Don't
part.BendTech.Cell.Save (...);   // crashes on manual-bend machines
DoStuff (part.Dwg);              // Dwg may be null / never built
// Do
if (part.BendTech?.Cell != null) ...
if (part.Dwg == null) part.UnfoldTo2D ();
if (part.Dwg != null) DoStuff (part.Dwg);

— Arvind, PR#1182, PR#1634

Don't round or truncate before a precision-sensitive computation or sign check

🔴 firm · 🆕 novel

Perform computations and comparisons on the full-precision value; round only for display or at the very end. Do not call RoundN() before checking whether a cosine is positive, or before deriving an angle you then need to equal 0/180 — the rounding is both unnecessary and corrupting.

“This code does not guarantee that csImage has a D-Axis of 0 or 180, because you lost some precision by rounding off dAxis to 1 decimal place before starting.”

// Don't
dAxis = RoundN (dAxis, 1);     // precision lost before it matters
if (RoundN (cos, 0) > 0) ...   // -0.1 rounds to 0 -> false positive
// Do
if (dAxis.EQ (0) || dAxis.EQ (180)) ...
if (cos > 0) ...

— Arvind, PR#877

Clamp against hard limits with an explicit safety margin, applied generically

🔴 firm · 🆕 novel

When a value feeds a downstream hard limit, clamp it with a reserved margin below the limit (e.g. Min(value, 599.9 - X) to stay under 600mm), and enforce this in Flux itself rather than hoping the HMI rounds favorably. Apply the fix generically across all machines/controllers, not just the one that reported the bug.

“the only way to ensure that we will never overflow 600mm is to clamp the retraction to 599.9 - X position ... Better to do this for all machines (not just Jupidu) so we don't run into this issue with some other controller.”

// Don't — rounding decimals never fixes the overflow
retraction = RoundN (retraction, 3);
// Do — reserve a margin below the hard limit, for ALL machines
retraction = Math.Min (retraction, 599.9 - xPosition);

— Arvind, PR#784

Bound every repeat-until-stable loop; a single pass or unbounded recursion is a bug

🔴 firm · 🆕 novel

When work must repeat until a condition holds, use a while loop that runs until every element is within bounds. Cap any repeat-until-stable / recursive routine at a sensible maximum (e.g. the item count) and exit early as soon as nothing changed, so a logic flaw degrades gracefully instead of hanging.

“This logic won't work if you have more than 198 bends. If you make the main if into a while, then it will work fine.”

// Don't — one split only covers up to 2x the limit
if (bends.Count > 198) Split ();
// Do
while (bends.Count > 198) Split ();

— Arvind, PR#1403, PR#961

Wrap streams/IDisposables in using, and guard before opening them

🔴 firm · 🆕 novel

Put every stream and IDisposable in a using statement so it closes deterministically. Place the guard condition (e.g. "am I in diagnostic mode?") before opening the stream, never after. Also hoist an expression used twice into a local instead of re-evaluating it.

“You are opening two streams that are not getting closed... Put both in using statements... the stream you created with FX.OpenWrite is still being held open.”

// Don't
var s = FX.OpenWrite (path);   // opened even when not needed; never closed
if (!diagnostic) return;
// Do
if (!diagnostic) return;
using var s = FX.OpenWrite (path);

— Arvind, PR#1158, PR#1755

Make temp-file handling concurrency-safe and never touch pre-existing user files

🔴 firm · 🆕 novel

Generate a unique temp filename per operation (e.g. a GUID plus extension) so concurrent instances never clash. Before extracting/writing a file that could collide with existing data, check for existence: if it already exists, do not overwrite it and do not add it to any temp/cleanup list.

“if you want to be really robust you should generate a new temporary filename each time (perhaps using a GUID with extension .stl) so that there is no name clash.”

— Arvind, PR#122, PR#130

When adding a null guard, don't drop state assignments that must still run

🔴 firm · 🆕 novel

When you add a null guard around a call, check whether any assignment inside the guarded block (e.g. setting a backing field to the incoming value) must still execute in the null case; if so, hoist that assignment outside the guard.

“If mSwitcher is null, shouldn't mSelMode be set to value anyway? Right now, if mSwitcher is null, the mSelMode will not get set to value...”

— Arvind, PR#1112

Confirm refactored conditionals preserve the original boolean logic

🔴 firm · 🆕 novel

When you restructure an if/boolean expression, verify the new form yields the same truth table as the original. If the behavior genuinely should change, call it out explicitly as a specification change rather than slipping it in as a refactor.

“Have you flipped the logic, or is this a change of specification?”

— Arvind, PR#794

Gate actions on explicit success status, not on excluding one failure code

🔴 firm · 🆕 novel

When conditioning an action (e.g. emitting a message) on an operation's outcome, test explicitly for the success value (status == EStatus.OK) so that all error codes are excluded, not just the one you happened to think of.

“What about other error status codes? Shouldn't you be outputting this message only if the code is EStatus.OK?”

— Arvind, PR#2407

Watch fallback paths that silently re-map a value through a secondary table

🔴 firm · 🆕 novel

When adding or reviewing fallback logic, trace what the fallback actually returns: confirm it does not re-map the value through a secondary table (e.g. FoldMachine.Materials) that yields a different code ("DC01") than the intended one ("1.0038").

“the fallback logic will of course find the material, but will then use FoldMachine.Materials to map it to "DC01", and not "1.0038".”

— Arvind, PR#1225

Use precise physical constants and avoid expensive runtime workarounds

🔴 firm · 🆕 novel

Use the correct physical constant (N-to-kg is 9.81, not 10) rather than a convenient round number. Avoid workarounds that force expensive repeated operations (e.g. two suction-cup database reloads per test); find an approach that doesn't reload state you already have.

“The N to Kg conversion is 9.81, not 10. Why the round-off?... The TmpSuctionCups workaround is not good - it is very expensive (requiring two suction cup database reloads for each of the tests where it is applied).”

— Arvind, PR#1818

Don't circumvent a file lock to read a locked file

🔴 firm · 🆕 novel

Do not use lock-circumventing read techniques to access a file another process holds locked. Verify the flush/commit guarantees with the owning system first; if the data isn't committed, the read is unsafe regardless of the trick used.

“The file is locked for a reason, and using this method to circumvent the lock seems reckless.”

— Arvind, PR#212

Ensure exceptions thrown on background threads are handled

🔴 firm · 🆕 novel

When introducing background/worker-thread work, verify what happens when it throws: catch and handle (or marshal) the exception deliberately rather than assuming the surrounding try/catch or the runtime will deal with it.

“Have you checked what happens when an exception is thrown on a 'background thread'. Is it handled correctly?”

— Arvind, PR#2590

Don't assume the default orientation, direction, or ordering of inputs

🟠 consider · 🆕 novel

When manipulating transforms/coordinate systems, verify behavior for rotated (90/180) and mirrored inputs, not just the default. When a hardcoded constant is used, confirm it doesn't actually depend on a condition like carrier direction. Never rely on element ordering (e.g. treating the last element specially) unless the ordering is genuinely guaranteed.

“Does this work if the pallet is rotated 90 degrees or 180 degrees”

— Arvind, PR#399, PR#859, PR#2640

Report an input-dependent error once, not on every processing stage

🟠 consider · 🆕 novel

When a condition depends solely on inputs fixed at the start of processing, compute and report it once at the point those inputs are established (e.g. at pickup), instead of re-evaluating it on each subsequent stage.

“The error depends only on the flat size and weight of the part, which do not change during the processing. So the error should be reported just once at the pickup.”

— Arvind, PR#1140

Clean up resources installed for a temporary mode when that mode ends

🟠 consider · 🆕 novel

When you install resources for a temporary mode, add the matching uninstall/cleanup on mode exit (e.g. remove the separators when the FXDIAG diagnostic mode closes), so nothing installed for that mode remains active afterward.

“When the diagnostic mode is over (we close the FXDIAG), the separators should no longer be installed.”

— Arvind, PR#1182

Verify guard conditions can actually be true (no dead branches)

🟠 consider · 🆕 novel

Before relying on collection.Count (or similar state) in a guard, confirm the collection is actually populated somewhere in the code path; a field that is only ever initialized empty makes the guarded branch unreachable, which usually signals a missing assignment or a misunderstanding.

“Initialized like this, so I am guessing not”

— Arvind, PR#693

Apply a floor by taking the max, not by adding a delta

🟠 consider · 🆕 novel

When enforcing a minimum/floor on an existing value, set it to the greater of the current value and the floor, rather than blindly adding the delta — so a correction that is already larger is preserved.

“Don't add 0.1f to the existing correction - just set it to 0.1 or RamPinchCorrect, whichever is greater.”

// Don't
correction += 0.1f;
// Do
correction = Math.Max (correction, 0.1f);   // or Max (correction, RamPinchCorrect)

— Arvind, PR#141

DXF export must not emit multiple LAYER objects with the same name

🟠 consider · 🆕 novel

When generating DXF, ensure each LAYER object has a unique name; multiple layers sharing a name break import in AutoCAD, SketchUp, and Blender and is a hard no-go.

“Outputting multiple layers with the same name breaks AutoCAD, SketchUp and Blender DXF import (among the tools that I tried). That seems a no-go.”

— Arvind, PR#1093

Add a small epsilon when deriving an integer limit from Math.Sqrt

⚪ suggest · 🆕 novel

When using Math.Sqrt to compute an integer loop limit (e.g. divisor enumeration), add a tiny epsilon (+0.00001) before flooring so perfect squares aren't lost. If a later Distinct() already removes duplicate divisors, you can also simplify the enumeration.

“The +0.00001 is needed since Sqrt(36) might be 5.999999999”

— Arvind, PR#1167
