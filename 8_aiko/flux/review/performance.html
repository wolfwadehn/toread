⚡ Flux Review — Performance

[!abstract] Scope · priority: consider Hot-path cost, short-circuit ordering, hoisting, allocation reuse, single-pass LINQ.

This page has two parts: the official repo rules for this theme (D007, D008, D009, D013, D022) and Arvind's mined additions (14 rules, 13 novel).

⬅ Back to [[Flux — Code Review Guidelines|the review index]].

📘 Official repo rules (source of truth)

[!note] Verbatim from the repo — do not edit here Copied from .github/instructions/design-principles.instructions.md (loaded automatically by Copilot/Claude), synced from commit cf7f99c55 on 2026-07-13. The repo is authoritative — edit there and re-run the KB sync.

D007: Compute Once, Apply Transform — Don't Reconvert

Converting between types is expensive (e.g. Mesh → Collider). Once you have a converted form, keep it and apply transforms instead of re-converting.

"Converting from Mesh to Collider and from Collider to Mesh is costly. But applying transform is not. So, once a collider is computed, we should apply transform."

// ❌ Wrong
Collider c = ToCollider (mesh.ApplyTransform (xfm));

// ✅ Correct
Collider c = ToCollider (mesh);
c = c.ApplyTransform (xfm); // cheap

D008: Use ReadOnlySpan<T> When Only Reading an Array

When a method takes an array argument and only reads from it, declare the parameter as ReadOnlySpan<T>. This prevents accidental mutation and enables stack allocation for small arrays.

"We want the function to be efficient as it will be called multiple times. As we are reading only Axes value, not writing to it, we should use ReadOnlySpan."

// ❌ Wrong
void Compute (double[] axes) { ... }

// ✅ Correct
void Compute (ReadOnlySpan<double> axes) { ... }

D009: bool? Nullable Flags → Use int with -1 Sentinel for Performance

Lazy-initialized boolean flags (tri-state: unknown/true/false) should use int with -1 as uninitialised, not bool?.
This avoids boxing and has better JIT inlining.

"I think it is efficient to use int instead of bool?. Please benchmark and see which is better."

// ❌ Slower
bool? mIsInstalled;
bool IsInstalled => mIsInstalled ??= Check ();

// ✅ Faster
static int sIsInstalled = -1;
static bool IsInstalled {
    get {
        if (sIsInstalled == -1) sIsInstalled = Check () ? 1 : 0;
        return sIsInstalled == 1;
    }
}

D013: Memory and File Size Awareness

Always question whether an increase in binary/file size is justified. When adding data files or serialized blobs, compare against existing similar assets.

"8.75 MB seems to be huge just to support a few tools. For comparison, our BendTools.wad is only around 1.5 MB even storing all data as strings, not bytes. In general, we should be aware of time consumption, size, and computational time."

Questions to ask before adding a large data file:

  • Is the size proportional to the value added?
  • Can the data be compressed (bytes vs strings)?
  • Can the data be generated at runtime instead of shipped?

D022: For Large Enumeration, Avoid Buffering What You Don't Need

When you only need the first and last element of a large stream, do not buffer the entire stream.

"As we need only first and last element, we can discard all the other elements without enqueuing. Imagine the scenario where in 2s we have 10,000 interactions for a single glob — we just need 1st and 10,000th data. For that we are capturing all the data in memory, then finally we are using only two elements."

// ❌ Wrong — buffers everything
var all = stream.ToList ();
var first = all[0]; var last = all[^1];

// ✅ Correct
T first = default, last = default; bool any = false;
foreach (var x in stream) { if (!any) { first = x; any = true; } last = x; }

🎓 Arvind's additions (mined from PR reviews)

Ordered by importance (severity, then how often he repeated it). Quotes verbatim; links to the source PR.

Keep hot/common code paths cheap: cache expensive calls, gate rare-case work

🔴 firm · 🆕 novel

Before adding work to a method, ask how often it runs. If it is on a hot path, cache the result of any expensive call (e.g. Process.GetProcesses()) instead of recomputing it, and restructure so rare/special cases are detected cheaply or gated behind a flag rather than costing every invocation. When an extended check imposes a measurable runtime penalty, enable it only for the specific scenario that needs it.

“This function is called thousands of times when Flux is running. Calling Process.GetProcesses() is very expensive. You need to rewrite to avoid this cost. the previous implementation has a cost of less than 10 clock cycles.”

— Arvind, PR#180, PR#47, PR#1129

Reuse allocations instead of allocating per iteration or per call

🟠 consider · 🆕 novel

Create a StringBuilder (or similar buffer) before the loop and call Clear() at the top of each iteration instead of constructing a new one. To reset a cached list, call list.Clear() rather than assigning a new list. Restructure pipelines so intermediate arrays/collections are reused or eliminated rather than allocated at every stage.

“Create the StringBuilder outside the loop so you can keep reusing the same one - that is much more efficient. In each iteration, you can just do combination.Clear ()”

// don't
foreach (var x in items) { var sb = new StringBuilder(); ... }
// do
var sb = new StringBuilder();
foreach (var x in items) { sb.Clear(); ... }

— Arvind, PR#1199, PR#1182, PR#1659

Hoist loop-invariant computation out of loops

🟠 consider · 🆕 novel

Fetch expensive properties into local variables before entering a loop instead of reading them each pass. Restructure loop bounds so an invariant expression is evaluated once (e.g. iterate backward so a bound like (1 << n) is computed a single time). Also move expensive initialization (cloning objects, building lists) inside the branch that actually uses it so early-return/cached paths skip it entirely.

“Fetch the values ErrWidePunch, ErrWideDie into local variables so you don't do that computation every time... remove that property evaluation out of the loop.”

// don't
for (int mask = 0; mask < (1 << n); mask++) ...
// do (bound evaluated once)
for (int mask = (1 << n) - 1; mask >= 0; mask--) ...

— Arvind, PR#163, PR#1199, PR#1108

Order short-circuit conditions so the cheapest test runs first

🟠 consider · 🆕 novel

When combining conditions, put simple field/length/enum comparisons before property reads, method calls, or string compares. Also use case-insensitive comparison for filename/identifier matching. This makes the expensive operand run only when necessary.

“do the mInfo.Attachments.Length check first - that will take 1 clock cycle only, and if it fails, there's no need to do the much more expensive string compare.”

// don't
if (name.Equals(other) && mInfo.Attachments.Length > 0) ...
// do (cheap test first, short-circuits the expensive compare)
if (mInfo.Attachments.Length > 0 && name.Equals(other, StringComparison.OrdinalIgnoreCase)) ...

— Arvind, PR#39, PR#1108

Do not evaluate a LINQ query twice for existence plus first-match

🟠 consider · 🆕 novel

Replace the Any()+FirstOrDefault() pattern with a single FirstOrDefault() call, then test for the default result (e.g. a default tuple has null/0 fields) instead of a separate existence check.

“GetToolingPlines() will now be evaluated twice - once for the Any call and once for the FirstOrDefault call. That is not ideal... If the set is empty, the FirstOrDefault will return a 'default' tuple with (null, 0).”

// don't
if (q.Any()) { var x = q.FirstOrDefault(); ... }
// do
var x = q.FirstOrDefault();
if (x.Item1 != null) { ... }

— Arvind, PR#1162

Prefer foreach over List.ForEach with a lambda

🟠 consider · 🆕 novel

Use foreach (var x in collection) instead of collection.ForEach(x => ...) when the body is simple statements, to avoid delegate allocation and closure captures.

“Why not use simply foreach (var op in tech.Ops) { and avoid the cost of creating a lambda, capturing variables etc.”

// don't
tech.Ops.ForEach(op => Process(op));
// do
foreach (var op in tech.Ops) Process(op);

— Arvind, PR#2552

Use targeted APIs, not heavyweight mechanisms, for a few fixed cases

🟠 consider · 🆕 novel

For two or three fixed options, compare against a small array instead of building a regex. Prefer narrowly-scoped APIs (e.g. Process.GetProcessesByName) over ones that enumerate the entire universe (Process.GetProcesses).

“Overkill to use a RegEx for just two options. Also, Process.GetProcesses() will enumerate all the thousands of processes while GetProcessByName could be more optimized.”

— Arvind, PR#1338

Reuse existing helpers and efficient framework APIs over hand-rolled loops

🟠 consider · 🆕 novel

When allocating and initializing an array, call the shared helper; where the helper (or your code) fills elements in a loop, switch to Array.Fill, which is faster than an element-by-element loop.

“1. Can use FX.MakeArray() 2. Update FX.MakeArray to use Array.Fill (should be faster than the current loop based implementation).”

— Arvind, PR#898

Return the object you just constructed instead of re-searching for it

🟠 consider · 🆕 novel

Hold onto the reference from the construction/insertion call and return it (e.g. return E2Bendline.Wrap(newEnt)) instead of running a lookup over the drawing/collection to find the same object.

“Why not just return E2Bendline.Wrap(newEnt), instead of searching again to find the bendline in the drawing.”

— Arvind, PR#1674

Skip generating unused side artifacts for throwaway files

🟠 consider · 🆕 novel

Pass the option that disables unnecessary artifact generation (e.g. ESaveFX.NoThumbnail) when writing temporary/throwaway files, to speed up the save.

“Use ESaveFX.NoThumbnail to avoid generating and saving a thumbnail (speeds up FX generation). We don't need a thumbnail for this FX file, since it is used only by the external tool and will be deleted shortly.”

— Arvind, PR#760

Compress large text before Base64-encoding it for storage

🟠 consider · 🆕 novel

When persisting large text as Base64, run it through the Compressed (deflate) method first and decompress on read, rather than storing the raw text encoded directly.

“perhaps use the Compressed method to deflate the HTML before storing it as Base64 (and of course the reverse). I think this will make it much smaller.”

— Arvind, PR#520

Replace magic literals with the named constant/property that represents them

🟠 consider · ↔ G006

Do not hard-code a numeric limit when a domain property already holds it; reference the property instead (e.g. replace the constant 99 with mTech.BMachine.MaxBends).

“Remove the constant 99 and replace with mTech.BMachine.MaxBends”

// don't
if (count > 99) ...
// do
if (count > mTech.BMachine.MaxBends) ...

— Arvind, PR#1403

Choose reasonable magnitudes for buffer/width constants

⚪ suggest · 🆕 novel

When setting a padding width or buffer size, use a realistic value (e.g. ~120 for a line width) rather than an arbitrarily large one that just wastes cycles printing filler characters.

“500 seems excessive. We will spend a bit of time just printing a lot of ' ' characters ... Just set it to a reasonable value like 120 or so.”

— Arvind, PR#1058

Validate performance at realistic large-scale inputs

⚪ suggest · 🆕 novel

When adding a feature that scales with input size, confirm it performs acceptably at realistic upper bounds (e.g. 500 parts on the stack) rather than validating only against small samples.

“Is the performance acceptable with 500 parts on the stack?”

— Arvind, PR#952
