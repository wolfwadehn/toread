✂️ Flux Review — Formatting & Style

[!abstract] Scope · priority: suggest Layout/format conventions. Mostly mechanical — apply, but rarely block a PR on these alone.

This page has two parts: the official repo rules for this theme (G004, G007, G008, G009, G012, G016, G018, G019, G024, G029, G030, G032) and Arvind's mined additions (13 rules, 7 novel).

⬅ Back to [[Flux — Code Review Guidelines|the review index]].

📘 Official repo rules (source of truth)

[!note] Verbatim from the repo — do not edit here Copied from .github/instructions/pr-review-guidelines.instructions.md (loaded automatically by Copilot/Claude), synced from commit cf7f99c55 on 2026-07-13. The repo is authoritative — edit there and re-run the KB sync.

G004: Class Segment / Region Organisation (67 occurrences)

Severity: High — affects every new class

Segments must appear in this exact order:

  1. #region Constructors
  2. #region Properties
  3. #region Methods
  4. #region Operators (if needed)
  5. #region Implementation (private methods, external overrides)
  6. #region Nested Types (if needed)
  7. #region Private Data

All public methods belong in Methods. Overrides of external base classes (e.g. object.ToString(), WPF base overrides) belong in Implementation. Overrides of Flux base classes belong in Methods.

// ❌ Wrong — method outside any region, or in wrong region
class MyTool {
    void Helper () { ... }          // private — must be in Implementation, not floating
    public void Process () { ... }  // public — must be in Methods region
}

// ✅ Correct
#region Methods --------------------------------------------------
/// <summary>Process the current item</summary>
public void Process () { ... }
#endregion

#region Implementation -------------------------------------------
void Helper () { ... }
#endregion

Common reviewer feedback:

"Around the Load(...) method we are missing the #region Interface; likewise, the first method GetTool(...) should be enclosed in #region Implementation."
"I noticed that the properties starting at line 1238 are not wrapped in any #region."
"Consider using #region blocks (Constructors, Properties, Methods etc) in this class which helps to navigate and maintain code easier."

G007: No Consecutive Blank Lines (44 occurrences)

Severity: Medium

Never use two or more consecutive blank lines anywhere in a file.

// ❌ Wrong
public void First () { }


public void Second () { }   // Two blank lines between methods

// ✅ Correct
public void First () { }

public void Second () { }   // Exactly one blank line

G008: Space Before Parentheses (41 occurrences)

Severity: Medium

Add a space before ( in control structures and standalone function calls. Not after . (method chains).

// ❌ Wrong
if(condition)
while(x > 0)
foreach(var item in list)
MyFunction()

// ✅ Correct
if (condition)
while (x > 0)
foreach (var item in list)
MyFunction ()

// ✅ Also correct — NO space after dot
obj.Method ()    // ← space here only because standalone after dot in some cases
list.Add (item)  // ← space before ( is required here too

G009: Region Header Format (29 occurrences)

Severity: Medium

  • Class/record-level regions must be exactly 100 characters wide: 
    #region class MyClassName ---------------------------------------------------------------
  • Segment regions must be exactly 70 characters wide: 
    #region Properties -----------------------------------------------
#region Methods --------------------------------------------------
#region Implementation -------------------------------------------
  • Count from the start of the line — pad with - to reach the exact column.
  • Allowed segment names: Constructors, Properties, Methods, Operators, Implementation, Nested Types, Private Data.
  • Exactly one blank line between #endregion and the next #region.

⚠️ AI reviewers: do NOT raise banner-width findings by eyeballing dash counts. An LLM cannot reliably count characters in a run of - (they tokenize together), so "this banner is N chars, should be 100/70" findings are almost always wrong by a few characters — a confirmed false-positive class. Only flag a width if you have measured it with a tool (e.g. byte/character length), AND the file's own sibling files in the same directory actually follow 100/70. Many existing merged files drift (e.g. BNCXStructs.cs uses 96/63), so trivial ±few-char padding is not worth a comment. Structural issues (missing #region/#endregion, wrong segment name, blank-line spacing) are fine to raise — just not hand-counted widths. (False positive: PR #3483, BNCXWriter.cs — miscounted banner widths.)

G012: Copyright Header (24 occurrences)

Severity: Medium — every new file needs it

Every new .cs file must begin with:

// Flux ~ Sheet metal CAD/CAM system, Copyright (c) Trumpf Metamation India.
// <FileName>.cs ~ <Brief one-line description of what this file contains>

Test files use:

// Flit ~ Test suites for Flux sheet metal CAD/CAM system, Copyright (c) Trumpf Metamation India.
// <FileName>.cs ~ <Brief description>

G016: Remove Unused using Statements (13 occurrences)

Severity: Low-Medium

Remove every using that is not referenced. Set system using statements before Flux/user-defined ones:

// ✅ Correct order
using System.Windows;
using System.Windows.Controls;
using Flux.API.Bend;   // user namespace comes after all System.*

G018: No private Keyword (6 occurrences)

Severity: Low — often missed by freshers unfamiliar with C# defaults

private is the default access modifier — never write it explicitly:

// ❌ Wrong
private Point3 mPoint;
private void DoSomething () { }
private static int sCount;

// ✅ Correct
Point3 mPoint;
void DoSomething () { }
static int sCount;

G019: Brace on Same Line (12 occurrences)

Severity: Low-Medium

Opening braces always go on the same line:

// ❌ Wrong
public void MyMethod ()
{
    ...
}

// ✅ Correct
public void MyMethod () {
    ...
}

G024: File-Scoped Namespaces (R007)

Severity: Medium

// ❌ Wrong
namespace Flux {
    class MyClass { }
}

// ✅ Correct
namespace Flux;

class MyClass { }

G029: Using Statement Order (R044)

Severity: Low

System/Microsoft namespaces before user-defined (Flux) namespaces:

// ✅ Correct
using System;
using System.Collections.Generic;
using System.Windows;
using Flux;
using Flux.API;

G030: Local Functions at End of Method (R045)

Severity: Low

Place local helper functions at the end of the enclosing method, preceded by a comment delimiter:

public void Clear (EClear clear) {
    if (Set (EClear.BendTech)) Q.BendTech = null;
    if (Set (EClear.FoldTech)) Q.FoldTech = null;

    // Helper ...............................
    bool Set (EClear bit) => (clear & bit) != 0;
}

G032: Backing Fields and Method-Local Fields Placement (R043b, R043g)

Severity: Low

  • Backing fields for properties with logic: place immediately after the property (not in Private Data).
  • Fields used only inside one method: place immediately after that method.
public double Area {
    get => mArea;
    set { mArea = value; PropertyChanged.Fire ("Area"); }
}
double mArea;   // ← here, not in Private Data section

public Rect2 GetBound () {
    if (mBound.IsEmpty) { /* compute */ }
    return mBound;
}
Rect2 mBound;   // ← here, not in Private Data section

🎓 Arvind's additions (mined from PR reviews)

Ordered by importance (severity, then how often he repeated it). Quotes verbatim; links to the source PR.

Place local functions at the end of their scope with a dotted banner

🟠 consider · ↔ G030

Move local helper functions below the main body of the method/scope and precede them with a dotted comment such as // Helper ...... to visually separate them from the primary logic.

“We place the local functions at the end of the corresponding scope, rather than at the beginning... We use a special comment format with ..... in it to delimit the local function.”

// Do
void Run () {
   DoMainWork ();
   // Helper ...............................
   int Score (Part p) => p.Q * 2;
}

— Arvind, PR#2265

Use named arguments for opaque literal parameters at call sites

🟠 consider · 🆕 novel

When invoking a method with multiple bool/literal arguments, prefix each with its parameter name (e.g. custom: true, importOld: true) rather than passing bare true, true, true.

“Make this more clear by adding in the meanings of the options parameters: tlib.Load (new[] , custom:true, importOld:true, isPreview:true)”

// Don't
tlib.Load (new[] { file }, true, true, true);
// Do
tlib.Load (new[] { file }, custom: true, importOld: true, isPreview: true);

— Arvind, PR#118

Avoid raw extended-Unicode glyphs in string literals

🟠 consider · 🆕 novel

Replace literal extended-Unicode glyphs with \uXXXX escape sequences, or in tests compare against the string's index rather than the literal character, so the source stays portable across editors.

“using extended Unicode characters in strings like this will cause issues when the code gets pushed / edited in different editors. Can you replace these with the corresponding \u encodings, or instead use the index of the string rather than the actual text in the tests.”

// Don't — raw extended-Unicode glyph in the literal
Assert.AreEqual ("±", result);
// Do — \u escape (portable across editors)
Assert.AreEqual ("\u00B1", result);

— Arvind, PR#2381

Write single-statement methods as expression-bodied members

⚪ suggest · ↔ G020

When a method (or property accessor) contains exactly one statement, convert it to => expr; form instead of { ... }. This is the standard Metamation style for one-liner members.

“Single statement methods - use lambda notation => Hub.Edit (part.Q);”

// Don't
void Show () { FX.IssueCmd (ECmd.PrimaryScreen); }
// Do
void Show () => FX.IssueCmd (ECmd.PrimaryScreen);

— Arvind, PR#1176

Keep private fields at the class end; name backing fields with the m prefix

⚪ suggest · ↔ G032

Move private data members to the bottom of the class body, and declare a property's backing field on its own line (not inline). Name it with the m prefix like any member field (mPlierOverlap) per G003 — not _. Reserve the _ prefix for lazily-computed cache fields (see G032's mArea/mBound examples above, and the _prev/_next cache convention in [[Design & Architecture]]).

“Move private data to the end of the class”

// Do — 'm' prefix for a settable state backing field
public double PlierOverlap { get => mPlierOverlap; set => mPlierOverlap = value; }
double mPlierOverlap;

— Arvind, PR#45, PR#1108

Omit braces around single-statement blocks, including else

⚪ suggest · ↔ G019

Drop the braces when a block (if, else, loop) contains just one statement, per Metamation convention.

“General Metamation convention: don't use braces if there is just a single statement. So you should remove the braces for the else clause.”

— Arvind, PR#839

Put a space before an open parenthesis

⚪ suggest · ↔ G008

Write if (cond), Method (args) with a space before (. Configure Visual Studio formatting so this is applied automatically.

“A space is required before an open parenthesis (after the if). If you are using Visual Studio, these kinds of formatting rules should normally be enforced automatically.”

// Don't
if(x > 0) Foo(x);
// Do
if (x > 0) Foo (x);

— Arvind, PR#2266

Use separator banners only between class sections, never inside a function

⚪ suggest · ↔ G004

Reserve // -------------------- separators for delimiting sections of a class. Do not use them to break up code within a method.

“Don't use // -------------------- type separators inside a function - we normally use that only to separate sections of a class”

— Arvind, PR#1156

Prefer a plain if-statement over a convoluted ternary

⚪ suggest · 🆕 novel

Do not force logic into a hard-to-read ternary or tuple-assignment expression when a straightforward if/else is clearer. Favor readability over compactness.

“I think the if statement is more clear than this ternary operator. Please revert it back.”

— Arvind, PR#2540

Declare multiple same-type variables in one declaration list

⚪ suggest · 🆕 novel

Combine same-type declarations (e.g. byte[] a, b;) rather than repeating the type for each variable.

“Don't need byte[] to be repeated twice.”

// Don't
byte[] head; byte[] body;
// Do
byte[] head, body;

— Arvind, PR#1294

Omit redundant default-value initializers

⚪ suggest · 🆕 novel

Do not write = null on reference-type fields or otherwise re-initialize fields to their default value; leave the declaration bare.

“= null; is an unnecessary initializer.”

// Don't
string _name = null;
// Do
string _name;

— Arvind, PR#2640

Number tests per fixture and keep no blank line above [Test]

⚪ suggest · 🆕 novel

Name test methods Test1(), Test2()... restarting the numbering in each new test fixture class, and remove any blank line directly above a [Test] attribute.

“Remove the blank line above the [Test] attribute”

— Arvind, PR#2501

Use standard line terminators, not a lone carriage return

⚪ suggest · 🆕 novel

Ensure source and data files (including Lua) use \r\n or \n line endings rather than a bare \r.

“Lua files use \r without a \n as the line terminator? Is that the standard?”

— Arvind, PR#1258
