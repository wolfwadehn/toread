💬 Flux Review — Error Messages & UX

[!abstract] Scope · priority: consider Specific messages populated from real data; propagate errors to every caller.

This page has two parts: the official repo rules for this theme (D011) and Arvind's mined additions (4 rules, 4 novel).

⬅ Back to [[Flux — Code Review Guidelines|the review index]].

📘 Official repo rules (source of truth)

[!note] Verbatim from the repo — do not edit here Copied from .github/instructions/design-principles.instructions.md (loaded automatically by Copilot/Claude), synced from commit cf7f99c55 on 2026-07-13. The repo is authoritative — edit there and re-run the KB sync.

D011: Add Meaningful Error Messages — Never Return Silently

When something goes wrong (file not found, invalid state, null reference), give the user or developer a useful message. Silent returns make bugs impossible to diagnose.

"A message that the given directory is missing or not found will be helpful instead of returning silently."

// ❌ Wrong
if (!Directory.Exists (path)) return;

// ✅ Correct
if (!Directory.Exists (path)) {
    Log.Error ($"Directory not found: {path}");
    return;
}

🎓 Arvind's additions (mined from PR reviews)

Ordered by importance (severity, then how often he repeated it). Quotes verbatim; links to the source PR.

Make error messages specific and populate them from real runtime data

🟠 consider · 🆕 novel

When emitting a validation/limit error, interpolate the concrete entity name and its actual measured value alongside the supported bound (e.g. name the gripper, its real cup count, and the maximum). Treat any sample wording in a ticket or review comment as illustrative only — never copy its literal numbers into the code; wire the value to the live data source instead.

“The message should read like Gripper ABCD has 40 cups - only 32 cups are supported”

// Don't — hardcodes the example value from the review
throw new Exception ("Gripper has 40 cups - only 32 cups are supported");

// Do — names the entity and uses the actual runtime count
throw new Exception ($"Gripper {gripper.Name} has {gripper.CupCount} cups - only {maxCups} cups are supported");

— Arvind, PR#2311

Propagate errors back to every calling context, including headless/automated callers

🟠 consider · 🆕 novel

When adding or changing error handling, enumerate the callers of the method (interactive UI, batch, and automated pipelines like Boost AutoCompute) and confirm the failure surfaces correctly to each. Do not rely on a mechanism (dialog, UI-only exception) that only reaches the interactive path.

“What if this is called from a Boost AutoCompute? How is the error transmitted back to Boost?”

— Arvind, PR#2594

Follow English wording and punctuation conventions in user-facing messages

⚪ suggest · 🆕 novel

When authoring or editing message strings, write concise, grammatically correct sentences: no capitalized word immediately after a comma, and terminate the message with a period. Prefer clear, accurate phrasing over verbose or ambiguous wording.

“you should not have a capital letter after a comma. Please change the message to this: Attachment {a.File} not found.”

Don't: "Attachment {a.File} Not found"
Do:    "Attachment {a.File} not found."

— Arvind, PR#1038, PR#1294

Word status/error messages generically so they stay accurate as behavior evolves

⚪ suggest · 🆕 novel

Avoid committing to a specific number or narrow outcome in message text when the operation could produce other outcomes later. Prefer wording that describes the action generically (e.g. 'splitting setup') over one that hardcodes a count (e.g. 'into 2') that a future machine could exceed.

“Change this message to Machine bends limit reached, splitting setup (since we might even split it into 3 or more for some machines).”

Don't: "Machine bends limit reached, splitting setup into 2"
Do:    "Machine bends limit reached, splitting setup"

— Arvind, PR#1403
