🧪 Flux Review — Testing

[!abstract] Scope · priority: firm Focused minimal tests, asserting the real invariant, isolation, cleanup, standard fixtures.

This page has two parts: the official repo rules for this theme (G005, G022) and Arvind's mined additions (18 rules, 15 novel).

⬅ Back to [[Flux — Code Review Guidelines|the review index]].

📘 Official repo rules (source of truth)

[!note] Verbatim from the repo — do not edit here Copied from .github/instructions/pr-review-guidelines.instructions.md (loaded automatically by Copilot/Claude), synced from commit cf7f99c55 on 2026-07-13. The repo is authoritative — edit there and re-run the KB sync.

G005: Test Attribute Format (65 occurrences)

Severity: High — test files have strict conventions

// ❌ Wrong — "Case" in description
[Test (37239, "Case 37239: Stop position in X direction is not correct")]

// ✅ Correct — just the description, or with "C" prefix only
[Test (37239, "Stop position in X direction is not correct")]
[Test (37239, "C37239: Stop position in X direction is not correct")]  // "C" prefix is OK
  • Test IDs must be globally unique — never reuse IDs from other branches.
  • If the current year's test file doesn't exist, create it. Do not add tests to last year's file.
  • If automated test is impossible, create a FogBugz case for a FlaUI UI test instead.
  • Use [SkipIfParallel] for tests that touch shared resources or rely on cleanup in finally.

G022: Test [SkipIfParallel] for Shared Resources (9 occurrences)

Severity: Medium for test authors

If your test modifies static/shared state, writes files, or uses finally for cleanup, mark it:

[SkipIfParallel]
[Test (44512, "Shared resource test")]
void TestWithSharedState () { ... }

🎓 Arvind's additions (mined from PR reviews)

Ordered by importance (severity, then how often he repeated it). Quotes verbatim; links to the source PR.

Assert the specific invariant, not full-file or full-UI-dump equality

🔴 firm · 🆕 novel

Test the targeted content directly — e.g. that the XML contains a PDFNote, or gh.HasTag(EGTag...).Is(false) — instead of AreTextFilesEqual on a whole file or a dump of all UI settings. Full comparisons are brittle: they break every time an unrelated setting is added, and full-file comparison of outputs like PDFs also fails across graphics cards. The goal is usually to confirm the expected element was produced, not to reproduce byte-for-byte contents.

“Don't compare the complete files with AreTextFilesEqual since the PDF is different for various graphics cards... The point is to see that the PDF is generated, not to check its actual contents.”

// Don't: brittle full comparison, breaks on any unrelated UI/output change
Assert.AreTextFilesEqual(expected, actual);
// Do: assert the specific fact under test
gh.HasTag(EGTag.OtherV).Is(false);

— Arvind, PR#231, PR#1930

Never commit or merge without running the tests green

🔴 firm · 🆕 novel

Before committing any change in this repo — no matter how trivial it looks — run at least the test you wrote and the affected suite. Never merge a change that breaks existing tests; rework it and confirm the whole suite is green first. If a fix turns out to break tests, expect it to be rolled back.

“Please never commit code without running the tests, it is literally Rule Number 0. No matter how trivial you think the changes are, don't skip this step.”

— Arvind, PR#2240, PR#1966

Tests must be isolated — never mutate shared or global state

🔴 firm · ↔ G022

Do not add to or modify global databases/registries (e.g. adding a material to the database) inside a test without undoing it. If a test passes standalone but fails within its fixture, treat it as a shared-state leak and hunt down the cross-test side effect rather than reordering tests to hide it.

“It looks like your test is adding a material to the database, and would therefore have a side effect on all tests that come after?”

— Arvind, PR#2539, PR#2241

Make sure the test actually exercises the behavior it claims

🔴 firm · 🆕 novel

Check that setup calls do real work given the fixture state — a call that is a no-op (e.g. DoBendTooling on an already-tooled part) means the test validates nothing. For conditional behavior, also assert the opposite condition: if elements are hidden at one viewpoint, assert they become visible at another (e.g. Viewpoint.Isometric), so you prove the behavior is genuinely conditional rather than always-hidden.

“This part is already tooled up, so this DoBendTooling call is not actually doing anything. I think this test is not correct.”

— Arvind, PR#782, PR#2216

Don't couple tests to UI components — drive state through the domain API

🔴 firm · 🆕 novel

Exercise the target logic directly through the domain API rather than routing through a UI dialog (e.g. don't drive a TBS-logic test through BRecomputeDlg). Keep the test's dependencies limited to the subsystem it actually validates.

“Don't use BRecomputeDlg in this test - we don't want this delicate coupling between this logic (which is just to do with TBS) and the recompute dialog.”

— Arvind, PR#990

Investigate a changed expected output before re-baselining it

🔴 firm · 🆕 novel

If updating a change causes a committed expected-output file (e.g. a C34995.txt golden file) to differ, stop and determine what caused the difference and verify the new result is genuinely correct before re-baselining. Never silently overwrite the expected file to make the test pass.

“What causes the test result to change? Have you inspected the change to make sure this is correct?”

— Arvind, PR#2496

Use standard always-installed machines, not bespoke setups

🔴 firm · 🆕 novel

Write tests against the standard machines/grippers that are always installed in Developer-Mode Flux rather than installing new ones. Reserve bespoke installation for the rare test that specifically validates installation behavior.

“Installing a new machine, installing a new gripper etc are expensive ... Most tests should try to use one of the standard machines that are always installed in a Developer-Mode Flux.”

— Arvind, PR#924

Keep tests focused and minimal — start from a pre-set-up fixture and the simplest part

🟠 consider · 🆕 novel

Load a fixture that is already in the state you need (e.g. an already-tooled-up part) instead of running DoSwitchToBending / full code generation to get there, unless that machinery is itself what you are testing. Use the simplest input that reproduces the case (a single rectangle with no holes, or the 2-3 parts that show the bug — not a full sheet). Skip setup steps irrelevant to the assertion (don't build bend technology just to check density). This keeps tests fast and insulates them from unrelated algorithm improvements. When an exhaustive test would need many full cycles, compose one rich setup that covers all cases in a single cycle.

“Tests should be as 'focused' as possible to the particular case in hand... Start with a part that is already tooled up... a. The test runs a bit faster... b. We are insulated from improvements in the auto-tooler”

// Don't: tool up from scratch just to test downstream logic
var part = Load(...); DoSwitchToBending(part); // slow, sensitive to auto-tooler changes
// Do: start from an already-tooled-up fixture unless you are testing the auto-tooler
var part = LoadToooledFixture(...);

— Arvind, PR#1141, PR#1149, PR#804, PR#2539, PR#2260, PR#1042, PR#1189

Clean up everything a test creates or changes

🟠 consider · 🆕 novel

Delete any artifact the test writes to a standard output path (e.g. a generated PDF). To undo a mutated shared value, save and reset just that value instead of an expensive full reload (e.g. set mc.HasACBLaser back to its previous value rather than reloading). When installing temporary resources, use the provided disposable helper (e.g. TmpCustomTools) whose Dispose restores shared state such as BToolLibrary(0) at test end.

“each time you run this test a PDF file is generated... and you are not deleting that PDF file.”

// Don't: expensive full reload to restore one flag
ReloadMachine();
// Do: save and reset the single value you changed
var prev = mc.HasACBLaser; /* ...test... */ mc.HasACBLaser = prev;

— Arvind, PR#231, PR#1149, PR#1930

Bake non-subject setup into the fixture and force the target state up front

🟠 consider · 🆕 novel

Save the fixture after any preparatory changes that aren't the subject of the test (e.g. save the FX file after the die change, since changing the die is not part of the test). Configure inputs so the system reaches the desired state on the first pass instead of setting it wrong and then correcting it — e.g. embed a GRIPPER: hint in the GEO so auto-tooling picks the right gripper immediately rather than tooling with one gripper and then swapping it.

“So instead of tooling up with some other gripper, and then changing the gripper, you can get the correct gripper right in the first phase... you can speed up the test by forcing the gripper choice.”

— Arvind, PR#806, PR#1930

Strip environment-dependent artifacts from tests

🟠 consider · 🆕 novel

Disable environment-variable artifacts when they aren't the point of the test — e.g. set EmbedImages = false so you don't have to maintain per-graphics-card variants. Keep the test focused on the workflow it is meant to exercise (e.g. the Boost workflow) rather than on machine-specific rendering.

“removed the images (setting EmbedImages = false) for these tests, to avoid having to generate variants for different graphics cards in the future. The point of these tests is to exercise the Boost workflow, and the images are not critical for that.”

— Arvind, PR#1372

Compare images with the purpose-built helper (Assert.AreBitmapsEqual)

🟠 consider · 🆕 novel

When comparing two images in a test, use Assert.AreBitmapsEqual rather than comparing encoded strings, so a failure displays both images side-by-side and is easy to diff.

“Use Assert.AreBitmapsEqual to compare two images. That way, if the comparison fails, we get the two images displayed side-by-side and we can diff them more easily.”

— Arvind, PR#1948

Don't assert on wall-clock elapsed time

🟠 consider · 🆕 novel

Do not assert that an operation completes within some wall-clock duration in a unit test — it fails on standard base-level VMs and debug builds. If a test's sole purpose is a time check, remove the whole test rather than keeping a check that must be deleted.

“This test fails when run on a standard base-level VM... I think we can remove this time check. Effectively that makes this test rather pointless, so perhaps we can remove this test altogether?”

— Arvind, PR#2641

Measure performance by running the focused subset in release mode

🟠 consider · 🆕 novel

When comparing performance or timing, run the relevant tests in release mode — switch with flux.console optimize 1 and rebuild — rather than drawing conclusions from a debug build.

“Make sure you are running the tests in release mode (which you can switch to using flux.console optimize 1 and rebuilding.”

— Arvind, PR#1129

Put trivial API/interface tests in the consuming product

🟠 consider · 🆕 novel

When a test only validates a public API/interface contract, consider placing it in the consuming product (such as Boost) rather than bloating the library's own suite with it.

“In some sense these tests (and also API tests) really belong outside Flux, in the places such as Boost that consume such API / interfaces.”

— Arvind, PR#1905

Reference test data via FX.TestFile, not hard-coded absolute paths

🟠 consider · 🆕 novel

Use FX.TestFile("Bend/API/TestPart1.geo") to resolve test data instead of a hard-coded X:\TData\ path, so tests don't depend on a specific mounted drive. Replace any existing X:\ references with FX.TestFile calls.

“Use FX.TestFile ("Bend/API/TestPart1.geo") to avoid hard-coding a dependency on X:\ (find all places were you are using X:\TData\ and replace with calls to FX.TestFile.”

// Don't
var path = @"X:\TData\Bend\API\TestPart1.geo";
// Do
var path = FX.TestFile("Bend/API/TestPart1.geo");

— Arvind, PR#45

Organize tests into year/theme-scoped classes and folders

⚪ suggest · ↔ G004

Group tests by year/theme — e.g. create a Fold2025 class and move its data files into a Fold/2025 folder — instead of appending them to an older or unrelated fixture.

“Move tests to a new class Fold2025, and move the test files to a Fold/2025 folder.”

— Arvind, PR#2501

Tag tests being extracted or temporarily broken with [Skip]

⚪ suggest · ↔ G005

When a test is going to be extracted or is temporarily failing for a known transitional reason, tag it [Skip] rather than leaving it to break the run.

“Since this test is going to be extracted out, can we tag it as [Skip] to avoid issues now?”

— Arvind, PR#2552
