🏷️ Flux Review — Naming & Documentation

[!abstract] Scope · priority: suggest Names that state meaning; scope-appropriate length; why-comments; subsystem rationale.

This page has two parts: the official repo rules for this theme (G002, G003, G031, D012, D019) and Arvind's mined additions (13 rules, 8 novel).

⬅ Back to [[Flux — Code Review Guidelines|the review index]].

📘 Official repo rules (source of truth)

[!note] Verbatim from the repo — do not edit here Copied from .github/instructions/pr-review-guidelines.instructions.md and .github/instructions/design-principles.instructions.md (loaded automatically by Copilot/Claude), synced from commit cf7f99c55 on 2026-07-13. G002: XML Documentation on Public Members (113 occurrences)

Severity: High — frequently flagged across all PR eras

Every public member in a public type must have a <summary> tag. Do not add documentation to members in non-public (internal/private) types.

// ❌ Wrong — missing XML doc on public member
public class MyProcessor {
    public void Process (Item item) { ... }
}

// ✅ Correct
/// <summary>Sends a Trumpf Analytics message via the REST interface</summary>
public class MyProcessor {
    /// <summary>Process the given item and update the result set</summary>
    public void Process (Item item) { ... }
}
  • Use single-line <summary> only — do NOT add <param> or <returns> on the same line (R029).
  • Internal/private types: members do not require XML docs.

G003: Naming Conventions — Fields, Methods, Types (82 occurrences)

Severity: High

Symbol Convention Example
Private instance field m prefix + PascalCase Point3 mStartPoint;
Private static field s prefix + PascalCase static int sCount;
Public field/property/method PascalCase public double MinHeight;
Enum type E prefix enum EKind, enum EFlag
Interface I prefix interface IDisplayDevice
Class/struct PascalCase, no prefix public class PlineIntersector 
// ❌ Wrong
private string strName;       // Hungarian notation
int intCount;                 // No m prefix
public double minHeight;      // Lowercase start

// ✅ Correct
string mName;
static int sCount;
public double MinHeight;

Method names must be proper English words — single-letter abbreviations like TA are rejected:

"the naming of a method should be in proper words so rename TA"

G031: No Type-Name Prefix in Class Members (R021)

Severity: Low

Do not repeat the namespace/class name in member names:

// ❌ Wrong (in class FChassis)
class FChassis {
    public FChassisMachineSettings MachineSettings;   // repeats FChassis
    public FChassisUtils Utils;
}

// ✅ Correct
class FChassis {
    public MCSettings MachineSettings;
    public Utils Utils;
}

D012: Comments Must Explain Non-Obvious Decisions

Add a comment whenever the code does something surprising, license-gated, or where the "why" isn't visible from the code itself.

"Please add comments that we are allowing 3D gripper import only if we have Hoops license because 3D file may be a file other than IGES. Also, it is not obvious from the tag DesignerImport that we are dealing with 3D gripper import."
"Add comments that it corresponds to height of origin mesh. Also add comments in CSMeshes that we have to update the constant when we change the origin mesh."

// ❌ Wrong
if (FX.Permits (EPermit.Hoops)) ShowImport3D ();

// ✅ Correct
// 3D gripper import is only supported with a Hoops license because
// the import handles non-IGES formats that require Hoops rendering.
if (FX.Permits (EPermit.Hoops)) ShowImport3D ();

D019: Domain Terminology Must Match Flux Vocabulary

Use the established Flux domain vocabulary, not generic engineering terms or NC-code terminology.

"In our domain, 'Gripper Tool' refers to something very specific — the external Gripper Tool used to design grippers. I would simply use 'Gripper' here."
"When I read 'Tool,' I think of bending tools. Please choose whichever you think fits better — just be precise."

Rule: When in doubt, use the same term that appears in the Flux UI and existing codebase, not the NC/machine term.

🎓 Arvind's additions (mined from PR reviews)

Ordered by importance (severity, then how often he repeated it). Quotes verbatim; links to the source PR.

Name members, parameters, and methods for what they actually mean — not codes, abbreviations, or misleading terms

🟠 consider · 🆕 novel

When you introduce or touch a field, property, enum member, parameter, or method, choose a name that a reader can understand without opening the implementation. Replace internal codes/abbreviations (AllowCS05 -> NestBetweenClamps) and generic or broad terms (a deposit shelf is DepositShelf, not something looser) with the real concept. Make the verb accurate: name a method for what it truly does (OpenEditor/CloseEditor, not CloseForEditing), and name a warning/override condition Warn..., not Err.... If a parameter name is still ambiguous, rename it and add a doc comment.

“CloseForEditing is a poor name choice - we are not actually closing the part for editing. Replace these names with OpenEditor(Part), and CloseEditor(Part).”

// Don't: internal code / misleading verb / broad term
bool AllowCS05;
void CloseForEditing (Part p);
Property ErrJawGripOverload;

// Do: name the concept and the real action
bool NestBetweenClamps;
void CloseEditor (Part p);
Property WarnJawGripOverload;   // it's a warning/override case, not an error

— Arvind, PR#1176, PR#2640, PR#1089, PR#1140, PR#1129

Use the 'm' prefix only for class member variables, never for locals

🟠 consider · ↔ G003

Prefix instance/data fields with 'm' (mPart). Strip the 'm' from any local variable (toolsToImport, not mToolsToImport). Check the declaration's scope before naming: field -> 'm' prefix; local -> plain camelCase.

“The m prefix is used only for variables that are members of classes. This is a local variable, so just call it toolsToImport.”

// local variable -> no prefix
var toolsToImport = ...;   // not mToolsToImport

// class data member -> 'm' prefix
private Part mPart;         // not part

— Arvind, PR#118, PR#119

Explain non-obvious logic with an inline comment justifying why

🟠 consider · 🆕 novel

When you write logic that a reader could not derive from context alone (sign flips, magic adjustments, corrections that reference an unrelated subsystem), add a code comment stating the reason and the connection. If you cannot articulate why it is needed, treat that as a signal the code may be wrong.

“It's not clear why we are flipping the sign of AngleCorrection in JupiduWriter. Could you write a note explaining that in JupiduWriter.cs”

— Arvind, PR#337

Model a sentinel-only int as a well-named boolean

🟠 consider · 🆕 novel

When you find an int/double that is only ever tested for equality/inequality against a magic sentinel, replace it with a bool carrying a meaningful name (hasAngle / isAngleSet) instead of leaking the sentinel comparison across the code.

“This should be boolean variable with an appropriate name. It's really behaving like a boolean flag - you are only checking if angle is -1 or not.”

// Don't: int used only as a flag
int angle = -1;
if (angle != -1) { ... }

// Do: a named boolean
bool hasAngle;
if (hasAngle) { ... }

— Arvind, PR#783

Write a structured XML comment for every public API member

🟠 consider · ↔ G002

Before submitting a new public type or member, add a /// XML comment describing what it does and the meaning of any non-obvious parameters. Treat this as mandatory for public surface, not optional.

“if you are adding a public API, you must write a structured comment.”

— Arvind, PR#1176

Name magic constants and tie them to their source

🟠 consider · ↔ G006

Replace bare magic numbers with named constants, and where the values originate from an external reference (a figure, spec, or diagram), name them to match that source and annotate the reference so a reader can trace where each value came from.

“It's not clear where these constants 170, 1303 come from. Can you mark them in the figure (give them names like CA, CB etc).”

— Arvind, PR#859

Document the rationale for a new subsystem

🟠 consider · 🆕 novel

When introducing a substantial new feature or subsystem, include documentation that answers "what is the need for this and why was it designed this way", and ensure it has adequate test coverage before submitting it for review.

“it might be useful to understand the basis decision for this project: "What is the need of PlatformBend". Some documentation about that would also be useful so we can understand the thinking.”

— Arvind, PR#938

Scale identifier length to scope — short in small scopes, but never ambiguous

⚪ suggest · 🆕 novel

In small scopes use short names: a lambda parameter should be a short token (a => a.Part == part), and a local confined to a few lines can be terse (ini). Do not, however, use names that are visually ambiguous — replace 'l' (confusable with the digit 1) with a real word like 'line'.

“Use smaller names as lambda function parameters. For example a => a.Part == part. That improves readability.”

// small scope -> short names
list.First (a => a.Part == part);
var ini = LoadIni ();

// but avoid ambiguous single letters
foreach (var line in lines) { ... }  // not 'l'

— Arvind, PR#1176, PR#1511, PR#51

Drop words already implied by the enclosing type

⚪ suggest · ↔ G031

Omit the enclosing type's name from a member (in DiagnosticMode, use mTempFiles, not mTempDiagnosticFiles). Omit the word 'Type' from a type/enum name (ERobotTrack, not ERobotTrackingType).

“Since this now in the DiagnosticMode class, you should just call this mTempFiles. You don't need the Diagnostic in the variable name.”

class DiagnosticMode {
    List<string> mTempFiles;   // not mTempDiagnosticFiles
}
enum ERobotTrack { ... }       // not ERobotTrackingType

— Arvind, PR#130, PR#2024

Do not reserve a vendor/company name as a file extension

⚪ suggest · 🆕 novel

When defining a file extension for a format Flux owns, prefix it with the app (.fxlantek) rather than using the vendor's whole name (.lantek).

“I am sure there are other files created by the Lantek company, and we should not reserve the entire company name for just one file format... Please rename this to .fxlantek”

// Don't: reserves the vendor's whole name
.lantek
// Do: namespace it to the app
.fxlantek

— Arvind, PR#1148

Use correct English spelling in identifiers

⚪ suggest · ↔ G003

Check the spelling of words used in names; fix misspellings (Lens, not Lense).

“It should be spelled as Lens, not Lense”

— Arvind, PR#2540

Give private/test fixtures clear, self-explanatory names

⚪ suggest · 🆕 novel

For private/test-only assets (e.g. a test machine), pick a name that conveys what it is at a glance (FX-BM150 Lua / FX-BM150 PLB) rather than an opaque label.

“Rename the machine to something more immediately clear like FX-BM150 Lua or FX-BM150 PLB. This is a private machine that is used only for testing, so we can rename it any way we want.”

— Arvind, PR#1258

Write release notes as part of a case/bug fix

⚪ suggest · 🆕 novel

Every case/bug fix PR should include its release-note entry; do not treat release notes as a separate follow-up.

“When fixing a case, please write also the release notes for the case”

— Arvind, PR#999
