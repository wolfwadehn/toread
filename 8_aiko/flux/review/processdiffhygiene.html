📋 Flux Review — Process & Diff Hygiene

[!abstract] Scope · priority: firm Commit/PR-time discipline: tests green, minimal scoped diffs, Case-title, release notes.

This page has three parts: the official repo rules for this theme (D010), a companion-repo (ReFlux) gate, and Arvind's mined additions (13 rules, 12 novel).

⬅ Back to [[Flux — Code Review Guidelines|the review index]].

📘 Official repo rules (source of truth)

[!note] Verbatim from the repo — do not edit here Copied from .github/instructions/design-principles.instructions.md (loaded automatically by Copilot/Claude), synced from commit cf7f99c55 on 2026-07-13. The repo is authoritative — edit there and re-run the KB sync.

D010: No Compiler Warnings — Treat Them as Errors

Warnings are not acceptable. A PR with warnings will be rejected the same way a PR with errors is.

"Like how we can't have errors during compilation, we cannot have warning messages also."
"Because you made it Obsolete, now the compiler creates 3 warning messages."

If marking something [Obsolete] introduces warnings in calling code, resolve all call sites first or use a non-warning path.

🔗 Companion repo (ReFlux) — open the matching PR

If your change needs companion assets, open the matching ReFlux PR

🔴 firm · 🆕 novel

Many Flux changes are not buildable/shippable without a matching PR in the ReFlux companion repo (the Y: drive): 3D source models, bend-tool catalogs, TBS settings, WIBU runtime/DLLs, static config/fonts, flavor resources, and security-related assets. Open the ReFlux PR and link it in the Flux PR body (the team convention is "depends on <ReFlux PR>"). Reviewers block merge until the ReFlux side exists. Watch the common specifics: source-model names in ReFlux must match the Flux mesh2 names; and never edit bendtools.curl directly — update the dxf files in ReFlux Y:\BendTools\<Catalog>\, bump bendtools.ini, then run auditbtools.

Full trigger → action checklist: [[ReFlux — Companion Repo Checklist]].

“Please add all the relevant source models to the ReFlux repository.” — @v-priya, PR#3397 “You should not update the bendtools.curl directly. Create a branch and update dxf files in the respective Y:\BendTools\Wilson-Euro folder of ReFlux repo. Remember to bump up the version in bendtools.ini. Use auditbtools…” — @varalakshmi-imm, PR#2738 “Did you also change the tbs-settings in ReFlux repo?” — @aikoradlingmayr, PR#3344

— mined from PR reviews: PR#3397, PR#2738, PR#3458, PR#3344, PR#3019, PR#2602, PR#995

🎓 Arvind's additions (mined from PR reviews)

Ordered by importance (severity, then how often he repeated it). Quotes verbatim; links to the source PR.

Run the full test suite with zero failures before pushing or opening a PR

🔴 firm · 🆕 novel

Before any push or PR, run the whole test suite (it takes ~10-12 minutes) and confirm zero failures — this is mandatory even for one-line changes. When a change deliberately alters expected test data, first validate that the diff matches exactly the intended set of additions/removals before regenerating fixtures. Any new default behavior that would change existing test fixtures must be disabled when running under test mode (FX.Testing == true) so it does not break unrelated tests.

“Before you push any changes to the repository, and before you create a pull request you must run all the tests and nothing should fail. This change causes 39 tests to fail!”

— Arvind, PR#799, PR#1649, PR#2316

Never commit whitespace-only or formatting-only changes

🟠 consider · 🆕 novel

Review the diff carefully before pushing and revert every whitespace-only or formatting-only delta — this applies to C#, XAML, .csproj and all other files. Never run AutoFormat on a whole file; at most format the specific block or function you are editing. Do not leave trailing whitespace on lines (install the Visual Studio extension that trims it on save), and keep a trailing newline at the end of each file. If a file shows up in the diff with only whitespace differences, drop it from the commit entirely.

“There is only one actual change, but there are 7 'whitespace changes' so it is difficult to do a diff and figure out what has actually changed... roll back all the the whitespace changes and keep only the one line that has changed.”

— Arvind, PR#197, PR#198, PR#202, PR#1258, PR#1397, PR#1616, PR#1880, PR#2640, PR#47, PR#170

Title PRs and commits as 'Case NNNNN: Description'

🟠 consider · 🆕 novel

Write titles as 'Case 12345: Meaningful description'. Put a space (never a period or nothing) between 'Case' and the number — that space is what creates the Fogbugz hyperlink. Follow the number with a colon, then a descriptive title derived from the Case title (abbreviated to fit one line), with the first letter after the colon capitalized. The title should describe the problem/case, not explain the fix you applied.

“If you use a title like Case 12345 in the commit message (space instead of . ) then the commit will show up as a hyperlink in the Fogbugz case”

Do:    Case 32707: Fix German umlauts in Gecco post
Don't: Case32707 Fix German umlauts   (no space → no Fogbugz link)
Don't: Case 32707. fix umlauts        (period, no colon, lowercase)

— Arvind, PR#353, PR#415, PR#416, PR#417, PR#689, PR#784, PR#924, PR#1478, PR#2281

Keep the changeset minimal and scoped to its case

🟠 consider · 🆕 novel

Do not broaden a behavior change beyond the intended subset (e.g. if the case is about multi-grippers, do not also alter normal grippers). Omit configuration/JSON settings whose value equals the default (e.g. ACBSpeed=disabled), since they add noise without changing behavior. Split unrelated change categories into separate PRs — for example, keep regenerated test-result changes apart from source/settings changes so each can be reviewed and regenerated independently.

“Why are the gripper names being changed to lower case even for normal grippers? I thought this change is only for multi-gripper?”

— Arvind, PR#1790, PR#1772, PR#349

Add release notes for every user-facing change

🟠 consider · 🆕 novel

Determine whether the change affects Flux users. If it does, add release notes before requesting merge — a missing release note blocks the PR. If the change is purely internal (no user impact), state that no release notes are needed. Reviewers must also verify that release notes have been added when applicable, not just authors.

“Release notes are missing.”

— Arvind, PR#2305, PR#865, PR#2419

Give reviewers context: explain the problem and the fix in the PR

🟠 consider · 🆕 novel

Add a brief note to the pull request describing the problem and the fix so reviewers have the context they need without reverse-engineering it from the diff. State what was failing before and why the change resolves it.

“What is the issue it is trying to address, and how is the old behavior failing?”

— Arvind, PR#897, PR#1188

Merge frequently and keep experimental code out of the production mainline

🟠 consider · 🆕 novel

Merge/integrate active branches with the mainline frequently rather than deferring — a deferred merge becomes near-impossible, and new code should ship with tests covering all its paths. At the same time, do not merge experimental or incomplete code into the production system; wait until there is a working end-to-end feature and a reasonably clear specification.

“it is important that we do this merge now (or very soon), and continue merging frequently, otherwise it will become near impossible at the end”

— Arvind, PR#938

Delete unused localized strings from all language string tables

🟠 consider · 🆕 novel

After removing the final reference to a localized string, verify it is not used anywhere else, and if not, delete it from all the language stringtables (not just one).

“Check if the strings 2572, 2571 and 2605 are not used anywhere else, and if so, remove them from all the language stringtables.”

— Arvind, PR#2653

Only the thread opener resolves a review conversation

🟠 consider · 🆕 novel

When you respond to a review comment, leave the thread open. Do not tag your own review conversations as resolved — resolution is reserved for the person who started the conversation, analogous to only the case opener closing the case.

“After you respond to one of these conversations, you should NOT tag it as resolved. Only I should do that... only the person who starts the conversation should be able to tag it as resolved.”

— Arvind, PR#794

Use the Assignee field to drive review flow

⚪ suggest · 🆕 novel

When requesting a review, set the Assignee to the reviewer. If review fails, set it back to the implementer; when it passes and is ready to merge, assign it to the merger. Do not expect action on a PR that is not assigned to that person.

“When assigning a case for review, set the Assignee to that reviewer. When the review is complete, set the assignee back to the implementor (if review fails) or to me (if it passes).”

— Arvind, PR#820, PR#876, PR#924

No emoji in professional communications

⚪ suggest · 🆕 novel

Do not use emoji in pull request comments, commit messages, or other professional/project communications.

“let's keep emoji out of our professional communications.”

— Arvind, PR#2634, PR#2626

Mark incomplete pull requests as draft

⚪ suggest · 🆕 novel

Switch a PR to draft mode while it is still incomplete or waiting on other changes; only move it out of draft when it is ready for review. This keeps the queue of pending pull requests limited to those actually awaiting action.

“Switch this pull request to draft mode until the other changes are completed. ... Then, it does not show up in the queue of pending pull requests.”

— Arvind, PR#570

Move dead/experimental code to the DeadCode store, not shipping projects

⚪ suggest · ↔ G011

Do not leave temporary/experimental code in production projects like Flux.Console. Move such code to the dedicated dead-code location (e.g. Y:/DeadCode/...), which is kept under version control for future reuse if needed.

“I moved the temporary code out of Flux.Console, into Y:/DeadCode/Bend (which is a new location where we will store such 'dead code' for future reuse if needed).”

— Arvind, PR#1283
