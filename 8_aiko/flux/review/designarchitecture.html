🏛️ Flux Review — Design & Architecture

[!abstract] Scope · priority: firm Root-cause thinking, API-surface hygiene, invariants-by-construction, strong typing, DRY.

This page has two parts: the official repo rules for this theme (G006, G011, G023, G026, G027, G033, G035, D001, D002, D003, D004, D005, D006, D014, D017, D018, D020, D021, D025) and Arvind's mined additions (29 rules, 26 novel).

📘 Official repo rules (source of truth)

[!note] Verbatim from the repo — do not edit here Copied from .github/instructions/pr-review-guidelines.instructions.md and .github/instructions/design-principles.instructions.md (loaded automatically by Copilot/Claude), synced from commit cf7f99c55 on 2026-07-13. The repo is authoritative — edit there and re-run the KB sync.

G006: Magic Numbers — Use Named Constants (58 occurrences)

Severity: High

Replace all unexplained numeric literals with named constants:

// ❌ Wrong
if (distance > 0.001) { }
mBuffer = new byte[4096];
for (int i = 0; i < 42; i++) { }

// ✅ Correct
const double Tolerance = 0.001;
const int BufferSize = 4096;
const int MaxIterations = 42;
if (distance > Tolerance) { }
mBuffer = new byte[BufferSize];

Real reviewer feedback:

"We should not use any magic numbers. Create a constant with a proper name and use it."
"Since the size is a fixed value, this can be a const."
"Replace magic numbers with double.MaxValue for clarity."

Exceptions (not magic numbers): -1, 0, 1, 2, 3, 4, 5 in loops; array indexing [0], [1]; 360, 180, 90 for geometry; 0.5 for halving; Math.PI; coordinate origin (0, 0, 0).

G011: Remove Dead / Commented-Out Code (24 occurrences)

Severity: Medium

Never commit commented-out code. Remove it entirely.

// ❌ Wrong
// var old = ComputeOld ();
// return old.Value;
return ComputeNew ();

// ✅ Correct
return ComputeNew ();

The only exception: a // TODO: comment with a full explanation of what is temporary and when/why it will be addressed:

// TODO: Camera position values are hard-coded for now. This will be replaced
// as soon as the tool master implementation is available (tracked in #45123).

Vague TODOs are also rejected:

// ❌ Vague and rejected
// TODO calc coords
// TODO fix this
// TODO mod even more coords for part, gripper

// ✅ Accepted — full sentence with context
// TODO: Stop positions are hard-coded pending the backgauge calibration API (Case 44801).

G023: Flat Namespaces Only (R020)

Severity: High — structural rule

Only these namespaces are allowed:

  • namespace Flux;
  • namespace Flux.API;
  • namespace Flux.APP;
  • namespace Flit; (for test files)
// ❌ Wrong
namespace Flux.Core;
namespace Flux.API.Bend;
namespace Flux.API.Bend.Post.BNCX;

// ✅ Correct
namespace Flux.API;

G026: Re-run APIGen After API Changes (P008)

Severity: Critical for API changes

If you add, modify, or remove any public member in namespace Flux.API:

  1. Re-run APIGen to regenerate the .gen.cs output files.
  2. Commit the regenerated files in the same PR.
  3. Document the API change in the PR description.

G027: Singleton Pattern with Lazy<T> (R018)

Severity: Low — but marks code quality

For thread-safe singletons:

// ✅ Thread-safe singleton
static readonly Lazy<MCSettings> mLazy = new (() => new ());
public static MCSettings It => mLazy.Value;

// ✅ Acceptable non-thread-safe (simple cases)
public static MCSettings It => mIt ??= new ();

Singleton property must be named It.

G033: Duplicate IDs Are Rejected

Severity: Critical

  • Translation IDs: must be globally unique across all lang files.
  • Test case IDs: must be unique; never reuse IDs from other branches.

"8091 and 8092 IDs are duplicated. Please use new IDs."

G035: Repeated Conditions — Extract to Property or Variable (P001)

Severity: Low — code quality

If you write the same condition 3+ times, extract it:

// ❌ Wrong — same condition repeated
TPickup = isMagnet ? 0 : plate["PickupTime"].F,
TRelease = isMagnet ? 0 : plate["ReleaseTime"].F,
TStop    = isMagnet ? 0 : plate["StopTime"].F,

// ✅ Better
bool isSuction = !isMagnet;
TPickup = isSuction ? plate["PickupTime"].F  : 0,
TRelease = isSuction ? plate["ReleaseTime"].F : 0,
TStop    = isSuction ? plate["StopTime"].F    : 0,

"We use this or combination at least 3 times. Should we make a property reflecting what it means?"

D001: Prefer 2D Over 3D When Possible

When a problem can be solved in 2D, do not introduce 3D.
If parts are placed flat (e.g. on a centering table, double-sheet detector), treat it as a 2D problem first.

"First, we should try to see whether we can solve the problem using 2d instead of 3d. Here, as we are placing the part flat, this can be a 2d problem."

Implication: Before adding a Point3 / Matrix3 / XForm4 computation, ask: is the Z axis actually needed here?

D002: Caching Requires an Explicit Invalidation Strategy

Every time you introduce a cache field (prefixed with _), you must immediately define and implement its invalidation trigger. Forgetting invalidation leads to stale data bugs.

"Now that you are caching it, we have to think about when to clear the cache. See, _prev, when we insert custom waypoint, _prev is set null. We may have to set _next also to null when you insert a way point. In another scenario, when we are constructing BendSteps and if we used Next in the code, as we are constructing we won't have the complete set of steps, so Next will be computed wrongly and cached."

Checklist when adding a cached field:

  • What action invalidates this cache?
  • Is there a second code path that modifies related state but doesn't reset the cache?
  • Is it safer to compute lazily at call site instead of caching (if called rarely)?

"As we are only using it in AppendCode, I think it is better getting the next step at the start and use it, instead of caching it."

D003: A Method That Does Two Things Must Be Split or Renamed

If a method has two distinct responsibilities, either:

  1. Split it into two methods with single-purpose names, or
  2. Rename it to make both responsibilities explicit in the name.

"If you look into EndMessage, it does two functions. Either the name should be EndAndSendMessage or split it. Also, I suggest all TrumpfAnalytics methods should return the JSON object which can be used for testing without having to send it."

Pattern to avoid:

void EndMessage () {
    WriteToLog ();      // side effect 1
    SendToAnalytics (); // side effect 2
}

Pattern to prefer:

string BuildMessage () => /* returns JSON */;
void Send (string json) => /* sends it */;

D004: Design for Testability — Methods Should Be Callable Without Side Effects

Methods that write files, send HTTP messages, or modify global state cannot be unit tested cleanly.
Extract the pure computation into a return value; let the caller decide what to do with it.

"Usually, we won't write to text file when called during testing. If we call the function for some other function, it will write to text file even though we don't need it. This calls for change in the logic."
"We refactored the TrumpfAnalytics code to make it properly testable. Most messages now return the JSON string and a new extension method can be called on top to send it. This allows us to test the messages without having to use FX.Testing."

Pattern: Return the data; don't send it internally.

D005: Machine-Specific if/else Must Become a Named Property

Never write if (machine is B36) or if (ePost == EPost.L95BC) directly in logic.
Instead, add a named boolean property to the machine class:

"I suspect there will be more series of machines which support this new format. My suggestion is to create a property in BendMachine like LCBV2 and use it instead of B36-specific code."

// ❌ Wrong — brittle, doesn't scale to new machines
if (mc.IsB36Series || mc.Model == "LCB") { ... }

// ✅ Correct
bool IsLCBV2 => mc.IsB36Series || mc.Model == "LCB";
// then in logic:
if (mc.IsLCBV2) { ... }

Why: New machine series will be added. Centralising the condition means you update one property, not 10 scattered if blocks.

D006: APIs Must Not Expose Temporary or Internal Fields

Do not add public properties to interfaces or base classes for fields that are implementation details or transitional.

"I think IsStandard should not be exposed. As it is temporary field, I think we need to think of other ways. How about we set UserImport flag to custom grippers and expose only that. As the Flags are serialized, it will be part of fxgrip."

Rule: If a field is temporary, find a way to express the stable, semantic intent. Expose the intent, not the implementation detail.

D014: Never Encode Machine Names in Logic — Always Abstract Upward

When you write a machine-specific condition, ask: "what is the semantic of this condition, and will other machines share it in the future?"

"We use this or combination at least 3 times. Should we make a property reflecting what it means? At least all the comments where || mc.IsB36Series was added need to be updated, because they only mention LCB laser."

Create a property in the right class (BendMachine, BCellTech, etc.) that encodes the semantic:

// In BendMachine:
/// <summary>True for machines that support the LCB V2 NC format</summary>
public bool IsLCBV2 => IsB36Series || Model.StartsWith ("LCB");

D017: Think About What Breaks When You Revert a Change

When a previous PR added something (an argument, a flag, a workaround) to fix a bug, and your PR removes it, explicitly verify the original bug is fixed.

"For Case 44397, you added the -os argument in PR #2976. Now it is removed. Is the original case fixed? Did you check? As the fix is reverted, we should reopen the case and investigate."

Rule: If your PR undoes a change from a prior PR, reference and verify the original FogBugz case.

D018: Extract Repeated Copy-Paste into a Shared Function

"Whenever you're tempted to avoid retyping repetitive code and instead copy/paste a template from somewhere else and tweak the differences, pause for a moment and consider whether something could be factored out and reused."

Duplicated blocks that differ only by parameter values should become a parameterised helper:

// ❌ Wrong — same 10-parameter call twice
NumberPair (prop1, min1, max1, step, ...);
NumberPair (prop2, min2, max2, step, ...);

// ✅ Correct
var (propName, min, max) = ...; // select upfront
NumberPair (propName, min, max, step, ...);

D020: Singleton Pattern Should Include a Key for Scoped Singletons

When implementing a singleton that may need to be scoped (by name, priority, or configuration), the key should encode all distinguishing attributes.

"In anticipating the other cases of Brick, please implement Singleton mechanism. And the key should include name and priority in addition to IFXHook-like interface."

D021: Prefer IEnumerable<T> Return Types When Caller Decides Materialisation

Return IEnumerable<T> from methods when the caller determines whether to materialise the collection. Only return List<T> if you must guarantee multiple enumeration or O(1) count.

"Also, see if you could use IEnumerable<string>."

D025: When Fixing a Regression, Prefer a Targeted Fix + Separate Refactor Case

If the PR needs to be in the next build urgently, do the minimal safe fix now and create a FogBugz case for the refactor. Don't block the fix on the refactor.

"As the pull request is needed in next build because we are trying to fix an exception and refactoring will take more time, I suggest two approaches: 1. Fix only the exception in the pull request and create another issue/case for test addition. 2. Rename the method and create another issue/case for refactoring."

🎓 Arvind's additions (mined from PR reviews)

Ordered by importance (severity, then how often he repeated it). Quotes verbatim; links to the source PR.

Keep the public API surface minimal and members as private as possible

🔴 firm · 🆕 novel

Default to private; justify each public member ('Why does X have to be public?'). Do not add fields/types to the API you don't need right now. Do not add narrowly-used extension methods to widely-used types (e.g. BendOp) — they become visible project-wide; keep single-use helpers as normal methods in the class that uses them. Don't let each post-processor add convenience functions into Flux.API. External code must depend only on Flux.API.* types — holding an internal implementation object is an abstraction leak. Expose getter-only for identity/immutable values (e.g. UID), and fire change events from the setter itself rather than exposing a separate public method.

“making private stuff public is a regressive step and should be done only as needed. It makes code analysis and refactoring more difficult, since I now no longer know if anybody is using some method”

— Arvind, PR#1055, PR#1258, PR#1176, PR#2541, PR#1685, PR#1493, PR#2201

Design with a security and privacy mindset

🔴 firm · 🆕 novel

Any in-memory buffer that grows per-event must have a bounded capacity that evicts oldest entries (e.g. cap at ~100 messages). Never trust authoritative-elsewhere data coming from external CAD (e.g. material Density) — remove all read/write of that key everywhere and rely on the internal database. Threat-model IPC auth: assume a malicious process can kill the real server and spoof responses on the same pipe. Do not push customer design data to the cloud without legal sign-off. Conversely, since .NET decompiles readily, don't over-invest in obscurity-based anti-tampering.

“This is unbounded ... if there are more than, say, 100 messages, start deleting the oldest ones. Otherwise it is a potential DOS vulnerability.”

— Arvind, PR#1294, PR#804, PR#1502, PR#386

Fix the root cause; reject crude hacks and feature-disabling patches

🔴 firm · 🆕 novel

When tempted to add a one-off guard (e.g. 'only when there is a single station') or to turn a feature off to make a bug go away, stop and find the real cause. Prefer removing an unwarranted mutation entirely over restricting it. Ask for the exact reproduction workflow before accepting a fix. Duplicated state that drifts out of sync (e.g. IsVisible vs Shading==Off) must be de-duplicated at the source, not kept in sync via setter patches.

“Why do this at all? I think we should retain the incoming setup as is without any changes. Otherwise the same bug will be reported later when they try this with a single-station setup.”

— Arvind, PR#74, PR#1017, PR#284, PR#931

Prevent invalid states by construction; model constraints as first-class data

🔴 firm · 🆕 novel

When a position/value could be invalid, narrow the selectable range up front so the invalid choice is impossible — then no warning bit is even needed. Do not rely on delicate implicit dependencies like Meshes[1]/Meshes[2] index conventions; model the constraint explicitly (e.g. a configurable shadow-zone array) and handle it uniformly across auto and manual paths. Detect invalid states through a proper reusable status mechanism (a status bit evaluated for all machines) rather than ad-hoc inspection of internal geometry.

“Why do we allow an incorrect position to be selected, and then generate a warning? Instead, we should narrow the X-Span ... and ensure the ACBLaser is never positioned in those areas ... Then, we don't even need a warning bit for this.”

— Arvind, PR#1283

An API or dialog must never close or drive UI the user may be interacting with

🔴 firm · 🆕 novel

Never let a child dialog's close implicitly close the main window — remove such code and, if closing is genuinely required, add a separate explicit call. An external/public API must never close or dismiss UI the user is possibly interacting with; redesign the workflow to avoid the API touching UI lifecycle at all.

“Why are we ever closing the main window when the MachineDBDlg is closed? That seems like a broken design.”

— Arvind, PR#2550, PR#2291

Exclude underscore-prefixed cached fields from equality and follow the _name convention

🔴 firm · 🆕 novel

When implementing Equals/comparison, compare only true state fields; skip cached fields like _area or _centerOfGravity. Non-serialized, lazily-computed backing fields should use the underscore-prefix (_nodes) convention rather than the m-prefix, precisely to signal they are cache, not state.

_“Private fields with names that begin with an underscore (like _area or centerOfGravity) are not part of the actual 'state' of the object, but are generally cached fields that are computed on demand. As such, these fields should not be compared when testing two objects for …”

— Arvind, PR#1659, PR#2267

Design extension points as dynamically-loaded plugins; never rely on a fixed shared class name

🔴 firm · 🆕 novel

Prefer a dynamic-load plugin mechanism so multiple independent variants coexist, rather than a single Flux.ExternalPost.dll the customer swaps out. Avoid any design that assumes exactly one type of a well-known name.

“Definitely a dynamic load mechanism is preferred over having a single Flux.ExternalPost.dll that will be 'replaced' by the customer.”

— Arvind, PR#1644

Property getters must have no write side-effects

🔴 firm · 🆕 novel

Keep getters pure. If a read of PostBend.Deduction would update PreBend.Deduction as a side effect, refactor so the computation is explicit and ordering-independent — code generated between the two reads must not depend on which read fired first.

“trying to read the deduction of this bend, should not update the deduction of it's pre-bend ... reading the PostBend.Deduction will update the PreBend.Deduction (unexpected!) but the code would have already been generated with the incorrect deduction.”

— Arvind, PR#227

Keep everything strongly typed; use enums and typed properties over strings, magic ints, and dictionaries

🟠 consider · 🆕 novel

Don't initialize a class from a Dictionary<string,string>; set its typed properties directly. Replace magic 0/1/2 return codes and bool-parameter bundles with named enums. Don't branch on human-readable display names (they change and prefixes collide) — use stable IDs and centralize related ID sets in named static properties. Don't introduce a lone const string when analogous keys are inline literals. The codebase direction is to eliminate strings from the public interface.

“In the adult world of C# we prefer to keep things strongly typed as far as possible ... the property assignment syntax will catch this at compile time.”

Do: enum EJawGripUsage { No, Yes, Manual } as the return type. Don't: return an int documented in a comment as 0=No, 1=Yes, 2=Manual.

— Arvind, PR#45, PR#1140, PR#2238, PR#2413, PR#255, PR#1117, PR#82

Consolidate repeated code, conditions, and derived values into one property or helper

🟠 consider · ↔ G035

Extract a repeated block into a local function (or a static local helper for parallel event handlers, keeping them perfectly in sync). Evaluate a repeated condition once. Create a single property (e.g. FoldTech.RotorYStroke) and route every call site through it, handling non-applicable machines centrally. Define derived flags off existing flags. When a comparison pattern recurs, add a well-named extension method (e.g. EQAbs) next to its siblings and grep for other sites it simplifies.

“This code is repeated twice here. Move this into a local function and call it in both the places to avoid duplication.”

Do: public static bool ShopFloor => B23 || SFDelem; (derive from existing flags). Don't: re-test the underlying enum conditions everywhere ShopFloor is needed.
