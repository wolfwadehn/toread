04 — Solution Strategy

The handful of decisions that shape everything else. Each is short on purpose — the deeper rationale lives in section 9 (Architecture Decisions).

4.1 One product, many flavors — same binary

A single Flux.exe build becomes any of the ten EFlavor values (Dev, Flux, Trumpf, Boost, Engine, ShopFloor, Lantek, Viewer, SDK, OneCore), depending on a Flux.flavor text file plus feature bits. B23, Fold (TecZoneFold) and Tech are installer variants on top of the Trumpf flavor. There are no per-flavor #if blocks.

Why: the cost of maintaining several differently compiled binaries (and several installers) was unacceptable. The flavor-specific installers compress to one rebrandable package via filename routing.

Reading: Notes\Tech\2013.FluxFlavors.ftx.

4.2 Domain projections (*Tech) over a shared Part

A Part (the work item) carries optional projections — BendTech, FoldTech, CutTech (= FlatTech), BCellTech, LayoutTech — each with its own ops, setups, and machine.

Why: a part is rarely just one process. Sheet-metal parts often go laser → bend → robot. Modeling each domain as a sibling projection keeps cross-cutting state (geometry, settings, undo) on Part while the domain logic stays self-contained per tech.

4.3 Model + view live in the same DLL

E3Plane (model) and E3PlaneVM (view) sit in Flux.Core together. The split between model and view is logical, not physical.

Why: CAD/CAM objects are tightly coupled to their visual representation. The earlier "Core has no rendering" architecture forced workarounds (the legacy "Hub whiteboard"). Pulling the view back next to the model collapses that complexity. Controllers (Glob) remain in Flux.UI because they really do need WPF, mouse, and keyboard — and the Engine flavor must be able to skip them.

Reading: Notes\Dev\1002.BuildingFlux.ftx lines 31–61.

4.4 Globs as composite controllers

Every editable domain object has a corresponding Glob — a controller that exposes properties via abstract GElement and commands. Multi-selection automatically yields a composite glob; the same property/command code handles both single and multi.

Why: bulk edits in CAM are common (select all bends, change V-width). Without a composite, every domain would re-implement multi-edit. With it, one domain author writes one set of cooperating properties.

4.5 Settings cascade via Sheaf

Every settings-bearing object implements ISheafSite. Reads walk to the parent if the local dict has no key. The cascade typically goes BendOp → BendTech → BendMachine → defaults.

Why: machine-level defaults must apply to every bend op unless overridden, and overrides must be precise (per op, per tech, per machine). A central setting registry (enum SH) plus a parent-pointer beats a flag-soup or environment-state model.

4.6 Cross-layer wiring via Hub slots

Static Func<> / Action<> slots in Src\Core\Hub.cs are filled in at startup by Flux.App (or Flux.API). Core / UI invoke them with null-safe dispatch.

Why: Core needs to ask the App for things (close a part, open a chooser dialog, wrap an object as API) without forming a project-reference cycle, and without an old-style "Hub whiteboard" object bag. The slot pattern is typed, debuggable, and naturally supports the Engine flavor (slots stay null, calls are no-ops).

4.7 Tests are golden files generated by Dump

Every tech has a Dump (TextWriter) method whose textual output is the test contract. Tests load fixtures, run the auto-tooler, dump, and compare against a .txt file checked into X:\TData.

Why: snapshots compress dozens of decisions into a reviewable diff. Hand-writing assertions for "the auto-tooler should produce this exact sequence with these exact tools at these positions" is impractical; the dump is a reviewable record.

Trade-off accepted: changing Dump cascades to dozens of golden files. That's a feature, not a bug — the change becomes a deliberate review.

4.8 Postprocessors are C# classes per dialect

Each NC dialect (TrumpfDLD, Bystronic, LVDWriter, BNCWriter for Cell5K / TrumpfB23, Cybelec, Safan, Jupidu, Muratec, Euromac, Komatsu, ESA, Cincinnati, …) is a hand-written C# class in Src\API\Bend\Post\. A switch in Src\API\Basis\Basis.cs::GenerateNC dispatches by post name.

Why: the Hex post-processor language plan from 2016 (Note 2004) was scrapped — once the dialect set stabilized at ~20, native C# proved both faster and easier to maintain. Each writer can use the full C# tooling for tests and refactoring; the language overhead disappeared.

4.9 Persistence: text Curl, binary Au, packaged FX

  • Curl — Lisp-flavored text format for hand-curated data: machines, tool catalogs, settings profiles. Readable, mergeable.
  • Au (also "Gold") — compact tagged binary for runtime state: parts, techs, ops. Each Au type carries an ObjVersion; deserialized objects can implement [PostLoad] for forward migration.
  • FX file — a zip bundling Curl + Au + thumbnail; the user-visible save format.

Why: Curl is for things humans read and edit; Au is for things engines read and write at scale. The boundary is intentional. FX wraps both for portability.

4.10 Determinism over performance over modularity

When trade-offs collide, this is the priority order. Examples:

  • Sorts that risk floating-point near-tie reordering use GeomSort rather than OrderBy. (Determinism > speed of one fewer hop through a comparator.)
  • The BendTech constructor is ~250 lines, not split into "small constructors". (Performance + invariants > textbook decomposition.)
  • Models and VMs share an assembly. (Practicality > strict modularity.)

4.11 Read-only first onboarding for new contributors

The team commits six months to a new developer's read-only learning path before expecting code commits. The Onboarding handbook (X:\Doc\Onboarding\) is the curriculum; Arc42 is the architectural backbone for it.

Why: the codebase is dense (~1.7 MB in Bend\ alone). A junior contributor who starts editing BendOp.cs (210 KB, sealed partial) before understanding the M/V/Glob/Sheaf/Hub stack will introduce subtle bugs faster than they can fix them. Reading is cheap; the cost of careless commits is high.

4.12 Strict, opinionated reviews

Every PR is reviewed against a synthesized rule-set derived from 5,013 historical review comments — captured in .github\instructions\design-principles.instructions.md and pr-review-guidelines.instructions.md. The Copilot integration loads these automatically. Examples of standing rules: caches require explicit invalidation (D002); machine-specific if/else becomes a named property (D005); compute-once-then-transform (D007); ReadOnlySpan<T> for read-only array params (D008); no compiler warnings (D010).

Why: with a small core team and a large surface, code-review consistency is the only sustainable QA mechanism. The instructions are the de-facto architecture rules.
