09ArchitectureDecisions

product: flux org: metamation type: design tags: [flux, arc42, architecture] source: 'D:\dev\Flux-Web\Doc\Arc42\09_Architecture_Decisions.md' updated: 2026-07-14

09 — Architecture Decisions

A retroactive ADR list. Decisions are extracted from Notes\Dev\ / Notes\Tech\ and the synthesized review-rule set under .github\instructions\. Some decisions are clearly attributed; others are codified by long-running practice.

Each ADR is structured: Decision · Status · Context · Consequences.

ADR-001 · Model and view live in the same DLL

Status. Accepted. (Reverses an earlier decision.)

Context. The original architecture put models in Flux.Core and views in a separate "UI" / view layer. CAD/CAM operations like generating an FX-file thumbnail or a setup-sheet PDF need to render geometry — they couldn't do that without reaching across the layer boundary, which forced the legacy "Hub whiteboard" anti-pattern (an untyped global object bag).

Decision. Keep model and VModel in the same assembly (Flux.Core). Make the rendering layer (Lux) a primitive in Flux.Base so both can reach it. Keep controllers (Glob) separate in Flux.UI.

Consequences.

  • The Engine flavor (no UI) can still render thumbnails and setup sheets headlessly.
  • Generating an FX file works without the App layer being loaded.
  • The strict logical separation is lost — but it was a fiction anyway, so the loss is on paper only.
  • Reading documented in Notes\Dev\1002.BuildingFlux.ftx lines 31–61.

ADR-002 · Cross-layer wiring uses typed Hub slots, not an object bag

Status. Accepted.

Context. The legacy Hub was an untyped Dictionary<string, object> used to push state across layers. Type-unsafe; opaque to callers; prone to silent failures.

Decision. Replace it with static Func<> / Action<> slots on Src\Core\Hub.cs. App fills slots at startup. Core/UI invoke null-safely.

Consequences.

  • Engine flavor works naturally — slots stay null, calls are no-ops.
  • Adding a slot is a deliberate design moment.
  • Refactoring tools see real signatures.
  • One small downside: Hub is a "service locator" smell at first glance, but the typed-slot variant is materially different from the runtime-key locator and not subject to its critique.

ADR-003 · Single binary, runtime-selected flavor

Status. Accepted.

Context. Ten EFlavor values (Dev, Flux, Trumpf, Boost, Engine, ShopFloor, Lantek, Viewer, SDK, OneCore) plus installer variants (B23, TecZoneFold, Tech-demo) on top of Trumpf. Compiling N variants would multiply CI time and ship-and-test cost. Per-flavor #if blocks distort the codebase.

Decision. One Flux.exe binary. A Flux.flavor text file next to the EXE selects the flavor at runtime. Feature bits (declared per flavor) gate features (UI / Bend / Laser / Punch / Trial / Internal / …).

Consequences.

  • One binary to test, one to ship.
  • The installer routes by filename: Setup.TecZoneBend.<build>.exe writes Flux.flavor=Trumpf, Setup.LantekBend.<build>.exe writes Flux.flavor=Lantek, etc.
  • The flavor matrix has to stay healthy (a feature added to one flavor must be considered for Trumpf, Boost, Lantek, OneCore, …).
  • Each flavor brings its own licensing back-end — see section 7.4. Adding a flavor is also a license-stack decision.
  • Documented in Notes\Tech\2013.FluxFlavors.ftx.

ADR-004 · Domain projections (*Tech) over a shared Part

Status. Accepted.

Context. A sheet-metal part is rarely a single domain — it may be cut, then bent, then handled by a robot. Mashing all domain logic into one giant aggregate breaks separation of concerns; spreading it across unrelated objects breaks cross-domain queries.

Decision. A Part is the shared aggregate. Each domain hangs a tech projection off the part: BendTech, FoldTech, FlatTech (laser/punch), BCellTech (cell automation), LayoutTech. Each tech is constructed via a static *.Make factory and is mutually independent.

Consequences.

  • Cross-cutting state (geometry, settings, undo) lives on Part.
  • Domain logic stays self-contained per tech.
  • Adding a domain means adding a new tech and wiring it on Part.

ADR-005 · Make factory pattern with private constructors

Status. Accepted.

Context. Substantial initialization logic in domain types. Public constructors fail to enforce all invariants and don't return EResult for predictable failures.

Decision. Every non-trivial top-level model (BendTech, BCellTech, Machine) is constructed via a static Make (...) returning EResult. The constructor itself is private.

Consequences.

  • Validation gates are unbypassable.
  • Constructors carry real logic — BendTech constructor is ~250 lines. This is intentional, not a smell.
  • New contributors must internalize the pattern early.

ADR-006 · Global Sheaf cascade for settings

Status. Accepted.

Context. Sheet-metal CAM has many settings — per-machine defaults, per-tech overrides, per-op tweaks. Independent dictionaries are a maintenance nightmare; a single flat dictionary loses parent semantics.

Decision. Every settings-bearing object implements ISheafSite { SHName, SHDict, SHParent }. Reads walk the chain. Keys are the closed enum SH.

Consequences.

  • Where you write matters — op-level shadows tech, tech-level shadows machine.
  • A bug class is "I changed the wrong level".
  • Adding a setting is a deliberate change to enum SH.

ADR-007 · Au binary + Curl text, with [PostLoad] migrations

Status. Accepted.

Context. Two persistence needs: machine-readable runtime state at scale (parts, techs, ops) vs. human-curated config (machines, tool catalogues). Trying to use one format for both is awkward.

Decision. Au binary for runtime state; Curl text for human-curated data. The FX file packages both with a thumbnail. Each Au type carries ObjVersion; deserialization runs [PostLoad] for forward migration.

Consequences.

  • Forward-migration is a first-class operation, not an afterthought.
  • Migrations are forward-only.
  • Dump (TextWriter) is the human-readable test contract for state — Curl/Au are not.

ADR-008 · Tests are golden files generated by Dump

Status. Accepted.

Context. Hand-writing assertions for "this auto-tooler should produce this exact sequence with these exact tools" is impractical at scale. A snapshot diff is.

Decision. Every tech has a Dump (TextWriter) method whose output is the test contract. Tests load fixture, run the auto-tooler, dump, and compare against a .txt golden file in X:\TData.

Consequences.

  • A change to Dump cascades through dozens of golden files. This is a feature — the change becomes a deliberate review.
  • Adding a test means adding a fixture (.geo / .fx) + golden output.
  • The team has built tooling around this — see Onboarding chapter 06.

ADR-009 · NC postprocessors are C# classes, not a scripting language

Status. Accepted. (Reverses an earlier 2016 plan.)

Context. The 2016 plan (Note 2004) was to implement a Hex post-processor scripting language so dialect support could be data-driven. As the dialect set grew to ~20 stable variants, scripting overhead exceeded the value of data-driven dialects.

Decision. Each NC dialect (TrumpfDLD, Bystronic, BNCWriter, LVDWriter, CybelecWriter, Safan, Jupidu, Muratec, Euromac, MCBWriter/Komatsu, ESA, Cincinnati, DLCWriter, BNCXWriter, PlatformBendWriter, Accurpress, SafanPBP, External) is a hand-written C# class in Src\API\Bend\Post\. Dispatched by post-name basename in Src\API\Basis\Basis.cs::GenerateNC (line 138).

Consequences.

  • Each writer can use the full C# tooling for tests and refactoring.
  • The Hex language no longer runs at runtime; Note 2004 is historical.
  • The .hx filename extension survives in machine config (e.g. wad:Post/Bend/TrumpfB23.hx) as a routing token only.
  • Adding a dialect is a code change with tests, not a script load.

Residual. Src\Base\HexLib.cs still exists, but it is not the Hex interpreter — it is a small XML/JSON document-builder utility (JDoc, XDoc, XElem, JBlock, XBlock, ZDoc) that kept the Flux.Hex namespace name. Live call sites: Src\API\Basis\ConfigSync.cs:17 (config-sync manifest), Src\Core\Bend\TSOBatch.cs:263 (TSO summary report), Src\Core\Bend\Ops\DLDExporter.cs:22 (DLD serialisation), Src\Core\Bend\Ops\BOptimizer.cs:363, 405 (parts / tools reports). Treat it as named infrastructure, not legacy code; renaming the namespace would be an unrelated cleanup.

ADR-010 · Composite globs for multi-selection

Status. Accepted.

Context. CAM users routinely multi-select (all bends, all cuts) and want to edit a property across the selection. Re-implementing multi-edit per domain is ugly.

Decision. Every concrete glob class has a corresponding "plural" composite (BendOpGlob / BendOpsGlob). The composite shows agreed properties, marks disagreed ones, dispatches commands to all members in a single undo unit. Most of this is built by the Glob machinery — domain authors write cooperating per-property code.

Consequences.

  • Domain authors write one set of properties; composite works for free.
  • Multi-edit semantics are uniform across the product.

ADR-011 · Modern C# (.NET 10), x64-only

Status. Accepted. (Reverses earlier any-CPU + 32/64-bit dual Hula scheme.)

Context. The original architecture supported both 32- and 64-bit deployments via the Flux.Hula32.dll / Flux.Hula64.dll mechanism (loaded via assembly-load-failure handling). Customer demand for 32-bit ended; the dual mechanism became costly.

Decision. Target .NET 10. <PlatformTarget>x64</PlatformTarget> in every csproj. Flux.Hula32.dll is gone; only Flux.Hula64.dll remains. Modern C# features adopted: file-scoped namespaces, #nullable enable, switch expressions, records, target-typed new.

Consequences.

  • Note 1002's "Why are there two separate wrappers for Hoops?" section is historical.
  • Smaller install size, simpler resolver code.
  • Modern code is more concise and safer.

ADR-012 · Strict, codified PR review based on synthesized rules

Status. Accepted.

Context. A small core team and a large surface (~938 .cs files in Src). Maintaining design quality across hundreds of PRs requires consistency.

Decision. Synthesize the recurring patterns from 5,013 PR review comments into .github\instructions\design-principles.instructions.md and pr-review-guidelines.instructions.md. Wire Copilot to load them automatically.

Consequences.

  • Standing rules are explicit: D001 (2D before 3D), D002 (cache invalidation), D004 (testability), D005 (machine props not if/else), D007 (compute once, transform), D010 (no warnings), D011 (no silent returns), …
  • New contributors can preview the standing review.
  • The instructions are de-facto architecture documentation — Arc42 sections 8 and 11 reference them.

ADR-013 · Single solution Flux.sln; HOOPS wrapper outside it

Status. Accepted.

Context. Eight C# projects + a C++/CLI wrapper. Mixing C++ and C# in one solution slows builds and complicates the dev workflow.

Decision. X:\Src\Flux.sln holds the eight C# projects. X:\Src\Hula\Hula64.sln is separate. The C++/CLI DLL is not built from source in routine development — pre-built Flux.Hula64.dll is copied from X:\Resources\Hoops.

Consequences.

  • Routine builds skip C++ tooling.
  • A HOOPS upgrade is a coordinated event involving the dedicated wrapper rebuild.
  • The repo's Hula64.sln is kept buildable for the upgrade scenario but doesn't run in CI.

ADR-014 · Mercurial → Git

Status. Accepted (already complete).

Context. Mercurial / Kiln (metamation.kilnhg.com) was the original VCS. Industry tooling shifted to Git.

Decision. Migrate to Git. PR culture follows GitHub style (numeric PR IDs visible in commit messages: (#3394)).

Consequences.

  • Note 1009 (Mercurial branches) is historical.
  • Branch naming, hook conventions, and CI integrations all changed accordingly.

ADR-015 · Read-only first onboarding

Status. Accepted.

Context. A junior engineer who starts editing BendOp.cs (210 KB sealed partial) before understanding M/V/Glob, Sheaf, Hub, and the test contract introduces subtle bugs faster than they can fix them.

Decision. Six months of structured read-only learning before code commits. The Onboarding handbook (X:\Doc\Onboarding\) is the curriculum.

Consequences.

  • Slower ramp to first commit.
  • Faster ramp to useful commit.
  • Encourages self-driven exploration over copy-paste contributions.

ADR-016 · Two crash engines coexist (in flight)

Status. Pending — migration in flight.

Context. BendOpCrash.cs (classic) and NBendCrash.cs (new) both exist (~70 KB each). The new engine handles cases the classic one didn't; cutover hasn't completed.

Decision. Both are kept active behind a runtime flag while migration completes. Code touching collision logic must consider both.

Consequences.

  • Doubled maintenance burden in the short term.
  • A clear pickup target for a future ADR resolution.
  • Listed as risk R-001 in section 11.
