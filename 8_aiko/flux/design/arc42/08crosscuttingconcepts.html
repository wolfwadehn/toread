08CrosscuttingConcepts

08 — Crosscutting Concepts

The recurring themes that show up everywhere in Flux. If you understand these, you can read code in any subsystem.

8.1 Settings cascade — Sheaf / ISheafSite

Where: Src\Core\Settings\Sheaf.cs.

Pattern. Every settings-bearing object implements:

public interface ISheafSite {
   string SHName { get; }                       // e.g. "Machine 135" or "Bend 3"
   Dictionary<SH, object> SHDict { get; set; }  // local overrides (may be null)
   ISheafSite SHParent { get; }                 // fallback site
}

A read for SH.RamVBend on a BendOp walks: BendOp.SHDict → BendTech.SHDict → BendMachine.SHDict → defaults. The first hit wins.

Implications.

  • Setting on the op level shadows tech and machine values.
  • Setting on the machine level affects every tech using that machine.
  • The keys are values of the closed enum SH.
  • Cascade reads must be efficient — they happen frequently during render and auto-tooling.

8.1.1 Defaults pipeline — base + unit overlay + flavor overlay + installation

The "defaults" end of the cascade is itself built by overlaying four sources, in order, in the FX.Settings getter (Src\Core\FX.cs:130–:166):

  1. Base — wad:core/settings.curl (~12 KB, ~190 lines). The factory floor: every section (Info, Bend, Fold, Cut, Laser, …) populated with conservative defaults.

  2. Unit overlay — wad:core/delta-inch.curl, merged in only if FX.DefaultUnit == EUnit.Inch (read from unit.dat via Notes.GetS("Unit")). Unit-driven, not flavor-driven.

  3. Flavor overlay — one of nine files in wad:core/, picked by Permit.SettingsOverlay (Src\Core\Permit.cs:332):

    Returned filename Selecting condition
    delta-dev.curl EFlavor.Dev
    delta-meta.curl EFlavor.Engine, Flux, Viewer
    delta-trumpf.curl EFlavor.Trumpf
    delta-boost.curl EFlavor.Boost
    delta-lantek.curl EFlavor.Lantek
    delta-sftouchpoint.curl Permit.SFTouchpoint (ShopFloor + FluxSFType=touchpoint)
    delta-sfdelem.curl Permit.SFDelem (ShopFloor + FluxSFType=delem)
    delta-sfplb.curl Permit.SFPlb (ShopFloor + FluxSFType=plb)
    (none) other flavors

    Each delta is a small Curl document ( ~300 B – ~2 kB) containing only the keys that diverge from base. Example (delta-trumpf.curl):

    (FluxSettings){
  Bend:{ Outputs:{ BendRepTemplate:"wad:Report/trumpf.bend.ftrep"
                   BendRepDestination:"C:\TecZoneBend"  ... } }
  Fold:{ Outputs:{ ... } }
}

    Lantek's overlay uses env-var substitution like BendRepTemplate:"$LANTEKINSTALLDIR\Data\Samples\Report\lantek.bend.ftrep", resolved at load.

  4. Installation overlay — home:System/settings.curl (per-install, customer-mutable). Wrapped as a SheafHolder whose parent is the merged factory holder (steps 1–3).

The result of step 4 is what every ISheafSite chain bottoms out at — so a per-op write shadows tech / machine / installation / flavor / unit / base, in that order.

Implication: shipping a per-flavor behaviour change is a content edit, not a code change. Adding a new flavor does require a delta file plus a Permit.SettingsOverlay arm.

8.2 Cross-layer wiring — Hub slots

Where: Src\Core\Hub.cs (definitions), Src\API\Basis\Basis.cs:122 (one set of fillers), Src\App (the rest).

Pattern. Static Func<> / Action<> slots. App fills at startup; Core/UI invoke null-safely.

// in Hub.cs
public static Func<object, string, object> GenerateNC;
public static Func<string, string, IList<string>, int, bool, object, int> BigChooser;
public static Action CloseBlankMainWindow;

// at startup (Basis.cs)
Hub.GenerateNC = GenerateNC;
Hub.APIWrapper = DoAPIWrap;
Hub.MCBtoTXT = MCBReader.Convert;

// from Core or UI
var nc = Hub.GenerateNC?.Invoke (part, "trumpfdld");

The pattern replaces the legacy "Hub whiteboard" anti-pattern (untyped object bag). It is explicit, typed, debuggable, and naturally null-safe for the headless Engine flavor.

8.3 Mutation through BA.Set

Where: Flux.Base, search class BA.

BA.Set<T>(ref _field, value, …) does three things in one call:

  1. Equality check (skip if no change).
  2. Notification (INotifyPropChanged).
  3. Undo registration.

Flag-based properties use a different overload — Set (EFlags.X, value) — but the contract is the same.

A direct _field = value is a smell unless the property has a deliberately different contract (private fixup, [PostLoad] migration, etc.). The PR-review rule is explicit on this.

8.4 Result enums (EResult) over exceptions

Where: Flux.Base.

Predictable failures return EResult (OK plus a fixed set of failure modes). Exceptions are reserved for invariant violations (CodingError).

Callers:

  • BendTech.Make (...).Is (EResult.OK)
  • Part.DoFoldTo3D ().Is (EResult.OK)

Adding a new failure mode is a deliberate change because callers exhaustive-switch on the enum. This is the source of high signal/noise in error handling.

8.5 Au binary persistence + [PostLoad] migrations

Where: Flux.Base\Gold\ (runtime), every persisted model (consumers).

Each Au-serialized type carries an ObjVersion. After deserialization, any method tagged [PostLoad] runs. Inside, callers check AuType.ObjVersion < N and migrate fields forward.

[PostLoad]
void PostLoad () {
   if (AuType.ObjVersion < 4 && BMachine != null) {
      // migrate clamp positions to new origin
      float dx = BMachine.Clamp0XPos;
      for (int i = 0; i < mClampPos.Length; i++) mClampPos[i] += dx;
   }
   if (AuType.ObjVersion < 5)
      foreach (var m in mMounts) AdjustLockedMount (m);
}

Migrations are forward-only. They never read into the future.

8.6 Curl text persistence

Where: machine definitions, tool catalogues, settings profiles. Documented in Notes\Tech\2007.CurlFiles.ftx.

Lisp-flavored, hand-readable, mergeable in version control. Curl is for things humans curate; Au is for things engines persist at scale.

8.7 Determinism

Several mechanisms enforce that the same input + machine + options produce the same output:

  • GeomSort instead of plain OrderBy on doubles — handles float near-ties consistently.
  • Stable test machines — id 13 (default standalone), id 99 (Default in BA.Testing), id 93 (cell-attached default). Their Machine.curl is the de-facto contract.
  • Dump test contract — the textual snapshot of the auto-tooler's output is the regression-test backbone.
  • No Random without explicit seed — design principle.

Determinism is the prerequisite for the golden-file test strategy (see §8.10).

8.8 Caching with explicit invalidation

Where: Pervasive — wherever you see a _field named with a leading underscore.

Design principle D002: every cached field gets a paired invalidation strategy. The naming convention (leading underscore) makes caches grep-able. Every cache must have an answer to:

  • What action invalidates this cache?
  • Is there a second code path that modifies related state but doesn't reset the cache?
  • Is it safer to compute lazily at the call site instead of caching?

A cache without an invalidation plan is a stale-data bug waiting to happen.

8.9 Compute once, transform — don't re-convert

Where: Numerical / geometric pipelines.

Design principle D007. Converting between heavy types (Mesh ↔ Collider ↔ scene-graph) is expensive; applying a transform is cheap. Once you have a converted form, transform it instead of round-tripping through the conversion.

Rule of thumb: if a method ever calls ToCollider(...) more than once on the same mesh, it's wrong.

8.10 Testing — Flit + golden files

Where: X:\Test\ (~169 files). Documented in Onboarding chapter 06.

Idiom:

[TestFixture (4, "Basic bend auto-tooler tests", Module = "Bend", Subsystem = "AutoTool")]
class BasicBendAuto {
   [Test (82, "Tooling basic part: Bend_04.geo")]
   void Test1 () => Test ("Bend/Auto/Bend_04.geo");

   public static Part Test (string file, int idMachine = 13, /* ... */) {
      Part part = FX.LoadTestPart (file);
      BendTech.Make (part, BendMachine.Get (idMachine)).Is (EResult.OK);
      BendTooler.Process (part.BendTech, flags);
      CheckDump (tech, outfile);   // ← golden-file compare
      return part;
   }
}

Golden files are .txt next to the input fixture.

8.11 Logging / messages — numeric IDs

Where: FX.Out (EOut.Info, msgId, args). Documented in Notes\Tech\2015.MessageIDs.ftx.

Each user-visible message has a numeric ID. Translation tables map IDs → strings per locale. Searching for a message ID in source code locates exactly where it's emitted.

Design principle: never return silently from a fallible operation. Always emit a message.

8.12 Threading and re-entrancy

Reality: UI thread + opportunistic worker tasks. No general concurrency model.

Static singletons (Part.Current, Part.Active, BendMachine.Default, Hub.*) are UI-thread-only in practice.

The realistic concurrency hazard is re-entrancy: a property setter triggering a render, which triggers another setter. Where re-entrancy matters, code uses if (mInsideX) return; guards.

8.13 Coordinate systems

CS Anchored to Used in
World scene origin overall rendering
Plane CS each E3Plane's side wall (Org / XVec / YVec / ZVec) bend-area modeling — see Notes\Dev\1005.BendAreaModeling.ftx
Flex CS inherited from leeward plane bend operations
Machine CS machine table (X along table length) machine-relative geometry
Mount CS local on table tool placement

When coordinates look wrong on screen, the first question is "which CS is this in?" Plane↔World transitions are a frequent source of subtle bugs.

8.14 Units and tolerances

  • All lengths in mm.
  • All angles in radians at runtime; degrees only in user-facing strings via .D2R() / .R2D().
  • Tolerances are domain-specific (geometric vs. simulation vs. file-format precision).

8.15 Identity

Concept Stable across Implementation
BendOp.UID, BendSetup.UID save/load per-tech sequence counter
Part.GUID save/load random GUID, persisted
BendMachine.Id install integer, used as folder name
VModel.Id one process scene-graph routing only — never persist

8.16 Telemetry / analytics

Trumpf-flavor builds emit telemetry through TrumpfAnalytics. Design principle D004 was extracted from feedback on this code: messages return their JSON payload; the send is a separate extension method. This makes them testable without a FX.Testing runtime check.

8.17 Permissions (FX.Permits)

Capability-style runtime checks. Examples:

  • FX.Permits (EPermit.Hoops) — gate 3D import features.
  • FX.Permits (EPermit.Bend) — gate the entire press-brake module.

The active permits are derived from flavor + license. The Engine flavor has different permits than the Trumpf flavor.

8.18 The Hub.APIWrapper indirection

Where: Src\API\Basis\Basis.cs:117.

A single delegate wraps Core objects with their API counterparts. When Core hands an object across the API boundary, it goes through Hub.APIWrapper?.Invoke (...). This keeps Core innocent of the API's existence.

8.19 Architecture invariants checklist (for code review)

When reviewing a PR, the unspoken checklist is:

  • Does it respect the M/V/Glob layering?
  • Is BA.Set used, not direct field assignment?
  • Are caches paired with invalidation?
  • Does the change keep the Engine flavor working (no UI dependency added to Core)?
  • Are new public types necessary, or can existing ones extend?
  • Is [PostLoad] updated for any persisted shape change?
  • Are golden files regenerated and reviewed?
  • Are message IDs added (not silent returns)?
  • Are warnings clean?

The review-ruleset under .github\instructions\ codifies this.

8.20 Localization — XL and the lang folder

Every user-facing string in Flux runs through XL ("translate"). It is an extension method with several overloads on string, int, Enum, Type, and MemberInfo, defined in Src\Core\Extension.cs:97+ and :400+. Two callers cover ~99 % of usage:

Caller Form What gets translated
FX.Out (EOut.Info, 1192, args) int.XL () A numeric message ID — looked up by its decimal name ("1192") in the lang dictionary. The convention is in Notes\Tech\2015.MessageIDs.ftx.
someEnum.XL () Enum.XL () An enum value — looked up by <TypeName>.<EnumValue> (e.g. EBStatus.PunchCrash). Used for status / error codes that need translation in error reports.

Both forms hit the same dictionary; the only difference is the lookup key. XL returns the English text if the active language has no entry — never throws.

File layout

Wad\lang\ (loose folder on dev machines; baked into Flux.wad on installs) holds one sub-folder per language:

Wad\lang\          ← English (default; root files)
        \DE\       ← German
        \CHS\      ← Chinese (Simplified)
        \CHT\      ← Chinese (Traditional)
        \CS\  \DA\ \ES\  \FR\  \GR\  \ID\  \IT\  \JP\  \KO\
        \HU\  \NL\ \PL\  \BR\  \RU\  \SK\  \FI\  \SV\  \TH\  \TR\
        \TE\       ← Trumpf English (override of EN for Trumpf-flavor terminology)

Each language folder contains topic-split .txt files (general.txt, bend.txt, fold.txt, cut.txt, editors.txt, settings.txt, report.txt, workflow.txt, boost.txt, 2d.txt, 3d.txt, …). Format is key, value per line:

EGTag.UseAsBasePlane, Set Baseplane
190, Set this as the base-plane for panel-bending

Numeric and string keys live in the same file. The 24 ELanguage enum values are declared in Src\Core\Enums.cs:64–:93 (Unk, EN, DE, CHS, CHT, CS, DA, ES, TE, FR, GR, ID, IT, JP, KO, HU, NL, PL, BR, RU, SK, FI, SV, TH, TR, _Last).

Active-language selection at startup

Src\App\App.xaml.cs:184–:188 (and Src\Core\FX.cs:1604 for the runtime setter):

if (FX.Env.Language == ELanguage.Unk && !FX.BatchRun) {
   if      (Permit.ShopFloor)              FX.Env.Language = ELanguage.DE;   // shop-floor HMIs ship German
   else if (args.Any (a => a.EndsWithIC (".fxcmd"))) FX.Env.Language = ELanguage.EN;  // Boost batch defaults to EN
   else    PickLanguage ();                                                  // interactive picker dialog
}

The picker (PickLanguage.xaml) writes the choice into FX.Notes; subsequent runs skip it. FX.SetLanguage flushes the lang dictionary and reloads from the chosen folder. Auto-compute paths inside the engine call SetLanguage per-job (so a German-locale install can still emit English error messages in a .fxresp file when the requesting Boost adapter asks for English).

Translator workflow

The Tools\XLate\ project is the round-trip tool: xlate make <lang> extracts an Excel spreadsheet from the current .txt tables (output into Y:\XLate\New); a translator fills it in; xlate use <lang> writes the result back into the lang folder. delpics <lang> strips embedded illustration images before checking the lang folder back into source control. See §05.10.

8.21 Experimental feature flags — Experimental class

A second feature-gating system, parallel to (not interacting with) the licensing EFeature enum. Where EFeature gates whole product capabilities sold under contract (Bend, Laser, Fold, BendCell, Trial, …), Experimental toggles in-development features that have shipped but aren't yet defaults.

Where: Src\Core\Classes.cs:20–:193. Static class. Each flag is a static bool property backed by a private static int field, plus optional [Nom("section~Description")] attribute on the property to mark it UI-visible.

Storage. Persistent in <DataDir>\System\experimental.ini (section [Settings], INI key/value). Loaded at static-constructor time (Classes.cs:23–:39); Save() (:41–:49) writes only the [Nom]-attributed flags so non-UI fields can stay private. Skipped under BA.Testing.

Sample flags (pulled from the file):

  • UndoBend, UndoCut — newer undo machinery for Bend / Cut.
  • FlexCellSupport — flexible robotic-cell machine type.
  • BNCOutput — output BNC files for B23 / B28 alongside DLD.
  • CanTurnGripper, BendFormsinGeo, BtdImportExport, ShoppingList, DLCGraphics, UpdateDuringDrag, CheckFoldOffCenter, ForceDXFImportUnit, FitArcOrLine, ShowModelOrigin, BToolExportDLD.
  • Non-bool fields: WindowMode (string), PressForceFactorTouchpoint (double), FlexCellMC (int).
  • DisableBricks — diagnostic kill-switch for the plugin loader (Src\API\Bricks.cs:22).

UI. The "Experimental" dialog (EditExperimental in Src\App\UI\MiscUI.cs:113–:150) reflects all [Nom] properties into a checkbox list. The Nom string format "Section~Description" (split on ~) groups related flags under bold section headers. Toggling fires TrumpfAnalytics.ButtonInteraction.

Telemetry. Experimental.GetFeatures (onlyNom: false) returns a Dictionary<string, int> of every int field's current value. Emitted with each application_startup analytics message (TrumpfAnalytics.AppStarted in Src\Core\CmdProcess.cs:1933–:1939) so Trumpf-side analysis knows which experimental paths a given session exercised.

Distinction from licensing. Flipping an experimental flag does not unlock a licensed feature; both gates apply independently. Promoting an experimental flag to "default on" is a code change (move it out of Experimental and into the relevant subsystem's settings).
