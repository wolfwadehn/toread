07 — Deployment View

How Flux gets onto a machine and where its files live at runtime.

7.1 Developer machine layout

C:\Work\Flux\         actual repository clone
  ├── Code\Src\         → mounted as X:\Src
  ├── Test\Test\        → mounted as X:\Test
  ├── Test\TData\       → mounted as X:\TData
  ├── Data\Doc\         → mounted as X:\Doc
  ├── Data\Data\        → mounted as X:\Data
  ├── Data\Resources\   → mounted as X:\Resources
  ├── Data\Wad\         → mounted as X:\Wad
  ├── Data\Help\        → mounted as X:\Help
  ├── Data\Notes\       → mounted as X:\Notes
  └── Code\Tools\       → mounted as X:\Tools

Everything assumes the X: subst is active. subst X: C:\Work\Flux is part of the developer onboarding ritual. Notes\Dev\1002.BuildingFlux.ftx documents the Mercurial-era version of this; the current setup uses Git but the same drive layout.

Required environment variables on a dev machine

Variable Value Purpose
FLUXDATA X:\Data Runtime data root
FLUXTESTDATA X:\TData Test inputs
FLUXDEVELOPER 1 Enables developer-mode features
FLUXWAD X:\Wad Read-only resources (loose folder, not zip)

Build prerequisites

  • Visual Studio with .NET 10 + WPF + WinForms workloads.
  • C++ workload only required if you bump HOOPS — otherwise pre-built Flux.Hula64.dll is copied from X:\Resources\Hoops.
  • Pre-setup installer (FluxPreSetup.<year>.exe) once per machine — installs MS VC runtimes and other shared dependencies.

7.2 End-user installation

Aspect Value
OS Windows 10/11 64-bit
Architecture x64
.NET Runtime .NET 10 (bundled with installer where needed)
Disk a few hundred MB
RAM 8 GB realistic minimum, more for large nests

File layout after install (Trumpf flavor example)

C:\Program Files\Trumpf\TecZoneBend\
  ├── Flux.exe
  ├── Flux.flavor              (text: "Trumpf")
  ├── Flux.wad                 (zipped read-only resources)
  ├── Flux.Hula64.dll          (HOOPS wrapper)
  ├── HOOPS DLLs               (~31 DLLs in win64\)
  ├── Trumpf.Licensing.dll
  ├── (other dependencies)

C:\ProgramData\Trumpf\Flux\Data\
  ├── Machine\<id>\            (machine definitions, .curl, .mech, IGES models)
  ├── BendTools\<id>\          (bend-tool catalogues)
  ├── PunchTools\<id>\         (punch-tool catalogues)
  ├── System\
  │   └── air-gap-tables.json  (custom panel-bender air-gap overrides)
  ├── Material\                (material database)
  └── …

The C:\ProgramData\Metamation\Flux\Data\ variant exists for the MetaCAM-branded "Flux" flavor.

7.3 The flavor → installer mapping

A single installer artifact Setup.Flux.<build>.exe is uploaded once per build; the filename at install time decides which flavor lands:

Installer name Installs flavor
Setup.Flux.<build>.exe Flux (MetaCAM-branded, Aegis-licensed)
Setup.TecZoneBend.<build>.exe Trumpf (TecZoneBend)
Setup.TecZoneBend(Boost).<build>.exe Boost
Setup.TecZoneBend(B23).<build>.exe B23 (BendCenter HMI)
Setup.TecZoneFold.<build>.exe Fold (TecZoneFold panel bender)
Setup.FluxTechDemo.<build>.exe Tech (time-limited demo)

Filename routing keeps a single binary, single installer, and one upload — the installer renames itself in flight to set Flux.flavor.

The Engine and Dev flavors have no installers — Engine ships as a packaged DLL inside Praxis; Dev runs only on whitelisted developer machines.

7.4 Licensing back-ends per flavor

The EFlavor enum (in Src\Core\Permit.cs) has ten values: Dev, Flux, Trumpf, Boost, Engine, ShopFloor, Lantek, Viewer, SDK, OneCore. The B23, Fold, and Tech brand names are installer variants on top of one of these flavors (Trumpf for B23 / Fold / Tech), not separate license back-ends. The dispatch is in Permit.GetFeature (Permit.cs:399):

Flavor License back-end Implementation Service required
Dev Env-switch FLUXDEVELOPER (no real protection) Permit.cs:407 none
Flux Aegis (online soft-locking) MMAegisLock, Aegis.API NuGet Internet to Aegis service
Trumpf (incl. B23, TecZoneFold installer variants) Trumpf License Expert (TLE) — WIBU CodeMeter TWibuLockTrumpf, Trumpf.Licensing NuGet TLE service installed
Boost Trumpf License Expert (TLE) — WIBU TWibuLockBoost, Trumpf.Licensing NuGet TLE service installed
TecZoneFold (Trumpf with Fold feature) Trumpf License Manager (TLM) — Sentinel Protection.Key.Standard NuGet TLM service installed
Engine (Praxis) Delegated to host; optional Aegis check via Lock.IsAegisLicensed Permit.cs:402 none direct (Praxis owns it)
OneCore Trumpf License Expert (TLE) — WIBU (Trumpf license route) TWibuLockTrumpf TLE service installed
ShopFloor (Touchpoint / Delem / PLB) Trumpf License Expert (TLE) — WIBU (Trumpf license route) TWibuLockTrumpf; sub-type from env var FluxSFType TLE service installed
Lantek Lantek SDK (Lantek.Key) + signed LantekLic XML (RSA-2048 / SHA-256) + remote validator FLConnect.exe LantekLock, Permit.cs:1274 Lantek SDK runtime; FLConnect.exe shipped alongside Flux.exe; signed license file present
Viewer (Flux Bend Viewer) Feature-only (FLAVOR_BENDVIEWER, no enforced lock) Permit.cs:401 none
SDK Aegis by default; can impersonate Boost / Trumpf / Lantek / ShopFloor via FLUXSDKLICENSEMODE env var Permit.cs:388-396 depends on impersonated flavor
Tech / Trial (Trumpf with EFeature.Trial) Time-bomb expiry on top of TLE feature bit, no separate lock TLE service installed

Switching license back-end is a flavor decision, not a runtime decision (except for SDK, which exists specifically to switch).

7.5 Unattended installation hooks

The installer accepts:

  • /SILENT — visible progress, no interaction.
  • /VERYSILENT — invisible install.
  • /LOG="<path>" — write installation log.
  • /TASKS="<comma-separated>" — sub-tasks: desktopicon, prereq2, tlmanager, tlexpert.

If a parent installer (e.g. Praxis bundle) already installs TLM/TLE, omit those sub-tasks. Documented in Notes\Tech\2013.FluxFlavors.ftx.

7.6 Praxis embedding (Engine flavor)

Praxis.exe
  └── loads Flux.API.dll
        └── (inside) Flux.Core.dll, Flux.Base.dll bundled as resources
        └── HOOPS DLLs alongside
        └── No Flux.exe, no Flux.UI.dll, no Flux.App.dll

Praxis owns the WPF dispatcher and the file dialogs. Flux.API never touches them.

7.7 The Wad

Flux.wad is a ZIP of read-only resources (shaders, metadata, fonts, post-processor metadata templates). On dev machines, the env var FLUXWAD=X:\Wad points at the loose folder, bypassing the zip. On installed machines, Flux.wad next to Flux.exe is the source.

The decision tree at startup:

  1. If FLUXWAD env var is set → use that loose folder.
  2. Else → unpack Flux.wad next to Flux.exe on demand.

7.8 Update / patch lifecycle

  • Major builds: full installer download. Old install is upgraded in place; user data in ProgramData\…\Data\ is preserved.
  • Patch builds: same flavor, same installer-rename mechanism.
  • Hotfix DLLs: not officially supported; in practice rare.

7.9 Auto-update

Flux does not auto-update. Updates are triggered by user-initiated download + run-installer.

7.10 Customer-data backup

Customer-modified data (machines added via UI, custom tool catalogues) lives in ProgramData\…\Data\. Backup is the customer's responsibility; Flux does not snapshot it.
