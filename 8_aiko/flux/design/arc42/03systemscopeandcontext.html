Key business actors

Actor Interaction
CAD designer Hands over a 3D part file.
CAM engineer / press-brake operator Sits in front of Flux, sets up the part, runs auto-tooling, generates NC. Primary direct user.
Production planner Batches multiple parts on a sheet, exports nesting + NC.
Robotic cell integrator Sets up the robotic cell components, regrip strategy, gripper inventory; reviews the simulated motion.
Quality team / archivist Receives the setup sheets and PDFs.
Trumpf service Distributes flavors (TecZoneBend, TecZoneFold) under their licensing scheme.
Praxis users Don't see Flux directly; Flux runs as a headless Engine DLL inside Praxis.

3.2.1 Inbound interfaces — who calls Flux

Each entry surface drives the same Flux.Core engine; what differs is process ownership, transport, and licensing.

# Surface Transport Process model Entry point Used by
1 End-user GUI (Flux.exe) WPF window, mouse / keyboard Long-running interactive Src\App\App.xaml.cs → MainWindow Customer-facing flavors: Trumpf (TecZoneBend), Boost, B23, Fold (TecZoneFold), Lantek, OneCore, ShopFloor, Flux (MetaCAM-branded), Tech (demo), Viewer
2 Praxis embedding DLL load (Flux.API.dll) In-process inside Praxis; no UI Flux.API.Library.Init (ELib.Engine) in Src\API\Basis\Basis.cs Trumpf Praxis (Engine flavor)
3 Boost — FXCMD command files .fxcmd text drop + new Flux.exe per call → .fxresp text return Engine-process-per-job + one long-running interactive Flux Src\Core\CmdProcess.cs — class FBoost. Spec Notes\Tech\2012.BoostInterface.ftx. Boost adapter (legacy path)
4 Boost — REST service In-process method calls on Flux.API.BendBoost Host owns lifecycle Src\API\Bend\BendBoost.cs — DoAutoCompute / UpdateBendSolution / GenerateOutputs Boost REST service (preferred path)
5 3rd-party automation / SDK DLL load (Flux.API.dll); same surface as Praxis but separately licensed Host process Flux.API.Library.Init (ELib.Console); SDK mode triggered by env var FLUXSDK_ACTIVE=YES OEM integrators outside Trumpf
6 Plugin Bricks DLLs in Plugins\ next to Flux.exe; classes attributed [Brick] implementing IHook interfaces In-process; loaded at startup Flux.API.Bricks.Init () in Src\API\Bricks.cs; IFXHook / IAppHook in Src\Core\Hook.cs Customer-side feature plugins
7 Internal CLI — FConsole Flux.Console.exe (FConsole) Short-lived per command Src\Console\FConsole.cs; [FConsoleCmd] methods Metamation engineers (not shipped)
8 One-shot CLI — Flux.Migrate Flux.Migrate.exe (Flume) Short-lived per migration Src\Migrate\ Customers migrating from MetaCAM PDG / TOPS

Plugin extension hooks (Bricks)

Plugins implement one or more IHook interfaces. The host fires events via Hub.HookManager.Invoke<T>(...).

Interface Methods Fires when
IFXHook OnFXLoading, OnFXLoaded, OnFXSaving, OnFXSaved, OnCodeGenerated FX file lifecycle and after NC generation
IAppHook OnAppStart (with EStatus { Success, Failure, SilentFailure }), OnAppExit App startup / shutdown — can veto startup

[Brick] attribute carries Moniker, Priority, Singleton. Bricks are sealed at the end of init; failed loads log to FX.Out (EOut.Error, ...) and do not abort startup unless an IAppHook returns Failure.

3.2.5 IPC primitives & host extension hooks

The Boost FXCMD path is the only Flux integration with cross-process IPC. Four primitives:

# Primitive Mechanism Purpose
1 FluxFileMediator push notifications External EXE pointed to by FLUXFILEMEDIATOR; spawned with the response-file path after every Boost command, and with -configupdated when in-process config mutates Lets the Boost adapter skip FileSystemWatcher polling — gets a kick the moment a .fxresp is written, or when the host-side config cache should be invalidated. Call sites: Src\Core\CmdProcess.cs:39, 455; also fired on PartSaved / PartClosed (MainWindow.xaml.cs:661, PartAux.cs:1098), TSO save (TSOBatch.cs:257), interactive tab events (DocumentTab.cs:262)
2 Flux-Boost-MMF whiteboard Named memory-mapped file, 16 KB = 128 slots × 128 bytes; each slot holds (PID, Interactive flag, JobID) Cross-process job registry. Backs the ProcessStatus Boost command. FBoost.Register / FBoost.Unregister claim and release slots. Code: Src\Core\CmdProcess.cs:1370–:1455
3 Flux-Boost-Mutex-{pid} liveness mutex One named mutex per Flux engine PID; created on register, gone when the process dies Zombie-slot cleanup: GetInstance zeros any slot whose mutex no longer exists. No host-side reaper needed. Code: Src\Core\CmdProcess.cs:1380, 1430
4 Interactive-instance forwarding Flux.exe job.fxcmd started with an interactive Flux already running forwards the args into the running window (new tab) and exits One interactive Flux serves all interactive Boost commands. The launched PID is unreliable for monitoring — see whiteboard above. Code: Src\App\ALib.cs:140 (RunInteractiveCmd), Src\App\App.xaml.cs:187

Other IPC in Flux:

  • End-user single-instance arg forwarding — distinct from the Boost stack above. Named mutex + named pipe per "scope" (appId): meta-flux (default), tzlaser (Permit.TrumpfTZLaser), boostlaser (Permit.BoostTZLaser). When a second Flux.exe is launched and finds the mutex held, it opens a NamedPipeClientStream to the same name, writes the args joined by [<sep>], sets FX.SecondInstance = true, and exits. The first instance's ListenForMessages loop dispatches the args back to the UI thread through ALib.OpenForEditing. See §6.10. Code: Src\App\App.xaml.cs:151, Src\UI\Misc\UI.cs:378+.
  • FluxLogPipe named pipe + FluxLogMutex — cross-process logging for the Flux.Log.exe developer console (Src\Base\Debug.cs:336+).

3.3 What is not part of Flux

  • The machine controllers themselves (Trumpf TruBend, B23 APC, Bystronic Xpert, …). Flux generates code; the controller executes it.
  • CAD modelling beyond sheet-metal — Flux is not SolidWorks.
  • Job-shop scheduling / MES — sister tools own that; Flux outputs the artifacts they consume.
  • Cloud sync / collaboration — Flux is single-user single-process desktop.
  • An automated build of Flux.Hula64.dll — the C++/CLI HOOPS wrapper is built separately and shipped as a pre-built binary into X:\Resources\Hoops. The repo's Hula64.sln is informational.

3.4 Embedding mode (Engine flavor)

The Engine flavor is unique in that Flux runs as a library inside the Trumpf Praxis process. The constraints that imposes:

  • No WPF UI is initialized — Hub.BigChooser, Hub.CloseBlankMainWindow, etc. are simply null and Core/UI code paths short-circuit.
  • The process lifetime, file dialogs, focus, and threading context are owned by Praxis, not by Flux.
  • Flux.API is the only entry surface; Praxis must not reach into Flux.Core directly.
  • Licensing is delegated to Praxis's own check (the Engine flavor has no separate license).

The Engine flavor is the strongest discipline driver in the codebase: any feature that demands UI for correctness can never run in this flavor.
