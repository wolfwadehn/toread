11RisksandTechnicalDebt

product: flux org: metamation type: design tags: [flux, arc42, architecture] source: 'D:\dev\Flux-Web\Doc\Arc42\11_Risks_and_Technical_Debt.md' updated: 2026-07-14

11 — Risks and Technical Debt

What's known to be problematic, where the sharp edges are, and what migration paths are open or in flight. The risks are ranked by probability × impact (subjectively).

R-001 · Two crash engines coexist (BendOpCrash ⇄ NBendCrash)

Severity. Medium-high.

State. In flight.

Context. Src\Core\Bend\BendOpCrash.cs (~68 KB, classic) and Src\Core\Bend\NBendCrash.cs (~78 KB, new) both exist. A runtime branch selects which is active. The new engine handles cases the classic one didn't; cutover hasn't completed.

Risks.

  • A change to collision logic might be made in only one of the two files, leading to silent divergence.
  • Code reviewers must remember "did the PR touch both?".
  • Performance characteristics differ — wrong choice can manifest as occasional slow auto-tooling.

Mitigation today.

  • Documented prominently in Onboarding chapter 02 §7.1.
  • The selection-flag check is grep-able.

Path forward.

  • Pick a winner. Cut over completely and delete the other.
  • Until then: any PR touching either file should explicitly state in the description which engine was changed and why.

R-002 · Notes\ directory has stale content

Severity. Medium.

State. Open — partial refresh has happened.

Context. Notes\Dev\ and Notes\Tech\ contain ~33 FTex files, several from 2013–2017. Some are still authoritative (1003 Au format, 1005 bend-area modeling, 2007 Curl, 2013 flavors). Others are outdated (1002 mentions Mercurial / .NET 4.6.1 / VS 2015; 1009 covers Mercurial branches; 2004 Hex post-processor language).

Risks.

  • New contributors trust 1002 verbatim and waste time on a dead build path.
  • Architecture decisions get cited from notes that no longer reflect reality.

Mitigation today.

  • The Onboarding handbook chapter 00 §8 contains a "1002 says vs. today" diff table.
  • Arc42 ADRs reference notes only when they're current.

Path forward.

  • Quarterly audit. Each note gets a "Verified against current code on YYYY-MM-DD" footer or moves to an Archive/ subfolder.

R-003 · BendOp.cs is 210 KB sealed partial

Severity. Medium.

State. Open.

Context. A single sealed partial class BendOp with ~200 properties spread across multiple files. It's the central state object for press-brake operations.

Risks.

  • A code search for a method may not find it in the file you'd expect — must search the whole solution.
  • New members are easy to add but pile up over time without natural decomposition.
  • Refactoring it is high-risk because so many call sites assume the full surface.

Mitigation today.

  • The partial decomposition keeps the file count manageable (one part per concern).
  • PR-review rules check that new properties have a justification.

Path forward.

  • Carve out clear sub-modules over time (BendOp.Routing.*, BendOp.RoboticCellAware.*, …).
  • Resist new state — prefer computed properties or move state to a sibling class.

R-004 · Static singletons hide re-entrancy bugs

Severity. Medium.

State. Open.

Context. Part.Current, Part.Active, BendMachine.Default, and the Hub slots are static. Re-entrancy during long operations (a property setter triggering rendering that triggers another property setter) is the most common "concurrency bug" reported.

Risks.

  • Subtle data corruption when re-entrancy happens during auto-tooling or simulation.
  • Hard to unit-test cleanly (Flit framework substitutes via BA.Testing = true, but production code still touches statics).

Mitigation today.

  • Long ops cooperatively check Part.Flags & Part.EFlags.AbortTooling.
  • Re-entrancy guards (if (mInsideX) return;) where the issue has been seen.

Path forward.

  • Prefer scoped state over statics for new features.
  • For existing statics, add re-entrancy guards as bugs surface.

R-005 · Hex post-processor language is gone, but .hx extensions remain

Severity. Low (just confusing).

State. Closed for code, open for naming.

Context. Note 2004 documented Hex as "the new post-processor language replacing PDL". The C# rewrite (ADR-009) retired Hex from runtime, but BMachine.Post still has values like wad:Post/Bend/TrumpfB23.hx. The extension is a routing token only.

Risks.

  • New contributors look at the file extension and assume Hex is involved.
  • Name confusion with Src\Core\IO\HXReader.cs (which is the HOOPS reader, not a Hex reader).

Mitigation today.

  • Documented in Onboarding chapter 00 §6 and §8, in Arc42 ADR-009, and in glossary entries.

Path forward.

  • Rename HXReader.cs to HoopsReader.cs in a future low-risk PR.
  • Either rename the routing tokens (Post/Bend/TrumpfB23) or accept the naming as legacy.

R-006 · Flux.Hula64.dll is binary-shipped, not built in CI

Severity. Medium.

State. Accepted.

Context. The C++/CLI HOOPS wrapper is built outside the repo's CI and shipped as a pre-built binary into X:\Resources\Hoops. CI cannot detect a regression in the wrapper.

Risks.

  • HOOPS upgrade goes wrong → 3D import fails on production but isn't caught in CI.
  • Pinned version (H.GetVersion () != "25.4") is the only safety net.

Mitigation today.

  • Version pin throws FX.Fatal on mismatch.
  • A small set of HOOPS-import tests in X:\Test\IO\ covers basic file round-trips.

Path forward.

  • Add a CI job that exercises 3D import with a curated fixture set; failures break the build.

R-007 · Onboarding curriculum requires active maintenance

Severity. Low (but increases over time if ignored).

State. Open.

Context. The Onboarding handbook references commits, file paths, and code patterns that drift as the codebase evolves. Chapter 00 §8 (the "1002 says vs. today" table) is the most fragile — touched any time the build toolchain shifts.

Risks.

  • New contributors follow stale instructions and waste time.

Mitigation today.

  • Maintenance ledger in the onboarding README lists the last full audit per chapter.
  • Each new joiner is asked to file at least one issue / PR against the handbook reflecting one inaccuracy.

Path forward.

  • Quarterly audit, kept short.

R-008 · License-back-end fragmentation

Severity. Medium.

State. Open.

Context. Five license back-ends across flavors: Aegis, Trumpf TLE (WIBU), Trumpf TLM (Sentinel), B23 APC fingerprint, dev whitelist. Each has its own service, its own service-down failure mode, its own renewal flow.

Risks.

  • A licensing infrastructure outage takes out customer Flux instances.
  • Switching between TLE and TLM at the OEM level is a coordinated change with installer impact.

Mitigation today.

  • Each flavor's installer ships the appropriate license back-end.
  • Cached license tokens absorb short outages.

Path forward.

  • No consolidation visible — different OEMs have different contractual constraints.

R-009 · WinForms residue

Severity. Low.

State. Slow migration in flight.

Context. Flux.Core.csproj sets both <UseWindowsForms>true</UseWindowsForms> and <UseWPF>true</UseWPF>. Some legacy interop predates WPF.

Risks.

  • Mixed UI stacks complicate styling, accessibility, theming.
  • Modern .NET versions deprecate Windows Forms features faster than WPF features.

Mitigation today.

  • New code goes WPF-only.
  • Globs + PanelMaker prefer WPF rendering.

Path forward.

  • Identify remaining WinForms touchpoints; migrate as touched.

R-010 · Inventory of unfixable test goldens grows over time

Severity. Low-medium.

State. Open.

Context. Test\Bend\Bend2017.cs … Bend2025.cs is a yearly accumulation of bug-regression fixtures. Each year's file grows, and a 2017 case may not be exercised by anyone reading current code.

Risks.

  • A semantic change to the auto-tooler perturbs ten 2017 goldens — no one knows whether the new output is correct.

Mitigation today.

  • PR review focuses on "is this golden change intentional?"
  • Comments inside the test reference the original case number (Case nnnnn).

Path forward.

  • Archive year-buckets that haven't changed in N years.
  • Annotate each test with the invariant it protects, not just the case number.

R-011 · BCellTech is abstract; concrete subclasses diverge

Severity. Medium.

State. Accepted.

Context. BCellTech has concrete subclasses for BM5000, BC7000, Fanuc, etc. Behavior diverges in subtle ways.

Risks.

  • A bug fixed in BM5000 might silently regress in BC7000Tech.
  • Test coverage spans cell types unevenly.

Mitigation today.

  • Per-cell test fixtures exist.
  • The base class enforces shared invariants.

Path forward.

  • Keep base-class behavior small. Push divergence into clearly-overridden methods, not "if (cellType == Fanuc) ..." inside shared code (per design principle D005).

R-012 · Bus-factor concentration

Severity. Medium.

State. Acknowledged.

Context. Several subsystems (the auto-tooler scoring, the BG placer, the post-writer dispatcher) have one or two engineers with deep familiarity. Onboarding curriculum exists, but real expertise takes years.

Risks.

  • A single departure can stall a critical area.

Mitigation today.

  • Onboarding curriculum and Arc42 (this set) reduce the friction of picking up a subsystem.
  • Pair-review on cross-subsystem PRs.

Path forward.

  • Rotate ownership where possible.
  • Prefer shared knowledge over heroic individual expertise.

R-013 · No automated UI tests

Severity. Medium.

State. Accepted.

Context. Flit covers domain logic. The WPF dialogs (TurretEditor, SheafEditor, etc.) have no automated test coverage.

Risks.

  • A WPF refactor breaks an editor; only customer reports surface it.

Mitigation today.

  • Manual qualification before each release.
  • Composite-glob multi-edit is exercised by domain tests indirectly.

Path forward.

  • Investigate WPF UI-automation frameworks (FlaUI, Appium WinAppDriver) for the most critical editors.
