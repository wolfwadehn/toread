10 — Quality Requirements

The quality goals from section 1 expressed as a quality tree, then concretized as testable scenarios.

10.1 Quality tree

Flux quality
├── Correctness
│   ├── NC code matches the planned operation
│   ├── Generated tool setups respect machine constraints
│   ├── Collisions are detected (no false negatives)
│   └── Persistence round-trip preserves all data (no silent loss)
├── Determinism
│   ├── Same input + machine + options → same output
│   ├── Floating-point near-ties don't reorder results
│   └── Tests succeed identically on different machines
├── Performance
│   ├── Auto-tooling a typical part finishes in seconds
│   ├── Opening a large nest fits in available RAM
│   └── UI stays responsive during long operations
├── Reliability
│   ├── No data loss on crash recovery
│   ├── License-server outage doesn't lose unsaved work
│   └── Forward-migration of old FX files succeeds
├── Modularity
│   ├── Engine flavor (no UI) builds and runs
│   └── 3rd-party API surface stays stable across releases
├── Extensibility
│   ├── Adding a new NC dialect is a localized code change
│   ├── Adding a new machine variant doesn't fork existing logic
│   └── Adding a feature bit doesn't require rebuilding all binaries
├── Usability (CAM)
│   ├── Auto-tooler succeeds first try on common parts
│   ├── Errors point at the cause (no silent fail)
│   └── Multi-edit (composite globs) works on every domain
└── Maintainability
    ├── New contributors can navigate after the onboarding curriculum
    ├── Code reviews stay consistent across the team
    └── Persistence migrations are routine, not crisis

10.2 Scenarios

Quality scenarios — concrete enough to drive tests or design decisions.

Q-01 · NC correctness regression

Stimulus. A change in BendTooler.cs (auto-tooler). Response. All Bend Test\Bend\BasicBendAuto* and yearly regression tests (Bend2017.cs … Bend2025.cs) run; any change in golden .txt is reviewed before merge. Measure. 100% of golden-file changes are explicitly approved in PR review. Zero un-reviewed golden changes ship to production.

Q-02 · Determinism across runs

Stimulus. The same fixture (Bend_04.geo) is auto-tooled twice on the same dev machine, same flavor, same date. Response. BendTech.Dump produces byte-identical output. Measure. Repeat-runs yield identical golden diffs. Exceptions logged as bugs.

Q-03 · Determinism across machines

Stimulus. A test runs on dev machine A and CI machine B. Response. Same golden output. Measure. CI agrees with local runs. Floating-point platform inconsistencies addressed via GeomSort + tolerance rules.

Q-04 · Auto-tooling latency on a typical part

Stimulus. User clicks "Auto Tool" on a 6-bend part with one setup. Response. Result visible in ≤ 5 seconds on a 2024-vintage developer machine. Measure. Manual benchmark; flagged as a perf-regression target.

Q-05 · Long operations don't freeze the UI

Stimulus. User triggers an operation longer than 1 second. Response. Status indicator visible; UI remains scrollable and cancellable (where supported); progress is communicated. Measure. No unresponsive-window dialogs from Windows during typical workflow.

Q-06 · Engine flavor (headless) runs every UI-independent feature

Stimulus. Praxis loads Flux.API.dll, calls BendTech.GenerateNCCode. Response. NC code generated without WPF being initialized. Measure. All Engine-flavor tests pass in CI without a WPF host.

Q-07 · Forward-migration of an old FX file

Stimulus. A user opens a 2018-era FX file in current Flux. Response. All [PostLoad] migrations apply; the part loads with no manual edits required; auto-tooling produces a sensible setup. Measure. Migration tests covering a curated sample of old files (X:\TData\Migration\…).

Q-08 · License-server outage doesn't lose work

Stimulus. Aegis server unreachable for 30 seconds while the user is editing. Response. Editing continues; the Save operation is allowed (subject to license cache). Measure. Manual qualification scenario.

Q-09 · Adding a new NC dialect

Stimulus. A new bend machine vendor requires a new dialect. Response. Add a writer class in Src\API\Bend\Post\<Dialect>.cs; add a case in Basis.GenerateNC; add tests. Measure. Done in under a week of focused work, no other module touched.

Q-10 · Adding a new machine variant

Stimulus. A Trumpf-series variant adds a new feature (e.g. wider table). Response. Add a property to BendMachine (per design principle D005), update relevant logic; no domain spread. Measure. Diff stays bounded — no shotgun edits across files.

Q-11 · Multi-edit on every domain

Stimulus. User selects N objects of any domain and edits a shared property. Response. Composite glob shows the property; setting it propagates to all N objects in one undo unit. Measure. Acceptance test for each domain's composite glob.

Q-12 · Onboarding effectiveness

Stimulus. A new engineer joins and follows the onboarding handbook. Response. After 6 months they pass the synthesis exercise (chapter 09 of the onboarding handbook): a 30-minute tech talk on a chosen subsystem with concrete improvement suggestions. Measure. Mentor sign-off. Pattern: read → discuss → contribute small.

Q-13 · No new compiler warnings

Stimulus. Any PR. Response. Build is warning-clean. Measure. CI rejects warnings as errors.

Q-14 · No silent failure paths

Stimulus. A method discovers an unexpected state (file missing, invalid input). Response. Emits a numeric FX.Out message before returning / throwing. Measure. Code review per design principle D011.

Q-15 · Rebuilding for a flavor change

Stimulus. Change the active flavor (e.g. switch from Dev to Trumpf to test). Response. Edit Flux.flavor text file and restart Flux.exe. No rebuild required. Measure. Manual; design principle from ADR-003.

10.3 What we do not claim

  • Real-time correctness guarantees — Flux is not safety-certified. The customer's machine controllers are the safety boundary.
  • Multi-user collaboration — single-user single-process model.
  • Cloud / network operation — desktop only, except for license check-in.
  • Accessibility certification — informal, not certified.
  • Localization completeness — UI text uses message-ID-based translation, but coverage varies per language.

10.4 Quality-relevant codified rules

The PR-review rule-set under .github\instructions\ directly serves several quality goals:

Quality goal Relevant rules
Correctness D002 (cache invalidation), D011 (meaningful errors), D012 (comments for non-obvious decisions)
Determinism "use GeomSort instead of OrderBy" guideline
Performance D007 (compute once, transform), D008 (ReadOnlySpan<T>), D013 (size awareness)
Maintainability D003 (split methods that do two things), D005 (named properties not if/else), D006 (don't expose temporary fields)
Reliability D004 (testability), D010 (no warnings)

10.5 Targets that need formalizing

The Arc42 template asks for measurable goals. Some of ours are still informal — written here as "next steps" rather than "current state":

  • Latency budget for auto-tooler stages — currently anecdotal ("seconds"), no SLA.
  • Memory footprint for large nests — no documented ceiling.
  • Cold-start time for Flux.exe — observed but not enforced.
  • Onboarding-to-first-PR — currently a six-month policy, not a measured median.

These are candidates for instrumentation in future quarters.
