05.4 — Module: Flux.App

The shell. This is what Flux.exe actually is.

Purpose

Flux.App is the application wrapper. Its responsibilities:

  • Bootstrap the .NET 10 + WPF runtime, set culture (CultureInfo.InvariantCulture), set regex timeout, attach the assembly resolver.
  • Read Flux.flavor and the active feature bits.
  • Validate licensing (Aegis, Trumpf WIBU, Trumpf Sentinel, B23 APC fingerprint, dev whitelist) for the active flavor.
  • Locate the data folder (FLUXDATA env var on dev, C:\ProgramData\… installed) and load the wad.
  • Wire Hub slots — fill in Hub.GenerateNC, Hub.BigChooser, Hub.ClosePartByJobID, Hub.APIWrapper, etc.
  • Construct the main window, the tab manager, the status bar.
  • Manage selection, undo lifecycle, glob-panel routing.
  • Open / save / close Part documents.
  • Restore last-open documents on launch.
  • Tear down on exit.

Code volume: 301 .cs files (the largest project by file count, but most files are small UI scaffolding — XAML code-behind, command handlers, menu definitions).

Folder layout (top level)

Src\App\
├── App.xaml.cs       Application class. Attaches assembly resolver, creates AppCore.
├── MainWindow.xaml.cs Main window, tabs, dockable panels.
├── ALib.cs           App-level shared utilities.
├── Globals.cs        Static app-level state.
├── MenuCmds.cs       Menu command bindings.
├── Workflow\         Multi-step workflows (e.g. switch-to-bending)
├── Job\              Job-level UI (the JobBar with NC-output button)
├── Mode\             Mode switching (2D / 3D / Bend / Fold / …)
├── Bend\, Cut\, Fold\, BCell\, …  per-domain shell pieces
├── Misc\             Top-bar widgets, small dialogs
├── Res\              Resources, icons, themes
└── Web\              Embedded web view (WebView2)

App startup sequence (simplified)

Flux.exe (Flux.App.App) starts
  ↓
App.xaml.cs constructor:
  • CultureInfo = Invariant
  • Regex default match timeout = 2 seconds (Case 35246 — prevent runaway regex)
  • AppDomain.AssemblyResolve += LibResolve  (loads Hula via assembly-load-failure)
  • new AppCore (this)                        (most of the real init)
  ↓
AppCore reads Flux.flavor   →  flavor enum + feature bits
  ↓
License validation per flavor
  • Dev whitelist             — only on developer PCs
  • Aegis (online soft-lock)  — for "Flux" flavor (MetaCAM-branded)
  • Trumpf WIBU (TLE)         — for "Trumpf" / "Boost" flavors
  • Trumpf Sentinel (TLM)     — for "Fold" flavor (TecZoneFold)
  • B23 APC fingerprint       — for "B23" flavor
  • Time-limited "trial"      — for "Tech" demo
  ↓
Locate data folder
  • Developer: $env:FLUXDATA  (= X:\Data)
  • Installed: C:\ProgramData\Trumpf\Flux\Data  or
               C:\ProgramData\Metamation\Flux\Data
  ↓
Locate wad
  • Developer: $env:FLUXWAD   (= X:\Wad)
  • Installed: Flux.wad next to Flux.exe (zip extracted on demand)
  ↓
Wire Hub slots (the cross-layer bridge)
  • Hub.GenerateNC  ←  Src\API\Basis\Basis.cs::GenerateNC
  • Hub.BigChooser  ←  WPF dialog implementation
  • Hub.MCBtoTXT    ←  Src\API\…
  • BCellTech.EINWriter ← Src\API\…
  • …
  ↓
Open MainWindow (unless headless flavor)
  ↓
Restore last-open Parts (if any)

The entry method on App.xaml.cs line 33 captures the "thin shell" idea: the constructor does only assembly-resolver setup, culture, regex-timeout, and then constructs AppCore. Everything else — including most error-prone code — lives in AppCore so that the assembly resolver can be in place before any Flux types load.

What lives in Flux.App that could be elsewhere?

The line between App and UI has drifted. Some patterns:

  • Per-domain "shell" folders (App\Bend\, App\Cut\, App\Fold\) — usually for app-wide commands, not Glob controllers. Globs proper live in Flux.UI.
  • Mode-switch logic (App\Mode\) — turning a 2D drawing into a 3D model, switching from cut to bend, etc. This is partly App because it spans multiple techs and orchestrates UI.
  • JobBar (App\Job\JobBar.xaml.cs) — the top-level command bar, including the Generate NC button (line 1003 — OnGenerateNC).

When in doubt: if it touches Application, MainWindow, or document tabs, it belongs in App. If it edits one domain object's properties, it belongs in UI.

Single-process runtime invariants

Flux.App is the only place that may safely set the static singletons:

  • Part.Current — the currently active document.
  • Part.Active — the list of open documents.
  • BendMachine.Default, LaserMachine.Default, etc.
  • Hub.* slots.

Other layers may read them. Writing them from Core or UI is a smell.

Constraints Flux.App enforces on itself

  • The shell must keep the Engine flavor in mind. Workflows must be invocable headlessly where possible; UI dependencies must be guarded by capability checks.
  • No domain logic. App orchestrates; the algorithms live in Flux.Core.
  • No file I/O for domain data here. Save/load goes through Part and Flux.Core\IO.
