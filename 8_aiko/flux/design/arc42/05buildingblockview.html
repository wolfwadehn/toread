05 — Building Block View

Static decomposition of Flux. This page is the Level-1 overview; ten sub-pages drill into each module — eight on the C# projects under Src\, plus the OEM customisation layer (a sub-folder of Flux.Core significant enough for its own page) and the auxiliary tools (X:\Tools\) that live alongside the main solution.

5.1 Level 1 — System decomposition

                        ┌───────────────────────────────────┐
                        │           Flux.exe                │
                        │     (entry — Flux.App project)    │
                        └─────────┬─────────────────────────┘
                                  │
                                  ▼
                        ┌───────────────────────────────────┐
                        │           Flux.UI                 │
                        │   Globs (controllers) + WPF       │
                        └─────────┬─────────────────────────┘
                                  │
                                  ▼
              ┌───────────────────────────────────┐    ┌───────────┐
              │           Flux.Core               │◄───┤ Flux.API  │
              │  Models + VModels + domain logic  │    │ (3rd-party│
              └─────────┬─────────────────────────┘    │  facade)  │
                        │                              └───────────┘
                        ▼
              ┌───────────────────────────────────┐
              │          Flux.Base                │
              │  Geo, Mesh, Pline, Lux (render),  │

Side projects (bind to Core):
  Flux.Test     ─► Core (in X:\Test\, framework "Flit")
  Flux.Migrate  ─► Core (CLI, namespace "Flume")
  Flux.Console  ─► Core (CLI, namespace "FConsole")

5.2 Level-1 building blocks at a glance

Block Project Stability Role Deep-dive
Flux.Base Src\Base\Flux.Base.csproj 🟢 stable CAD/CAM-agnostic foundation: geometry, mesh, polyline, GL/Lux rendering, undo, IO primitives, Au serialization runtime Module: Flux.Base
Flux.Core Src\Core\Flux.Core.csproj 🟡 internal Domain engine: Bend, Fold, Laser, Punch, Nest, BCell, Sim, Drawing, Layout, Trim, IO, Settings, Model, OEM, Part, Report. Models + VModels live here Module: Flux.Core
Flux.UI Src\UI\Flux.UI.csproj 🟡 internal Per-domain Glob controllers + WPF dialogs (TurretEditor, SheafEditor, LaserDBEditor, …) + agents + sheets Module: Flux.UI
Flux.App Src\App\Flux.App.csproj 🟡 internal The shell that becomes Flux.exe: main window, tabs, selection state, undo lifecycle, Hub slot wiring at startup Module: Flux.App
Flux.API Src\API\Flux.API.csproj 🟢 stable Hardened façade for 3rd parties / Praxis. Mirrors a sub-set of Core types behind Flux.API.* wrappers. Hosts the C# postprocessor writers (Src\API\Bend\Post\) Module: Flux.API
Flux.Console Src\Console\Flux.Console.csproj 🟡 internal Developer CLI utilities: metadata rebuild, wad packing, internal viewers (BNCViewer, DLDViewer, JupiduViewer, DLCViewer), BNCReader Module: Flux.Console
Flux.Migrate Src\Migrate\Flux.Migrate.csproj 🟡 internal One-shot CLI to migrate legacy MetaCAM / TOPS data: bend tools, machines, laser, 5-axis Module: Flux.Migrate
Flux.Hula Src\Hula\Hula64.sln (separate) 🟢 stable C++/CLI wrapper around HOOPS. Not built from this repo's CI — pre-built Flux.Hula64.dll is copied from X:\Resources\Hoops Module: Flux.Hula
Flux.Test X:\Test\Flux.Test.csproj 🟢 stable Test suites under the Flit framework. ~169 .cs files. Inputs in X:\TData, golden files alongside (covered in onboarding chapter 06)

5.3 Inter-block contracts

The arrows in §5.1 are the only allowed dependencies. Crossing them sideways or upward is a smell.

Contract Allowed Disallowed
Flux.UI → Flux.Core yes —
Flux.Core → Flux.UI no (use Hub slots instead) direct method calls
Flux.Core → Flux.Base yes —
Flux.Base → Flux.Core no the base assembly must remain CAD/CAM-agnostic
Flux.API → Flux.Core yes —
Flux.Core → Flux.API only via Hub.APIWrapper slot direct reference
Flux.App → Flux.UI and Flux.API yes —
Flux.Test → Flux.Core, Flux.Base, Flux.UI yes (tests can break encapsulation) —

5.5 Inside Flux.Core — Level 2 (domain folders)

Src\Core\
├── Bend\ (47 files, ~1.7 MB)         press-brake CAM
├── Fold\ (42 files)                  panel-bender CAM
├── BCell\ (34 files)                 robotic bend cell
├── Laser\                            laser cutting
├── Punch\ (13 files)                 punching
├── Nest\ (10 files)                  nesting
├── Layout\ (14 files)                machine setup layouts
├── Trim\                             edge trimming
├── Drawing\ (7 files)                2D sketch / drawing
├── Sim\ (5 files)                    simulation orchestration
├── Model\ (9 files)                  Entity3 hierarchy, IFlexSpine
├── Part\                             Part aggregate (77 KB Part.cs)
├── IO\                               format readers/writers
├── Settings\                         Sheaf cascade
├── Report\                           setup sheets, PDFs
└── OEM\                              OEM-specific overrides

Each domain folder is logically independent and roughly mirrors the M/V/Glob structure: model classes (BendOp), view-models in the same folder (BendVM.cs), and Glob controllers in the parallel Src\UI\<domain>\ folder.

5.6 Reading order through the building blocks

  1. Flux.Base — internalize geometry primitives (Pline, Mesh3, Geo.cs) and the rendering layer (VModel, Lux).
  2. Flux.Core — pick one domain (Bend is the most thoroughly documented) and read it end-to-end (covered by Onboarding chapter 02).
  3. Flux.UI — read one Glob (e.g. BendOpUI.cs) to see how the controllers connect to models.
  4. Flux.App — App.xaml.cs and MainWindow.xaml.cs are short; this is the shell.
  5. Flux.API — Src\API\Basis\Basis.cs and Src\API\Bend\Post\TrumpfDLD.cs together show how the facade and post writers compose.
  6. Flux.Console / Flux.Migrate — short CLI front-ends; reading them clarifies the library boundary.
  7. Flux.Hula — only relevant if you touch 3D import; otherwise opaque.
