05.5 — Module: Flux.API

The hardened façade. Gives 3rd parties (and Trumpf Praxis as the Engine flavor) a controlled subset of Flux's capabilities, without exposing Flux.Core directly.

Purpose

Flux.API provides:

  • A wrapped subset of Flux types (Flux.API.Part wraps Flux.Part, Flux.API.BendOp wraps Flux.BendOp, etc.).
  • The hand-written C# postprocessor writers (Src\API\Bend\Post\).
  • The dispatcher that wires Hub.GenerateNC to those writers (Src\API\Basis\Basis.cs).
  • EINWriter for Trumpf simulation files.
  • Utility converters (MCBReader.Convert, GetPrintable, BCellTech.EINWriter).
  • Basis bootstrap that the App / Praxis both call.

When shipped to a 3rd party, Flux.API.dll carries Flux.Core.dll, Flux.Base.dll, and Flux.Hula64.dll bundled inside as resources — only the API surface is visible.

Code volume: 98 .cs files.

How NC code generation works

  1. BendTech.GenerateNCCode(int nSetup) (Src\Core\Bend\BendTech.cs:1192) is called by the App.
  2. It reads BMachine.Post (e.g. "wad:Post/Bend/TrumpfB23.hx") and extracts the basename ("TrumpfB23").
  3. It calls Hub.GenerateNC (Owner, postname).
  4. Hub.GenerateNC is wired at startup to Src\API\Basis\Basis.cs::GenerateNC (line 138).
  5. That method does a switch (post.ToLowerInvariant ()) and instantiates the appropriate writer: 
    "trumpfdld" => new TrumpfDLD (apart).Generate (),
"bystronic" => new Bystronic (apart).Generate (),
"lvd"       => new LVDWriter (apart).Generate (),
"cell5k"    => new BNCWriter (apart).Generate (),
...
  6. The writer returns an object — typically a string (text NC), a byte[] (binary), or a MemoryStream for compound formats.

The XML-doc comment on GenerateNC (line 135) says it explicitly: "Generate NC code directly for a part (without using Hex)". The Hex post-processor language plan (Note 2004, 2016) was retired.

How a writer is structured

A typical writer (e.g. LVD.cs):

public class LVDWriter {
   readonly Part part;
   public LVDWriter (Part part) { this.part = part; }
   public byte[] Generate () {
      foreach (var setup in part.BendTech.Setups)
         GenerateNC (setup.Index);
      // emit accumulated lines as bytes
   }
   void GenerateNC (int idx) { /* per-setup logic */ }
}

Structure varies — some return strings, some return JSON, some return zipped containers. The dispatcher switch is the source of truth for the contract.

Constraints Flux.API enforces

  • Shipped binary dependencies are bundled inside. A 3rd party sees Flux.API.dll only.
  • License-checked at the Basis entry. if (FX.IsApi && !Permit.Valid) throw new APIException (EResult.NoLicense); (Basis.cs:127).
  • No leakage of internal Core types. Wrappers exist for everything exposed.
  • Engine flavor is the strictest customer. Praxis must be able to call API entry points without a UI.

Adding a new NC dialect

  1. Add a new <DialectName>.cs in Src\API\Bend\Post\.
  2. Implement a class with a constructor (Part) and a Generate() method returning the appropriate type.
  3. Add a switch arm in Src\API\Basis\Basis.cs::GenerateNC that maps the post name (lowercase) to your new class.
  4. (If the dialect needs a custom NC extension) extend BendMachine.NCExtension handling.
  5. Add tests under X:\Test\Bend\ (Flit fixtures) with golden .txt outputs — and ideally .nc golden outputs if your writer emits NC code that can round-trip.

Why not a plug-in / scripting model?

The team chose hand-written C# writers over a scripting language (Hex was the original 2016 plan; abandoned) because:

  • The dialect set is finite (~20) and grows slowly.
  • Each dialect has machine-specific quirks that benefit from full C# tooling and unit tests.
  • A scripting language adds runtime overhead and another maintenance surface.
  • Writers can directly use shared abstractions in Flux.Core — no marshaling layer.

This is recorded as ADR-009 in section 9.

Boost integration paths

Two distinct integrations let Boost drive Flux. They share the underlying compute (the auto-tooler in Flux.Core) but differ entirely in transport, lifecycle, and entry point.

1. FXCMD command-file path (legacy)

The original integration. Boost (or its adapter) writes a plain-text command file with the .fxcmd extension, then launches Flux.exe c:\etc\job1234.fxcmd. Flux processes the command and writes a .fxresp response file alongside it; the adapter typically watches with a FileSystemWatcher.

  • Entry point: Src\Core\CmdProcess.cs — class FBoost. Its Run() reads the [Header] / [Command] INI sections and dispatches by the Type= key (AutoCompute, Interactive, ListWorkplaces, ListBendTools, ListToolLists, ChangeMachine, ConfigureMachine, Get/SetFluxConfig, Get/SetMachineConfig, DataManagement, TSOInteractive, TSOBatch, ImportToolARV, ImportVacuumGripper, ApplyJupiduCorrections, DisplayMessage, ProcessStatus, …).
  • Lifecycle: each non-interactive command spawns a fresh Flux.exe engine process; interactive commands forward to the long-running interactive Flux. Process IDs are not reliable — use the ProcessStatus command instead.
  • Wire format: human-readable INI in both directions; per-command schemas are versioned with a single InterfaceVersion global.
  • Reference: Notes\Tech\2012.BoostInterface.ftx is the authoritative spec.

2. In-process path via BendBoost (REST service)

The newer integration. A host process (the Boost REST service) loads Flux.API.dll, fills a Flux.API.BendBoost instance with the AutoCompute inputs, and drives the run by calling its methods directly. There is no fxcmd file, no fxresp file, no separate process.

  • Entry point: Src\API\Bend\BendBoost.cs — class BendBoost. Properties carry the inputs (GeometryFile, MeshesFile, Workplace, ToolList, Material, TensilStrength, Density, BendMaterial, NCMaterialName, NCReleasePath, BendDeductionCalculation, GeometryAdapt, UILanguage, UIUnit, SetupPlanLanguage, SetupPlanUnit, DlcNumber, DwgNumber, Author, Comment, …). Three drivers: DoAutoCompute() (run from a 2D/3D geometry file), UpdateBendSolution() (re-run on an already-loaded FX), and GenerateOutputs(console, forceSave, outputDir) (emit BNC, HTML, FX, OUT — populates Outputs). Errors and warnings accumulate in Messages; TranslateMessage produces a per-language dictionary suitable for a JSON response.
  • Lifecycle: synchronous, in-process. The REST service owns concurrency and request lifetime; one Flux engine per request is the typical hosting model.
  • Reuse: internally BendBoost still funnels through the same FBoost machinery (BA.BoostCmd = "AUTOCOMPUTE"), so output files and message IDs match the FXCMD path bit-for-bit.
  • Test: Test\Bend\API\BendBoostInterface.cs exercises the class headlessly.

Choosing between them

Concern FXCMD BendBoost (REST)
Transport Files on disk + new process per call In-process method calls
Lifecycle owner Boost adapter polls for .fxresp Host owns request/response
Latency Process-start cost per call None
Crash isolation Each job in its own process Host shares the Flux engine
Spec source Notes\Tech\2012.BoostInterface.ftx BendBoost.cs properties + XML-doc
Status Legacy, still supported Preferred for new integrations

Both paths set BA.BoostFlavor = Permit.Boost and route through the same auto-tooler — feature parity is intentional.
