06 — Runtime View

Dynamic behavior — what happens when, in which order, on which thread.

6.1 Application startup (full UI flavor)

Process start (Flux.exe)
  │
  ▼
App constructor (App.xaml.cs:33)
  │ — culture = Invariant
  │ — Regex default match timeout = 2 sec  (Case 35246)
  │ — AssemblyResolve += LibResolve         (handles mixed-mode Hula DLL)
  │ — new AppCore (this)
  ▼
AppCore.Init
  │ — read Flux.flavor → EFlavor + feature bits
  │ — license validation (Aegis / WIBU / Sentinel / B23 APC / dev whitelist)
  │ — locate FLUXDATA / wad
  │ — FX.Init (), AuType.LoadDefault (), UI.Init ()
  │ — wire Hub slots:
  │       Hub.GenerateNC      ← Src\API\Basis\Basis.cs::GenerateNC
  │       Hub.BigChooser      ← WPF dialog implementation
  │       Hub.MCBtoTXT        ← MCBReader.Convert
  │       Hub.APIWrapper      ← DoAPIWrap
  │       BCellTech.EINWriter ← EINWriter.GenerateEIN
  │       …
  │ — single-instance check (UI.IsAlreadyRunning):
  │       if a prior Flux is alive, forward args via named pipe and exit
  │       (see §6.11)
  │ — register PStatic-bearing assemblies and load `recent:pstatic.curl`
  │       restores recent-files, dialog paths, splitter positions, window geometry
  │       (see glossary entry [PStatic])
  │ — invoke IAppHook.OnAppStart for every loaded brick
  │       a brick returning EStatus.Failure aborts startup
  │
  ▼
Open MainWindow
  │ — restore last-session tabs
  │ — set up status bar, dockable panels
  │
  ▼
Idle event loop (WPF Dispatcher)

6.2 Application startup (Engine flavor — headless, embedded in Praxis)

Praxis loads Flux.API.dll
  │
  ▼
Praxis calls Library.Init(...) in Src\API\Basis\Basis.cs
  │ — (no MainWindow, no UI.Init)
  │ — license check delegated to Praxis
  │ — Hub slots that require UI stay null
  │ — Hub slots that don't (e.g. Hub.GenerateNC) get filled
  │
  ▼
Praxis calls API methods on Flux.API.Part (and friends)
  │
  ▼
Internally: Flux.Core uses Hub?.X?.Invoke(…) — nulls are safe no-ops

6.3 Opening a 3D part end-to-end

The "happy path" for a press-brake part — illustrative scenario.

User picks File > Open part.fx
  │
  ▼ MainWindow command handler
  Part.Load (path)
  │ — Au-deserialize the FX zip
  │ — for each persisted type, call [PostLoad] migrations
  │
  ▼
Part is added to Part.Active and set as Part.Current
  │
  ▼
Part.Model is populated (E3Plane / E3Flex tree)
  │
  ▼ if user clicks "Switch to Bend" or auto-detect kicks in:
  Part.DoSwitchToBending (flags, machine)
  │
  ▼
BendTech.Make (part, machine)
  │ — private constructor (250 lines):
  │     RefineColliders, group flexes, split hem phases,
  │     create BendOps, ValidOrder, assign SeqNo
  │
  ▼ User clicks "Auto Tool"
  BendTooler.Process (tech, flags)
  │ — PrepareForTooling
  │ — SetupBasicSequence
  │ — TurnOnBumpBending
  │ — DemoteCrashingTools
  │ — UpdateToolScores
  │ — DoToolerCore
  │     · final sequence
  │     · setup generation
  │     · BG placement
  │     · BA placement
  │
  ▼
Validation passes
  │ — BendOpStatus / BendOpCrash / NBendCrash
  │ — Per-Op EBATIssue flags collected
  │
  ▼ Lux re-renders the affected scene-graph nodes
  │
  ▼ User reviews → optional manual edits via Globs → undo registered
  │
  ▼ User clicks "Generate NC"
  BendTech.GenerateNCCode (nSetup)
  │ — strips post-name basename, e.g. "TrumpfDLD"
  │ — Hub.GenerateNC (part, "trumpfdld")
  │
  ▼
Src\API\Basis\Basis.cs::GenerateNC
  │ — switch on dialect → new TrumpfDLD (apart).Generate ()
  │
  ▼
NC code returned to MainWindow → user saves to disk

6.4 Robotic-cell run end-to-end

Adds two phases on top of §6.3 — Pickup before bends, Deposit after, plus optional Regrips between bends.

Part with cell-attached BendMachine (id 93 is the standard test machine)
  │
  ▼ (steps 1–3 same as §6.3 — Part loaded, BendTech.Make, BendTooler.Process)
  │ — but now: BendTech.Cell is non-null → mRobotic = true
  │ — auto-tooler scores tools differently for robotic context
  │
  ▼
Cell-level expert passes:
  │ PickupExpert / DispenserExpert  → BCPickup parameters
  │ BRegripExpert                   → list of BCRegrip operations
  │ BDepositExpert                  → BDepositPlan (lattice)
  │ CellRefine                      → refine plan
  │ RPathPlanner                    → robot motion between every pose
  │ BStepComputer                   → per-step waypoints
  │
  ▼
BSimStepNeo
  │ — simulate end-to-end
  │ — collect EBCStatus / EBStatus flags
  │
  ▼ User clicks "Generate NC"
  BendTech.GenerateNCCode → Hub.GenerateNC → BNCWriter / TrumpfDLD / …
  │
  ▼ User clicks "Generate Robot Code"
  BCellTech.RobotCode + MangleRobotCode
  │ — produces compact text with delta moves, speed, tolerance, regrip
  │ — emitted as the test-contract for cell tests (.txt golden files)
  │
  ▼ Optional EIN file
  BCellTech.EINWriter (= Hub-wired)

6.5 Saving an FX file

User picks File > Save
  │
  ▼
Part.SaveFX (stream, ESaveFX.…)
  │ — Au-serialize Part + all techs
  │ — generate thumbnail via Lux (must run on UI thread)
  │ — Curl-serialize machine references
  │ — package everything as zip
  │
  ▼ Confluence/preview thumbnails note: this is *why* models and views live together
  │  in Flux.Core — generating a thumbnail without rendering would be impossible.

6.6 Threading model

Thread Owns Notes
UI thread (Dispatcher) Main window, all WPF, all Lux rendering, Part.Current, Part.Active, BendMachine.Default, Hub.* Most domain code runs here.
Worker (Task.Run) Long ops (auto-tooler when initiated headlessly, large imports, batch nesting) Results must marshal back to UI thread before mutating live state.

There is no CancellationToken plumbing throughout. Long ops cooperatively check Part.Flags & Part.EFlags.AbortTooling (see BendTooler.DoTooling).

The realistic concurrency hazard is re-entrancy, not multi-tenancy: two property setters firing on the same domain object during user interaction. Almost all "concurrency bugs" reported are actually re-entrancy bugs.

6.7 Undo lifecycle

User edits a property of BendOp via BendOpGlob
  │
  ▼ setter routes through BA.Set<T>(ref field, value)
  │ — equality check
  │ — INotifyPropChanged
  │ — register an undo unit on the active Part's undo stack
  │
  ▼ change propagates: VModel marks dirty, Lux schedules redraw
  │
  ▼ user invokes Undo (Ctrl-Z)
  │ — pop undo unit, apply inverse → setter routes again, except undo not registered this time
  │
  ▼ visible: VModel re-renders

Per-Part undo stack — switching tabs switches stacks.

Pseudocode for any Core/UI call into App-territory:

// In Core or UI
var rc = Hub.ClosePartByJobID?.Invoke (jobId, force) ?? -1;
//                            ^                       ^
//                            |                       └── default if slot unset
//                            └── null-safe — Engine flavor leaves slots null

6.9 Test-time substitution

In Flit test fixtures:

  • BA.Testing = true is set at fixture entry.
  • BendMachine.Default returns machine 99 in test mode — X:\Data\Machine\99\.
  • FX.Testing is checked in scattered places to skip telemetry, file-write side effects, dialog prompts.
  • Part.Current may be substituted via the test loader.

The substitution is mostly transparent. Where it isn't, design-principle D004 ("design for testability") drove explicit refactors so unit tests don't need FX.Testing checks at all.

6.10 Multi-instance handling — single-window arg forwarding

A user double-clicks a .fx, .fxcmd, .geo, .dxf, or any other Flux-handled file. Windows spawns a new Flux.exe with the path on the command line. The user expects the file to open in their existing Flux window, not in a second one. The mechanism:

new Flux.exe (file path on cmdline)
  │
  ▼
App.OnStartup → UI.IsAlreadyRunning (this, appId, args, HandleArgs)
  │   appId ∈ { "meta-flux"  (default)
  │            ,  "tzlaser"   (if Permit.TrumpfTZLaser)
  │            ,  "boostlaser" (if Permit.BoostTZLaser) }
  │
  ├── Mutex.TryOpenExisting (appId)  succeeds  ─────►  another Flux is alive
  │       │
  │       ▼
  │   Connect NamedPipeClientStream(".", appId, PipeDirection.Out)
  │       │
  │       ▼
  │   Write args joined by "[<sep>]"; close pipe
  │       │
  │       ▼
  │   FX.SecondInstance = true; Application.Shutdown()      ← this process exits immediately
  │
  └── Mutex doesn't exist → we are the first instance
          │
          ▼
      Create Mutex(true, appId); spawn background Task ListenForMessages():
          while running:
             accept one client on NamedPipeServerStream(appId, PipeDirection.In)
             read bytes → split on "[<sep>]" → BA.UIPost(() => HandleArgs(parts))
                 │
                 ▼
             HandleArgs → ALib.OpenForEditing(file, true)
                 .fx / .fxjob / .fxlyt / .geo / .dxf → Hub.Edit(...)
                 .fxcmd / .cmd → ALib.RunInteractiveCmd(file)  (see §3.2.5)
                 .mcb / .ftrep / .tso / .curl / .fxmcconfig → kind-specific handler

Key points:

  • Three independent instance scopes, one mutex/pipe per scope. Two tzlaser Flux instances refuse to coexist; a tzlaser and a boostlaser can run side-by-side.
  • The IPC is named pipes plus named mutex. No memory-mapped file, no WM_COPYDATA, no Win32 atom.
  • The mutex doubles as the existence check. It is owned by the live process; the OS releases it when that process dies, so TryOpenExisting is a clean liveness probe.
  • FX.SecondInstance (Src\Core\FX.cs:395) is also set to true for three other reasons: -refreshconfig flag during shutdown, .NET runtime too old, license expired. Code paths gated on it skip pstatic save and other side effects.
  • The forwarded path goes through the same ALib.OpenForEditing switch as the in-process File > Open menu, so behaviour matches.

Relationship to the Boost FXCMD interactive forwarding (§3.2.5 #4): same conceptual goal (route work into the running interactive Flux), different mechanism. End-user file-open uses the named-pipe channel. Boost interactive .fxcmd files arrive on the new process's command line, get matched in ALib.OpenForEditing to RunInteractiveCmd, and from there flow through FBoost.Run against the live MainWindow. The two forwarders are wired in parallel; they don't share IPC.

Code: Src\App\App.xaml.cs:151–:191, Src\UI\Misc\UI.cs:378–:428, Src\App\ALib.cs:155+, Src\App\ALib.cs:140 (RunInteractiveCmd).

6.11 Common scenarios at a glance

Scenario Entry Key sequence
Open + auto-tool a bend part File > Open Part.Load → BendTech.Make → BendTooler.Process
Save File > Save Part.SaveFX
Multi-edit a property Multi-select + property change composite Glob (BendOpsGlob) → loop setters → single undo unit
Generate NC "Generate NC" button BendTech.GenerateNCCode → Hub.GenerateNC → C# writer
Run a Flit test console runner FX.Testing=true → fixture Test() → CheckDump (golden compare)
Add a regrip Glob command BendOpGlob.AddRegrip → BCRegrip(...) constructor → BendTech.Cell update
Switch flavor (dev only) startup, Flux.flavor file App reads file → feature bits adjust → some menus disappear
