RustBackendWebFrontend1to1AutoPort

RustBackendWebFrontend1to1AutoPort

product: flux org: metamation type: analysis project: Flux tags: [metamation, flux, architecture, rust, web, port, transpile, feasibility] updated: 2026-07-20 owner: aiko.radlingmayr revision: 'v2 — adds §7 (refined proposal: drop features + AI-authored changes + golden-test oracle)' source: 'Static analysis of Src/ on main (2026-07-20) + [[WPF Decoupling]] spec'

Flux → Rust backend + Web frontend, kept in 1:1 sync from C#

The proposal (as stated): keep C# development in github.com/metamation/Flux as the canonical line of work, and automatically convert every branch, 1:1, into a companion repo with a Rust backend + web frontend — so the modern stack always mirrors the legacy one.

Verdict up front: the idea splits into two very different claims, and they must not be judged together.

[!danger] The Rust auto-transpiler half is not feasible A script that converts C# → Rust "1:1, every branch" is not achievable with today's (or near-term) tooling, and the dual-repo, kept-in-sync model would fail on process grounds even if the transpiler existed. Do not pursue this half.

[!note] Refinement (v2) changes the answer for the Rust half The proposal was refined: drop hard-to-port features (e.g. runtime scripting), no transpiler script — let AI author every change, validated by the C# suite's tests. This is materially stronger and dissolves the two hardest technical blockers. It turns "impossible transpiler" into "credible one-time AI-assisted rewrite anchored on approval tests" — but the "keep C# canonical and mirror forever" framing is still the wrong steady state. See [[#7. Refinement — drop features + AI-authored changes + golden-test oracle|§7]].

[!tip] The web-frontend half is not only feasible — it is already specced Replacing the WPF desktop shell with a web UI over a headless C# backend is real, planned, and mostly a refactor of code we own. That is the [[WPF Decoupling]] program. The modern version of Flux comes from finishing that, not from porting the language.

1. What Flux actually is (grounding the estimate)

Measured on main, 2026-07-20:

Fact Value Why it matters
C# source ~428,000 lines, 917 files, 39 projects Scale of any "convert" job
Src/Core 206k lines The CAM/CAD domain — bend, laser, nesting, NC/post. The crown jewels.
Src/UI + Src/App ~73k lines WPF The part a web UI would actually replace
Target framework net10.0 already (25 projects -windows, 7 plain) Flux is not legacy .NET Framework. The "legacy" is WPF + in-process OpenGL, not the runtime.
Files touching GL/Lux 684 Graphics coupling runs deep through Core/API
Change velocity 224 commits / 90 days (~2.5/day), 34 authors/180d The "convert every branch" firehose
Native code Src/Hula C++, P/Invoke to opengl32/glu32/gdi32 Not expressible in a naive transpile
Proprietary deps Aegis / WIBU / Trumpf.Licensing (Windows-only NuGet) No Rust equivalent; licensing is legally/tech bound
Runtime C# scripting Core/Classes.cs:289 → CSharpScript.RunAsync(...) The app compiles and runs C# at runtime.
Reflection-driven serialization 23 files use the [Rep (…)] attribute; 77 files touch reflection Behaviour depends on the C# type system at runtime

The two rows in bold are, on their own, enough to sink automated transpilation. Everything below explains why.

2. Why "auto-convert C# → Rust, 1:1" cannot work

2.1 There is no C#→Rust transpiler that produces maintainable code

Cross-language transpilers exist for narrow, garbage-collected → garbage-collected hops with similar semantics (e.g. C#→Java-ish). C#→Rust is a semantic-model change, not a syntax change:

  • Ownership/borrow model. C# is GC'd with unrestricted aliasing and cyclic object graphs. Flux's domain is full of shared, mutable, cyclic references (a Part knows its Model, which knows its Machine, which back-references parts…). Rust rejects exactly this without a manual redesign into Rc<RefCell<>>/arenas/indices. A machine translator can only produce either (a) a sea of Rc<RefCell<>> that is slower and uglier than the C# and still not idiomatic, or (b) nothing.
  • Inheritance & virtual dispatch. Flux uses class hierarchies and overrides throughout. Rust has no inheritance; the faithful mapping (enums + trait objects) is a design decision per hierarchy, not a mechanical rewrite.
  • Exceptions vs Result. 428k lines of throw/try/catch control flow have no 1:1 image in Rust's Result/panic model. "1:1" is undefined here.
  • async/threading, dynamic (19 files), unsafe/pointers (28 files), LINQ (130 files). Each is a different impedance mismatch. LINQ iterator semantics alone rarely survive a literal port.

Even the best-in-class LLM-assisted porting efforts in industry (e.g. large COBOL→Java, or C→Rust government programs) are one-time, human-supervised migrations that take teams months and end the old codebase — not repeatable, unattended, per-branch converters. Nobody ships a button that turns an arbitrary C# branch into correct idiomatic Rust.

2.2 Two features make even a heroic port impossible without reimplementation

  • Runtime C# scripting. Core/Classes.cs evaluates C# source at runtime via Roslyn (CSharpScript.RunAsync). To preserve behaviour, a Rust port would have to embed a C# scripting engine inside the Rust process (i.e. ship the CLR anyway) or reimplement the entire scripting subsystem in another language. Either way it is not a translation of the branch — it is a new design.
  • Reflection-based persistence ([Rep (…)], 23 files). Flux's serialization/format behaviour is driven by walking C# attributes and types at runtime. Rust has no runtime reflection. This must be re-expressed as codegen/serde derive by hand, per type — and file/format compatibility (customers' saved jobs, NC output) must match byte-for-byte, which a transpiler cannot verify.

2.3 The graphics/native/licensing floor

  • Lux/OpenGL (684 files) is in-process immediate-mode GL via P/Invoke. A web target removes GL from the backend entirely (render in the browser) — so this code isn't "ported", it's replaced by a scene-serialization protocol (exactly what [[WPF Decoupling]] §1 designs). Auto-porting it to Rust would port code that the target architecture deletes.
  • Src/Hula is C++, and Aegis/WIBU licensing is a Windows-only proprietary binding. Neither has a Rust image; the licensing story is contractual, not just technical.

2.4 "1:1" is the wrong invariant for a rewrite

A modern Rust+web Flux would want to differ from the C#: web scene protocol instead of GL, serde instead of [Rep], Result instead of exceptions, arenas instead of object soup. "1:1 with the C#" and "idiomatic/modern" are in direct tension — you can have a faithful mirror or a modern codebase, not both from the same automated pass.

3. Why the dual-repo sync model fails even setting transpilation aside

Suppose the magic converter existed. The "keep C# canonical, mirror every branch" operating model still breaks:

  • We already live the two-repo tax and it's the #1 forgotten step. [[ReFlux — Companion Repo Checklist]] documents that Flux ↔ ReFlux (a binary-asset companion, far simpler than a code port) is "the single most frequently forgotten thing in Flux code review." Now imagine that coupling for all 428k lines, on 224 branches/quarter.
  • Bidirectional reality. Bugs, security fixes, and reviews would land in whichever repo the team actually runs. A "C# is canonical, Rust is generated" rule survives contact with production for about one hotfix. Then the repos diverge and the converter can no longer reconcile them.
  • Doubled CI, doubled review, doubled test oracles. Every branch needs green tests in both languages. Flux has "no headless test net today — even Flux.Console links WPF" (WPF Decoupling §11.3). We would be validating a generated Rust tree we can't easily test, against a C# tree we can.
  • Merge/rebase across a transpile boundary is undefined. A 3-way merge in the Rust repo has no meaning when the Rust is a derived artifact — conflicts can only be resolved in C#, then regenerated, which defeats "develop in whichever is convenient."

Net: even a perfect converter yields a permanent, growing synchronization liability with no payoff until the day you stop generating and switch the Rust repo to canonical — at which point you have simply done a (worse, machine-shaped) rewrite.

4. What "a modern version of this legacy app" actually requires

Separate the two things the proposal bundles:

Concern Is it real? Right move
Runtime is old ❌ No — already net10.0 Nothing to do
Shell is WPF desktop + in-process OpenGL ✅ Yes — this is the "legacy" Web UI over headless C# backend → [[WPF Decoupling]]
Domain logic (Core) is dated Partially Harden it in place (Step 1 / Phase G pushes safeguards down into the domain)
Backend language should be Rust ❓ A want, not a need Only justified by a real driver (perf, memory safety, hiring). Not delivered by auto-port.

The already-written [[WPF Decoupling]] spec is the credible modernization: make Base/Core/API headless net10.0, add a scene-serialization protocol + Flux.Host (WebSocket/HTTP), and build the flux-renderer WebGL/WebGPU front-end — reusing the 206k-line domain we already trust, replacing only the ~73k lines of WPF/GL shell. Effort: XL, multi-month, several engineers — but it is moving and wrapping code we own, with the desktop app still working throughout via transitional *.UI projects.

5. Options compared

Option Backend Reuses Core? Sync tax Feasibility Modern result
A. Auto-port C#→Rust, mirror every branch (this proposal) Rust (generated) ❌ regenerated 🔴 permanent, doubling ❌ Not feasible (scripting, reflection, ownership, native) —
B. One-time AI-assisted C#→Rust rewrite, anchored on the golden corpus Rust ❌ reimplemented none (old repo retired) 🟢 credible & de-risked by 343 MB oracle (v2, §7) — still big, still freezes features ✅ but disproportionate to the actual "legacy" problem
C. Headless C# + Web UI ([[WPF Decoupling]]) C# net10.0 ✅ fully none ✅ feasible, specced ✅ web UI, modern shell
D. C now, carve selected hotspots to Rust later via FFI C# + targeted Rust libs ✅ low (normal native-lib coupling) ✅ incremental, optional ✅ + targeted perf

Recommendation: Option C, with Option D held in reserve. If Rust is genuinely wanted, the sane path is not a whole-codebase mirror — it is, after the headless split exists, to move a specific, self-contained, performance-critical module (e.g. a nesting or geometry kernel) behind a stable interface and reimplement that one module in Rust as a native library the C# backend calls. That gives real Rust in the stack, one bounded piece at a time, with a normal FFI boundary instead of a whole-repo transpiler.

7. Refinement — drop features + AI-authored changes + golden-test oracle

The proposal was sharpened on three points. Each is assessed on evidence, not vibes.

7.1 "Drop hard-to-port features, e.g. the scripting" — ✅ legitimate, with a caveat

The runtime C# scripting I flagged as a blocker (§2.2) is, on inspection, an interactive developer REPL — Core/Classes.cs ConsoleScriptShell/IScriptShell, a CSharpScript.RunAsync debug console. It is not a customer-facing NC/post feature, so dropping it in a Rust build loses no end-user capability. The instinct is right here.

[!warning] Caveat: "1:1" and "drop features" are mutually exclusive — and dropping needs per-feature due diligence Every dropped feature makes the Rust build a subset, not a mirror, so the "1:1" claim quietly weakens with each cut. And the reflection-based persistence ([Rep (…)], 23 files) is not droppable the way the REPL is — it defines on-disk/NC file-format compatibility with customers' saved jobs. That one must be reimplemented (as serde/codegen producing byte-identical output), not dropped. Vet each "we'll just drop it" against: does a customer / machine / saved file depend on it?

7.2 "Let AI write every change" — the right shape is AI editing, not regenerating

This removes my "no good transpiler exists" objection (§2.1): an AI can make the design decisions a transpiler can't (ownership model, enums-vs-traits, Result-vs-exceptions). But it only works in one specific form:

  • ✅ Viable: a stable, human-owned Rust architecture that AI makes incremental edits to, branch by branch, guided by tests. The Rust repo is a real codebase that humans review.
  • ❌ Not viable: AI re-deriving the Rust from each C# branch independently. Stochastic per-branch regeneration produces inconsistent architecture and silent drift — the same divergence failure as the transpiler, just non-deterministic. "1:1 mirror" is not a property AI regeneration can hold.

Your phrasing ("AI writes all the changes always") is compatible with the viable form — as long as it means maintaining the Rust codebase, not regenerating it.

7.3 "The tests are already there from the C# version" — half true, and the true half is gold

This is the load-bearing claim, so it was measured:

What exists Portable to Rust? Notes
TData/ golden corpus — 343 MB, 11,145 files (740 .nc, 941 .geo, 536 .dxf, 375 .curl, 3432 .txt, 158 .png…) ✅ Yes — fully Language-agnostic input→expected-output pairs. This is the real prize.
Approval-test mechanism (Assert.AreTextFilesEqual / AreBinaryFilesEqual / AreBitmapsEqual, -regenerate + windiff) ✅ concept ports Classic characterization/approval testing — exactly the correct oracle for a legacy rewrite.
The harness + test code — Flit (custom, not xUnit), 169 files, 51k LOC, reflection-driven, net10.0-windows, 43 files link WPF/GL/Dispatcher ❌ No The runner and ~51k LOC of test code are C#-specific and must be re-authored in Rust.
API-level unit asserts on C# objects (part of the 2,101 assert sites) ❌ mostly no Only behavior that emits a comparable artifact is captured by file diffs.

So the accurate statement is: the behavioral oracle (343 MB of real cases with expected NC/geo outputs) largely is already there and is language-neutral — a Rust port can be driven against the exact same corpus and required to match byte-for-byte. That is the strongest possible foundation and it genuinely de-risks a rewrite. But the test suite is not "already there" — 51k LOC of harness+cases is C#-bound and must be rebuilt (an AI-assisted but real task), and golden files only cover artifact-producing behavior. Interactive/UI flows, and anything TData doesn't exercise, are coverage gaps where AI can silently diverge and no test will complain.

[!important] Two sequencing truths the golden oracle forces

  1. A golden test can't run in Rust until Rust implements the whole path to that artifact. So you cannot mirror one PR at a time from day one — nothing goes green until a large slab of the pipeline is ported. It is a big upfront port, then per-branch maintenance — not incremental mirroring from the start.
  2. Golden tests pin current behavior including current bugs. Faithful reimplementation reproduces those bugs; any "modern" improvement that changes output surfaces as a diff you must manually bless. Fidelity and modernization pull against each other on every diff.

7.4 What the refinement does — and does not — fix

Objection (from §2–§3) Status after refinement
No maintainable C#→Rust transpiler (§2.1) ✅ Dissolved — AI authors idiomatic Rust instead
Runtime C# scripting blocker (§2.2) ✅ Dissolved — it's a dev REPL, safely dropped
Reflection-based persistence (§2.2) 🟡 Still real — must be reimplemented for file-format compat, not dropped
No correctness oracle ✅ Largely solved — 343 MB golden corpus is the oracle
Native/GL/licensing floor (§2.3) 🟡 unchanged — GL is replaced by the web protocol; Hula/WIBU still need answers
Permanent dual-repo maintenance tax (§3) 🔴 Unchanged — tests validate correctness, not the cost of running two production codebases
Divergence / double review / double CI (§3) 🔴 Unchanged — 224 branches/quarter still reviewed & kept green twice
"Keep C# canonical forever" is the wrong end-state 🔴 Unchanged — the golden oracle's payoff is that it lets you cut over and retire C#, not maintain both indefinitely

The refinement fixes the technical half and leaves the operating-model half intact. The golden corpus makes a one-time, AI-assisted, approval-test-anchored rewrite genuinely credible (it upgrades Option B from "possible but disproportionate" to "possible and materially de-risked"). It does not rescue "mirror every branch, forever" — that remains a growing liability whose only rational exit is to stop mirroring and switch the Rust repo to canonical, i.e. a migration, not a permanent twin.

6. Bottom line

  • "Auto-convert every branch 1:1 into Rust+web" via a script — no. No transpiler produces maintainable Rust from this codebase (ownership model, inheritance, exceptions, reflection, native interop, Windows-only licensing).
  • Refined form — "drop hard features, AI authors changes, C# tests validate" (v2, §7) — the technology becomes credible, the operating model does not. The 343 MB TData golden corpus is a genuine, language-neutral oracle that de-risks a rewrite; dropping the dev-REPL scripting is fine; reflection-based file-format persistence must be reimplemented, not dropped; and the 51k-LOC test harness is C#-bound, so "the tests are already there" is only half-true (the data is, the harness isn't). But tests validate correctness, not the cost of two production codebases — the permanent dual-maintenance/double-review tax we already mishandle at 1/100th the scale (ReFlux) is untouched. Mirror-forever is the wrong end-state; its only rational exit is a cutover.
  • "Modern version of this app" — yes, and the plan already exists. It's a web frontend over a headless net10.0 backend ([[WPF Decoupling]]), reusing the domain rather than rewriting the language. The "legacy" is the WPF/OpenGL shell, not the runtime.
  • If Rust is a real goal, earn it incrementally via FFI on one carved-out module after the headless split — never as a whole-repo auto-mirror.
