Step1RemoveUILogicandValidation

product: flux org: metamation tags: [metamation, knowledge-base, flux, refactor, wpf, architecture, spec] type: spec project: Flux updated: 2026-07-14

Part of the [[WPF Decoupling]] spec · Step 1 — do this first · then → [[Step 2 - Split into Decoupled Assemblies]]

Findings & extraction plan: move domain logic and validation out of the WPF Glob menus into the headless domain. §13.4 is the validations catalog — the key deliverable.

13. The Glob menus: logic & safeguards trapped in WPF (the pre-step — do this first)

Why this is a separate, earlier step than everything above. §7–§10 move rendering code out of the domain. This section is about the opposite leak: domain logic and safeguards that live inside the WPF UI and must move down into the headless layer. The Glob "menus" are Flux's property editors, and many of them are not thin view code — they enforce machine limits, run inverse-kinematics, and do collision/crash validation before they let a value through. If the WPF is swapped for a web front-end before this logic is extracted, those safeguards silently disappear and the headless backend will happily accept physically-invalid states (unreachable robot poses, back-gauge crashes, over-stroke gauges). So this is Phase G in §11.2, ahead of Phase 0. It is also independently valuable: it hardens the domain even if the web UI never ships.

13.1 What a "Glob" is (the mechanism)

A Glob is a source of programmatically-generated UI for a domain object (UI/Glob/Glob.cs:16). Each …Glob subclass overrides GetUI(List<GElement>) to declare abstract UI pieces — GButton, GTextBox (numeric spin-box with min/max/step), GChoices, GSlider, GCheckBox, GInfo… (all in UI/Glob/GElement.cs). The pipeline:

flowchart LR
    Dom["domain (headless)<br/>Hub.Edit(obj) → BHub.Selection<br/>SelectionChanged event"]
    Sel["Glob.Select(obj)<br/>builds Glob tree via GetUI()"]
    PM["PanelMaker<br/>GElement → WPF controls"]
    Host["GlobHost : Window<br/>FSpinBox, ComboBox…"]
    Dom -->|"UI subscribes<br/>UI/Misc/UI.cs:343"| Sel
    Sel -->|"CurrentGlobChanged<br/>UI/Misc/UI.cs:348"| Host
    Sel --> PM --> Host
    classDef f fill:#e6f4ea,stroke:#137333,color:#0d652d;
    classDef w fill:#fce8e6,stroke:#c5221f,color:#a50e0e;
    class Dom f; class Sel,PM,Host w;

Two facts make this the right first target:

  1. The domain→editor trigger is already a clean, headless seam. The domain never references a Glob; it calls Hub.Edit(obj) / sets BHub.Selection (Base/BHub.cs:41), which raises SelectionChanged. The UI subscribes (UI/Misc/UI.cs:343: Hub.SelectionChanged += (_,_) => Glob.Select(Hub.Selection)) and the glob machinery lives entirely UI-side. No override void GetUI exists in Base/Core/API — all 87 …Glob subclasses are in Flux.UI.
  2. The abstraction is already ~95 % WPF-free and even carries domain metadata. EGTag (UI/Glob/EGTag.cs) is a pure enum whose members are decorated with unit/semantic attributes — [Length], [Degree], [Angle], [Speed], [Position], [LinearForce], [NoGang] — exactly the metadata a web renderer needs to format and validate a field. Glob/GElement/the composite globs (ConcatGlob, GangedGlob) are otherwise WPF-free. This is a movable model layer, not a rewrite.

Repositioned for the web goal: the Glob/GElement tree is the model-view separation the web UI needs — a declarative description of a form. It is simply on the wrong side of the assembly line, and has accreted domain logic. The end state mirrors §1: the headless backend emits a menu/form schema (fields + units + ranges + enable-state + validation verdicts) and the browser renders controls — PanelMaker is replaced the same way the GL target is replaced by an ISceneEmitter.

13.2 The three shallow WPF leaks in the abstraction itself

Before the model can move headless, three small leaks must be neutralized (all trivial — this is the easy part):

Leak Where Fix
System.Windows.Input.Key in KeyWatch(Key) GElement.cs:203 (GButton), GElement.cs:552 (GNavigate) retype to the neutral Flux key enum proposed in §8.2 (BHub.cs Key→neutral)
FrameworkElement type-check GElement.cs:294 (GChoiceItem tooltip) drop / replace with an object check
Keyboard/FrameworkElement KLUDGE Glob.cs:360-362 (Glob.Refresh(), already flagged "abomination" in-code) route focus through IUiScheduler/IInputState (§6)

Everything WPF beyond this is concentrated in the renderer (PanelMaker.cs, GlobHost.cs) and in GlobAux.cs — the latter's GlobActors/GlobMouser/GlobVModel depend on Lux/GL (VModel, GLMouse, Lux.UIScene) and therefore travel with Flux.Lux/Flux.Lux.Wpf (§7), not with the model.

13.3 The real problem — domain logic & safeguards inside the 87 subclasses

Every machine-facing domain (bend, laser cut, robot cell/waypoint, back-gauge, trim, fold) has "fat" globs that embed kinematics, machine limits, and process-legality rules. The report/drawing/info globs are mostly "thin" layout. Rough split:

  • Fat (extraction candidates): BWaypointGlob (BCell/BWaypointUI.cs, the heaviest — a robot IK module in a Glob costume), BGGlob (Bend/BGUI.cs, back-gauge collision), BendOpGlob (Bend/BendOpUI.cs), BendMountGlob (Bend/BendMountUI.cs, ~1000 LOC), BRegripGlob (BCell/BRegripUI.cs), TrimPoseGlob/ TrimModelGlob (Trim/TrimUI.cs), E3FlexGlob/E3SurfaceGlob (Model/Entity3UI.cs), CutTechGlob (Laser/CutUI.cs), BDepositGlob/BPickupGlob (BCell/), FoldKB40 globs, MechanismGlob (Sim/).
  • Thin (port as-is): RILabelGlob/RICodeGlob/RIFieldGlob/RIShapeGlob (Report/ReportUI.cs), E2PointGlob/E2TextGlob/EntitiesGlob (Dwg/Entity2UI.cs), the Report/PictureUI.cs picture-prop globs, info-only TrimIssueGlob/CmdCoplanarityInfoGlob.

13.4 Validations catalog — the key deliverable of this step

The user asked specifically that all validations in the globs be enumerated. There are two very different situations, and telling them apart drives the whole plan:

  • (D) Domain-computed, UI-only-displayed — the domain object already computes an Err*/Warn* flag; the glob merely renders it as a red Info/Separator. These are already safe — only the display moves, the validation is already headless.
  • (U) UI-enforced — the glob itself clamps to a limit, runs a crash test, or gates an edit on reachability, and rolls back / rejects if it fails. These are the leak — the setter on the domain object often does not re-check, so the safeguard exists only in the WPF. Each (U) must move into a domain method (a validating setter, or a TryApply(...)→bool on the domain object) that the glob — and later the web backend — calls.

(U) UI-ENFORCED safeguards — must be extracted into the domain

(D) Domain-computed, UI-only-displayed — already safe, only the display moves

These confirm the domain can own validation — the pattern already exists and should be extended to absorb the (U) cases. The glob reads a domain flag and shows a red line:

  • ACB Bend/BendACBUI.cs:71-92 surfaces WarnACBOffRange, ErrACBReference, WarnACBFlange, ErrACBHole, ErrBGACBCrash, ErrACBCrash, ErrACBTraceLength, ErrACBLaserCrash, ErrRobotACBLaserCrash, ErrGripperACBLaserCrash, ErrACBDiskOverload, WarnACBOneLaserUsed.
  • Bend op Bend/BendOpUI.cs:109 reads ErrPunchCrash/ErrDieCrash/ErrPunchSpan/ErrDieSpan (also ErrToolingCrash, ErrPunchOverload, ErrDieOverload, ErrMCOverload, ErrNoPunches).
  • Back-gauge ErrBGStroke (4 sites), ErrBGMissing (2) — surfaced as Info(Error,…).
  • Robot stroke / regrip ErrRobotStroke gating in BCell/BRegripUI.cs:128-130.
  • Gripper ErrGripperSelfCrash, ErrGripperOverrun, ErrFlangeTooNarrow (BCell/BGripperUI.cs:190, …).

13.5 Dynamic enable/disable business rules (a third leak, adjacent to validation)

Field enable-state is frequently a domain predicate computed in the glob and pushed via Enable(tag,cond) or conditional emission in GetUI:

  • BWaypointUI.cs:488-496 — EnableStuff() gates insert/remove/reset/interpolate on CanWaypoint(), IsCustom(), waypoint count, CanEditInterpolation(); :116-128 emits Config/Interp/Regrip only for Is6Axis/HasRegripStns/IsForward and locks via Disable(8002).
  • BDepositUI.cs:183-184 — Enable(GapXY, Columns>1), Enable(GapY, Rows>1 && !plan.IsInclined).
  • BRegripUI.cs:556,678-679; BendMountUI.cs:486 (Enable(SplitGap, mnGap==0)); Laser/CutUI.cs:652-654, 957-958 (wire-joint buttons vs bevel state); BendOpUI.cs:83-115 (fields gated on IsLargeR/IsBumping/ IsFormBend/Robotic&&IsHem/error flags).

These "can I edit this?" predicates are business rules; they belong next to the validation on the domain object (a web UI needs the same answers to grey-out controls).

13.6 Reactions to domain events & undo/transaction framing

  • OnObjPropChanged overrides (only ~7, mostly thin): recompute-triggering ones are Layout/LayoutUI.cs:416-427 (on PcmtXfm → invalidate bounds + UpdatePositionUI), Fold/FoldKB40UI.cs:221 (on KB40Error/HeadConfig → re-push derived fields); redraw-only in Dwg/DrawingUI.cs:173, Laser/LaserUI.cs:1233, BCell/BRegripUI.cs:514, Report/ReportUI.cs:535, Bend/BendMountUI.cs:788. Related: BWaypointUI.cs:154-158 re-initializes step/pose on EProp.SimFrame.
  • Undo framing is scattered through the globs (Undo.Frame/Undo.Mark): Laser/CutUI.cs (6), Layout/CutNavigator.cs (3), Laser/LaserUI.cs (3), Dwg/DrawingUI.cs (2), Layout/LayoutUI.cs (2), plus single sites in BendOpUI, BendSetupUI, BendClampUI, BGUI, BendAidUI, BendACBUI, BRegripUI. (GElement/GButton also auto-frame undo — GElement.cs:64-84, GButton.cs:224 — so the generic case is already centralized; only these bespoke frames need attention.) Direct domain mutations from globs: BendMountUI.cs:793 DoFlip()+CodeDirty; BendOpUI.cs:65-72 AddRegrip/ResetSteps; BWaypointUI.cs:477-484 IDirty(EBInput.Waypoint).

13.7 The extraction plan for Phase G

  1. Neutralize the 3 abstraction leaks (§13.2) — small, unblocks moving the model.
  2. Relocate the Glob model — Glob, GElement & subclasses, EGTag (+ its semantic attributes), the composite globs — into a headless location (a new Flux.Globs on net10.0, or fold into Core). Keep PanelMaker/GlobHost/TooltipFrame in Flux.UI (the WPF renderer). GlobAux.cs travels with Flux.Lux.Wpf (§7). This can only complete once Base/Core are headless (§4), so the model may sit in Core initially and split out later — but the logic extraction (step 3) is independent and can start now.
  3. Push every (U) safeguard down (§13.4): for each UI-enforced clamp/crash-test/reachability gate, add the check to the domain — either a validating setter or a bool TryApply(value, out reason) / Validate(...)→verdict method on the domain object (BendOp, BCRegrip, BGPos/gauge, waypoint pose, deposit plan…). The glob (and later the web backend) calls it and reflects the verdict. Machine-limit literals (§13.4 note) become domain-supplied ranges (SetRange pattern) so the bound has one source of truth. Add a regression test per safeguard — this is the safety net that lets the web UI trust the backend.
  4. Model the enable-predicates and validation verdicts as part of the emitted schema (§13.5) so a browser renderer greys-out and red-flags fields identically without re-implementing the rules.

Payoff / ordering: step 3 hardens the current WPF app immediately (the domain stops trusting the UI to prevent crashes) and is the prerequisite that makes the eventual scene/menu protocol (§1, §11.2 Phase 8) safe. Do it before Lux extraction (§7) where the two overlap only in GlobAux.cs.

Effort: M–L. The abstraction move is M; the per-safeguard extraction across ~10 fat globs (back-gauge crash, robot IK/overtravel, arm/deposit clamps, regrip legality, trim pose) is the bulk and is L, because each needs a domain method + test and careful behavior-preservation. The ~120 literal numeric ranges are individually trivial but numerous.

Residual risk / method: the (U)/(D) split and the citations above come from a targeted grep sweep of Src/UI/**/*Glob*/*UI.cs (class …:Glob, GetUI, setter bodies, Clamp/Crash/Overtravel/Enable/ Err*/Warn*/SetRange/CheckTracking). As in §12 these are reliable lower bounds — a full audit of all 87 subclasses will surface more (U) cases. Also note the name "Glob" is overloaded: API/Bend/Glob.cs and a Core static Glob refer to bend-grouping, unrelated to the property-editor Glob analyzed here — don't conflate them during the move.
