CRAAssessmentFlux

product: flux org: metamation tags: [metamation, knowledge-base, flux, cra, security, assessment] type: assessment project: Flux source: Flux/CRA (PROSEC "Support Guide for the Quick Assessment") updated: 2026-07-06

CRA / IEC 62443 Quick Assessment — Flux CAD/CAM

Component: Flux (metamation/Flux) — Windows desktop sheet-metal CAD/CAM application Version assessed: 2026.07.665.1 "Veles" (source tree at X:\) Assessment basis: IEC 62443-4-2 component requirements, per TRUMPF "Support Guide for the Quick Assessment" (v0.22) Scope decision: Crosses a trust boundary → 24-section ("with trust boundaries") assessment Date: 2026-07-06 Status: Code-evidence analysis intended to seed the official Component_QuickAssessment.xlsx — not a substitute for it. See §2 for method & limitations.

1. Executive summary

Flux is a Windows desktop CAD/CAM application (.NET 10, WPF + WinForms, plus a C++/CLI HOOPS wrapper) that imports CAD, assigns bend/fold/laser/punch/trim technology, nests parts, and generates machine NC code. It ships in many flavors from a single code base, including TRUMPF-branded TecZone Bend/Laser, their Boost integrations, and ShopFloor/HMI builds that install on the machine control PC.

Estimated conformity (adversarially verified)

Foundational Requirement Applicable Fulfillment
FR1 — Identification & Authentication Control Yes (partial; Windows-delegated) 0.30
FR2 — Use Control Yes 0.10
FR3 — System Integrity Yes 0.25
FR4 — Data Confidentiality Yes 0.20
FR5 — Restricted Data Flow Yes 0.20
FR6 — Timely Response to Events Yes 0.10
FR7 — Resource Availability Yes 0.30

Estimated overall Conformity ≈ 21 % of applicable sections. Estimated Applicability ≈ 70–80 % (wireless, PKI, physical-tamper, boot/roots-of-trust, emergency-power sections are N/A for a user-mode desktop app). Exact Applicability % / Conformity % are produced by the XLSX from per-section 0/1 entries — see §9.

🔴 Release-blocking candidates under the CRA

The guide states that shipping a known exploitable vulnerability voids the machine's CE conformity. The following qualify:

  1. Two unauthenticated arbitrary-code-execution paths.
    • -script <file> reads a file and runs it through a full-trust, unsandboxed Roslyn C# engine (ScriptOptions.Default, #r/#load supported) — Src/App/App.xaml.cs:244-250, Src/Core/Classes.cs:197-208,251-264. Reachable directly (Flux.exe -script evil.csx) and by injecting args over the single-instance named pipe, which is created with no PipeSecurity/ACL (Src/UI/Misc/UI.cs:410-426) — any process in the same interactive session can drive it.
    • The Bricks plugin auto-loader does Assembly.LoadFrom on every DLL in a Plugins folder at startup, with no signature/integrity/allow-list check — Src/API/Bricks.cs:21-40, invoked at Src/App/App.xaml.cs:202. Classic DLL-plant / uncontrolled-mobile-code vector.
  2. Remote-controlled download written to disk with no integrity check. GripperTool fetches URLs taken verbatim from a service's JSON response and File.WriteAllBytes them with no signature/hash, no scheme/host allow-list, no size cap, and no timeout on the download client — Src/Core/BCell/GripperTool.cs:113-134. Spoof/MITM ⇒ arbitrary content to disk (+ SSRF + memory-exhaustion).
  3. End-of-life / unmaintained shipped components (flavor-dependent, see §5/§7): Ionic.Zip.Reduced.dll = DotNetZip 1.9.1.8 (abandoned, known path-traversal CVEs); and for Boost/ShopFloor flavors, VC++ 2005/2010/2013 redistributables (all past end-of-support). This is exactly the class DependencyTrack must gate.

🟠 Systemic weaknesses

  • Cleartext HTTP for every data-bearing / credentialed flow (only two data-less HEAD probes use TLS).
  • Weak secret handling: shared cred.bin (base64 + reverse "obfuscation"), TA.ini cleartext creds, embedded XOR-obfuscated RSA key + SHA-1 signing (DelemSign), new Random() license nonce (Permit.cs:572), static IV/salt + trivial KDF (TouchpointInit), AES-CBC without a MAC.
  • Installer weakens ACLs: grants Users:(OI)(CI)F on the entire data tree (Flux.iss:223) and elevates during install.
  • No security audit logging / monitoring (FR6): no Windows Event Log, no logging framework; diagnostic logging is gated behind a Developer license and inert on customer machines.
  • License entitlement is not a security control and is trivially bypassable via environment variables (Permit.cs:360-398).

2. Assessment method & limitations

  • Method: A multi-agent static analysis over the X:\ source tree — 8 product-summary recon dimensions, a trust-boundary determination, and all 7 Foundational Requirements each assessed and then adversarially verified against the actual code, with file:line citations. The guide's no-confabulation rule was enforced (every claim must be backed by code).
  • Scores are code-evidence estimates to seed the official XLSX, not the official CRA scores. They reflect the source in this working tree today.
  • Runtime-only facts not visible in source may shift specifics: the production value of GripperToolConnection, the LTT AuthenticationCode, and the loopback agents' onward transport to TRUMPF.
  • Flavor scope: findings below apply to all TRUMPF flavors unless noted; §5 breaks down what actually ships per flavor.
  • No git writes were made (per repo policy).

4. Trust-boundary determination → 24 sections

Decision: crosses a trust boundary (confidence: high). Per the guide, any outbound data push (even to TRUMPF via a separate channel) counts.

Channel Destination Data Evidence
HTTP(S) POST (multipart) user-configurable GripperToolConnection (any host; no https enforcement) customer part GEO geometry + machine/tool/robot config GripperTool.cs:94-103, 322-351
HTTP GET → disk server-supplied URL (remote-controlled) .geo / .zip, File.WriteAllBytes GripperTool.cs:113-134
HTTPS HEAD contexthelp.api.trumpf.com, 2dlaserguide.trumpf.com component + version + language MenuCmds.cs:709-726, 793-802

Inbound is local-only IPC (no network listener) — irrelevant to the outbound-based boundary test, but the unauthenticated pipe and plugin loader are serious local findings (§6, FR1/FR2/FR3).

5. What is actually shipped per flavor (from the FShip ship project)

Build model: FShip.cs runs one dotnet publish -c Release and compiles one Inno installer. The flavor is chosen at install time from the setup EXE's filename (Flux.iss:305-319). Therefore the managed code is identical in every flavor — the flavor only changes data files, licensing DLLs, native post-processors, the flavor marker, and install paths. The shipped build is optimized, but binaries are unsigned and PDBs are shipped (Flux.iss:85-89).

Consequence: every code-level finding in this report (Roslyn scripting, plugin loader, gripper HTTP, analytics, all CAD parsers, weak crypto) is present in every TRUMPF flavor. The flavor system removes no attack surface.

⚠️ The legacy-dependency split

The installer's IsTrumpf predicate is only BEND or LASER (Flux.iss:344). The Check: not IsTrumpf gate therefore includes the Boost and ShopFloor variants:

  • TecZone Bend / Laser (standalone) get the lean set — they do not ship Cybelec, Trek/MetaCAM, VC++ 2005/2010/2013, or .NET FX 4.7.2.
  • Boost + ShopFloor/HMI flavors still ship the full legacy load: the Cybelec 32-bit COM server (regserver sharedfile uninsneveruninstall into {sys} — persists forever, never uninstalled), the Trek/MetaCAM native engine, VC++ 2005/2010/2013 (EOL), and .NET FX 4.7.2.

Headline: the "clean dependencies for TRUMPF" work only reached the two standalone products. The machine-embedded ShopFloor/HMI builds — the highest-risk deployment — still carry EOL runtimes and a permanent system-wide COM server. Confirm with the build owners whether this is intended or a side effect of the narrow IsTrumpf predicate.

6. Foundational Requirements assessment

FR1 — Identification & Authentication Control · 0.30

No in-app human auth (delegated to Windows — a legitimate compensating control for a machine-PC app; CR1.6 wireless, CR1.8/1.9 PKI, CR1.14 symmetric-key are N/A). Machine-to-service auth is weak/absent: analytics HTTP Basic over cleartext with a base64+reverse password (CmdProcess.cs:1906-1913, 2995-3000); LTT Bearer <AuthenticationCode> where AuthenticationCode is never assigned → empty token, endpoint effectively unauthenticated (LaserCore.cs:2215); gripper POST carries no client credential. The TLS positive is real but near-irrelevant (only two data-less HEADs). CR1.2 fails via the unauthenticated pipe/plugin → code execution. No system-use banner (CR1.12).

FR2 — Use Control · 0.10

  • CR2.1 Authorization: only license entitlement gating (EFeature/Permit.IsMCValid), no user RBAC, and the non-CodeMeter part is env-var-bypassable (Permit.cs:360-398). No re-auth for high-risk actions.
  • CR2.4 Mobile code: two unsandboxed full-trust vectors — Roslyn -script (Classes.cs:197-208, App.xaml.cs:244-250) and the Bricks plugin auto-loader (Bricks.cs:21-40, App.xaml.cs:202). Neither has signing, integrity, allow-list, or user confirmation.
  • CR2.5 Session lock: none (confirmed absent).
  • CR2.7 Concurrent sessions: incidental only (single-instance mutex + CodeMeter floating-seat cap).
  • CR2.8–2.12 Audit / timestamps / non-repudiation: absent — no audit subsystem; existing signing protects OEM/laser IP, not user actions.
  • CR2.13 Physical diagnostic interfaces: N/A.

FR3 — System Integrity · 0.25

Physical/boot CRs (3.11–3.14) N/A. Weak where it matters: gripper download has no signature/hash/allow-list (GripperTool.cs:113-134); no code-signing of binaries or installer and no signed-update verification; AES-CBC without a MAC and SHA-1 DelemSign (DelemSign.cs:57-64); installer weakens data-tree ACLs (Flux.iss:223); unsandboxed mobile code reachable via unauthenticated pipe/plugin (CR3.2/3.8 near-zero). Positives: structured FileParseException input validation, fail-safe loaders, global unhandled-exception handlers, and no TLS-validation bypass anywhere (verified). Watch: zip-extraction paths built from entry data without traversal canonicalization (Console/Commands.cs:684-698).

FR4 — Data Confidentiality · 0.20

Customer CAD/NC/job data persisted plaintext, no encryption-at-rest, no DPAPI. The only AES protects TRUMPF's laser-tech IP with a fixed embedded key (LaserCore.cs:2437). Confidential geometry egress (gripper) does not enforce TLS. Weak-crypto cluster: XOR-obfuscated embedded RSA key + SHA-1 (DelemSign.cs:62,73-78), non-cryptographic Random() challenge (Permit.cs:572), static IV/salt + trivial KDF (TouchpointInit.cs:53-80). CR4.2: temp files with customer data not purged (PartEditAgent.cs:171-172, BCellImport.cs:188-189).

FR5 — Restricted Data Flow · 0.20

No egress restriction/allow-list; GripperToolConnection is an unconstrained free-string setting (Settings.cs:204) — arbitrary destination, no scheme validation, cleartext possible. Download destination fully server-controlled with no allow-list or integrity check. Multiple independent endpoints, no central enable/disable and no data-flow logging. Sensitive fields (part ID, license serial) ride the analytics channel off-box.

FR6 — Timely Response to Events · 0.10

No security audit logging and no operator-accessible log/monitoring. No Windows Event Log / EventSource / logging framework (verified). Diagnostic Debug.* is hard-gated behind the Developer license → inert on customer machines (Debug.cs:178-243,314). User-facing FX.Out is transient/in-memory. Telemetry is off-by-default, cleartext, vendor-bound (not asset-owner-accessible), and fails silently (mError, no retry/alert). A _recentCrashLog.txt exists (PartAux.cs:794) but is single-overwrite, untimestamped, and world-writable — reinforcing the gap. A gripper 401 is only a transient UI message (GripperTool.cs:101).

FR7 — Resource Availability · 0.30

Real but narrow positives: global regex timeout (App.xaml.cs:37), a 30s timeout on the gripper POST only, background-exec with cancellation (Base.cs:267). Gaps: the gripper download path has no timeout and no size cap (memory-exhaustion, GripperTool.cs:122-134); unsandboxed Roslyn = unbounded CPU/mem/threads; no autosave/crash-recovery for parts/jobs (only a single-level editor .bak); no in-repo component inventory/SBOM (CR7.8 — but see §7: an external pipeline covers this). Emergency power (CR7.5) N/A.

7. SBOM & vulnerability posture

SBOM recommendations (guide-aligned)

  1. Make the SBOM flavor-aware (or state which flavor is assessed) — the shipped component set differs materially between TecZone Bend/Laser and Boost/ShopFloor.
  2. Maintain a manual CycloneDX fragment for native/commercial libs that .NET scanners miss (HOOPS, tbs_x64, Cybelec, Trek/MetaCAM, Wibu) and merge it into the pipeline SBOM; ensure CPE/PURL identifiers so DependencyTrack surfaces vendor advisories.
  3. Treat as explicit release-blocking watch items: DotNetZip 1.9.1.8 (all flavors) and VC++ 2005/2010/2013 (Boost/ShopFloor). A known-exploitable finding here voids CE conformity.

8. Prioritized measures

🔴 High — before release

  1. Lock down both mobile-code vectors. For -script: gate behind the Script permit + explicit user confirmation, restrict ScriptOptions (disable #r/#load), run in a least-privilege AssemblyLoadContext, or require Authenticode-signed scripts. For the plugin loader: require signed plugin DLLs (or a TRUMPF allow-list/hash manifest), verify before Assembly.LoadFrom. (enabler: TRUMPF code-signing / plugin allow-list service) — Classes.cs:197-264, App.xaml.cs:202,244-250, Bricks.cs:21-40
  2. Harden local IPC. Create the single-instance pipe with a PipeSecurity ACL restricted to the current-user SID; whitelist the marshalled verbs; never execute code from pipe args. (enabler: System.IO.Pipes PipeSecurity) — UI.cs:410-426
  3. Verify downloaded content. Require a signature/SHA-256 per gripper package; enforce https-only + host allow-list + size cap + timeout before File.WriteAllBytes. — GripperTool.cs:113-134
  4. Code-sign all binaries + installer and verify at launch/update. (enabler: central signing pipeline in FShip)
  5. Enforce TLS on all data-bearing flows; reject cleartext to non-loopback gripper hosts.
  6. DependencyTrack gate on the Azure DevOps SBOM, with DotNetZip and the EOL VC++ redists explicitly tracked; retire DotNetZip for a maintained zip library.

🟠 Medium

  1. Replace ad-hoc secret handling with DPAPI / Windows Credential Manager (cred.bin, TA.ini); resolve or remove the dead LTT Bearer token.
  2. Tighten installer ACLs — drop the blanket Users:(OI)(CI)F on the data tree; grant minimal Modify only where required (Flux.iss:223).
  3. Modernize crypto: AES-GCM instead of AES-CBC; SHA-256 instead of SHA-1 (DelemSign); a real KDF + random IV/salt (TouchpointInit); RandomNumberGenerator instead of Random() for the license nonce.
  4. Security audit logging → Windows Event Log / EventSource (SIEM-forwardable) for app start/stop, config/machine-DB changes, license & service auth failures, outbound exports, and mobile-code load/execution; make the crash log append-only, timestamped, ACL-protected.
  5. Add schema validation + defined-state error handling around service JSON; stop swallowing integrity-relevant errors in empty catches.
  6. Trim legacy dependencies from Boost/ShopFloor (or confirm they are required): EOL VC++ redists, the persistent Cybelec COM server, .NET FX 4.7.2 — reconsider the IsTrumpf packaging predicate.

🟡 Low

  1. Cert pinning + min-TLS / revocation on the fixed *.trumpf.com endpoints (keep default validation — never add an accept-all callback).
  2. Optional system-use / legal banner for HMI/ShopFloor installs (CR1.12).
  3. Periodic autosave / crash-recovery for parts/jobs; canonicalize zip-extraction paths (zip-slip).
  4. Stop shipping PDBs to customers; document that human I&A is intentionally Windows-delegated.
  5. Add a configurable UI inactivity lock (CR2.5).
