Flux Assemblies

The picture below1 shows the various components of Flux, and their dependencies.

  • The ellipses are Flux DLLs, and their names are of the form Flux.Core.dll, Flux.UI.dll etc.
  • The rectangles are Flux executables, and their names are of the form Flux.Test.exe, Flux.exe etc. (Flux.exe is the final Flux executable - this what end-users will run).
  • Other nodes in this graph are components above and below Flux.

Here's a brief explanation of each of these components.

Component Meaning
Core This is essentially the Flux Engine - it contains everything in Flux except the user-interface to manipulate Flux objects using keyboard and mouse. If you use the Model-View-Controller paradigm, Flux.Core contains the models and the views. In other words, it contains a lot of 'model' classes such as E3Plane, E2Spline, LaserCut etc. And it also contains their corresponding views, such as E3PlaneVM, E2SplineVM and LaserCutVM.

The views know how to render themselves using OpenGL (though this rendering happens through a small set of entry-points, and it should be possible in the future to switch to another rendering system fairly easily).

A key question is whether these VM classes (all derived from VModel) belong here, or should be in another layer. That was the earlier architecture, but it provided difficult for several reasons. The key one is this: Flux is not a typical 'business' application, where there are 'business objects' (model), and a 'presentation layer' (view). The objects in Flux are CAD and CAM objects that are more tightly coupled to their visual representation.

Thus, while it is possible for a payroll processing application to perform all operations with no concern for 'views' at all, it is not really the case with Flux. Every a basic operation like generating NC code requires that we be able to render 2D or 3D views of the part/model for inclusion in the NC code. Rendering a bend setup sheet (definitely a Core operation) requires rendering thumbnails or even 3D-PDF data of the bend models.

The earlier separation between Core and UI (with UI being at a higher layer than Core) meant that a simple call like BendTech.GenerateCode was internally quite hairy. We had to use some artificial, inelegant and type-unsafe mechanisms (like the Hub whiteboard) to connect Core with components 'upstream' to complete these tasks. Core was even unable to save a Flux-native file (FX) file without these hacks, since the thumbnail that is part of the FX file had to be rendered by some layer above.

So: modularity is all very well and good, but we have now gone full circle - we tried modularity and we have to back off a bit, and head towards a more monolithic architecture.
UI Continuing the MVC paradigm, this contains the 'controllers' for Flux objects. You will find here objects like E3PlaneGlob, E2SplineGlob and LaserCutGlob (all derived from the Glob class) that implement the operations possible on these objects.

Globs expose properties that can be viewed and edited, and also expose operations that can be peformed on these objects. The Glob system has good methods for making 'composite globs' when multiple objects are selected. The Glob properties and opeartions are expressed in terms of objects derived from GElement, and these get translated into actual working UI by some classes such as PanelMaker which convert these abstract GElements into WPF controls. (It is fairly straightforward to implement a different UI rendering layer, replacing WPF with HTML or some other mechanism).

In addition to the Glob hierarchy, the UI layer also implements a lot of WPF dialogs and windows (like TurretEditor, SheafEditor, LaserDBEditor etc).
App Flux.App is a thin layer that implements the main-window for Flux, and manages some global UI required for selection-state, Glob-panel creation, undo state management etc. It also maintains the concept of multiple Flux documents and a tabbed editor for switching between them. Flux.App is fairly small compared with Flux.Core and Flux.UI. In a typical end-user installation of Flux, Flux.exe is the only file that contains code; Flux.Core.dll and Flux.UI.dll are packed as resources inside Flux.exe and the end-user never sees them.
API This DLL is a thin wrapper around Core that provides sequestered access to Flux classes. For several classes in Flux, we provide wrapper classes at this layer that provide a sub-set of functionality. 3rd party tools (like automation tools etc) should be implemented using this layer. When we ship Flux.API.dll to a 3rd party, the other dependencies (like Core) are bundled inside and are not visible or available for them to use directly.
Migrate Flux.Migrate is a command-line application that is used to migrate configuration information from MetaCAM and other legacy systems (notably TOPS). It will include commands to convert a bend-tool library from TOPS format to Flux format, or to import a punch-machine definition from MetaCAM. This tool is expected to be used by system integrators and Metamation support staff; it is not designed for end-user use.
Console Flux.Console is a command-line application that is meant for use by Flux developers. It provides support for 'system' level operations like re-building Flux metadata and several other utilities. This is for use within Metamation.
Test Flux.Test.exe is the set of test suites for Flux. This is a console-mode test runner, as well as a set of test suites. There is also a GUI-based test runner that provides test-coverage functionality as well.

Flux Code Repositories

In my development computer, the X:\ drive is a substituted drive that stores everything related to Flux

X: => C:\Work\Flux

You could use any other mechanism, but the discussion below assumes that you are using an identical layout to this. If you change these paths, you might have to slightly tweak project files. These 3 drives are populated from the following repositories: Note: In the table that follows, substitute root with https://metamation.kilnhg.com/Code/Flux.

Repository Components Clone to
root/Code/Src2 Core, UI, App, API, Console, Migrate X:\Src
root/Test/Test Test X:\Test
root/Test/TData Test data X:\TData
root/Data/Doc Flux release notes X:\Doc
root/Data/Data Runtime Data (machines, tools) X:\Data
root/Data/Resources Resources (like fonts) X:\Resources
root/Code/Tools Tools for Flux X:\Tools
root/Data/Wad Files that go into the wadfile X:\Wad
root/Data/Help Source files for the Flux user-manual X:\Help
root/Data/Notes Source files for Flux tech-notes X:\Notes

When you compile, all binaries (including the test system binaries) build into X:\Src\bin

The Flux.Hula library

There are two project files in the U:\Hula folder - Hula64.sln and Hula32.sln. These are managed code wrappers around the Hoops3 library. We need two because Hoops library exists in different 32-bit and 64-bit variants. Building these generates U:\bin\Flux.Hula64.dll and U:\bin\Flux.Hula32.dll. Then, only Flux.Hula64.dll is actually referenced within Flux.

Note: Do not attempt to build either Hula64 or Hula32; neither of them will build correctly. Instead, simply use the pre-built Hoops components:

  • Copy Flux.Hula32.dll and Flux.Hula64.dll from X:\Resources\Hoops to X:\Src\bin\hoops
  • Copy the 31 DLLs from X:\Resources\Hoops\win32 to X:\Src\bin\hoops\win32
  • Copy the 31 DLLs from X:\Resources\Hoops\win64 to X:\Src\bin\hoops\win64

Why are there two separate wrappers for Hoops?

The problem is this: Flux.Core, Flux.UI and Flux.App are all built using the Any CPU model. This means that we make generic IL code that can be finally converted to 32-bit or 64-bit native code on the customers machine. This is very nice and convenient and saves us the trouble of shipping separate 32-bit and 64-bit versions of Flux. However, when we have to use a managed library (like Hoops) that exists in two different flavors, this model does not work so cleanly.

The Solution: We build Flux.Hula64.dll and Flux.Hula32.dll. Both of these get compressed and converted into resources that are stored inside U:\App\Res (they are called H32 and H64). When we ship Flux, we don't actually ship either of these DLLs; they are deleted. When Flux loads and tries to use these, an Assembly-load-failure happens. We handle this exception and provide the assembly loader with the appropriate 32-bit or 64-bit version of the Hula DLL (which then connects to the correct version of Hoops and works with that).

Developer machines: On developer machines (which are all 64-bit), we need only Flux.Hula64.dll, and Flux.Core also has a dependency only Flux.Hula64.dll. The compiler will crib when we are building Flux.core (the crib is this: Flux.Core is built for Any CPU, but it uses a DLL (Flux.Hula64) that will run only on 64-bit computers). The compiler (rightly) thinks that this is dangerous since it will fail on 32-bit computers. It is correct, but it does not know of the solution we have taken (of supplying the loader with either the 32-bit or 64-bit version of the DLL depending on whether Flux is running as a 32-bit or 64-bit process). So, ignore this compilation warning.

Running Flux: On 64-bit development machines, nothing special has to be done - Flux will run correctly automatically, since Flux.Core will look for Flux.Hula64.dll and will find it in the U:\Bin folder and everything will just work. If you try running this on a 32-bit computer, things will fail. Flux.Core (now running in 32-bit mode) will attempt to load Flux.Hula64.dll, and that load operation will fail since the target architecture is mismatched. The assembly loader will shut down the application after displaying this error. To get things to work, just delete Flux.Hula64.dll from U:\Bin. Now, there will be an assembly load failure, Flux.Core will handle that, and provide the correct 32-bit version of the DLL to the assembly loader system. Everything will be fine. (This is always the situation on end-user machines, since we don't install the Flux.Hula32.dll or Flux.Hula64.dll, and always depend on this assembly-load-failure event to be generated)4.

Installing runtime libraries

There are various Microsoft runtime libraries required for Flux and its components to work. These include the VC++ 2008 runtime library, VC++ 2013 runtime library and the .Net Framework 4.6.1. The simplest way to ensure all these are installed is to run the FluxPreSetup.2017.A.exe installer from this location.

If you have these components already installed, this setup will finish very quickly. Else, it may take a few minutes to complete. If you don't run this setup program, Flux will not work (since it depends on this setup program making an annotation in the registry stating that FluxPreSetup 2016A is complete).

Environment variables for Flux

Some environment variables need to be set (at least on developer computers) for Flux to work

FLUXDATA = X:\Data
FLUXTESTDATA = X:\TDATA
FLUXDEVELOPER = 1
FLUXWAD = X:\Wad

Compiling Flux

Flux uses the C#6 dialect, which means that you need Visual Studio 2015 to compile it. Some of us are using the Visual Studio 2016 Pro compiler already. Others can download and install the Visual C# 2015 Express compiler to compile Flux. If you find this compiler is not powerful enough for your needs, let me know, and I can upgrade your compiler to Visual C# 2015 Professional.

Important Note: Do NOT download or use the Visual C# 2015 Community compiler. This is expressly forbidden for use in a company the size of Metamation. This compiler should never be installed in any of the computers you are using.

The Flux.wad file

There are many 'read-only' files that Flux needs to run. Examples are the stdshaders.txt file that contains the source code for the OpenGL shaders we use, and the metadata.curl file that contains the Au format metadata for all Flux types. These files can be picked up in one of two ways:

  1. If the FLUXWAD environment variable is set, this variable is expected to point to a Wad folder, and all the wad files are picked up from sub-folders of that. On development machines, just set FLUXWAD to point to X:\Wad and you should be fine.
  2. On deployment installations, the contents of the Wad folder are zipped into a standard Zipfile, called Flux.wad. This file should be copied into the same location where Flux.exe is installed. (The Flux setup program does this).

Note that the FLUXWAD environment variable takes precedence; if it is set, the Flux.wad file is not used.

Flux Data Folder

The X:\Data folder contains all the run-time data required for Flux to work. These are some of the important sub-folders inside Data:

BendTools

This folder contains all the bend-tool catalogues. Each catalogue is in a sub-folder of this folder, with a name made up of just the ID of that catalogue. Each bend-tool catalogue is just a single Curl file, so the entire Trumpf bend-tool catalogue would be found in U:\Data\BendTools\1\BendTools.curl, for example.

PunchTools

This folder contains the punch-tool catalogues, one stored in each sub-folder.

Machine

This folder contains all the machine definitions. Each machine-definition is found in a sub-folder whose name is the same as the integer ID of the machine. Within that sub-folder, there may be several files, depending on the type of machine. Here are some examples:

File Meaning
Machine.curl Contains the Machine object, stored in Curl format. This file must be present for all machines.
Machine.mech A mechanism file that provides a 3-D model of the machine, in an animatable format. This is necessary for any machines that have a 3D model (a 5-axis machine, a bend-machine etc).
Post.hx The post-processor for this machine (if this machine has a Hex5 post-processor)
Post.pdl The post-processor for this machine (if it uses a standard PDL post-processor)
Model* The Machine.mech mechanism file typically refers to multiple IGES files to define the component pieces of the machine. These IGES files are stored in the Model sub-directory.

The Trek program and associated tools

Flux has to interact with legacy MetaCAM data. In particular, this means that we will need to be able to read PDG and 3D files, and we would like to be able to use MetaCAM posts and code finishers. We also would like to use various bend post-processors (like IBC-Accur, IBC-Safan etc). However, we don't want a dependency on MetaCAM being installed, nor can we assume that a Flux customer will also be a MetaCAM customer.

So, Flux will ship with its own private version of MetaCAM and associated tools (like code finishers). There is a branched copy of the MetaCAM repository for this purpose, and we call this modified (command-line only) version of MetaCAM as Trek.exe. You will have to clone the Trek repositories and build that to get a Trek.exe for some Flux functionality to work correctly.

  1. Fetch the Trek repository from https://metamation.kilnhg.com/Code/Internal/MCAM/Trek, and put it into the W:\Trek location on your hard disk.
  2. Subst the N:\ drive to this location, so N:\ = W:\Trek. Then, build these projects:
    • N:\lego\vc\lego.sln
    • N:\assist\vc\assist.sln
    • N:\metacam\vc\metacam.sln
    • N:\metacam\res\vc\resources.sln
  3. Set the environment variable TREKPATH to point to the location of Trek.exe. So, you should set TREKPATH=N:\Bin
  4. There will be additional sln files getting added into N:\ (for example, code finishers, IBC translators etc). Find these SLN files and build them as well. All binaries will go into N:\Bin

With all these set, Flux now knows where Trek is, and can use the Trek.exe and associated tools to perform various tasks.
