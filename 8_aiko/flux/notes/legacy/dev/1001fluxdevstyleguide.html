1001 ◉ Flux Development Style Guide

[!info]- Revision history

Rev Date Author Note
V1 2013-11-10 AV

This document explains the style guidelines for Flux development. It covers the code formatting style, naming conventions and commenting conventions for Flux code, as well as the formatting style-sheets for Flux tech-notes.

Code Formatting

Tabs

Use spaces instead of Tab characters in source files. Set the indent level as 3 spaces. (2 is too narrow, 4 is too wide, 3 is the Goldilocks number).

Indentation & Newlines

We generally use the K&R style (which is close to the 1TBS (or One True Brace Style)), but dispenses with braces where there is only one statement. That is:

if (nLevel > 0 && !mLevelStack.IsEmpty)
   PopLevel ();

rather than:

if (nLevel > 0 && !mLevelStack.IsEmpty) {
   PopLevel ();
}

However, this is discretionary; if you think the braces clarify the meaning, add them. This is how the Indentation settings look:

A key point with these brace styles it that we try to reduce the number of lines code occupies. Thus, the New Lines section of the Visual Studio editor is configured by turning all the new line check-boxes off:

Continuing the 'brevity of lines' theme, the Wrapping settings are configured thus:

Spacing

The spacing rules to follow are:

  • Space before open parenthesis or braces ( {
  • No space before a square bracket [
  • No space between the parenthesis for an empty pair ()
  • No space after an open parenthesis or before a close parenthesis (x + 2)
  • Space before and after the ternary operator symbols ? :

File & Class Headers

Insert something like the following header at the start of every file:

// ---------------------------------------------------------------------------------------
// Flux ~ Sheet metal CAD/CAM system
// Copyright (c) Metamation India.                                                ===  --  
// ---------------------------------------------------------------------------      ==(  )
// Part.cs                                                                        ===  --
// Implements the Part class, which is the generic unit of processing in
// Flux. A part may be a flat-sheet part, a bending part, a 5-axis laser part,
// a welding part (or many of these at the same time).
// ---------------------------------------------------------------------------------------

This header is from Flux.Core.dll, the other DLLs have a slightly different first line.

Each top-level class in a file has a header like this, where the divider extends to column 100 (with the region open). The region header contains just two words like class Something or interface AnotherThing or enum YetAnother:

namespace Flux {
   #region class Part ------------------------------------------------------------------------------
   /// <summary>Summary for class Part</summary>
   /// More detailed documentation for class Part (a few lines, to a page or two even)
   public class Part {
      … many lines …
   }
   #endregion
}

The class itself is divided into several segments and each segment has a header like this, extending to column 70:

   public class Part {
      #region Properties ---------------------------------------------
      … properties …
      #endregion

      #region Methods ------------------------------------------------
      … methods …
      #endregion     
   }

The section below explains the possible segments in a class

Class Segments

The members of a class are organized into one or more segments. The order in which these segments are listed below is the preferred ordering of segments, and we explain here what should go into each segment.

Constructors

Public1 or protected constructors go here; private constructors go into the Implementation section. Static constructors should be private, and therefore should be in the implementation section. If there are static factory methods that create objects, then those should appear here in the Constructors section. For example:

   class Pline {
      #region Constructors -------------------------------------------
      /// <summary>Construct a Circle polyline, given the center and radius</summary>
      static Pline MakeCircle (Point2 center, double radius) {
         … code …
      }
      #endregion
   }

Note that this appears in the constructors section only if this is static, and the return type is the enclosing class itself. In other words, it is effectively a constructor. The constructors are ordered in increasing complexity of parameter lists2.

Properties

The properties section lists all public properties, fields and events. We don't distinguish between public properties and public fields, and where there is no particular need to use a property, we would recommend using a field instead. For example, consider this class:

class Point2 {
   public double X {
      get { return mX; } 
      set { mX = value; } 
   }
   double mX;

   public double Y { 
      get { return mY; } 
      set { mY = value; } 
   }
   double mY;
}

This could safely be replaced by this:

class Point2 {
   public double X;
   public double Y;
}

If, for some reason, we find it necessary to make X and Y properties (maybe we want to enforce some kind of range checking, or fire a property-changed event), this entails re-compilation of all the downstream code using Point2. That's OK; we have the luxury of enforcing such re-compilation.

Properties are ordered alphabetically.

Methods

This lists all the public or protected methods of the type. Private methods go into the implementation section.

Overrides are treated in a special manner. If the root method of an override is part of Flux, then the method belongs here. For example, GridPunch.GenCode() method is listed here (since it implements ToolingItem.GenCode(), which is declared in Flux). On the other hand, GridPunch.ToString() method appears in the implementation section, since it overrides the Object.ToString() method, which is declared outside Flux.

In some situations (as in implementing containers, or in WPF controls) one overrides a number of methods from a particular base class or interface. When doing this, it is a good idea to have a separate section titled something like UserControl implementation or IList implementation. Don't do this if there are just one or two methods being overridden.

Methods appear in alphabetical order; methods with the same name are sorted in increasing order of parameter complexity.

Operators

This lists all public or protected type conversion operators, binary and unary operators. Private operators are moved into the implementation section3.

Implementation

This list all the private methods, as well as the overrides that got shunted here from the methods section.

Nested types

This lists all the nested types (including enumerations) that are declared within this class. Public types first, private types next. Types are listed in alphabetical order.

Private data

This lists private fields and properties. All instance fields come first, followed by all static fields. Within these sections they are listed in alphabetical order. There are some exceptions, as noted below.

A field or private property that is used only in one method (for example, some kind of cache) can be placed immediately after that method:

      public Rect2 GetBound () {
         if (mBound.IsEmpty) { … compute bound … }
         return mBound;
      }
      Rect2 mBound;  // Place this here, rather than in the private data section

A field that is used as a backing field for a property is placed immediately after that property:

      public double Area {
         get { return mArea; }
         set { mArea = value; PropertyChanged.Fire ("Area"); } 
      }
      double mArea;  // Place this here, rather than in the Private data section

Follow this rule in general. Extending this, one could infer that static data that is used only in one static constructor should appear immediately after that static constructor.

Naming Conventions

Class names: PlineIntersector
Methods: GetExtendedBounds (…)
Public fields & properties: MinHeight
Private instance fields & properties: mExtending
Private static fields and properties: sCharMap
Enumeration types: EClampType, ECorner, ECharacterSet
Interface types: IDisplayDevice, ICurlable, IFormattable

Use an m prefix for instance fields, and an s prefix for static fields, but no other type-specific (Hungarian) prefixes4.

Flux Technotes

This particular document defines the standard template for Flux technotes. Use these fonts and styles everywhere. It may be necessary to install these fonts; they are available in the Flux/Resources repository. The fonts we use are these:

Quattrocento Sans

Used for all body text. This is a very beautiful and light font somewhat reminiscent of Optima, but with an even more subtle taper to the verticals. The font has a slightly fat feel, somewhat reminiscent of Verdana, without being so over-the top. We also like the rather tight line and character spacing; this helps keep our documentation sufficiently dense. (Credit: Pablo Impallari).

Dosis

Used for headings and titles. This is a very informal looking rounded sans-serif font. We choose this because it goes well with Quattrocento, being sufficiently different to set headings apart. Also, the font is a 'narrow' font meaning we can set fairly long headings in large type without running out of room. The font also looks very good in colors other than black, which we will use for headings. (Credit: Pablo Impallari – now you know why it works well with Quattrocento Sans)

Ubuntu Mono

Code is typeset in Ubuntu Mono, a clean and simple sans-serif monospaced font that goes well with Dosis. The simplified letters (see u and n above) make code very legible even at small point sizes, while there is no confusion between 0 and O with Ubunto mono.
