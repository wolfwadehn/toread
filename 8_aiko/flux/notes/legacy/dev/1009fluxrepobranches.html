1009 ◉ Flux Repository Branches

[!info]- Revision history

Rev Date Author Note
V1 2017-04-02 AV

Branches in Flux repositories

Flux is a live, shipping product and contributing to Flux source code comes with serious responsibilities. Read this section carefully, and discuss with me if you have any doubts1. Here are the goals we have for managing the Flux source code:

  • The code in the repository is generally 'good to go', and we should be able to create an installer at any time. This means that more obvious pre-requisites are met - the code you check out from the repository will always be able to compile and will always pass 100% of the tests.
  • It should be possible for others to tinker around with the Flux code without disturbing the shipping version of Flux.
  • We should not be spending too much time maintaining multiple versions of the code and shifting fixes and patches between them.

After a lot of analysis, and weighing multiple options, a set of guidelines are now in place about how this development should go forward.

Per-developer branches

The Flux code will use one branch2 per developer. I will pull rank and use the default branch for my work, while every other developer will use a branch named after him or her. Branch names should be single words, and should be in lowercase (to maintain consistency with 'default'). Thus, branch names could be like bilbo or gandalf.

The default and release branch

In addition to the per-developer branches, you will notice the default and release branches in the Flux repositories. The default branch is where most of the development work is staged. I will be pulling from various per-developer branches into this branch at frequent intervals, and that is how new features will be getting added to the development build. In addition, I will often be using this as a code-writing branch for my use (keeping the arvind branch for more dangerous experiments).

We ship many builds to our partners (Trumpf, USMM, FAS), but only a few of those are meant as customer facing builds. These builds will have version names like TecZoneBend 2017.3 etc (rather than names like Flux 199). Let us call these customer-facing builds as release builds, and these builds are issued from this branch. Example: Build 200, on April 1 2017, was deemed to be a release candidate for TecZone Bend 2017.3. I cloned all the repositories at that point from the default to the release branch, and issued the release from there. Technically, the assembly-version for that build was 2017.3.200.1, and subsequent rapid development continues on the default line (with Flux 201).

It is possible that a few weeks hence, it may be necessary to issue some service pack for 2017.3, and to do that I will switch to the release branch and work there, making the fixes, and will then ship a new build from those changes. On the release branch, the build number will never be bumped up, so the assembly version will be 2017.3.200.2 (and we will call that TecZone Bend 2017.3.2).

Eventually (2 or 3 months later), we may have TecZone Bend 2017.4, and that will then be done by doing a fresh merge from the default to the release branches, and issuing, for example, 2017.4.225.1 from that branch.

FAQ

Q: How do I create a branch?
A: Short answer: Ask me to create your branch! Long answer: Use hg branch to create a branch. The first time you push this into the Kiln repository, you will need a special new-branch parameter to the push3:

hg branch brahma                               _create new branch 'brahma'_
_... make code changes ..._
hg commit -m "Working on laser unloader"
hg push -b . --new-branch                      _force creation of new branch on server repo as well_

This is only the first time you push your code to the repository. Subsequently, you will do this:

hg update brahma                               _switch to your branch_
... make code changes ...
hg commit -m "Working on punch code"               
hg push -b .                                   _push ONLY YOUR BRANCH to the repository_

Q: What's that -b paramter to the hg push?
A: The -b . parameter to push tells it to push only one branch (the . is a special way to indicate the 'current branch'). In general, you should push only changes you make in your branch. If you follow the more general rule that you don't make commits into any other branch, this is moot - there will not be any changes in any other branches when you are doing a push. The -b . is just a safety check to ensure you don't write into any other branches.

Q: What if I need multiple branches to maintain different threads of my work?
A: You're out of luck. You get one branch to represent all your work. If you are the type that needs to have multiple parallel states of development, we suggest you look at mercurial queues to handle this (Enable the mq4 extension, and then look through the documentation for qpush, qpop, qrestore, qcommit etc).

Q: Can I pull changes from the default branch into my branch?
A: Yes, you should do this, and often. The default branch changes rapidly and if you don't pull changes regularly from the default branch, you will have a nightmare when you finally try to merge your code in. You pull changes from the default branch into your branch using:

hg merge default

Q: How do I push changes from my branch to the default branch?
A: You don't! When you have completed work on a feature or bug, and your code is ready to get merged into the main trunk, inform me. I will pull the code from your branch and merge it into the default. It is possible that the changes may be cherry-picked (some changes will be accepted, and some may get rejected). In general, if the code is not ready to be merged, it will be sent back to you for re-work before it gets merged in.

Before you send a request for your code to get up-merged into default, you should ensure that you merge the changes from the default branch into your branch. Do not push your changes to the server without doing this. If you do so, it will be immediately returned to you for rework.

Q: What about shipped revisions, hotfixes, patches etc? Are they also handled using special branches?
A: No. Mercurial tags are used to maintain references to shipped revisions, and occasionally hotfixes may be applied based on some older revision (rather than the tip). In general though, most development happens on the leading edge. Flux never strays too far from the 'shippable product' state at any time.

It is possible that some code in Flux is only for internal tests, and not for general shipment. Such code is usually protected from end-user exposure by INI switches or other DeveloperMode flags. (It is still shipped to the user).

Q: Why don't we use the Kiln branches instead?
A: What Kiln calls 'branches' are just clones of the repository. It is much more painful to 'cherry-pick' fixes from across repositories than it is across branches. We can use powerful mercurial commands like hg graft to move only selected change-sets between branches. If we use Kiln branches, these are then separate repositories, and it becomes more painful.

In addition, the Kiln branching system requires separate directory trees for each of the 'branches' on my local disk, and to bring everything in sync will require a lot more of pulls from the server. Kiln branches are a 'dumbed down' version of Mercurial branches. It looks like they were created since Mercurial branches are a bit more 'risky' (more easy to shoot yourself in the foot), but we are intrepid and reckless...

Summary of mercurial usage rules

  • Do not commit into any branch other than your own.
    Before doing a hg commit, you should ensure that you are on your branch, by just typing in hg branch to check the current branch. If you are on the wrong branch, use hg up to switch to the correct branch first. In general, you should never stray away from your branch; even if you temporarily switch to some other branch, switch back immediately to avoid any erroneous commit.
  • Do not merge into any branch other than your own.
    You should be in your branch, and you should then use a hg merge default to merge from the default branch into your own branch. You should never do a merge in the opposite direction (this follows from the previous rule, really, since such a merge would have to be followed by a commit into the default branch).
  • Push only your branch to the remote server, don't push all branches.
    Check you are in your branch, and then use the -b . option to push to ensure you are pushing only the current branch. If you follow the first two rules correctly, this is irrelevant, since you would not have made any changes to any other branches anyway.

The FhgHook tool

Inevitably, these rules will get forgotten one time, and you will end up committing code to the wrong branch. How do we ensure this does not happen? By using the concept of mercurial hooks and plugging in our own hook that checks before you merge, commit or push. Compile the code in X:\Tools\Tiny\FHGHook.cs and store the resulting executable somewhere in your path. Then, edit the .hg\hgrc file that you will find in each of the 8 Flux repositories on your hard disk and add the following lines:

[hooks]
pre-commit=FhgHook
pre-push=FhgHook
pre-merge=FhgHook

Then, set the environment variable FLUXREPOBRANCH to your assigned branch-name. This hook checks that the current hg branch is set to the same value as this environment variable. If it is not, it aborts the commit/push/merge operation. Also, when you are doing a push operation, it ensures you use the -b . flag. So, this program should hopefully ensure you never mess up the wrong branch of the repository.

Unfortunately, the hgrc file itself is not revision controlled, so we cannot just make these changes in the Kiln repository and have them propagate through; each user will have to make it in each of the Flux repositories on their computer.

Q: What if I forget to add the hooks into my .hg\hgrc file, and end up corrupting the default branch in spite of all these precautions?
A: You will be fired!
