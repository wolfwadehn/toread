PR #3645 — Case 48000: FlexCell: Overbending is missing when base plane is inside the machine

PR #3645 — Case 48000: FlexCell: Overbending is missing when base plane is inside the machine

  • Repo/PR: metamation/Flux #3645 · branch Case.48000 → main
  • Author: florian (EngertFlo) · Date reviewed: 2026-07-17
  • Size: +66 / −38, 11 files (net = 2 source files + 9 Fanuc goldens; 6 commits) · Label: bend
  • Verdict: ✅ Approve — no blockers, no correctness bugs. Fix is minimal, monotonic, and the golden regeneration is provably complete. Two follow-ups + one domain sign-off recommended before merge.

Reviewed with a deep manual pass plus a 6-agent adversarial verification workflow. All six agents (5 attack + completeness critic) returned CONFIRMED_CORRECT at high confidence.

What the PR does

Two coherent changes under Case 48000. Net diff is only 2 source files — commits 1 & 4 add-then-fully-revert an abandoned BendLie/pose-sheet-interpolation approach (BRobotPose.cs/BendTech.cs/ModelAux.cs), leaving zero residue.

1. Enable overbending for non-BendMaster when base plane is inside the machine — Src/Core/Bend/BendOp.cs, NeedsOverbending:

// The base-plane-inside check moved from applying to ALL robotic cells to BendMaster only:
if (cell.IsBendMaster) {
   // If the base plane is inside the machine, we are not adding overbending for BendMaster. Needs investigation.
   if ((Owner.Model.HandleCS.Org * ZeroPoseSheet.XfmToMC).Y > 0) return false;
   if (mRouting?.Bend is BRouting.EBend.NoSupport || RegripDuringBend) return false;
}
if (cell.Is6Axis && !cell.UsingJawGripper) return false;

2. Make the OverBending waypoint editable — Src/Core/BCell/BCellUtil.cs, CanWaypoint:

  • B1 (step-level): EBPhase.Bending → EBPhase.Bending or EBPhase.OverBending (editable when noSupport || RegripDuringBend).
  • B2: remove EBPhase.OverBending from the sFixed set used by the phase-level CanWaypoint(EBPhase).

3. Regenerate 9 TData/Fanuc/*.txt goldens (add OverBending + Decompress lines).

Correctness analysis

Change 1 — NeedsOverbending (verified correct)

  • Monotonic for non-BendMaster: the PR only removes a return false from the non-BM path (the base-plane check is now BendMaster-gated), so NeedsOverbending can only flip false→true, never true→false. It cannot remove overbending anywhere.
  • BendMaster is byte-identical: both checks (base-plane, then NoSupport/RegripDuringBend) are retained in the same order, now inside if (IsBendMaster). BM5000Tech is 5-axis (Is6Axis=false), so the Is6Axis && !jaw guard never fires for BendMaster.
  • Affected set: IsBendMaster = NCName contains BM60/BM150. Only BCFanucTech and BC7000Tech are Is6Axis=true. Given the Is6Axis && !jaw guard, the newly-affected cells are exactly non-BM 6-axis + jaw = Fanuc-jaw and Cell7000-jaw.
  • Fix direction matches the bug: Y > 0 = "base plane inside machine" previously forced no-overbending; removing that suppression for non-BM makes overbending appear — exactly the reported defect.
  • No downstream regression: every NeedsOverbending consumer gates coherently. Notably BendOpCrash.cs:336 now runs the OverBending crash test (it was skipped only when !NeedsOverbending), so the new overbend poses get collision coverage rather than bypassing it. The overbend pose machinery (SimSpringbackLie) is the same already exercised by BendMaster/Cell7000.

Change 2 — CanWaypoint (verified correct; B2 is load-bearing)

  • B2 is not cosmetic — it is required. BRobotPose.WithWaypoint(wp) (line 90) gates whether the edited position (XSeed/Axes/WCS) is applied on the phase-level wp.Phase.CanWaypoint(). Without removing OverBending from sFixed, an edited OverBending waypoint would be saved but silently ignored.
  • B1+B2 make OverBending behave exactly like Bending in both CanWaypoint overloads — a clean, principled symmetry. sFixed has one reader (the phase-level overload), whose only direct external caller is WithWaypoint.
  • Crash-safe: a waypoint edit maps to RPath (BendOpStatus.cs), which clears all crash flags → full re-evaluation, identical to a Bending edit.

Test / golden regeneration is provably complete

  • The change is monotonic, so any golden already showing OverBending on all its bends cannot change.
  • Cell7000 (the other non-BM 6-axis family) is unaffected: all 8 TData/Cell7K/*.txt already have Bending == OverBending counts.
  • Fanuc completeness proven: the full set of Fanuc goldens with a Bending > OverBending gap = the 9 regenerated files ∪ C44659.txt. All 9 were regenerated. C44659.txt is correctly omitted: BEND 1 is a hem prebend and BEND 2 a hem, both rejected by the raw Kind != EBendKind.AirBend && !IsFlatPreBend test at BendOp.cs:1818 (which fires before the base-plane check), and BEND 3 already overbends. (The all-zero/ImpossibleIK pose in BEND 1 was a red herring — emission still requires NeedsOverbending=true.)
  • Goldens are internally consistent: each changed bend gets an OverBending line (pose == the new Bending pose — arm holds while the ram over-pushes) plus a Decompress line whose pose == the old CatchAfterBend pose (a clean springback-to-nominal story). Surrounding phases and phase order are otherwise stable. The degenerate C47779 BEND 3 correctly gets all-zero OverBending/Decompress.
  • Test-ID mapping confirmed: 2336→6Bend_1(+flip), 2346→1Bend_8(+flip), 2353→3Bend_1, 2371→C47779(+flip), 2359→SimpleGridRight, 2360→SimpleGridLeft = exactly the 9 changed files.

Note: no GitHub CI is configured on this repo, so completeness was reasoned from source + goldens (monotonicity + exhaustive gap sweep), not from a green check.

Findings (severity-ranked)

# Sev Area Finding
1 minor maintainability // … Needs investigation. comment (BendOp.cs:1821). It openly admits the reason BendMaster still skips overbending when the base plane is inside the machine is not understood — the fix removes the suppression for non-BM but leaves it (unexplained) for BM. Not dead code, so not a G011 violation, but "Needs investigation" is a vague-TODO smell. Replace with a tracked case/issue reference so the asymmetry is resolved rather than left indefinitely.
2 minor domain sign-off Physical desirability is a bend-expert call. The code is correct and the 9 regenerated goldens are exactly the base-plane-inside cases now being overbent (crash-checked). But whether enabling overbending in this geometry produces the desired, collision-free motion for Fanuc-jaw is a domain judgment — worth an explicit OK from the bend lead (Arvind/tarydon), since the retained comment shows the original suppression's rationale is unknown.
3 minor test-coverage No dedicated regression test for the new OverBending waypoint-editability path (B1+B2 → WithWaypoint). The goldens verify overbend generation, not the edit-and-apply path. Low priority (symmetric with shipping Bending editability), but PR #3649 added exactly such a test (Test16) for its analogous waypoint fix — consider mirroring that here.
4 nit commit hygiene Squash before merge. Commit 1's abandoned BendLie/pose-sheet-interpolation approach (3 files) was fully reverted in commit 4 with zero net residue — no need for it in main's history.
5 nit pre-existing A stale OverBending waypoint could survive a NoSupport → supported routing change (the Bend setter doesn't clear mUWaypoints) and be applied by WithWaypoint while the UI shows it read-only. Not introduced by this PR — Bending already behaves identically, and the pose is re-crash-checked. Noted only for completeness.

Praise

  • Minimal, monotonic fix; BendMaster path byte-identical.
  • Sharp insight that B2 is load-bearing (removing from sFixed is required for edits to apply, not just tidy-up), and that B1+B2 make OverBending a clean mirror of Bending.
  • Golden regeneration is exact and complete, and enabling overbending brings it under crash coverage rather than bypassing it.

Guideline compliance (G001–G035)

Clean. Both files are namespace Flux; (not Flux.API) and the touched members aren't public API → no APIGen/.gen.cs regeneration (G026 N/A). No new files → no copyright/nullable header rules. No translation files. Scope is coherent (enabling overbending in more cases naturally requires those waypoints to be editable). Documented false-positive traps (G009 banner widths, G013 method-group) deliberately not raised.

Bottom line

Correct, minimal, well-scoped, with a provably complete golden regeneration. Safe to merge after: (1) replacing Needs investigation. with a tracked case reference, (2) a domain OK from the bend lead on overbending-when-base-plane-inside for Fanuc-jaw, and (3) squashing the abandoned-approach commits. A small waypoint-editability regression test would be a nice-to-have.
