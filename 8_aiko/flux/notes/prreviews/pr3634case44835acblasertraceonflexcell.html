PR #3634 — Case 44835: ACB Laser trace is not shown in simulation on FlexCell

PR #3634 — Case 44835: ACB Laser trace is not shown in simulation on FlexCell

  • Repo/PR: metamation/Flux #3634 · branch Case.44835 → main · state OPEN
  • Author: florian (EngertFlo) · Date reviewed: 2026-07-20
  • Size: +157 / −10, 8 files (3 source + 2 regenerated goldens + 2 new test-data files + 1 test) · 6 commits · Label: bend
  • Verdict: ✅ Approve with follow-ups — no blockers, no correctness bugs. Root-cause-accurate fix. Two real gates before merge: (1) run the full golden suite (no CI), (2) domain/visual sign-off on an actual FlexCell part.

Reviewed with a deep manual source pass plus a 7-agent adversarial verification workflow (6 dimension attackers + 1 completeness critic, each independently re-deriving from source and trying to falsify). All 7 returned CONFIRMED_CORRECT; every finding below is a coverage/process/tech-debt item, not a defect.

What the PR does

Fixes the ACB laser sensor trace not appearing in the FlexCell bend simulation when ACB runs in ACBSmart (Corrected) mode. Three source changes + test artifacts.

Root cause (verified)

On FlexCell, ACB Identify mode is not allowed — BendOp.cs BadACBModes sets dict[EACBMode.Identify] = 18508 // Not supported for FlexCell. FlexCell ACB laser therefore always runs in Corrected (ACBSmart) mode. The old code gated the PressHold phase (and hence the laser measurement/trace) on ACBMode == EACBMode.Identify, so on FlexCell it was never added → no press-hold → no laser trace. The fix keys on laser activity instead of the specific mode.

Change 1 — Src/Core/BCell/Ops/BStepComputer.cs (PinchToBend)

bool isLaserActive = mOp.UsingACBLaser && mOp.ACB.IsLaserActive;   // new, top of method
...
// supported-overbend branch: gate broadened
- if (mOp.UsingACBLaser && mOp.ACBMode == EACBMode.Identify)
-    Add (EBPhase.PressHold, RPOverBend.Clone ());
+ if (isLaserActive) Add (EBPhase.PressHold, RPOverBend.Clone ());
...
// NoSupport jaw release-and-retake branch (both overbend + non-overbend sub-branches):
  Add (EBPhase.CatchAfterBend, poses[^n], speed, catchT);
+ if (isLaserActive) Add (EBPhase.PressHold, poses[^n].Clone ());   // new

Change 2 — Src/Core/BCell/Ops/RPathPlanner.cs (GetRegripAtBendingJawSteps, regrip-during-bend)

bool isLaserActive = op.UsingACBLaser && op.ACB.IsLaserActive;      // new
...
  Add2 (EBPhase.RegripGrip, poses[^n], speed, regripT);
+ if (isLaserActive) Add2 (EBPhase.PressHold, poses[^n].Clone ());  // new (before Decompress in the overbend branch)

Change 3 — Src/Core/Bend/Ops/BendOpStep.cs (ACBLaserPosEx, laser sensor geometry per phase)

  • FootSwitch/MutePoint case now also covers the two pre-bend regrip phases: phase is GaugeRetract or RegripRetract or RegripSwivel1 or Bending.
  • New block — hold the laser at Measure1 through the regrip-swivel: 
    if (!flat && (phase is CatchAfterBend or RegripGrip || phase >= RegripSwivel1 && phase <= RegripSwivel9))
   sindex = eindex = ELCBPhase.Measure1;
  • Release-phase fix — for robotic, release the laser from the final measurement at UpOpen when there is no overbending: 
    - phase == (op.Tech.Robotic ? (op.NextStage is BCRegrip {Flavor: PostBend} ? UpOpen : Decompress) : UpRelease)
+ phase == (op.Tech.Robotic ? (!op.NeedsOverbending || op.NextStage is BCRegrip {Flavor: PostBend} ? UpOpen : Decompress) : UpRelease)

Test artifacts

  • New: TData/Fanuc/C44835.fx (+.txt) — Fanuc10, HasACBLaser=true, 2 bends ACB=Laser Mode=Corrected; dump shows the new PressHold pose after CatchAfterBend in both bends.
  • New: Test/Bend/Fanuc/FanucBase.cs Test21 [Test (18532, "C44835: …ACBSmart")].
  • Regenerated (incidental, non-laser): TData/Cell/2021/C30886.txt (Test 4920, BM150) and TData/Cell/Gripper/Standard_Serviceklappe_BM60TM_Multi_S.txt (Test 2208, BM60).

Correctness analysis (the deep part)

The semantic change is exactly right — and null-safe

IsLaserActive (BendACB.cs:267) = System == Laser && Mode.IsLaserOn(), and IsLaserOn() (BendExtensions.cs:129) = mode is Identify or Corrected. So the gate widens from Identify-only to Identify + Corrected (ACBSmart) — precisely the FlexCell case. Learned/LearnSB correctly stay excluded (they copy a reference bend, no live measurement). UsingACBLaser => mACB is { System: Laser } (BendOp.cs:889) is true only when mACB is non-null, && short-circuits, and ACB is a pure get => mACB — so mOp.ACB.IsLaserActive is never dereferenced on null. Every PressHold consumer (duration 2*Measurements at BendOpStep.cs:49; geometry at :139/:153) keys on Laser/IsLaserActive, both true for Corrected, so a Corrected press-hold behaves identically to the Identify one that already shipped.

The release-phase fix targets a real dead branch

Decompress is emitted only when overbending (both PinchToBend and GetRegripAtBendingJawSteps). So for a non-overbend robotic laser bend the old phase == Decompress release condition never matched → the laser stayed pinned at the last measurement position through extraction. The fix routes release to UpOpen when !NeedsOverbending. Verified safe on all axes:

  • UpOpen always exists on every non-overbend robotic path — BendToFinish (BStepComputer.cs:465) emits it unconditionally and is the terminal step-producer (reached via Compute(), the regrip-during-bend chain RPathPlanner.cs:140/230, and BRegripAux.cs:591), always keeping Op = the laser op so ACBLaserPos fires.
  • Overbend path unchanged — when NeedsOverbending is true the ternary collapses to the exact old NextStage is PostBend ? UpOpen : Decompress.
  • Precedence — is > || > ?:, so it parses as (!NeedsOverbending || NextStage is …) ? UpOpen : Decompress.

Known limitation (author-flagged; validated → deferred to Case 48031): this fix covers only the release transition. For a post-bend regrip the release is pinned to UpOpen, and every extraction phase after it — PostBendSafe plus all extraction-strategy phases (OutSlide/OutLower/OutRotate*/OutTallFlange*/SideSlide) — is unhandled in ACBLaserPosEx (none are named there), so the laser defaults to Release with no strategy awareness → the ACB-laser trace is wrong during those phases. Pre-existing, machine-agnostic (the extraction default path isn't IsBendMaster-gated → affects BendMaster too), and untouched by this PR — the postbend → UpOpen branch is byte-identical before/after #3634 (the added !NeedsOverbending || only alters the non-postbend branch). See finding #6.

The regrip-swivel block is correct (with one pre-existing, out-of-scope gap)

Precedence groups as (phase is CatchAfterBend or RegripGrip) || (phase >= RegripSwivel1 && phase <= RegripSwivel9). Enum ranges check out — RegripSwivel1..9 = 310..318, RegripSwivelNext (319) correctly excluded (only between-bend regrips use it). RegripRetract/RegripSwivel1 are always flat (they're in sBeforeBending → BendLie returns 0), so they're handled by the switch's flat→Measure1 path and the new !flat block never touches them; RegripSwivel2..9/CatchAfterBend/RegripGrip are always non-flat → the new block drives them to Measure1, and no later block re-writes them. Adding RegripRetract/RegripSwivel1 to MutePoint/FootSwitch brings those into line with the default StepChange case (not an asymmetry). Gap: the whole regrip-swivel block lives in the PrepStrategy == None branch, so an 8000-series machine (PrepStrategy != None, e.g. TruBend 8000/B36) doing a during-bend regrip with the laser would leave swivel phases at Release. Pre-existing, out of scope (the test machine FANUC10 is PrepStrategy == None); likely unreachable, but worth a tracked note.

Golden regeneration is provably complete for the laser change

The two new PressHold paths fire only when isLaserActive and the op takes the NoSupport-jaw or regrip-during-bend branch (signature: a RegripSwivel1 line immediately followed by Bending, or a CatchAfterBend). A full-TData cross-check finds zero files that contain both ACB=Laser and either signature. All 57 existing robotic laser bends are Mode=Identify (37) or Learned (20) — none Corrected, none overbend — so the gate broadening changes no existing golden. ACBLaserPosEx only touches ACBLaserPos, which is not written to any dump. So the only laser golden needed is the new C44835.

The two incidental non-laser goldens are safe — but not caused by this PR's logic

C30886 (BM150) and the Serviceklappe gripper (BM60) are both NoACB bends on machines that physically carry the laser. None of the three code changes can affect a non-laser part (all PressHold adds are isLaserActive-gated; ACBLaserPosEx returns early for op.ACB == null). What actually changed them: the new unconditional mOp.UsingACBLaser && mOp.ACB.IsLaserActive read at the top of PinchToBend (and in GetRegripAtBendingJawSteps) accesses the ACBSettings.System/Mode getters, whose stale-reset + Dirty cascade (BendACB.cs:224-234/407-414) forces re-derivation of ACB-related caches that were serialized stale in the old .fx files. Why it's safe: for a NoACB bend the simulator always models the laser at the parked Release position — BendOpStep.cs:153 if (!acb.IsLaserActive && !isMoving) sindex = eindex = Release; — and that line is unchanged. So the laser-box geometry the collision test sees is byte-identical before and after; no crash is newly hidden and no clearance is newly dropped. The fresh recompute is therefore the source of truth: the dropped ACBLaserCrash flag and the 12 mm smaller extraction lift were stale FX state, exactly as the author suspected. (Likely drift from Case 47639 / #3546 "reduce retract distance on release-and-regrip", which never regenerated C30886.)

Findings (severity-ranked)

# Sev Area Finding
1 minor merge gate / hidden drift Run the full cell+fanuc golden suite before merge. The new unconditional isLaserActive read has proven side effects on non-laser goldens (C30886, Serviceklappe re-derived from stale FX caches). With no CI on this repo, there is no green check that some other cell golden on an ACB-laser-carrying BendMaster with stale FX state won't also silently shift. The completeness reasoning says the laser change is clean, but the incidental-drift channel means only a full-suite regen closes it. Treat as a pre-merge gate, not a note.
2 minor test-coverage The fix's core is essentially untested by goldens. The user-visible bug is 3D laser-trace geometry, and ACBLaserPos/ACBLaserPosEx output is never dumped (grep LaserPos over TData = 0). C44835.txt only proves a PressHold step is emitted for the Fanuc overbend release-and-retake path. Unverified by any golden: the RPathPlanner regrip-during-bend PressHold, the non-overbend CatchAfterBend+PressHold branch (both C44835 bends are overbend), and all ACBLaserPosEx geometry. Consider adding a during-bend-regrip laser part + a non-overbend robotic-laser part, and require a manual visual check on an actual FlexCell part.
3 minor domain sign-off Bend-expert OK on the robot motion + machine fidelity. Inserting PressHold after CatchAfterBend/RegripGrip (holding at the regrip pose while the laser cycles measurements) is a physical-motion judgment for ACBSmart — worth an explicit OK from the bend lead (Arvind / tarydon). Also: the ticket is FlexCell, but the repro forces BendMachine.Get(FANUC10).HasACBLaser = true rather than a FlexCell profile — it exercises the code path but not the named machine.
4 minor tech-debt Incidental goldens fix a symptom, not the root cause. The two non-laser golden corrections come from an evaluation-order side effect re-deriving stale FX caches, not from addressing the load-time invalidation gap (FX keeps ACB-derived caches a fresh part wouldn't). The corrected goldens now encode a dependence on the isLaserActive read staying at the top of PinchToBend; a future refactor that moves/short-circuits it could silently revert both. Worth a tracked case for the load-time invalidation.
5 minor scope (pre-existing) 8000-series regrip-swivel laser gap. The new regrip-swivel→Measure1 handling is only in the PrepStrategy == None branch (BendOpStep.cs:89-91); a PrepStrategy != None machine (8000/B36) doing a during-bend regrip with the laser would leave those phases at Release. Pre-existing and out of this PR's FlexCell scope — note only.
6 minor scope (pre-existing → C48031) Post-bend-regrip extraction-phase ACB laser position is wrong (author-flagged; validated). For a post-bend regrip the release is pinned to UpOpen (BendOpStep.cs:147) and every extraction phase after it — PostBendSafe + all extraction-strategy phases (OutSlide/OutLower/OutRotate*/OutTallFlange*/SideSlide) — is unhandled in ACBLaserPosEx, so the laser defaults to Release with no strategy awareness. Untouched by this PR (the postbend → UpOpen branch is byte-identical before/after #3634; #3634's laser edits are all during-bend/no-support phases) and machine-agnostic (extraction default isn't IsBendMaster-gated → BendMaster too). Correctly deferred to Case 48031.
7 nit robustness New gate no longer forces ComputeACBMode(). The old ACBMode read triggered it; ACB.IsLaserActive reads raw Mode/System. If the ACB were Dirty at step-compute time, Mode→Unknown→PressHold silently skipped. Not a real defect (ACB is cleaned upstream by BendToolerRefine; C44835 confirms emission), but correctness now depends on the ACB being non-dirty by PinchToBend.
8 nit G022 Test21 mutates the shared cached BendMachine.Get(FANUC10).HasACBLaser via try/finally with no [SkipIfParallel]/TmpMachine. Real risk ≈ zero — parallelism is process-per-fixture (Test/Parallel.cs) with a per-process machine cache, sequential in-fixture, finally-restore — and it matches the established convention (BendACB.cs Test7, Test9→CheckACBGlob(83)).
9 nit dead-but-harmless RegripSwivel1 inside the !flat range (BendOpStep.cs:90) never executes (always flat → the block could start at RegripSwivel2). Also _BDC + during-bend robotic regrip would force CatchAfterBend/RegripGrip to Measure1 before the _BDC insert — premature, but an implausible/untested combination and not dumped.
10 nit commit hygiene 6 commits incl. a merge, "Fix spelling", "Remove redundant variable". Squash/rebase-merge rather than carry the merge commit.

Praise

  • Root-cause-accurate: keys on laser activity (IsLaserActive) rather than a specific mode, correctly capturing FlexCell's Corrected-only ACBSmart — instead of special-casing FlexCell.
  • Clean, null-safe gate reused consistently across all three paths, with correct .Clone() to avoid the shared-pose mutation trap (Add/Add2 mutate Speed/Tolerance).
  • Honest dev note flagging the two unexplained goldens — the instinct ("old state in the FX") was correct; the mechanism is a stale-cache re-derivation validated against the unchanged parked-laser geometry (BendOpStep.cs:153).

Guideline compliance (G001–G035)

Clean. G005 ✓ ("C44835:" prefix allowed; not "Case"). G033 — test ID 18532 is unique on main, but ⚠️ collides cross-branch with open PR #3597 (FanucUI.cs Test15, also 18532): whichever merges second trips the duplicate-ID guard. One of the two must be renumbered. See [[PR-3597 Case 47665 - Multi-pickup per-corner error handling]]. G022 — nit only (see #7). Source hunks are style-clean; mOp.UsingACBLaser before mOp.ACB.IsLaserActive is a required null-guard, not a redundant lambda. All touched types are internal in namespace Flux (not Flux.API) → no APIGen/.gen.cs (G026 N/A). New test-data files are .fx/.txt (not .cs) → G012/G014 N/A; the one new .cs is a test method, not a file. No translation files (G025/G033). Documented false-positive traps (G009 banner widths by eye, G013 method-group with optional/params) deliberately not raised.

ReFlux companion: not required — no machine/3D-model, tool-catalog, TBS, WIBU, or flavor changes (only bend-sim code + test data). See [[ReFlux — Companion Repo Checklist]].

Bottom line

Correct, minimal, root-cause-accurate, and — for the laser change — provably complete on goldens. Safe to merge after: (1) a full golden-suite run to confirm no other stale-FX drift (no CI), (2) a domain + visual OK on an actual FlexCell ACBSmart part (the trace geometry the case is about is not captured by any dump), and (3) squashing the commits. The incidental non-laser goldens are safe corrections of stale FX state; documenting that (and optionally tracking the load-time invalidation gap) would close the loop.
