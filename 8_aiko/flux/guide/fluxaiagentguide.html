FluxAIAgentGuide

product: flux org: metamation tags: [metamation, knowledge-base, ai-agents, flux] type: project-guide project: Flux repo: metamation/Flux owner: aiko.radlingmayr updated: 2026-07-13

🔧 Flux — AI Agent Guide

[!abstract] Orientation Flux is Metamation's sheet-metal bending CAM application for TRUMPF press brakes: it imports part geometry, tools up the part, computes the bend sequence and gripper/tooling setup, simulates it, and generates machine code (DLD / NC). It is a large C# + WPF codebase (~380k LOC) with a small native C++ component. Repo: metamation/Flux on GitHub.

This page orients an AI agent: where code lives, how to build & test, the domain vocabulary, and which in-repo files are the source of truth. For review expectations, read [[Flux — Code Review Guidelines]] first.

🗂️ Repository layout

Folder Contents
Src/ All product source + Flux.sln (the main solution)
Test/ The test suite (Flux.Test.csproj) — grouped 2D/, 3D/, Bend/, CAM/, Cut/
Tools/ Dev tools: APIGen, XLate (translations), FDoc (docs), FShip, Sim5K/7K, etc.
SDK/ The FLUXSDK ship project
Data/, TData/ Runtime data / test data (machine models, tool catalogs, .geo/.fx fixtures)
Notes/ Developer & technical notes (FTex .ftx). Converted into the KB → [[Flux Notes]] (kept as legacy reference under Flux/Legacy/; read there, not the raw .ftx).
Doc/ Assets + config for the generated API reference (see below) — Doc/Img/ images referenced by source XML comments, Doc/Gen/API.fdoc (FDoc config), Doc/Misc/nextid.txt (translation-ID counter)
Resources/, Help/, Wad/, Lib/ Assets, help, packaged content, libs

[!tip] The X:/ convention The team maps the repo checkout to drive X:/. The in-repo instruction files reference paths like @X:\.github\instructions\…. When you see X:/… in docs or comments, it means "repo root". (Locally this checkout is at ~/dev/trumpf/Flux.)

🧱 Solution & projects (Src/Flux.sln)

Dependency direction (arrows = "depends on"): Core → Base, UI → Base, Core, API → Base, Core, UI, App → API, UI, Core, Base, Console → UI.

Project ~LOC Role
Flux.Base 50k Foundation: geometry, math, utilities — also currently embeds the Lux/OpenGL render engine and a WPF toolkit.
Flux.Core 206k The domain heart — bending/tooling/simulation/codegen logic — plus ViewModels. Most work happens here.
Flux.UI 62k WPF views/controls.
Flux.API 29k The public API external clients depend on (e.g. Praxis, Boost) + the FLUXSDK scaffold. Guard its surface carefully.
Flux.App 30k The WPF desktop shell (windows, ribbons, dialogs).
Flux.Console 3k CLI entry point.
Flux.Migrate — Data/settings migration.
Hula (Hula64.vcxproj) — Native C++ component (interop DLL).

Deep architecture (dependency graph, sizes, the WPF-decoupling plan) lives in [[WPF_DECOUPLING|the WPF decoupling spec]] in this vault.

🛠️ Build & test

  • Build: open Src/Flux.sln in Visual Studio (the code targets net10.0-windows, uses WPF and WinForms). Flux.App is the runnable desktop app; Flux.Console is the CLI.
  • CI/CD: builds run in Azure DevOps (TrumpfCorp/Flux), which mounts the GitHub checkout to X: — a SonarCloud analysis on every push to main, and a manual SBOM→DependencyTrack pipeline. Details: [[DevOps]].
  • Test: the suite is Test/Flux.Test.csproj, built on a custom test framework ("Flit", see Test/Flit.cs / Test/Assert.cs) rather than plain NUnit/xUnit.
    • Tests use numeric IDs and attributes: [TestFixture (1400, "…", Module = "Bend")] and [Test (14020, "C39942: …")]. The Cxxxxx in a test name is the Fogbugz case number.
    • Custom asserts exist: Assert.AreBitmapsEqual (side-by-side image diff on failure), Assert.AreTextFilesEqual. Prefer these over hand-rolled comparisons.
    • [SkipIfParallel] marks tests that touch shared resources.

[!danger] Rule Number 0 — run the ENTIRE suite before you push The lead reviewer's single most repeated demand: run all the tests locally and have none failing before pushing or opening a PR, no matter how trivial the change. See [[Flux — Code Review Guidelines#⭐ If you remember nothing else]].

📁 File types & generated code

Thing Meaning
.fx Flux's native save file for a part/job. Has a build number; loading an old build triggers version-gated PostLoad migration (clear/repurpose bits for old files).
.geo Geometry input file (part outline).
DLD / NC Generated machine code output.
*.gen.cs Generated C# — produced by the APIGen tool from a manifest. Do not hand-edit; re-run APIGen after API changes.
lang .txt + IDs Translation strings. Never edit an existing English string in place — delete it and add a new ID (counter in Doc/Misc/nextid.txt) so all language files re-propagate.

🧩 Domain vocabulary (quick glossary)

Term Meaning
Part The sheet-metal workpiece being manufactured.
Bend / Fold A single bending operation. FoldOp (Src/Core/Fold/) models one.
BendSetup A tooling/station configuration for bending a part (Src/Core/Bend/BendSetup.cs).
Station A position along the press-brake tooling where a bend is performed.
Tooling The punches/dies fitted to stations; "tooling up" a part = assigning tools.
Gripper The robot/manipulator that holds and repositions the part between bends.
Pline A polyline — core 2D geometry primitive (Src/API/Gen/Geometry.gen.cs).
DLD The generated code/output describing the full bending program.
Setup split Splitting a bend sequence across multiple machine setups when limits are hit.

Match this vocabulary in code and comments — the reviewer flags terms that drift from Flux's established names (design principle D019).

📚 Documentation & notes

Flux has several bodies of documentation. Prefer the KB copy where one exists.

  • Developer & technical notes (legacy) → [[Flux Notes]] under Flux/Legacy/. The team's older .ftx notes from the repo's Notes/ folder — dev style guide, build steps, machine-ID schemes, file formats (Au/Vdwg/Curl/DXF), the Hex language, and the Boost/MetaCAM interfaces — converted to Markdown. Kept as legacy reference; read them in the KB, not the raw .ftx.
  • CI / build & supply-chain → [[DevOps]] — the SonarCloud CI and SBOM→DependencyTrack pipelines (and why the codebase uses X:/ paths).
  • Security / CRA → [[CRA-Assessment-Flux]] (Flux/CRA/) — the IEC 62443 / EU Cyber Resilience Act quick-assessment (release-blocking findings with file:line evidence) plus the PROSEC spec PDFs under Flux/CRA/Specs/. Consult before shipping security-relevant changes.
  • Architecture / refactor specs → [[WPF_DECOUPLING]] (Flux/Refactor/) — the deep spec for making Base/Core/API headless and replacing the WPF app + OpenGL/Lux with a web UI.
  • API reference (classes/methods of Flux.API) → generated, not in the KB. It is produced by the FDoc tool (Tools/FDoc) from Flux.API.xml (compiler-emitted XML doc comments) plus the ~250 images in Doc/Img/ that those comments reference. Because the text lives in source XML comments and the output is regenerated, the API docs stay in the repo/build; the Doc/Img/ images were intentionally not copied into the KB (they'd be context-free without the generated text). To view it, run FDoc against a built Flux.API.dll/.xml (config: Doc/Gen/API.fdoc).

📌 Authoritative in-repo instruction files (source of truth)

Treat these as operative rules — Copilot and Claude load them automatically:

  • .github/copilot-instructions.md — entry point (loads the two below).
  • .github/instructions/pr-review-guidelines.instructions.md — G001–G035, mechanical/style rules synthesized from 5,013 PR comments.
  • .github/instructions/design-principles.instructions.md — D001–D025, design/judgement rules synthesized from PR reviews.
  • .github/USAGE-INFO.md — how to enable the instruction files in Visual Studio / VS Code.
  • .claude/CLAUDE.md — project rules for Claude (review process, commit rules, known false positives).

These G/D rules are copied into the KB by theme — each page under Flux/Review/ opens with its 📘 Official repo rules section (verbatim, with a synced-commit banner) followed by Arvind's mined additions, so an agent gets everything for a theme in one file. The repo copies remain the source of truth. Start at [[Flux — Code Review Guidelines]] (the index).
